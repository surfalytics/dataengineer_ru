# Глоссарий книги The DataOps Way to Data Quality and Data Observability

Одинаковые формы для перевода и конспекта. Варианты для согласования вынесены в план. Написание названий продуктов, команд и идентификаторов сохраняем по оригиналу.

| English | Как пишем | Не писать | Пояснение |
|---|---|---|---|
| DataOps | `DataOps` | датаопс | Подход к работе команды с данными. Объединяет короткие циклы разработки, автоматические проверки и контроль качества в ходе обработки. |
| data quality | качество данных | — | Насколько данные подходят для конкретной задачи. Как название одного из четырёх процессов в первой главе обозначает работу над качеством критически важных источников. |
| data quality testing | проверка качества данных | — | Выполнение тестов, которые сравнивают фактические свойства данных с ожиданиями. Отдельное исполняемое правило можно называть тестом. |
| data observability | наблюдаемость данных | обсервабилити | Возможность судить о состоянии данных по наблюдаемым признакам. В первой главе авторы рассматривают массовую проверку таблиц на аномалии. DataOps Observability с прописных букв обозначает продукт. |
| data monitoring | мониторинг данных | — | Команда регулярно измеряет выбранные показатели и следит за их изменениями. |
| data production | обработка данных в рабочей среде | — | Регулярное получение, преобразование и доставка данных пользователям. |
| deployment to production | развёртывание в рабочей среде | — | Команда выпускает новую версию кода. Сюда относятся проверки регрессий и последствий изменений перед выпуском. |
| Data Journey Quality | качество данных на этапах обработки | — | Авторское название проверок на пути от входных данных до итогового продукта. Показывает, успевает ли команда остановить ошибку до следующего шага. |
| data downtime | период непригодности данных | даунтайм данных | В этот период данные отсутствуют, ошибочны или по другой причине непригодны для использования, даже если хранилище доступно. |
| data pipeline | `pipeline` | пайплайн | Цепочка шагов получения и преобразования данных. Написание принято в инженерных конспектах портала. |
| test coverage | покрытие тестами | — | Какие таблицы, поля, этапы или риски проверяются. Основание расчёта указываем по контексту. |
| data contract | контракт данных | — | Соглашение поставщика и потребителя о структуре, содержании, сроках и порядке изменений. |
| tripwire | блокирующая проверка | растяжка | При нарушении условия проверка останавливает дальнейшую обработку данных. |
| shift-left | `shift-left` | шифт-лефт | Проверять раньше, ближе к месту появления ошибки. В разработке это также означает проверку до выпуска изменений. |
| shift-down | `shift-down` | шифт-даун | Выполнять проверки на уровне вычислительной инфраструктуры или хранилища. |
| data lineage | `lineage` | линидж | Происхождение данных и зависимости между источниками, преобразованиями и результатами. |
| process lineage | история выполнения процесса | — | Какой запуск, шаг или инструмент произвёл результат. Указываем время и связь с данными, когда они известны. |
| process guardianship | сопровождение общей бизнес-логики | — | Команда сводит определения и расчёты в одно место, проверяет и поддерживает их для всех потребителей. |
| impact dimensions | категории воздействия ошибок | — | Авторы группируют сбои по тому, что они означают для команды и потребителя. В их схеме четыре категории. |
| reliability | надёжность | — | В классификации авторов показывает, доставляет ли система ожидаемые данные. |
| conformance | соответствие правилам | — | Проверка значений, форматов и диапазонов по известным ограничениям. |
| regularity | устойчивость закономерностей | — | Проверка того, следуют ли данные привычным статистическим закономерностям. |
| usability | пригодность к использованию | — | Насколько легко потребитель может применить данные в своей работе. |
| fit for purpose | пригодный для конкретной задачи | — | Качество оценивают с учётом назначения данных. |
| freshness | свежесть | — | Как давно обновились данные. |
| timeliness | своевременность | — | Поступили ли данные к согласованному сроку. |
| completeness | полнота | — | Присутствуют ли все необходимые записи и значения. |
| accuracy | точность | — | Насколько значения отражают фактическое положение дел. |
| consistency | согласованность | неконсистентность | Совместимы ли значения и определения между источниками или в пределах набора данных. |
| validity | допустимость значений | — | Укладываются ли значения в заданные форматы и ограничения. |
| uniqueness | уникальность | — | Отсутствуют ли повторы там, где ожидается единственное значение. |
| data profiling | профилирование данных | — | Вычисление статистики и изучение структуры и значений набора данных. |
| alert fatigue | усталость от оповещений | — | При избытке сигналов люди перестают реагировать в том числе на существенные сбои. |
| false positive | ложное срабатывание | — | Проверка сигнализировала о проблеме, хотя данные удовлетворяли требованиям. |
| false negative | пропуск проблемы | — | Дефект остался незамеченным при проверке. |
| data trust | доверие к данным | — | Насколько потребитель уверен, что может опираться на результат. |
| data product | продукт данных | — | Результат, который команда поставляет определённым потребителям и поддерживает с учётом их задач. |
| medallion architecture | медальонная архитектура | — | Архитектура с последовательными слоями данных, обычно bronze, silver и gold. Имена объектов в коде сохраняем. |
| FITT | `FITT` | — | Functional, Idempotent, Tested, Two-stage. Авторы так называют архитектуру с функциональными и идемпотентными преобразованиями, тестами и двумя этапами обработки. |
| SLA | `SLA` | — | Соглашение об уровне обслуживания, например о сроке поставки данных. |
| data quality tax | «налог на качество данных» | — | Авторская метафора. Конкретный вид затрат уточняем по контексту. |
| DataKitchen / DataOps TestGen / DataOps Observability | DataKitchen / DataOps TestGen / DataOps Observability | — | Компания и названия её продуктов. Сокращённое TestGen сохраняем, если его используют авторы. |
| regression test | регрессионный тест | — | Проверяет, сохранилось ли ранее работавшее поведение после изменения. |
| data diff | сравнение данных | — | Сопоставление версий набора данных. |
| business metric | бизнес-показатель | — | Числовая характеристика процесса, значимая для бизнеса. |
| bronze layer | бронзовый слой | — | Слой исходных поставок в медальонной архитектуре. |
| generic test | параметризованный тест | — | Повторно используемая проверка dbt с параметрами. |
| schema registry | реестр схем | — | Сервис хранения и согласования схем сообщений. |
| baseline | исходный уровень | — | Значение или период для сравнения с последующим состоянием. |
| FMEA | FMEA | — | Анализ видов и последствий потенциальных отказов. |
| business rule | бизнес-правило | — | Проверяемое ограничение, определяемое предметной областью. |
| runtime lineage | происхождение на уровне процессов | — | Связь данных с фактическими запусками. |
| ODCS | ODCS | — | Открытый стандарт описания контрактов данных. |
| zero-copy clone | копия без физического дублирования | — | Отдельное представление набора, использующее физические данные оригинала. |
| OneLake | OneLake | — | Единое хранилище данных в Microsoft Fabric. |
| volume | объём | — | Количество записей или размер данных в выбранном окне. |
| critical data element | критически важный элемент данных | — | Поле, состояние которого существенно для деятельности или обязательств. |
| suppression window | окно подавления | — | Период, в который известное событие не требует уведомления. |
| distribution drift | дрейф распределения | — | Изменение распределения признака относительно исторического поведения. |
| Databricks Asset Bundles | Databricks Asset Bundles | — | Формат описания и развёртывания ресурсов Databricks. |
