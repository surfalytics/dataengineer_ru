**DevOps**-принципы и практики широко применяются в Data Engineering и Data Analytics. Они упрощают управление данными, дают автоматизацию и масштабируемость.

DevOps и Data Engineering/Data Analytics тесно связаны. Есть даже специальный термин: **DataOps** — это
развитие DevOps для обработки данных.
Как и DevOps, DataOps включает разработку, автоматизацию и аналитику.

## DevOps и Data Engineering: общие принципы

Где Data Engineering пересекается с DevOps:

1. **Автоматизация и CI/CD**  
   Практики CI/CD автоматизируют загрузку данных, их трансформацию и доставку 
пользователям. Это упрощает разработку data pipelines.

2. **Инфраструктура как код (IaC)**  
   Kubernetes, Terraform и Ansible позволяют управлять инфраструктурой, которая работает с данными, в виде кода. Так 
инфраструктуру легко воспроизвести, ручных ошибок меньше, а масштабировать проще.

3. **Мониторинг и логирование**  
   Prometheus, Grafana и ELK помогают отслеживать производительность ETL-процессов, находить сбои и держать 
системы аналитики стабильными. Для этого нужно правильно настроить мониторинг и алерты.

## Что такое DataOps?

[DataOps](https://ru.wikipedia.org/wiki/DataOps) — это подход, основанный на принципах DevOps, но адаптированный для 
обработки данных. Его цель — ускорение разработки data pipelines, повышение качества данных и упрощение анализа. 
Основные аспекты DataOps включают:

1. **Гибкость и адаптивность**  
   CI/CD и IaC ускоряют обработку данных и разработку новых pipeline. Под изменения проще подстроиться: часто достаточно 
поменять конфигурационный файл.

2. **Качество данных и тестирование**  
   Автоматические тесты гарантируют, что изменения в pipeline не портят качество данных. Тесты проверяют, что данные 
корректны, без пропусков и согласованы между собой.

3. **Совместная работа**  
   DataOps объединяет аналитиков, инженеров данных и DevOps-специалистов. Разные команды работают вместе
и используют общие инструменты.

## Repository Templates

Repository Templates (шаблоны репозиториев) — это готовые структуры папок и файлов для нового проекта. С ними новый проект проще начать. В Data Engineering они особенно полезны: все проекты команды устроены одинаково и следуют лучшим практикам.

- [Cookiecutter](https://cookiecutter-data-science.drivendata.org/) — инструмент для создания шаблонов репозиториев. Ставится как Python-библиотека и создаёт репозиторий с готовой структурой файлов и папок.
- [Kedro](https://kedro.org/) — фреймворк для создания data pipelines, который включает в себя шаблоны репозиториев для разработки ETL-процессов. Создаёт проекты с готовой структурой и инструментами для разработки.

## Инструменты для работы с зависимостями

Зависимости — это внешние библиотеки, которые нужны проекту. Без управления зависимостями проект data engineering или ETL-pipeline не получится воспроизвести на другой машине.

- [Pyenv](https://github.com/pyenv/pyenv) — инструмент для управления версиями Python. Позволяет устанавливать и использовать разные версии Python на одной машине.
- [Poetry](https://python-poetry.org/) — инструмент для управления зависимостями в проектах на Python. Позволяет создавать виртуальные окружения, устанавливать и обновлять зависимости, а также управлять версиями пакетов.
- [Conda](https://docs.conda.io/en/latest/) — пакетный менеджер и система управления окружениями для Python и других языков программирования. Позволяет создавать виртуальные окружения, устанавливать пакеты и управлять их версиями.
- [Pipenv](https://pipenv.pypa.io/en/latest/) — инструмент для управления зависимостями в проектах на Python. С помощью Pipenv можно создавать виртуальные окружения, устанавливать и обновлять зависимости и управлять версиями пакетов.

## Formatters

Форматтеры кода — это инструменты, которые автоматически приводят код к единому стилю. Так код легче читать, и он соответствует принятым стандартам. В Data Engineering они помогают сохранять качество кода в data pipelines и аналитических скриптах.

- [Black](https://black.readthedocs.io/) — популярный форматтер для Python, который применяет строгие правила форматирования. С ним в команде нет споров о стиле, а код во всём проекте выглядит одинаково.
- [isort](https://pycqa.github.io/isort/) — инструмент для автоматической сортировки и форматирования импортов в Python-файлах. Делит импорты на группы и держит их в порядке по правилам PEP 8.
- Также полезно положить в корень репозитория файл `.editorconfig`. В нём задают общие правила форматирования для разных типов файлов (например, Python, SQL, YAML).

Зачем нужны форматтеры:

- Автоматизация рутинной задачи по форматированию кода
- Устранение споров в команде о стиле кодирования
- Повышение читаемости кода для всех участников проекта
- Экономия времени при code review, так как вам уже не нужно обсуждать стиль
- Единообразие кода во всём проекте независимо от автора изменений

## Linters

Линтеры (статические анализаторы кода) проверяют код без запуска: ищут возможные ошибки, проблемы с качеством и отступления от принятых стандартов. В Data Engineering они помогают делать data pipelines надёжными и простыми в поддержке.

1. **Основные линтеры для Python**
   - [Pylint](https://pylint.org/) — комплексный линтер, который проверяет соответствие стандартам PEP 8, выявляет ошибки и предлагает рекомендации по улучшению кода
   - [Flake8](https://flake8.pycqa.org/) — комбинация нескольких инструментов для проверки стиля и качества кода
   - [Ruff](https://github.com/astral-sh/ruff) — быстрый линтер, написанный на Rust, поддерживающий большинство проверок Flake8
   - [mypy](https://mypy.readthedocs.io/) — статический анализатор типов для Python, который помогает выявлять ошибки типизации

2. **Специализированные линтеры для SQL**
   - [SQLFluff](https://www.sqlfluff.com/) — линтер для SQL, который помогает поддерживать единый стиль SQL-запросов в проекте
   - [sql-lint](https://github.com/joereynolds/sql-lint) — простой линтер для проверки базового синтаксиса SQL
  
Зачем нужны линтеры:

- Раннее/автоматическое обнаружение потенциальных ошибок в коде
- Обеспечение соответствия кода стандартам и лучшим практикам
- Поддержание качества кода на протяжении всего жизненного цикла проекта
- Упрощение процесса code review за счёт автоматических проверок
- Обучение разработчиков лучшим практикам через подсказки линтера

Классический набор для Python: `black`, `isort`, `flake8`, `mypy`. 

## Тестирование

Тестирование в Data Engineering охватывает не только проверку логики кода, но и валидацию данных, проверку ETL-процессов и тестирование производительности pipeline. Основные аспекты тестирования включают:

1. **Unit-тестирование (Модульное тестирование)**
   
   Мы берём маленькую часть кода (например, одну функцию) и проверяем, правильно ли она работает сама по себе. Допустим, у вас есть функция, которая очищает данные от пропусков — вы проверяете, действительно ли она удаляет пропуски и не портит при этом остальные данные.

   Популярные инструменты:
   - [pytest](https://docs.pytest.org/) — основной фреймворк для написания и выполнения тестов в Python
   - [unittest](https://docs.python.org/3/library/unittest.html) — встроенный в стандартную библиотеку Python модуль для создания unit-тестов
   - [nose2](https://docs.nose2.io/) — расширенная версия unittest с дополнительными возможностями

2. **Тестирование данных (Data Testing)**
   
   Здесь проверяют сами данные, а не код. Например, мы берём нужные данные и проверяем, что в колонке с возрастом нет отрицательных значений, что почтовые адреса соответствуют правильному формату, или что общая сумма продаж не превышает реалистичных значений.

   Основные инструменты:
   - [Great Expectations](https://greatexpectations.io/) — фреймворк для валидации, документирования и профилирования данных
   - [Pandas Testing](https://pandas.pydata.org/docs/reference/testing.html) — модуль для тестирования операций с DataFrame

3. **Интеграционное тестирование (Integration Testing)**
   
   Такие тесты проверяют, как части системы работают вместе. Unit-тесты проверяют отдельные функции, а интеграционные — их связку. Например, мы проверяем, правильно ли данные:
   - Загружаются из базы данных
   - Проходят все этапы обработки
   - Сохраняются в конечное хранилище
   
   При этом мы тестируем взаимодействие с реальными системами или их имитациями.

   Основные инструменты:
   - [TestContainers](https://testcontainers-python.readthedocs.io/) — библиотека для тестирования с использованием Docker-контейнеров (например, можно поднять временную базу данных для тестов)
   - [Moto](https://github.com/getmoto/moto) — библиотека, которая имитирует сервисы AWS в тестах (mock): например, S3, DynamoDB и другие

Зачем нужно тестирование:

- Гарантия корректной работы ETL-процессов и трансформаций данных
- Обеспечение надёжности data pipeline при изменениях в коде
- Проверка качества и целостности данных на всех этапах обработки данных
- Выявление проблем производительности до релиза в продакшн
- Документирование ожидаемого поведения системы через тесты
- Упрощение рефакторинга и доработки существующего кода проектов

## Docker и Docker Compose

Docker упаковывает код и все зависимости в контейнер, и такой контейнер работает одинаково на ноутбуке, на сервере и в облаке. А Docker Compose запускает несколько контейнеров вместе, например Airflow + Postgres.

- [Docker: Get started](https://docs.docker.com/get-started/) 🇬🇧 — официальный старт.
- [Docker Compose](https://docs.docker.com/compose/) 🇬🇧 — документация.

## Kubernetes и Minikube

Kubernetes запускает и масштабирует контейнеры на кластере. Многие дата-платформы (Airflow, Spark, Trino) работают именно в нём. Для учёбы есть Minikube: он поднимает маленький кластер на вашем компьютере.

- [Kubernetes Basics](https://kubernetes.io/docs/tutorials/kubernetes-basics/) 🇬🇧 — официальный туториал.
- [Minikube](https://minikube.sigs.k8s.io/docs/start/) 🇬🇧 — локальный кластер.

## CI/CD

CI (continuous integration) — при каждом изменении автоматически запускаются линтеры и тесты. CD (continuous delivery/deployment) — изменения автоматически выкатываются на окружение. Для дата-проектов это, например, запуск `dbt build` на pull request и деплой DAG в Airflow после merge.

- [GitHub Actions](https://docs.github.com/en/actions) 🇬🇧
- [GitLab CI/CD](https://docs.gitlab.com/ee/ci/) 🇬🇧
- [Azure Pipelines](https://learn.microsoft.com/en-us/azure/devops/pipelines/) 🇬🇧

## Semantic Versioning

[Semantic Versioning](https://semver.org/lang/ru/) 🇷🇺 — правило нумерации версий `MAJOR.MINOR.PATCH`. `MAJOR` — ломающие изменения, `MINOR` — новые функции, `PATCH` — исправления. Такая нумерация полезна для своих Python-пакетов, dbt-пакетов и API.

## Инфраструктура как код

Инфраструктура как код (Infrastructure as Code, IaC) — вы описываете облачные ресурсы в файлах: хранилище, базу данных, кластер, права доступа. Затем инструмент сам создаёт или меняет их по этому описанию.

Зачем это инженеру данных:

- **Повторяемость.** Окружения dev, test и prod одинаковые.
- **Review.** Изменения инфраструктуры проходят pull request, как код.
- **История.** В Git видно, кто, когда и зачем поменял ресурс.
- **Нет ручных кликов.** Ресурсы не создаются руками в консоли облака.

Основные инструменты:

| Инструмент | Облако | Язык |
|---|---|---|
| [Terraform](https://developer.hashicorp.com/terraform) | Любое (AWS, Azure, GCP, Snowflake, Databricks и др.) | HCL |
| [OpenTofu](https://opentofu.org/) | Любое | HCL, open-source форк Terraform |
| [Bicep](https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/overview) | Только Azure | Bicep |

| [Pulumi](https://www.pulumi.com/) | Любое | Python, TypeScript, Go и др. |

Если не знаете, с чего начать, начните с Terraform. Он работает с любым облаком и с дата-платформами: у Snowflake и Databricks есть свои Terraform-провайдеры.

- [Terraform: Get Started](https://developer.hashicorp.com/terraform/tutorials) 🇬🇧 — официальные туториалы для AWS, Azure и GCP.

- [Terraform: Up & Running](https://www.terraformupandrunning.com/) 🇬🇧 ⭐ — книга Евгения Брикмана.

## Мониторинг и логирование

Мониторинг отвечает на вопрос «работает ли система», а логи — на вопрос «что именно случилось». Для `pipeline` при этом важно знать о падении раньше, чем об этом напишет пользователь дашборда.

- [Prometheus](https://prometheus.io/) 🇬🇧 — сбор метрик.
- [Grafana](https://grafana.com/) 🇬🇧 — дашборды и алерты.
- [OpenTelemetry](https://opentelemetry.io/) 🇬🇧 — открытый стандарт для метрик, логов и трейсов.

Мониторинг самих данных (свежесть, объём, схема) — это data observability. Подробнее о ней — на странице [Качество данных](/processing/data-quality/#data-observability).
