## Как работать с кейсами

Это не уроки синтаксиса. Это три задачи, какие аналитик получает на работе. Здесь мало знать SQL. Нужно понять, что вы измеряете и что значат цифры.

Перед кейсами вы должны уверенно писать запросы с `GROUP BY`, `JOIN`, `CASE` и датами. Если нет — вернитесь к разделам [«Основы» и «Средний уровень»](/practice/sql/).

### Компания: Yammer

Yammer — социальная сеть для общения с коллегами. Люди публикуют сообщения, документы и идеи в группах.

- Пользоваться Yammer можно бесплатно.
- Компания платит, если хочет админские функции. Например, связь с ActiveDirectory.

В Yammer есть центральная команда аналитики. Она помогает принимать решения о продукте на основе данных:

- делает разовые исследования под конкретные вопросы;
- даёт другим командам инструменты и знания для работы с данными.

### Как думают аналитики Yammer

- **Время дорого.** Быстрый и примерный ответ часто лучше точного и долгого.
- **Смотрим на всю компанию.** Любое изменение продукта оценивают по главным метрикам: вовлечённость, удержание, рост. Метрики конкретной функции — только дополнение.

### Как работать над кейсом

1. **Прочитайте задачу.** Поймите, что именно показывает график или таблица и чего она не показывает.
2. **Запишите гипотезы до того, как откроете данные.** Что могло вызвать такой результат? Нужен список из 5–8 пунктов.
3. **Для каждой гипотезы запишите проверку.** Какой запрос её подтвердит или опровергнет?
4. **Расставьте гипотезы по порядку.** Сначала — вероятные и быстрые в проверке. Запишите, по какому правилу вы их сортировали.
5. **Пишите запросы.** Сохраняйте их в файл. Каждый запрос — одна гипотеза.
6. **Сформулируйте вывод.** 3–5 предложений для руководителя: что случилось и что делать.
7. **Только потом откройте разбор.** Сравните свои гипотезы и выводы с нашими.

:::caution
Без AI. Кейс учит думать, а не писать запросы. Если AI выдвинет гипотезы за вас, вы пропустите самое важное.
:::

:::tip
Запросы в разборах местами используют оконные функции и `WITH` (CTE). Они из раздела «Продвинутый уровень». Можно решить кейс простыми запросами. Можно вернуться к кейсам после продвинутого раздела.
:::

## Кейс 1: падение вовлечённости

Это кейс, а не урок. Здесь нет готовых заданий с проверкой. Задача — понять, почему упала вовлечённость, и предложить, что делать. Перед началом прочитайте [описание кейсов и Yammer](/practice/sql/analytics/) и правила работы.

Решайте сами, без AI. Ответы откройте только после того, как попробовали сами: [разбор](/practice/sql/analytics/#кейс-1-разбор).

### Задача

Вы пришли на работу во вторник, 2 сентября 2014 года. Руководитель продукта подходит к вашему столу. Он просит посмотреть на дашборд вовлечённости. На дашборде видно падение в конце графика.

Что показывает график:

- по оси X — неделя;
- по оси Y — число вовлечённых пользователей за неделю.

В Yammer пользователь «вовлечён», если сделал хотя бы один запрос к серверу, пока работал с продуктом. В данных это события с `event_type = 'engagement'`.

Одна точка графика читается так: «сколько пользователей сделали хотя бы одно engagement-событие за неделю, которая начинается с этой даты».

Ваша задача:

- найти причину падения;
- если нужно, предложить решение.

### Первый шаг: ориентация

Не открывайте данные сразу. Сначала подумайте.

- Составьте список возможных причин падения.
- Запишите, как вы проверите каждую причину.
- Расставьте причины по порядку проверки. Запишите правило, по которому вы их сортировали.
- Поймите, что график показывает, а чего не показывает. Например, из него не видно, кто именно перестал заходить.

:::tip
Хороший список — это 5–8 гипотез. У каждой есть запрос или вопрос, который её проверяет. Если вы не знаете, как проверить гипотезу, отложите её.
:::

### Данные

Нужны четыре таблицы. Данные не настоящие. Мы сгенерировали их сами. Структура похожа на данные Yammer.

#### `tutorial.yammer_users`

Одна строка на пользователя.

| Колонка | Что это |
|---|---|
| `user_id` | Уникальный ID пользователя. Связывает с `user_id` в других таблицах. |
| `created_at` | Когда пользователь зарегистрировался. |
| `state` | Статус: `active` или `pending`. |
| `activated_at` | Когда пользователь активировался (если активен). |
| `company_id` | ID компании пользователя. |
| `language` | Язык, который выбрал пользователь. |

#### `tutorial.yammer_events`

Одна строка на событие. Событие — это действие пользователя в Yammer: вход, сообщение, поиск, шаг регистрации.

| Колонка | Что это |
|---|---|
| `user_id` | Кто совершил событие. |
| `occurred_at` | Когда произошло событие. |
| `event_type` | Общий тип. `signup_flow` — процесс регистрации. `engagement` — работа с продуктом после регистрации. |
| `event_name` | Конкретное действие (список ниже). |
| `location` | Страна, из которой пришло событие (по IP). |
| `device` | Устройство, с которого пришло событие. |
| `user_type` | Тип пользователя: число 1, 2 или 3. |

Значения `event_name`:

| Значение | Что значит |
|---|---|
| `create_user` | Пользователя добавили в базу при регистрации. |
| `enter_email` | Начал регистрацию, ввёл email. |
| `enter_info` | Ввёл имя и личные данные. |
| `complete_signup` | Завершил регистрацию. |
| `home_page` | Открыл главную страницу. |
| `like_message` | Поставил лайк чужому сообщению. |
| `login` | Вошёл в Yammer. |
| `search_autocomplete` | Выбрал результат из подсказок поиска. |
| `search_run` | Запустил поиск и открыл страницу результатов. |
| `search_click_result_X` | Нажал на результат поиска номер X (X от 1 до 10). |
| `send_message` | Написал сообщение. |
| `view_inbox` | Открыл входящие. |

#### `tutorial.yammer_emails`

События, связанные с письмами. Структура похожа на таблицу событий.

| Колонка | Что это |
|---|---|
| `user_id` | Пользователь, которому относится событие. |
| `occurred_at` | Когда произошло событие. |
| `action` | Что произошло (список ниже). |
| `user_type` | Тип пользователя (число). |

Значения `action`:

| Значение | Что значит |
|---|---|
| `sent_weekly_digest` | Пользователю отправили письмо-дайджест с актуальными обсуждениями. |
| `sent_reengagement_email` | Пользователю отправили письмо, чтобы вернуть его в продукт. |
| `email_open` | Пользователь открыл письмо. |
| `email_clickthrough` | Пользователь нажал на ссылку в письме. |

Значения `sent_reengagement_email` нет в оригинальном описании ThoughtSpot. Оно есть в наших данных. Не пропустите его, когда будете считать письма.
:::

#### `benn.dimension_rollup_periods`

Справочник скользящих периодов. Он нужен, чтобы построить график выше. Вам не обязательно его использовать. Но стоит понять, как он работает.

| Колонка | Что это |
|---|---|
| `period_id` | Тип периода. Дашборд использует `1007` — скользящие 7 дней. |
| `time_id` | Точка на графике. Для `2014-08-01` это 7 дней, которые закончились 2014-08-01. |
| `pst_start` | Начало периода по тихоокеанскому времени. Для `2014-08-01` это `2014-07-25`. |
| `pst_end` | Конец периода по тихоокеанскому времени. Для `2014-08-01` это `2014-08-01`. |
| `utc_start` | Начало периода по UTC. |
| `utc_end` | Конец периода по UTC. |

Так выглядит запрос, который строит график скользящих 7 дней. Он берёт по одной точке в неделю.

```sql
SELECT p.time_id::DATE AS day,
       COUNT(DISTINCT e.user_id) AS engaged_users_7d
FROM benn.dimension_rollup_periods p
JOIN tutorial.yammer_events e
  ON e.occurred_at >= p.pst_start
 AND e.occurred_at < p.pst_end
 AND e.event_type = 'engagement'
WHERE p.period_id = 1007
  AND p.time_id BETWEEN '2014-07-20' AND '2014-09-01'
  AND DAYOFWEEK(p.time_id) = 1
GROUP BY 1
ORDER BY 1;
```

:::note
Здесь `DAYOFWEEK(...) = 1` оставляет только понедельники (в DuckDB воскресенье — это 0). Без этого фильтра будет по строке на каждый день.
:::

### Гипотезы и порядок проверки

Главная часть кейса — не запросы, а список гипотез. Хороший список экономит время.

Полного списка не существует. Вот наш:

| Гипотеза | Как проверить |
|---|---|
| Праздник. В какой-то стране люди работают меньше. | Разбить вовлечённость по странам. |
| Сломана функция. Что-то в продукте не работает. | Разбить метрику по устройствам и событиям. Ломается часть продукта — падает только часть метрики. |
| Сломан код трекинга. События перестали записываться. | Искать падение до нуля по одному типу события. Сначала исключить сломанную функцию. |
| Боты. Бот-трафик стало труднее создавать. | Искать подозрительные шаблоны поведения. Сложно проверить. |
| Сайт заблокирован у провайдеров. | Смотреть на падение по странам и сетям. Бывает редко. |
| Маркетинговая акция. Всплеск новых пользователей, потом спад. | Спросить маркетинг. Посмотреть рост регистраций. |
| Плохие данные. Тестовые данные попали в боевую базу. | Искать события от очень малого числа пользователей. Здесь это маловероятно. |
| Поисковые системы изменили выдачу. | Смотреть на трафик новых пользователей. |

Как расставить гипотезы по порядку:

- **Опыт.** Вы уже видели такие проблемы. Знаете, какие встречаются чаще.
- **Общение.** Спросить коллегу из маркетинга быстро и дёшево. Делайте это первым.
- **Скорость.** Если две гипотезы одинаково вероятны, проверяйте ту, что быстрее.
- **Зависимость.** Если результат одной проверки упрощает другую, идите в таком порядке.

Посчитаем доли. Открытие — в течение 5 минут после отправки. Клик — в течение 5 минут после открытия:

  AND e1.occurred_at >= '2014-06-30'

ORDER BY 1;

### Как сейчас работает поиск

- В шапке каждой страницы есть строка поиска. Она предлагает искать людей, группы и обсуждения.
- Когда пользователь начинает печатать, появляется список лучших результатов. Он разбит по категориям: люди, обсуждения, файлы. Есть пункт «показать все результаты».
- Если пользователь нажимает Enter или «показать все результаты», он попадает на страницу результатов. Там вкладки по категориям. Результаты на каждой вкладке отсортированы по релевантности и по дате: свежие сообщения выше.
- На странице результатов есть «расширенный поиск». Он позволяет искать ещё раз внутри группы или за период.

### Задача

Команда продукта выбирает приоритеты на следующий цикл разработки. Они думают об улучшении поиска.

Каждая новая функция отнимает время у другой функции. Поэтому команда хочет знать:

- стоит ли вообще заниматься поиском;
- если стоит, что именно менять.

- Как измерить качество поиска для одного пользователя?

:::tip
Подумайте, на каком уровне вы будете считать метрики. По пользователям? По дням? По отдельным событиям? Подсказка: качество поиска удобнее смотреть по сессиям. Разбор начинается с этого.

### Гипотезы

Начните с вопросов, не с запросов.

- **Зачем поиск?** Чтобы быстро найти человека, группу или обсуждение.
- **Как понять, что поиск справляется?** Пользователь ищет и находит. После поиска он нажимает на результат. Потом возвращается к поиску снова.
- **Как измерить качество?** Через сессию. Мы смотрим, что пользователь делает за один визит.

Наши гипотезы:

| Гипотеза | Как проверить |
|---|---|
| Поиском пользуются часто, он нужен. | Доля сессий с подсказками и с полным поиском. |
| Если поиск хороший, пользователи нажимают на результаты. | Клики после `search_run`. |
| Если ранжирование хорошее, кликают в основном по первым результатам. | Клики по позициям 1–10. |
| Довольные пользователи возвращаются к поиску. | Сколько сессий с функцией в следующие 30 дней. |

### Что такое сессия

Поиск удобно оценивать по сессиям. В данных сессии нет, её нужно определить самим.

В этом разборе: **сессия** — это события одного пользователя без паузы в 10 минут и больше. Если пауза 10 минут или дольше, начинается новая сессия.

Алгоритм:

1. Для каждого события найдите время предыдущего события этого же пользователя (`LAG`).
2. Если предыдущего нет или пауза от 10 минут, пометьте событие как начало сессии.
3. Нарастающая сумма этих меток даёт номер сессии (`SUM() OVER`).
4. Сгруппируйте по пользователю и номеру сессии. Посчитайте события поиска.

Создадим временную таблицу `sessions`. Она живёт, пока открыта сессия DuckDB, и не меняет вашу базу.

```sql
CREATE TEMP TABLE sessions AS
WITH ordered AS (
  SELECT user_id, occurred_at, event_name,
         LAG(occurred_at) OVER (PARTITION BY user_id ORDER BY occurred_at) AS prev_at
  FROM tutorial.yammer_events
  WHERE event_type = 'engagement'
), flagged AS (
  SELECT *,
         CASE WHEN prev_at IS NULL OR occurred_at - prev_at >= INTERVAL 10 MINUTE
              THEN 1 ELSE 0 END AS is_new_session
  FROM ordered
), numbered AS (
  SELECT *,
         SUM(is_new_session) OVER (PARTITION BY user_id ORDER BY occurred_at
                                   ROWS UNBOUNDED PRECEDING) AS session_no
  FROM flagged
)
SELECT user_id, session_no,
       MIN(occurred_at) AS session_start,
       COUNT(*) FILTER (WHERE event_name = 'search_autocomplete') AS autocompletes,
       COUNT(*) FILTER (WHERE event_name = 'search_run') AS runs,
       COUNT(*) FILTER (WHERE event_name LIKE 'search_click_result_%') AS clicks
FROM numbered
GROUP BY user_id, session_no;
```

### Шаг 5. Возвращаются ли пользователи

Для каждого пользователя берём первую сессию с функцией. Считаем, в скольких сессиях с этой функцией он был за следующие 30 дней (включая первую). Берём только пользователей, чья первая сессия была до 1 августа. Так виден полный месяц.

```sql
-- не запускать отдельно: нужна таблица sessions
WITH firsts AS (
  SELECT user_id,
         MIN(session_start) FILTER (WHERE runs > 0) AS first_run,
         MIN(session_start) FILTER (WHERE autocompletes > 0) AS first_auto
  FROM sessions
  GROUP BY user_id
), run_ret AS (
  SELECT f.user_id, COUNT(*) AS n_sessions
  FROM firsts f
  JOIN sessions s
    ON s.user_id = f.user_id AND s.runs > 0
   AND s.session_start >= f.first_run
   AND s.session_start < f.first_run + INTERVAL 30 DAY
  WHERE f.first_run < '2014-08-01'
  GROUP BY f.user_id
), auto_ret AS (
  SELECT f.user_id, COUNT(*) AS n_sessions
  FROM firsts f
  JOIN sessions s
    ON s.user_id = f.user_id AND s.autocompletes > 0
   AND s.session_start >= f.first_auto
   AND s.session_start < f.first_auto + INTERVAL 30 DAY
  WHERE f.first_auto < '2014-08-01'
  GROUP BY f.user_id
)
SELECT LEAST(n_sessions, 6) AS sessions_in_30d, COUNT(*) AS users, 'search_run' AS feature
FROM run_ret GROUP BY 1
UNION ALL
SELECT LEAST(n_sessions, 6), COUNT(*), 'autocomplete'
FROM auto_ret GROUP BY 1
ORDER BY 3, 1;
```

Значение 6 означает «6 и больше».

| Сессий за 30 дней | Пользователей, полный поиск | Пользователей, подсказки |
|---:|---:|---:|
| 1 | 2647 | 1453 |
| 2 | 366 | 1062 |
| 3 | 42 | 647 |
| 4 | 8 | 347 |
| 5 | — | 192 |
| 6 и больше | — | 309 |

Вывод:

- Из 3063 пользователей полного поиска 2647 (86%) использовали его только один раз за месяц.
- Из 4010 пользователей подсказок только 1453 (36%) остановились на одной сессии. Остальные вернулись.

Подсказки удерживают пользователей. Полный поиск — нет.

### Рекомендация

Что мы увидели:

| Факт | Цифра |
|---|---|
| Подсказки используют | 25% сессий |
| Полный поиск используют | 8% сессий |
| Сессии с поиском без кликов | 78% |
| Клики по позициям | почти равномерно |
| Вернулись к полному поиску | 14% |
| Вернулись к подсказкам | 64% |

Вывод: подсказки работают нормально. Полный поиск работает плохо.

Что предложить:

- Главный фокус — порядок результатов на странице полного поиска.
- Люди идут в полный поиск, когда подсказки не дали нужного. Возможно, стоит сделать результаты полного поиска немного другими, чем подсказки.
- Есть разные способы улучшить поиск. Важно, что фокус — полный поиск.

Как проверить, что стало лучше:

- Запустить A/B-тест нового ранжирования.
- Метрики успеха: доля сессий поиска с хотя бы одним кликом, сдвиг кликов к первым позициям, возврат к полному поиску в течение 30 дней.
- Следить и за побочными метриками: использование подсказок не должно упасть.

Один важный ограничитель: мы не знаем, что искал пользователь. Мы видим только события. Поэтому «нет клика» может значить, что результаты плохие, а может — что ответ был виден в самом списке.

## Кейс 3: проверка A/B-теста

Это кейс, а не урок. Здесь нет заданий с проверкой. Вы проверяете результат A/B-теста и даёте рекомендацию. Правила работы — на странице [Аналитические кейсы](/practice/sql/analytics/).

Решайте сами, без AI. Ответы откройте только после того, как попробовали сами: [разбор](/practice/sql/analytics/#кейс-3-разбор).

### Задача

Yammer не только делает новые функции. Компания постоянно улучшает и старые. Перед выпуском функции для всех клиентов её обычно проверяют в A/B-тесте. Тест показывает, как функция влияет на поведение пользователей.

Этот кейс про «публикатор» (publisher). Это блок вверху ленты Yammer, где пользователь пишет сообщение. Команда продукта сделала новую версию публикатора.

A/B-тест шёл с 1 по 30 июня:

- пользователи, которые заходили в Yammer, видели либо старую версию (`control_group`),
- либо новую версию (`test_group`).

1 июля вы смотрите результаты. Сообщений в тестовой группе на 50% больше. Это очень большой рост.

### Как читать результат теста

Результат — таблица по группам. Вот что значат колонки:

| Колонка | Что это |
|---|---|
| `users` | Сколько пользователей увидели эту версию. |
| `total_treated_users` | Сколько пользователей получили любую версию. |
| `treatment_percent` | Доля группы среди всех пользователей теста. |
| `total` | Сколько сообщений написала группа. |
| `average` | Среднее число сообщений на пользователя: `total / users`. |
| `rate_difference` | Разница средних: среднее группы минус среднее контрольной. |
| `rate_lift` | Разница в процентах: `среднее группы / среднее контрольной - 1`. |
| `stdev` | Стандартное отклонение сообщений на пользователя. |
| `t_stat` | Статистика, которая показывает, различаются ли средние. Считается по средним и стандартным отклонениям двух групп. |
| `p_value` | Вероятность увидеть такую разницу случайно. Малое значение — разница значима. |

Для сравнения средних тест использует t-критерий Стьюдента. Он двусторонний: тестовая группа может быть как лучше, так и хуже контрольной.

:::note
В оригинале есть таблица нормального распределения для расчёта `p_value`. В нашей базе её нет. Для больших выборок хватит `t_stat`: если он по модулю больше 2, разница значима на уровне 5%.
:::

Ваша задача: понять, настоящий это успех или слишком хорошо, чтобы быть правдой. Команда продукта ждёт совета. Дайте как можно больше информации о том, что произошло.

### Шаг 0. Воспроизведите результат

Нужен расчёт по пользователям. Для каждого пользователя из эксперимента считаем сообщения, входы и дни активности с момента попадания в группу до 1 июля. Пользователь, который не написал ни одного сообщения, остаётся в данных с нулём (`LEFT JOIN`).

Мы также помечаем пользователя как нового (`new`), если он активирован в июне, и существующего (`existing`) в остальных случаях. Пригодится на шаге 3.

```sql
CREATE TEMP TABLE ab_users AS
SELECT ex.user_id,
       ex.experiment_group,
       CASE WHEN u.activated_at >= '2014-06-01' THEN 'new' ELSE 'existing' END AS user_kind,
       COUNT(e.user_id) FILTER (WHERE e.event_name = 'send_message') AS messages,
       COUNT(e.user_id) FILTER (WHERE e.event_name = 'login') AS logins,
       COUNT(DISTINCT e.occurred_at::DATE) AS days_engaged
FROM tutorial.yammer_experiments ex
JOIN tutorial.yammer_users u ON u.user_id = ex.user_id
LEFT JOIN tutorial.yammer_events e
  ON e.user_id = ex.user_id
 AND e.event_type = 'engagement'
 AND e.occurred_at >= ex.occurred_at
 AND e.occurred_at < '2014-07-01'
WHERE ex.experiment = 'publisher_update'
GROUP BY ex.user_id, ex.experiment_group, user_kind;
```

Теперь итоговая таблица теста. Для t-статистики используем средние и стандартные отклонения двух групп:

```sql
-- не запускать отдельно: нужна таблица ab_users
WITH g AS (
  SELECT experiment_group,
         COUNT(*) AS users,
         AVG(messages) AS average,
         STDDEV_SAMP(messages) AS stdev
  FROM ab_users
  GROUP BY 1
), c AS (
  SELECT * FROM g WHERE experiment_group = 'control_group'
)
SELECT g.experiment_group,
       g.users,
       ROUND(g.average, 3) AS average,
       ROUND(g.average - c.average, 3) AS rate_difference,
       ROUND(g.average / c.average - 1, 3) AS rate_lift,
       ROUND((g.average - c.average)
             / SQRT(g.stdev ^ 2 / g.users + c.stdev ^ 2 / c.users), 2) AS t_stat
FROM g CROSS JOIN c
ORDER BY 1;
```

| Группа | Пользователей | Среднее | Разница | Рост | t_stat |
|---|---:|---:|---:|---:|---:|
| control_group | 1783 | 2.189 | 0 | 0% | 0 |
| test_group | 1042 | 3.385 | 1.196 | +54.6% | 10.42 |

Это исходный результат: +55% и очень большая значимость (`t_stat` намного больше 2).

### Шаг 1. Другие метрики

Одних сообщений мало. Нужны метрики, которые показывают пользу. В Yammer главная такая метрика — частота входов. Добавим дни активности: в сколько разных дней пользователь заходил.

```sql
-- не запускать отдельно: нужна таблица ab_users
SELECT experiment_group,
       ROUND(AVG(messages), 2) AS avg_messages,
       ROUND(AVG(logins), 2) AS avg_logins,
       ROUND(AVG(days_engaged), 2) AS avg_days_engaged
FROM ab_users
GROUP BY 1
ORDER BY 1;
```

| Группа | Сообщений | Входов | Дней активности |
|---|---:|---:|---:|
| control_group | 2.19 | 3.83 | 3.90 |
| test_group | 3.38 | 4.37 | 4.37 |

Вывод: входов больше, дней активности тоже больше. Если бы входы росли, а дни были бы без изменений, это могло значить, что пользователи заходят и сразу выходят. Возможно, ошибка входа. Здесь такого нет. По метрикам всё хорошо.

Значит, проблема не в выборе метрики.

### Шаг 2. Метод расчёта

Спорить о математике можно: односторонний или двусторонний тест, размер выборки, форма распределения. Но на этот результат такие выборы не повлияют.

Зато в тесте есть ошибка метода. Он смешивает новых и существующих пользователей и считает все сообщения до конца июня.

- Пользователь, зарегистрированный в январе, мог писать весь месяц.
- Пользователь, зарегистрированный за день до конца теста, почти не имел времени писать.

Нужно считать новых и существующих отдельно. Так величины сравнимы. Так же можно проверить эффект новизны: опытные пользователи могут пробовать функцию просто потому, что она новая. Для новых пользователей публикатор не «новый», они не знают старого.

### Шаг 3. Как распределили пользователей

Посмотрим на группы с учётом возраста пользователя:

```sql
-- не запускать отдельно: нужна таблица ab_users
SELECT user_kind,
       experiment_group,
       COUNT(*) AS users,
       ROUND(AVG(messages), 2) AS avg_messages
FROM ab_users
GROUP BY 1, 2
ORDER BY 1, 2;
```

| Тип | Группа | Пользователей | Сообщений в среднем |
|---|---|---:|---:|
| existing | control_group | 1076 | 2.65 |
| existing | test_group | 1042 | 3.38 |
| new | control_group | 707 | 1.49 |

Это и есть ошибка. В тестовой группе нет ни одного нового пользователя. Все 707 новых пользователей попали в контрольную группу.

Чем это плохо:

- Новые пользователи пишут меньше, потому что у них мало времени. Это не связано с версией публикатора.
- Все они в контроле, поэтому среднее контроля занижено.
- Часть «роста» создана ошибкой в распределении, а не новой функцией.

:::caution
Это типичная ошибка A/B-тестов. Если группы не случайные, вывод теста нельзя принимать. Всегда проверяйте состав групп до анализа результата.
:::

### Шаг 4. Честное сравнение

Сравним только существующих пользователей. У них у обоих групп сопоставимое время для публикаций:

```sql
-- не запускать отдельно: нужна таблица ab_users
WITH g AS (
  SELECT experiment_group,
         COUNT(*) AS users,
         AVG(messages) AS average,
         STDDEV_SAMP(messages) AS stdev
  FROM ab_users
  WHERE user_kind = 'existing'
  GROUP BY 1
), c AS (
  SELECT * FROM g WHERE experiment_group = 'control_group'
)
SELECT g.experiment_group,
       g.users,
       ROUND(g.average, 3) AS average,
       ROUND(g.average - c.average, 3) AS rate_difference,
       ROUND(g.average / c.average - 1, 3) AS rate_lift,
       ROUND((g.average - c.average)
             / SQRT(g.stdev ^ 2 / g.users + c.stdev ^ 2 / c.users), 2) AS t_stat
FROM g CROSS JOIN c
ORDER BY 1;
```

| Группа | Пользователей | Среднее | Разница | Рост | t_stat |
|---|---:|---:|---:|---:|---:|
| control_group | 1076 | 2.650 | 0 | 0% | 0 |
| test_group | 1042 | 3.385 | 0.735 | +27.7% | 5.88 |

Вывод: рост упал с +55% до +28%. Но он остаётся значимым (`t_stat` 5.88).

Другие метрики на тех же существующих пользователях:

```sql
-- не запускать отдельно: нужна таблица ab_users
SELECT experiment_group,
       ROUND(AVG(messages), 2) AS avg_messages,
       ROUND(AVG(logins), 2) AS avg_logins,
       ROUND(AVG(days_engaged), 2) AS avg_days_engaged
FROM ab_users
WHERE user_kind = 'existing'
GROUP BY 1
ORDER BY 1;
```

| Группа | Сообщений | Входов | Дней активности |
|---|---:|---:|---:|
| control_group | 2.65 | 3.59 | 3.70 |
| test_group | 3.38 | 4.37 | 4.37 |

Тестовая группа впереди по всем трём метрикам, но разрыв меньше.

### Шаг 5. Другие когорты

Исправили одну проблему. Это не значит, что других нет. Проблем может быть несколько, и они часто связаны. Типовые когорты для проверки: устройство и тип пользователя (пишет контент или читает).

Среднее число сообщений у существующих пользователей по устройствам:

```sql
-- не запускать отдельно: нужна таблица ab_users
SELECT CASE WHEN ex.device IN ('iphone 5', 'iphone 5s', 'iphone 4s',
              'samsung galaxy s4', 'nexus 5', 'htc one', 'nokia lumia 635',
              'samsung galaxy note', 'amazon fire phone') THEN 'phone'
            WHEN ex.device IN ('ipad air', 'ipad mini', 'nexus 7', 'nexus 10',
              'kindle fire', 'samsung galaxy tablet') THEN 'tablet'
            ELSE 'computer' END AS device_class,
       a.experiment_group,
       COUNT(*) AS users,
       ROUND(AVG(a.messages), 2) AS avg_messages
FROM ab_users a
JOIN tutorial.yammer_experiments ex
  ON ex.user_id = a.user_id AND ex.experiment = 'publisher_update'
WHERE a.user_kind = 'existing'
GROUP BY 1, 2
ORDER BY 1, 2;
```

| Устройство | Группа | Пользователей | Сообщений |
|---|---|---:|---:|
| computer | control_group | 767 | 2.70 |
| computer | test_group | 780 | 3.48 |
| phone | control_group | 242 | 2.37 |
| phone | test_group | 206 | 3.15 |
| tablet | control_group | 67 | 3.12 |
| tablet | test_group | 56 | 2.95 |

По типу пользователя (`user_type` берём из событий):

```sql
-- не запускать отдельно: нужна таблица ab_users
SELECT t.user_type,
       a.experiment_group,
       COUNT(*) AS users,
       ROUND(AVG(a.messages), 2) AS avg_messages
FROM ab_users a
JOIN (SELECT DISTINCT user_id, user_type FROM tutorial.yammer_events) t
  ON t.user_id = a.user_id

```

| Тип | Группа | Пользователей | Сообщений |
|---:|---|---:|---:|
| 1 | control_group | 300 | 4.46 |
| 1 | test_group | 295 | 6.05 |
| 2 | control_group | 511 | 2.19 |
| 2 | test_group | 490 | 2.74 |
| 3 | control_group | 265 | 1.49 |
| 3 | test_group | 257 | 1.54 |

Вывод:

- На компьютерах и телефонах тестовая группа впереди примерно на 0.8 сообщения.
- У планшетов тестовая группа чуть ниже контрольной. Но там всего 56 и 67 пользователей, это может быть шум.
- Больше всего выигрывают пользователи типа 1 (те, кто пишет много). У типа 3 почти нет разницы.

Ни одна когорта не объясняет весь эффект. Но эффект неравномерный. Это стоит проверить в следующем тесте.

### Рекомендация

Что сказать команде продукта:

- Исходные +55% завышены. Ошибка в распределении: все новые пользователи попали в контроль.
- На честном сравнении (только существующие) рост +28%. Он всё ещё значимый. Входы и дни активности тоже выше.
- Новую функцию стоит развивать, а не отменять.

Что делать:

1. Найти и исправить ошибку, из-за которой все новые пользователи попадают в контрольную группу.
2. Повторить тест с правильным распределением. Или хотя бы проверить результат отдельно для новых пользователей.
3. Проверить результат по когортам: устройство, тип пользователя. Особенно планшеты и пользователи типа 3.
4. До переделанного теста не говорить о «+50%». Говорить о «примерно +28% среди существующих пользователей».

:::note
Для новых пользователей ответа пока нет. В тестовой группе их нет вообще. Значит, как функция работает для них, мы не знаем.
:::
