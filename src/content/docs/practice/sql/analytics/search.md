Это кейс, а не урок. Здесь нет заданий с проверкой. Вы изучаете данные и даёте рекомендацию команде продукта. Правила работы — на странице [Аналитические кейсы](/practice/sql/analytics/).

Решайте сами, без AI. Ответы откройте только после того, как попробовали сами: [разбор](/practice/sql/analytics/search-answers/).

## Как сейчас работает поиск

- В шапке каждой страницы есть строка поиска. Она предлагает искать людей, группы и обсуждения.
- Когда пользователь начинает печатать, появляется список лучших результатов. Он разбит по категориям: люди, обсуждения, файлы. Есть пункт «показать все результаты».
- Если пользователь нажимает Enter или «показать все результаты», он попадает на страницу результатов. Там вкладки по категориям. Результаты на каждой вкладке отсортированы по релевантности и по дате: свежие сообщения выше.
- На странице результатов есть «расширенный поиск». Он позволяет искать ещё раз внутри группы или за период.

## Задача

Команда продукта выбирает приоритеты на следующий цикл разработки. Они думают об улучшении поиска.

Каждая новая функция отнимает время у другой функции. Поэтому команда хочет знать:

- стоит ли вообще заниматься поиском;
- если стоит, что именно менять.

## Первый шаг: ориентация

Не открывайте данные сразу. Ответьте письменно на вопросы:

- Зачем пользователю поиск?
- Как понять, что поиск выполняет свою задачу?
- Как измерить качество поиска для одного пользователя?

:::tip
Подумайте, на каком уровне вы будете считать метрики. По пользователям? По дням? По отдельным событиям? Подсказка: качество поиска удобнее смотреть по сессиям. Разбор начинается с этого.
:::

## Данные

Нужны две таблицы. Данные не настоящие. Мы сгенерировали их сами.

### `tutorial.yammer_users`

Одна строка на пользователя.

| Колонка | Что это |
|---|---|
| `user_id` | Уникальный ID пользователя. |
| `created_at` | Когда пользователь зарегистрировался. |
| `state` | Статус: `active` или `pending`. |
| `activated_at` | Когда пользователь активировался. |
| `company_id` | ID компании. |
| `language` | Язык пользователя. |

### `tutorial.yammer_events`

Одна строка на событие.

| Колонка | Что это |
|---|---|
| `user_id` | Кто совершил событие. |
| `occurred_at` | Когда. |
| `event_type` | `signup_flow` (регистрация) или `engagement` (работа с продуктом). |
| `event_name` | Конкретное действие. |
| `location` | Страна (по IP). |
| `device` | Устройство. |
| `user_type` | Тип пользователя (число). |

Поиска касаются три события:

| Событие | Когда записывается |
|---|---|
| `search_autocomplete` | Пользователь выбрал результат из списка подсказок. |
| `search_run` | Пользователь запустил поиск и увидел страницу результатов. |
| `search_click_result_X` | Пользователь нажал на результат X на странице результатов. X от 1 до 10 — позиция результата. |

Остальные значения `event_name`: `login`, `home_page`, `send_message`, `like_message`, `view_inbox`, а также шаги регистрации `create_user`, `enter_email`, `enter_info`, `complete_signup`.

## Что нужно сделать

Проверьте свои гипотезы на данных. Ответьте на вопросы:

1. Хороший или плохой опыт у пользователей с поиском?
2. Стоит ли вообще работать над поиском?
3. Если стоит, что именно нужно улучшить?

Подготовьте короткий вывод для команды продукта. Показывайте цифры в небольших таблицах. Если вам не хватает данных для проверки важной гипотезы, напишите об этом.

И последний вопрос: как вы узнаете, что ваши предложения действительно улучшили поиск? Считайте, что предложенное уже сделано.
