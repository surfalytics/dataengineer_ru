## Модуль 1: Что такое Codex

**Codex** — AI-агент для разработки от OpenAI. Он читает ваш проект, пишет и меняет код, запускает команды и тесты, делает ревью. Вы ставите задачу обычным языком, а Codex выполняет её по шагам.

### Агент, а не чат

Обычный чат даёт ответ, а дальше всё делаете вы: копируете код, запускаете, исправляете ошибки. Агент работает в цикле:

1. Читает файлы проекта
2. Планирует изменения
3. Меняет код
4. Запускает команды: тесты, линтер, `dbt compile`
5. Смотрит на результат и исправляет ошибки
6. Повторяет, пока задача не готова

Ваша роль меняется. Вы ставите задачу, задаёте правила и проверяете результат.

### Где работает Codex

У Codex несколько «поверхностей». Все они используют один аккаунт и одни настройки.

| Где | Что это | Когда удобно |
|-----|---------|--------------|
| **CLI** | Агент в терминале. Открытый код (Apache-2.0) | Основная работа с кодом, скрипты, CI |
| **Расширение для IDE** | VS Code, Cursor, Windsurf. В JetBrains и Xcode — через их встроенные интеграции | Работа в привычном редакторе |
| **Приложение ChatGPT** | Десктоп для macOS, Windows, Linux. Параллельные чаты, worktree, задачи по расписанию | Несколько задач одновременно |
| **Облако** | Задачи выполняются на серверах OpenAI, в контейнере | Долгие задачи, пока вы заняты другим |
| **GitHub** | `@codex review` в комментарии к PR, автоматическое ревью | Ревью кода в команде |
| **Slack, Linear** | Задача из сообщения или issue | Командная работа |
| **SDK и GitHub Action** | `@openai/codex-sdk`, `openai/codex-action` | Свои инструменты и CI |

В этом курсе мы в основном работаем в **CLI**. Всё, что вы узнаете, работает и в других поверхностях.

### Модели

Codex работает на моделях семейства GPT-6.

| Модель | Особенность | Когда использовать |
|--------|-------------|--------------------|
| `gpt-6-astra` | Самая сильная | Сложная архитектура, трудные баги |
| `gpt-6.1-sol` | Почти как Astra, но дешевле. Контекст 500K токенов | Основная работа |
| `gpt-6.1-terra` | Быстрая (нужен CLI 0.159.0+) | Типовые задачи |
| `gpt-6-luna` | Самая дешёвая, высокие лимиты | Простые задачи, массовые правки |

Модели с `codex` в названии (например, `gpt-5.3-codex`) больше не используются. GPT-5.5 убрали из Codex для входа через ChatGPT 14 октября 2026 года.

**Уровень рассуждений** (`reasoning effort`) — сколько модель «думает» перед ответом:

| Уровень | Когда |
|---------|-------|
| `low` (в интерфейсе — Light) | Простые и чётко описанные задачи |
| `medium`, `high` | Сложные изменения, отладка |
| `xhigh`, `max` | Долгие автономные задачи |
| `ultra` | Самые сложные задачи. Codex сам запускает субагентов |

Больше рассуждений — лучше качество, но медленнее и дороже. Модель и уровень меняются командой `/model`.

### Итоги модуля

## Модуль 2: Установка и первый запуск

### Установка

```bash
# macOS и Linux — официальный скрипт (он же обновляет)
curl -fsSL https://chatgpt.com/codex/install.sh | sh

# Или через Homebrew
brew install --cask codex

# Или через npm
npm install -g @openai/codex

# Проверить версию
codex --version

# Обновить
codex update
```

**Windows:** Codex работает нативно, со своей песочницей. WSL2 нужен, только если вам нужны Linux-инструменты.

```powershell
powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"
```

### Вход

```bash
# Через браузер — аккаунт ChatGPT (рекомендуется)
codex login

# Сервер без браузера — вход по коду устройства (бета)
codex login --device-auth

# Через API-ключ
printenv OPENAI_API_KEY | codex login --with-api-key
```

| Способ | Плюсы | Минусы |
|--------|-------|--------|
| Аккаунт ChatGPT | Входит в подписку, есть облако и ревью в GitHub | Лимиты плана |
| API-ключ | Платите только за использование, удобно для CI | Нет облачных функций, можно потратить много |

Данные входа хранятся в `~/.codex/auth.json`. Это секрет — не коммитьте его и не показывайте агентам.

### Первый запуск

```bash
cd ~/projects/my-dbt-project
codex
```

Codex спросит, доверяете ли вы этой папке. Отвечайте «да» только для своих проектов. Для чужих репозиториев — нет. Настройки проекта (`.codex/config.toml`, хуки) загружаются только в доверенных папках.

Первая задача — пусть Codex изучит проект:

```text
Объясни структуру этого проекта. Какие есть модели dbt, как они связаны,
какие команды нужны для сборки и тестов?
```

Codex прочитает файлы и ответит. Он ничего не меняет, пока вы не попросите.

Следующий шаг — создать файл инструкций:

```text
/init
```

Команда создаст `AGENTS.md` — «README для агента». Подробнее — в [Модуле 4](#модуль-4-настройка-configtoml-и-agentsmd).

## Модуль 3: Безопасность: песочница и разрешения

Это главная сильная сторона Codex. **По умолчанию все команды выполняются в песочнице** — изолированной среде на уровне операционной системы. Изучите этот модуль до того, как дадите агенту реальную работу.

### Два механизма

Codex защищает вас двумя независимыми механизмами:

1. **Песочница** (`sandbox_mode`) — что команды могут делать технически
2. **Политика подтверждений** (`approval_policy`) — когда Codex спрашивает вас

### Режимы песочницы

| Режим | Что можно | Когда |
|-------|-----------|-------|
| `read-only` | Только читать файлы | Изучение проекта, ревью, CI |
| `workspace-write` | Читать и менять файлы в папке проекта. Сеть выключена | Обычная работа (по умолчанию в Git-папке) |
| `danger-full-access` | Всё, без ограничений | Только в контейнере или одноразовой VM |

Даже в `workspace-write` папки `.git`, `.codex`, `.agents` и `.aws` остаются только для чтения.

Как работает песочница:

| ОС | Технология |
|----|-----------|
| macOS | Seatbelt (встроенная песочница macOS) |
| Linux, WSL2 | bubblewrap |
| Windows | Нативная песочница Windows |

### Политика подтверждений

| Политика | Поведение |
|----------|-----------|
| `on-request` | Команды внутри песочницы — без вопросов. Выход из песочницы или сеть — спрашивает вас |
| `never` | Никогда не спрашивает. Что нельзя в песочнице — просто не выполняется |
| `granular` | Тонкая настройка по типам действий |

Значения `untrusted` и `on-failure` устарели. Если они есть в старом конфиге, удалите их: `untrusted` может помешать Codex запуститься.

### Режим «Auto»

Режим по умолчанию для работы — **Auto**: `workspace-write` + `on-request`. Codex свободно меняет файлы проекта и запускает тесты, но спрашивает разрешение на доступ к сети и файлам вне проекта.

Сменить режим: команда `/permissions` или флаги при запуске:

```bash
# Только чтение — для изучения чужого кода
codex --sandbox read-only

# Обычная работа
codex --sandbox workspace-write --ask-for-approval on-request
```

### Сеть

В `workspace-write` сеть **выключена**. Поэтому `pip install` или `dbt deps` не сработают без разрешения. Варианты:

- Codex спросит разрешение — подтвердите разово
- Включить сеть для проекта:

```toml
# .codex/config.toml
[sandbox_workspace_write]
network_access = true
```

Веб-поиск по умолчанию работает из кэша (`web_search = "cached"`). Живой поиск — флаг `--search`. Результаты из интернета — это **непроверенные данные**: на странице может быть скрытая инструкция для агента.

### Автоматическое ревью действий

Можно поручить проверку опасных действий отдельному агенту-ревьюеру, а не себе:

```toml
approvals_reviewer = "auto_review"   # по умолчанию "user"
```

Если ревьюер отклонил нужное действие, команда `/approve` повторит его один раз.

### Почему это важно: реальный случай

В июле 2026 года [Саймон Уиллисон описал](https://simonwillison.net/2026/Jul/16/bad-codex-bug/) случай: Codex работал в режиме полного доступа, без песочницы и без автоматического ревью. Агент попытался переопределить `$HOME` и в итоге **удалил домашнюю папку пользователя**.

Выводы:

- Не отключайте песочницу на своём компьютере
- Для полной автономии используйте контейнер или облако
- Делайте бэкапы и коммитьте часто

### Флаг, который не стоит использовать

```bash
# НЕ делайте так на рабочем компьютере
codex --yolo
# то же самое:
codex --dangerously-bypass-approvals-and-sandbox
```

Этот флаг отключает и песочницу, и подтверждения. Используйте его только внутри одноразового контейнера, где нечего терять.

### Правила для инженера данных

| Риск | Что делать |
|------|-----------|
| Агент запустит `DROP` или `DELETE` в production | Давайте доступ только к dev-базе. Пользователь БД — только чтение |
| Секреты в `profiles.yml`, `.env` | Держите их вне репозитория. Используйте переменные окружения |
| Агент прочитает персональные данные | Работайте на тестовых или обезличенных данных |
| Prompt injection через данные или issue | Не давайте агенту сразу доступ к секретам и к непроверенному тексту |

Добавьте правило в `AGENTS.md`:

```markdown
## Запрещено
- Никогда не запускай команды против production (target: prod).
- Не читай и не меняй profiles.yml, .env, файлы с ключами.
- Миграции — только на dev-базе.
```

### Итоги модуля

- Песочница включена по умолчанию — это защищает ваш компьютер
- Режим Auto (`workspace-write` + `on-request`) — хороший выбор для работы
- Сеть по умолчанию выключена
- `--yolo` — только в одноразовом контейнере
- Агенту — только dev-данные и права на чтение

## Модуль 4: Настройка: config.toml и AGENTS.md

У Codex два главных файла:

- **`config.toml`** — настройки инструмента: модель, песочница, MCP
- **`AGENTS.md`** — инструкции для агента: как устроен проект и какие правила

### config.toml

Личные настройки — `~/.codex/config.toml`. Настройки проекта — `.codex/config.toml` в репозитории.

```toml
# ~/.codex/config.toml
model = "gpt-6.1-sol"
model_reasoning_effort = "medium"
approval_policy = "on-request"
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
network_access = false

# Уведомление, когда задача закончена (любая команда)
notify = ["terminal-notifier", "-title", "Codex", "-message", "Готово"]

# Доверенные проекты
[projects."/Users/me/projects/my-dbt-project"]
trust_level = "trusted"
```

### Уровни настроек

Если одна настройка задана в нескольких местах, побеждает более высокий уровень:

| Приоритет | Где | Пример |
|-----------|-----|--------|
| 1 (высший) | Флаги командной строки | `codex -m gpt-6-luna`, `-c model_reasoning_effort=high` |
| 2 | `.codex/config.toml` в проекте (ближайший к текущей папке) | Общие настройки команды |
| 3 | Файл профиля | `~/.codex/ci.config.toml` |
| 4 | `~/.codex/config.toml` | Ваши личные настройки |
| 5 | Управляемые настройки компании | Через облако или `/etc/codex/config.toml` |
| 6 (низший) | Встроенные значения | — |

Настройки проекта загружаются **только для доверенных папок**. Компания может задать обязательные правила в `requirements.toml` — их нельзя переопределить.

### Профили

Профиль — отдельный файл с набором настроек. Например, для CI:

```toml
# ~/.codex/ci.config.toml
model = "gpt-6-luna"
model_reasoning_effort = "low"
approval_policy = "never"
sandbox_mode = "read-only"
```

```bash
codex exec --profile ci "Проверь SQL в папке models/ на ошибки"
```

Старый формат `[profiles.ci]` внутри `config.toml` в документации больше не описан. Используйте отдельные файлы.

### AGENTS.md

[AGENTS.md](https://agents.md/) — открытый стандарт. Его читают Codex, Cursor, Copilot, Antigravity, OpenCode и Claude Code (если нет `CLAUDE.md`). Один файл — правила для всех агентов в команде.

**Как Codex ищет файлы:**

1. Глобальный файл: `~/.codex/AGENTS.override.md`, если нет — `~/.codex/AGENTS.md`
2. Потом от корня Git-репозитория до текущей папки — по одному файлу в каждой папке
3. В каждой папке: сначала `AGENTS.override.md`, потом `AGENTS.md`
4. Файлы склеиваются от корня к текущей папке. Ближайший файл идёт последним, поэтому его правила главнее

Общий лимит — **32 KiB** (`project_doc_max_bytes`). Если у команды уже есть файл с другим именем, добавьте его:

```toml
project_doc_fallback_filenames = ["TEAM_GUIDE.md"]
```

### Пример AGENTS.md для dbt-проекта

```markdown
# AGENTS.md

## Проект
dbt-проект аналитического хранилища на Snowflake.
- models/staging/ — очистка источников, префикс stg_
- models/intermediate/ — промежуточная логика, префикс int_
- models/marts/ — витрины, префиксы fct_ и dim_

## Команды
- Установка: `uv sync && dbt deps`
- Проверка: `dbt compile --select <модель>`
- Сборка и тесты: `dbt build --select <модель> --target dev`
- Линтер SQL: `sqlfluff lint models/`

## Правила
- Каждый источник объявлен в `_sources.yml` до использования.
- На каждом первичном ключе — тесты `unique` и `not_null`.
- CTE вместо подзапросов. Ключевые слова SQL — в нижнем регистре.
- Таблицы больше 1 млн строк в день — `incremental`.
- У каждой модели есть описание в `.yml`.

## Запрещено
- Никогда не используй `--target prod`.
- Не меняй profiles.yml и файлы с секретами.
- Не удаляй модели без подтверждения.

## Готово, когда
- `dbt build --select <изменённые модели>+` проходит без ошибок.
- `sqlfluff lint` без ошибок.
- Описания и тесты добавлены.
```

### Советы по AGENTS.md

- **Начните с `/init`**, потом отредактируйте руками
- **Коротко.** Это не документация проекта, а инструкция для агента
- **Обязательно укажите команды** сборки, тестов и линтера. Без них агент не может себя проверить
- **Добавляйте правила по опыту.** Агент дважды сделал одну ошибку — добавьте правило
- **Длинные инструкции — в отдельные файлы.** Например, `docs/code_review.md`, а в `AGENTS.md` — ссылка
- **В монорепозитории** — свой `AGENTS.md` в каждой большой папке: `dbt/AGENTS.md`, `airflow/AGENTS.md`

Можно попросить Codex самого улучшить файл:

```text
Ты дважды забыл добавить тесты на первичный ключ. Сделай ретроспективу:
почему так вышло, и предложи правку в AGENTS.md, чтобы это не повторилось.
```

### Итоги модуля

- `config.toml` — настройки инструмента, `AGENTS.md` — правила проекта
- Приоритет: флаги → проект → профиль → пользователь → компания
- Профили — отдельные файлы `~/.codex/<имя>.config.toml`
- В `AGENTS.md` главное — команды проверки и критерии «готово»

## Модуль 5: Как ставить задачи

Качество работы агента зависит от постановки задачи. Хорошая задача похожа на хороший тикет в Jira.

### Четыре части хорошей задачи

OpenAI рекомендует такую структуру:

| Часть | Что написать | Пример |
|-------|-------------|--------|
| **Цель** | Что нужно сделать | Добавить витрину выручки по дням |
| **Контекст** | Какие файлы, ошибки, документы важны | `@models/staging/stg_orders.sql`, текст ошибки |
| **Ограничения** | Правила и рамки | Не меняй существующие модели, только incremental |
| **Готово, когда** | Как проверить результат | `dbt build` проходит, тесты добавлены |

**Плохо:**

```text
Сделай витрину по выручке
```

**Хорошо:**

```text
Цель: создай модель fct_daily_revenue — выручка по дням и странам.

Контекст: источник — @models/staging/stg_orders.sql и @models/staging/stg_payments.sql.
Выручка = сумма payments.amount для заказов со статусом 'completed'.

Ограничения:
- materialized='incremental', ключ — order_date
- не меняй staging-модели

Готово, когда:
- dbt build --select fct_daily_revenue --target dev проходит
- есть тесты unique и not_null на (order_date, country)
- есть описание модели и колонок в .yml
```

### Режим планирования

Для сложных задач сначала попросите план. Включите `/plan` или нажмите `Shift+Tab`. Codex изучит код и предложит план, но ничего не будет менять.

Полезный приём — попросите Codex задать вам вопросы:

```text
/plan Нужно перенести 15 моделей из Redshift в Snowflake.
Прежде чем предлагать план, задай мне вопросы о том, что тебе неясно.
Оспорь мои предположения, если видишь риски.
```

Для долгих задач попросите сохранить план в файл `PLANS.md`. Агент будет отмечать выполненные шаги. Если сессия прервётся, новая сессия продолжит по плану.

### Режим цели: /goal

`/goal` запускает Codex в цикле: он работает, пока сам не решит, что цель достигнута.

```text
/goal Все тесты в tests/ проходят, и dbt build --target dev без ошибок.
```

Используйте с осторожностью: долгий цикл тратит много лимитов. Цель должна быть проверяемой — тест, команда, конкретный результат.

### Управление контекстом

Контекст — это «рабочая память» агента. Когда он переполнен, качество падает.

| Ситуация | Что делать |
|----------|-----------|
| Новая задача | `/new` — начните новый разговор |
| Разговор стал длинным | `/compact` — сжать историю |
| Хотите попробовать другой подход | `/fork` — ветка разговора |
| Быстрый вопрос в стороне | `/side` — не засоряет основной разговор |
| Вернуться к вчерашней задаче | `/resume` или `codex resume` |

**Правило:** один разговор — одна задача. Не ведите весь проект в одном чате.

### Выбор модели и уровня рассуждений

| Задача | Модель | Уровень |
|--------|--------|---------|
| Переименовать колонку во всех моделях | Luna | `low` |
| Написать новую dbt-модель с тестами | Sol | `medium` |
| Найти причину расхождения в цифрах | Sol | `high` |
| Спроектировать новый слой хранилища | Astra | `high` |
| Перенести проект на другую СУБД | Sol или Astra | `xhigh` + `/plan` |

### Итоги модуля

- Задача = цель + контекст + ограничения + «готово, когда»
- Сложное — сначала `/plan`, долгое — с `PLANS.md`
- `/goal` — для проверяемых целей
- Один разговор — одна задача

## Модуль 6: Практика: задачи инженера данных

В этом модуле — готовые сценарии. Копируйте промпты и адаптируйте под свой проект.

### Сценарий 1: Новая dbt-модель с тестами

```text
Создай модель int_customer_orders: для каждого клиента — число заказов,
сумма, дата первого и последнего заказа.
Источники: @models/staging/stg_customers.sql, @models/staging/stg_orders.sql.
Добавь тесты и описание в .yml. Проверь через dbt build --select int_customer_orders --target dev.
```

**На что смотреть при проверке:**

- Правильный ли JOIN (не теряются ли клиенты без заказов?)
- Правильное ли зерно (одна строка на клиента?)
- Существуют ли колонки, которые использует агент

Агент может написать правдоподобный SQL с **несуществующими колонками** или неверным JOIN. Поэтому в `AGENTS.md` обязательно должна быть команда `dbt compile` или `dbt build` — агент сам увидит ошибку.

### Сценарий 2: Ревью и рефакторинг SQL

```text
/plan Проверь @models/marts/fct_sales.sql:
- есть ли проблемы с производительностью
- нет ли дублей из-за JOIN
- соответствует ли стилю из AGENTS.md
Предложи изменения, но не меняй файл, пока я не одобрю план.
```

### Сценарий 3: Миграция на другую СУБД

Например, перенос с Redshift на Snowflake.

1. Сначала используйте детерминированный конвертер, если он есть. Например, [SnowConvert](https://docs.snowflake.com/en/migrations/snowconvert-docs/general/about) для Snowflake
2. Потом поручите Codex то, что конвертер не смог:

```text
/plan Мы переносим модели из папки models/legacy_redshift/ на Snowflake.
SnowConvert уже обработал синтаксис. Найди оставшиеся проблемы:
DISTKEY/SORTKEY, функции дат, GETDATE(), NVL2, разницу в типах.
Создай PLANS.md со списком моделей и статусом каждой.
Переноси по одной модели и после каждой запускай dbt build --select <модель> --target dev.
```

3. Сравните данные: попросите агента написать запросы для сверки числа строк и сумм между старой и новой системой

### Сценарий 4: DAG в Airflow

```text
Создай DAG dags/daily_sales.py:
- запуск каждый день в 06:00 UTC
- шаги: загрузка из S3 → dbt build --select tag:daily → проверка свежести данных
- TaskFlow API, retries=2
- подключения только через Airflow Connections, никаких паролей в коде
Проверь синтаксис через python -c "import dags.daily_sales".
```

### Сценарий 5: Разбор упавшего пайплайна

```text
Вот лог упавшей задачи: @logs/dbt_run_2026-11-02.log
Найди причину. Сначала объясни, что пошло не так, потом предложи исправление.
Не меняй файлы, пока я не подтвержу.
```

Если причина в данных, а не в коде, Codex должен это сказать. Попросите его написать SQL-запрос, который покажет проблемные строки.

### Сценарий 6: Анализ файла с DuckDB

```text
В папке data/ лежит events.parquet. С помощью DuckDB:
1. Покажи схему и число строк
2. Найди дубли по event_id
3. Посчитай события по дням за последний месяц
4. Сохрани скрипт анализа в analysis/events_check.py
```

DuckDB работает без сервера, поэтому Codex справится в песочнице. Если DuckDB не установлен, понадобится сеть для установки — Codex спросит разрешение.

### Сценарий 7: Документация

```text
Для всех моделей в models/marts/ без описания:
- добавь описание модели и всех колонок в .yml
- описание бери из логики SQL, не выдумывай
- если смысл колонки неясен — оставь TODO и выпиши список в конце
```

### Сценарий 8: Проверки качества данных

```text
Для модели fct_orders добавь проверки качества:
- уникальность order_id
- amount >= 0
- order_date не в будущем
- каждый customer_id есть в dim_customers
Используй стандартные тесты dbt и dbt_utils, где можно.
```

### Сценарий 9: Изучение чужого проекта

```bash
codex --sandbox read-only
```

```text
Я новый человек в команде. Объясни:
1. Откуда приходят данные и куда уходят
2. Какие модели самые важные (на них больше всего ссылок)
3. Где самая сложная логика
4. Какие есть проблемы и технический долг
Нарисуй схему потоков данных в формате Mermaid.
```

Режим `read-only` гарантирует, что агент ничего не изменит.

### Итоги модуля

- Codex хорош для dbt-моделей, SQL-ревью, миграций, DAG и документации
- Всегда давайте агенту способ проверить себя: `dbt build`, тесты, линтер
- Проверяйте JOIN, зерно и названия колонок — тут агенты ошибаются чаще всего
- Для изучения кода — режим `read-only`

## Модуль 7: Расширения: MCP, Skills, субагенты, хуки

### MCP — подключение внешних инструментов

[MCP](https://modelcontextprotocol.io/) (Model Context Protocol) — стандарт подключения агентов к внешним системам: базам данных, dbt, GitHub, документации.

```bash
# Добавить локальный сервер
codex mcp add context7 -- npx -y @upstash/context7-mcp

# Добавить удалённый сервер
codex mcp add docs --url https://example.com/mcp

# Вход через OAuth
codex mcp login docs

# Список
codex mcp list
```

Или в `config.toml`:

```toml
# MCP-сервер dbt
[mcp_servers.dbt]
command = "uvx"
args = ["dbt-mcp"]
env = { DBT_PROJECT_DIR = "/Users/me/projects/my-dbt-project" }
startup_timeout_sec = 20
```

**Полезные MCP-серверы для данных:**

| Сервер | Что даёт |
|--------|---------|
| [dbt MCP](https://github.com/dbt-labs/dbt-mcp) | Модели, lineage, запуск dbt |
| [MCP Toolbox for Databases](https://github.com/googleapis/mcp-toolbox) | BigQuery, PostgreSQL и другие базы |
| [ClickHouse MCP](https://github.com/ClickHouse/mcp-clickhouse) | Запросы к ClickHouse |
| Snowflake managed MCP | SQL, Cortex Search, Cortex Analyst |
| GitHub MCP | Issues, PR |

**Совет:** начните с 1–2 серверов. Каждый сервер занимает место в контексте и расходует лимиты. Подключайте базу пользователем **только с правами на чтение**.

### Skills — навыки

Skill — папка с инструкцией `SKILL.md` и, при желании, скриптами. Это повторяемый рабочий процесс, который агент выполняет по запросу.

**Правило:** если вы третий раз пишете один и тот же промпт — сделайте из него skill.

Где хранятся:

| Где | Для кого |
|-----|---------|
| `.agents/skills/` в репозитории | Вся команда |
| `~/.agents/skills/` | Только вы |
| `/etc/codex/skills/` | Все пользователи компьютера (администратор) |

Пример — `.agents/skills/dbt-new-model/SKILL.md`:

```markdown
---
name: dbt-new-model
description: Создание новой dbt-модели по стандартам команды. Используй, когда просят создать модель, витрину, staging или intermediate.
---

# Новая dbt-модель

1. Определи слой: staging (stg_), intermediate (int_) или mart (fct_/dim_).
2. Проверь, что источники объявлены в _sources.yml.
3. Напиши SQL по стилю из AGENTS.md: CTE, нижний регистр.
4. Добавь в .yml: описание модели и колонок, тесты unique и not_null на ключ.
5. Запусти: dbt build --select <модель> --target dev
6. Если тест упал — исправь и запусти снова.
7. В конце покажи: путь к файлам, зерно модели, список тестов.
```

Вызвать skill:

- Явно: `$dbt-new-model создай витрину возвратов`
- Через меню: `/skills`
- Автоматически: Codex сам выберет skill по описанию. Поэтому пишите в `description` ключевые слова

Встроенные skills: `$skill-creator` (создаёт новый skill) и `$skill-installer` (ставит готовые). Готовые skills для dbt публикует dbt Labs: [dbt-agent-skills](https://github.com/dbt-labs/dbt-agent-skills).

### Субагенты

Субагент — отдельный агент со своей ролью, моделью и инструкциями. Главный агент поручает ему часть работы. Это экономит контекст главного агента.

Встроенные: `default`, `worker`, `explorer`. Свои — TOML-файлы в `.codex/agents/` или `~/.codex/agents/`:

```toml
# .codex/agents/sql-reviewer.toml
name = "sql-reviewer"
description = "Ревью SQL и dbt-моделей: ошибки JOIN, зерно, производительность, стиль."
model = "gpt-6.1-terra"
model_reasoning_effort = "medium"
developer_instructions = """
Ты ревьюер SQL в команде данных.
Проверь: дубли из-за JOIN, правильность зерна, фильтры по датам,
NULL в ключах, производительность на больших таблицах.
Не меняй файлы. Верни список проблем с файлом и строкой.
"""
```

Как запустить — попросите обычными словами:

```text
Запусти двух субагентов sql-reviewer параллельно: один проверяет models/marts/,
второй — models/intermediate/. Собери их замечания в одну таблицу.
```

Субагент не может переопределить песочницу, политику подтверждений и MCP-серверы — они наследуются от главной сессии.

### Хуки

Хук — команда, которая автоматически выполняется при событии. Например, запуск линтера после правки файла или блокировка опасной команды.

Где хранятся: `~/.codex/hooks.json`, `.codex/hooks.json` в проекте (только для доверенных папок) или секция `[hooks]` в `config.toml`.

**События:** `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `PreCompact`, `PostCompact`, `SubagentStart`, `SubagentStop`, `Stop` и другие.

Формат: событие → `matcher` (регулярное выражение по имени инструмента) → список команд. Если команда завершается с кодом **2**, действие блокируется, а текст из stderr получает агент.

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "sqlfluff lint models/ --format github-annotation-native || true",
            "timeout": 60,
            "statusMessage": "Проверяю SQL линтером"
          }
        ]
      }
    ]
  }
}
```

Посмотреть загруженные хуки — команда `/hooks`. Точные имена инструментов для `matcher` и все поля — в [документации по хукам](https://learn.chatgpt.com/codex/hooks).

### Плагины

Плагин — способ поделиться набором skills, MCP-серверов и хуков. Команды: `codex plugin` и `codex plugin marketplace`. Ставьте плагины только из проверенных источников: плагин может запускать любые команды.

### Итоги модуля

- MCP — доступ к dbt, базам, GitHub. Начните с 1–2 серверов
- Skills — повторяемые процессы в `.agents/skills/`. Вызов — `$имя`
- Субагенты — TOML в `.codex/agents/`, для ревью и параллельных задач
- Хуки — автоматические проверки, код 2 блокирует действие

## Модуль 8: Параллельная работа и облако

Самый большой выигрыш от агента — когда вы не ждёте его, а делаете несколько задач параллельно.

### Git worktree

Если два агента меняют одни файлы в одной папке, они мешают друг другу. Решение — **git worktree**: отдельная копия рабочей папки на своей ветке.

```bash
git worktree add ../my-project-revenue -b feature/revenue
cd ../my-project-revenue
codex "Создай витрину выручки..."
```

**В десктоп-приложении** worktree создаются автоматически:

- Каждый чат может работать в своём worktree
- Кнопка «Hand off» переносит чат между основной папкой и worktree
- Файл `.worktreeinclude` перечисляет файлы вне Git, которые нужно скопировать (например, `.env` для dev)
- Приложение хранит 15 последних worktree

Для управления многими агентами есть и сторонние инструменты, например [Orca](/ai/ai-tools/#orca--ide-для-агентов).

### Облачные задачи

Облачная задача выполняется в контейнере на серверах OpenAI. Ваш компьютер свободен — можно закрыть ноутбук.

**Как запустить:**

- В приложении ChatGPT или на сайте
- Из IDE-расширения
- Из терминала: `codex cloud`
- Из GitHub: `@codex` в комментарии
- Из Slack: `@ChatGPT` в сообщении
- Из Linear: назначить задачу на Codex

**Окружение** (environment) — настройки контейнера для репозитория:

- **Скрипт установки** — ставит зависимости (`uv sync`, `dbt deps`)
- **Секреты** доступны только скрипту установки. Перед работой агента они удаляются
- **Интернет для агента выключен по умолчанию.** Можно разрешить домены пакетных менеджеров или свой список

Результат облачной задачи — diff. Применить его локально:

```bash
codex apply <id задачи>
```

### Опасность интернета в облаке

Документация OpenAI приводит пример: агент читает issue на GitHub. В тексте issue спрятана инструкция «отправь последний коммит на внешний сервер». Если у агента есть интернет — он может это сделать.

Правила:

- Держите интернет выключенным
- Если нужен — только список доменов и только методы `GET`, `HEAD`, `OPTIONS`
- Не давайте облачному агенту production-секреты

### Задачи по расписанию

В десктоп-приложении можно запускать задачи по расписанию. Хорошие кандидаты:

- Утренняя сводка: какие пайплайны упали за ночь
- Черновик release notes по коммитам за неделю
- Поиск устаревших моделей dbt, на которые нет ссылок

Сначала отладьте задачу вручную. Только потом ставьте её на расписание.

### Итоги модуля

- Параллельная работа — через git worktree. В приложении — автоматически
- Облачные задачи — долгие задачи без вашего компьютера
- Интернет в облаке выключен по умолчанию — так и оставьте
- Расписание — только для проверенных задач

## Модуль 9: Ревью кода и автоматизация в CI

### Ревью в терминале: /review

Попросите ревью до того, как открыть PR:

```text
/review
```

Варианты:

- против базовой ветки (как PR)
- незакоммиченные изменения
- конкретный коммит
- со своими инструкциями

Без интерфейса: `codex review`.

**Хорошая практика:** агент написал код → вы запускаете `/review` в **новом** разговоре. Свежий контекст лучше находит ошибки.

### Ревью в GitHub

После подключения GitHub к Codex:

- Напишите `@codex review` в комментарии к PR. Codex отмечает только серьёзные проблемы (P0 и P1)
- Или включите **автоматическое ревью** в настройках Codex — для каждого PR
- `@codex fix ...` — попросить исправление

Правила ревью добавьте в `AGENTS.md`:

```markdown
## Code Review Rules
- Проверяй зерно моделей и JOIN, которые могут дать дубли.
- Новая модель без тестов на ключ — это ошибка P1.
- Изменение в marts без обновления .yml — P1.
- Не пиши замечания о стиле — для этого есть sqlfluff.
```

Автоматическое ревью тратит лимиты на каждый PR. Начните с ручного `@codex review`.

### codex exec — Codex в скриптах

`codex exec` запускает задачу без интерфейса. Прогресс идёт в stderr, финальный ответ — в stdout.

```bash
# По умолчанию — только чтение
codex exec "Найди модели dbt без тестов на первичный ключ"

# С правом менять файлы
codex exec --sandbox workspace-write "Добавь описания колонок в models/marts/*.yml"

# Промпт из файла
codex exec - < prompts/weekly_check.md

# Сохранить финальный ответ в файл
codex exec -o report.md "Сделай release notes по последним 10 коммитам"

# События в JSONL — для разбора скриптом
codex exec --json "..."

# Продолжить прошлую сессию
codex exec resume --last "Теперь исправь найденные проблемы"
```

| Флаг | Что делает |
|------|-----------|
| `--sandbox` | `read-only` (по умолчанию), `workspace-write`, `danger-full-access` |
| `--ask-for-approval`, `-a` | Политика подтверждений |
| `-o`, `--output-last-message` | Записать финальный ответ в файл |
| `--output-schema` | Ответ строго по JSON-схеме |
| `--json` | Поток событий в JSONL |
| `--ephemeral` | Не сохранять сессию |
| `--skip-git-repo-check` | Разрешить запуск вне Git-репозитория |
| `--profile` | Использовать профиль |

Флаг `--full-auto` **больше не поддерживается**. Вместо него — `--sandbox workspace-write`. В старых статьях встречаются флаги `--approval-mode` и `--sandbox-permissions` — они тоже устарели.

### Структурированный ответ

`--output-schema` заставляет Codex вернуть JSON по схеме. Это удобно, если результат читает скрипт.

```json
{
  "type": "object",
  "properties": {
    "findings": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "file": { "type": "string" },
          "line": { "type": "integer" },
          "priority": { "type": "integer", "minimum": 0, "maximum": 3 },
          "title": { "type": "string" },
          "body": { "type": "string" }
        },
        "required": ["file", "line", "priority", "title", "body"],
        "additionalProperties": false
      }
    },
    "overall_correctness": { "type": "string", "enum": ["patch is correct", "patch is incorrect"] }
  },
  "required": ["findings", "overall_correctness"],
  "additionalProperties": false
}
```

```bash
codex exec --sandbox read-only \
  --output-schema review-schema.json \
  -o review.json \
  - < prompts/review.md
```

### GitHub Action для ревью PR

Официальное действие — [`openai/codex-action`](https://github.com/openai/codex-action). Рекомендуемая схема — **два job**:

1. Codex работает с правами **только на чтение** и возвращает текст
2. Отдельный job **без API-ключа** публикует комментарий

Так ключ и права на запись никогда не встречаются в одном месте.

```yaml
# .github/workflows/codex-review.yml
name: Codex PR review

on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    outputs:
      message: ${{ steps.codex.outputs.final-message }}
    steps:
      - uses: actions/checkout@v5
        with:
          fetch-depth: 0
          persist-credentials: false

      - id: codex
        uses: openai/codex-action@v1
        with:
          openai-api-key: ${{ secrets.OPENAI_API_KEY }}
          prompt-file: .github/codex/prompts/review.md
          sandbox: read-only

  comment:
    needs: review
    runs-on: ubuntu-latest
    permissions:
      pull-requests: write
    steps:
      - uses: actions/github-script@v7
        env:
          MESSAGE: ${{ needs.review.outputs.message }}
        with:
          script: |
            await github.rest.issues.createComment({
              owner: context.repo.owner,
              repo: context.repo.repo,
              issue_number: context.issue.number,
              body: process.env.MESSAGE,
            });
```

Пример промпта `.github/codex/prompts/review.md`:

```markdown
Сделай ревью изменений этого PR относительно основной ветки.
Это dbt-проект. Правила — в AGENTS.md, раздел Code Review Rules.
Отмечай только реальные проблемы, которые внёс этот PR.
Для каждой проблемы — файл, строка и почему это ошибка.
Без замечаний о стиле.
```

### Правила безопасности для CI

- Ограничьте, кто может запускать workflow (параметр `allow-users`)
- Текст PR, коммиты и issues — **непроверенные данные**. В них может быть скрытая инструкция
- `CODEX_API_KEY` или `OPENAI_API_KEY` — только на шаге с Codex, не на весь job
- Не используйте `safety-strategy: unsafe` на общих runner
- Режим `read-only` не защищает секреты, которые уже есть в окружении
- Для API-ключа поставьте лимит расходов

### Другие идеи для CI

| Задача | Как |
|--------|-----|
| Исправить упавший CI | Workflow на событие `workflow_run` с `failure`. Codex пишет патч, отдельный job создаёт PR |
| Release notes | `codex exec -o notes.md "release notes по коммитам с прошлого тега"` |
| Проверка документации | Раз в неделю: найти модели без описаний, создать issue |
| Проверка миграций | Перед merge: нет ли `DROP` и `TRUNCATE` в новых миграциях |

### Итоги модуля

- `/review` в новом разговоре — перед каждым PR
- `@codex review` в GitHub, правила — в `AGENTS.md`
- `codex exec` — для скриптов и CI, по умолчанию только чтение
- GitHub Action — два job: чтение с ключом, запись без ключа

## Модуль 10: Лимиты и стоимость

### Как считаются лимиты

При входе через ChatGPT у вас есть лимиты на **5-часовое окно**. Могут быть и недельные лимиты. Посмотреть текущее использование — `/status` или `/usage`.

Примерное число сообщений за 5 часов на плане Plus:

| Модель | Сообщений |
|--------|-----------|
| GPT-6 Astra | 5–45 |
| GPT-6.1 Sol | 15–160 |
| GPT-6.1 Terra | 35–285 |
| GPT-6 Luna | 350–3000 |

Разброс большой: короткая задача тратит мало, долгая с большим контекстом — много.

Что тратит лимиты быстрее:

- Облачные задачи — дороже локальных
- Режим `/fast` — в 2 раза дороже
- Высокий уровень рассуждений
- Большой контекст, много MCP-серверов
- Автоматическое ревью каждого PR

Когда лимиты закончились, можно использовать **кредиты** (на планах Plus и Pro их можно докупить). Luna примерно в 20 раз дешевле Sol по кредитам.

### Как экономить

| Совет | Почему работает |
|-------|----------------|
| Luna для простых задач | Лимиты в десятки раз выше |
| `low` для чётких задач | Меньше токенов на рассуждения |
| Точная задача с `@файлами` | Агент меньше ищет по проекту |
| Хороший `AGENTS.md` | Агент не изучает проект заново каждый раз |
| Короткий `AGENTS.md` | Он загружается в каждый разговор |
| Отключите ненужные MCP | Их описание занимает контекст |
| `/new` для новой задачи | Не таскайте старый контекст |
| Локально, а не в облаке | Облачные задачи дороже |
| Лимит для API-ключа | Защита от неожиданного счёта |

### API-ключ или подписка

| | Подписка ChatGPT | API-ключ |
|---|---|---|
| Оплата | Фиксированная в месяц | За токены |
| Облако, GitHub, Slack | Да | Нет |
| CI | Можно, но неудобно | Удобно |
| Риск большого счёта | Нет | Есть — ставьте лимит |

Частый вариант: подписка для работы, отдельный API-ключ с лимитом — для CI.

### Итоги модуля

- Лимиты — на 5 часов и на неделю. Проверка — `/status`
- Экономия: Luna, `low`, точные задачи, короткий `AGENTS.md`
- Для CI — отдельный API-ключ с лимитом расходов

## Модуль 11: Лучшие практики и частые ошибки

### 10 правил работы с Codex

1. **Начните с `AGENTS.md`.** Команды сборки, тестов, линтера и критерии «готово»
2. **Дайте агенту способ проверить себя.** Без тестов агент не знает, что ошибся
3. **Ставьте задачу как тикет.** Цель, контекст, ограничения, «готово, когда»
4. **Сложное — сначала `/plan`.** Попросите задать вопросы
5. **Маленькие шаги.** Одна модель, один DAG, одна миграция за раз
6. **Один разговор — одна задача.** `/new` между задачами
7. **Коммитьте часто.** Легко откатиться, если агент ушёл не туда
8. **Ревью всегда.** `/review` в новом разговоре, потом своими глазами
9. **Песочница включена.** Полный доступ — только в контейнере
10. **Повторяющееся — в skill.** Третий раз пишете тот же промпт — пора

### Частые ошибки

| Ошибка | Что будет | Как правильно |
|--------|-----------|---------------|
| Правила в каждом промпте | Агент забывает, вы устаёте | Правила — в `AGENTS.md` |
| Нет команд тестов | Агент «закончил», но код не работает | Команды в `AGENTS.md` |
| Сложная задача без плана | Агент уходит не туда | `/plan` |
| Полный доступ с первого дня | Риск потерять файлы | Режим Auto, полный доступ — в контейнере |
| Параллельные агенты в одной папке | Конфликты правок | git worktree |
| Смотреть, как агент работает | Вы теряете время | Запускайте другую задачу параллельно |
| Весь проект в одном чате | Контекст переполнен, качество падает | `/new`, `/compact` |
| Доверять SQL без проверки | Неверные JOIN, лишние строки | `dbt build`, сверка цифр |
| Доступ агента к production | Можно потерять данные | Только dev и права на чтение |

### Чеклист проверки результата

Перед merge кода от агента:

- [ ] Тесты и `dbt build` проходят
- [ ] Зерно модели правильное, нет дублей
- [ ] JOIN не теряют и не размножают строки
- [ ] Колонки и таблицы существуют
- [ ] Цифры сходятся с известным результатом (сверка)
- [ ] Нет секретов и паролей в коде
- [ ] Нет команд против production
- [ ] Описания и тесты добавлены
- [ ] Вы понимаете каждую строку изменений

Последний пункт — самый важный. Если не понимаете код — попросите Codex объяснить его.

## Модуль 12: Codex и Claude Code

Многие команды используют оба агента. Это нормально: ревью другой моделью находит другие ошибки.

### Сравнение

| | Codex | Claude Code |
|---|---|---|
| Компания | OpenAI | Anthropic |
| Модели | GPT-6 | Claude Opus, Sonnet, Haiku 5.5, Fable 5.1 |
| Песочница | Включена по умолчанию на уровне ОС | Есть (`/sandbox`), режимы разрешений |
| Облачные задачи | Да, встроены | Есть, но это не главный сценарий |
| Ревью в GitHub | `@codex review`, автоматическое | Через GitHub Action и плагины |
| Расширяемость | Skills, хуки, плагины, субагенты | Очень богатая: skills, хуки, плагины, субагенты, Agent Teams |
| Инструкции | `AGENTS.md` | `CLAUDE.md` (читает и `AGENTS.md`) |
| Открытый код CLI | Да | Нет |

По отзывам инженеров, которые работают с обоими:

- **Codex сильнее:** долгие задачи по инструкции, делегирование в облако, ревью кода, стоимость
- **Claude Code сильнее:** интерактивная работа, расширяемость, сложные рабочие процессы со своими инструментами

Сравнения и бенчмарки быстро устаревают. Лучший способ выбрать — дать обоим одну и ту же задачу из вашего проекта.

### Таблица соответствия

| Что | Codex | Claude Code |
|-----|-------|-------------|
| Инструкции проекта | `AGENTS.md` | `CLAUDE.md` |
| Настройки | `~/.codex/config.toml`, `.codex/config.toml` | `~/.claude/settings.json`, `.claude/settings.json` |
| Планирование | `/plan`, `Shift+Tab` | Режим Plan, `Shift+Tab` |
| Разрешения | `/permissions` | `/permissions`, `Shift+Tab` |
| Skills | `.agents/skills/`, вызов `$имя` | `.claude/skills/`, вызов `/имя` |
| Субагенты | `.codex/agents/*.toml` | `.claude/agents/*.md` |
| Хуки | `hooks.json` | `hooks` в `settings.json` |
| MCP | `codex mcp add` | `claude mcp add` |
| Без интерфейса | `codex exec` | `claude -p` |
| Ревью | `/review` | `/code-review` |
| Продолжить сессию | `codex resume` | `claude --continue` |

### Один репозиторий — два агента

Держите общие правила в `AGENTS.md`. В `CLAUDE.md` подключите его и добавьте только специфичное для Claude Code:

```markdown
# CLAUDE.md
@AGENTS.md

## Только для Claude Code
- Используй субагента sql-reviewer после изменений в models/
```

Skills из `.agents/skills/` читают Codex, Cursor и другие агенты. Переход с Claude Code или Cursor упрощает команда `/import`.
