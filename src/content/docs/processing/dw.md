Хранилище данных (аналитическое хранилище данных) — система, которая хранит большие объёмы данных в одном месте и позволяет их обрабатывать и анализировать. На этих данных компания принимает обоснованные решения (data-driven подход).

## Базовая архитектура хранилищ данных

Самая простая архитектура DWH состоит из четырёх компонентов:

1. **Системы-источники данных**

- транзакционные базы данных (например, база данных CRM-системы)
- приложения и системы, отправляющие данные с помощью программных интерфейсов (API) (например, API рекламных кабинетов: Яндекс.Метрика и т.п.)
- внешние открытые данные (пример: данные о курсе валют с открытого ресурса, забираемые парсингом или через API)
- файлы и документы (пример: папки с Excel-файлами в Google Drive или таблицы Google Sheets)

Источников данных может быть очень много, и чтобы их данные попали в аналитическое хранилище, нужно построить *data pipeline* (поток данных). Это похоже на водопровод: 

ключи и подземные источники ➔ строим трубопровод, очистительные сооружения ➔ вода попадает потребителям

С данными так же: роль родников играют источники данных. Чтобы данные попали из источников в DWH, нужны `pipeline` (трубы) и процессы выгрузки, трансформации и загрузки данных.

2. **Потоки данных (ETL/ELT)**

ETL-процесс — процесс извлечения (extract), преобразования (transform) и загрузки (load) данных из системы-источника в DWH. Подробнее о подходах ETL/ELT и инструментах — в разделе *ETL/ELT (Batch)*.

![Схема ETL процесса](/assets/etlschema.png)

3. **Хранение данных**

Главный компонент DWH — система хранения данных. Эту роль могут играть различные аналитические базы данных и платформы для хранения, например Greenplum, ClickHouse, Snowflake, Amazon Redshift, Google BigQuery и др. Система хранения выполняет три функции: 
- обеспечение надёжного хранения большого объёма данных
- предоставление доступа к данным на чтение/редактирование/удаление/вставку согласно ролевой модели и правам доступа пользователей
- обеспечение вычислительных ресурсов и возможностей для аналитики над данными

Данные в хранилище обычно раскладывают по слоям (layers). В самом базовом сценарии обычно выделяют 3 слоя:
- raw layer — необработанные данные, которые попали из источника
- core layer — обработанные данные, приведённые к единому виду и разложенные по сущностям хранилища
- business layer — подготовленные данные для отчётности или более детальной аналитики пользователями, витрины данных (*data marts*)

На практике каждая компания сама выбирает конфигурацию хранилища и слоёв данных, которая подходит под требования и ключевые задачи конкретного бизнеса. 

4. **BI-решения**

Слой BI показывает результаты анализа данных из хранилища в виде графиков и отчётов и доносит их до бизнес-пользователей. Бизнесу нужны оцифрованные метрики в формах, удобных для принятия решений: интерактивные отчёты (дашборды), информативные визуальные графики, презентации от аналитиков и другие формы отчётов (например, сообщения в мессенджерах с ключевой информацией о метриках). 
Поэтому в архитектуру хранилища данных закладывают BI-инструменты, такие как Tableau, Power BI, Apache Superset, DataLens и другие.
Все BI-инструменты умеют подключаться к хранилищу, так что его данные удобно и быстро использовать для аналитической отчётности.


## Разнообразие архитектур хранилищ данных 

Существуют разные подходы к построению хранилищ данных, и на это влияет множество факторов:
- различные форматы данных для хранения и обработки (структурированные и неструктурированные)
- разные задачи анализа данных (описательная BI-отчётность и/или обучение ML-моделей, например, для CV и NLP)
- разные ресурсы, масштабы, корпоративные подходы и экспертиза компаний, внедряющих аналитические хранилища в свой бизнес

С учётом этих факторов выделяют несколько архитектурных подходов к хранилищам данных:

### Data Warehouse 

Это централизованное хранилище, предназначенное для хранения и анализа в основном структурированных данных. Оно оптимизировано для выполнения сложных аналитических запросов на языке SQL и построения BI-отчётности для бизнес-пользователей.

**Примеры:** Snowflake, Amazon Redshift, Google BigQuery, Greenplum, ClickHouse

### Data Lake

Data Lake, или озеро данных, предназначено для хранения в основном неструктурированных данных. Данные лежат в нём в виде файлов самых разных форматов: аудио, картинки, видео, текстовые файлы, файлы структурированных данных, json и др.

Чаще всего озеро данных строят на S3-совместимых хранилищах (объектных хранилищах). В хранилище создают *бакеты (buckets)* с уникальными названиями, а уже в бакетах лежат файлы. Упрощённо бакет можно сравнить с папкой на компьютере, но есть важное отличие: объектные хранилища не поддерживают иерархическую структуру, то есть нельзя создать бакет внутри другого бакета. 

Большой плюс озёр данных — низкая стоимость хранения по сравнению с решениями для Data Warehouse.

**Примеры:** Amazon S3, Yandex Object Storage, Azure Data Lake Storage, Hadoop Distributed File System (HDFS)

### Data Lakehouse 

Data Lakehouse — это гибридная архитектура, которая объединяет лучшие черты озёр данных и хранилищ данных. Она сочетает гибкость и масштабируемость озёр данных с возможностями управления данными, характерными для DWH. Её плюс — более дешёвое хранение неструктурированных данных в Data Lake (его также можно использовать для *холодного* хранения структурированных данных). При этом сохраняются все преимущества DWH для работы со структурированными данными в виде таблиц.

**Примеры:** Databricks Lakehouse, Delta Lake, Apache Hudi

### Data Mesh

Data Mesh — децентрализованная архитектура, которая распределяет управление данными между различными доменами или командами. Каждый домен отвечает за свои данные и предоставляет их другим доменам через стандартизированные интерфейсы.

Для Data Mesh технически могут использоваться одни и те же инструменты, что и для других архитектур: разница здесь больше в правилах управления хранилищем и в децентрализованном подходе.
Представьте компанию, в которой есть, например, отделы маркетинга, продаж и поддержки клиентов. У каждого отдела свои бизнес-процессы и данные. 

В подходе Data Warehouse выделялась бы одна централизованная команда DWH, которая работает с отделами компании как разными бизнес-заказчиками. А в Data Mesh у каждого отдела есть свои ресурсы для управления аналитическими данными, и он отвечает за свой бизнес-домен. Команда хранилища тогда отвечает только за техническую платформу, а задачи на ней бизнес-домены решают сами. Однако в децентрализованном подходе необходимо фиксировать единые правила и подходы для работы с данными — Data Governance и Data Management. Без них каждый бизнес-домен будет работать только по своим правилам и не будет знать общих подходов к данным и инструментам.

### Data Fabric

Data Fabric — это архитектура, которая интегрирует различные источники данных, системы хранения и аналитические инструменты в единую сеть. Она обеспечивает гибкость и масштабируемость для управления данными в реальном времени.

## OLAP vs OLTP системы или почему база данных != хранилище данных

**OLAP (online analytical processing)** — аналитические хранилища данных, про которые речь шла на этой странице выше. Их задача: хранить и обрабатывать большие объёмы данных для аналитических задач бизнеса.

**OLTP (online transactional processing)** — транзакционные системы баз данных. Их задача: записывать и хранить данные текущей работы компании (например, заказы и платежи).
