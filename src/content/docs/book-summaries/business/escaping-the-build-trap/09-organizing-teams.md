**Главная мысль:** организуйте команды вокруг целей и потоков ценности (`value streams`), а не вокруг технических компонентов. Иначе команды создают работу ради работы.

## О чём глава

[Глава 8](/book-summaries/business/escaping-the-build-trap/08-pm-career-path/) разобрала уровни PM. Здесь: как строить команды. Темы: три способа организации, команды вокруг целей (TransferWise), value streams, перестройка продуктовой команды Marquetly, Pandora.

![Три способа организовать команды: по техническим компонентам, по фичам и по value streams, и к чему ведёт каждый](/assets/escaping-the-build-trap/ch09-team-structures.png)

## Три способа организации

- **По техническим компонентам.** Каждая часть системы покрыта. Но команда продолжает работать, даже когда компонент стабилен.
- **По фичам.** У каждой части продукта есть владелец. Но это ведёт к `output`-мышлению: что ещё добавить в «свой кусок». Стабильную фичу нужно мониторить и переходить к важному.
- **По value streams и целям.** Работа связана с ценностью для клиента. Но нужно много координации.

В Marquetly команды стояли над каждым компонентом: так посоветовал Agile-коуч, чтобы было «покрытие». Product owner команды login API сказала, что ей нужно держать бэклог полным, иначе разработчикам нечего делать. Но API уже работал стабильно. Она считала, что команда владеет им навсегда, и придумывала задачи.

## Команды вокруг целей: TransferWise

TransferWise из Лондона делает дешёвые денежные переводы в другие страны. У неё около 12 продуктовых команд, и каждая строится вокруг стратегической цели: `retention`, новые валюты, привлечение пользователей. Команда владеет целью, и её оценивают по `outcome`. Она может менять любые продукты ради цели.

Плюсы: мало команд, поэтому жёсткая приоритизация и нет бесполезной работы. Знания не сидят в одной голове. Не нужно ждать «владельца», чтобы исправить баг. Минус: нужна плотная координация. Автор называет это крайним случаем, при большем числе продуктов так может не получиться.

## Value streams

`Value stream` — все действия, чтобы доставить клиенту ценность: от поиска проблемы и целей до поставки продукта или сервиса. Как организоваться вокруг него:

1. Начните с клиента: какую ценность он получает.
2. Идите назад: через какие точки контакта с компанией он проходит.
3. Упростите этот путь, чтобы давать больше ценности быстрее.

Продукт — это не приложение, фича или интерфейс, а средство доставки ценности. Пример: у страховой компании продукт — страховка авто, а мобильное приложение для полисов лишь часть value stream. У приложения может быть свой PM, но он должен быть в подразделении страхования авто, чтобы стратегия и её выполнение оставались рядом.

При росте нужно больше уровней управления, но не перебарщивайте. Меньше слоёв и больше охват у PM — проще держать стратегию.

## Кейс: продуктовая команда Marquetly

Было 20 команд по компонентам, и PM весь день писали user stories. Большинство из 20 PM были по сути associate PM. Один senior, Карен, VP of product, учила всех. Над платформой для преподавателей работали четыре PM, и никто не отвечал за общее видение.

Автор рекомендовала перестроиться вокруг value streams. Сначала нанять опытного CPO: Карен сильный VP, но портфель продуктов и совет директоров ей пока не по силам. Карен оставить на опыте преподавателей, найти ещё одного VP для опыта студентов и нанять больше senior-людей.

Новая структура — первая версия, её планировали менять, когда CPO уточнит видение. Без видения продукта структуру не построить. Людей стало меньше 20: когда продукт разделили по ценности, 20 областей не нашлось.

## Маленькая команда как преимущество: Pandora

Pandora, сервис музыки по подписке, выросла до 70 млн пользователей в месяц с 40 инженерами. Секрет — жёсткая приоритизация каждый квартал. Это заложило основу оценки в $7 млрд.

PM нужен охват, чтобы влиять на целую цель, измеряемую через `outcome`. Без ясной стратегии с несколькими целями команды распыляются: многие оптимизируют части, но не целое. Как построить такую стратегию, расскажет Часть III.

## Итоги главы

- Команды по компонентам создают работу ради работы, когда компонент уже стабилен.
- Команды по фичам ведут к `output`-мышлению.
- Команда, владеющая целью, оценивается по `outcome` и может менять любые продукты.
- Value stream — все действия, чтобы доставить клиенту ценность. Организацию строят от клиента назад.
- Продукт — это средство доставки ценности, а не приложение.
- После перестройки Marquetly понадобилось меньше 20 PM.
- Жёсткая приоритизация помогла Pandora вырасти с малой командой.

## Ключевые термины

| Термин | Значение |
|---|---|
| `value stream` | Все шаги, чтобы доставить ценность клиенту |
| `component team` | Команда, которая владеет техническим компонентом, например API |
| `goal-oriented team` | Команда, которая владеет целью и оценивается по `outcome` |

## Что это значит на практике

- Data-команды часто строят по компонентам: «команда Kafka», «команда BI». Риск тот же: работа ради работы над стабильной системой.
- Организуйте работу вокруг value stream или цели, например данные для `retention` от событий до дашборда.
- Стабильному пайплайну нужны мониторинг и тесты в `dbt`, а не постоянные доработки.
- Если знание о пайплайне есть у одного инженера, это риск. Помогут документация и ревью.
- Прежде чем просить новых людей, проверьте: может, задач по ценности меньше, чем кажется? Как у Marquetly и Pandora.
