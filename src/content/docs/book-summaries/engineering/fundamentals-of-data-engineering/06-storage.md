**Главная мысль:** Хранение лежит в основе всех стадий lifecycle. Выбор хранилища зависит от того, как данные будут читать и обновлять, и от цены. Нужно знать три уровня: физические компоненты, системы хранения и абстракции над ними.

## О чём глава

В [главе 5](/book-summaries/engineering/fundamentals-of-data-engineering/05-data-generation-in-source-systems/) речь шла о хранилищах источников, которые инженер обычно не контролирует. Здесь речь о хранилищах, которыми он управляет сам: от ingestion до serving. Данные сохраняются много раз по пути, и пока их не обработают дальше, они лежат в storage. Первый шаг к выбору хранилища — понять, как данные будут читать в будущем. Глава идёт снизу вверх: raw ingredients (диски, память, сеть, serialization, compression, caching), потом системы хранения (file, block, object, cache, HDFS, streaming), потом абстракции (warehouse, lake, lakehouse) и большие идеи (catalog, schema, разделение compute и storage, lifecycle и retention).

![Три уровня хранения: raw ingredients, storage systems, abstractions](/assets/fundamentals-of-data-engineering/ch06-storage-layers.png)

## Raw ingredients: из чего состоит хранение

Хранение так привычно, что о нём не думают. Авторы удивляются, сколько инженеров ежедневно пользуются им и не знают, как оно устроено. Даже в эпоху managed-сервисов нужно понимать свойства базовых компонентов: скорость, долговечность и цену. В типичной архитектуре данные по пути проходят через магнитные диски, SSD и память.

### Магнитный диск (HDD)

Диск — это вращающиеся пластины с ферромагнитным слоем. Головка намагничивает слой при записи и читает поле при чтении. Технологию придумали в IBM в 1950-х. Первый коммерческий диск IBM 350 вмещал 3,75 MB, сегодня есть диски на 20 TB. HDD остаются основой массовых хранилищ, потому что стоят примерно 3 цента за GB. Но физика ограничивает их:

- **Скорость передачи** растёт медленнее ёмкости. Ёмкость зависит от плотности на площади, скорость от плотности вдоль дорожки. Если ёмкость выросла в 4 раза, скорость выросла только в 2. Сегодня потолок 200–300 MB/s. Чтобы прочитать диск на 30 TB целиком, нужно больше 20 часов.
- **Seek time и rotational latency.** Головку нужно переместить к дорожке и дождаться, пока нужное место провернётся под ней. При 7200 оборотов в минуту средняя задержка больше 4 мс.
- **IOPS.** Для транзакционных баз это критично. Диск даёт 50–500 IOPS.

Ускорить диск можно (быстрее вращение, узкая зона записи), но для случайного чтения он не конкурент SSD. Зато диски можно объединять. Это идея cloud object storage: данные лежат на тысячах дисков, скорость растёт за счёт параллельного чтения и ограничена в основном сетью.

### SSD

SSD хранит данные как заряд во flash-ячейках. Механики нет. Случайный поиск быстрее 0,1 мс, а скорость и IOPS растут за счёт параллельных контроллеров: гигабайты в секунду и десятки тысяч IOPS. Поэтому SSD стали стандартом для OLTP: PostgreSQL, MySQL и SQL Server обрабатывают на них тысячи транзакций в секунду. Но цена 20–30 центов за GB, почти в 10 раз выше HDD. Поэтому для больших аналитических хранилищ лидирует object storage на HDD. В OLAP SSD служат кешем для частых данных.

### RAM

RAM подключена к CPU и хранит код и данные, которые он обрабатывает. Она volatile: без питания теряет данные меньше чем за секунду. Задержка DDR5 около 100 нс, примерно в 1000 раз быстрее SSD. Пропускная способность до 100 GB/s и миллионы IOPS. Цена около 10 долларов за GB. Объём ограничен на один CPU, а серверы с большой памятью сложнее и дороже. RAM всё равно медленнее кеша CPU. Если база держит RAM как основной слой, помните о volatility: даже при репликации по кластеру отключение питания на нескольких узлах может стоить данных. Долговечные системы используют батарею и сбрасывают данные на диск при потере питания.

### Network и CPU

Хранилища распределены ради скорости, долговечности и доступности. RAID параллелит диски на одном сервере, а cloud object storage делает это на много большем масштабе: диски в сети, в нескольких дата-центрах и availability zones. **Availability zone** — изолированная среда облака со своим питанием и ресурсами. Хранение в нескольких зонах повышает availability и durability. CPU обслуживает запросы, агрегирует чтение и раздаёт запись, и хранилище становится веб-приложением с API и балансировкой. Инженер всё время балансирует между durability (данные разнесены географически) и скоростью и ценой (данные рядом с потребителем). Облачные сети разобраны в приложении B.

### Serialization

Данные в памяти не подходят для диска или сети. Serialization упаковывает их в стандартный формат, который читатель сможет декодировать. Алгоритм определяет работу с типами, правила структуры и исключения. Например, в объектах Python бывают циклические ссылки: алгоритм может выдать ошибку или ограничить глубину. Низкоуровневое хранение базы тоже serialization. Row-based базы хранят строки для быстрых lookups и обновлений на месте. Columnar базы хранят колонки для сильного сжатия и быстрого scan. Выбор формата определяет скорость запросов по сети, нагрузку на CPU и latency. Знайте популярные форматы: Parquet, гибридные (Hudi) и in-memory (Arrow). Подробнее в приложении A.

### Compression

Сжатие даёт три выигрыша. Данные занимают меньше места. Эффективная скорость scan растёт: при сжатии 10:1 диск на 200 MB/s читает как 2 GB/s. Растёт и сеть: канал EC2–S3 на 10 Gbps при 10:1 даёт эффективные 100 Gbps. Цена — время и ресурсы CPU на сжатие и распаковку.

### Caching

Идея: хранить частые или недавние данные в быстром слое. Чем быстрее кеш, тем он дороже и меньше. Полезно ставить каждый вид хранилища в иерархию.

| Уровень | Задержка | Скорость | Цена |
|---|---|---|---|
| CPU cache | 1 нс | 1 TB/s | — |
| RAM | 0,1 мкс | 100 GB/s | 10 $/GB |
| SSD | 0,1 мс | 4 GB/s | 0,20 $/GB |
| HDD | 4 мс | 300 MB/s | 0,03 $/GB |
| Object storage | 100 мс | 10 GB/s | 0,02 $/GB в месяц |
| Archival | 12 часов | как object storage после доступности | 0,004 $/GB в месяц |

Archival можно считать reverse cache: плохой доступ за низкую цену. Его используют для backup и compliance. В типичных случаях к данным обращаются лишь в аварии или при юридическом запросе.

## Системы хранения

Системы хранения стоят уровнем выше raw ingredients. Диск — это ингредиент, а S3 и HDFS — системы на дисках.

![Выбор типа хранилища по задаче](/assets/fundamentals-of-data-engineering/ch06-storage-choice.png)

### Одна машина и distributed storage

Когда одного сервера мало, данные распределяют по многим. Distributed storage координирует серверы для скорости, масштаба и redundancy при отказе сервера. На нём работают object storage, Spark и cloud data warehouses.

### Eventual и strong consistency

Данные лежат на разных серверах, а репликация изменений занимает время. Поэтому есть баланс между актуальными данными и «почти актуальными». Существует противоположность ACID — **BASE**: basically available (чтение и запись best effort), soft-state (состояние транзакции нечёткое) и eventual consistency (когда-нибудь чтения вернут согласованные значения). Eventual consistency — частая цена горизонтального масштаба: данные читаются быстро без проверки, что версия свежая на всех узлах. Strong consistency требует, чтобы запись сначала согласовалась между узлами. Выбирайте её, если выдержите большую задержку и всегда нужны верные данные.

Решения по consistency принимаются в трёх местах: технология базы, её настройки и иногда отдельный запрос. Например, DynamoDB даёт eventually и strongly consistent reads. Strong медленнее и дороже, поэтому используйте экономно. Требования нужно согласовать с бизнесом, это и технологическая, и организационная задача.

### File storage

Файл — это поток байтов конечной длины. В него можно добавлять байты (append) и читать или писать в любую позицию (random access). Файлы лежат в дереве каталогов. Каталог хранит метаданные: имя, права и указатель. Чтобы найти файл, ОС идёт по уровням. У объектов в object storage есть только конечная длина.

- **Local disk** — файловая система ОС (NTFS, ext4). Устроена так, чтобы переживать потерю питания при записи (несохранённое всё же теряется). Есть read after write consistency и блокировки при параллельной записи. Бывают journaling, snapshots, шифрование, сжатие.
- **NAS** — файловая система по сети. Есть цена скорости, но и плюсы виртуализации: redundancy, тонкий контроль, объединение дисков, общий доступ. Нужно знать модель consistency, особенно при нескольких клиентах.
- **Cloud filesystem**, например Amazon EFS — управляемый аналог NAS по протоколу NFS 4. Масштабируется сам, платите за хранение. После закрытия файла все новые читатели видят изменения.

В pipeline осторожно относитесь к состоянию и по возможности используйте эфемерные среды. Для промежуточных данных берите object storage. Ручную работу с файлами оставьте для разовой загрузки и экспериментов.

### Block storage

Block — наименьшая адресуемая единица диска. Раньше было 512 байт, сегодня обычно 4096: запись менее тонкая, но меньше издержек на управление. Блоки на HDD лежат геометрически: два блока на одной дорожке читаются без перемещения головки. Транзакционные базы работают с блоками напрямую ради скорости случайного доступа. Это и стандартный загрузочный диск для облачных VM.

- **RAID** управляет несколькими дисками для durability, скорости и объединения ёмкости. Схем много: баланс между пропускной способностью и устойчивостью к отказам.
- **SAN** — виртуальные блочные устройства по сети из общего пула. Есть в on-prem, а облачная версия — следующий пункт.
- **Amazon EBS** — стандартное хранилище для EC2. Есть уровни по IOPS и throughput: быстрые на SSD, дешёвые на HDD. Данные лежат отдельно от хоста, но в той же зоне, поэтому том переживает остановку и удаление инстанса. Данные реплицируются минимум на два хоста. Мгновенные snapshots замораживают блоки, пока диск работает. После первого полного snapshot в S3 пишутся только изменённые блоки. Зону целиком EBS не переживает.
- **Instance store** — диск на хосте VM. Дешёвый, с низкой latency и высокими IOPS. Но данные пропадают при остановке или удалении VM, нет репликации и snapshots. Подходит как локальный кеш. Пример: эфемерный кластер EMR читает S3, держит данные во временной HDFS, пишет результат в S3. Продумайте худший сценарий: отказ диска, случайное выключение, сбой зоны. Помогают периодические checkpoint в S3.

### Object storage

Объекты бывают любыми: TXT, CSV, JSON, картинки, видео, аудио. Примеры: Amazon S3, Azure Blob Storage и Google Cloud Storage. Cloud warehouses и всё больше баз используют его как слой хранения, а cloud data lakes на нём построены. Это одно из первых «serverless» хранилищ: можно не думать о серверах и дисках.

Object store — это key-value хранилище **неизменяемых** объектов. Нет random writes и append. Объект пишется один раз как поток байтов. Чтобы изменить, его перезаписывают целиком. Random reads возможны через range requests, но хуже SSD. Ограничения дают плюс: не нужны блокировки и синхронизация изменений, поэтому данные можно разнести по огромному кластеру. Скорость записи растёт с числом потоков, скорость чтения — с числом запросов, VM и ядер. Это идеально для высокого веб-трафика и параллельных query engines. Данные лежат в нескольких зонах: durability и availability заложены в цену. Ёмкость почти неограничена, предел — бюджет, и не нужно планировать серверы на месяцы вперёд.

Object storage — ключ к разделению compute и storage: эфемерные кластеры. Это сделало big data доступными маленьким компаниям, которые не могут держать железо для редких задач. Тренд: обработка в облаке на эфемерных кластерах, object store как основа хранения и serving.

**Для data engineering.** Object store отлично читает и пишет большими batch, как нужно OLAP. Фольклор «object store не годится для обновлений» верен лишь отчасти. Он плох для транзакций с множеством мелких обновлений в секунду, для них берут OLTP или block storage. Для редких обновлений больших объёмов он подходит. Сегодня это золотой стандарт для data lake. В ранние годы стандартом был write once, read many (WORM), но причина была в сложности управления версиями, а не в ограничениях HDFS и object stores. Потом Hudi и Delta Lake сняли сложность, а GDPR и CCPA сделали удаление и обновление обязательными. Управление обновлениями в object storage — идея data lakehouse. Хранилище подходит и для неструктурированных данных (текст, изображения, видео, аудио для ML).

**Object lookup.** Каталогов нет. Есть bucket (имя уникально во всём AWS) и ключ (уникален в bucket). Путь `project-data/11/23/2021/data.txt` — одна строка-ключ, а не вложенные папки, хотя консоль и `ls` показывают «каталоги». Поэтому «каталожные» операции дороги: хранилище фильтрует ключи по префиксу, и в bucket с миллионами объектов это занимает время.

**Consistency и versioning.** Объект обновляют записью нового объекта под тем же ключом. До недавних пор S3 был eventually consistent: после записи он мог вернуть старую версию. Строгость можно добавить внешней базой (например, PostgreSQL): после записи объекта метаданные версии (хеш или timestamp) пишут в базу, а читатель сверяет с ней версию и повторяет чтение, пока она не совпадёт. Это даёт strong consistency ценой latency. Versioning хранит старые версии: пара key + version всегда указывает на один неизменяемый объект. Минус — цена: хранятся полные копии, а не разницы, и это может быть почти бесплатно или катастрофически дорого. Помогают lifecycle policies: удаление старых версий по возрасту или по числу новых.

**Storage classes.** Хранение дешевле, но доступ дороже или надёжность ниже (пример S3):

| Класс | Особенность |
|---|---|
| Standard | Базовый |
| Infrequent Access | Дешевле хранение, дороже чтение |
| One Zone-IA | Одна зона. Доступность падает с 99,9% до 99,5%. Данные теряются при уничтожении зоны |
| Glacier | Огромное снижение цены хранения при высокой цене доступа. Скорость восстановления от минут до часов, быстрее значит дороже |
| Glacier Deep Archive | От 1 $/TB в месяц, восстановление около 12 часов. Для данных на 7–10 лет, к которым обращаются 1–2 раза в год |

Предупреждение: в архив легко войти, а достать данные часто дорого, особенно если нужны чаще, чем ожидалось.

**Object store как файловая система.** s3fs и S3 File Gateway монтируют bucket как диск. File Gateway умеет эффективно собирать изменения. Но быстрые транзакционные записи перегрузят object store. Подходит для редко меняемых файлов.

### Cache и memory-based

RAM быстрая, но один сбой питания стирает данные. Такие системы нужны для кеша, а для хранения данные пишут на устойчивый носитель.

- **Memcached** — key-value кеш результатов запросов и ответов API. Простые типы (строки и числа), очень низкая latency, снимает нагрузку с бэкенда.
- **Redis** — более сложные типы (списки, множества) и persistence (snapshots, journaling). По умолчанию пишет на диск примерно раз в две секунды: годится для очень быстрых задач с допустимой небольшой потерей.

### HDFS

Раньше «Hadoop» значил «big data». HDFS основана на Google File System и создана для MapReduce. Файлы режутся на блоки (до нескольких сотен MB). NameNode ведёт каталоги, метаданные и положение блоков. Обычно каждый блок реплицируется на три узла. Если узел или диск упал, NameNode просит другие узлы восстановить число копий. Потеря данных маловероятна, если нет коррелированного сбоя (авторы шутят про астероид). В отличие от object storage, Hadoop совмещает compute и storage на тех же узлах.

«Hadoop мёртв» верно лишь отчасти. Это больше не передний край, чистый MapReduce ушёл, а Pig и другие инструменты работают в основном на старых задачах. Но HDFS жив: он есть в legacy, в EMR, и Spark часто запускают на HDFS. Для компаний с тысячами узлов и ресурсами на on-prem это разумно. Небольшим стоит сравнить цену и лимиты маленького кластера с облаком.

### Streaming storage

У очередей сообщений данные временные. Но Kafka поддерживает хранение сколь угодно долго: старые сообщения переносятся в object storage. Kinesis, Pulsar и Pub/Sub тоже. **Replay** возвращает диапазон исторических данных. Это основной способ чтения из streaming storage: для batch-запросов за период или для повторной обработки. Для real-time аналитики есть и свои движки. Транзакционные базы тоже видны запросам сразу после записи, но у них есть ограничения по масштабу и блокировкам.

## Indexes, partitioning, clustering

**Index** — карта таблицы по полям для быстрого поиска записей. Без него нужен scan всей таблицы. В RDBMS индексы строят для primary и foreign keys, и можно по другим колонкам. Так база ищет и обновляет тысячи строк в секунду.

**От строк к колонкам.** Ранние warehouse строили на обычных RDBMS. Затем MPP-системы дали параллельную обработку, но row-based MPP всё ещё использовали индексы для joins и условий. Columnar-хранение читает только нужные колонки, а одинаковые значения рядом хорошо сжимаются. Колоночные базы плохи для транзакций (много точечных строк) и очень хороши для больших scan: преобразований, агрегатов, статистики. Раньше они плохо делали joins, и советовали денормализацию: широкие схемы, массивы, вложенные данные. Сегодня joins ускорились, денормализация уже не обязательна.

**Partitioning и clustering.** Даже при быстрых scan нужно читать меньше. Таблицу делят на части по полю. Чаще всего по дате или времени, потому что в аналитике часто сканируют период. **Clustering** сортирует данные внутри partitions по одному или нескольким полям, и похожие значения лежат рядом. Это ускоряет фильтры, сортировки и joins.

**Snowflake micro-partitions.** Это группы строк по 50–500 MB в несжатом виде. Snowflake алгоритмически группирует похожие строки, а не делит по одному полю вроде даты. Метаданные хранят число строк и диапазоны значений по полям. По ним система исключает partitions, где нужного значения нет (pruning). Метаданные играют роль индекса.

## Абстракции хранения

Это способы организации данных и запросов над системами хранения. Выбор зависит от четырёх вещей: цели, шаблона обновлений (bulk, streaming, upsert), цены (деньги, time to value, opportunity cost) и разделения compute и storage. Границы между OLAP-базами и lakes стираются. Крупные cloud warehouses и lakes движутся навстречу, и скоро различия могут остаться только в названии.

- **Data warehouse** — стандартная OLAP-архитектура. Путь: warehouse на транзакционной базе, row-based MPP (Teradata, Netezza), columnar MPP (Vertica), затем cloud warehouse и data platform. Cloud warehouse часто используют для организации data lake — хранилища сырых данных, как придумал Джеймс Диксон. Они справляются с большим текстом и сложным JSON. Но не с настоящими неструктурированными данными (изображения, видео, аудио), в отличие от lake. В паре с object storage получается полноценный lake.
- **Data lake.** Сначала хранилище «сырых» данных на Hadoop, где дешёвое хранение позволяло держать огромные объёмы без цены MPP. За последние годы было два сдвига. Во-первых, миграция от Hadoop к cloud object storage с разделением compute и storage. Во-вторых, инженеры поняли, что функции MPP (управление схемой, update, merge, delete) очень полезны, хотя их отбросили в спешке за lakes. Так появился lakehouse.
- **Data lakehouse** — совмещает warehouse и lake. Данные в object storage, а сверху функции, дающие опыт warehouse: таблицы и схемы, инкрементальные update и delete, история таблиц и rollback через старые версии файлов и метаданных. Это слой метаданных и управления файлами. Databricks продвигал идею с Delta Lake. Появились Apache Hudi и Iceberg. Похожим образом устроены BigQuery и Snowflake, где сложности файлов скрыты от пользователя. Главное преимущество перед проприетарными системами — interoperability: открытый формат проще обменивать. Переупаковка из проприетарного формата стоит времени и денег. Много данных в lakehouse может вообще не иметь табличной структуры.
- **Data platform.** Вендоры строят экосистемы инструментов, тесно связанных с ядром хранения. При оценке проверьте, что инструменты вам подходят. Остальные можно подключить с издержками на обмен. Идея платформы пока не оформилась. Идёт гонка за «walled garden», которая упрощает работу и сильно привязывает к вендору.
- **Stream-to-batch.** Похоже на Lambda. Поток topic идёт нескольким потребителям: одни — real-time обработка, другой — batch для долгого хранения и запросов (Kinesis Firehose пишет объекты в S3 по триггерам времени и размера). BigQuery принимает потоки в streaming buffer, который автоматически превращается в колоночные объекты, и запрос видит оба.

## Большие идеи хранения

### Data catalog

Централизованное хранилище метаданных всей организации. Это не абстракция хранения верхнего уровня, но интегрируется со многими системами. Каталог работает с операционными и аналитическими источниками, показывает lineage и связи, позволяет редактировать описания. Инженер обычно отвечает за подключение систем и целостность каталога.

- **Интеграция с каталогом:** идеально приложения сами работают с API каталога.
- **Automated scanning:** на практике метаданные собирает сканер по lakes, warehouses и базам, он же может выводить связи ключей и наличие чувствительных данных.
- **Portal и social layer:** веб-интерфейс для поиска и wiki, где пользователи описывают наборы данных и задают вопросы.
- **Use cases:** для систем (каталог — ключ lakehouse: открываемость таблиц) и для людей (бизнес, аналитики, data scientists ищут данные, упрощается коммуникация).

### Data sharing

Организации и люди делятся конкретными данными с точными правами. Внутри компании data scientist делится данными из sandbox с коллегами. Между компаниями рекламная компания делится данными с клиентами. Облачная multitenant среда это облегчает, но создаёт риски: нужно строго контролировать, кто с кем делится, чтобы не было случайной утечки или кражи. См. [главу 5](/book-summaries/engineering/fundamentals-of-data-engineering/05-data-generation-in-source-systems/).

### Schema

Schema — «Розеттский камень»: инструкция, как читать данные. Какой формат файла, структурированы ли данные, какие типы, как данные связаны. Схема не обязана быть реляционной: для картинок в lake это формат, разрешение и место в иерархии. Два паттерна:

- **Schema on write.** Классический warehouse: у таблицы встроенная схема, запись должна ей соответствовать. Lake для этого нужен schema metastore. Плюс: данные соблюдают стандарты и проще потребляются.
- **Schema on read.** Схема определяется при записи, а читатель выясняет её при чтении. Гибко: можно записать что угодно. Но потреблять сложнее. Лучше использовать форматы со встроенной схемой (Parquet, JSON). CSV печально известен несогласованностью схемы и не рекомендован.

### Separation of compute and storage

![Colocation и separation compute и storage: когда что выбрать](/assets/fundamentals-of-data-engineering/ch06-compute-storage.png)

Это стандартный облачный шаблон: lakes хранят данные в object store и поднимают временный compute. Большинство управляемых OLAP тоже опираются на object storage.

**Colocation** давно ускоряет базы: данные рядом с обработкой. У транзакционных баз быстрые чтения и высокая пропускная способность, даже с EBS данные близко. Так же в HDFS и MapReduce: map-задачи идут к блокам и работают локально. Shuffle в reduce-шаге идёт по сети. Локальный map экономит полосу для shuffle, а сильно фильтрующий map сокращает объём shuffle.

**Зачем разделять?**

- **Ephemerality и scalability.** Купить и держать сервер дешевле, чем арендовать, если он работает 24 часа годами. Но нагрузки колеблются, и pay-as-you-go даёт выгоду, когда серверы масштабируются: так для веб-магазина и для периодических big data задач. Эфемерный кластер поднимают на задачу и удаляют. Выигрыш от временного сверхмасштаба может перевесить ограничения полосы object storage.
- **Durability и availability.** Cloud object stores сильно снижают риск потери данных и дают высокую доступность. S3 хранит данные в нескольких зонах, и если зону уничтожила стихия, данные доступны в остальных. Страшна ошибка в конфигурации, но есть простые меры: копировать данные в несколько регионов (конфигурации обычно выкатывают в один регион за раз) или у нескольких провайдеров.

**Hybrid.** На практике разделение и colocation смешивают двумя способами: multitier caching (object storage для долгого хранения, локальный storage на время запросов) и hybrid object storage (object storage, тесно связанное с compute).

- **EMR с S3 и HDFS.** Поднимают временный HDFS на SSD, читают из S3, промежуточные результаты хранят в HDFS. Это быстрее, чем работать прямо с S3. Итог пишут в S3, кластер удаляют.
- **Spark.** Работает на HDFS или другой эфемерной файловой системе и сильно использует память. Своя DRAM дорогая, а в облаке память арендуют на время задачи.
- **Druid.** Опирается на SSD и хранит одну копию данных, снижая «живую» стоимость втрое. Долговечность даёт object store: при отказе узла данные восстанавливаются.
- **Hybrid object storage.** Файловая система Google Colossus позволяет тонко управлять расположением блоков, хотя публично это не открыто. BigQuery использует это, чтобы держать таблицы клиента в одном месте и получать очень высокую полосу. У Amazon есть S3 Select: фильтрация данных внутри кластера S3 до передачи по сети. Авторы предполагают, что облака будут шире использовать hybrid object storage. Это показывает, что низкоуровневый доступ к железу всё ещё даёт преимущества.

### Zero-copy cloning

Облачные системы на object storage создают виртуальную копию (например, таблицы) без физического копирования. Создаются новые указатели на те же файлы. Изменения в новой таблице не попадают в старую. Это «shallow copy», как в Python. Но в data lake удаление файлов оригинала может стереть и клон. В управляемых системах (Snowflake, BigQuery) нужно знать точные границы shallow copy. В Databricks доступ к object storage шире: и благо, и проклятие. Не удаляйте сырые файлы без осторожности. Иногда есть deep copy: копируются все объекты. Дороже, но надёжнее.

### Data storage lifecycle и retention

Хранение — не «положил и забыл». Lifecycle отвечает на вопрос, насколько данные важны потребителям и как часто нужны. Retention — как долго их хранить.

**Hot, warm, cold.** Данные имеют «температуру» по частоте доступа. Новые данные читают чаще старых.

| Температура | Доступ | Хранилище | Цена |
|---|---|---|---|
| Hot | Мгновенный или частый. Рекомендации, страницы товаров, query results cache | SSD, память | Хранение дорогое, чтение дешёвое |
| Warm | Примерно раз в месяц | S3 Infrequent Access, Nearline | Хранение дешевле, чтение чуть дороже |
| Cold | Редкий. Долгий архив | HDD, tape, облачные архивы | Хранение дешёвое, чтение дорогое |

Query results cache — пример горячих данных: при повторе того же запроса система отдаёт готовый результат на ограниченное время. Хранить всё в hot — огромные деньги. Всё в cold — дёшево, но долго и дорого читать. Cold раньше значил физические копии, которые отправляли по почте в хранилище-«сейф». Теперь у каждого облака есть cold-решение: сравните цену загрузки с ценой и временем извлечения.

**Spillover.** Память дорога и конечна, поэтому горячие данные при переполнении сбрасываются на диск. Некоторые базы выгружают редкие данные на HDD или в object storage (всё чаще). В managed-сервисах это происходит автоматически.

Для облачного object storage задайте автоматические lifecycle policies. Если данные нужны раз в месяц, переведите их в Infrequent Access. Если данным 180 дней и текущие запросы их не используют, в архив. Учтите цену и время извлечения: некоторые облака делают вход в архив простым и дешёвым, а возврат дорогим и медленным.

**Retention.** В ранние годы big data старались копить всё «на случай, если пригодится». Это привело к data swamps и ужесточению регуляторов. Теперь нужно решать, что и как долго хранить.

- **Value.** Данные — актив. Можно ли их легко воссоздать из источника или нет? Что будет для потребителей, если их нет?
- **Time.** Новые данные ценнее и читаются чаще. Для кеша или памяти задайте TTL, иначе hot-хранилище переполнится и запросы замедлятся.
- **Compliance.** HIPAA и PCI могут требовать хранить данные, и их нужно выдать по запросу. Другие правила требуют удалить в срок, поэтому нужны процесс хранения и архивации и поиск данных.
- **Cost.** Данные должны давать ROI. Автоматически переносите в cold или удаляйте, когда срок вышел.

### Single-tenant и multitenant

При **single-tenant** у каждого клиента (пользователь, группа, аккаунт) свои ресурсы, например база. Данные изолированы полностью. Схемы и bucket-структуры независимы: вы можете сделать их одинаковыми или дать расходиться. Это и плюс, и минус. Если схемы разные, сложно собрать единый вид по всем клиентам. При **multitenant** клиенты делят базу, схемы или таблицы. Запросы к обоим вариантам разобраны в главе 8.

## Партнёры и undercurrents

Вы работаете с теми, кто владеет IT-инфраструктурой: DevOps, security, cloud architects. Заранее определите зоны ответственности. Может ли data engineer сам развернуть инфраструктуру в аккаунте AWS или это делает другая команда? Разделение зависит от зрелости компании. В ранней компании инженер управляет всей системой хранения, в зрелой — частью, и общается с коллегами по ingestion и transformation. Он должен обеспечить, чтобы хранилище было безопасным, с качественными данными, с запасом места и быстрым для запросов.

Undercurrents для хранения особые: storage — хаб всех стадий и есть везде.

| Область | Что важно |
|---|---|
| Security | Безопасность — не помеха, а помощник: надёжная защита данных в покое и в движении позволяет шире делиться данными, и ценность растёт. Принцип least privilege: полный доступ к базе почти никому не нужен. Контроль на уровне колонок, строк и ячеек |
| Data management | Каталог и метаданные: discovery, lineage ускоряет поиск проблем, data dictionary хранит знания. Versioning в object storage: восстановление при порче и воспроизводимость ML (как git для данных). Privacy: GDPR, удаление по запросу, анонимизация и masking |
| DataOps | Мониторинг систем (включая serverless), FinOps, безопасность и доступ. Мониторинг самих данных: статистика, anomaly detection, проверки логики |
| Architecture | Надёжность и durability под требования. Понимайте источники и будущие запросы. Активный FinOps, не оптимизируйте преждевременно, но готовьтесь к росту. Предпочитайте fully managed и знайте SLA |
| Orchestration | Хранилище — труба, orchestration — насос. Помогает справиться со сложностью множества систем хранения и движков |
| Software engineering | Код должен хорошо работать с хранилищем, без утечек памяти. Инфраструктура как код и эфемерный compute, чтобы не связывать слои хранения и запросов |

## Итоги главы

- Хранение лежит под всеми стадиями lifecycle, поэтому нужно знать его три уровня: компоненты, системы и абстракции.
- HDD дёшевы, но медленны для случайного доступа. SSD быстры и годятся для OLTP, а RAM быстрее всех, но теряет данные без питания.
- Compression и caching ускоряют работу. Archival — это reverse cache: дёшево хранить, дорого и долго читать.
- Object storage хранит неизменяемые объекты и подходит для data lake и больших batch-операций, но не для частых мелких обновлений.
- Eventual consistency — цена горизонтального масштаба, а strong consistency нужна при строгих требованиях к точности.
- Lakehouse добавляет к lake таблицы, схемы и транзакционные функции и сохраняет открытые форматы и interoperability.
- Разделение compute и storage даёт эфемерность, масштаб и durability. На практике его смешивают с colocation через кеши и hybrid object storage.
- Lifecycle policies и retention снижают цену. Важны value, time, compliance и cost.
- Zero-copy cloning быстр, но удаление исходных файлов может сломать клон.
- Data catalog, versioning, least privilege и GDPR — часть дизайна хранения, а не поздняя надстройка.

## Ключевые термины

| Термин (EN) | Что значит |
|---|---|
| IOPS | Число операций ввода-вывода в секунду |
| Serialization | Упаковка данных в формат для хранения и передачи |
| Eventual consistency | Данные согласуются через некоторое время |
| Block storage | Сырые блоки диска, основа для OLTP |
| Object storage | Хранилище неизменяемых объектов по ключу |
| Bucket | Верхний контейнер объектов |
| Storage class / tier | Класс хранения с разной ценой хранения и доступа |
| Replay | Повторное чтение исторических событий потока |
| Partitioning / clustering | Разбиение и сортировка таблицы для сокращения scan |
| Data lakehouse | Lake в object storage с таблицами и транзакционными функциями |
| Schema on write / on read | Схема проверяется при записи или определяется при чтении |
| Zero-copy cloning | Копия через указатели без копирования данных |
| Retention / TTL | Срок хранения данных |

## Что это значит на практике

- Выбирайте хранилище по шаблону доступа: lookup по строкам (SSD, OLTP) или большие scan (object storage, columnar).
- Не делайте частые мелкие обновления в object storage. Для этого есть lakehouse-форматы.
- Настройте lifecycle policies и retention. Проверьте цену и время извлечения из архива.
- Включайте versioning осознанно и следите за ростом стоимости.
- Не удаляйте файлы под клонами и таблицами в data lake без проверки.
- Предпочитайте форматы со схемой (Parquet), не CSV.
- Готовьтесь к запросам на удаление данных (GDPR). Подключите catalog и lineage.
- Используйте эфемерный compute и инфраструктуру как код.
- Для локальных дисков VM продумайте худший случай и делайте checkpoint в object storage.
