**Главная мысль:** хорошая архитектура данных помогает меняться. Она строится на гибких и обратимых решениях и на честной оценке компромиссов. Идеальной архитектуры нет. Есть наименее плохая для вашей задачи.

## О чём глава

[Глава 2](/book-summaries/engineering/fundamentals-of-data-engineering/02-data-engineering-lifecycle/) назвала архитектуру одним из undercurrents. Эта глава отвечает на вопрос: что такое хорошая архитектура данных. Сначала авторы дают определение. Потом идут девять принципов и основные понятия: domains, распределённые системы, coupling, multitenancy, события, brownfield и greenfield. В конце разобраны примеры архитектур: warehouse, lake, lakehouse, modern data stack, Lambda, Kappa, IoT и data mesh. Авторы сразу честно говорят: их определение «не всех устроит», зато оно практичное для компаний любого размера.

![Девять принципов хорошей архитектуры данных, сгруппированные по темам](/assets/fundamentals-of-data-engineering/ch03-principles.png)

## Что такое data architecture

Определений архитектуры много, они противоречат друг другу и часто устарели. Сначала нужен контекст: enterprise architecture. Слово «enterprise» вызывает смешанные чувства: холодные офисы, водопадное планирование, пустые лозунги. Но учиться есть чему. Авторы разбирают три известных определения:

- **TOGAF** (стандарт The Open Group): архитектура охватывает всю компанию или одну область, но всегда пересекает несколько систем и функциональных групп.
- **Gartner**: дисциплина, которая заранее и целостно ведёт компанию через разрушительные изменения к желаемому видению бизнеса.
- **EABOK** (справочник MITRE, черновик 2004 года): организационная модель, которая связывает стратегию, операции и технологии в карту пути к успеху.

Общие нити: изменения, согласованность, организация, возможности, решение проблем, миграция. Из них авторы делают своё определение.

- **Enterprise architecture** это проектирование систем, которые поддерживают изменения в компании, через гибкие и обратимые решения, принятые после оценки компромиссов.
- **Data architecture** это часть enterprise architecture: проектирование систем под меняющиеся потребности компании в данных, по тем же правилам. Архитектура data engineering это часть общей архитектуры данных, как lifecycle инженера часть общего data lifecycle.

Определение держится на трёх идеях.

**Гибкие и обратимые решения.** Они нужны по двум причинам. Мир меняется, будущее предсказать нельзя. Кроме того, с ростом организации «костенеют», а культура обратимых решений снижает риск шага. Идею «дверей» приписывают Jeff Bezos. **One-way door** почти нельзя отменить: если бы Amazon закрыл AWS, такое облако второй раз не построить. **Two-way door** легко вернуть: Amazon может потребовать DynamoDB для новых микросервисов и отменить это, если не сработает. Ставки низкие, поэтому организация принимает больше решений и быстрее учится.

**Change management.** Большие инициативы режут на малые обратимые шаги. Между статьёй о DynamoDB (2007) и анонсом сервиса (2012) прошло пять лет мелких шагов. Управление ими и есть change management. Архитектор не рисует абстрактное будущее: он находит проблемы текущего состояния, описывает желаемое и ведёт к нему малыми шагами. Технические решения существуют не ради себя, а ради бизнес-целей.

**Оценка компромиссов.** Авторы опираются на Richards и Ford: компромиссы неизбежны. ПО гибко, и кажется, что физика нас не касается. Но цифровые системы упираются в задержку, надёжность, энергию, а ещё в сложность и бюджет. «Магическое мышление» ведёт к плохой инженерии. Инженер учитывает компромиссы на каждом шаге и минимизирует technical debt с высокими процентами.

Есть и два вида архитектуры. **Operational** отвечает на вопрос «что нужно сделать»: какие бизнес-процессы обслуживают данные, как управляется качество, какая нужна задержка. **Technical** отвечает на вопрос «как»: как данные принимают, хранят, преобразуют и отдают. Например, как возить 10 ТБ в час из базы в озеро.

## Что значит «хорошая» архитектура

По словам Mark Richards и Neal Ford, нужно стремиться не к лучшей, а к «наименее плохой» архитектуре. Grady Booch говорит: архитектура это значимые решения, а «значимость» измеряется ценой изменения.

- Хорошая архитектура обслуживает требования бизнеса из общего набора повторно используемых блоков, остаётся гибкой и делает разумные компромиссы.
- Основа хорошей архитектуры это agility: она признаёт, что мир текуч. Архитектура, которая годилась в прошлом году, может не годиться сегодня.
- Плохая архитектура авторитарна: она пытается запихнуть решения «один размер для всех» в большой ком грязи. Она сильно связана (tightly coupled), жёсткая, слишком централизованная или собрана из неподходящих инструментов. Тогда страдают разработка и управление изменениями.
- Основа для любой зрелости данных это undercurrents: security, data management, DataOps, architecture, orchestration, software engineering.
- Хорошая архитектура «живая». Она никогда не закончена, ведь изменение входит в её смысл.

## Девять принципов

Авторы берут идеи из двух источников. AWS Well-Architected Framework имеет шесть столпов: operational excellence, security, reliability, performance efficiency, cost optimization, sustainability. У Google Cloud пять принципов: automation, разумная работа с состоянием, управляемые сервисы, defense in depth, always be architecting. Авторы советуют изучить оба и расширяют их своими девятью принципами.

| # | Принцип | Суть |
|---|---|---|
| 1 | Choose common components wisely | Общие компоненты связывают команды и разрушают силосы |
| 2 | Plan for failure | Всё ломается. Заранее определите availability, reliability, RTO и RPO |
| 3 | Architect for scalability | Система растёт и уменьшается. Не усложняйте без нужды |
| 4 | Architecture is leadership | Архитектор обучает и ведёт, а не командует |
| 5 | Always be architecting | Целевая архитектура меняется. Нужен план последовательности |
| 6 | Build loosely coupled systems | Команды общаются через API и схемы сообщений |
| 7 | Make reversible decisions | Выбирайте лучшее на сегодня и будьте готовы заменить |
| 8 | Prioritize security | Zero trust и shared responsibility. Каждый data engineer отвечает за безопасность |
| 9 | Embrace FinOps | Расходы в облаке динамические. Их нужно мониторить и ограничивать |

### Принципы 1-3

**Общие компоненты.** Это всё, что широко полезно: object storage, version control, observability, orchestration. Команды должны брать их, а не изобретать заново. Нужны надёжные права. Облако идеально для этого: общий слой хранения и разные инструменты запросов. Нужен баланс: нельзя навязывать «один размер для всех» командам, которые решают задачи своей области (подробнее в главе 4).

**Plan for failure.** Любой компонент рано или поздно откажет, даже на надёжном железе. **Availability** это доля времени, когда сервис работает. **Reliability** это вероятность, что система выполняет функцию по стандарту. **RTO** это допустимое время простоя, его задают по бизнес-ущербу: для внутренней отчётности день простоя нормален, а для интернет-магазина пять минут уже серьёзны. **RPO** это допустимая потеря данных.

**Architect for scalability.** Система должна расти (кластер для обучения модели на петабайте) и уменьшаться, когда нагрузка спала. Это связано с принципом 9. **Elasticity** это автоматическое изменение под нагрузкой. Некоторые системы умеют **scale to zero**, например serverless-функции. Лишнее масштабирование даёт сложные и дорогие системы: иногда хватает обычной базы с одним резервным узлом. Измерьте нагрузку, оцените всплески и рост на несколько лет.

### Принципы 4-7

**Architecture is leadership.** Архитектор отвечает за решения и передаёт их через лидерство и обучение. Он технически силён, но большую работу делегирует. Лидерство не значит командование. Раньше архитекторы заставляли все команды хранить данные в одной проприетарной базе. Авторы против: это вредит проектам. Martin Fowler описывает идеального архитектора так: его главное дело это наставничество, чтобы команда решала более сложные задачи. Так у архитектора больше рычага, чем у единственного решающего, который становится узким местом. Инженеру советуют практиковать лидерство и искать наставников.

**Always be architecting.** Принцип Google Cloud. Архитектор не поддерживает статус-кво, а проектирует новое в ответ на изменения. По EABOK, он знает текущую архитектуру (baseline), разрабатывает целевую (target) и составляет план последовательности (sequencing plan). Подход должен быть гибким, а не водопадным: цель движется, а план задаёт ближайшие приоритеты.

**Build loosely coupled systems.** Если архитектура позволяет командам тестировать, выкатывать и менять системы без зависимостей, общения нужно мало. Исторический пример: в 2002 году Bezos разослал письмо, известное как **Bezos API Mandate**. Все команды открывают данные и функции только через сервисные интерфейсы и общаются только через них. Запрещены прямые связи, чтение чужих баз, общая память и «чёрные ходы». Каждый интерфейс проектируют так, чтобы его можно было открыть внешним разработчикам. Это считают переломом для Amazon: сервисы за API дали слабую связь и в итоге AWS. Google тоже вырос благодаря слабой связи.

Технически слабая связь это много малых компонентов, которые общаются через API или шину сообщений и прячут детали. Внутренние изменения не требуют правок в других частях. Организационно это малые команды: каждая отвечает за свой компонент, публикует API или схемы сообщений и выпускает обновления независимо. Это прямо облегчает принцип 7.

**Make reversible decisions.** Сегодняшняя модная технология завтра забыта. Fowler писал, что одна из задач архитектора это убирать архитектуру, то есть устранять необратимость. Bezos называет необратимые решения Type 1, а остальные «двусторонними дверями». Выбирайте лучшее на сегодня и будьте готовы обновить.

### Принципы 8-9

**Prioritize security.** Каждый инженер отвечает за безопасность систем, которые строит. Две идеи: zero trust и shared responsibility. Традиционная модель верит периметру: «доверенные» внутри, «недоверенные» снаружи. Но она всегда была уязвима к инсайдерам и фишингу. Авторы вспоминают фильм «Миссия невыполнима»: данные лежат в охраняемой комнате, но герой обманывает человека и выносит их. Сотрудники связаны с миром через почту и телефоны, поэтому внешние угрозы становятся внутренними. В облаке периметр размыт ещё сильнее.

По **shared responsibility** провайдер отвечает за безопасность самого облака, а пользователь за безопасность в облаке: чувствительность данных, требования компании и законы. В компаниях безопасностью часто занимаются отдельные команды. Облако перекладывает ответственность на инженеров без такой роли, поэтому каждый data engineer должен считать себя инженером по безопасности. Много утечек случились из-за простой ошибки: S3 bucket сделали публичным.

**Embrace FinOps.** FinOps это дисциплина и культура управления облачными финансами: инженеры, финансисты и бизнес вместе принимают решения о расходах на основе данных. Структура затрат изменилась. On-prem системы покупали раз в несколько лет (capex): покупка с запасом это потерянные деньги, а с недостатком мешает проектам. В облаке почти всё оплачивается по факту, за запрос или за мощность. Можно разогнаться и вернуть мощность. Но траты становятся динамическими, и нужно управлять бюджетом и эффективностью. Раньше инженеры оптимизировали скорость на фиксированных ресурсах. Теперь надо думать и о структуре затрат: например, когда перейти от оплаты за запрос на зарезервированную мощность.

FinOps расширяет мониторинг: следите за расходами, ставьте алерты на всплески и подумайте о жёстких лимитах с мягким отказом. Помните о **cost attack**: как DDoS, массовые загрузки из S3 bucket могут поднять счёт до банкротства малого стартапа. При публичном обмене ставьте requester-pays или быстро закрывайте доступ. FinOps Foundation основан в 2019, поэтому думайте о нём заранее, до больших счетов.

## Основные концепции архитектуры

Новые инструменты и архитектуры появляются каждую неделю. Но цель у всех одна: превратить данные в полезное для потребителей.

### Domains и services

**Domain** это область реального мира, для которой вы строите архитектуру. **Service** это набор функций для одной задачи, например обработка заказов. Один domain содержит несколько services. Домен sales может включать orders, invoicing и products, а домен accounting делит с ним сервис invoicing: продажа создаёт счёт, а бухгалтерия следит за оплатой. Определяя домен, идите от реального мира и не копируйте чужие решения. Лучший совет: поговорите с пользователями и заинтересованными сторонами. Избегайте ловушки «архитектуры в вакууме».

### Распределённые системы, scalability и failure

Для инженера важны четыре связанных свойства.

| Свойство | Значение |
|---|---|
| Scalability | Можно увеличить мощность, чтобы справиться со спросом |
| Elasticity | Система сама растёт и уменьшается под нагрузкой, иногда до нуля |
| Availability | Доля времени, когда сервис работает |
| Reliability | Вероятность, что система работает по стандарту |

Они связаны: низкая надёжность ведёт к низкой доступности, а elasticity повышает reliability, потому что держит скорость без ручной работы. Один сервер можно усиливать (vertical scaling), но у него жёсткий предел, а если он упадёт, нужен план резервирования. Поэтому используют **horizontal scaling**: добавляют машины. Обычно есть leader node, который запускает работу и собирает результат, и worker nodes. Данные реплицируют, и если машина упала, другие продолжают. Почти любое облачное хранилище внутри распределённое. Детали обычно скрыты, но авторы советуют изучить распределённые системы (например, книгу Kleppmann): это помогает улучшать pipelines.

### Tight и loose coupling: tiers, monolith, microservices

Вы выбираете, насколько связаны домены, сервисы и ресурсы. На одном конце всё жёстко зависит от всего (tightly coupled). На другом децентрализованные домены (loosely coupled). У слабой связи свой риск: команды строят системы, чьи данные не годятся соседям. Поэтому нужны общие стандарты, владельцы и ответственность.

| Уровень | Описание |
|---|---|
| Single tier | База и приложение на одном сервере. Сбой любой части роняет всё. Хорошо для прототипа, не для production. Аналитику на рабочей базе запускать нельзя: можно остановить приложение |
| Multitier | Данные, логика и представление разделены. Часто three-tier. В каждом слое свои технологии |
| Monolith | Всё под одной крышей. Связность техническая (слои) и доменная (как связаны домены) |
| Microservices | Отдельные слабо связанные сервисы. Сбой одного не мешает другим |

Single tier работает, пока не перестаёт: данные и логика конкурируют за ресурсы. Совет: начинайте с простого и закладывайте развитие. В распределённой системе есть выбор. **Shared-nothing**: один узел обрабатывает запрос и не делит ресурсы с другими. Либо узлы делят диск и память (**shared disk**), что полезно при отказе узла, но рискует contention.

У монолита слабая модульность. Замена компонента похожа на игру «убей крота»: улучшили одно, а в другом месте всплыли последствия. Команды данных часто игнорируют растущую сложность, и монолит превращается в большой ком грязи. Есть и странный гибрид, distributed monolith: распределённая система со слишком жёсткой связью (глава 4). Как превратить монолит в микросервисы? Если он не разбирается, начинают параллельную архитектуру. Авторы не советуют полный рефакторинг, а выделять сервисы по одному, с поддержкой владельцев монолита.

**Для данных.** Центральное хранилище по природе монолитно. Аналог микросервисов это доменные pipelines с доменными хранилищами: sales pipeline с sales warehouse, и так же для inventory. Для общих доменов есть два подхода: централизация (одна команда собирает данные всех доменов, классика хранилищ) и data mesh (каждая команда готовит свои данные). Авторы не проповедуют микросервисы догматично: используйте слабую связь как идеал с учётом ограничений технологий. Монолит не всегда плох: когда нужна скорость, начать с него проще. Но будьте готовы разделить его.

### Multitenancy

Все облачные сервисы в каком-то смысле multitenant. Виртуальная машина изолирована на общем сервере, а object storage изолирован при верных правах. Инженеры решают это и в малом: делят ли отделы одно хранилище, лежат ли данные многих клиентов в одной таблице. Два фактора. **Производительность**: нет ли noisy neighbor, когда нагрузка одного арендатора замедляет других. **Безопасность**: данные арендаторов изолированы, утечки исключены. Часто общие таблицы с изоляцией через views нормальны, но убедитесь, что views не текут. Читайте документацию вендора.

### Event-driven architecture

В бизнесе постоянно что-то происходит: новый клиент, заказ. Это **события**: что-то случилось, обычно изменилось состояние. Event-driven workflow создаёт, обновляет и асинхронно передаёт события между частями lifecycle. В нём три части: производство, маршрутизация и потребление события. Производитель, роутер и потребитель не должны жёстко зависеть друг от друга. Event-driven architecture строит на этом общение сервисов. Её плюс: состояние события распределено по нескольким сервисам. Это помогает, когда сервис упал, узел отказал или несколько потребителей хотят одни события. Любые слабо связанные сервисы кандидаты на неё.

### Brownfield и greenfield

Сначала нужно знать, начинаете ли вы с чистого листа или переделываете существующее.

**Brownfield** связан выбором прошлого. Критиковать прежнюю команду легко, но лучше понять, почему так решили: эмпатия и контекст помогают найти проблемы. Многие пробуют big-bang, то есть переписать всё сразу и придумать вывод старого по ходу. Авторы не советуют: риск высок, плана нет, решения необратимы. Альтернатива это **strangler pattern**: новые системы постепенно заменяют части старой, пока она не исчезнет. Каждый раз выводят одну часть и оценивают влияние на зависимые системы. Но вывод старого не всегда возможен. В большой организации кто-то всегда использует старые компоненты. «Legacy это снисходительное слово для того, что приносит деньги». Если вывод возможен, сначала покажите ценность новой платформы, а потом следуйте плану выхода.

> **Пояснение:** Например, команда переносит в новое хранилище один отчёт по продажам, сверяет цифры и только потом выключает старый отчёт. Каждый шаг можно отменить.

**Greenfield** это чистый старт. Он обычно проще и веселее. Но есть риски. **Shiny object syndrome**: тянуться к последней моде, не понимая её влияния на ценность. **Resume-driven development**: нагромождать модные технологии ради резюме. Требования важнее, чем «круто». В обоих случаях оценивайте компромиссы, выбирайте обратимые решения и стремитесь к положительному ROI.

## Типы и примеры архитектуры данных

Архитектура абстрактна, поэтому лучше рассуждать на примерах. Часть из них существует десятилетиями (warehouse), часть новая (lakehouse), а часть быстро появилась и ушла, но повлияла на современные шаблоны (Lambda).

![Развитие архитектур: warehouse, data lake, lakehouse и data mesh](/assets/fundamentals-of-data-engineering/ch03-warehouse-lake.png)

### Data warehouse

Центральное хранилище для отчётов и аналитики со структурированными данными. Это одна из старейших архитектур. Bill Inmon в 1989 году определил её как «предметно-ориентированную, интегрированную, неизменяемую и привязанную ко времени коллекцию данных для поддержки решений». Раньше хранилища были у корпораций с бюджетами в миллионы долларов и большими командами. Облачная модель pay-as-you-go сделала их доступными даже малым компаниям.

Есть два вида архитектуры хранилища. **Организационная** связывает данные со структурой команд и процессов. **Техническая** отражает устройство, например MPP. Они часто идут вместе, но не обязаны. Организационная архитектура имеет две черты:

- Она отделяет **OLAP** от рабочих **OLTP** баз. С ростом бизнеса это важно: нагрузка уходит с production, а аналитика ускоряется.
- Она централизует данные. Классически их тянут из приложений через **ETL**: extract берёт данные, transform чистит и применяет бизнес-логику, load пишет в хранилище и в несколько data marts под нужды отделов.

Техническая сторона: MPP поддерживают обычный SQL, но оптимизированы для параллельного сканирования огромных объёмов, а сейчас переходят от строчной к **колоночной** архитектуре. Вариант **ELT**: данные почти сразу идут в staging внутри хранилища в сыром виде, а преобразования идут там же. Цель: использовать мощность облачных хранилищ. ELT популярен и в потоках: события идут через CDC в staging и преобразуются в хранилище.

**Облачное хранилище** серьёзно изменило архитектуру. Amazon Redshift начал революцию: вместо оценки размера MPP на годы вперёд и многомиллионного контракта можно поднять кластер по требованию и удалить, когда он не нужен. Затем BigQuery, Snowflake и другие популяризировали **разделение compute и storage**: данные лежат в object storage, а вычисления поднимают по требованию. Они обрабатывают петабайты в одном запросе и покрыли многие задачи, для которых недавно нужен был Hadoop. Граница с озером размывается: сервисы становятся более широкими data platforms.

**Data mart** это подмножество хранилища для одного подразделения. Он делает данные удобнее для аналитиков и добавляет ещё одну стадию преобразования, которая ускоряет запросы со сложными join и агрегатами на больших данных (глава 8).

### Data lake

В эпоху big data появилась идея: не ограничивать данные структурой, а сложить всё, структурированное и нет, в одно место. Озеро обещало «демократизировать» данные. Но «data lake 1.0» в целом не выполнило обещание. Оно строилось на HDFS, потом ушло в облачный object storage с дешёвым и почти безлимитным хранением. Для запросов поднимали кластер и выбирали инструмент: MapReduce, Spark, Presto, Hive.

Проблемы 1.0:

- Озеро стало свалкой: data swamp, dark data, WORN. Данные росли без управления схемой, каталогов и поиска.
- Озеро было почти «только для записи». GDPR требует точечного удаления записей, и это вызвало головную боль.
- Обработка была тяжёлой. Даже join в MapReduce писать мучительно. Pig и Hive чуть помогли, но удаление и обновление строк делали созданием новых таблиц.
- Не сбылась и экономия. Вместо дорогих MPP обещали open source и дешёвое железо. В реальности управление Hadoop требовало больших команд, и расходы раздулись.

Не стоит преуменьшать пользу первых озёр: Netflix и Facebook, у которых были ресурсы на свои инструменты, получили большую ценность. Для многих других озеро стало «свалкой отходов, разочарований и растущих расходов».

### Lakehouse и data platform

Databricks предложила **data lakehouse**. Данные остаются в object storage и доступны разным движкам, но есть управление и структуры, как в хранилище. Главное отличие: **ACID-транзакции**, шаг от модели «лей и не меняй». С другой стороны, облачные хранилища стали похожи на озёра: разделяют compute и storage, обрабатывают петабайты, хранят полуструктурированные данные и дружат со Spark и Beam. Авторы уверены, что сближение продолжится: озеро и хранилище останутся разными архитектурами, но на практике границу заметят немногие. Вендоры (AWS, Azure, Google Cloud, Snowflake, Databricks) предлагают платформы с обеими возможностями. Будущий инженер будет выбирать не «озеро или хранилище», а converged data platform по вендору, экосистеме и открытости.

### Modern data stack

Это модная аналитическая архитектура, которая показывает рост абстракции. Прежние стеки опирались на дорогие монолитные наборы. Цель modern data stack: облачные plug-and-play компоненты (pipelines, хранилище, transformation, governance, мониторинг, визуализация), из которых собирают модульную и недорогую архитектуру. Результаты: self-service, гибкое управление данными, open source или простые инструменты с понятными ценами. Важна и community: пользователи тестируют ранние версии, предлагают функции и шлют pull requests. Для analytics engineering авторы считают этот стек выбором по умолчанию.

### Lambda, Kappa и unified batch/streaming

В начале 2010-х streaming стал очень популярен благодаря Kafka, Storm и Samza. Инженерам нужно было соединить batch и streaming в одной архитектуре.

![Сравнение Lambda, Kappa и модели Dataflow](/assets/fundamentals-of-data-engineering/ch03-batch-streaming.png)

- **Lambda.** Системы batch, streaming и serving работают независимо. Источник (в идеале append-only) шлёт данные в два места. Поток обрабатывается в «speed layer» с минимальной задержкой, обычно в NoSQL. В batch layer данные считаются в хранилище и дают заранее посчитанные агрегаты. Serving layer объединяет результаты. Минус: управлять системами с разным кодом тяжело, код и данные трудно сверять. Авторы не рекомендуют Lambda первой, хотя о ней до сих пор много пишут.
- **Kappa.** Jay Kreps предложил её как ответ на Lambda. Идея: взять платформу потоков как основу для всего (приём, хранение, выдача). Real-time и batch идут по одним данным: читают живой поток и «переигрывают» историю. Статья вышла в 2014, но широкого применения нет. Во-первых, streaming для многих всё ещё трудно в исполнении. Во-вторых, Kappa сложна и дорога: для огромной истории batch остаётся эффективнее.
- **Dataflow model.** И Lambda, и Kappa «склеивали» неподходящие инструменты Hadoop. Проблема нескольких путей кода осталась. Google предложил модель Dataflow и реализовал её в Apache Beam. Все данные это события, а агрегаты считаются по окнам (sliding, tumbling). Поток в реальном времени это unbounded данные, а batch это просто bounded поток, и его границы дают окно. Real-time и batch идут в одной системе почти одним кодом. Идея «batch как частный случай streaming» теперь широко принята: Flink и Spark идут тем же путём.

### Architecture for IoT

**IoT** это распределённая коллекция устройств с доступом в интернет. Данные создают устройства, которые периодически собирают их из среды, а не люди с клавиатуры. Они часто маломощны и работают при малой пропускной способности. Авторы ждут, что IoT станет одним из главных источников данных, поэтому разбирают его подробнее.

- **Devices** собирают данные и шлют дальше: звонок, часы, камера на конвейере, GPS-трекер. Устройство может ещё обрабатывать данные или запускать ML до отправки (edge computing). Инженеру не нужны внутренности, но он должен знать, какие данные устройство собирает, какие вычисления делает до отправки, как часто шлёт и что будет при сбое сети.
- **IoT gateway** это узел, который соединяет устройства и безопасно направляет их данные. Он позволяет устройствам работать с малой мощностью и хранит данные на промежутке. Обычно шлюз стоит в каждой точке, где есть устройства.
- **Ingestion** начинается со шлюза, дальше события идут в архитектуру приёма. Шлюз может копить данные и грузить батчами. В удалённых местах связи часто нет. Разнообразие даёт осложнения: поздние данные, разные схемы, повреждения и обрывы.
- **Storage** зависит от задержки. Для научных сенсоров достаточно batch object storage. Для «умного дома» нужны почти real-time ответы, и подходят очередь сообщений или time-series база.
- **Serving** разнообразна: отчёт из облачного хранилища или тревога о пожаре из потока. Важный шаблон похож на reverse ETL: данные станков анализируют и отправляют обратно для перенастройки устройств.

### Data mesh

Data mesh это недавний ответ на разросшиеся монолитные платформы (центральные озёра и хранилища) и на «великий разрыв» между операционными и аналитическими данными. Он применяет к данным идеи domain-driven design. Главная часть это децентрализация. Zhamak Dehghani пишет: вместо того чтобы лить данные из доменов в центральное озеро, домены сами хранят и отдают свои наборы данных в удобном виде. Четыре компонента:

- domain-oriented ownership: каждый домен владеет своими данными;
- data as a product: данные это продукт для потребителей;
- self-serve data infrastructure: общая платформа даёт доменам инструменты;
- federated computational governance: правила управления согласованы по доменам.

### Другие примеры

Есть и другие варианты: data fabric, data hub, metadata-first, live data stack (глава 11). Авторы выбрали самые важные: устоявшиеся или быстро развивающиеся. Следите за новыми подходами, но не привязывайтесь эмоционально к одному. Когда видите пользу, углубитесь и принимайте конкретные решения.

## Кто проектирует архитектуру

Архитектуру не проектируют в вакууме. Дни «башни из слоновой кости» прошли: архитекторы должны быть в курсе технологий, а граница между архитектурой и инженерией исчезает. В малой или малозрелой компании инженер может совмещать обе роли. Выбирая архитектуру, вы вместе с бизнесом оцениваете компромиссы: облачное хранилище или озеро, какое облако, когда подходит единый batch/streaming фреймворк (Beam, Flink).

## Итоги главы

- Data architecture это проектирование систем под меняющиеся потребности в данных. Она держится на гибких и обратимых решениях и оценке компромиссов.
- Two-way door можно отменить, поэтому такие решения стоит принимать чаще. Большие изменения режут на малые обратимые шаги.
- Хорошая архитектура гибкая, не навязывает «один размер для всех» и никогда не заканчивается.
- Девять принципов: общие компоненты, план на сбой, масштабируемость, лидерство, постоянная архитектурная работа, слабая связь, обратимость, безопасность и FinOps.
- Каждый data engineer отвечает за безопасность. Публичный S3 bucket частая причина утечек.
- Слабая связь идёт от Bezos API Mandate. Монолит не всегда плох, но будьте готовы его разделить.
- Для brownfield берите strangler pattern, а не big-bang. Для greenfield не поддавайтесь моде.
- Data lake 1.0 не оправдал надежд. Lakehouse добавил ACID и управление, а хранилище и озеро сближаются.
- Lambda сложна из-за двух кодовых путей, Kappa мало применяется, а Dataflow трактует batch как bounded поток.
- Data mesh отдаёт владение данными доменам. IoT добавляет устройства, шлюзы и обратный поток данных.

## Ключевые термины

| Термин (EN) | Что значит |
|---|---|
| Two-way door | Решение, которое легко отменить |
| Loose coupling | Слабая связь: части меняются независимо |
| RTO / RPO | Допустимое время простоя / допустимая потеря данных |
| Elasticity | Автоматическое увеличение и уменьшение ресурсов |
| Zero trust | Никому не доверять по умолчанию, даже внутри сети |
| Strangler pattern | Постепенная замена старой системы по частям |
| MPP | Параллельная обработка запросов на многих узлах |
| Data lakehouse | Озеро данных с ACID и управлением как у хранилища |
| Lambda / Kappa | Архитектуры для объединения batch и streaming |
| Data mesh | Децентрализованное владение данными по доменам |

## Что это значит на практике

- Записывайте решения и помечайте, какие из них one-way. Для таких решений нужна особая осторожность.
- Для каждой системы задайте RTO, RPO и целевую availability. Не копируйте чужие значения.
- Не запускайте аналитические запросы на продуктовой базе. Выносите данные в отдельное хранилище.
- Начинайте с простого монолита, если нужна скорость. Но заранее продумайте, как его разделить.
- Перед любым публичным доступом проверьте права на bucket. Настройте оповещения о расходах.
- Для старых систем используйте strangler pattern, а не большой переезд за один раз.
- Не выбирайте Lambda, Kappa или data mesh из-за моды. Сначала сформулируйте бизнес-требования.
