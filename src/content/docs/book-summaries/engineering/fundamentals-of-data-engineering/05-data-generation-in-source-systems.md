**Главная мысль:** Источники данных (source systems) обычно не в вашей власти. Но их устройство определяет, как вы будете забирать, хранить и считать данные. Нужно понимать, как источник создаёт данные, и договариваться с его владельцами.

## О чём глава

[Глава 4](/book-summaries/engineering/fundamentals-of-data-engineering/04-choosing-technologies/) была про выбор технологий. Теперь начинается сам lifecycle, и его первая стадия — generation в source systems. Прежде чем получить сырые данные, нужно понять, где они лежат, как создаются и какие у них особенности. Главные темы: типы источников (файлы, API, OLTP, OLAP, CDC, логи, очереди), шаблоны хранения изменений, виды времени, базы данных и API в деталях, data sharing, работа с владельцами источников и undercurrents.

Авторы ожидают, что с ростом data sharing рутинная работа «перенести данные из A в B» сильно упростится. Роль инженера сместится к пониманию связи между источниками и получателями. Поэтому знание природы данных в источнике останется критичным.

![Типы источников данных и способы забрать из них данные](/assets/fundamentals-of-data-engineering/ch05-source-types.png)

## Как создаются данные

Данные — это неорганизованный набор фактов без контекста. **Аналоговые** данные возникают в реальном мире (речь, текст на бумаге, музыка) и часто мимолётны. **Цифровые** данные получены из аналоговых (приложение превращает речь в текст) или родились в цифровой системе (оплата картой в интернет-магазине записывается в несколько баз). Источники: сайт, мобильное приложение, IoT, платёжные терминалы, биржа. Совет авторов: изучите документацию источника и его особенности, они влияют на приём данных.

## Основные идеи

### Файлы

Файл — это последовательность байтов на диске. В файлы приложения пишут параметры, события, логи, изображения и аудио. Файл — универсальный способ обмена: многие организации до сих пор отправляют файлы. Например, государственное ведомство даёт Excel или CSV, иногда по почте. Основные форматы источников: Excel, CSV, TXT, JSON, XML. Они бывают структурированными (Excel, CSV), полуструктурированными (JSON, XML, CSV) и неструктурированными (TXT, CSV). Parquet, ORC и Avro разобраны в [главе 6](/book-summaries/engineering/fundamentals-of-data-engineering/06-storage/).

### API

API — стандартный способ обмена между системами. В теории он упрощает ingestion. На практике многие API оставляют много сложности, и инженеры тратят силы на поддержку своих подключений.

### OLTP и ACID

Базу приложения обычно называют **OLTP** (online transaction processing). Она хранит состояние приложения, например баланс банковского счёта, и очень быстро читает и пишет отдельные записи. Термин «транзакционная» не обязательно означает поддержку атомарных транзакций. RDBMS выбирает или обновляет строку быстрее миллисекунды (без сети) и выдерживает тысячи операций в секунду. Кластер документной базы выдерживает ещё больше, но может быть неконсистентным. OLTP хорош как бэкенд приложения, когда тысячи или миллионы пользователей одновременно пишут данные. Для аналитики в большом масштабе, где запрос сканирует огромный объём, он подходит хуже.

**ACID** — набор гарантий: atomicity, consistency, isolation, durability.

- **Atomicity.** Набор изменений фиксируется как единое целое. Пример: банковский перевод проверяет балансы счетов A и B и переводит деньги, если на A хватает. Либо обновляются оба счёта, либо ни один.
- **Consistency.** Любое чтение вернёт последнюю записанную версию.
- **Isolation.** Если два обновления идут одновременно, итог такой же, как при последовательном выполнении.
- **Durability.** Зафиксированные данные не пропадут даже при отключении питания.

ACID не обязателен для бэкенда приложения, а ослабление гарантий может сильно повысить скорость и масштаб. Но ACID даёт согласованную картину мира и упрощает жизнь разработчику. Некоторые распределённые базы используют eventual consistency для скорости. Нужно знать модель согласованности источника. Это защитит от катастроф.

**OLTP и аналитика.** Малые компании часто запускают аналитику прямо на OLTP. Это работает недолго, потому что упирается в структурные ограничения OLTP и в конкуренцию за ресурсы с транзакциями. Data engineer должен понимать внутренности OLTP, чтобы подключить аналитику и не замедлить production. Приложения, которые совмещают транзакции и аналитику, авторы называют **data application**.

### OLAP

OLAP-система создана для больших аналитических запросов и плохо ищет отдельные записи. Колоночные базы сканируют много данных и обходятся без индексов. Запрос обычно читает блок данных от 100 MB. Тысячи точечных запросов в секунду «положат» такую систему без слоя кеша. Термин «OLAP» здесь означает любую систему для интерактивной аналитики, а не только кубы. Зачем говорить об OLAP в главе об источниках? Инженерам часто нужно читать из него. Например, warehouse даёт данные для обучения ML. Или OLAP питает reverse ETL, когда производные данные возвращаются в CRM, SaaS-платформу или транзакционное приложение.

### CDC

**Change data capture** извлекает каждое событие изменения (insert, update, delete) в базе. Её применяют для репликации между базами почти в реальном времени и для event stream. Реляционные базы часто пишут лог событий на сервере базы, из него делают поток. Многие облачные NoSQL могут отправлять лог или поток событий в целевое хранилище.

### Логи

Лог фиксирует события в системе. Он богат данными для аналитики, ML и автоматизации. Источники: операционные системы, приложения, серверы, контейнеры, сети и IoT-устройства. Минимум в логе: **who** (человек, система или сервисный аккаунт), **what** (событие и метаданные) и **when** (timestamp).

| Кодирование | Свойства |
|---|---|
| Binary | Компактный формат для места и быстрого I/O. Пример: логи баз данных |
| Semistructured | Текст, чаще JSON. Читается машиной и переносим, но менее эффективен. Для извлечения нужен свой код |
| Plain text | Вывод консоли. Общего стандарта нет, разбирать сложно |

**Resolution** — сколько данных о событии пишется. Лог базы хранит достаточно, чтобы восстановить состояние на любой момент. Для big data записать все изменения непрактично, тогда лог лишь отмечает факт коммита. **Level** — условия записи, особенно для ошибок и отладки: пишется всё или только ошибки.

**Latency.** Batch-логи часто пишутся непрерывно в файл. Для real-time отдельные записи отправляют в систему сообщений, например Kafka или Pulsar.

**Database logs.** Write-ahead log — это бинарный файл в формате базы. База получает запросы на запись и обновление и пишет каждую операцию в лог до подтверждения. Если сервер упал, он восстановит состояние при перезапуске по незавершённой работе из лога. Эти логи очень полезны в data engineering, особенно для CDC.

### CRUD и insert-only

**CRUD** (create, read, update, delete) — самый частый шаблон хранения состояния приложения. Данные нужно создать, потом читать и обновлять, потом, возможно, удалить. CRUD используют в API и базах. Из таких баз можно извлекать snapshot. Событийное извлечение через CDC даёт полную историю операций и анализ почти в реальном времени.

**Insert-only** хранит историю прямо в таблице. Запись не обновляется: вставляется новая версия с timestamp. Пример: таблица адресов клиентов. При CRUD смена адреса — это update. При insert-only вставляется новая запись с тем же ID клиента, а текущий адрес берётся из последней. Это как лог базы внутри таблицы. Так хорошо работает банковское приложение, которому нужна история адресов. Есть и отдельный аналитический вариант — **insert-only ETL**: конвейер вставляет новую запись в аналитическую таблицу при каждом обновлении в CRUD-таблице. Минусы: таблица быстро растёт (иногда записи чистят по дате «заката» или по максимальному числу версий) и чтение текущего состояния требует `MAX(created_timestamp)`, что дорого при сотнях и тысячах версий на ID.

### Сообщения и потоки

Термины message queue и streaming platform часто путают, но разница важна. **Message** — это сырые данные между двумя и более системами. Обычно сообщение идёт через очередь от publisher к consumer и после доставки удаляется. Пример: IoT-датчик отправляет температуру, сервис решает, включать ли печь, и шлёт сообщение контроллеру. После получения сообщение убирают.

**Stream** — append-only лог записей событий. Они копятся в упорядоченной последовательности (порядок задаёт timestamp или ID; из-за распределённых систем доставка не всегда точна). Потоки нужны, когда важно, что произошло в серии событий. Записи хранятся долго, недели и месяцы. Это позволяет агрегировать несколько записей и «отматывать» поток к точке во времени. Системы потоков умеют обрабатывать сообщения, и платформы потоков часто используют для передачи сообщений. Сообщения копят в потоке для аналитики. В примере с печью температуру можно потом анализировать для трендов.

### Виды времени

Время важно для любого ingestion, а в стриминге особенно: данные непрерывны и их ждут сразу после создания.

![Четыре вида времени события: event, ingestion, process, processing](/assets/fundamentals-of-data-engineering/ch05-time-types.png)

- **Event time** — когда событие возникло в источнике. До приёма проходит неопределённая задержка.
- **Ingestion time** — когда оно попало из источника в очередь, кеш, память, object storage или базу. Обработка может идти сразу, через минуты или дни, а может и вовсе не идти.
- **Process time** — когда данные обработаны (обычно преобразованы).
- **Processing time** — сколько длилась обработка.

Записывайте timestamp на каждом этапе, желательно автоматически. Настройте мониторинг, чтобы точно отслеживать путь данных.

## Практические детали источников

Конкретные API-фреймворки и базы быстро меняются. Но это базовые знания, а читать нужно много, чтобы не отставать.

### Базы данных: на что смотреть

- **DBMS:** состоит из storage engine, query optimizer, disaster recovery и других компонентов.
- **Lookups:** как база ищет данные. Бывают индексы (B-tree, LSM), а бывают базы без них. Знайте это и используйте для эффективного извлечения.
- **Query optimizer:** есть ли он и каковы его свойства.
- **Scaling:** масштабируется ли база горизонтально (больше узлов) или вертикально (больше ресурсов на одной машине).
- **Modeling patterns:** что лучше работает: нормализация или широкие таблицы.
- **CRUD:** каждая база обрабатывает его по-своему.
- **Consistency:** полная или ослабленная (eventual); есть ли строгие чтения как опция.

### Реляционные базы

RDBMS появились в IBM в 1970-х, популярны стали благодаря Oracle в 1980-х, а рост интернета породил LAMP-стек (Linux, Apache, MySQL, PHP). Данные лежат в таблицах: строки и поля. У всех строк одна схема со статическими типами. Таблицы индексируются по primary key, а foreign key связывают таблицы и дают joins. Нормализация убирает дубли и не требует обновлять состояние в нескольких местах. RDBMS обычно ACID, поэтому они хороши для быстро меняющегося состояния приложения. Задача data engineer — понять, как сохранить это состояние во времени.

### NoSQL

Авторы замечают: часто начинают с реляционной базы как с «универсального прибора» и натягивают на неё все задачи. Когда требования к данным и запросам меняются, она рушится под тяжестью. Тогда нужна база под конкретную нагрузку. NoSQL («not only SQL») — класс баз, которые отказались от реляционной парадигмы. Они выигрывают в скорости, масштабе и гибкости схемы, но обычно теряют строгую consistency, joins или фиксированную схему. История: в начале 2000-х Google и Amazon переросли реляционные базы и создали распределённые нереляционные. Термин появился в 1998, а современный смысл ему дал Эрик Эванс. Название расплывчато и в 2022 году, но стало общим для «новой школы» баз.

![Выбор типа NoSQL базы по задаче](/assets/fundamentals-of-data-engineering/ch05-nosql-choice.png)

- **Key-value.** Запись ищется по уникальному ключу, как в hash map, но масштабируемее. In-memory версии популярны как кеш сессий: нужен быстрый поиск и высокая параллельность, а данные при остановке исчезают. Такой кеш снимает нагрузку с основной базы. Есть и долговечные key-value: интернет-магазин хранит каждое событие заказа на диске и на нескольких узлах.
- **Document.** Особый key-value. Документ — вложенный объект, практически JSON. Документы лежат в collections (аналог таблицы). Joins нет, поэтому данные трудно нормализовать. Одно и то же иногда приходится держать в нескольких документах и обновлять везде. Схема не навязана: это и благо, и проклятие. Авторы видели документные базы, с которыми невозможно работать: данные становились несогласованными и раздутыми. Смена схемы без предупреждения ломает ingestion. Обычно нет ACID. Для аналитики нужен full scan коллекции или CDC. Scan замедляет базу, а serverless-облака берут за него деньги.
- **Wide-column.** Огромные объёмы и очень низкая задержка: петабайты, миллионы запросов в секунду, менее 10 мс. Популярны в e-commerce, fintech, ad tech и IoT. Только один индекс (row key), сложных запросов нет. Для них данные выгружают во вторичную систему через большие scans или CDC.
- **Graph.** Узлы и рёбра (Neo4j, продукты Amazon и Oracle). Подходит для анализа связности. В документной базе число прямых друзей найти просто, а сколько людей достижимо через два перехода, считать медленно и дорого. Граф создан для таких обходов. Для data engineer варианты такие: переложить граф в реляционные строки, анализировать на месте или взять специальный инструмент. Большие запросы могут перегрузить production.
- **Search.** Нужны для текстового поиска (точного, нечёткого, семантического) и анализа логов. Примеры: Elasticsearch, Solr, Algolia. Инженеру придётся выгружать оттуда данные для KPI-отчётов.
- **Time series.** Значения по времени: цены акций, температура датчика. Для быстрых потоков (IoT, логи, ad tech, fintech) нужны специальные базы, часто с буфером в памяти для быстрой записи. Есть измерения (регулярные) и события (нерегулярные). Хороши для операционной аналитики, но не для BI. Joins редки.

### API

API стали стандартным способом обмена в облаке, у SaaS и внутри компаний. Нас интересуют API на HTTP.

- **REST.** Сейчас доминирует. Основы заложил Рой Филдинг в диссертации 2000 года. Он построен на HTTP-методах (GET, PUT). Взаимодействие stateless: сессии нет, каждый вызов независим. Критики говорят, что REST — не полная спецификация, и нужно много знаний предметной области. Уровень абстракции разный: от тонкой обёртки до продуманного API для аналитики. Работу упрощают client libraries (особенно на Python) и готовые коннекторы. Но для многих API их нет, и в крупной компании инженер пишет и поддерживает свой код: понять структуру данных, написать извлечение, выбрать стратегию синхронизации.
- **GraphQL.** Создан в Facebook как альтернатива общим REST API. REST обычно ограничивает запросы одной моделью данных, а GraphQL позволяет получить несколько моделей за один запрос. Он построен на JSON, ответ повторяет форму запроса. Между REST и GraphQL идёт «священная война», но инженеры встречают оба.
- **Webhooks.** Простая событийная передача: когда в источнике происходит событие, он вызывает HTTP endpoint потребителя. Направление противоположно обычному API, поэтому webhooks называют reverse API. Endpoint получает POST и может запустить процесс или сохранить данные. Для большого потока используют очереди сообщений.
- **RPC и gRPC.** RPC запускает процедуру на удалённой системе. gRPC разработан в Google в 2015 году и затем стал открытым стандартом. Его API есть у Google Ads и GCP. Он построен на Protocol Buffers и делает упор на эффективный двусторонний обмен по HTTP/2: загрузка CPU, энергопотребление, батарея, полоса. Как и GraphQL, он задаёт более жёсткие стандарты, чем REST, поэтому подходят общие client libraries, а навыки переносятся.

### Data sharing и сторонние данные

В основе data sharing — multitenant система с политиками безопасности для обмена между арендаторами. Любое объектное хранилище публичного облака с тонкими правами может быть такой платформой. Облачные warehouse тоже поддерживают sharing. Многие платформы умеют фильтровать строки, колонки и чувствительные данные. **Data marketplace** — центр торговли данными, где поставщики продают их, не думая о сетевом доступе. Sharing упрощает и конвейеры внутри организации: подразделения управляют своими данными и своими расходами на запросы и вычисления, а значит, поддерживают децентрализацию, например data mesh. Авторам это близко: выбирайте общие компоненты для простого обмена данными и опытом, а не самую модную технологию.

**Сторонние источники.** Сегодня каждая компания технологическая, и многие компании и госорганы открывают данные клиентам. Примеры: Бюро статистики труда США, NASA, Facebook для рекламодателей. Зачем? Данные «липкие»: пользователь встраивает ваше приложение в свои системы, больше использования значит больше данных. Доступ: через API, data sharing или загрузку. Типичный сценарий: данные CRM, потом scoring модель клиентов, затем reverse ETL обратно в CRM, чтобы продавцы звонили более подходящим лидам.

### Очереди сообщений и event-streaming

Событийная архитектура распространена и растёт: в облаке очереди и платформы потоков проще настроить, а приложения с real-time аналитикой (data apps) развиваются. События и запускают работу приложения, и питают аналитику. Эти системы пересекают несколько стадий lifecycle: одна платформа может быть источником (передача сообщений в приложении) и системой ingestion или transformation для real-time аналитики.

**Message queue** асинхронно передаёт небольшие сообщения (килобайты) между системами по модели publish/subscribe. Получатель подтверждает приём, и сообщение исчезает. Очередь развязывает сервисы (поэтому нужна в микросервисах), буферизует всплески и делает сообщения долговечными через репликацию. Три вещи:

- **Порядок.** В распределённых очередях это сложная задача. Часто порядок «нечёткий». Строгий FIFO обещает, что A, принятое раньше B, доставят раньше. На практике сообщения приходят вразнобой. SQS standard старается сохранить порядок, SQS FIFO даёт гарантии сильнее, но дороже. Не рассчитывайте на порядок, если очередь его не гарантирует.
- **Частота доставки.** Exactly once или at least once. При at least once сообщение могут получить несколько раз. Идеально, если система **idempotent**: результат одной и нескольких обработок один. Даже при exactly once потребитель мог полностью обработать сообщение и упасть перед подтверждением. Тогда обработка пройдёт дважды.
- **Масштаб.** Популярные очереди масштабируются горизонтально: растут и сжимаются, буферизуют сообщения при отставании систем, хранят их долговечно. Цена: дубли и нечёткий порядок.

**Event-streaming platform** продолжает идею очереди, но хранит упорядоченный лог записей. Данные удерживаются, и сообщения можно перечитать с любого прошлого момента. Событие состоит из key, value и timestamp. Что важно:

- **Topic** — набор связанных событий: заказы, фрод-оповещения, показания IoT. У topic может быть много producers и consumers. Пример: topic «web orders» читают fulfillment (запускает выполнение заказа) и marketing (real-time аналитика и ML). Граница между аналитикой и событийной системой размыта.
- **Partitions** — деление потока на несколько. Аналогия: многополосная трасса, параллелизм и пропускная способность. Сообщения распределяют по partition key, одинаковый ключ всегда попадает в одну partition. Для IoT удобно взять device ID, чтобы все сообщения устройства шли на один сервер.
- **Hotspotting** — перекос, когда в одну partition приходит непропорционально много сообщений. Пример: ключ «штат США» при устройствах, распределённых по населению: partitions Калифорнии, Техаса, Флориды и Нью-Йорка перегружены. Выбирайте ключ с равномерным распределением.
- **Fault tolerance.** Поток хранится на нескольких узлах. Если узел упал, его заменяет другой, записи не теряются.

## С кем работать

Дипломатия и отношения с владельцами источников — недооценённая часть работы. Авторы выделяют два типа stakeholders. **Systems stakeholders** строят и поддерживают источники: разработчики, сторонние поставщики. **Data stakeholders** владеют данными и доступом: IT, data governance, сторонние компании. Часто это разные люди, иногда одни и те же. Вы зависите от того, насколько они следуют хорошим практикам разработки и работы с базами. Идеально, если они используют DevOps и agile.

Авторы советуют создать обратную связь с ними, чтобы они знали, как используются данные. Это одна из самых упускаемых возможностей. Что-то обязательно случится: изменится схема, упадёт сервер. Вы должны узнать о влиянии заранее.

- **Data contract** — письменное соглашение между владельцем источника и командой, которая принимает данные в конвейер. Определение Джеймса Денмора: контракт фиксирует, какие данные, каким методом (full или incremental), как часто, кто контакты у источника и у приёма. Храните его в известном месте (репозиторий GitHub, внутренняя документация), по возможности в стандартной форме, чтобы её можно было встроить в разработку или запрашивать программно.
- **SLA** — ожидания от источника, например «данные будут надёжно доступны и хорошего качества». **SLO** — измеримая цель по SLA, например «аптайм 99%». Если это слишком формально, хотя бы устно договоритесь об аптайме, качестве и других важных гарантиях.

## Undercurrents для источников

В отличие от других стадий, источники обычно вне вашего контроля. Вы надеетесь, что владельцы следуют хорошим практикам. Стремитесь получить как можно больше поддержки сверху.

| Область | Вопросы |
|---|---|
| Security | Данные зашифрованы при хранении и передаче? Доступ через публичный интернет или VPN? Секреты (SSH-ключи, пароли, токены) в менеджере ключей или SSO. Можно ли доверять источнику: trust but verify, чтобы не принять данные от злоумышленника |
| Data management | Governance (кто управляет данными), quality (договоритесь об ожиданиях), schema (ждите изменений и просите предупреждать), master data management, privacy и ethics (сырые или обфусцированные данные, срок хранения), регуляторные ограничения |
| DataOps | Automation (автоматизация источника не должна ломать вашу: развяжите их), observability (аптайм, схема, качество, согласованность записей, хеширование по политике), incident response (что делает конвейер, если источник упал, и как делать backfill). Пример: база для CDC упёрлась в I/O и её масштабируют, доступны ли данные |
| Data architecture | Reliability (предсказуемость, частота сбоев, MTTR), durability (потеря данных при отказе железа или сети, масштаб сбоя), availability, people (кто отвечает за дизайн и как вы узнаете о breaking changes); договоритесь о SLA |
| Orchestration | Нужны сеть, authentication и authorization. Cadence: данные по расписанию или в любой момент. Common frameworks: общий Kubernetes или Airflow с командой приложения; баланс пользы интеграции и риска сильной связанности |
| Software engineering | Сеть (HTTPS, SSH, VPN), credentials без попадания в код и репозиторий, IAM roles, access patterns (pagination, драйверы, retries, timeouts), orchestration, parallelization, deployment |

## Итоги главы

- Источник данных вне вашего контроля, но определяет приём, хранение и обработку, поэтому изучайте его документацию и особенности.
- OLTP хранит состояние приложения и даёт ACID. Аналитику на нём запускать нельзя, она не масштабируется и мешает production.
- Для истории изменений нужны CDC или insert-only. Snapshot CRUD-таблицы теряет промежуточные версии.
- Сообщение исчезает после доставки, а поток хранит упорядоченный лог событий и даёт перечитывать его.
- Записывайте event, ingestion и process time, чтобы видеть путь данных и задержки.
- Тип NoSQL определяет, как извлекать данные: document и wide-column нужны scan или CDC, graph и time series требуют особого подхода.
- API бывают REST, GraphQL, webhooks и gRPC. Для многих API инженер всё равно пишет и поддерживает свой код.
- В очередях порядок нечёткий, а дубли возможны. Делайте обработку idempotent и выбирайте partition key без hotspotting.
- Data contract и SLA/SLO с владельцами источников лучше любых сюрпризов. Нужна обратная связь о смене схемы.
- Источник — не «чужая проблема»: игнорировать его опасно для вас, а хорошая работа с командами приложений повышает качество данных.

## Ключевые термины

| Термин (EN) | Что значит |
|---|---|
| Source system | Система, где данные возникают |
| OLTP | База для частых быстрых операций над записями |
| OLAP | Система для больших аналитических запросов |
| ACID | Набор гарантий транзакций |
| CDC | Захват каждого изменения в базе |
| Write-ahead log | Лог операций, записанный до подтверждения |
| Insert-only | Шаблон: новые версии вместо обновления |
| Event time / ingestion time | Время события и время приёма |
| Idempotent | Повтор операции не меняет результат |
| Partition key | Ключ распределения сообщений по partitions |
| Hotspotting | Перекос нагрузки на одну partition |
| Data contract | Соглашение об извлечении данных из источника |
| Webhook | Вызов вашего endpoint из источника при событии |

## Что это значит на практике

- Прочитайте документацию источника. Узнайте, как он пишет, коммитит и индексирует данные.
- Не запускайте тяжёлую аналитику на production OLTP. Используйте реплику, CDC или выгрузку.
- Для истории изменений берите CDC или insert-only. Простой snapshot теряет промежуточные версии.
- Делайте обработку idempotent. Дубли и нарушенный порядок в очередях неизбежны.
- Пишите event, ingestion и process time. Иначе трудно разобрать задержки.
- Заключите data contract или хотя бы устное соглашение. Настройте уведомления об изменении схемы.
- Храните секреты в менеджере. Не кладите их в код и репозиторий.
- Подружитесь с командой приложения и предложите ей аналитику для её пользователей. Так вы получаете поддержку и общий результат.
