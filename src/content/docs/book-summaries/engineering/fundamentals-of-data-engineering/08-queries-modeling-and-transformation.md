**Главная мысль:** на этой стадии сырые данные становятся полезными. Запрос читает данные, модель вкладывает в них бизнес-логику, а трансформация сохраняет результат для следующих шагов. Авторы считают, что на этой стадии дата-инженер работает с данными плотнее всего и добавляет больше всего ценности.

## О чём глава

Предыдущие стадии `data engineering lifecycle` в основном двигали данные или хранили их. Глава про [приём данных](/book-summaries/engineering/fundamentals-of-data-engineering/07-ingestion/) закончилась тем, что данные лежат в системе. Теперь их нужно превратить во что-то, чем пользуются аналитики, data scientists и ML-инженеры.

Глава идёт в таком порядке:

- запросы: как работает query, почему он бывает медленным, чем отличаются запросы к batch и к streaming данным;
- моделирование: нормализация, Inmon, Kimball, `Data Vault`, wide table и что делать с потоком;
- трансформации: batch и streaming, update patterns, MapReduce, views и federation;
- участники и undercurrents на этой стадии.

Главный язык главы — SQL. Авторы предполагают, что вы знаете SQL, primary и foreign key. Слово `database` они используют для связки «движок запросов плюс хранилище»: это может быть cloud warehouse или Spark над S3. Большая часть идей работает и для полуструктурированных данных, а многое подходит и для неструктурированных.

## Запросы

Запрос (`query`) позволяет получить данные и что-то с ними сделать. В [главе 5](/book-summaries/engineering/fundamentals-of-data-engineering/05-data-generation-in-source-systems/) мы говорили про CRUD. Когда query читает данные, это буква R. Например, `SELECT * FROM foo WHERE id=1` просит записи, которые подходят под условие (predicate). Многие базы позволяют ещё создавать, менять и удалять записи: это CUD.

В SQL команды делят на четыре группы:

| Группа | Для чего | Примеры |
|---|---|---|
| DDL (data definition language) | Описывает объекты: базы, схемы, таблицы, пользователей | `CREATE`, `DROP`, `ALTER` |
| DML (data manipulation language) | Добавляет и меняет данные внутри объектов | `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `COPY`, `MERGE` |
| DCL (data control language) | Управляет доступом | `GRANT`, `DENY`, `REVOKE` |
| TCL (transaction control language) | Управляет транзакциями: точки фиксации и откаты | `COMMIT`, `ROLLBACK` |

Авторы приводят пример с DCL. В компанию приходит data scientist Сара, и ей нужен доступ на чтение к одной базе: вы даёте `GRANT SELECT`. Через пару месяцев её переманивает другая компания, и вы отзываете доступ командой `REVOKE`. Если вы понимаете DCL, вы быстрее решаете проблемы вида «коллега не видит нужные данные» и не оставляете людям лишний доступ.

### Жизнь запроса

За простым «написал код, получил результат» стоит четыре шага:

1. Движок компилирует SQL: проверяет синтаксис, что объекты существуют и что у пользователя есть права.
2. Код превращается в bytecode: компактный набор шагов, который понимает движок.
3. `Query optimizer` разбирает bytecode, переставляет и упрощает шаги, чтобы лучше использовать ресурсы.
4. Запрос выполняется, и вы получаете результат.

`Query optimizer` — это часть базы, которая ищет самый дешёвый способ выполнить запрос. Он оценивает join, индексы, объём данных для scan и другие факторы. Время работы одного и того же запроса может сильно отличаться в зависимости от плана, который выбрал optimizer. Напрямую вы optimizer не настраиваете, но понимание его работы помогает писать быстрые запросы и читать `explain plan`.

### Как ускорить запрос

Медленные запросы встретятся обязательно. Авторы советуют не бороться с базой: изучите её сильные стороны и компенсируйте слабые.

**Join и схема.** Одна таблица редко полезна сама по себе, ценность появляется после объединения. Даже columnar-базы, которые раньше считались слабыми в join, теперь справляются хорошо. Если аналитики снова и снова соединяют одни и те же таблицы, эти таблицы можно соединить заранее (`pre-join`). Для этого ослабляют нормализацию и делают таблицу шире, иногда с массивами и структурами вместо связанных сущностей. Другой путь: оставить нормализованную схему, но добавить заранее соединённые таблицы или materialized views для частых сценариев.

Сложные условия join тоже требуют ресурсов. В row-oriented базах помогают индексы по вычисляемому значению. Например, PostgreSQL умеет строить индекс по `lower(name)`, и optimizer применит его, если `lower()` стоит в условии. Можно также завести производную колонку для join, но тогда пользователей придётся научить ею пользоваться.

Отдельная неприятность — `row explosion`. Она случается, когда в ключах join много повторов: каждая строка слева сочетается с каждой подходящей строкой справа. Если значение `this` пять раз встречается в таблице A и десять раз в таблице B, получится 5 × 10 = 50 строк. При большом числе повторов строк становится так много, что запрос съедает ресурсы базы или падает.

```sql
SELECT count(*) AS строк_в_результате
FROM (SELECT 'this' AS k FROM range(5)) a
JOIN (SELECT 'this' AS k FROM range(10)) b USING (k);
```

```text
┌────────────────────┐
│ строк_в_результате │
├────────────────────┤
│ 50                 │
└────────────────────┘
```

Важно знать, умеет ли ваш optimizer переставлять join и predicate. Если не умеет, row explosion на раннем шаге уронит запрос, хотя условие позже убрало бы повторы. Наконец, лучше использовать CTE (common table expressions), а не вложенные подзапросы и временные таблицы: CTE читаются как последовательность шагов, а часто ещё и работают быстрее скрипта с промежуточными таблицами. Если промежуточные таблицы всё же нужны, делайте их временными.

**Explain plan и мониторинг.** `Explain plan` показывает, как optimizer выбрал самый дешёвый план: какие объекты он использует (таблицы, индексы, кэш) и сколько ресурсов тратит каждый шаг. Одни базы показывают его графически, другие через команду `EXPLAIN`. Кроме плана следите за метриками базы:

- диск, память и сеть;
- время загрузки данных против времени обработки;
- время выполнения, число записей, объём scan и объём shuffle;
- конкурирующие запросы, которые мешают друг другу;
- число одновременных подключений: если их не хватает, пользователи просто не смогут подключиться.

**Не читайте всю таблицу.** Правило простое: запрашивайте только нужные данные. `SELECT *` без условий читает все строки и все колонки. Это неэффективно и дорого, особенно если база берёт плату за прочитанные байты или время вычислений. Чтобы сократить scan, применяют `pruning`: чтение только нужных частей данных. В columnar-базе для этого выбирают только нужные колонки. Snowflake и BigQuery на очень больших таблицах (от нескольких терабайт) дают cluster key, который упорядочивает данные так, что запрос читает меньше. BigQuery ещё позволяет разбить таблицу на партиции и читать только нужные. Но неудачный clustering ухудшает скорость. В row-oriented базах pruning обычно сводится к индексам (мы разбирали их в [главе 6](/book-summaries/engineering/fundamentals-of-data-engineering/06-storage/)): индексы нужны для самых важных запросов, но слишком много индексов тормозит таблицу.

**Как база фиксирует изменения (commit).** Транзакция объединяет несколько операций так, чтобы база всегда оставалась согласованной, в том числе при сбое. Без транзакций разные пользователи получили бы противоречивые результаты. Нужно точно знать, как ваша база работает с commit: даёт ли она ACID и возможны ли `dirty read`, когда запрос видит строку, изменённую незавершённой транзакцией. Ещё одна деталь: при update и delete многие базы пишут новые файлы и держат старые как точку возврата. Тогда много мелких commit засоряют хранилище, и его приходится чистить.

Авторы сравнивают три базы:

| База | Как фиксирует изменения | Плюс | Минус |
|---|---|---|---|
| PostgreSQL | ACID-транзакции, блокировка строк. Аналитический запрос видит согласованную картину на момент времени | Надёжные транзакции | Блокировки замедляют работу. Не рассчитана на большие scan |
| BigQuery (похожи Snowflake и Spark) | Commit всей таблицы на момент времени. Запрос читает последний snapshot и не видит новых изменений | Нет блокировок на чтение | Одна запись за раз, остальные ждут в очереди |
| MongoDB | Настраиваемая согласованность: на уровне базы и отдельных запросов | Высокая масштабируемость и скорость записи | В некоторых режимах при перегрузке молча теряет записи |

Потеря записей в MongoDB подходит для IoT, где важна масса измерений, а не каждое из них. Для точной статистики это плохой выбор. Авторы подчёркивают: плохих баз нет, есть неверный выбор и неверные настройки. Инженер обязан понимать свои инструменты и задачу, ведь от этого зависит, будет проект успешным или провальным. Подробнее о согласованности см. главу 6.

**Vacuum.** Из-за транзакций в базе копятся старые версии записей. Когда они больше не нужны, их удаляют: это `vacuum`. Зачем это нужно:

- освобождается место, таблицы меньше «пухнут», запросы быстрее;
- планы запросов точнее, потому что optimizer не смотрит на устаревшие записи;
- чистятся плохие индексы.

В разных системах vacuum работает по-разному. В базах на object storage (BigQuery, Snowflake, Databricks) старые версии лишь занимают место и стоят денег. В Snowflake vacuum напрямую не запускают: вы задаёте интервал time travel, и после него snapshots удаляются сами. BigQuery хранит историю фиксированные семь дней. Databricks держит данные бессрочно, пока их не почистят вручную, поэтому vacuum нужен для контроля расходов на S3. В Redshift vacuum идёт автоматически, но иногда его запускают вручную для тонкой настройки. Для PostgreSQL и MySQL vacuum ещё важнее, потому что много транзакций быстро копят мёртвые записи.

**Кэш результатов.** Представьте тяжёлый запрос, за который база берёт деньги при каждом запуске. Многие облачные OLAP-базы сохраняют результат. Первый запуск (cold query) может занять 40 секунд. Повторный возьмёт результат из кэша и вернёт его за секунду или быстрее. Используйте кэш там, где можно: он снижает нагрузку на базу и ускоряет частые запросы. Materialized view тоже работает как кэш запроса.

### Запросы к streaming-данным

Streaming-данные постоянно в движении, поэтому запросы к ним устроены иначе. Kafka и Pulsar облегчают такие запросы. Начнём с простых шаблонов.

**Fast follower.** Как мы видели в [главе 7](/book-summaries/engineering/fundamentals-of-data-engineering/07-ingestion/), непрерывный `CDC` превращает аналитическую базу в «быстрого последователя» production-базы. Запросы идут в аналитическую базу и отстают от production совсем немного. Почему не запускать их сразу в production? В принципе можно, но на практике production-база не рассчитана на тяжёлые аналитические scan в дополнение к рабочей нагрузке. Такой запрос может замедлить приложение или уронить его. Авторы знают случай: новый аналитик крупной сети магазинов запустил `SELECT *` на production-базе, и база инвентаря три дня не работала.

Последователем может быть обычная транзакционная база, но лучше OLAP-система. Druid и BigQuery сочетают streaming buffer с долгосрочным columnar storage, как в `lambda`-архитектуре (см. [главу 3](/book-summaries/engineering/fundamentals-of-data-engineering/03-designing-good-data-architecture/)). Это хорошо работает для статистики по большой истории с почти мгновенным обновлением. У подхода есть предел: вы всё ещё запускаете `SELECT` по текущему состоянию таблицы и не можете запускать действия по событиям потока.

**`Kappa`-архитектура.** Её идея в том, чтобы считать все данные событиями и хранить их как поток, а не как таблицу. Источником могут быть CDC, backend приложения или IoT-устройства. Streaming-хранилище здесь не просто buffer: оно держит события месяцами и даже годами, тогда как в чисто real-time системах retention обычно не больше недели. Запросы идут либо в само хранилище (Kafka KSQL умеет агрегаты, статистику и даже sessionization), либо через внешний инструмент. Например, Spark читает нужный период из Kafka и считает результат. Поток также могут читать stream processor, такой как Flink или Beam.

**Окна, триггеры, поздние данные.** Обычный batch-запрос смотрит на данные снаружи: его запускает cron или менеджер, открывший дашборд. В streaming-системах расчёт запускают сами данные. Система может выдавать среднее и медиану после каждых N записей в buffer или итог сессии, когда она закрылась. Для этого нужны окна (`windows`): маленькие batch, которые обрабатываются по динамическим триггерам.

![Типы окон в streaming: fixed, sliding, session и watermark](/assets/fundamentals-of-data-engineering/ch08-stream-windows.png)

Схема показывает три вида окон на оси времени и то, как watermark делит события на вовремя пришедшие и опоздавшие.

- **Session window** собирает события, которые идут близко друг к другу, и отсекает паузы: например, сессия закрывается после пяти минут тишины. Окна считаются отдельно по каждому ключу, то есть у каждого пользователя свои сессии. Окно можно оставить открытым для поздних событий. Динамическая sessionization меняет смысл результата: ретроспективная позволяет отправить купон через день после сессии, а динамическая даёт пользователю полезное уведомление по тому, что он делал последние 15 минут.
- **Fixed (tumbling) window** идёт строго по расписанию и обрабатывает всё, что накопилось с закрытия прошлого окна. Например, раз в 20 секунд считаем среднее и медиану. Это похоже на обычный batch ETL, только окна чаще и задержка меньше. Авторы повторяют: batch — частный случай streaming.
- **Sliding (hopping) window** состоит из окон фиксированной длины, но новые окна стартуют чаще, чем кончаются старые: например, окно в 60 секунд создаётся каждые 30 секунд. Статистику можно выдавать и только по триггеру, скажем, при клике на баннер. Тогда во время всплеска результатов много, а в затишье нет совсем.
- **Watermark** — порог, по которому окно решает, успели ли данные вовремя. Данные, пришедшие в окно, но старше watermark, считаются поздними (`late-arriving data`). Мы говорили о неупорядоченной доставке в главе 7.

**Как объединять потоки с другими данными.**

- *Обычный join таблиц.* Одна или обе таблицы питаются потоком, а соединяют их как всегда в базе.
- *Enrichment* — это join потока с другими данными, чаще всего чтобы получить обогащённый поток. Пример: интернет-магазин получает от партнёра события с ID товара и пользователя. Serverless-функция ищет их в кэше (in-memory база), дописывает данные о товаре и пользователе и отправляет в новый поток. Источником обогащения может быть таблица в warehouse, RDBMS или файл в object storage.
- *Stream-to-stream join.* Например, магазин хочет соединить веб-события с потоком от рекламной платформы. Задержки у потоков разные: реклама может приходить с пятиминутным опозданием, а событие закрытия сессии или данные из офлайн-приложения могут появиться ещё позже. Поэтому используют streaming buffer. События ждут пары в течение настраиваемого retention interval и после него вытесняются. Чем он дольше, тем больше памяти и других ресурсов нужно.

## Моделирование данных

Авторы пишут, что слишком часто видят команды, которые строят системы данных без плана. Хорошая архитектура должна отражать цели и бизнес-логику организации. Моделирование — это осознанный выбор связной структуры данных. Практике уже десятки лет: нормализация известна с ранних RDBMS, а методы для warehouse с начала 1990-х. В первой половине 2010-х моделирование вышло из моды. `Data lake` 1.0, NoSQL и big data позволили обходить моделирование. Иногда это давало выигрыш в скорости, а иногда порождало `data swamp` с дублями и неверными данными. Сейчас маятник качается назад: `data governance` и качество данных требуют понятной бизнес-логики.

### Что такое модель

Модель данных описывает, как данные связаны с реальным миром. Она должна отражать процессы, определения и логику вашей организации. Плохая модель, или её отсутствие, даёт хаос. Модель нужна, как гигиена зубов: все согласны, что полезно, но многие пропускают.

Главное — связать модель с бизнес-результатом. Пример: слово «клиент» значит разное для разных отделов. Клиент ли тот, кто купил за последние 30 дней? А если последняя покупка была полгода или год назад? От ответа зависят отчёты по поведению клиентов и модели оттока, где время с последней покупки — важный признак.

Обсуждение в основном про batch-моделирование: техники родились там. К streaming мы вернёмся в конце раздела.

### Концептуальная, логическая и физическая модели

Моделирование идёт от абстрактного к конкретному, и модели образуют три уровня:

| Уровень | Что описывает |
|---|---|
| Conceptual | Бизнес-сущности и правила: заказы, клиенты, товары. Удобно рисовать как ER-диаграмму |
| Logical | Реализация подробнее: типы полей, primary и foreign key |
| Physical | Реализация в конкретной базе: схемы, таблицы, настройки |

Авторы подчёркивают: к моделированию надо привлекать бизнес с самого начала. Инженеру нужны определения и цели данных. В моделировании постоянно участвуют все, а цель — дать бизнесу качественные данные для решений и автоматизации.

Ещё один важный вопрос — `grain` (зерно): уровень детализации, с которым данные хранятся и запрашиваются. Обычно grain совпадает с primary key таблицы (customer ID, order ID), часто плюс дата или время. Пример: маленькая компания начинает BI, а один человек совмещает роли инженера и аналитика. Просят отчёт: кто из клиентов делал заказы за день, сколько заказов и на какую сумму. Соблазн велик: взять из production-базы заказов только агрегаты. Но тогда на запрос с большей детализацией придётся начинать с нуля. Опытный инженер сразу сохраняет всё: каждый заказ, позицию, цену, ID товара. Grain тогда равен «заказ клиента», и данные можно как анализировать, так и агрегировать. Вывод: храните данные на самом мелком grain. Агрегировать легко, а восстановить стёртые детали невозможно.

На схеме показано, как выглядит путь от источников к отчётам в четырёх подходах из этого раздела. Мы вернёмся к ней после нормализации.

### Нормализация

`Normalization` — это практика, которая жёстко контролирует связи между таблицами и колонками. Цель: убрать избыточность данных и обеспечить referential integrity. Это принцип DRY (don't repeat yourself), применённый к данным. Её ввёл Эдгар Кодд, создатель реляционной модели. Он ставил цели: избавиться от аномалий вставки, обновления и удаления, не перестраивать схему при появлении новых типов данных и сделать её независимой от статистики запросов. Кодд описал нормальные формы. Они идут по порядку, и каждая включает условия предыдущих.

Сначала два термина. Unique primary key — это поле или набор полей, которые однозначно определяют строку. Все остальные значения строки зависят от ключа. Partial dependency возникает, когда неключевая колонка определяется частью составного ключа. Transitive dependency — когда неключевое поле зависит от другого неключевого.

| Форма | Требование |
|---|---|
| Denormalized | Ограничений нет: допустимы вложенные и повторяющиеся значения |
| 1NF | Каждая колонка содержит одно значение. Есть уникальный primary key |
| 2NF | Условия 1NF и нет partial dependency |
| 3NF | Условия 2NF и нет transitive dependency: в таблице только поля, связанные с её ключом |

Авторы показывают путь на примере заказов интернет-магазина. Сначала таблица `OrderDetail` с ключом `OrderID`, где поле `OrderItems` хранит вложенный объект: два SKU с ценой, количеством и названием. Для 1NF вложенный объект раскладывают на отдельные поля. Но тогда `OrderID = 100` встречается в двух строках, и ключ перестаёт быть уникальным. Поэтому добавляют номер строки в заказе, и составной ключ (`OrderID`, `LineItemNumber`) снова уникален.

Для 2NF нужно убрать partial dependency: поля заказа (клиент, дата) зависят только от `OrderID`, а не от всего составного ключа. Таблицу делят на `Orders` и `OrderLineItem`. Для 3NF ищут transitive dependency: `Sku` определяет `ProductName`, а `Sku` зависит от ключа строки. Название товара выносят в таблицу `Skus`. Теперь `OrderLineItem` и `Skus` в 3NF, а `Orders` ещё нет: в ней неключевые поля клиента тоже зависят друг от друга.

Бывают и более высокие формы, до 6NF в системе Бойса-Кодда, но они редки. Базу обычно считают нормализованной на 3NF. Степень нормализации зависит от задачи. Денормализация выглядит как антипаттерн, но в OLAP это норма, особенно для полуструктурированных данных.

В warehouse и lake сырые данные бывают любой формы, а на выходе нужна структурированная модель из строк и колонок. Подходов несколько, и их часто сочетают: многие команды сначала строят `Data Vault`, а рядом добавляют star schema Kimball. Inmon, Kimball и Data Vault авторы описывают коротко и советуют прочитать книги их авторов. В примерах везде моделируется система заказов.

### Inmon

Билл Инмон создал свой подход в 1990 году. До этого аналитику часто запускали прямо на системе-источнике, и долгие запросы тормозили production. Цель warehouse — разделить источник и аналитику. Инмон определяет warehouse как предметно-ориентированный, интегрированный, неизменяемый (nonvolatile) и привязанный ко времени (time-variant) набор данных для поддержки решений менеджмента. Эти четыре свойства значат следующее:

- *Предметная ориентация.* Warehouse фокусируется на одной области, скажем, продажах или маркетинге, и хранит всё про неё: бизнес-ключи, связи, атрибуты.
- *Интегрированность.* Это важнейшее свойство. Данные из разных источников преобразуются и приводятся к одному виду, так что в warehouse у них единый «физический образ».
- *Неизменяемость.* Записанные данные не меняются.
- *Привязка ко времени.* История хранится, и пока хватает места, можно запросить исходные данные.

Эти свойства делают warehouse системой для аналитики, а не OLTP. Данные из ключевых бизнес-систем через ETL попадают в сильно нормализованную (3NF) модель, часто похожую на структуру источника. Загрузка идёт постепенно, начиная с самых важных областей. Строгая нормализация минимизирует дублирование, поэтому в аналитике меньше ошибок от разошедшихся копий. Warehouse становится «единственным источником правды». Потребителям данные отдают через `data marts` отделов, которые уже могут быть денормализованы.

Пример с интернет-магазином: источники — заказы, склад и маркетинг. Они через ETL попадают в warehouse в 3NF. Затем ещё один ETL строит data marts для продаж, маркетинга и закупок. Часто в витрине используют star schema, но подойдёт любая понятная модель. Каждый отдел получает структуру под свои нужды.

### Kimball

Ральф Кимбалл создал подход в начале 1990-х. Он находится на другом конце спектра: меньше нормализации, а местами допускается денормализация. Инмон считал, что `data mart` никогда не заменяет warehouse. Кимбалл идёт снизу вверх: аналитику отделов строят и отдают прямо в warehouse. Итерации быстрее, но интеграция слабее, а данные могут дублироваться и повторяться (Инмон возражает, что такой подход искажает само понятие warehouse).

Данные хранятся в таблицах двух типов:

| Таблица | Что хранит | Форма и свойства |
|---|---|---|
| Fact | Числа, события, измерения | Узкая и длинная. Неизменяемая, только append. На самом мелком grain. Ссылается на dimensions, но не на другие факты |
| Dimension | Контекст события: что, где, когда, кто | Короткая и широкая. Денормализована, дубли допустимы |

Запросы к star schema начинаются с fact-таблицы. Не агрегируйте и не вычисляйте ничего внутри fact-таблицы: для этого есть downstream-запросы, `data mart` и view. Fact-таблица содержит только числа и ключи, без строк. Так, в таблице заказов может быть `OrderID`, `CustomerKey`, `DateKey` и `GrossSalesAmt`. Если у клиента 7 два заказа за день, это две строки: grain задан заказом.

Даты обычно вынесены в date dimension: по ключу `DateKey` можно легко спросить про первый квартал или сравнить вторники и среды. В такую таблицу можно добавлять сколько угодно полезных атрибутов. В customer dimension лежат имя, zip code и пара необычных дат: они нужны для `Slowly changing dimension` (SCD).

**SCD** хранит, как меняются атрибуты. Например, у клиента есть запись с `EFF_StartDate` (начало действия) и `EFF_EndDate = 9999-01-01`: запись активна. Если клиент переехал, старая запись получает реальную дату окончания, а рядом появляется новая. Типов бывает до семи, но главные три:

| Тип | Что делает |
|---|---|
| Type 1 | Заменяет старое значение новым. История теряется. Самый простой тип и поведение большинства warehouse по умолчанию |
| Type 2 | Вставляет новую запись при изменении, а старую закрывает датой. Хранит полную историю. Чаще всего встречается на практике |
| Type 3 | Добавляет новую колонку: старое значение в одной, новое в другой, плюс дата изменения |

**Star schema** — это fact-таблица, окружённая нужными dimensions. Она не повторяет конкретный отчёт (отчёт моделируют в `data mart` или в BI), а описывает факты и атрибуты бизнеса. В ней меньше join, чем в нормализованных моделях, поэтому запросы быстрее, а бизнесу она понятнее. Так как fact-таблица одна, для разных фактов бизнеса получаются разные star schemas. Dimensions стоит использовать повторно. Dimension, общий для нескольких star schemas, называется `conformed dimension`: он позволяет объединять факты из разных звёзд. Дубли в Kimball допустимы, но копировать одну и ту же dimension не стоит: определения разойдутся, а целостность пострадает. Авторы предупреждают: модель Kimball подходит только для batch, на streaming её нелегко перенести. И так как она очень популярна, вы с ней почти наверняка встретитесь.

### Data Vault

Если Kimball и Inmon описывают структуру бизнес-логики в warehouse, то `Data Vault` предлагает иное. Его создал Дэн Линстедт в 1990-х, авторы описывают версию 2.0. Модель отделяет структуру данных системы-источника от их атрибутов. Данные не раскладывают по фактам, dimensions или нормализованным таблицам, а просто грузят из источников в несколько специальных таблиц, и только на вставку (insert-only). Понятий «хорошие», «плохие» или conformed данные здесь нет. Цель — держать данные максимально близко к бизнесу, даже когда бизнес меняется. Логика применяется при чтении.

Таблиц три типа:

| Таблица | Что хранит |
|---|---|
| Hub | Бизнес-ключи (ID клиента или заказа), по которым пользователи ищут данные. Поля: hash key (MD5 или похожий), load date, record source и сам business key. Только insert, данные не меняются |
| Link | Связи между бизнес-ключами из разных hubs. Соединяет минимум два hub, на самом мелком grain, отношение many-to-many |
| Satellite | Описательные атрибуты и контекст hub или link. Обязателен ключ родителя и load date, остальное по желанию |

Чтобы спроектировать hub, нужно найти business key: как пользователи системы-источника обычно ищут данные? Лучше выяснить это ещё при построении conceptual-модели. В магазине можно завести `HubProduct`, `HubOrder` и `LinkOrderProduct`, а название и цену товара положить в `SatelliteProduct`. Пользователь обращается к hub, а тот через link и satellite приводит к нужным атрибутам.

Если связи в бизнесе меняются, это решается просто: добавляете новый hub и новую связь в link. Есть и другие таблицы: `PIT` (point in time) и bridge. Авторы их не разбирают. Часто `Data Vault` служит слоем загрузки (landing zone) для аналитических данных, а потом их моделируют отдельно, например, в star schema. Подходит он также для NoSQL и streaming.

### Wide table

Строгие подходы Kimball и Inmon родились, когда warehouse были дорогими, стояли на своих серверах (`on premises`) и были жёстко ограничены ресурсами, а compute и хранение были связаны. Теперь batch-моделирование стало мягче. Во-первых, облако сделало хранение дешёвым: проще хранить данные, чем мучительно искать оптимальную форму. Во-вторых, вложенные данные (JSON и подобные) сделали схемы гибкими.

Можно положить всё в одну wide table. Это очень широкая денормализованная таблица, обычно в columnar-базе, с тысячами колонок (в реляционных базах обычно меньше 100). Поле может содержать как простое значение, так и вложенные данные. Ключи таблицы связаны с её grain. Такие таблицы разрежены: большинство значений в колонке может быть null. Для обычной реляционной базы это дорого: она выделяет фиксированное место под каждое поле и читает строку целиком. Columnar-база читает только выбранные колонки, а null занимает почти ноль места. Wide table обычно появляются через `schema evolution`: поля добавляют постепенно. В реляционной базе это медленно и тяжело, а в columnar добавление поля сначала только правка метаданных.

Аналитические запросы к wide table часто быстрее, чем к нормализованным данным с множеством join: исчезают join и ускоряется scan. Факты и dimensions лежат в одной таблице. Не нужно много думать о модели: загружаете данные и запрашиваете. Критика есть: теряется бизнес-логика, а обновление элемента вложенного массива обходится дорого. Авторы советуют wide table, когда моделировать не хочется или данных очень много и нужна гибкость. Она хорошо подходит для streaming. Они ожидают волну новых подходов, возможно, «ослабленной нормализации» (`relaxed normalization`).

### Не моделировать вообще

Можно просто запрашивать источники напрямую. Это часто делают в начале, чтобы быстро получить ответы. Но нужно задать себе вопросы:

- Как узнать, что результаты согласованы, если данные не смоделированы?
- Правильны ли определения бизнес-логики в источнике и даст ли запрос верный ответ?
- Какую нагрузку вы создаёте на системы-источники и как это влияет на их пользователей?

Рано или поздно придётся перейти к строгой batch-модели и отдельной архитектуре, где источники не делают всю тяжёлую работу.

### Моделирование streaming-данных

Для batch подходов много, для streaming их нет. Поток бесконечен и непрерывен, поэтому перенести Kimball туда сложно, если вообще возможно. Как, например, непрерывно вести SCD Type 2, не положив warehouse? Единого подхода нет. Эксперты по streaming в основном говорят, что batch-моделирование к потоку не применимо. Некоторые предлагают для потока `Data Vault`.

Проблема в том, что схема payload может измениться без предупреждения. Пример: IoT-устройство обновило прошивку и добавило поле, а warehouse или pipeline об этом не знает и ломается. Или CDC неожиданно меняет тип поля: вместо ISO datetime приходит строка. Эксперты почти единодушно советуют ждать изменений и держать гибкую схему, то есть без жёсткой модели в аналитической базе. Нужно считать, что источник отдаёт верные данные с правильными определениями. Так как хранение дёшево, храните недавние streaming-данные и историю так, чтобы запрашивать их вместе. И вместо реакции на отчёты стройте автоматику, которая реагирует на аномалии в потоке.

Авторы ждут смены парадигмы. Вероятно, в новых подходах объединятся metrics и `semantic layer`, pipeline и обычная аналитика в streaming-слое прямо над источником. Когда данные рождаются в реальном времени, разделение на источник и аналитику теряет смысл. Подробнее в [главе 11](/book-summaries/engineering/fundamentals-of-data-engineering/11-future-of-data-engineering/).

## Трансформации

Результат трансформации — это возможность объединить данные и увидеть их как единое целое. Без трансформаций нельзя получить единый взгляд на данные всей организации. Но зачем трансформации, если можно смоделировать данные и запросить их? Затем, что трансформация обрабатывает, улучшает и сохраняет данные масштабируемо, надёжно и недорого. Представьте запрос, который парсит, чистит, соединяет и агрегирует 20 наборов данных. Он выполняется 30 минут и повторяется сотни раз в день. Вы платите облаку за каждый запуск. Разумнее сохранить результат или хотя бы самые тяжёлые части.

Трансформация отличается от запроса двумя вещами:

- *Сохранение.* Запрос только достаёт данные по условиям фильтрации и join. Трансформация сохраняет результат, чтобы им пользовались другие трансформации и запросы. Сохранение может быть временным или постоянным.
- *Сложность.* Вы строите pipeline, которые объединяют много источников и повторно используют промежуточные результаты. Такой поток можно собрать и в одном запросе через CTE, скрипты или DAG, но это быстро становится запутанным и непоследовательным.

Трансформации опираются на `orchestration`: она связывает отдельные операции, которые сохраняют данные временно или навсегда для следующих шагов или для выдачи. Всё чаще pipeline трансформаций охватывают не только несколько таблиц, но и несколько систем.

### Batch-трансформации

Batch-трансформации работают с дискретными порциями данных, по расписанию: раз в день, час или 15 минут. Они кормят отчёты, аналитику и ML-модели.

**Распределённые join.** Логический join из запроса разбивается на много малых join на узлах кластера. Это одинаково для MapReduce, BigQuery, Snowflake и Spark, различаются лишь детали промежуточного хранения (диск или память).

![Broadcast join и shuffle hash join: как данные попадают на узлы](/assets/fundamentals-of-data-engineering/ch08-joins.png)

| Тип | Когда используют | Как работает | Цена |
|---|---|---|---|
| Broadcast join | Одна таблица (A) мала и помещается на узел | Движок «рассылает» A на все узлы, где она соединяется с частями большой таблицы B | Дёшево |
| Shuffle hash join | Обе таблицы большие | Хеш join-ключа перераспределяет строки обеих таблиц по узлам. Затем на каждом узле соединяют свои части | Дорого: много сети, диска и памяти |

Одна из главных задач optimizer — менять порядок join. Если рано применить фильтры и поставить маленькие таблицы слева (для left join), данных в каждом join станет намного меньше. Фильтруйте заранее: так часто получается broadcast join вместо shuffle.

**ETL и ELT.** Классический batch ETL — внешняя система забирает, преобразует и чистит данные под целевую схему (`data mart` или star schema Kimball), а потом грузит в warehouse. ETL возник из ограничений: extract упирался в возможности источника (RDBMS), а warehouse был слишком скромным по месту и CPU, чтобы преобразовывать данные у себя. `ELT` — эволюция: warehouse стали мощнее, поэтому сырые данные грузят почти без преобразований, а чистят и меняют внутри. Есть и вторая версия ELT, из мира `data lake`: данные грузят без подготовки и плана, а трансформацию откладывают на неопределённое будущее. Загрузка данных без плана — рецепт для `data swamp`. Инмон говорит, что видел слишком много случаев «загрузим сейчас, преобразуем потом», и через шесть месяцев до этих данных никто не дотрагивался.

В `lakehouse` граница размыта: с object storage в основе уже неясно, что внутри базы, а что снаружи. Federation, virtualization и live tables усиливают неясность. Авторы считают, что термины ETL и ELT нужно применять на микроуровне, к отдельным pipeline, а не ко всей организации. Организации не обязаны выбирать один подход: достаточно применять нужный в каждом конкретном случае.

**SQL или код.** Различие между SQL и не-SQL системами уже искусственное. Со времён Hive SQL стал полноправным участником big data: у Spark есть Spark SQL, а Kafka, Flink и Beam тоже поддерживают SQL. Правильнее делить инструменты на «только SQL» и «с универсальным языком программирования». Говорят, что SQL «не процедурный». Это верно: он декларативный, то есть вы описываете, какими должны быть данные, а компилятор и optimizer решают, как это сделать. Но из этого не следует, что на нём нельзя строить сложные pipeline: подойдут CTE, SQL-скрипты и оркестрация. У SQL есть пределы, но авторы часто видят, как в Python и Spark делают то, что проще и эффективнее решить в SQL.

Когда в Spark писать нативный код или PySpark вместо Spark SQL? Задайте три вопроса:

1. Насколько сложно записать это в SQL? Если легко, пишите на SQL. Если трансформация невыразима или очень неудобна, нужен нативный Spark. Например, word stemming на SQL получится очень громоздким, с множеством особых случаев.
2. Насколько читаемым и поддерживаемым будет SQL-код? Для stemming он будет нечитаемым.
3. Нужно ли вынести часть кода в библиотеку для повторного использования? В SQL нет естественного понятия библиотеки. Исключение — UDF как объекты в базе, но без внешнего CI/CD они не попадают в Git.

Но и SQL можно использовать повторно. Результат запроса сохраняют в таблицу или view, лучше через оркестратор вроде `Airflow`, чтобы следующие запросы стартовали после предыдущего. А dbt помогает переиспользовать SQL и даёт язык шаблонов.

Сторонники Spark жалуются, что SQL не даёт контроля над обработкой. Но в Spark оптимизация ложится на автора кода, а API мощный и сложный, поэтому командам нужны экспертиза и обучение. Советы для нативного Spark:

- Фильтруйте данные как можно раньше: в SQL optimizer часто переставит фильтры сам, а Spark может этого не сделать.
- Опирайтесь на core API Spark и поддерживаемые библиотеки. Если пишете очень сложный свой код, поищите нативный способ.
- Осторожно с UDF. PySpark — обёртка над Scala Spark: вызовы API выполняются в JVM, а Python UDF заставляет передавать данные в Python, где обработка менее эффективна. Если UDF неизбежна, перепишите её на Scala или Java.
- Смешивайте нативный код со Spark SQL. SQL использует Catalyst optimizer, который может выжать больше скорости, и проще для простых операций.

Эти советы подходят и Beam: программируемые API требуют больше внимания к оптимизации, чем SQL.

### Update patterns

Трансформации сохраняют данные, поэтому часто обновляют их на месте. Обновление — частая проблема команд, особенно при смене технологий. Исходная концепция `data lake` не учитывала обновлений, и теперь это выглядит абсурдно: перезапускать большую работу только из-за отсутствия update глупо. В `lakehouse` обновления заложены. К тому же GDPR и подобные правила требуют удалять данные точечно.

![Шаблоны обновления данных: truncate, insert only и upsert/merge](/assets/fundamentals-of-data-engineering/ch08-update-patterns.png)

| Шаблон | Суть и подводные камни |
|---|---|
| Truncate and reload | Таблицу очищают и перезаписывают результатами заново. Ничего не «обновляет», просто стирает старое |
| Insert only | Вставляются новые записи, старые не меняются и не удаляются. Текущее состояние даёт запрос или view: берёт самую новую запись по primary key. Columnar-базы обычно не проверяют primary key, его ведёт инженер. Поиск последней записи на лету может быть очень дорогим, поэтому делают materialized view или комбинацию: insert-only таблица со всеми записями плюс truncate-and-reload таблица с текущим состоянием |
| Delete | Hard delete стирает запись навсегда: так делают из-за размера или требований закона. Soft delete помечает запись удалённой и скрывает её. Insert deletion вставляет новую версию записи с флагом удаления: остаётся insert-only, но запрос текущего состояния усложняется, ведь нужно найти последнюю версию по ключу и скрыть удалённые |
| Upsert / merge | Берёт записи источника и ищет совпадения в целевой таблице по ключу или другому условию. Если нашёл, заменяет запись. Если нет, вставляет. Merge ещё и удаляет |

Типичная ошибка для columnar: вставлять по одной строке, как в row-oriented базах. Это сильно грузит систему, данные записываются множеством мелких файлов, и последующие чтения неэффективны, а позже данные приходится переупаковывать. Загружайте batch или micro-batch. Исключение — enhanced `lambda`-архитектура в BigQuery и Druid, которая сочетает streaming buffer с columnar-хранилищем. Удаления и обновления на месте остаются дорогими: в columnar-системах и data lake delete дороже insert.

Самые проблемные шаблоны — upsert и merge, особенно для команд, переходящих с row-based warehouse на columnar. Причина в том, что merge придумали для row-based баз, где запись находят и меняют на месте. Файловые системы так не умеют и используют `copy on write` (COW): если в файле меняют или удаляют одну запись, весь файл переписывают. Поэтому первые адепты big data и data lake вообще отказались от updates: проще было вставлять и находить актуальное при чтении. Но columnar-базы вроде Vertica давно поддерживают update на месте, скрывая COW от пользователя: сканируют файлы, меняют записи, пишут новые файлы и переключают указатели таблицы. Все крупные columnar-warehouse в облаке поддерживают update и merge, но если вы берёте экзотическую технологию, проверьте это.

Что здесь важно понимать:

- Merge стоит дорого, когда меняете одну запись. Зато для больших наборов он может быть очень быстрым и даже обгонять отдельные insert.
- COW редко переписывает всю таблицу. Зависит от системы: переписывается партиция, кластер или блок. Для быстрых обновлений нужна подходящая стратегия партиций и clustering.
- Следите за частотой update и merge. Авторы видели много команд, которые при смене базы пытались запускать near real-time merge из CDC, как раньше. Это не работает: большинство columnar-warehouse не выдерживает такой нагрузки. Системы отставали от источника на недели, хотя более простой подход справился бы быстро. Лучше делайте merge, скажем, раз в час.
- Приблизить columnar к real time помогают особые механизмы. BigQuery позволяет stream insert и особые materialized views с дедуплицированным представлением. Druid использует двухуровневое хранение на SSD.

### Schema updates

Данные подвержены энтропии: внешние источники меняют схему, команды приложений добавляют поля. У columnar-систем есть плюс: обновлять данные сложнее, чем схему, а колонки добавлять легко. Но организационное управление схемой труднее. Нужно решить несколько вопросов:

- Будут ли какие-то обновления схемы автоматическими? Так делает Fivetran при репликации. Это удобно, но downstream-трансформации могут сломаться.
- Есть ли простой процесс запроса на изменение схемы? Что если data science команда просит добавить колонку, которую раньше не загружали? Как проходит review? Сломает ли это нижестоящие процессы? Нет ли запросов с `SELECT *`: в columnar это плохая практика. Сколько займёт внедрение? Можно ли сделать table fork, то есть версию таблицы для одного проекта?

Для полуструктурированных данных есть интересный вариант. По примеру document stores многие облачные warehouse поддерживают тип для произвольного JSON. Можно хранить сырой JSON в одном поле, а часто нужные данные раскладывать в соседние плоские поля. Это занимает больше места, но даёт удобство плоских данных и гибкость полуструктурированных. Часто используемые элементы JSON со временем можно перенести прямо в схему. Особенно хорошо это работает, когда нужно загружать данные из document store приложения с часто меняющейся схемой.

### Data wrangling

`Data wrangling` превращает грязные, поломанные данные в чистые. Это обычно batch-процесс и давняя проблема ETL-разработчиков. Пример: партнёр присылает данные EDI (см. главу 7) о транзакциях и счетах, смесь структурированных данных и текста. Сначала их пытаются загрузить. Часто они так испорчены, что нужна предобработка текста: например, загрузить всю строку как одно текстовое поле, а потом писать запросы, которые разбирают её. Постепенно находят аномалии и особые случаи, и данные приводят в приличный вид. Только после этого начинается обычная трансформация.

Инструменты для wrangling упрощают процесс. Инженеров они часто отталкивают словами «no code», но авторы предлагают видеть в них IDE для плохих данных. Такой инструмент показывает выборку, выведенные типы, распределения, аномалии и null. Пользователь добавляет шаги обработки, например, исправить тип или разделить поле. Готовый рецепт запускают на всём наборе, а большие наборы уходят в Spark. Авторы советуют попробовать такие инструменты всем: часть разбора данных можно передать аналитикам.

### Пример: типичная batch-трансформация

Пример: pipeline берёт данные из трёх API в формате JSON. Приём идёт в `Airflow`, потом Airflow запускает Spark job. Spark читает источники в dataframes, объединяет их в одну таблицу, фильтрует SQL-запросом и пишет результат в таблицу Delta Lake (Parquet) в S3.

Spark строит DAG шагов по коду. Часть данных не помещается в память и уходит на диск (spill). Join требует shuffle по ключу, и там тоже возможен spill. Airflow периодически спрашивает Spark, закончилась ли работа, и помечает свой DAG выполненным. Здесь два вида DAG: в Airflow и в Spark.

### Бизнес-логика и derived data

Один из самых частых случаев трансформации — применение бизнес-логики. Пример: в компании есть два расчёта прибыли, до и после маркетинговых расходов. Это кажется простой бухгалтерией, но каждый сложен. До маркетинга нужно учесть фродовые заказы: чтобы оценить прибыль за вчера, надо прикинуть, какую долю выручки потеряют из-за отмен. Есть ли в базе флаг фрода или бизнес берёт фиксированный процент? После маркетинга добавляется атрибуция расходов: по цене товара, по отделу или, в самых продвинутых компаниях, по кликам на рекламу. Где лежит модель атрибуции: в недрах ETL-скриптов или в таблице из данных рекламных платформ?

Такие данные называют `derived data`: они вычислены из других данных системы. Критики говорят, что ETL трудно поддерживать согласованным: поменяли модель атрибуции, и изменение надо вносить во множество скриптов (ETL-скрипты славятся нарушением DRY). Авторы считают критику справедливой, но не конструктивной: альтернатива не лучше. Без прибыли в warehouse аналитики считают её в своих отчётах, и логика расползается по запросам. Интересный выход — `metrics layer`: бизнес-логика кодируется отдельно, а тяжёлую работу делает warehouse. Аналитики собирают сложную аналитику из библиотеки метрик, а слой сам порождает запросы. Подробнее о semantic и metrics layer в [главе 9](/book-summaries/engineering/fundamentals-of-data-engineering/09-serving-data/).

### MapReduce

Без MapReduce разговор о batch-трансформациях неполон. Не потому, что им сегодня пользуются широко, а потому что он определил batch-обработку эпохи big data, всё ещё влияет на распределённые системы и полезен для понимания. Google описала его в статье после работы про GFS, а Hadoop стал открытым аналогом.

Простая MapReduce-работа состоит из map-задач, которые читают блоки данных на узлах, затем shuffle перераспределяет результаты по кластеру, а reduce агрегирует их. Пример: запрос считает записи по ID пользователя. На каждый блок создаётся map-задача, и она считает ID в своём блоке. Блок занимает сотни мегабайт, вся таблица — петабайты, но map почти идеально параллелится: скорость чтения растёт линейно с числом узлов. Затем shuffle (обычно по хешу ключа) отправляет каждый ключ ровно на один узел, и там результаты суммируются. Реальные задачи сложнее: запрос с WHERE, тремя join и оконной функцией превращается в много шагов map и reduce.

Модель Google мощная, но теперь считается слишком жёсткой. Она использует много коротких задач, которые читают с диска и пишут на диск, и не хранит промежуточное состояние в памяти. Это упрощает управление состоянием, но нагружает диск и замедляет обработку. Расчёт был на то, что диски настолько дёшевы, что для быстрых запросов можно просто выделить огромный объём дисков. Так и было в первые годы Hadoop.

Но мы давно живём в мире после MapReduce. Он не выброшен: элементы map, shuffle и reduce остались, но ограничения ослаблены ради кэширования в памяти. RAM быстрее SSD и HDD, и даже небольшой объём данных в памяти сильно ускоряет обработку. Spark и BigQuery строятся вокруг памяти: при нехватке данные уходят на диск (spill), и диск считается вторичным слоем. Облако помогает: арендовать память на время задачи выгоднее, чем держать её круглосуточно.

### Views, materialized views, federation и virtualization

Это техники, которые подают результат запроса как таблицу. Их можно включить в pipeline трансформаций или поставить прямо перед потребителем.

- **View** — объект базы, из которого можно делать select, как из таблицы. На деле это запрос к другим таблицам: база встраивает его в ваш запрос, и optimizer оптимизирует всё вместе. Views нужны для безопасности (только нужные колонки и строки), для текущей дедуплицированной картины insert-only таблицы и для частых шаблонов доступа, например, соединения пяти таблиц в одну широкую. У обычного view нет предварительных вычислений, поэтому такой join выполняется при каждом запросе.
- **Materialized view** считает часть или всю работу заранее. В примере он может сохранять результат join пяти таблиц при каждом изменении источников, и пользователь читает уже соединённые данные. Это де-факто шаг трансформации, хотя им управляет база. Во многих базах materialized view ещё и ускоряет запросы, которые на него не ссылаются: optimizer замечает запрос, «похожий» на view, и переписывает его на предрассчитанные данные. Обычно materialized view нельзя строить поверх другого materialized view. Но появляются инструменты, которые это позволяют. Например, Databricks представил live tables: каждая таблица обновляется при поступлении данных, и изменения асинхронно текут вниз к следующим.
- **Federated query** позволяет OLAP-базе делать select из внешнего источника: object storage, MySQL, PostgreSQL. Snowflake поддерживает external tables на S3: данные не загружаются, при запросе Snowflake читает S3, и их можно соединять с внутренними таблицами. Так Snowflake лучше вписывается в среду `data lake`. Некоторые OLAP-системы превращают federated query в materialized view: скорость близка к родной таблице, а вручную грузить данные не нужно.
- **Data virtualization** — это система обработки и запросов, которая сама ничего не хранит. Лучшие примеры сейчас Trino (например, Starburst) и Presto. Любой движок с external tables может стать движком virtualization. Главное: какие внешние источники поддерживаются и как работает производительность. Близкое понятие — `query pushdown`: перенос как можно большей части работы в базы-источники, например, передача условий фильтрации в запросы к источникам. Это снимает вычисления с уровня virtualization и уменьшает данные, идущие по сети, а сеть — главное узкое место virtualization.

Virtualization полезна, когда данные лежат в разных источниках, но использовать её надо с умом. Virtualization production-базы MySQL не решает главную проблему: Trino ничего не хранит и обращается к MySQL при каждом запросе, так что аналитика по-прежнему мешает production. Лучше сделать её частью pipeline: Trino раз в сутки ночью читает MySQL и сохраняет результат в S3. Virtualization расширяет `data lake` на много источников и хорошо сочетается с `data mesh` (см. главу 3): команды готовят данные и делятся ими, а virtualization служит слоем доступа.

## Streaming-трансформации и обработка

Разница между streaming-запросами и streaming-трансформациями тонкая. Streaming-запрос динамически показывает текущее состояние данных. Streaming-трансформация готовит данные для потребителя. Пример: поток событий от IoT, в каждом событии ID устройства и данные. Их нужно обогатить метаданными устройства из отдельной базы. Stream processor по ID запрашивает базу, создаёт новые события с добавленными данными и передаёт в другой поток. На этом обогащённом потоке работают live-запросы и метрики по триггерам.

Граница между трансформацией и запросом размыта и в batch, а в streaming тем более. Если мы динамически считаем статистику по окнам и отправляем результат в другой поток, это трансформация или запрос? Возможно, для streaming когда-нибудь придумают новые термины. Пока приходится использовать существующие.

**Streaming DAG.** Мы говорили об оркестрации в [главе 2](/book-summaries/engineering/fundamentals-of-data-engineering/02-data-engineering-lifecycle/), и она по сути batch-понятие. Но что, если нужно в реальном времени обогащать, объединять и разделять потоки? Пример: объединить clickstream сайта с IoT-данными, чтобы получить единую картину действий пользователя, и каждый поток сначала привести к стандартному формату. Раньше для этого соединяли streaming-хранилище (Kafka) и stream processor (Flink), и DAG превращался в громоздкую конструкцию из множества topic и шагов обработки. Pulsar сильно упрощает задачу: DAG здесь базовая абстракция, и инженеры описывают streaming DAG кодом в одной системе вместо управления потоками между несколькими.

**Micro-batch и true streaming.** Давний спор: micro-batch против true streaming. Нужно понимать задачу, требования и возможности технологии. Micro-batch применяет batch-фреймворк к потоку: пачки запускаются от каждых двух минут до каждой секунды. Некоторые фреймворки, например Spark Streaming, созданы для этого и хорошо работают при правильных ресурсах и высокой частоте. (DBA давно использовали micro-batch с обычными базами, и это нередко кончалось ужасной производительностью.) True streaming (Beam, Flink) обрабатывает по одному событию, но с большими накладными расходами. К тому же и в true streaming многое остаётся пакетным. Простое обогащение идёт по одному событию с малой задержкой, а метрика по окнам считается раз в несколько секунд или минут.

Выбор зависит от частоты окон и допустимой задержки. Метрики Black Friday раз в несколько минут подойдут micro-batch. А если ops-команда считает метрики каждую секунду, чтобы обнаружить DDoS, нужен true streaming. Универсального ответа нет. Слово micro-batch часто использовали, чтобы отмахнуться от конкурентов, но оно может прекрасно подойти, особенно если команда знает Spark. Нет замены экспертизе и реальным тестам: проверьте варианты в облаке. Остерегайтесь вендорских benchmark (см. [главу 4](/book-summaries/engineering/fundamentals-of-data-engineering/04-choosing-technologies/)): их примеры подобраны удобно, и преимущество часто не воспроизводится на ваших данных.

## С кем вы работаете

Запросы, трансформации и моделирование касаются всех участников цикла. Технически дата-инженер проектирует, строит и поддерживает системы, которые запрашивают и преобразуют данные, а также реализует в них модели данных. Цель — как можно больше ценности: рабочие системы и надёжные, заслуживающие доверия данные.

| Кто | Что важно |
|---|---|
| Upstream: те, кто задаёт бизнес-определения | Нужно знать источники: что это, как используются, какие определения заложены. Работать с инженерами систем-источников и бизнес-владельцами продуктов. Участвовать в проектировании модели данных и её обновлений при смене логики. Трансформацию сделать легко (запрос и результат в таблицу), а сделать её быстрой и полезной бизнесу сложно |
| Upstream: те, кто владеет системами | Хотят, чтобы ваши запросы минимально влияли на их системы. Нужна двусторонняя связь об изменениях моделей (колонки, индексы), а вам нужно узнавать об изменениях схемы: новые и удалённые поля, смена типов |
| Downstream: аналитики, data scientists, ML-инженеры, бизнес | Модель и трансформации должны быть быстрыми (запросы выполняются быстро и дёшево) и полезными: данные высокого качества и полноты, готовые для их workflow и data products. Бизнес должен доверять, что преобразованные данные точны и пригодны для действий |

## Undercurrents

На стадии трансформации данные меняют форму, поэтому undercurrents здесь особенно важны.

| Undercurrent | Что делать |
|---|---|
| Security | Новые наборы данных нужно защищать: решите, кто к ним имеет доступ, вплоть до колонок, строк и ячеек, и строго контролируйте права чтения и записи. Не вставляйте пароли и токены в код: пароли базы в репозиториях GitHub встречаются пугающе часто. Не передавайте незащищённые данные по публичному интернету |
| Управление данными (data management) | Трансформации порождают новые наборы данных, которыми надо управлять. Согласуйте со всеми модели, ожидания и понятные бизнесу имена полей, а в каталоге данных пусть будут описание, дата создания и владелец. Растёт популярность `semantic layer` и metrics layer отдельно от трансформаций. Если возможен `MDM`, внедряйте его: `conformed dimension` на него опираются. Нужен `lineage`: он показывает, как получен набор. Учтите регуляторику: маскируйте чувствительные поля и умейте удалять данные по запросу вместе с производными |
| DataOps | Две области: данные и системы. Для данных запускайте тесты качества на входе и выходе трансформации (схема, min/max, число null). При проблеме пометьте её и откатите результат. Для систем следите за очередью запросов, concurrency, памятью, диском и сетью: метрики покажут, что настраивать, запрос или базу. SaaS-базы с оплатой по потреблению сместили задачу от выжимания максимума из купленной системы к управлению расходами: это `FinOps` (см. главу 4) |
| Data architecture | Не используйте RDBMS или Elasticsearch как warehouse: они не рассчитаны на тяжёлые агрегирующие OLAP-запросы и «взорвутся». Выбор приёма и хранения напрямую влияет на запросы и трансформации. Понимайте компромиссы своей архитектуры |
| Orchestration | Простое расписание (cron) сначала работает, но по мере усложнения workflow превращается в кошмар. Используйте оркестрацию с зависимостями между задачами |
| Software engineering | Знайте особенности языка и платформы. Не используйте UDF там, где есть встроенная функция: авторы видели, как замена медленных UDF одной встроенной командой дала мгновенный выигрыш. Analytics engineering (dbt, «analytics as code») приносит практики разработки аналитикам, а дата-инженер всё чаще настраивает репозиторий и CI/CD. Low-code инструменты генерируют SQL: понимайте его для отладки и не считайте автоматически эффективным. Не заменяйте чистый и быстрый код дополнительными ресурсами |

## Итоги главы

- Query проходит четыре шага: compile, bytecode, optimizer, выполнение. План запроса читается через `EXPLAIN`.
- Запросы ускоряют pre-join, CTE, pruning, vacuum и кэш. Плохие join с повторами дают `row explosion`.
- Нужно знать, как база фиксирует изменения: PostgreSQL блокирует строки, BigQuery читает snapshot, MongoDB может молча терять записи.
- Streaming-запросы запускают сами данные. Для них нужны окна (fixed, sliding, session) и watermark для поздних данных.
- Модель данных связывает данные с бизнесом. Храните данные на самом мелком grain: агрегировать легко, восстановить детали нельзя.
- Inmon строит единый warehouse в 3NF и `data marts` над ним. Kimball строит star schema из fact и dimensions. `Data Vault` грузит данные в hub, link и satellite. Wide table отказывается от строгой модели.
- Для streaming единой модели нет. Эксперты советуют гибкую схему и ожидают новые подходы с metrics и `semantic layer`.
- Трансформация, в отличие от запроса, сохраняет результат и опирается на `orchestration`.
- Broadcast join дёшев, shuffle hash join дорог. Фильтруйте данные заранее.
- В columnar не вставляйте строки по одной и не делайте частый merge: COW и мелкие файлы сильно снижают скорость.
- Бизнес-логику лучше держать в одном месте, например, в metrics layer, а не в десятках ETL-скриптов.
- Micro-batch подходит для метрик раз в минуты. True streaming нужен, когда важна секунда.

## Ключевые термины

| Термин | Значение |
|---|---|
| `Query optimizer` | Часть базы, которая выбирает самый дешёвый план запроса |
| `Explain plan` | План выполнения запроса: шаги, объекты и затраты |
| `Row explosion` | Резкий рост числа строк из-за повторов в ключах join |
| `Pruning` | Чтение только нужных колонок и партиций |
| `Vacuum` | Удаление старых версий записей |
| Window | Окно событий в streaming: fixed, sliding или session |
| Watermark | Порог времени, после которого событие считается поздним |
| `Grain` | Уровень детализации строки таблицы |
| `Normalization` | Устранение дублирования данных через нормальные формы |
| Fact / dimension | Событие с числами и контекст к нему в модели Kimball |
| `SCD` | Slowly changing dimension: способ хранить историю атрибутов |
| `Data Vault` | Модель из hub, link и satellite |
| Broadcast / shuffle hash join | Два способа распределённого join |
| Upsert / merge | Обновить по ключу или вставить, а при merge ещё и удалить |
| `Copy on write` | Изменение файла через его полную перезапись |
| Materialized view | View с заранее посчитанным результатом |
| Data virtualization | Запросы к внешним источникам без собственного хранилища |
| `Metrics layer` | Слой, где в одном месте определены бизнес-метрики |

## Что это значит на практике

- Читайте `EXPLAIN` до оптимизации. Сначала уберите лишний scan и повторные join.
- Храните факты на самом мелком grain. Агрегаты делайте в `data marts`.
- Выберите модель под задачу. Для отчётов подходит star schema, для гибкой загрузки `Data Vault`, для больших вложенных данных wide table.
- В columnar-базе не делайте построчные insert и частые merge. Загружайте данные batch-ами, а merge делайте, скажем, раз в час.
- Определения метрик держите в одном месте: metrics layer или dbt. Не копируйте логику по ETL-скриптам.
- Ставьте тесты качества на входе и выходе трансформации. Следите за стоимостью запросов.
- Не нагружайте production-базу аналитикой. Используйте `CDC` и отдельную OLAP-базу.
- Проверьте, как ваша база фиксирует изменения и чистит старые версии. Это влияет на результат запросов и на счёт за хранение.
- Не фильтруйте поздно: ставьте фильтры до join, чтобы получить broadcast join.
- Вместо `SELECT *` перечисляйте колонки. Тогда новые колонки в источнике не ломают downstream.

## Практика в DuckDB

Запустите `duckdb` в терминале или откройте [shell.duckdb.org](https://shell.duckdb.org). Блоки идут по порядку и работают в одной сессии. Мы пересоздаём идеи главы на маленьких данных: SCD Type 2, insert-only с merge и окна.

### Шаг 1. Создаём таблицы

`dim_customer` хранит историю клиента (SCD Type 2): у Бориса две записи, потому что он сменил zip code. `fact_orders` хранит заказы на самом мелком grain.

```sql
CREATE TABLE dim_customer AS
SELECT * FROM (VALUES
  (1, 5, 'Анна',  '10001', DATE '2019-01-04', DATE '9999-01-01'),
  (2, 7, 'Борис', '84101', DATE '2020-05-04', DATE '2021-09-18'),
  (3, 7, 'Борис', '90210', DATE '2021-09-19', DATE '9999-01-01')
) AS t(customer_key, customer_id, name, zip, eff_start, eff_end);

CREATE TABLE fact_orders AS
SELECT * FROM (VALUES
  (100, 5, DATE '2022-03-01', 100.00),
  (101, 7, DATE '2022-03-01',  75.00),
  (102, 7, DATE '2022-03-01',  25.00),
  (103, 7, DATE '2021-06-10',  40.00),
  (104, 5, DATE '2022-03-02',  60.00)
) AS t(order_id, customer_id, order_date, gross_sales);
```

### Шаг 2. Проверяем

Должно быть 5 заказов на 300. Второй запрос обязан вернуть 0 строк: у клиента не бывает двух текущих записей.

```sql
SELECT count(*) AS orders, sum(gross_sales) AS total FROM fact_orders;

SELECT customer_id, count(*) AS current_rows
FROM dim_customer
WHERE eff_end = DATE '9999-01-01'
GROUP BY customer_id
HAVING count(*) > 1;
```

```text
┌────────┬────────┐
│ orders │ total  │
├────────┼────────┤
│ 5      │ 300.00 │
└────────┴────────┘
```

### Задания

**Задание 1.** Посчитайте продажи по zip code так, как он выглядел на момент заказа.

<details><summary>Решение</summary>

```sql
SELECT d.zip, count(*) AS orders, sum(f.gross_sales) AS sales
FROM fact_orders f
JOIN dim_customer d
  ON d.customer_id = f.customer_id
 AND f.order_date BETWEEN d.eff_start AND d.eff_end
GROUP BY d.zip
ORDER BY d.zip;
```

```text
┌───────┬────────┬────────┐
│  zip  │ orders │ sales  │
├───────┼────────┼────────┤
│ 10001 │ 2      │ 160.00 │
│ 84101 │ 1      │ 40.00  │
│ 90210 │ 2      │ 100.00 │
└───────┴────────┴────────┘
```

Старый заказ 103 попал в `84101`, потому что на его дату действовала старая запись. Без SCD Type 2 он оказался бы в `90210`.

**Задание 2.** Сделайте insert-only журнал заказов с флагом удаления и получите текущее состояние. Затем обновите таблицу `orders_now` командой `MERGE`.

<details><summary>Решение</summary>

```sql
CREATE TABLE orders_log AS
SELECT * FROM (VALUES
  (100, 'new',     TIMESTAMP '2022-03-01 10:00:00', false),
  (100, 'paid',    TIMESTAMP '2022-03-01 10:05:00', false),
  (101, 'new',     TIMESTAMP '2022-03-01 11:00:00', false),
  (101, 'deleted', TIMESTAMP '2022-03-01 12:00:00', true),
  (102, 'new',     TIMESTAMP '2022-03-01 13:00:00', false)
) AS t(order_id, status, updated_at, is_deleted);

SELECT order_id, status
FROM orders_log
QUALIFY row_number() OVER (PARTITION BY order_id ORDER BY updated_at DESC) = 1
   AND NOT is_deleted
ORDER BY order_id;

CREATE TABLE orders_now (order_id INTEGER PRIMARY KEY, status VARCHAR);
INSERT INTO orders_now VALUES (100, 'new'), (102, 'new');

MERGE INTO orders_now AS t
USING (SELECT * FROM (VALUES (100, 'paid'), (103, 'new')) AS s(order_id, status)) AS s
ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET status = s.status
WHEN NOT MATCHED THEN INSERT VALUES (s.order_id, s.status);

SELECT * FROM orders_now ORDER BY order_id;
```

```text
┌──────────┬────────┐
│ order_id │ status │
├──────────┼────────┤
│ 100      │ paid   │
│ 102      │ new    │
└──────────┴────────┘
┌──────────┬────────┐
│ order_id │ status │
├──────────┼────────┤
│ 100      │ paid   │
│ 102      │ new    │
│ 103      │ new    │
└──────────┴────────┘
```

Заказ 101 исчез из текущего состояния: его последняя версия помечена как удалённая (insert deletion). Merge обновил заказ 100 и добавил заказ 103.

</details>

**Задание 3.** Разбейте события на session windows с паузой 5 минут и посчитайте события в fixed windows по 10 минут.

<details><summary>Решение</summary>

```sql
CREATE TABLE events AS
SELECT * FROM (VALUES
  (1, TIMESTAMP '2022-03-01 10:00:00'), (1, TIMESTAMP '2022-03-01 10:02:00'),
  (1, TIMESTAMP '2022-03-01 10:03:30'), (1, TIMESTAMP '2022-03-01 10:20:00'),
  (1, TIMESTAMP '2022-03-01 10:22:00'), (2, TIMESTAMP '2022-03-01 10:01:00')
) AS t(user_id, ts);

WITH marked AS (
  SELECT *, CASE WHEN ts - lag(ts) OVER (PARTITION BY user_id ORDER BY ts) >= INTERVAL 5 MINUTE
                 THEN 1 ELSE 0 END AS new_session
  FROM events
), numbered AS (
  SELECT *, sum(new_session) OVER (PARTITION BY user_id ORDER BY ts) AS session_no
  FROM marked
)
SELECT user_id, session_no, min(ts) AS started, max(ts) AS ended, count(*) AS events
FROM numbered
GROUP BY user_id, session_no
ORDER BY user_id, session_no;

SELECT time_bucket(INTERVAL 10 MINUTE, ts) AS window_start, count(*) AS events
FROM events
GROUP BY window_start
ORDER BY window_start;
```

```text
┌─────────┬────────────┬─────────────────────┬─────────────────────┬────────┐
│ user_id │ session_no │       started       │        ended        │ events │
├─────────┼────────────┼─────────────────────┼─────────────────────┼────────┤
│ 1       │ 0          │ 2022-03-01 10:00:00 │ 2022-03-01 10:03:30 │ 3      │
│ 1       │ 1          │ 2022-03-01 10:20:00 │ 2022-03-01 10:22:00 │ 2      │
│ 2       │ 0          │ 2022-03-01 10:01:00 │ 2022-03-01 10:01:00 │ 1      │
└─────────┴────────────┴─────────────────────┴─────────────────────┴────────┘
┌─────────────────────┬────────┐
│     window_start    │ events │
├─────────────────────┼────────┤
│ 2022-03-01 10:00:00 │ 4      │
│ 2022-03-01 10:20:00 │ 2      │
└─────────────────────┴────────┘
```

Сессии считаются отдельно для каждого ключа, а fixed windows делят все события на окна по десять минут независимо от пользователя. Это batch-версия окон: в streaming-системе то же самое делают динамически.

</details>
