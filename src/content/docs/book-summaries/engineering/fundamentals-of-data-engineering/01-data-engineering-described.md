**Главная мысль:** data engineering это создание и поддержка систем, которые превращают сырые данные в качественную информацию для аналитики и ML. Инженер отвечает за весь путь данных, а не за одну технологию.

## О чём глава

Это первая глава книги. Она отвечает на вопрос: что такое data engineering и чем занимается data engineer. Сначала авторы дают определение и коротко рассказывают историю профессии, от хранилищ данных до облаков. Потом идут навыки инженера, три стадии зрелости данных, два типа инженеров (Type A и Type B) и люди, с которыми инженер работает.

![Три стадии зрелости данных в компании и задачи data engineer на каждой стадии](/assets/fundamentals-of-data-engineering/ch01-maturity.png)

## Что такое data engineering

Путаницы вокруг профессии много. К началу 2022 года по запросу «what is data engineering?» Google находил больше 91 000 страниц. Авторы приводят четыре определения экспертов, и они очень разные. Одни видят инфраструктуру, по которой текут данные. Другие делят работу на SQL-вид и big data-вид. Третьи называют профессию надмножеством BI и хранилищ данных. Четвёртые говорят коротко: перемещение, обработка и управление данными. Общий рисунок у всех один: инженер получает данные, хранит их и готовит для аналитиков и data scientists. Из этого авторы делают своё определение:

- Data engineering это разработка, внедрение и поддержка систем и процессов, которые берут сырые данные и дают из них согласованную информацию для аналитики и ML.
- Это пересечение шести тем: security, data management, DataOps, data architecture, orchestration, software engineering.
- Data engineer управляет **data engineering lifecycle**: от получения данных из источников до выдачи для аналитики и ML.

Авторы вводят lifecycle, потому что легко зациклиться на технологиях и потерять общую картину. Lifecycle переносит разговор с инструментов на сами данные и на цели, ради которых они нужны. В нём пять стадий: Generation, Storage, Ingestion, Transformation, Serving. Шесть тем из определения названы undercurrents: они проходят через все стадии. Подробно они разобраны в [главе 2](/book-summaries/engineering/fundamentals-of-data-engineering/02-data-engineering-lifecycle/).

## Как развивалась профессия

Авторы говорят, что это не урок истории. Прошлое помогает понять, куда идёт область. Главная мысль истории: «старое снова становится новым».

### 1980-2000: от хранилищ данных к вебу

- Корни профессии лежат в хранилищах данных. Bill Inmon ввёл термин data warehouse в 1989 году.
- Инженеры IBM создали реляционную базу и SQL, Oracle сделал их популярными. Данных стало больше, и бизнесу понадобились pipelines для отчётов и BI.
- Ralph Kimball и Inmon разработали методы моделирования бизнес-логики. Их используют до сих пор.
- Хранилища дали первую эпоху масштабируемой аналитики: MPP-базы считают на многих процессорах сразу. Роли BI engineer, ETL developer и data warehouse engineer это предшественники data engineer.
- С середины 1990-х интернет стал массовым. Веб-компании вроде AOL, Yahoo и Amazon работали на дорогих монолитных системах. Производители не ждали такого объёма данных.

### Начало 2000-х: рождение современной профессии

Пузырь dot-com лопнул и оставил мало выживших. Yahoo, Google и Amazon выросли в гигантов. Сначала они жили на старых монолитных базах и довели их до предела. Нужны были системы, которые дёшево масштабируются и остаются надёжными. Одновременно подешевело обычное железо: серверы, память, диски. Появилась распределённая обработка на огромных кластерах. Так началась эра **big data**. Её часто описывают тремя V: velocity, variety, volume.

Ключевые события:

- 2003 и 2004: Google публикует статьи про Google File System и MapReduce. Корни big data были и раньше (MPP-хранилища, физические эксперименты), но эти статьи авторы называют «большим взрывом».
- 2006: инженеры Yahoo по мотивам статей создают Apache Hadoop и открывают его код. Компании копят терабайты и петабайты, и появляется big data engineer.
- Amazon решает свой рост данных и создаёт EC2 (вычисления), S3 (хранение) и DynamoDB (NoSQL). Он продаёт их другим через AWS. Это первое массовое публичное облако: вместо покупки железа разработчик арендует ресурсы. Затем идут Google Cloud, Azure и DigitalOcean. Авторы считают облако одной из главных инноваций XXI века.

### 2000-2010-е: эра big data

Инструменты вокруг Hadoop быстро созрели. Впервые любая компания получила те же средства, что у лучших tech-гигантов. Случился ещё один переход: от batch к event streaming, то есть к «real-time». Инженеры выбирали из Hadoop, Hive, HBase, Storm, Cassandra, Spark, Presto. Старые GUI-инструменты казались устаревшими, моден был подход code-first. Big data engineer хорошо писал код, знал низкоуровневую инфраструктуру и держал огромные кластеры. Он уже не развивал ядро технологии, а доставлял данные.

Big data стало жертвой собственного успеха. Из-за шума и маркетинга компании поднимали Hadoop ради нескольких гигабайт.

Почему термин потерял силу? Одно слово: simplification. Open source инструменты мощные, но требуют постоянного внимания. Целые команды big data engineers стоили миллионы долларов в год. Они тратили много времени на поддержку и мало на пользу бизнесу. Тогда open source проекты, облака и сторонние компании начали прятать сложность и убирать расходы на кластеры. Данных стало больше, но обработка так упростилась, что отдельный термин не нужен. Big data engineers теперь просто data engineers.

### 2020-е: инженерия жизненного цикла данных

Раньше инженер занимался деталями монолитов (Hadoop, Spark, Informatica). Теперь тренд идёт к управляемым инструментам с высокой абстракцией. Популярен **modern data stack**: набор готовых open source и сторонних продуктов, который облегчает жизнь аналитикам. Data engineering всё больше похоже на сборку LEGO из технологий ради бизнес-целей.

Авторы называют такого инженера **data lifecycle engineer**. Низкоуровневые навыки у него остаются, но внимание уходит выше по цепочке ценности: security, data management, DataOps, architecture, orchestration. Изменился и настрой. Раньше хвалились «самыми большими данными», теперь заботятся об управлении, поиске и качестве. Инженеры знают CCPA и GDPR (законы о приватности данных в Калифорнии и в ЕС) и думают об анонимизации, удалении данных и соответствии нормам.

Снова «старое стало новым». Quality и governance были нормой в больших корпорациях до big data, а малые компании их почти не применяли. Теперь сложные проблемы прошлого упакованы в продукты. Поэтому технологи вернулись к «enterprise-теме», но с упором на децентрализацию и гибкость, а не на командно-административный стиль. Авторы называют настоящее золотым веком управления жизненным циклом данных.

## Data engineering и data science

Некоторые считают data engineering подобластью data science. Авторы не согласны: дисциплины разные и дополняют друг друга. Data engineering стоит **upstream**. Инженеры дают входные данные, а data scientists (downstream) превращают их в полезный результат.

Авторы опираются на **Data Science Hierarchy of Needs** (Monica Rogati, 2017). Внизу этой пирамиды сбор, перемещение и хранение данных, выше аналитика, на вершине AI и ML. Rogati считает: сначала нужен прочный фундамент, и только потом AI и ML.

По оценке, 70-80% времени data scientists тратят на нижние три уровня: сбор, очистку и обработку. На анализ и ML остаётся малая часть. Их обычно не учат строить production-системы, и без помощи инженера они делают это кое-как. В идеале они тратят больше 90% времени на верх пирамиды. Когда инженеры закрывают нижние уровни, data scientists получают основу для успеха. Авторы ставят data engineering на один уровень важности с data science.

## Навыки и задачи

Навыки инженера покрывают undercurrents. Нужно оценивать инструменты и знать, как данные рождаются в источниках и как их потом используют. Кроме того, инженер постоянно балансирует шесть осей: cost, agility, scalability, simplicity, reuse, interoperability.

Раньше инженер занимался администрированием монолитов вроде Hadoop и Teradata. Сегодня он подбирает самые простые и недорогие сервисы, которые дают ценность, и строит гибкую архитектуру.

**Чего инженер обычно не делает:** не строит ML-модели, не делает отчёты и дашборды, не анализирует данные, не считает KPI, не пишет прикладное ПО. Но он понимает эти области, чтобы служить заказчикам.

## Зрелость данных

Data maturity это рост использования данных, возможностей и интеграции в компании. Она не зависит от возраста или выручки: стартап может быть зрелее столетней корпорации. Важно, как компания использует данные для конкурентного преимущества. Готовые модели зрелости сложны, поэтому авторы придумали свою, простую: три стадии.

### Стадия 1: Starting with data

Цели размыты, архитектура только планируется, команда меньше десяти человек. Инженер здесь generalist: он совмещает роли data scientist и software engineer. Его задача быстро получить результат.

Соблазн прыгнуть в ML велик, но авторы против. Они видели много команд, которые застряли. Без фундамента нет данных для обучения и нет способа развернуть модели в production. Авторы в шутку зовут себя «recovering data scientists»: они сами участвовали в преждевременных проектах.

Что делать:

- Получить поддержку руководства, лучше спонсора для важных инициатив.
- Определить архитектуру, чаще в одиночку. Для этого нужны бизнес-цели и конкурентное преимущество. См. [главу 3](/book-summaries/engineering/fundamentals-of-data-engineering/03-designing-good-data-architecture/).
- Найти и проверить нужные данные и построить основу для будущих аналитиков. Пока их нет, отчёты иногда приходится делать самому.

Подводные камни:

- Без громких успехов у организации пропадает желание продолжать. Нужны быстрые победы, но они создают technical debt. Нужен план по его снижению.
- Не работайте в изоляции. Команды часто сидят «в пузыре» и делают то, что мало кому нужно.
- Избегайте **undifferentiated heavy lifting**. Берите готовые решения. Свой код нужен только там, где он даёт конкурентное преимущество.

### Стадия 2: Scaling with data

Компания ушла от разовых запросов к формальным практикам. Теперь нужна масштабируемая архитектура. Роли переходят от generalists к specialists.

Цели инженера: формальные практики, надёжная архитектура, DevOps и DataOps, системы для ML и по-прежнему никакого undifferentiated heavy lifting. Предупреждения:

- Растёт соблазн взять новейшие технологии, потому что их взяла Кремниевая долина. Это редко стоит усилий. Выбор технологии должен идти от ценности для клиентов.
- Узкое место масштабирования это не кластер, а команда data engineering. Выбирайте решения, которые просто развернуть и поддерживать.
- Не изображайте «гения данных». Лучше станьте прагматичным лидером: объясняйте другим командам пользу данных и учите организацию их использовать.

### Стадия 3: Leading with data

Компания data-driven. Автоматические pipelines дают self-service аналитику и ML. Новые источники подключаются легко. Роли специализируются ещё глубже. Инженер автоматизирует подключение данных, строит свои инструменты там, где данные дают преимущество, и занимается governance, качеством и DataOps. Он вводит каталоги и lineage и строит среду, где люди говорят открыто.

Опасности две. Первая это самодовольство: без постоянного улучшения компания откатится на стадию ниже. Вторая это технологические отвлечения, дорогие «хобби-проекты» без пользы для бизнеса.

## Бэкграунд и навыки data engineer

Профессия молодая. Единой программы нет ни в университетах, ни в буткемпах, поэтому нужно много учиться самому. Легче всего переходят из смежных ролей: software engineering, ETL, администрирование БД, data science, анализ данных. Лучшие инженеры смотрят и бизнес-глазами, и технически.

### Бизнес-навыки

- Общаться с техническими и нетехническими людьми. Следите за иерархией и «силосами» в организации.
- Собирать и уточнять требования и согласовывать их с заказчиками.
- Понимать культуру Agile, DevOps и DataOps. Многие думают, что это решается технологией. Авторы называют это опасной ошибкой: нужна поддержка всей организации.
- Контролировать расходы: time to value, total cost of ownership (TCO), opportunity cost.
- Постоянно учиться и отличать полезное от незрелого и от моды.

Команды побеждают благодаря общению. Проигрывают они редко из-за технологии.

### Технические навыки

Должен ли инженер писать код? Да, на уровне production. Managed сервисы заменили много низкоуровневого кода, и инженеры чаще пишут pipelines как код внутри orchestration-фреймворка. Но хороший код даёт преимущество, а кто не пишет production-код, тот сильно ограничен.

| Язык | Зачем нужен |
|---|---|
| SQL | Основной интерфейс к базам и data lake. Эпоха MapReduce отодвинула его, но он вернулся как lingua franca данных |
| Python | Связь между data engineering и data science. Есть в pandas, Airflow, PySpark. «Клей» между компонентами |
| JVM (Java, Scala) | Spark, Hive, Druid. Быстрее Python и открывает низкоуровневые функции |
| bash | Командная строка. awk и sed часто обрабатывают файлы в pipeline. В Windows можно взять PowerShell |

Авторы отдельно хвалят SQL. Spark SQL, BigQuery, Snowflake и Hive обрабатывают огромные объёмы декларативным SQL. Его понимают и Flink, Beam, Kafka. Инженер должен отлично знать SQL, его современные возможности для JSON и вложенных данных, и dbt. Но SQL не панацея. Токенизировать текст для NLP лучше на Spark. Хороший инженер видит, когда SQL не подходит.

Вторичные языки (R, JavaScript, Go, Rust, C#) нужны, если их используют в компании. Например, на JavaScript пишут функции в облачных хранилищах.

Как не отстать? Учите основы, которые не меняются, и следите за новинками. Оценивайте новую технологию по пользе для lifecycle.

## Type A и Type B

Вакансии рисуют data engineer как «единорога» с любым навыком. На деле работа разная. Авторы взяли идею из data science (Type A это analysis, Type B это building) и применили к инженерам.

![Сравнение Type A (abstraction) и Type B (build) data engineers](/assets/fundamentals-of-data-engineering/ch01-type-a-b.png)

- **Type A** (abstraction): избегает undifferentiated heavy lifting, держит архитектуру простой и работает на готовых продуктах и managed сервисах. Нужен в компаниях любой зрелости.
- **Type B** (build): строит инструменты, которые опираются на ключевую компетенцию компании. Чаще нужен на стадиях 2 и 3 или когда первый use case так уникален, что без своих инструментов не начать.

Оба типа могут быть в одной компании и даже в одном человеке. Чаще первым нанимают Type A, а навыки Type B приходят позже.

> **Пояснение:** Type A берёт готовый managed сервис для загрузки данных вместо своего кода. Type B пишет свой код, только если без него нет конкурентного преимущества.

## С кем работает data engineer

Инженер не работает в вакууме. Он общается с техническими и нетехническими людьми и смотрит внутрь и наружу компании.

### Internal-facing и external-facing

**External-facing** инженер работает с пользователями внешних приложений: соцсети, IoT, e-commerce. Он строит системы сбора и обработки транзакций и событий. Тут есть петля обратной связи: приложение, pipeline и снова приложение. Проблемы особые. Concurrency запросов намного выше, поэтому запросы пользователя жёстко ограничивают. Безопасность сложнее, особенно при multitenancy (данные многих клиентов в одной таблице).

**Internal-facing** инженер решает задачи бизнеса: pipelines и хранилища для BI, отчётов, data science и ML.

Роли часто смешаны, ведь внутренние данные обычно нужны раньше внешних. Тогда у инженера два типа пользователей с разными требованиями к concurrency и безопасности.

### Другие технические роли

![Data engineer между upstream-ролями (источники данных) и downstream-ролями (потребители)](/assets/fundamentals-of-data-engineering/ch01-stakeholders.png)

Инженер стоит как узел между производителями данных (software engineers, архитекторы, DevOps и SRE) и потребителями (аналитики, data scientists, ML engineers).

**Upstream:**

- **Data architects** работают на уровень абстракции выше и рисуют план управления данными. Они мост между технической и нетехнической частью, задают политики для разных подразделений и часто ведут миграцию в облако. Облако сдвинуло границу: решения, которые требовали закупки железа, теперь принимаются по ходу внедрения. В небольшой компании инженер может заменять архитектора. Авторы ставят архитекторов upstream, потому что они часто проектируют слои данных приложений, то есть источники.
- **Software engineers** создают приложения и производят внутренние данные: события и логи. Это ценный актив, в отличие от внешних данных из SaaS. В хороших компаниях инженеры договариваются со старта: об объёме, частоте и формате данных, о безопасности и регуляторных требованиях.
- **DevOps и SRE** производят данные мониторинга. Они upstream, но бывают и downstream, когда смотрят дашборды.

**Downstream.** Data engineering существует ради потребителей данных. Модели работы бывают две: централизованная команда или кросс-функциональные команды.

- **Data scientists** строят прогнозные модели. Фольклор говорит, что 70-80% времени они готовят данные. Авторы считают, что такие цифры показывают незрелые практики. Работа на одной машине заставляет брать подвыборку, а локальный код трудно выкатить в production. Если инженеры работают хорошо, data scientists после начальной разведки не чистят данные: инженеры автоматизируют это. Запрос на production-ready data science это один из главных двигателей профессии. Сами авторы перешли из data science в data engineering из-за него.
- **Data analysts** смотрят на прошлое и настоящее, пишут SQL и работают в BI (Power BI, Looker, Tableau). Они эксперты предметной области: знают определения и проблемы качества данных. Их знания очень помогают качеству.
- **ML engineers и AI researchers.** ML engineers обучают модели и поддерживают инфраструктуру ML в production. Границы с data engineering размыты. ML engineering сегодня усваивает MLOps и практики DevOps. AI researchers исследуют новые методы в больших техкомпаниях, стартапах вроде OpenAI и DeepMind или в университетах.

### Data engineers и руководство

Бизнес всё сильнее опирается на данные, поэтому инженеры участвуют в стратегии и ведут инициативы за пределами IT.

| Роль | Что важно для инженера |
|---|---|
| CEO | Задаёт видение. Инженер показывает, что возможно, и ведёт карту доступных данных. Участвует в больших изменениях: облако, streaming |
| CIO и CTO | CIO отвечает за внутренний IT и помогает сформировать культуру данных. CTO смотрит наружу: веб, мобильные приложения, IoT. Инженеры часто подчиняются CTO |
| CDO | Роль появилась в 2002 в Capital One. Отвечает за данные как актив: data products, master data management, приватность |
| CAO и chief algorithms officer | CAO отвечает за аналитику и решения. Chief algorithms officer это техническая роль про data science и ML |

**Project managers** направляют поток работ и выступают «привратниками»: из длинного списка запросов бизнеса они выбирают главное. Инженер ходит на планирование спринтов и standups и сообщает о блокерах. **Product managers** владеют data products и всё чаще общаются с инженерами. С остальными руководителями работа идёт по двум моделям: централизованная команда принимает запросы или инженер закреплён за менеджером, проектом или продуктом.

Авторы заканчивают мыслью: инженера нанимают не ради кода в изоляции. Нужно понимать задачи, инструменты и людей, которым ты служишь.

## Итоги главы

- Data engineering это разработка и поддержка систем, которые превращают сырые данные в информацию для аналитики и ML. Инженер управляет всем lifecycle.
- Профессия выросла из хранилищ данных. Статьи Google, Hadoop и облако AWS запустили эру big data, а упрощение сделало big data engineer просто data engineer.
- В 2020-е инженер меньше занят низким уровнем и больше безопасностью, качеством, архитектурой и governance.
- Data engineering стоит upstream от data science. Без фундамента данных ML-модели не работают в production.
- Data maturity имеет три стадии: starting, scaling и leading with data. У каждой свои задачи и свои ошибки.
- Главное правило всех стадий: не делайте undifferentiated heavy lifting. Свои решения нужны только для конкурентного преимущества.
- Успех инженера чаще зависит от общения, требований и контроля затрат, а не от технологии.
- Type A строит на готовых сервисах, Type B строит свои системы. Первым обычно нанимают Type A.
- Инженер связывает производителей данных (software engineers, архитекторов, DevOps) с потребителями (аналитики, data scientists, ML engineers) и руководством.

## Ключевые термины

| Термин (EN) | Что значит |
|---|---|
| Data engineering lifecycle | Пять стадий пути данных: от источника до выдачи |
| Undercurrents | Сквозные темы, которые поддерживают все стадии |
| Big data | Эпоха кластеров Hadoop. Сегодня термин почти не нужен |
| Modern data stack | Набор готовых open source и сторонних продуктов |
| Data maturity | Уровень использования данных в компании |
| Undifferentiated heavy lifting | Тяжёлая работа, которая не даёт преимущества |
| Type A / Type B | Инженер на готовых сервисах или строящий свои системы |
| Upstream / downstream | Источники данных и потребители данных |

## Что это значит на практике

- Определите стадию зрелости своей компании. От неё зависят задачи и инструменты.
- Не начинайте с ML, пока нет основы: сбор, хранение, качество данных.
- Берите готовые сервисы. Свой код нужен только для конкурентного преимущества.
- Договаривайтесь с software engineers о формате данных до запуска проекта.
- Развивайте навыки общения и контроля затрат. Успех чаще зависит от них, чем от технологии.
- Хорошо знайте SQL и Python. Для open source на JVM пригодится Java или Scala.
