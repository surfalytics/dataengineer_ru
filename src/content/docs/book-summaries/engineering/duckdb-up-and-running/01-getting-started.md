**Главная мысль:** DuckDB — это аналитическая база данных, которая работает внутри вашего процесса. Не нужен сервер. Не нужно сначала загружать файл в базу. Вы пишете SQL и сразу читаете CSV, Parquet или DataFrame. Автор показывает, что так быстрее и легче по памяти, чем грузить всё в pandas.

## О чём глава

Глава отвечает на три вопроса. Что такое DuckDB? Почему он быстрый? Как начать работать за несколько минут? Это первая глава, общую картину книги смотрите в [обзоре](/book-summaries/engineering/duckdb-up-and-running/).

![Обычный путь с сервером базы данных и путь с DuckDB: без шага загрузки и без сервера](/assets/duckdb-up-and-running/ch01-traditional-vs-duckdb.png)

Верхняя полоса — обычный путь: файл, загрузка в сервер, SQL, DataFrame. Нижняя — путь с DuckDB: файл, SQL, результат.

## Зачем нужен DuckDB

Для анализа данных многие берут `pandas`. Недавно появился `Polars`, он быстрее и экономнее. Но самый известный язык у разработчиков всё равно SQL. Автор спрашивает: не проще ли обрабатывать данные сразу на SQL?

DuckDB придумали в 2018 году как `OLAP`-базу (online analytical processing): она создана для быстрых аналитических запросов. Цель была занять место между полноценной СУБД и простым встроенным движком вроде SQLite, но с упором на аналитику, а не на транзакции. Первый стабильный релиз вышел в 2019 году. В 2021 году основали DuckDB Labs: она даёт коммерческую поддержку, сам DuckDB остаётся открытым. Позже появился MotherDuck: это DuckDB как облачный сервис (`SaaS`). Подробнее в главе 9.

> **Пояснение:** `OLAP` — это мало запросов, но каждый читает много строк и считает суммы или группировки. `OLTP` — наоборот, много коротких операций над отдельными строками, например «создать заказ».

## Что такое DuckDB

DuckDB — реляционная СУБД (`RDBMS`) с поддержкой SQL, созданная для `OLAP`. Автор выделяет четыре свойства:

- **Работает внутри процесса (`in-process`).** Это библиотека, а не сервер. Установки и настройки нет.
- **Запросы к pandas без копирования.** SQL идёт прямо над данными DataFrame, их не нужно импортировать или дублировать.
- **Векторная обработка на одной машине.** Данные идут порциями, удобными для процессора. Spark и Flink, наоборот, раздают данные и вычисления по многим узлам кластера.
- **Хранение по столбцам.** MySQL и SQLite хранят данные по строкам. DuckDB хранит по столбцам, и автор называет это ключом к скорости.

### Зачем использовать DuckDB

Данные приходят из CSV, Excel, JSON, Parquet и баз. В процессе `ELT` (Extract, Load, Transform) вы обычно сначала загружаете файл в сервер БД, потом приложение запрашивает его через SQL и получает DataFrame. DuckDB убирает шаг загрузки: вы работаете с набором данных напрямую на SQL. Если данные уже лежат в pandas DataFrame, DuckDB тоже запрашивает их на месте, без отдельного сервера.

## Почему DuckDB быстрый

Автор называет шесть решений.

**Колоночное хранение.** В строковой базе все поля одной строки лежат рядом. В DuckDB данные лежат столбец за столбцом. Аналитический запрос часто читает один-два столбца по очень многим строкам, например суммирует их. DuckDB читает только нужные. Если нужны 2 столбца из 10, остальные 8 даже не трогаются, а строковая база загрузила бы все.

![Хранение по строкам и по столбцам: запрос AVG(age) читает все поля строк или только один столбец](/assets/duckdb-up-and-running/ch01-row-vs-column.png)

**Векторное выполнение.** Движок берёт не одну строку, а порцию (вектор). На каждую строку по отдельности уходит лишняя работа: обращения к памяти и выбор следующей инструкции. На порции эти расходы делятся. Порция лучше помещается в кеш процессора, поэтому реже случаются `cache miss` (процессору приходится идти за данными в медленную память).

**Экономия памяти.** DuckDB работает над структурами в памяти без лишних копий. Данные идут кусками, поэтому набор не обязан целиком влезать в память.

**Параллельное выполнение.** Запрос идёт на всех ядрах. Например, агрегацию или `JOIN` на большой таблице движок делит на части и считает их одновременно.

**Отложенная материализация (`late materialization`).** Материализация — это когда движок достаёт полные строки в память. Обычные базы делают это рано, хотя в результате нужна часть столбцов. DuckDB откладывает шаг: сначала работает с метаданными, например с номерами столбцов, и достаёт данные только для нужных столбцов. Выигрыш виден в запросах с фильтрами и `JOIN` больших таблиц.

**Оптимизатор запросов.** Перед выполнением планировщик перестраивает запрос. Он использует `predicate pushdown` (фильтр применяется как можно ближе к источнику данных) и `join reordering` (выбор лучшего порядка соединения таблиц).

![Путь запроса внутри DuckDB: планировщик, чтение нужных столбцов векторами, параллельная обработка на ядрах, сборка итога в конце](/assets/duckdb-up-and-running/ch01-query-pipeline.png)

**Переносимость.** DuckDB не нужен отдельный сервер, поэтому его встраивают куда угодно: в локальные приложения и ноутбуки data science. Он работает на Windows, Linux и macOS.

## Языки, SQL и открытый код

DuckDB поддерживает стандартный SQL (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) и форматы CSV, Parquet, JSON, а также pandas DataFrame. Языки: Python, R, C/C++, Julia, Java, Go, Node.js, Rust.

Код DuckDB открыт. Автор называет четыре плюса: прозрачность (видно, как всё устроено), быстрые обновления от сообщества, бесплатность без лицензий и сильная экосистема из расширений, документации и уроков.

## Быстрый старт

В книге все примеры идут в Jupyter Notebook. Пакет ставится через `pip install duckdb`. База создаётся функцией `connect()`. С именем файла она сохраняется на диск. Со значением `':memory:'` она живёт только в памяти.

> Автор предупреждает: изменения в базе в памяти пропадают при её закрытии. Чтобы данные жили между сессиями, берите файл.

Дальше автор шаг за шагом показывает полный путь:

1. `CREATE TABLE employees` (id, name, age, department) и проверка через `SHOW TABLES`.
2. `INSERT INTO` четырёх сотрудников.
3. `SELECT *` для просмотра таблицы.
4. Агрегация: `COUNT`, `AVG`, `MAX` с `GROUP BY` (сколько людей в отделе, средний и максимальный возраст).
5. `JOIN` таблиц `orders` и `customers` по `customer_id`, потом `SUM` и `GROUP BY` для суммы трат клиента.

Результат `execute()` превращают в DataFrame методом `.df()`.

### Чтение из pandas

Если данные уже в pandas DataFrame, DuckDB читает их без копирования. В SQL на DataFrame ссылаются просто по имени переменной. Автор берёт DataFrame сотрудников и продаж, соединяет их через `LEFT JOIN` и считает сумму продаж по отделам. Вот короткая версия ([полный код](https://github.com/surfalytics/dataengineer.ru/tree/main/scripts/duckdb-code/ch01_df_by_name.py), файл `scripts/duckdb-code/ch01_df_by_name.py`):

```python
import duckdb
import pandas as pd

employees = pd.DataFrame({"employee_id": [1, 2, 3, 4],
                          "department": ["HR", "Engineering", "Marketing", "Engineering"]})
sales = pd.DataFrame({"employee_id": [1, 2, 1, 3, 4], "sale_amount": [200, 500, 150, 300, 700]})

# employees и sales - это переменные Python. В SQL их видно по имени.
print(duckdb.sql("""
    SELECT e.department, SUM(s.sale_amount) AS total_sales
    FROM employees e LEFT JOIN sales s ON e.employee_id = s.employee_id
    GROUP BY e.department ORDER BY e.department
""").df().to_string(index=False))
```

```text
 department  total_sales
Engineering       1200.0
         HR        350.0
  Marketing        300.0
```

Остальной код быстрого старта: `ch01_quick_look.py` и `ch01_dataframe.py` в той же папке.

> **Пояснение:** в запросах книги два места легко прочитать неверно. `AVG(sale_amount)` считает среднюю одну продажу, а не среднюю на сотрудника. Запрос «top performers» даёт лучшую продажу каждого сотрудника, не отдела.

## Почему DuckDB эффективнее

Автор проверяет скорость и память на файле `flights.csv` (рейсы США за 2015 год): почти 600 МБ, больше 5,8 млн строк, около 30 полей, среди них `AIRLINE` и `ARRIVAL_DELAY`.

**Скорость.** pandas грузит файл около 7,5 с (7,46 с, разброс 568 мс), потом считает среднюю задержку по авиакомпаниям за 186 мс. Итого около 7,5 с, почти всё время уходит на загрузку. DuckDB делает то же одним запросом через `read_csv_auto()` примерно за 0,5 с (496 мс). Эта функция сама определяет типы столбцов и обрабатывает данные на лету, не загружая весь файл в память.

**Память.** Автор измеряет память процесса через `psutil`. После загрузки CSV в pandas процесс вырос с 131 МБ до 4363 МБ, то есть примерно на 4,2 ГБ. После запроса DuckDB процесс вырос с 72 МБ до 348 МБ, то есть примерно на 280 МБ.

![Сравнение pandas и DuckDB на CSV с 5,8 млн строк: время около 7,5 с против 0,5 с, память около 4,2 ГБ против 280 МБ](/assets/duckdb-up-and-running/ch01-speed-memory.png)

Выводы автора:

- DuckDB сильно сокращает время, особенно для разовых операций над CSV, потому что не тратит время на загрузку.
- Если нужно много операций над одними данными и памяти хватает, эффективнее один раз загрузить их в pandas.

Мы повторили замер на синтетическом файле с 5,8 млн строк (259 МБ). Код: `scripts/duckdb-code/ch01_speed_memory.py`. Это один настоящий запуск, на вашей машине цифры будут другими:

```text
Файл: 5 800 000 строк  259 МБ
pandas  время:  1.88 с   память до:    39.2 МБ   после:  2886.3 МБ   выросла на:  2847.1 МБ   групп: 14
duckdb  время:  0.32 с   память до:    39.2 МБ   после:   299.2 МБ   выросла на:   260.0 МБ   групп: 14
```

## Итоги главы

- DuckDB — это `in-process` реляционная СУБД для `OLAP`. Она работает внутри программы и не требует сервера.
- Главный выигрыш: нет шага загрузки. SQL идёт прямо над CSV, Parquet, JSON и pandas DataFrame.
- Скорость даёт сочетание приёмов: колонки, векторы, параллельность, отложенная материализация и оптимизатор.
- Он поддерживает стандартный SQL и восемь языков. Код открыт.
- Быстрый старт — это `connect()`, `CREATE TABLE`, `INSERT`, `SELECT`, `GROUP BY`, `JOIN` и `.df()`.
- На CSV с 5,8 млн строк у автора 0,5 с и около 280 МБ против 7,5 с и 4,2 ГБ у pandas.

## Ключевые термины

| Термин | Значение |
|---|---|
| `In-process database` | База внутри вашей программы, без сервера |
| `OLAP` / `OLTP` | Аналитические запросы / много коротких операций над строками |
| `Columnar storage` | Хранение по столбцам |
| `Vectorized execution` | Обработка порциями строк |
| `Late materialization` | Сборка полных строк в последний момент |
| `Predicate pushdown` | Фильтр применяется как можно ближе к источнику |
| `read_csv_auto` | Чтение CSV с автоопределением типов |

## Что это значит на практике

- Для локальной разработки пайплайна и `dbt` DuckDB заменяет тяжёлый сервер. Тесты идут быстро.
- Проверить файл от поставщика можно одним запросом, без загрузки в хранилище.
- DuckDB не заменяет сервер для многих одновременных пишущих пользователей. Он про аналитику на одной машине.
- Сравнение скорости делайте на своих данных. Цифры из книги — только пример.
- Закрепляйте версии `duckdb` и `pandas`: с pandas 3.1.1 DuckDB 1.4.3 падал на строковых столбцах DataFrame.
- Данные, которые нужны потом, храните в файле базы. База `:memory:` пропадает вместе с процессом.

## Практика в DuckDB

Запустите `duckdb` в терминале или откройте [shell.duckdb.org](https://shell.duckdb.org). Блоки идут по порядку.

### Шаг 1. Создаём таблицы

```sql
CREATE TABLE staff (id INTEGER PRIMARY KEY, name VARCHAR, age INTEGER, team VARCHAR);

INSERT INTO staff VALUES
    (1, 'Анна',  31, 'Data'),
    (2, 'Борис', 36, 'Data'),
    (3, 'Вера',  27, 'BI'),
    (4, 'Глеб',  42, 'Platform');

CREATE TABLE staff_orders (order_id INTEGER, staff_id INTEGER, amount DOUBLE);

INSERT INTO staff_orders VALUES
    (1, 1, 100.0),
    (2, 2, 200.0),
    (3, 1, 150.0),
    (4, 3, 80.0);
```

### Шаг 2. Проверяем

```sql
SELECT team, count(*) AS people, round(avg(age), 1) AS avg_age
FROM staff
GROUP BY team
ORDER BY team;
```

Ожидаемо: три команды. В `BI` один человек, в `Data` двое (средний возраст 33,5), в `Platform` один.

### Задания

**1.** Покажите всех сотрудников, даже без заказов, с суммой заказов. Для тех, у кого заказов нет, сумма должна быть 0.

<details>
<summary>Решение</summary>

```sql
SELECT s.name, coalesce(sum(o.amount), 0) AS total
FROM staff s
LEFT JOIN staff_orders o ON s.id = o.staff_id
GROUP BY s.name
ORDER BY s.name;
```

Глеб получает 0. `LEFT JOIN` оставляет Глеба, а `coalesce` меняет `NULL` на 0.

</details>

**2.** Сгенерируйте файл на 2 млн строк, запишите его в CSV и посчитайте среднее по группам без `CREATE TABLE`.

<details>
<summary>Решение</summary>

```sql
COPY (
    SELECT i AS id, 'A' || (i % 5) AS grp, (i % 100) * 1.5 AS val
    FROM range(2000000) t(i)
) TO '/tmp/duck_ch1_big.csv' (HEADER, DELIMITER ',');

SELECT grp, round(avg(val), 2) AS avg_val
FROM read_csv_auto('/tmp/duck_ch1_big.csv')
GROUP BY grp
ORDER BY grp;
```

Пять групп `A0`–`A4`. Среднее растёт от 71,25 до 77,25. Файл читается прямо в запросе.

</details>

**3.** Запишите данные в Parquet и посмотрите план запроса через `EXPLAIN`. Найдите, какие столбцы читает `PARQUET_SCAN` и где стоит фильтр.

<details>
<summary>Решение</summary>

```sql
COPY (
    SELECT i AS id,
           ['AA','DL','UA'][1 + (i % 3)] AS airline,
           CAST(hash(i) % 100 AS INTEGER) - 20 AS arr_delay,
           'note ' || i AS note
    FROM range(300000) t(i)
) TO '/tmp/duck_ch1_flights.parquet' (FORMAT parquet);

EXPLAIN
SELECT airline, avg(arr_delay)
FROM '/tmp/duck_ch1_flights.parquet'
WHERE arr_delay > 60
GROUP BY airline;
```

В строке `Projections` у `PARQUET_SCAN` только `arr_delay` и `airline`: столбцы `id` и `note` не читаются. Строка `Filters: arr_delay>60` стоит в самом чтении, это `predicate pushdown`. Полный вывод плана: `scripts/duckdb-code/ch01_explain.py`.

</details>
