**Главная мысль:** MotherDuck — это DuckDB как облачный сервис. Вы загружаете данные один раз, делитесь ими по ссылке и запускаете запросы без своего сервера. Главная особенность — hybrid-запрос: один запрос читает и локальные файлы, и таблицы в облаке.

## О чём глава

До сих пор DuckDB стоял на вашей машине, его надо ставить и настраивать. Глава отвечает: как анализировать данные, не настраивая машину? Предыдущая тема — [удалённые данные](/book-summaries/engineering/duckdb-up-and-running/08-remote-data/). Это последняя глава книги.

Темы: загрузка данных, базы и схемы, shares, запросы в вебе, ИИ-функции, подключение из CLI и hybrid-запросы.

![DuckDB на вашей машине и MotherDuck в облаке: подключение через ATTACH и токен](/assets/duckdb-up-and-running/ch09-architecture.png)

Слева ваша машина с DuckDB и файлами. Справа облако: свой compute, базы и веб-интерфейс. Мост между ними — команда `ATTACH 'md:'`.

> **Важно:** MotherDuck требует аккаунт и токен. У нас их нет. Поэтому команды MotherDuck в этой главе **мы не запускали**. Они взяты из книги и помечены. Запускали мы только локальную имитацию в разделе «Практика в DuckDB».

## Что такое MotherDuck

Многим аналитикам нужно не сложное решение, а serverless-хранилище, которым легко делиться. Вы загружаете данные в облако и сразу запрашиваете их.

- Он читает Parquet, CSV, JSON, Iceberg и Delta Lake.
- Dual Execution: часть запроса идёт локально, часть в облаке.
- Каждому пользователю даётся отдельный изолированный compute. Он растёт сам по себе и тянет нагрузки до нескольких терабайт.
- Инфраструктура работает в AWS. Сервисы идут в основном в контейнерах под Kubernetes.

### Вход и тарифы

Начните с бесплатного 30-дневного trial. Вход через Google, GitHub или email. Веб-интерфейс похож на Jupyter: слева панели Notebooks и Attached databases, справа ноутбук с SQL-ячейками.

После trial можно остаться на Free или взять Standard. Разница в compute units (`CU`, единица вычислений) и хранилище: на Standard их можно докупать.

## Базы, схемы и таблицы

По умолчанию подключены две базы:

- `my_db` — ваша база. Чтение и запись.
- `sample_data` — учебные таблицы. Только чтение, потому что это shared database. На значке такой базы нарисован человек.

Внутри базы таблицы группируются в схемы. Схема — это логическая группа связанных таблиц. Полное имя: `база.схема.таблица`. Схема по умолчанию называется `main`.

![Иерархия объектов: аккаунт, базы, схемы, таблицы](/assets/duckdb-up-and-running/ch09-hierarchy.png)

### Загрузка таблицы

Кнопка Add Data открывает выбор файла. Для CSV интерфейс сам создаёт ячейку с `CREATE OR REPLACE TABLE ... AS SELECT * FROM read_csv_auto([...])`. Перед запуском нужно дописать, куда класть данные: базу и схему. Автор грузит `airlines.csv`:

```text
CREATE OR REPLACE TABLE my_db.main.airlines AS
SELECT * FROM read_csv_auto(['airlines.csv']);
```

Удалить таблицу можно через `DROP TABLE my_db.main.airlines;`.

### Схемы

Свою схему создают так: `CREATE SCHEMA my_db.Titanic`. Таблицу грузят в неё как выше. `DROP SCHEMA` не сработает, если в схеме есть таблицы. Сначала удалите таблицы или добавьте `CASCADE`.

## Shares: общий доступ без копий

Автор называет шаринг одной из лучших возможностей. Таблицу на миллионы строк не надо грузить каждому коллеге: вы грузите один раз и делитесь. Получатели создают ссылку на базу, копий нет.

Share создают через меню базы. Нужно задать имя и доступ:

- **Anyone in my organization** — вся организация, частый случай для небольших команд.
- **Anyone with the share link** — любой пользователь со ссылкой.

![Схема share: владелец создаёт share, получатели подключают его только для чтения](/assets/duckdb-up-and-running/ch09-share.png)

Общие базы доступны **только на чтение**. После создания MotherDuck показывает готовую команду для получателя. Она выглядит так (не запускали, нужен аккаунт):

```text
ATTACH 'md:_share/<имя_share>/<id>' AS my_db_wml;
```

У получателя уже может быть база `my_db`. Поэтому автор советует переименовать общую базу через `AS`. Дальше:

| Что нужно | Команда или действие |
|---|---|
| Отправить получателям новые правки | `UPDATE SHARE <имя>;` |
| Показать свои shares | `LIST SHARES` |
| Отозвать доступ у части людей | Меню share, Alter |
| Остановить share | Меню share, Drop |

После Drop база недоступна получателям.

## Создать, выбрать, отключить базу

`CREATE DATABASE flights_db;` создаёт новую базу. В ней сразу есть схема `main`. Если баз несколько, `USE flights_db;` делает базу активной, и все следующие запросы идут в неё. Через интерфейс базу пока создать нельзя.

`DETACH flights_db;` отключает базу. Так вы освобождаете память и ресурсы. Данные остаются, базу можно подключить обратно.

## Запросы в веб-интерфейсе

Справа от результата MotherDuck показывает статистику по каждой колонке. Для текста это распределение значений. Для числа это гистограмма и сводные метрики: min, max и другие. На таблице Titanic автор так смотрит `Survived`, `Pclass`, `Sex` и `Age`. Это быстрая EDA без отдельных `GROUP BY`.

## ИИ пишет SQL

MotherDuck встроил LLM в SQL как функции и pragma. Функция считает внутри запроса. Pragma — директива, она управляет поведением базы.

| Что | Что делает |
|---|---|
| `prompt_sql()` | Пишет SQL по вопросу на английском |
| `prompt_query` | Сразу отвечает на вопрос о данных |
| `prompt_fixup()` | Исправляет запрос |
| `prompt_fix_line()` | Исправляет запрос построчно |
| `prompt_schema()` | Описывает содержимое базы |
| `prompt_explain()` | Объясняет, что делает запрос |

Сначала выберите базу через `USE`. Потом вызовите `prompt_sql` через `CALL`. Пример автора (не запускали, нужен аккаунт):

```text
USE my_db;
CALL prompt_sql('How many people who were alone survived');
PRAGMA prompt_query('How many airlines are there?');
```

Функция вернула текст запроса. Автор запустил его: результат 163 выживших одиночек. Второй вопрос — доля выживших по возрастным группам. Модель сама написала `CASE` по десятилетиям. Лучше всех выжили дети. `prompt_query` сразу отдал ответ: 14 авиакомпаний. `prompt_explain` пересказал запрос про возраст простыми словами.

> Проверяйте SQL от модели перед запуском. В примере выше «был один» превратился в условие `SibSp = 0 AND Parch = 0`. Это разумный вариант, но не единственный.

Похожий запрос на придуманных данных запускается без аккаунта: см. раздел «Практика в DuckDB».

## MotherDuck через DuckDB CLI

Для терминала и SSH нужен DuckDB версии 1.0.0 или выше. Запустите `duckdb` и подключитесь:

```text
ATTACH 'md:';
```

Команда печатает ссылку и код. Откройте ссылку, сверьте код с терминалом, нажмите Confirm, войдите и нажмите Accept. Токен получен.

`PRAGMA PRINT_MD_TOKEN;` показывает токен. Положите его в переменную окружения, и входить заново не придётся. Токен — это пароль: не публикуйте его и не коммитьте в репозиторий.

Дальше всё как в локальном DuckDB:

- `SHOW databases;` показывает `memory`, `my_db`, `sample_data`.
- `current_database()` и `current_schema()` показывают, где вы. Сначала это `memory` и `main`.
- `USE my_db.Titanic;` задаёт базу и схему. Дальше таблицу зовут по короткому имени.
- Загрузка файла и `CREATE DATABASE`, `CREATE SCHEMA`, `INSERT` работают как в вебе. Новая база сразу видна в интерфейсе.

Всё это мы не запускали: нужен токен.

## Hybrid-запросы

Это ключевая возможность MotherDuck. Один запрос работает с локальной базой и с облачной вместе.

![Hybrid-запрос: локальный CSV и облачная таблица airlines соединяются одним JOIN](/assets/duckdb-up-and-running/ch09-hybrid.png)

В облаке лежит `airlines` (14 авиакомпаний), локально `flights.csv` из главы 2. В файле только код авиакомпании. Первые 10 строк соединяются с облачной таблицей:

```text
SELECT f.AIRLINE, f.FLIGHT_NUMBER, a.AIRLINE
FROM (SELECT AIRLINE, FLIGHT_NUMBER FROM './flights.csv' LIMIT 10) AS f
JOIN my_db.main.airlines AS a ON f.AIRLINE = a.IATA_CODE;
```

В результате у каждого рейса есть полное название авиакомпании. Это пример из книги, мы его не запускали.

## Итоги главы

- MotherDuck — serverless-платформа на DuckDB: не нужно ставить и настраивать свою машину.
- Данные идут по пути `база.схема.таблица`. Есть две базы по умолчанию: `my_db` и `sample_data`.
- Share даёт другим доступ к базе на чтение без копий. Правки уходят получателям через `UPDATE SHARE`.
- ИИ-функции пишут, исправляют и объясняют SQL, а `prompt_query` сразу отвечает.
- CLI подключается через `ATTACH 'md:'` и токен. Токен надо беречь.
- Hybrid-запрос соединяет локальный файл и облачную таблицу в одном запросе.
- Автор итожит книгу так: DuckDB быстр благодаря колоночному хранению, векторному выполнению и работе внутри процесса. Он дружит с pandas и Polars, читает много форматов и легко встраивается.

## Ключевые термины

| Термин | Значение |
|---|---|
| MotherDuck | Облачный сервис на DuckDB |
| Serverless | Нет своего сервера. Платите за использование |
| Compute unit (CU) | Единица вычислений в тарифе |
| Share | Доступ к снимку базы только для чтения |
| `ATTACH` / `DETACH` | Подключить / отключить базу |
| Schema | Группа таблиц внутри базы |
| Dual Execution | Запрос идёт частично локально, частично в облаке |
| Hybrid query | Запрос по локальным и облачным данным |

## Что это значит на практике

- Для небольшой команды MotherDuck — простое хранилище без администрирования. Для больших нагрузок проверьте тарифы и лимиты.
- Shares удобны для общих справочников и учебных данных. Не нужно копировать и рассылать файлы.
- Работайте в двух средах: локально для разработки, в облаке для общих данных. Hybrid-запрос соединяет их.
- LLM-функции ускоряют черновики SQL, но результат нужно проверять. В `dbt` такой SQL попадает в модели только после ревью и тестов.
- Токены MotherDuck храните как секреты, не в репозитории.

## Практика в DuckDB

Запустите `duckdb` в терминале. Блоки идут по порядку. Аккаунт не нужен. Вторая база в памяти играет роль облака: у неё те же команды `ATTACH`, `USE`, `CREATE SCHEMA`. Для настоящего облака адрес будет `md:` вместо `:memory:`.

### Шаг 1. «Облачная» база и таблицы

```sql
-- вторая база. В MotherDuck было бы ATTACH 'md:my_db'
ATTACH ':memory:' AS cloud_db;

CREATE SCHEMA cloud_db.ref;

CREATE TABLE cloud_db.ref.airlines AS
SELECT * FROM (VALUES
    ('AA', 'Air Alpha'),
    ('BB', 'Blue Bird'),
    ('CC', 'Cloud Carrier')
) t(iata_code, airline_name);

-- «локальные» рейсы в основной базе
CREATE TABLE flights AS
SELECT
    ['AA', 'BB', 'CC', 'DD'][1 + i % 4] AS airline,
    1000 + i AS flight_number
FROM range(0, 12) t(i);
```

### Шаг 2. Проверяем

```sql
SHOW DATABASES;
SELECT current_database() AS db, current_schema() AS schema_name;
SELECT count(*) AS n FROM cloud_db.ref.airlines;  -- ожидаем 3
```

### Шаг 3. Hybrid-запрос

```sql
SELECT f.airline, a.airline_name, count(*) AS flights
FROM flights AS f
LEFT JOIN cloud_db.ref.airlines AS a ON f.airline = a.iata_code
GROUP BY f.airline, a.airline_name
ORDER BY f.airline;
```

Проверка: для авиакомпании `DD` имени нет. Это `NULL`, потому что в справочнике её нет.

### Задания

1. Выберите `cloud_db.ref` как схему по умолчанию командой `USE` и прочитайте `airlines` без полного имени.
2. Создайте базу `scratch`, таблицу в ней, потом отключите базу командой `DETACH`.
3. Найдите рейсы без авиакомпании в справочнике.
4. Удалите схему `ref` вместе с таблицами.

<details>
<summary>Решение</summary>

```sql
-- 1. короткое имя после USE
USE cloud_db.ref;
SELECT count(*) AS n FROM airlines;
USE memory.main;

-- 2. своя база и DETACH
ATTACH ':memory:' AS scratch;
CREATE TABLE scratch.main.t AS SELECT 1 AS id;
DETACH scratch;

-- 3. рейсы без записи в справочнике (антиджойн)
SELECT f.*
FROM flights AS f
LEFT JOIN cloud_db.ref.airlines AS a ON f.airline = a.iata_code
WHERE a.iata_code IS NULL;

-- 4. схема удаляется только с CASCADE, если в ней есть таблицы
DROP SCHEMA cloud_db.ref CASCADE;
SELECT count(*) AS schemas_left FROM information_schema.schemata WHERE catalog_name = 'cloud_db' AND schema_name = 'ref';
```

Пункт 3 вернул 3 рейса компании `DD`. Последний запрос вернул 0: схемы больше нет.

</details>
