**Главная мысль:** Structured Streaming позволяет обрабатывать бесконечный поток теми же `DataFrame` и SQL, что и обычные таблицы. Поток здесь — это таблица, в которую всё время добавляют строки. Движок сам следит за отказоустойчивостью, `state` и опоздавшими данными.

## О чём глава

В [главе 7](/book-summaries/engineering/learning-spark/07-optimizing-and-tuning/) мы настраивали конечные batch-задачи. Теперь данные приходят без конца, и их нужно считать почти сразу. Глава объясняет, как те же structured API работают для потоков.

Темы главы:

- как Spark пришёл от `DStream` к `micro-batch` и к Structured Streaming;
- модель «поток как таблица» и три режима вывода (`output mode`);
- пять шагов, из которых строится потоковый запрос, и его перезапуск без потерь;
- источники и приёмники данных: файлы, Kafka и свой код записи;
- `stateful` агрегации, окна по `event time` и `watermark`;
- `stream-static join` и `stream-stream join`;
- произвольное состояние, `timeout` и настройка производительности.

![Схема: поток данных превращается во входную таблицу, запрос обновляет result table, результат уходит в sink](/assets/learning-spark/ch08-unbounded-table.png)

Новые записи — это новые строки входной таблицы. Запрос обновляет `result table`, а `trigger` решает, как часто это делать.

## Как Spark пришёл к Structured Streaming

### Две модели обработки потока

Потоковая обработка (`stream`) — это непрерывная обработка бесконечного потока данных. Когда данных стало слишком много для одного узла, такие системы стали распределёнными. Обычно они работают по модели `record-at-a-time`: граф узлов, где каждый узел берёт одну запись, обрабатывает её и передаёт следующему узлу.

Плюс модели — очень малая задержка, миллисекунды. Минус — тяжёлое восстановление. После сбоя узла или при медленном узле (`straggler`) приходится выбирать: либо держать много запасных ресурсов и восстанавливаться быстро, либо экономить и восстанавливаться медленно.

Spark ответил на это идеей `micro-batch`: поток режется на маленькие порции, например по секунде. Каждая порция обрабатывается как небольшое batch-задание из нескольких детерминированных `task`.

![Схема: традиционная модель передаёт записи по одной через узлы, а micro-batch режет поток на порции и запускает tasks](/assets/learning-spark/ch08-micro-batch.png)

Верхняя цепочка — `record-at-a-time`, нижняя — `micro-batch`. У нижней задержка больше, но восстановление проще.

У `micro-batch` два преимущества:

- Spark быстро перезапускает упавший `task` на любом другом `executor`. Медленный `executor` тоже не страшен: копию `task` запускают рядом.
- `Task` детерминированный, поэтому повторный запуск даёт тот же результат. Из этого следует `exactly-once` на всём пути: каждая входная запись влияет на результат ровно один раз.

Платим за это задержкой: обычно секунды, иногда полсекунды. Авторы считают, что большинству задач этого хватает:

- результат читает почасовое задание, и задержка меньше секунды ему не нужна;
- другие части конвейера уже добавляют задержку: например, датчик пишет в Kafka пачками.

Первый потоковый API Spark, `DStream` (Spark Streaming), строился на `RDD`, поэтому имел ту же семантику и отказоустойчивость. Так Spark Streaming показал, что один движок может дать общую семантику для batch, интерактивных запросов и потоков.

### Чему научил DStream

У старого API нашли три слабых места:

- **Нет единого API для batch и потока.** Операции у потокового и batch-API одинаковые, но классы разные. Чтобы превратить batch-задание в потоковое, код приходилось переписывать на другие классы.
- **Нет разделения логического и физического плана.** `DStream` выполняет операции в том порядке, в котором их написал разработчик. Фактически разработчик сам задаёт физический план, поэтому автоматической оптимизации нет, и код приходилось оптимизировать вручную.
- **Нет окон по `event time`.** `DStream` считал окна только по времени получения записи (`processing time`). Но часто нужно время создания записи (`event time`).

## Философия Structured Streaming

Центральная идея авторов: писать потоковый `pipeline` должно быть так же легко, как batch. Из неё следуют два принципа:

- **Единая модель и единый интерфейс.** К потоку применяют привычные `DataFrame` и SQL, как к batch. Отказоустойчивость, оптимизации и опоздавшие данные берёт на себя движок.
- **Более широкое определение потоковой обработки.** Граница между real-time и batch размылась. Поэтому в Structured Streaming должно укладываться любое приложение, которое обрабатывает данные от «раз в несколько часов» до «непрерывно».

## Модель программирования

Таблица — понятие, которое знает каждый разработчик batch-кода. Structured Streaming распространяет его на потоки: поток считается бесконечной таблицей (`unbounded table`), в которую добавляются строки. Каждая новая запись — это новая строка.

Движок не хранит весь вход. Но результат на момент T совпадает с тем, что дал бы batch-запрос по всей таблице данных до T.

Дальше разработчик описывает запрос к этой воображаемой таблице, как к обычной статичной. Из такого запроса получается `result table`. Spark превращает batch-запрос в потоковый план сам. Это называется `incrementalization`: Spark определяет, какой `state` нужно хранить, чтобы обновлять результат при каждой новой записи. Остаётся задать `trigger` — правило, когда проверять новые данные и обновлять результат.

Результат нужно записать во внешнюю систему: в файловую (HDFS, S3) или в базу (MySQL, Cassandra). Писать обычно хочется инкрементально, и для этого есть три режима вывода:

| Режим | Что записывается |
|---|---|
| `append` | Только новые строки `result table` с прошлого `trigger`. Годится, если уже записанные строки не меняются (например, `map` по входу) |
| `update` | Только строки, которые изменились с прошлого `trigger`. Нужен приёмник, который умеет обновлять строки, например таблица MySQL |
| `complete` | Вся `result table` целиком |

Если не выбран `complete`, Spark не хранит `result table` целиком. Он держит ровно столько информации (`state`), сколько нужно для вычисления изменений.

## Основы потокового запроса

### Пять шагов

На примере подсчёта слов в тексте разберём пять шагов. Книга читает текст из `socket`. Для воспроизводимости мы кладём файлы в папку, а запуск ограничиваем `trigger(availableNow=True)`: он обрабатывает всё, что уже есть, и останавливается.

> **Пояснение:** в книге есть режим `Trigger.Once`. В Spark 4 вместо него используют `availableNow`: он умеет резать работу на несколько `micro-batch`. Код ниже проверен на Spark 4.3.0.

**Шаг 1. Источник.** Для batch мы писали `spark.read`, для потока пишем `spark.readStream`. Он создаёт `DataStreamReader`, у которого почти те же методы. Как и `spark.read`, он ничего не читает, пока запрос не запущен. Spark сразу умеет читать `socket`, Kafka и файлы всех форматов `DataFrameReader` (Parquet, ORC, JSON). В одном запросе можно соединять несколько источников, потоковых и batch.

**Шаг 2. Преобразования.** Обычные операции `DataFrame`: разбить строки на слова и посчитать. Они делятся на два класса:

- `Stateless` — операции вроде `select`, `filter`, `map`. Строка обрабатывается сама по себе, память о прошлом не нужна. Работают одинаково на batch и потоке.
- `Stateful` — группировка, агрегация, `join`. Они требуют `state`, чтобы объединять строки разных `micro-batch`. Некоторые комбинации не поддерживаются: их нельзя считать инкрементально или это слишком дорого.

**Шаг 3. Приёмник и режим вывода.** Для записи есть `DataFrame.writeStream` и его `DataStreamWriter`. Режим вывода определяет, какую часть результата писать после каждой порции:

- `append` — режим по умолчанию. Он гарантирует: записанная строка больше не изменится. Поэтому он подходит только запросам, у которых выведенные строки не меняются, например `stateless`. Подсчёт слов может менять старые счётчики, поэтому `append` ему не подходит.
- `complete` — выводит все строки при каждом `trigger`. Это разумно, когда итог намного меньше входа и помещается в память. Для подсчёта слов подходит.
- `update` — выводит только изменённые строки. Его поддерживает большинство запросов.

Spark пишет потоки в файлы и в Kafka. Для остальных систем есть `foreachBatch` и `foreach`.

**Шаг 4. Детали обработки.** Здесь два вида настроек, и первый из них — `trigger`:

| Вариант `trigger` | Что делает |
|---|---|
| По умолчанию | Следующий `micro-batch` стартует, как только закончился предыдущий |
| `processingTime` с интервалом | `micro-batch` по фиксированному интервалу |
| `once` | Один `micro-batch` по всем новым данным, потом запрос останавливается. Подходит для внешнего планировщика, например раз в день ради экономии |
| `continuous` | Экспериментальный режим: данные идут непрерывно, задержка до миллисекунд, но поддерживает мало операций |

Второй вид — `checkpoint location`. Это папка в HDFS-совместимой файловой системе, где запрос хранит прогресс: какие данные уже обработаны. После сбоя запрос по ней продолжает с того же места. Без `checkpoint` нет восстановления с `exactly-once`.

**Шаг 5. Запуск.** `start()` не блокирует: запрос работает в фоне. `awaitTermination()` блокирует основной поток до остановки и повторяет исключение, если запрос упал. Остановить запрос можно через `stop()`.

Вот наш запуск в режимах `update` и `complete` для двух файлов (по файлу на `micro-batch`), затем попытка `append` и перезапуск с тем же `checkpoint`. Полный код: [ch08_wordcount.py](https://github.com/surfalytics/dataengineer_ru/blob/main/scripts/learning-spark-code/ch08_wordcount.py).

```python
lines = (spark.readStream.format("text")
         .option("maxFilesPerTrigger", 1).load(str(src)))   # один файл на micro-batch
words = lines.select(explode(split(col("value"), " ")).alias("word"))
counts = words.groupBy("word").count()

q = (counts.writeStream.foreachBatch(show_batch).outputMode("complete")
     .option("checkpointLocation", str(base / "ck_complete"))
     .trigger(availableNow=True).start())
q.awaitTermination()
```

Отличие режимов видно сразу. `update` во втором batch вывел только `hadoop`, `is`, `slow`, а `complete` — всю таблицу. `append` для агрегации без `watermark` Spark отклоняет. После перезапуска `batch 2` продолжил старые счётчики: `is=4`, `spark=3`.

### Что происходит внутри

После `start()` код `DataFrame` превращается в логический план — абстрактное описание вычисления. Дальше работает Spark SQL:

1. Spark SQL анализирует и оптимизирует план, чтобы его можно было выполнять инкрементально.
2. В фоне запускается цикл: по интервалу `trigger` поток проверяет, появились ли новые данные. Если да, запускается `micro-batch`: из оптимизированного плана строится план выполнения, который читает новые данные, инкрементально считает результат и пишет его в приёмник.
3. Для каждого `micro-batch` в `checkpoint` сохраняется точный диапазон данных (набор файлов или `offset` Kafka) и связанный `state`. Поэтому диапазон можно детерминированно обработать заново.
4. Цикл идёт, пока запрос не завершится. Причины: сбой, вызов `stop()`, или для `trigger once` — выполнен один `micro-batch`.

![Схема: цикл активного запроса из четырёх шагов: проверка trigger, поиск новых данных, micro-batch, сохранение в checkpoint](/assets/learning-spark/ch08-query-loop.png)

Схема показывает цикл фонового потока. Цикл работает для `micro-batch`, но не для `continuous`.

Важный вывод: внизу работает Spark SQL. Поэтому потоковые запросы получают те же оптимизации и ту же высокую пропускную способность, что и batch.

### Перезапуск и exactly-once

Чтобы перезапустить остановленный запрос в новом процессе, нужно создать новую `SparkSession`, заново определить все `DataFrame` и запустить запрос с тем же `checkpoint location`. В этой папке хранится уникальный идентификатор запроса: пока папка та же, это тот же запрос. Если её удалить или указать другую, получится новый запрос с нуля.

В `checkpoint` лежит информация на уровне записей (например, `offset` Kafka). Перезапущенный запрос продолжает точно после последнего завершённого `micro-batch`. Если предыдущий запрос спланировал порцию, но не закончил, он обработает тот же диапазон заново. В сочетании с детерминированными `task` вывод получится тем же, как если бы сбоя не было.

Сквозной `exactly-once` Structured Streaming гарантирует при трёх условиях:

- **Источник воспроизводимый** (`replayable source`): диапазон последнего незавершённого `micro-batch` можно перечитать.
- **Вычисления детерминированные:** одинаковый вход всегда даёт одинаковый результат.
- **Приёмник идемпотентный** (`idempotent sink`): он узнаёт повторно выполненный `micro-batch` и игнорирует дубли записи.

Пример со `socket` и `console` `exactly-once` не даёт: `socket` не воспроизводимый, а `console` не идемпотентный.

Между перезапусками запрос можно слегка менять:

- **Преобразования.** Например, добавить `filter`, который отбрасывает испорченные строки. После перезапуска фильтр применится ко всему, что обработано с момента перезапуска, включая последний неоконченный `micro-batch`.
- **Опции источника и приёмника.** Зависит от конкретного источника. Нельзя менять `host` и `port` у `socket`, но можно добавить опцию `numRows` для `console`.
- **Детали обработки.** `Checkpoint location` менять нельзя, а интервал `trigger` можно.

### Мониторинг

В production важно следить за здоровьем запроса. Есть три способа.

**`StreamingQuery`.** Метод `lastProgress()` возвращает информацию о последнем завершённом `micro-batch` (в Python — словарь). Важные поля:

| Поле | Что значит |
|---|---|
| `id` | Уникальный идентификатор, привязан к `checkpoint`. Не меняется при перезапусках |
| `runId` | Идентификатор текущего запуска. Меняется при каждом перезапуске |
| `numInputRows` | Сколько строк обработал последний `micro-batch` |
| `inputRowsPerSecond` | Скорость, с которой источник создаёт строки |
| `processedRowsPerSecond` | Скорость, с которой строки обрабатываются и пишутся. Если она постоянно ниже входной, запрос не успевает |
| `sources`, `sink` | Детали по источнику и приёмнику |

Метод `status()` показывает, что фоновый поток делает сейчас: например, «Waiting for data to arrive».

**Dropwizard Metrics.** Библиотека отдаёт метрики в Ganglia, Graphite и другие системы. Для Structured Streaming она по умолчанию выключена из-за большого объёма метрик: нужно поставить `spark.sql.streaming.metricsEnabled` в `true`. Публикуется только часть данных `lastProgress()`.

**`StreamingQueryListener`.** Это интерфейс с тремя событиями: запуск, прогресс (отработал `trigger`) и остановка. С ним можно публиковать метрики куда угодно. В книге этот API есть только в Scala и Java. В PySpark он есть с версии 3.4.

## Источники и приёмники

### Файлы

Structured Streaming читает файлы из папки как поток и пишет в те же форматы: текст, CSV, JSON, Parquet, ORC. Что важно при чтении:

- Все файлы одного формата и схемы. Иначе данные разберутся неправильно (например, в `null`) или запрос упадёт.
- Файл должен появляться в папке целиком и атомарно, и потом не меняться. Spark запоминает, что файл обработан, поэтому правки не увидит.
- Если за один `micro-batch` не получается взять все новые файлы (из-за лимита), Spark берёт файлы с самым ранним временем. Внутри `micro-batch` порядок не задан: файлы читаются параллельно.

У источника есть опции. Например, `maxFilesPerTrigger` ограничивает, сколько файлов берёт одна порция.

При записи в файлы работает только `append`: добавить файл в папку легко, а менять уже записанные данные трудно. Для `exactly-once` Spark ведёт журнал записанных файлов в подпапке `_spark_metadata`. Запрос Spark к папке читает журнал, поэтому не увидит дублей и недописанных файлов. Другие движки журнал могут не знать и гарантий не дадут. Если схема результата меняется между перезапусками, в папке окажутся данные в разных схемах.

### Kafka

Kafka — популярная система `publish/subscribe`, куда часто пишут потоки. Spark читает и пишет в неё напрямую. В `DataFrame` из Kafka такие колонки:

| Колонка | Тип | Что это |
|---|---|---|
| `key`, `value` | binary | Ключ и значение записи в байтах |
| `topic` | string | Топик (удобно при подписке на несколько) |
| `partition` | int | Номер `partition` топика Kafka |
| `offset` | long | Позиция записи |
| `timestamp`, `timestampType` | long, int | Время записи и его тип |

Можно подписаться на несколько топиков, на шаблон или на конкретную `partition`, читать только новое или всё доступное, и даже читать Kafka из batch-запроса как таблицу.

Для записи нужны колонки с определёнными именами: `value` (обязательна), `key` (необязательна), `topic` (нужна, если опция `topic` не задана). Писать можно во всех трёх режимах, но `complete` не советуют: он снова и снова выводит те же записи.

```python
# Не запускается: нужен брокер Kafka. Чтение и запись word count в Kafka.
inputDF = (spark.readStream.format("kafka")
           .option("kafka.bootstrap.servers", "host1:port1,host2:port2")
           .option("subscribe", "events").load())

streamingQuery = (counts
    .selectExpr("cast(word as string) as key", "cast(count as string) as value")
    .writeStream.format("kafka")
    .option("kafka.bootstrap.servers", "host1:port1,host2:port2")
    .option("topic", "wordCounts").outputMode("update")
    .option("checkpointLocation", checkpointDir).start())
```

### Свои источники и приёмники

Если для хранилища нет встроенной поддержки, есть два метода записи: `foreachBatch()` и `foreach()`. `foreach()` даёт свою логику записи для каждой строки, а `foreachBatch()` — для результата каждого `micro-batch`.

`foreachBatch()` принимает функцию с двумя параметрами: `DataFrame` с результатом порции и её уникальный номер (`batchId`). Он нужен, чтобы:

- **Использовать готовые batch-приёмники.** Книга пишет в Cassandra через batch-коннектор, потому что потоковой записи у коннектора версии 2.4.2 не было.
- **Писать в несколько мест.** Каждая запись может заново вычислить результат порции, вплоть до повторного чтения входа. Поэтому `DataFrame` сначала кэшируют (`persist`), пишут в нужные места и снимают кэш (`unpersist`).
- **Применять операции, которые на потоке не поддерживаются.** Но за сквозную семантику тогда отвечаете вы.

Важное предупреждение: `foreachBatch()` даёт только `at-least-once`. Чтобы получить `exactly-once`, используйте `batchId` для дедупликации повторных записей.

`foreach()` нужен, если batch-писателя нет. Логика делится на три метода: `open()`, `process()`, `close()`. Spark вызывает их для каждой `partition` результата. В Python `open()` и `close()` необязательны, а `process()` обязателен.

Официального способа читать из произвольного хранилища в книге нет: API своих источников (DataSourceV2) в Spark 3.0 ещё экспериментальный.

Ниже в одном скрипте: запись в файлы, `foreachBatch` в две папки с дедупликацией по `batchId`, `foreach` и `listener`. Полный код: [ch08_sinks.py](https://github.com/surfalytics/dataengineer_ru/blob/main/scripts/learning-spark-code/ch08_sinks.py).

```python
done = set()
def write_two(batch_df, batch_id):
    if batch_id in done:                    # повторный запуск micro-batch не пишем второй раз
        return
    batch_df.persist()                      # чтобы не считать batch два раза
    batch_df.write.mode("append").parquet(str(base / "loc1"))
    batch_df.write.mode("append").parquet(str(base / "loc2"))
    batch_df.unpersist()
    done.add(batch_id)

(source().writeStream.foreachBatch(write_two)
    .option("checkpointLocation", str(base / "ck2"))
    .trigger(availableNow=True).start().awaitTermination())
```

```text
file sink: 6 строк, журнал есть: True
foreachBatch: 6 6 строк в двух местах
foreach: [0, 1, 10, 11, 20, 21]
listener: ['started', 'progress rows=2', 'progress rows=2'] ... terminated | всего событий: True
```

## Преобразования данных

Spark SQL (`Catalyst`) переводит операции `DataFrame` в оптимизированный логический план. Если план потоковый, вместо одного физического плана строится непрерывная последовательность планов. Каждый план обновляет итог инкрементально: обрабатывает только новую порцию и, возможно, промежуточный результат предыдущего плана.

Каждое выполнение — это `micro-batch`, а промежуточный результат между ними называется `state`. Операции делятся на `stateless` и `stateful` по тому, нужен ли им `state`. Слишком дорогие или невозможные инкрементально операции не поддерживаются: `cube()` или `rollup()` бросят `UnsupportedOperationException`.

### Stateless

Проекции (`select`, `explode`, `map`, `flatMap`) и выборки (`filter`, `where`) обрабатывают запись сами по себе. Запрос только из таких операций поддерживает `append` и `update`, но не `complete`. Выведенная строка такого запроса никогда не изменится, поэтому его можно писать в любой приёмник, в том числе в файлы. Но такой запрос не объединяет записи и не уменьшает объём данных, и для `complete` пришлось бы хранить растущий без конца результат.

### Stateful

Самый простой пример — `groupBy().count()`: бегущий счётчик записей с начала запроса. В каждом `micro-batch` план добавляет счёт новых записей к счёту прошлого `micro-batch`. Это частичное значение и есть `state`. Он хранится в памяти `executor` и сохраняется в `checkpoint` на случай сбоя.

![Схема: два micro-batch группируют слова на executor, state хранится в памяти и записывается в checkpoint](/assets/learning-spark/ch08-state.png)

Каждый `micro-batch` читает новые слова, группирует их по ключу, считает и добавляет к бегущему счёту. Новый счёт — одновременно результат и `state` для следующего `micro-batch`. Следующая порция распределяет слова по узлам так же, как предыдущая. Поэтому каждое слово всегда попадает на один и тот же `executor` и читает свой счётчик локально.

Но хранить `state` только в памяти мало: при сбое `executor` или всего приложения он пропадёт. Поэтому изменения `state` синхронно пишутся в `checkpoint` как лог изменений. Они версионируются вместе с диапазонами данных. После сбоя Spark перечитывает лог, восстанавливает нужную версию `state` и повторяет порцию с тем же входом и тем же `state`. Результат получается тот же. Это важно для `exactly-once`.

Операции делятся по тому, кто чистит `state`:

- **Управляемые** (`managed`) — Spark сам находит и удаляет старый `state`. «Старое» определяется для каждой операции по-своему, и вы можете менять порог, чтобы управлять памятью. Сюда входят потоковые агрегации, `stream-stream join` и потоковая дедупликация.
- **Неуправляемые** (`unmanaged`) — вы пишете логику очистки сами. Сюда входят `mapGroupsWithState` и `flatMapGroupsWithState`. Они позволяют делать произвольные stateful операции, например сессионизацию.

## Stateful агрегации

Агрегировать можно по ключу (word count) и по времени (сколько записей за час).

### Агрегации без времени

Они бывают двух видов:

- **Глобальные** — по всему потоку. Например, бегущий счётчик показаний датчиков: `sensorReadings.groupBy().count()`.
- **Сгруппированные** — по ключу. Например, бегущее среднее по каждому датчику: `groupBy("sensorId").mean("value")`.

Нельзя использовать `DataFrame.count()` и `Dataset.reduce()` напрямую. На статичном `DataFrame` они сразу возвращают итог, а на потоке итог надо постоянно обновлять. Для потока всегда нужны `groupBy()` или `groupByKey()`.

Поддерживаются все встроенные агрегатные функции (`sum`, `mean`, `stddev`, `countDistinct`, `collect_set`, `approx_count_distinct`), несколько агрегатов сразу и пользовательские агрегатные функции (`UDAF`).

### Окна по event time

Часто нужны агрегаты по окнам времени, а не по всему потоку. Пример: каждый датчик шлёт не больше одного показания в минуту, и надо найти датчики, которые шлют слишком часто. Для этого считают показания каждого датчика в пятиминутных окнах. Окно надо строить по `event time` — моменту создания показания, — а не по моменту получения: иначе задержка в пути исказит результат.

Окно задаёт функция `window()`. Она создаёт динамически вычисляемую колонку для группировки:

```python
(sensorReadings.groupBy("sensorId", window("eventTime", "5 minute")).count())
```

Для каждого показания Spark вычисляет по `eventTime` окно, в которое оно попадает, группирует по паре (окно, `sensorId`) и обновляет счёт этой группы. События приходят позже и не по порядку, но каждое попадёт в свою группу, когда бы его ни обработали. Так поздние и неупорядоченные данные обрабатываются автоматически: они просто обновляют старые группы.

Окна `tumbling` не пересекаются. Для `sliding window` задают длину и шаг. Например, `window("eventTime", "10 minute", "5 minute")` — окна по 10 минут с шагом 5. Тогда каждое событие попадает в два окна: событие 12:07 увеличит счёт для (12:00–12:10) и для (12:05–12:15).

![Схема: событие 12:07 попадает в одно tumbling-окно и в два sliding-окна](/assets/learning-spark/ch08-windows.png)


### Watermark: поздние данные

С окнами по времени возникает проблема: `state` растёт бесконечно. Новые группы создаются, а старые ждут запоздавших данных. Запрос не знает, что данные не могут опоздать, скажем, больше чем на семь дней. Поэтому он не удаляет старые окна. Ограничить опоздание можно через `watermark`.

`Watermark` — это порог в `event time`, который идёт позади максимального `event time`, увиденного запросом. Расстояние между ними называется `watermark delay`: оно задаёт, сколько Spark ждёт запоздавших данных. Зная порог, после которого данных больше не будет, движок завершает агрегаты и убирает группы из `state`. Так объём `state` ограничен.

Если датчик не опаздывает больше чем на 10 минут, пишем:

```python
(sensorReadings
    .withWatermark("eventTime", "10 minutes")
    .groupBy("sensorId", window("eventTime", "10 minutes", "5 minutes"))
    .mean("value"))
```

`withWatermark()` вызывают до `groupBy()` и на той же колонке времени, по которой строятся окна. Запрос отслеживает максимум `eventTime`, обновляет `watermark`, отбрасывает слишком поздние данные и чистит старые окна.

![Схема: watermark равен максимальному event time минус delay; поздние события до порога отбрасываются, окна до порога закрываются](/assets/learning-spark/ch08-watermark.png)

`Watermark` для порции считается по максимальному `event time` из предыдущих порций. В нашем примере после порции с максимумом 12:15 `watermark` равен 12:05. Событие 12:13 пришло после события 12:15, но оно позже порога, и его посчитали. Событие 11:30 раньше порога, и его отбросили.

Автор уточняет гарантию. `Watermark` в 10 минут обещает, что Spark не отбросит данные, которые опоздали меньше чем на 10 минут относительно последнего `event time`. Но в обратную сторону гарантия не строгая: данные, опоздавшие больше, могут отбросить, а могут и учесть. Это зависит от того, когда пришла запись и когда запустился `micro-batch`. Чем больше `watermark delay`, тем позже данные можно принять, но тем больше `state` и памяти.

### Режимы вывода для окон

В отличие от агрегаций без времени, оконные агрегации работают во всех трёх режимах, но у каждого свои последствия для `state`:

- **`update`** — каждый `micro-batch` выводит только изменённые строки. Работает для всех агрегаций. С `watermark` `state` регулярно чистится. Это самый полезный и эффективный режим. Но его нельзя использовать для записи в приёмники только на добавление вроде Parquet и ORC (кроме Delta Lake, о нём в [главе 9](/book-summaries/engineering/learning-spark/09-reliable-data-lakes/)).
- **`complete`** — выводит все агрегаты независимо от возраста. `State` не чистится, даже если задан `watermark`: вывод всех агрегатов требует всего прошлого. Используйте с осторожностью: `state` и память могут расти без предела.
- **`append`** — работает только с окнами по `event time` и включённым `watermark`. Без `watermark` любой агрегат может измениться, поэтому вывести его в `append` нельзя. С `watermark` Spark знает, когда агрегат больше не изменится, и выводит окно один раз, уже финальным. Плюс — можно писать в файлы. Минус — вывод задерживается на длину `watermark`.

Запустим пример: файл — это один `micro-batch`, события приходят не по порядку, а 11:30 слишком старое.

```python
counts = (readings.withWatermark("eventTime", "10 minutes")
          .groupBy("sensorId", window("eventTime", "5 minutes")).count())
```

```text
=== update, окно 5 минут, watermark 10 минут
batch 0: id1 12:05-12:10 = 1; id2 12:05-12:10 = 1
batch 1: id1 12:10-12:15 = 1; id1 12:15-12:20 = 1
batch 2: id3 12:10-12:15 = 1
batch 3: id2 12:30-12:35 = 1
batch 4: id1 12:30-12:35 = 1
batch 5: -
=== append: окно выводится один раз, когда watermark его закрыл
batch 0: -
batch 1: -
batch 2: -
batch 3: -
batch 4: id1 12:05-12:10 = 1; id2 12:05-12:10 = 1; id1 12:10-12:15 = 1; id3 12:10-12:15 = 1; id1 12:15-12:20 = 1
batch 5: -
=== окно 10 минут, шаг 5: событие 12:07 попадает в два окна
id1 12:00-12:10 1
id1 12:05-12:15 1
```

В `batch 2` режима `update` нет записи 11:30: `watermark` её отбросил. Режим `append` молчал четыре порции, пока событие 12:30 не продвинуло `watermark` до 12:20. Тогда окна до 12:20 вышли по одному разу. Окна 12:30 ещё ждут. Полный код: [ch08_windows.py](https://github.com/surfalytics/dataengineer_ru/blob/main/scripts/learning-spark-code/ch08_windows.py).

## Потоковые join

Structured Streaming соединяет потоковый `Dataset` со статичным или с другим потоковым. Разберём пример с рекламой. Компания показывает рекламу на сайтах и зарабатывает на кликах. Показы (`impressions`) хранятся в одном месте, клики — в потоке событий. Чтобы посчитать доход от кликов, каждый клик надо сопоставить с показом.

### Stream-static join

Пусть таблица показов статичная, а клики идут потоком. Тогда достаточно обычного `inner join` по колонке `adId`: `clicksStream.join(impressionsStatic, "adId")`. Это тот же код, что для двух статичных `DataFrame`. Отличие только в `readStream` для потока. Каждый `micro-batch` кликов соединяется со статичной таблицей.

Поддерживаются и внешние join двух видов: левый, если поток слева, и правый, если поток справа. Остальные (например, `full outer` или левый с потоком справа) не поддерживаются, потому что их трудно считать инкрементально.

Что важно запомнить:

- `Stream-static join` — это `stateless` операция, `watermark` ей не нужен.
- Статичный `DataFrame` перечитывается для каждого `micro-batch`. Его можно закэшировать (`cache`) для скорости.
- Увидит ли запрос изменения данных, зависит от источника. Если статичный `DataFrame` построен на файлах, изменения не будут видны, пока запрос не перезапустят.

Предположение «таблица статична» нереалистично: новые показы появляются потоком. `Stream-static join` подходит для обогащения потока статичными или медленно меняющимися данными. Если оба источника быстро меняются, нужен `stream-stream join`.

### Stream-stream join

Сложность в том, что в любой момент оба набора неполны. Событие и его пара приходят в любом порядке и с произвольной задержкой. Например, показ и клик по нему могут прийти не по порядку и с большим интервалом. Spark буферизует вход обеих сторон как `state` и непрерывно ищет совпадения.

![Схема: показы и клики записываются в буферы state, join сопоставляет их по adId и условию времени](/assets/learning-spark/ch08-join-state.png)

Буферы — это `state`. Они хранят события, пока для них ещё возможна пара.

**Inner join.** Код тот же: `impressions.join(clicks, "adId")`, но выполнение совсем другое. Spark сам распознаёт `stream-stream join`, буферизует показы и клики и выдаёт пару, как только пришёл клик к показу в буфере (или наоборот).

Но в таком коде не сказано, сколько ждать совпадения, и `state` растёт бесконечно. Нужны ответы на два вопроса:

- Сколько времени максимум может пройти между созданием двух событий? В примере клик возможен через 0–1 час после показа.
- На сколько событие может задержаться в пути? В примере показ — до двух часов, клик — до трёх.

Эти ограничения кодируются так: `watermark` на каждом входе плюс условие по времени (диапазон времени в условии join или равенство окон). Код получается таким:

```python
impressions = (stream("impressions", "impressionTime")
               .selectExpr("adId AS impressionAdId", "impressionTime")
               .withWatermark("impressionTime", "2 hours"))
clicks = (stream("clicks", "clickTime")
          .selectExpr("adId AS clickAdId", "clickTime")
          .withWatermark("clickTime", "3 hours"))
cond = expr("""clickAdId = impressionAdId AND
               clickTime BETWEEN impressionTime AND impressionTime + interval 1 hour""")
impressions.join(clicks, cond, "inner")        # или "leftOuter"
```

Из этих ограничений Spark сам вычисляет, как долго хранить события:

- Показ хранится не больше четырёх часов: клик с трёхчасовым опозданием может прийти к показу четырёхчасовой давности (3 часа опоздания плюс до часа между показом и кликом).
- Клик хранится не больше двух часов: показ может опоздать на два часа.

Для `inner join` `watermark` и условие по времени необязательны, но очистка `state` работает, только если заданы оба. Гарантия та же, что для агрегаций: данные с опозданием меньше задержки не потеряются, более поздние могут и не обработаться.

**Outer join.** `Inner join` выводит только показы, у которых был клик. Чтобы получить все показы, с кликом или без (например, для расчёта доли кликов), нужен `outer join`. Достаточно указать тип join: `"leftOuter"`.

Здесь есть отличия:

- `Watermark` и условие по времени обязательны. Чтобы вывести `NULL`, Spark должен знать, что событие больше ни с чем не совпадёт.
- Поэтому строки с `NULL` выходят с задержкой: движок ждёт то максимальное время хранения, которое он вычислил (четыре часа для показов и два для кликов).

Запуск нашего примера: показы и клики идут по одному файлу на `micro-batch`. Показ `a2` без клика появляется в `leftOuter` только в `batch 4`, когда `watermark` ушёл достаточно далеко. Полный код: [ch08_joins.py](https://github.com/surfalytics/dataengineer_ru/blob/main/scripts/learning-spark-code/ch08_joins.py).

```text
=== stream-static join: обогащаем клики
batch 0: a1 12:20 Acme
batch 1: a3 13:30 Globex
batch 2: a4 15:20 Initech
batch 3: a5 18:10 Globex
=== stream-stream join: inner
batch 0: impression a1@12:00 + click a1@12:20
batch 1: impression a3@13:00 + click a3@13:30
batch 2: impression a4@15:00 + click a4@15:20
batch 3: impression a5@18:00 + click a5@18:10
batch 4: -
=== stream-stream join: leftOuter
batch 0: impression a1@12:00 + click a1@12:20
batch 1: impression a3@13:00 + click a3@13:30
batch 2: impression a4@15:00 + click a4@15:20
batch 3: impression a5@18:00 + click a5@18:10
batch 4: impression a2@12:05 + click None@None
```

## Произвольные stateful вычисления

Бывают задачи сложнее SQL. Например, нужно отслеживать статус пользователя (вошёл, занят, неактивен) по его событиям (клики). Тогда для каждого пользователя хранится история с произвольной структурой, и к ней применяются сложные изменения. Для этого есть `mapGroupsWithState()` и более гибкий `flatMapGroupsWithState()`. В книге (Spark 3.0) они доступны только в Scala и Java.

> **Пояснение:** в PySpark 3.4 появился `applyInPandasWithState`, а в Spark 4.0 — `transformWithStateInPandas`. Ниже показан `applyInPandasWithState`. Ему нужен PyArrow версии 18 и выше. В нашем образе стоит 17.0.0, поэтому код запускали с PyArrow 19.

### mapGroupsWithState

Состояние с произвольной схемой и произвольные преобразования задаются пользовательской функцией. Она получает прежнее значение `state` и новые данные, а возвращает новое `state` и результат. В Scala её сигнатура принимает `key` (ключ), `newDataForKey` (итератор новых данных) и `previousStateForKey` (обёртку `GroupState` над `state`) и возвращает значение типа `U`. Типы ключа, входа, `state` и результата должны поддерживаться `encoder` Spark SQL.

Spark вызывает функцию в каждом `micro-batch` для каждого ключа, у которого есть новые данные. Для примера со статусом пользователя нужно три шага. Сначала выбрать типы: вход `UserAction`, ключ `userId`, `state` и результат `UserStatus`. Затем написать функцию: взять прежний `state` или создать, применить новые события, обновить `state` и вернуть статус. В конце сгруппировать события через `groupByKey()` и применить функцию.

Важные детали:

- Порядок записей в итераторе не определён. Если порядок важен, сортируйте сами по `event time`. Если записи могут прийти из источника не по порядку, будущий `micro-batch` может принести данные, которые надо было обработать раньше. Тогда записи придётся буферизовать в `state`.
- Функция вызывается для ключа только когда в `micro-batch` есть данные по нему. Если пользователь молчит давно, функции для него не будет. Для таких случаев нужны `timeout`.
- Результат `mapGroupsWithState()` движок считает обновляемыми парами ключ-значение, как у агрегаций. Из-за этого допустимы не все операции и приёмники: например, нельзя писать `append` в файлы. Больше свободы даёт `flatMapGroupsWithState()`.

### Timeout для неактивных ключей

Если пользователей становится больше, растёт число ключей в `state` и память. Неактивных пользователей хранить незачем. Но неактивность — это отсутствие событий в течение порога, а функция для такого ключа не вызывается. Для этого есть `timeout`:

- При каждом вызове функции для ключа задают `timeout` (длительностью или временной отметкой).
- Если новых данных нет и условие выполнено, ключ помечается как «`timed out`». Следующий `micro-batch` вызовет функцию для него, даже без данных. В этом вызове итератор пуст, а `GroupState.hasTimedOut()` возвращает `true`.

Две версии `timeout` соответствуют двум видам времени:

- **`Processing-time`** — по системным часам машины. Если ключ получил данные в момент T, а сейчас больше T плюс срок, функция вызывается с пустым итератором.
- **`Event-time`** — по `event time` в данных и `watermark`. Ключ истекает, когда `watermark` превысит заданную отметку T. `Watermark` идёт вперёд в темпе обработки данных, поэтому сбои и задержки обработки не вызывают ложных срабатываний.

Что нужно помнить:

- `Timeout`, поставленный прошлым вызовом, отменяется при следующем вызове. Поэтому его надо задавать при каждом вызове.
- `Timeout` срабатывает внутри `micro-batch`, поэтому он неточен и зависит от интервала `trigger`. Для точного управления временем не подходит.
- `Processing-time timeout` нестоек к простоям. Если запрос стоял больше часа, после перезапуска истекут сразу все ключи. То же при отставании от источника (скажем, данные копятся в Kafka).
- У `event-time timeout` задают временную отметку, а не длительность. Отметка должна быть больше текущего `watermark`.

Наш пример: `event-time timeout` в один час, ключ — пользователь, `state` — счётчик событий.

```python
def update_status(key, pdf_iter, state):
    user = key[0]
    if state.hasTimedOut:                       # данных нет, но пора убрать состояние
        (n,) = state.get
        state.remove()
        yield pd.DataFrame({"userId": [user], "status": ["inactive"], "actions": [n]})
        return
    n = state.get[0] if state.exists else 0     # прошлое состояние, если оно есть
    last = None
    for pdf in pdf_iter:
        n += len(pdf)
        last = pdf["eventTime"].max() if last is None else max(last, pdf["eventTime"].max())
    state.update((n,))
    state.setTimeoutTimestamp(int(last.timestamp() * 1000) + ONE_HOUR_MS)
    yield pd.DataFrame({"userId": [user], "status": ["active"], "actions": [n]})

result = (actions.groupBy("userId")
          .applyInPandasWithState(update_status, out_schema, state_schema,
                                  "append", GroupStateTimeout.EventTimeTimeout))
```

```text
batch 0: u1 active (1); u2 active (1)
batch 1: u1 active (2)
batch 2: u3 active (1)
batch 3: u4 active (1)
batch 4: u1 inactive (2); u2 inactive (1)
```

Пользователи `u1` и `u2` перестали присылать события. Когда `u4` в 14:00 продвинул `watermark`, у них истёк `timeout`, и функция вернула `inactive`. Полный код: [ch08_state.py](https://github.com/surfalytics/dataengineer_ru/blob/main/scripts/learning-spark-code/ch08_state.py).

### flatMapGroupsWithState

У `mapGroupsWithState()` два ограничения для сложных задач (например, цепочки сессионизаций):

- Функция всегда возвращает ровно одну запись. Иногда в некоторых `trigger` вывод не нужен.
- Движок не знает, что внутри функции, и считает результат обновляемыми парами ключ-значение. Поэтому он запрещает часть операций, например `append` в файлы.

`flatMapGroupsWithState()` снимает оба ограничения ценой чуть более сложного синтаксиса:

- Он возвращает итератор: можно вернуть любое число записей или ни одной.
- Он принимает ещё `operator output mode` — не путать с режимом вывода запроса. Он говорит, что выводимые записи — это новые строки для добавления (`OutputMode.Append`) или обновления пар ключ-значение (`OutputMode.Update`).

Например, если надо генерировать оповещения только для некоторых изменений и писать их в файлы, используют `flatMapGroupsWithState` с `OutputMode.Append`.

## Настройка производительности

Structured Streaming работает на Spark SQL, поэтому подходят те же параметры, что в главах 5 и 7. Но `micro-batch` обычно обрабатывает намного меньше данных, чем batch. Поэтому кластер для потоков настраивают немного иначе:

- **Ресурсы кластера.** Потоковый кластер работает круглосуточно, и ресурсы надо подбирать точно. Если их мало, запрос отстаёт: порции занимают всё больше времени. Если много, деньги тратятся впустую. Запросам `stateless` обычно нужно больше ядер, а `stateful` — больше памяти.
- **Число `partition` для `shuffle`.** Для потоков его ставят заметно меньше, чем для batch: слишком мелкое деление увеличивает накладные расходы. У `stateful` операций накладные расходы на `task` из-за `checkpoint` ещё выше. Для `stateful` запросов с `trigger` в секунды или минуты советуют снизить значение по умолчанию 200 до числа, которое не больше чем в 2–3 раза превышает число выделенных ядер.
- **Лимиты скорости источника.** Внезапный всплеск данных может создать огромное задание и нестабильность. Вместо дорогого запаса ресурсов ставят лимиты на источнике (Kafka, файлы). Всплеск остаётся в источнике, запрос потом догонит. Но слишком низкий лимит оставляет ресурсы без дела. Кроме того, лимит не спасает от долгого роста входа: данные в источнике будут копиться бесконечно, а вместе с ними вырастет сквозная задержка.
- **Несколько запросов в одном приложении.** Они делят между собой ресурсы кластера, но каждый запрос постоянно занимает ресурсы `driver`. Это ограничивает число запросов: можно упереться в планирование `task` или в память. Для более честного распределения запросам задают разные `scheduler pool`: перед стартом каждого запроса вызывают `spark.sparkContext.setLocalProperty("spark.scheduler.pool", "pool1")`, для следующего — `"pool2"`.

## Итоги главы

- Structured Streaming строит потоковые запросы на тех же `DataFrame` и SQL, что и batch, а `pipeline` для потока пишется так же просто.
- Поток — это бесконечная таблица, а результат запроса на момент T равен результату batch-запроса по всем данным до T.
- Запрос задаётся пятью шагами: источник, преобразования, приёмник с режимом вывода, детали обработки (`trigger` и `checkpoint`) и запуск.
- Сквозной `exactly-once` требует `replayable source`, детерминированных вычислений и идемпотентного приёмника, а перезапуск требует прежнего `checkpoint location`.
- Для записи в произвольные системы есть `foreachBatch` (даёт `at-least-once`, `exactly-once` строится по `batchId`) и `foreach`.
- Агрегации по `event time` используют окна, а `watermark` ограничивает `state` и решает, какие поздние данные принимать.
- Режим `append` для окон работает только с `watermark`, а `complete` не чистит `state` и опасен для памяти.
- `Stream-static join` не хранит `state`, а `stream-stream join` буферизует обе стороны, и для очистки ему нужны `watermark` и условие по времени. Для `outer join` они обязательны.
- Для произвольного состояния есть `mapGroupsWithState` и `flatMapGroupsWithState`, а `timeout` убирает неактивные ключи.
- Для потоков число `shuffle partition`, лимиты источника и `scheduler pool` настраивают иначе, чем для batch.

## Ключевые термины

| Термин | Значение |
|---|---|
| `micro-batch` | Маленькая порция потока, которую Spark обрабатывает как небольшое batch-задание |
| `DStream` | Старый потоковый API Spark Streaming на базе `RDD` |
| `unbounded table` | Модель: поток — это таблица, в которую всё время добавляют строки |
| `incrementalization` | Превращение batch-запроса в запрос, который обновляет результат по новым данным |
| `output mode` | Что писать после каждого `trigger`: `append`, `update` или `complete` |
| `trigger` | Правило, когда проверять новые данные и запускать `micro-batch` |
| `checkpoint` | Сохранённый прогресс и `state` запроса. Нужен для перезапуска |
| `exactly-once` | Эффект ровно один раз при повторах |
| `stateful` / `stateless` | Операция с памятью между `micro-batch` / без памяти |
| `event time` / `processing time` | Когда событие случилось / когда его обработали |
| `watermark` | Порог позади максимального `event time`: старые данные отбрасывают, старый `state` удаляют |
| `tumbling window` / `sliding window` | Окна без пересечений / окна с шагом меньше длины |
| `stream-static join` / `stream-stream join` | Join потока со статичной таблицей / с другим потоком |
| `foreachBatch` / `foreach` | Методы записи результата в произвольное хранилище |
| `timeout` | Срок, после которого `state` ключа считается устаревшим |
| `scheduler pool` | Отдельная очередь `task` для запроса, чтобы запросы делили ресурсы честно |

## Что это значит на практике

- Для почти любого потока хватает `micro-batch`. Задержка в секунды обычно не важна: другие части конвейера добавляют свою, например запись в Kafka пачками.
- Всегда задавайте `checkpoint location` и не меняйте его между перезапусками. Без него нет восстановления.
- Для окон и `stream-stream join` ставьте `watermark`. Без него `state` растёт без предела, и рано или поздно запрос упадёт из-за нехватки памяти.
- При записи через `foreachBatch` дедуплицируйте по `batchId`, иначе при повторе порции получите дубли.
- Файловые приёмники пишут только `append`. Если нужно обновлять строки, смотрите Delta Lake в [следующей главе](/book-summaries/engineering/learning-spark/09-reliable-data-lakes/).
- Число `shuffle partition` для потока ставьте близко к числу ядер, а не 200 по умолчанию.

## Практика в DuckDB

Запустите `duckdb` в терминале или откройте [shell.duckdb.org](https://shell.duckdb.org). Блоки идут по порядку. Идеи этой главы — окна по `event time`, `watermark` и бегущий `state` — можно повторить обычным SQL. Каждая строка таблицы — событие, а `batch` — номер `micro-batch`, в котором оно пришло.

### Шаг 1. Создаём события

```sql
CREATE TABLE readings AS
SELECT * FROM (VALUES
  (0, 'id1', TIMESTAMP '2026-01-01 12:07:00'),
  (0, 'id2', TIMESTAMP '2026-01-01 12:08:00'),
  (1, 'id1', TIMESTAMP '2026-01-01 12:11:00'),
  (1, 'id1', TIMESTAMP '2026-01-01 12:15:00'),
  (2, 'id3', TIMESTAMP '2026-01-01 12:13:00'),
  (2, 'id1', TIMESTAMP '2026-01-01 11:30:00'),
  (3, 'id2', TIMESTAMP '2026-01-01 12:30:00')
) t(batch, sensor_id, event_time);
```

### Шаг 2. Проверяем

```sql
SELECT count(*) AS rows_total, count(DISTINCT batch) AS batches FROM readings;
```

Должно получиться 7 строк и 4 `batch`.

### Задания

**Задание 1.** Посчитайте события каждого датчика в `tumbling` окнах по 5 минут по `event time`. Подсказка: `time_bucket(INTERVAL 5 MINUTE, event_time)`.

<details>
<summary>Решение</summary>

```sql
SELECT sensor_id,
       time_bucket(INTERVAL 5 MINUTE, event_time) AS window_start,
       count(*) AS cnt
FROM readings
GROUP BY ALL
ORDER BY window_start, sensor_id;
```

Окно выбирает `event_time`, а не номер `batch`. Событие 11:30 уходит в старое окно 11:30, хотя пришло в `batch` 2.

</details>

**Задание 2.** Для каждого `batch` посчитайте `watermark` с задержкой 10 минут: максимум `event_time` по всем предыдущим `batch` минус 10 минут. Пометьте событие как `accepted`, если оно не раньше `watermark`.

<details>
<summary>Решение</summary>

```sql
WITH batch_max AS (
  SELECT batch, max(event_time) AS max_event_time FROM readings GROUP BY batch
), wm AS (
  SELECT batch,
         max(max_event_time) OVER (ORDER BY batch ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING)
           - INTERVAL 10 MINUTE AS watermark
  FROM batch_max
)
SELECT r.batch, r.sensor_id, r.event_time, w.watermark,
       coalesce(r.event_time >= w.watermark, true) AS accepted
FROM readings r JOIN wm w USING (batch)
ORDER BY r.batch, r.event_time;
```

В `batch` 2 `watermark` равен 12:05, поэтому событие 11:30 получает `accepted = false`, а 12:13 принято. В `batch` 0 `watermark` пока нет, и всё принимается.

</details>

**Задание 3.** Эмулируйте `state` и режим `update`: для каждого `batch` выведите только датчики, чей счётчик изменился, с бегущим числом принятых событий.

<details>
<summary>Решение</summary>

```sql
WITH batch_max AS (
  SELECT batch, max(event_time) AS max_event_time FROM readings GROUP BY batch
), wm AS (
  SELECT batch,
         max(max_event_time) OVER (ORDER BY batch ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING)
           - INTERVAL 10 MINUTE AS watermark
  FROM batch_max
), accepted AS (
  SELECT r.* FROM readings r JOIN wm w USING (batch)
  WHERE coalesce(r.event_time >= w.watermark, true)
), per_batch AS (
  SELECT batch, sensor_id, count(*) AS new_events FROM accepted GROUP BY ALL
)
SELECT batch, sensor_id,
       sum(new_events) OVER (PARTITION BY sensor_id ORDER BY batch) AS running_count
FROM per_batch
ORDER BY batch, sensor_id;
```

Строка есть только у датчика, который получил новые события в этом `batch`. Это и есть `update`. Бегущая сумма — это `state`. Событие 11:30 в счёт не вошло.

</details>
