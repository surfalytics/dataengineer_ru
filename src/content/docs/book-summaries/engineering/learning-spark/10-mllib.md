**Главная мысль:** в `spark.ml` вся работа с моделью строится из двух видов шагов: `transformer` меняет `DataFrame`, а `estimator` учится на нём. Из них собирают `Pipeline`, а гиперпараметры подбирают через `cross-validation`. Так подготовка данных и обучение остаются в одном движке и масштабируются вместе с данными.

До сих пор книга говорила о задачах data engineering. Но подготовка данных обычно идёт перед машинным обучением (ML), поэтому в этой главе мы строим модели. Глава продолжает [главу 9 про озёра данных](/book-summaries/engineering/learning-spark/09-reliable-data-lakes/): чистые данные из озера становятся входом для модели. Темы: виды ML, пакеты `spark.mllib` и `spark.ml`, `transformer`, `estimator` и `Pipeline`, `one-hot encoding`, метрики, деревья и `random forest`, подбор гиперпараметров. Следующая [глава 11](/book-summaries/engineering/learning-spark/11-ml-pipelines/) покажет, как запускать и масштабировать такие `ML pipeline`.

![Схема: Pipeline учится на trainDF и становится PipelineModel, который применяют к новым данным](/assets/learning-spark/ch10-pipeline.png)

Слева обучающие данные проходят шаги `Pipeline` (метод `fit`). Результат — `PipelineModel`: он принимает новые данные и добавляет колонку `prediction` (метод `transform`).

Книга показывает код на Scala и Python. Здесь только PySpark, а Scala отличается лишь синтаксисом. Весь код мы запускали на Spark 4.3.0, как описано в [главе 1](/book-summaries/engineering/learning-spark/01-intro-to-spark/).

## Что такое машинное обучение

Машинное обучение (ML) — это способ находить закономерности в данных с помощью статистики, линейной алгебры и численной оптимизации. Так предсказывают потребление электричества, ищут кошек на видео или группируют похожие товары. Книга приводит оценку McKinsey: 35% покупок на Amazon и 75% просмотров на Netflix идут из рекомендаций моделей. Бывает обучение с учителем, без учителя, частичное и с подкреплением. Глава в основном о первом и немного о втором.

### Обучение с учителем

В обучении с учителем (`supervised learning`) у каждой записи есть метка (`label`). Цель — предсказать метку для новой записи. Метка бывает двух видов, поэтому и задач две:

- **Классификация** делит записи на классы. Если классов два («собака» или «не собака»), это бинарная классификация. Если три и больше (порода собаки), это мультиклассовая.
- **Регрессия** предсказывает непрерывное число. Например, продажи мороженого по температуре. Модель может выдать $77,67, хотя такого значения не было ни в одной обучающей паре.

Таблица показывает популярные алгоритмы `MLlib` и то, для каких задач они подходят.

| Алгоритм | Задача |
|---|---|
| Linear regression | Регрессия |
| Logistic regression | Классификация (несмотря на «regression» в названии) |
| Decision trees, gradient boosted trees, random forests | Обе |
| Naive Bayes, support vector machines (SVM) | Классификация |

### Обучение без учителя

Размеченные данные дороги, а иногда их просто нет. Тогда помогает обучение без учителя (`unsupervised learning`). Оно не предсказывает метку, а показывает структуру данных. Например, `k-means` находит в облаке точек естественные кластеры. Ещё его используют для поиска выбросов и для уменьшения числа измерений перед обучением с учителем. В `MLlib` есть `k-means`, Latent Dirichlet Allocation (LDA) и Gaussian mixture models.

## Зачем Spark для ML

Spark — единый движок: приём данных, `feature engineering`, обучение и запуск модели живут в одном месте. Без него пришлось бы собирать много разных инструментов, и всё равно были бы проблемы с масштабом. У Spark два ML-пакета:

- `spark.mllib` — старый API на `RDD`. Он в режиме поддержки с Spark 2.0.
- `spark.ml` — новый API на `DataFrame`. Остальная глава про него.

Словом «MLlib» книга называет оба пакета вместе. В `spark.ml` специалист по данным готовит данные и строит модель в одной среде и не режет данные до размера одной машины. Модель масштабируется линейно с числом записей: это `O(n) scale-out`. Если вы знаете `scikit-learn`, многие API покажутся знакомыми, но есть тонкие отличия. Компромисс между распределённой и одномашинной библиотекой книга разбирает в главе 11.

## Проектирование ML pipeline

`Pipeline` организует цепочку операций над данными. Идея общая для многих ML-фреймворков, а в `MLlib` это высокоуровневый API поверх `DataFrame`. В главе на примере предсказывают цену за ночь аренды жилья в Сан-Франциско (данные Inside Airbnb: спальни, район, оценки и так далее). Цена — непрерывная величина, значит, это регрессия. Данные неряшливые, так что слабые первые модели — это нормально.

### Термины MLlib

| Термин | Что делает |
|---|---|
| `transformer` | Принимает `DataFrame`, возвращает новый с добавленными колонками. Ничего не учит, применяет правила. Метод `transform()` |
| `estimator` | Учит параметры на `DataFrame` методом `fit()` и возвращает модель. Модель — это `transformer` |
| `Pipeline` | Собирает `transformer` и `estimator` в одну цепочку. Сам он `estimator`, а результат `fit()` (`PipelineModel`) — `transformer` |

### Данные и разбиение на train и test

Авторы заранее убрали выбросы (аренда за $0), перевели целые числа в `double` и выбрали часть из более чем ста полей. Пропуски в числовых колонках заменили медианой и добавили колонку-флаг (`bedrooms_na`). Так модель или аналитик отличит подставленное значение от настоящего.

Перед моделью данные делят на `train` и `test`. Обычно берут 80/20. Нельзя обучать на всех данных: модель может просто запомнить обучающие записи (это называют переобучением), и тогда нечем будет проверить, как она работает на новых. Качество на `test` — оценка того, что будет в продакшене, если распределение данных то же. Обучающие признаки — матрица `X` размером `n x d` (`n` записей, `d` признаков), метки — вектор `y` длиной `n`. Для классификации частая метрика — `accuracy`, доля верных ответов.

Здесь и дальше мы работаем на своих сгенерированных данных: 400 объявлений с колонками `hood`, `room_type`, `bedrooms`, `price`. Поэтому числа ниже отличаются от книги. Разбиение:

```python
train, test = df.randomSplit([.8, .2], seed=42)
print(f"train={train.count()}, test={test.count()}")
```

```text
train=332, test=68
```

`seed` нужен для воспроизводимости. Но если изменится число `executor`, `Catalyst` может иначе разложить строки по `partition`. Каждый worker делит свои строки независимо от других, поэтому тот же `seed` даст другое разбиение. Авторы советуют один раз разбить данные и записать `train` и `test` в отдельные папки. Пока вы исследуете данные, `train` стоит закэшировать (`cache`), потому что к нему будут много раз обращаться.

### Признаки: Transformer

Линейная регрессия, как и многие алгоритмы Spark, требует, чтобы все признаки лежали в одной колонке-векторе. Это делает `VectorAssembler`: берёт список колонок и добавляет колонку `features`.

```python
va1 = VectorAssembler(inputCols=["bedrooms"], outputCol="features")
va1.transform(train).select("bedrooms", "features", "price").orderBy("price", "bedrooms").show(3)
```

```text
+--------+--------+-----+
|bedrooms|features|price|
+--------+--------+-----+
|     1.0|   [1.0]| 49.9|
|     1.0|   [1.0]| 61.8|
|     1.0|   [1.0]| 66.1|
+--------+--------+-----+
only showing top 3 rows
```

В Scala у `VectorAssembler` параметры задают только сеттерами. В Python можно передать их в конструктор или тоже сеттерами.

### Линейная регрессия и Estimator

Линейная регрессия моделирует линейную связь между метками (зависимая переменная) и признаками. Для одного признака это прямая `y = mx + b`, где `m` — наклон, `b` — сдвиг. Точки не лежат на прямой, поэтому модель такая: `y ≈ mx + b + ε`, где `ε` — ошибка (остаток). Линия подбирается так, чтобы сумма квадратов остатков была минимальной. С тремя признаками у каждого свой вес: `y ≈ w0 + w1x1 + w2x2 + w3x3 + ε`. Поиск весов и сдвига называют обучением (fitting).

`LinearRegression` — это `estimator`: он берёт `DataFrame` и возвращает модель. `fit()` сразу запускает `job` (он энергичный), а `transform()` вычисляется лениво. Другие `estimator` — `Imputer`, `DecisionTreeClassifier`, `RandomForestRegressor`.

```python
lr = LinearRegression(featuresCol="features", labelCol="price")
lr_model = lr.fit(va1.transform(train))
print(f"price = {lr_model.coefficients[0]:.2f}*bedrooms + {lr_model.intercept:.2f}")
```

```text
price = 70.38*bedrooms + 99.19
```

Результат `fit()` — `LinearRegressionModel`, и он `transformer`. Он применяет выученные параметры к новым данным.

### Pipeline

Чтобы применить модель к `test`, его надо подготовить так же, как `train`. Шагов часто несколько, и легко забыть порядок. `Pipeline` решает это: вы перечисляете шаги по порядку, а Spark сам вызывает на каждом `fit` или `transform`. Это ещё и наводит порядок в коде, и позволяет использовать шаги повторно.

```python
pm = Pipeline(stages=[va1, lr]).fit(train)
pm.transform(test).select("bedrooms", "price", "prediction").orderBy("price", "bedrooms").show(3)
```

```text
+--------+-----+-----------------+
|bedrooms|price|       prediction|
+--------+-----+-----------------+
|     1.0| 55.7|169.5733876293201|
|     1.0| 60.6|169.5733876293201|
|     1.0| 78.8|169.5733876293201|
+--------+-----+-----------------+
only showing top 3 rows
```

Все объявления с одной спальней получили один прогноз: модель знает только `bedrooms`.

### One-hot encoding

Чтобы использовать все признаки, нужны и категориальные: у них конечный набор значений без порядка (профессия, страна). Большинство моделей `MLlib` ждут числа. Простая нумерация «Dog = 1, Cat = 2, Fish = 3» вносит ложную связь: выходит, что Cat вдвое больше Dog. Поэтому делают `one-hot encoding` (OHE): для каждого значения своя колонка, и в ней стоит 1 или 0. В `pandas` то же делает `get_dummies()`.

![Схема: StringIndexer, OneHotEncoder и VectorAssembler превращают строку в вектор, а нумерация животных 1, 2, 3 вводит ложный порядок](/assets/learning-spark/ch10-ohe.png)

Сверху три шага `MLlib`, снизу идея OHE и плохая нумерация.

Хватит ли памяти на 300 колонок для 300 животных? Хватит: Spark хранит такие векторы как `SparseVector`, если почти все значения нули. Он помнит размер вектора, индексы ненулевых элементов и сами значения. Вектор из 10 элементов, где на местах 3 и 5 стоят 7 и 2, — это `SparseVector(10, [3, 5], [7, 2])`.

Обычный путь — `StringIndexer`, потом `OneHotEncoder`:

- `StringIndexer` (он `estimator`) превращает категории в индексы. Самая частая категория получает индекс 0, поэтому результат повторяется от запуска к запуску.
- `OneHotEncoder` превращает индексы в бинарные векторы. В Spark 3.0 он принимает сразу несколько колонок, а старый `OneHotEncoderEstimator` из Spark 2.3 и 2.4 убрали.

```python
cat_cols = [f for f, t in train.dtypes if t == "string"]
idx_cols = [c + "Index" for c in cat_cols]
ohe_cols = [c + "OHE" for c in cat_cols]
indexer = StringIndexer(inputCols=cat_cols, outputCols=idx_cols, handleInvalid="skip")
ohe = OneHotEncoder(inputCols=idx_cols, outputCols=ohe_cols)
num_cols = [f for f, t in train.dtypes if t == "double" and f != "price"]
va = VectorAssembler(inputCols=ohe_cols + num_cols, outputCol="features")
lr = LinearRegression(labelCol="price", featuresCol="features")
pm = Pipeline(stages=[indexer, ohe, va, lr]).fit(train)
pred = pm.transform(test)
```

Колонка типа `string` считается категориальной. Если у вас числовая колонка на самом деле категория (или наоборот), явно укажите, в какой список она попадает. Параметр `handleInvalid` отвечает за новые категории, которых не было в `train`: `skip` убирает строки, `error` бросает ошибку, `keep` кладёт их в отдельную корзину с индексом `numLabels`.

У подхода есть слабое место: `StringIndexer` надо явно сказать, какие колонки категориальные. `VectorIndexer` ищет их сам, но дорого: проходит по всем колонкам и проверяет, что различных значений меньше `maxCategories`, а это число тоже надо выбрать.

Ещё один путь — `RFormula` с синтаксисом из языка R. Формула `"price ~ ."` значит «предсказать `price` по всем остальным колонкам». Поддерживаются операторы `~`, `.`, `:`, `+`, `-`. `RFormula` сам делает `StringIndexer` и OHE для строк, приводит числа к `double` и собирает вектор. Тогда всё предыдущее заменяет одна строка:

```python
rFormula = RFormula(formula="price ~ .", featuresCol="features", labelCol="price", handleInvalid="skip")
```

Но у `RFormula` есть минус: OHE нужен не всем алгоритмам. Деревья умеют работать с категориями напрямую (хватает `StringIndexer`), а OHE часто ухудшает их. Универсального рецепта для `feature engineering` нет, он зависит от алгоритма. Авторы просят: если признаки готовит кто-то другой, пусть он документирует, как их получил.

В книге после OHE получилось 98 признаков, и колонка `features` была `SparseVector`. У нас признаков мало, поэтому Spark сам выбирает формат (плотный или разрежённый). Один из прогнозов в книге был отрицательной ценой аренды, и это повод оценить модель числами.

### Оценка модели

В `spark.ml` есть evaluator для классификации, регрессии, кластеризации и ранжирования (последний с Spark 3.0). Для регрессии берут `RMSE` и `R2`.

**RMSE** (root-mean-square error) лежит в диапазоне от нуля до бесконечности, и чем ближе к нулю, тем лучше. Считают по шагам:

1. Ошибка — разность между истиной `y` и прогнозом `ŷ`.
2. Её возводят в квадрат, чтобы плюсы и минусы не гасили друг друга.
3. Квадраты суммируют по всем `n` записям: это `SSE`.
4. `SSE` делят на `n` и получают `MSE`. Иначе ошибка росла бы с размером набора.
5. Берут корень, чтобы вернуться к единицам метки: `RMSE = √(SSE / n)`.

```python
ev = RegressionEvaluator(predictionCol="prediction", labelCol="price", metricName="rmse")
print(f"RMSE is {ev.evaluate(pred):.1f}")
```

```text
RMSE is 23.5
```

Хороша ли эта цифра? Сравните с `baseline`: средняя цена по `train` как прогноз для каждой записи. Для классификации `baseline` — самый частый класс. Если `baseline` не побит, где-то ошибка. У книги модель дала RMSE 220,6 против `baseline` 240,7. У нас 23,5 против 77,9. Единица метки влияет на RMSE: рост в сантиметрах даст число больше, чем в метрах. Поэтому всегда сравнивайте с `baseline`.

**R2** считают как `1 − SSres / SStot`. `SSres` — сумма квадратов ошибок модели. `SStot` — та же сумма, если всегда предсказывать среднее `ȳ`. Идеальная модель даёт `R2 = 1`. Модель не лучше среднего даёт 0. Если модель хуже среднего, `R2` отрицательный, и процесс надо пересмотреть. Диапазон — от минус бесконечности до 1, поэтому отдельный `baseline` строить не нужно.

```python
print(f"R2 is {ev.setMetricName('r2').evaluate(pred):.3f}")
```

```text
R2 is 0.907
```

В книге `R2` вышел 0,16: положительный, но близкий к нулю. Одна из причин — цена распределена лог-нормально: логарифм цены похож на нормальное распределение. С ценами так бывает часто: большинство аренд около $200, но есть и за тысячи. Авторы предлагают предсказывать логарифм цены, а потом брать экспоненту: тогда `RMSE` падает, а `R2` растёт. У нас данные почти симметричны, поэтому `R2` высокий.

### Сохранение и загрузка

Сохранить модель так же просто, как записать `DataFrame`: `model.write().overwrite().save(path)`. Метод `overwrite()` перезаписывает данные в папке. При загрузке нужно указать тип модели. Поэтому авторы советуют всегда класть `transformer` и `estimator` в `Pipeline`: тогда для любой модели загружают `PipelineModel` и меняют только путь.

```python
pm.write().overwrite().save("/tmp/ch10-lr-pipeline")
loaded = PipelineModel.load("/tmp/ch10-lr-pipeline")
```

Загруженную модель применяют к новым данным. Но её веса нельзя взять как старт для нового обучения: в Spark нет `warm start`. Если данные немного изменились, модель учат заново.

## Подбор гиперпараметров

Гиперпараметр (`hyperparameter`) — это значение, которое вы задаёте до обучения. Модель его не учит, в отличие от обычных параметров. Число деревьев в `random forest` — гиперпараметр. Подбор гиперпараметров проверим на деревьях, но идеи общие.

### Деревья решений

Модели на деревьях (`decision tree`, `gradient boosted trees`, `random forest`) просты, сильны и легко объясняются, поэтому популярны. `Decision tree` — это цепочка правил if-then-else, выученных из данных. Он быстро строится, понятен и не чувствителен к масштабу: стандартизировать числовые признаки не нужно.

![Схема: дерево решений про оффер: зарплата, дорога, бесплатный кофе](/assets/learning-spark/ch10-tree.png)

В примере предсказывают, примет ли человек оффер. Верхний узел (корень, `root`) — самый информативный `split`. Если зарплата меньше $50 000, большинство откажется. Иначе идём к следующему признаку, и так до листа (`leaf`), где ответ. Книга шутит, что дерево рисуют корнем вверх. Подробности о выборе `split` ищите в книге Hastie, Tibshirani и Friedman. Один признак можно разбивать несколько раз, но по разным порогам.

Глубина дерева — длина самого длинного пути от корня до листа (в примере 3). Слишком глубокие деревья переобучаются, то есть запоминают шум. Слишком мелкие недообучаются: упускают сигнал.

Деревьям для категориальных признаков не нужен OHE, достаточно `StringIndexer`. Но если обучить дерево с параметрами по умолчанию на колонке с 36 значениями, получим ошибку.

```python
dt = DecisionTreeRegressor(labelCol="price")
Pipeline(stages=[indexer, va, dt]).fit(train)   # колонка hood имеет 36 значений
```

```text
ОШИБКА: requirement failed: DecisionTree requires maxBins (= 32) to be at least as large as the number of values in each categorical feature, but categorical feature 0 has 36 values
```

`maxBins` — число корзин, на которые Spark разбивает непрерывные признаки. Такая дискретизация нужна для распределённого обучения. В `scikit-learn` этого параметра нет: там данные и модель на одной машине. В Spark у каждого worker есть все колонки, но только часть строк. Чтобы все worker проверяли одни и те же точки `split`, нужна общая дискретизация. Книга показывает это на реализации PLANET: каждый worker считает сводную статистику по каждому признаку и каждой точке `split`, а потом статистику складывают. Для категорий `maxBins` должен быть не меньше числа значений. По умолчанию он равен 32. Значение 64 удвоило бы число `split` для непрерывных признаков и сильно замедлило бы счёт, поэтому берём 40:

```python
dt.setMaxBins(40)
pm = Pipeline(stages=[indexer, va, dt]).fit(train)
dt_model = pm.stages[-1]
print("depth =", dt_model.depth, ", numNodes =", dt_model.numNodes)
```

```text
depth = 5 , numNodes = 63
```

Результаты `MLlib` и `scikit-learn` обычно немного различаются из-за реализации. Это нормально. Важно понять причины и сравнить параметры обеих библиотек. Когда метрики двух библиотек на одних данных станут близки, модель на `MLlib` можно запустить на данных, которые `scikit-learn` не вытянет.

Правила дерева можно напечатать через `dt_model.toDebugString`: числовые признаки сравниваются с порогом (`<=`), категориальные проверяются на вхождение в набор. Ещё модель выдаёт важность признаков:

```python
imp = sorted(zip(va.getInputCols(), dt_model.featureImportances), key=lambda t: -t[1])
```

```text
bedrooms     0.453
room_typeIndex 0.429
hoodIndex    0.115
reviews      0.003
```

Дерево гибкое, но не всегда самое точное. На данных книги `R2` на `test` вышел бы даже отрицательным: хуже, чем прогноз средним. Поэтому берут ансамбль.

### Random forest

Ансамбль объединяет ответы многих моделей. Представьте банку с конфетами: сто человек гадают, сколько их внутри, и среднее ответов обычно ближе к истине, чем большинство отдельных ответов. Так и с моделями: усреднение многих устойчивее одной.

`Random forest` — ансамбль деревьев с двумя приёмами.

![Схема: random forest: у каждого дерева своя bootstrap-выборка строк и случайные признаки на split, ответы усредняются или идут на голосование](/assets/learning-spark/ch10-forest.png)

Слева данные идут в разные выборки, в центре растут деревья, справа ответы объединяются.

- **Bootstrap по строкам.** `Bootstrap` — выборка с возвращением из исходных данных. Каждое дерево учится на своей выборке, поэтому деревья получаются разные. Объединение ответов называют `bagging` (bootstrap aggregating). Размер выборки задаёт `subsamplingRate`.
- **Случайные признаки по столбцам.** Без этого деревья сильно коррелируют и учат одно и то же. Поэтому на каждом `split` смотрят только случайную часть признаков: треть для `RandomForestRegressor` и корень из их числа для `RandomForestClassifier`. Из-за этой случайности каждое дерево обычно делают неглубоким. Каждое «слабее» одного дерева решений, но каждое выучило что-то своё, и ансамбль надёжнее.

Для классификации лес пропускает точку через все деревья и берёт большинство голосов. Для регрессии усредняет ответы. API почти как у дерева:

```python
rf = RandomForestRegressor(labelCol="price", maxBins=40, seed=42)
```

`Random forest` хорошо показывает силу распределённого ML: деревья строятся независимо (дерево 10 не ждёт дерево 3), а внутри уровня дерева поиск лучших `split` тоже распараллеливается.

### k-fold cross-validation

Как выбрать число деревьев и глубину? Это задача подбора гиперпараметров. На `train` нельзя: модель переобучится. На `test` тоже нельзя: он перестанет быть «новыми» данными. Значит, нужен третий набор — валидационный. Можно резать 60/20/20, но тогда мы теряем 25% обучающих данных (было 80%). Поэтому есть `k-fold cross-validation`.

![Схема: train 80% и test 20%; train делится на 3 fold, каждый по очереди становится валидацией, RMSE усредняется](/assets/learning-spark/ch10-cv.png)

Сначала режем на `train` и `test`, как раньше. Потом `train` делим на `k` частей (`fold`). Для одной конфигурации гиперпараметров обучаем модель на `k−1` частях и проверяем на оставшейся, и так `k` раз. Среднее по `k` проверкам — оценка конфигурации: каждая запись побывала в валидации ровно один раз. Это повторяют для каждой конфигурации.

Пространство поиска выбирать трудно. Случайный поиск часто бьёт структурированный перебор по сетке. Есть и специальные библиотеки, например Hyperopt, о которой пойдёт речь в главе 11.

Подбор в Spark идёт в четыре шага:

1. Определить `estimator`.
2. Задать гиперпараметры и их значения через `ParamGridBuilder`.
3. Выбрать `evaluator` с метрикой.
4. Запустить `CrossValidator`.

```python
grid = (ParamGridBuilder()
        .addGrid(rf.maxDepth, [2, 4, 6])
        .addGrid(rf.numTrees, [10, 50])
        .build())
cv = CrossValidator(estimator=Pipeline(stages=[indexer, va, rf]), evaluator=ev,
                    estimatorParamMaps=grid, numFolds=3, seed=42)
cv_model = cv.fit(train)
```

В книге сетка была 3 × 2 с `numTrees` 10 и 100. Сколько моделей обучено? Не 18 (6 конфигураций × 3 fold), а 19: усреднять модели трудно, поэтому Spark после выбора лучшей конфигурации заново учит модель на всём `train`. Промежуточные модели сохранит параметр `collectSubModels=True`. Среднее `RMSE` по конфигурациям лежит в `cv_model.avgMetrics`:

```text
конфигураций: 6 , моделей: 3 x 6 + 1 финальная = 19
maxDepth=2 numTrees=10  avg RMSE=42.8
maxDepth=2 numTrees=50  avg RMSE=43.1
maxDepth=4 numTrees=10  avg RMSE=35.0
maxDepth=4 numTrees=50  avg RMSE=33.7
maxDepth=6 numTrees=10  avg RMSE=34.3
maxDepth=6 numTrees=50  avg RMSE=34.1
лучшая модель: maxDepth = 4 , numTrees = 50
forest RMSE на test = 36.6
```

Лучшая конфигурация — с наименьшим `RMSE`. У книги это `maxDepth=6` и `numTrees=100` (RMSE 292,1).

### Ускорение

Подбор гиперпараметров обучает много моделей, поэтому он долгий. Модели в `CrossValidator` независимы, но `spark.ml` по умолчанию учит их по очереди. С Spark 2.3 есть параметр `parallelism`: сколько моделей учить одновременно. Документация Spark советует выбирать его так, чтобы не превысить ресурсы кластера, и до 10 хватает для большинства кластеров. С `parallelism=4` книга ускорила обучение с 1,07 минуты до 31,45 секунды.

Второй приём — положить `CrossValidator` внутрь `Pipeline`, а не наоборот. Если `Pipeline` внутри `CrossValidator`, то для каждой модели все шаги считаются заново, даже неизменные, например `StringIndexer`. Если `CrossValidator` внутри `Pipeline`, `StringIndexer` учится один раз:

```python
cv_in = CrossValidator(estimator=rf, evaluator=ev, estimatorParamMaps=grid,
                       numFolds=3, parallelism=2, seed=42)
pm2 = Pipeline(stages=[indexer, va, cv_in]).fit(train)
```

Результат на `test` не меняется: `RMSE` тот же, 36,6. У книги время упало до 26,21 секунды. Выигрыш в секундах, но на больших данных и моделях он растёт.

> **Пояснение:** мы засекли время на ноутбуке в Docker с `local[2]`: последовательный запуск шёл примерно 9,5 секунды, `parallelism=2` — 5,1, `CrossValidator` внутри `Pipeline` — 4,0. Цифры зависят от машины, а метрики в скрипте при этом не меняются.

## Итоги главы

- В главе строят ML-модели на `spark.ml`: API на `DataFrame`, который заменил старый `spark.mllib` на `RDD`.
- `Transformer` применяет правила и не учится, `estimator` учится методом `fit` и возвращает модель, которая сама `transformer`.
- `Pipeline` держит шаги в одном порядке, сам вызывает `fit` и `transform`, а `PipelineModel` пригоден и для сохранения, и для применения к `test`.
- Категории превращают в числа через `StringIndexer` и `OneHotEncoder` (или одним `RFormula`); для деревьев OHE не нужен и даже вредит.
- Для регрессии качество считают через `RMSE` и `R2`, а `RMSE` сравнивают с `baseline`: без этого число ничего не говорит.
- У деревьев в Spark есть `maxBins`: он должен быть не меньше числа значений категориального признака, а большие значения замедляют обучение.
- `Random forest` берёт случайные строки (`bootstrap`) и случайные признаки на каждом `split`, а ответ усредняет или собирает голосованием.
- Гиперпараметры подбирают через `CrossValidator` и `ParamGridBuilder`; финальная модель переобучается на всём `train`.
- Обучение ускоряют параметром `parallelism` и тем, что `CrossValidator` кладут внутрь `Pipeline`.

## Ключевые термины

| Термин | Значение |
|---|---|
| `label` (метка) | Значение, которое модель учится предсказывать |
| `feature` (признак) | Колонка входных данных. Все признаки собираются в один вектор |
| `transformer` | Меняет `DataFrame` методом `transform`, ничего не учит |
| `estimator` | Учится на данных методом `fit` и возвращает модель |
| `ML pipeline` | Цепочка `transformer` и `estimator`; класс `Pipeline` |
| `one-hot encoding` | Для каждой категории своя бинарная колонка |
| `RMSE` | Корень из среднего квадрата ошибки, в единицах метки |
| `R2` | Доля объяснённого разброса; 1 идеально, 0 как среднее, ниже 0 хуже среднего |
| `baseline` | Простой прогноз для сравнения, например среднее по `train` |
| `hyperparameter` | Настройка модели, заданная до обучения |
| `decision tree` | Цепочка правил if-then-else |
| `random forest` | Ансамбль деревьев на разных выборках и признаках |
| `cross-validation` | `train` делят на `k` частей и по очереди проверяют на каждой |

## Что это значит на практике

- Один раз разбейте данные на `train` и `test`, запишите их в отдельные папки и больше не режьте. Тогда число `executor` не меняет результат.
- Всегда кладите шаги в `Pipeline`: загрузка модели тогда одинакова для любого алгоритма.
- Сохраняйте и версионируйте всё, что делает признаки. Тот, кто готовит признаки, должен их документировать.
- Не доверяйте голому `RMSE`. Считайте `baseline` и смотрите на `R2`: отрицательное значение значит, что модель хуже среднего.
- Для деревьев и лесов не делайте OHE. Если ловите ошибку `maxBins`, поднимите значение чуть выше числа категорий, а не до огромного.
- Перед подбором гиперпараметров оцените цену: число моделей равно конфигурации × `k` плюс одна. Включите `parallelism` и поставьте `CrossValidator` внутрь `Pipeline`.
- Модель из `scikit-learn` не даст то же число в `MLlib`. Сравните параметры и допустите небольшую разницу.

## Практика в DuckDB

Запустите `duckdb` в терминале или откройте [shell.duckdb.org](https://shell.duckdb.org). Блоки идут по порядку. Здесь мы повторяем идеи главы на SQL: разбиение, линейная регрессия, `RMSE`, `R2` и `one-hot encoding`.

### Шаг 1. Создаём данные

Данные генерируются формулами, поэтому разбиение и числа всегда одинаковы. Разбиваем по ключу (`id % 5`): так `test` не меняется при перезапуске.

```sql
CREATE TABLE listings AS
SELECT i AS id,
       ['Mission','Marina','Sunset','Haight'][1 + (i * 31 % 97) % 4] AS hood,
       ['Entire home','Private room','Shared room'][1 + (i * 7919 % 101) % 3] AS room_type,
       1 + (i * 104729 % 103) % 3 AS bedrooms,
       50 + 70 * (1 + (i * 104729 % 103) % 3)
          + CASE (i * 7919 % 101) % 3 WHEN 0 THEN 90 WHEN 1 THEN 0 ELSE -30 END
          + CASE (i * 31 % 97) % 4 WHEN 0 THEN 40 WHEN 1 THEN 60 WHEN 2 THEN 0 ELSE 20 END
          + (i * 37 % 51) - 25 AS price
FROM range(1, 401) t(i);

CREATE TABLE train AS SELECT * FROM listings WHERE id % 5 <> 0;
CREATE TABLE test  AS SELECT * FROM listings WHERE id % 5 = 0;
```

### Шаг 2. Проверяем

Должно быть 320 и 80 строк, и общих строк у `train` и `test` быть не должно.

```sql
SELECT (SELECT count(*) FROM train) AS train_rows,
       (SELECT count(*) FROM test) AS test_rows,
       (SELECT count(*) FROM train JOIN test USING (id)) AS overlap;
```

├────────────┼───────────┼─────────┤

### Задания

**1. Линейная регрессия и baseline.** Найдите наклон и сдвиг `price ~ bedrooms` на `train`. Посчитайте `RMSE` на `test` для модели и для `baseline` (средняя цена по `train`).

<details><summary>Решение</summary>

```sql
WITH model AS (
  SELECT regr_slope(price, bedrooms) AS m, regr_intercept(price, bedrooms) AS b FROM train),
base AS (SELECT avg(price) AS y_bar FROM train)
SELECT round(m.m, 2) AS m, round(m.b, 2) AS b,
       round(sqrt(avg(power(t.price - (m.m * t.bedrooms + m.b), 2))), 1) AS rmse_model,
       round(sqrt(avg(power(t.price - base.y_bar, 2))), 1) AS rmse_baseline
FROM test t, model m, base
GROUP BY m.m, m.b;
```

```text
┌────────┬────────┬────────────┬───────────────┐
│   m    │   b    │ rmse_model │ rmse_baseline │
│ double │ double │   double   │    double     │
├────────┼────────┼────────────┼───────────────┤
│  72.36 │  92.63 │       58.6 │          80.3 │
└────────┴────────┴────────────┴───────────────┘
```

Функции `regr_slope` и `regr_intercept` — это то же, что делает `LinearRegression` с одним признаком. Модель бьёт `baseline`: 58,6 меньше 80,3.

</details>

**2. R2.** Посчитайте `R2` этой модели на `test` по формуле `1 − SSres / SStot`.

<details><summary>Решение</summary>

```sql
WITH model AS (
  SELECT regr_slope(price, bedrooms) AS m, regr_intercept(price, bedrooms) AS b FROM train),
base AS (SELECT avg(price) AS y_bar FROM train)
SELECT round(1 - sum(power(t.price - (m.m * t.bedrooms + m.b), 2))
                 / sum(power(t.price - base.y_bar, 2)), 3) AS r2
FROM test t, model m, base;
```

```text
┌────────┐
│   r2   │
│ double │
├────────┤
│  0.468 │
└────────┘
```

`R2` положительный, значит модель лучше среднего. Но он невысокий: тип жилья и район мы пока не учли.

</details>

**3. One-hot encoding.** Сделайте из `room_type` две колонки `entire_home` и `private_room` (третье значение кодируется парой нулей) и посчитайте среднюю цену по каждой комбинации.

<details><summary>Решение</summary>

```sql
SELECT (room_type = 'Entire home')::INT AS entire_home,
       (room_type = 'Private room')::INT AS private_room,
       count(*) AS n, round(avg(price), 1) AS avg_price
FROM train GROUP BY 1, 2 ORDER BY 1, 2;
```

```text
┌─────────────┬──────────────┬───────┬───────────┐
│ entire_home │ private_room │   n   │ avg_price │
│    int32    │    int32     │ int64 │  double   │
├─────────────┼──────────────┼───────┼───────────┤
│           0 │            0 │   119 │     187.9 │
│           0 │            1 │   100 │     218.5 │
│           1 │            0 │   101 │     312.2 │
└─────────────┴──────────────┴───────┴───────────┘
```

Колонок на одну меньше, чем значений: если обе равны нулю, это `Shared room`. Spark по умолчанию делает так же (`dropLast`). Три значения дают три разные цены, и числовая нумерация 1, 2, 3 этого бы не передала.

</details>
