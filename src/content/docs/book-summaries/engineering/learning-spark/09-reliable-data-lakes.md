**Главная мысль:** базы данных дают транзакции, но плохо масштабируются и закрыты для ML. `Data lake` масштабируется дёшево, но не даёт транзакций. `Lakehouse` соединяет оба подхода: файлы озера плюс `transaction log`. Для Spark главный пример такой системы — Delta Lake.

## О чём глава

В [прошлой главе](/book-summaries/engineering/learning-spark/08-structured-streaming/) мы писали логику обработки. Но надёжность pipeline зависит и от того, где лежат данные. Глава отвечает на вопрос: какое хранилище выбрать и как работать с ним из Spark. Темы:

- свойства хорошего хранилища;
- базы данных и их пределы;
- `data lake` и его слабые места;
- `lakehouse`: Apache Hudi, Apache Iceberg, Delta Lake;
- Delta Lake на практике: запись, схема, `UPDATE`, `DELETE`, `MERGE`, история и `time travel`.

![Схема: база данных, data lake и lakehouse с их свойствами](/assets/learning-spark/ch09-evolution.png)

На схеме слева направо хранилища сменяли друг друга: каждое решало проблему предыдущего.

## Каким должно быть хранилище

Авторы называют пять желаемых свойств:

- **Масштаб и скорость.** Хранилище растёт вместе с данными и держит нужные throughput и задержку.
- **Транзакции.** Сложные нагрузки читают и пишут одновременно, поэтому нужны ACID-гарантии (`ACID`: транзакция атомарна, согласована, изолирована и долговечна).
- **Разные форматы данных.** Неструктурированные (логи), полуструктурированные (JSON) и таблицы.
- **Разные нагрузки.** SQL для BI, пакетный ETL, ML и AI.
- **Открытость.** Данные в открытых форматах со стандартными API, чтобы под каждую задачу брать лучший инструмент.

## Базы данных

### Как устроены

База хранит структурированные данные в таблицах и отвечает на SQL. Схема строгая, поэтому СУБД тесно связывает формат файлов и индексы со своим движком запросов. Это даёт быстрые вычисления и ACID на каждой операции. SQL-нагрузки бывают двух видов:

| Тип | Пример | Запросы |
|---|---|---|
| `OLTP` | банковские транзакции | много одновременных, быстрых, простых; читают или меняют несколько строк |
| `OLAP` | периодические отчёты | сложные (агрегаты, `join`), быстрое сканирование многих строк |

Spark создан для `OLAP`, поэтому дальше речь только об аналитике.

### Чтение и запись из Spark

Для баз с поддержкой JDBC (PostgreSQL, MySQL) есть встроенный источник `jdbc`: к нему нужен jar-файл от поставщика базы. Для Snowflake, Azure Cosmos DB и других есть свои коннекторы, они подключаются по имени формата. Примеры авторы разбирали в главе 5. Так Spark легко добавляется к существующему хранилищу.

```python
# не запускается: нужен сервер PostgreSQL
df = (spark.read.format("jdbc")
      .option("url", "jdbc:postgresql://host:5432/shop")
      .option("dbtable", "loans")
      .option("user", "reader").option("password", "...")
      .load())
```

### Ограничения

Последние десять лет принесли два сдвига. Данных стало больше: от гигабайт до терабайт и петабайт. Аналитика стала разнообразнее: появились ML и deep learning. Базы справляются с этим плохо по двум причинам:

- **Scale-out очень дорог.** Данные растут быстрее, чем мощность одной машины, значит, нужны много машин. Но большинство баз, особенно открытых, не умеют распределённую обработку. Те, что умеют, закрыты и работают на специальном железе.
- **Non-SQL аналитика неудобна.** Формат файлов часто закрыт и оптимизирован под один движок. ML-системы читают данные только целиком через базу, а расширить базу под ML трудно.

## Data lake

### Идея

`Data lake` отделяет распределённое хранилище от распределённых вычислений, и каждая часть растёт сама по себе. Данные лежат файлами в открытых форматах, их читает любой движок. Идею популяризировал HDFS в конце 2000-х, а он вырос из статьи Google «The Google File System». Организация выбирает три части отдельно:

| Часть | Варианты |
|---|---|
| Хранилище | HDFS или облачный object store: AWS S3, Azure Data Lake Storage, Google Cloud Storage |
| Формат файлов | Parquet, ORC (структурные); JSON; текст, картинки, аудио, видео |
| Движок | пакетный (Spark, Presto, Hive), потоковый (Spark, Flink), ML (MLlib, scikit-learn, R) |

Свобода выбора — главное преимущество перед базами. При той же производительности `data lake` обычно намного дешевле базы.

### Spark и data lake

Spark подходит для озера по трём причинам. Он поддерживает разные нагрузки: пакетную обработку, ETL, Spark SQL, Structured Streaming (глава 8) и MLlib (глава 10). Он читает все форматы (глава 4). И он работает с любой системой, у которой есть Hadoop `FileSystem` API, а такой API стал стандартом.

Для облака нужно настроить безопасный доступ. Кроме того, облачные хранилища ведут себя не как обычная файловая система: например, у S3 действует eventual consistency. Если не настроить Spark под это, результаты могут быть несогласованными. Детали авторы отсылают к документации по cloud integration.

### Ограничения

Главный изъян озера — нет транзакционных гарантий:

- **Атомарность и изолированность.** Spark пишет данные многими файлами. Если запись упала, уже записанные файлы нельзя откатить, и остаются испорченные данные. Параллельные записи усугубляют проблему.
- **Согласованность.** Из-за неатомарной записи читатели видят неполную картину. Качество данных трудно удержать и после успешной записи: например, в озеро легко записать файлы с форматом или схемой, которые не совпадают со старыми.

Разработчики обходят это хитростями. Для обновления нескольких записей переписывают целую папку `partition` (пишут во временную папку и меняют ссылки). Расписания записывающих и читающих задач разводят, чтобы они не пересекались. Всё это неудобно, и поэтому появились lakehouse.

## Lakehouse

`Lakehouse` — это новая парадигма для `OLAP`: функции базы данных работают прямо на дешёвом хранилище озера. Авторы перечисляют требования:

- **Транзакции:** ACID при параллельных нагрузках.
- **Контроль схемы и governance:** таблица не принимает данные с неверной схемой, схему меняют явно, есть аудит.
- **Разные типы данных в открытых форматах** со стандартными API.
- **Разные нагрузки** в одном хранилище: без изолированных `data silos`, от SQL и потоков до ML.
- **Upsert и delete** для `CDC` (change data capture) и `SCD` (медленно меняющиеся измерения) с транзакционными гарантиями.
- **Governance:** можно проверять целостность и аудировать все изменения.

Сегодня такие системы строят на трёх открытых проектах. Все три хранят данные в структурных файлах на масштабируемой файловой системе. Все ведут `transaction log`: журнал атомарных изменений. По журналу они определяют версии таблицы и дают `snapshot isolation` между читателями и писателями. Все три читаются и пишутся из Spark. Авторы предупреждают, что проекты быстро меняются, поэтому описание могло устареть.

| Проект | Кто создал | На что нацелен | Особенности |
|---|---|---|---|
| Apache Hudi | Uber | инкрементальные upsert и delete над key/value | колонночные (Parquet) и строчные (Avro) файлы; быстрые индексы; rollback; чтение инкрементальных изменений; savepoints; фоновая compaction |
| Apache Iceberg | Netflix | универсальное хранилище, петабайты в одной таблице | schema evolution; hidden partitioning; partition evolution; `time travel`; rollback; serializable isolation между писателями |
| Delta Lake | создатели Spark, проект Linux Foundation | транзакции, схема, потоки | запись и чтение из Structured Streaming; `UPDATE`, `DELETE`, `MERGE`; schema enforcement и evolution; `time travel`; rollback; serializable isolation |

Delta Lake теснее всех встроен в источники данных Spark (пакетные и потоковые) и в SQL (`MERGE`). Поэтому глава берёт его как пример.

## Lakehouse на Spark и Delta Lake

Авторы показывают пять приёмов: чтение и запись таблиц Delta, параллельные пакетные и потоковые записи с ACID, контроль схемы, `UPDATE`/`DELETE`/`MERGE` и аудит с `time travel`. Данные: Lending Club Loan Data, займы 2012–2017 с суммой, оплатой, штатом и статусом. Мы генерируем свою маленькую таблицу займов.

### Настройка

В книге Delta подключают через `--packages io.delta:delta-core_2.12:0.7.0` для Spark 3.0 (для Spark 2.4 нужна версия 0.6.0). Сейчас так не делают.

> **Пояснение:** примеры Delta мы запускали на Spark 4.2.0, потому что `delta-spark` пока не поддерживает 4.3. Вместо `--packages` берём `pip install delta-spark` и функцию `configure_spark_with_delta_pip`. Две настройки (`spark.sql.extensions` и `spark.sql.catalog.spark_catalog`) включают SQL-команды Delta. О Spark 4.3 и установке читайте в [главе 1](/book-summaries/engineering/learning-spark/01-intro-to-spark/).

```python
from delta import configure_spark_with_delta_pip, DeltaTable

builder = (SparkSession.builder.master("local[2]")
           .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
           .config("spark.sql.catalog.spark_catalog",
                   "org.apache.spark.sql.delta.catalog.DeltaCatalog"))
spark = configure_spark_with_delta_pip(builder).getOrCreate()
```

В книге есть и Scala-версии всех примеров. Мы показываем только PySpark.

### Загрузка данных

Если озеро уже построено на Parquet, переход на Delta простой: везде замените `format("parquet")` на `format("delta")`. Затем таблицу читают как любую другую, например через `temporary view`.

```python
spark.read.format("parquet").load(parquet_path).write.format("delta").save(delta_path)
spark.read.format("delta").load(delta_path).createOrReplaceTempView("loans_delta")
```

### Загрузка потоков

Structured Streaming тоже пишет в Delta: достаточно `format("delta")`, `checkpointLocation` и пути к таблице. Как и для других форматов, остаётся гарантия `exactly-once`. У Delta есть три дополнительных плюса:

- В одну таблицу пишут и пакетные, и потоковые задачи. В других форматах поток затирает данные, которые уже есть в таблице: метаданные для `exactly-once` не учитывают записи не из потока.
- В одну таблицу могут писать несколько потоков. Delta хранит информацию о транзакциях каждого запроса.
- ACID работает и при параллельных записях.

```python
q = (stream_df.writeStream.format("delta")
     .option("checkpointLocation", ckpt)
     .trigger(availableNow=True).start(delta_path))
```

> В книге триггер `processingTime = "10 seconds"` запускает бесконечный поток. Мы взяли `availableNow=True`, чтобы скрипт завершался сам.

![Схема: пакетные и потоковые записи коммитят в журнал Delta, версии ведут к time travel](/assets/learning-spark/ch09-delta-log.png)

Обе записи идут через `transaction log`. Журнал нумерует версии таблицы, а сами данные остаются в файлах Parquet.

### Контроль схемы при записи

Parquet, JSON и ORC описывают схему отдельных файлов, но не всей таблицы. Поэтому любая задача может записать в таблицу файлы с другой схемой, и согласованности всей таблицы нет. Delta хранит схему как метаданные таблицы и проверяет каждую запись. Если схема не подходит, Spark выбрасывает ошибку до того, как данные попали в таблицу. В примере мы дописываем строки с новой колонкой `closed`. Spark выдаёт ошибку `AnalysisException`, и в её тексте есть подсказка: опция `mergeSchema`.

### Schema evolution: схему меняем явно

Если новая колонка нужна, её добавляют явно: `.option("mergeSchema", "true")`. Колонка попадает в схему, новые данные дописываются, а в старых строках новое поле читается как `NULL`. Схему можно менять и командой `ALTER TABLE`.

![Схема: проверка схемы при записи, ошибка и явный mergeSchema](/assets/learning-spark/ch09-schema.png)

Без `mergeSchema` запись с чужой схемой отклоняется целиком. С ним схема таблицы расширяется.

### Изменение данных

`UPDATE`, `DELETE` и `MERGE` доступны из Java, Scala, Python и SQL, и каждая операция даёт ACID.

**Исправление ошибок.** Допустим, займы со штатом `OR` на самом деле нужно записать как `WA`. Для обычной Parquet-таблицы пришлось бы пройти четыре шага. Сначала скопировать нетронутые строки в новую таблицу. Затем скопировать затронутые строки в `DataFrame` и изменить их. Потом добавить их в новую таблицу. В конце удалить старую таблицу и дать новой её имя. В Delta достаточно одного вызова:

```python
dt = DeltaTable.forPath(spark, delta_path)
dt.update("addr_state = 'OR'", {"addr_state": "'WA'"})
```

**Удаление данных пользователя.** Закон GDPR требует удалять данные пользователей из всех таблиц. В примере книги правило требует удалить все полностью оплаченные займы:

```python
dt.delete("funded_amnt <= paid_amnt")
```

В книге условие записано как `funded_amnt >= paid_amnt`, но оно выбирает не полностью оплаченные займы, то есть противоположное. Мы взяли `<=`: оплата не меньше суммы займа.

**Upsert через `merge()`.** Типичный случай — `CDC`: изменения строк в `OLTP`-таблице переносят в аналитическую. В таблице изменений часть займов новая, часть обновляет старые. `merge()` повторяет SQL `MERGE`: совпавшие строки обновляет, новые добавляет.

```python
(dt.alias("t").merge(changes.alias("s"), "t.loan_id = s.loan_id")
   .whenMatchedUpdateAll().whenNotMatchedInsertAll().execute())
```

Если изменения приходят потоком, Structured Streaming читает их порциями (micro-batch), а `foreachBatch()` применяет каждую порцию к таблице.

**Дедупликация при вставке.** Расширенный `MERGE` в Delta умеет больше стандарта ANSI: удаление (`WHEN MATCHED THEN DELETE`), дополнительные условия в ветках WHEN MATCHED и WHEN NOT MATCHED. Любую из этих веток можно опустить, а `UPDATE *`/`INSERT *` берут все колонки. Например, вы догружаете исторические займы, но не хотите перезаписывать уже загруженные: они могут быть свежее. Тогда в операции оставляют только вставку: займы с уже известным ключом пропускаются.

```python
(dt.alias("t").merge(hist.alias("s"), "t.loan_id = s.loan_id")
   .whenNotMatchedInsertAll().execute())
```

Расширенный синтаксис упрощает и более сложные случаи: `CDC` с удалениями и таблицы `SCD`. Примеры авторы отсылают к документации Delta.

### История операций

Каждое изменение таблицы записывается в `transaction log` как коммит и получает версию. Историю даёт `dt.history()`. Для аудита полезны колонки `version`, `timestamp`, `operation` и `operationParameters`.

### Time travel

Прошлую версию таблицы читают опциями `versionAsOf` и `timestampAsOf`. Это полезно в трёх случаях:

- воспроизвести ML-эксперимент или отчёт на нужной версии таблицы;
- сравнить версии при аудите;
- откатить ошибку: прочитать старый снимок и перезаписать им таблицу.

```python
v0 = spark.read.format("delta").option("versionAsOf", 0).load(delta_path)
```

## Итоги главы

- Хорошее хранилище масштабируется, даёт транзакции, держит разные форматы и нагрузки и остаётся открытым.
- Базы данных дают быстрый SQL и ACID, но scale-out дорог, а ML и другая non-SQL аналитика неудобны.
- `Data lake` отделяет хранилище от вычислений и хранит открытые файлы, поэтому он дёшев и гибок.
- У озера нет ACID: упавшая запись оставляет испорченные файлы, параллельные записи конфликтуют, схему никто не проверяет.
- `Lakehouse` добавляет к дешёвому хранилищу функции базы: транзакции, схему, `upsert`, аудит.
- Hudi, Iceberg и Delta Lake похожи: открытые файлы плюс `transaction log` со снимками версий.
- Delta Lake принимает пакетные и потоковые записи в одну таблицу и держит `exactly-once`.
- Схема проверяется при каждой записи, а `mergeSchema` меняет её явно.
- `UPDATE`, `DELETE` и `MERGE` заменяют ручную перезапись файлов.
- История и `time travel` показывают прошлые версии для аудита, воспроизводимости и отката.

## Ключевые термины

| Термин | Значение |
|---|---|
| `ACID` | свойства транзакции: атомарность, согласованность, изолированность, долговечность |
| `OLTP` / `OLAP` | много мелких быстрых операций / сложные аналитические запросы по большим объёмам |
| `data lake` | хранилище файлов в открытых форматах, отдельное от вычислений |
| `lakehouse` | файлы озера плюс таблицы и транзакции базы |
| `transaction log` | журнал атомарных изменений таблицы, по нему строятся версии |
| `schema enforcement` / `schema evolution` | запись с чужой схемой отклоняют / схему меняют явно |
| `MERGE` / `upsert` | вставка или обновление строк по ключу |
| `time travel` | чтение таблицы на прошлый момент или версию |
| `CDC` | change data capture: перенос изменений строк из одной таблицы в другую |

## Что это значит на практике

- Данные на S3 или в HDFS без слоя `transaction log` небезопасно читать во время записи. Берите формат таблиц (Delta, Iceberg или Hudi), а не голые Parquet-файлы.
- Перевод Parquet-озера на Delta обычно сводится к замене `parquet` на `delta` в чтении и записи.
- Исправления, удаления по GDPR и upsert пишите через `UPDATE`, `DELETE` и `MERGE`, а не перезаписью папок.
- Для догрузки истории без дублей используйте `MERGE` только со вставкой.
- Включайте `mergeSchema` осознанно: пусть неожиданная колонка сначала упадёт с ошибкой, и вы решите, нужна ли она.
- Перед откатом посмотрите `history()` и прочитайте нужную версию через `versionAsOf`.

## Практика в PySpark

Полный скрипт: `scripts/learning-spark-code/ch09_delta.py` (запуск в Docker с образом Delta, Spark 4.2.0). Скрипт создаёт 10 займов, переводит их в Delta, дописывает 2 строки потоком, проверяет схему, а потом делает `UPDATE`, `DELETE`, два `MERGE` и `time travel`. Вывод:

```text

closed IS NULL: 12 of 14
OR left: 0
rows after delete: 11
loan 1: {'loan_id': 1, 'funded_amnt': 1500, 'paid_amnt': 999.0, 'addr_state': 'NY', 'closed': False}
loan 1 still: NY | loan 777 added: 1
v0 WRITE
v1 STREAMING UPDATE
v2 WRITE
v3 UPDATE
v4 DELETE
v5 MERGE
v6 MERGE
v0 rows: 10 | columns: ['loan_id', 'funded_amnt', 'paid_amnt', 'addr_state']
now rows: 13
```

Версии идут подряд: запись, поток (`v1`), запись с `mergeSchema` (`v2`), затем `UPDATE`, `DELETE` и два `MERGE`. Версия `v0` осталась без колонки `closed` и с 10 строками.

> В Spark 4 включён ANSI SQL mode, поэтому в скрипте `funded_amnt` приводится к `int` явно: `createDataFrame` по умолчанию даёт `long`.

## Практика в DuckDB

У таблиц DuckDB нет журнала версий, как у Delta. Поэтому журнал мы ведём сами в отдельной таблице и показываем те же идеи на SQL. Запустите `duckdb` в терминале или откройте [shell.duckdb.org](https://shell.duckdb.org). Блоки идут по порядку.

### Шаг 1. Создаём займы и журнал изменений

Таблица `loans` — текущее состояние. Таблица `history` — наш простой журнал: версия, займ, операция и штат.

```sql
CREATE TABLE loans AS
SELECT * FROM (VALUES
  (1, 1000, 1000.0, 'CA'),
  (2, 1500,  250.0, 'OR'),
  (3, 2000,  800.0, 'OR'),
  (4, 1000,    0.0, 'TX'),
  (5, 3000, 3000.0, 'WA')
) t(loan_id, funded_amnt, paid_amnt, addr_state);

CREATE TABLE history AS
SELECT * FROM (VALUES
  (0, 1, 'WRITE', 'CA'), (0, 2, 'WRITE', 'OR'), (0, 3, 'WRITE', 'OR'),
  (1, 2, 'UPDATE', 'WA'), (1, 3, 'UPDATE', 'WA'),
  (2, 1, 'DELETE', 'CA')
) t(version, loan_id, op, addr_state);
```

### Шаг 2. Проверяем

```sql
SELECT count(*) AS n, count(DISTINCT loan_id) AS ids FROM loans;
```

```text
┌───────┬───────┐
│   n   │  ids  │
│ int64 │ int64 │
├───────┼───────┤
│     5 │     5 │
└───────┴───────┘
```

Числа равны: `loan_id` уникален, значит, `MERGE` по этому ключу не создаст дублей.

### Задания

**Задание 1.** Переименуйте штат `OR` в `WA` и удалите полностью оплаченные займы. Сколько займов осталось?

<details><summary>Решение</summary>

```sql
UPDATE loans SET addr_state = 'WA' WHERE addr_state = 'OR';
DELETE FROM loans WHERE funded_amnt <= paid_amnt;
SELECT * FROM loans ORDER BY loan_id;
```

```text
loan_id | funded_amnt | paid_amnt | addr_state
2       | 1500        | 250.0     | WA
3       | 2000        | 800.0     | WA
4       | 1000        | 0.0       | TX
```

Остались 3 займа: займы 1 и 5 полностью оплачены, их удалил `DELETE`.
</details>

**Задание 2.** Таблица `changes` содержит займ 2 с новой оплатой 900 и новый займ 6. Сделайте `upsert` через `MERGE INTO`.

<details><summary>Решение</summary>

```sql
CREATE TABLE changes AS
SELECT * FROM (VALUES
  (2, 1500, 900.0, 'WA'),
  (6, 500, 0.0, 'NV')
) t(loan_id, funded_amnt, paid_amnt, addr_state);

MERGE INTO loans AS t USING changes AS s ON t.loan_id = s.loan_id
WHEN MATCHED THEN UPDATE SET paid_amnt = s.paid_amnt
WHEN NOT MATCHED THEN INSERT *;

SELECT * FROM loans ORDER BY loan_id;
```

```text
loan_id | funded_amnt | paid_amnt | addr_state
2       | 1500        | 900.0     | WA
3       | 2000        | 800.0     | WA
4       | 1000        | 0.0       | TX
6       | 500         | 0.0       | NV
```

У займа 2 изменилась оплата, займ 6 добавлен.
</details>

**Задание 3.** Восстановите состояние займов на версию 1 и на версию 2 по таблице `history`.

<details><summary>Решение</summary>

```sql
SELECT loan_id, arg_max(addr_state, version) AS addr_state
FROM history WHERE version <= 1
GROUP BY loan_id HAVING arg_max(op, version) <> 'DELETE' ORDER BY loan_id;

SELECT loan_id, arg_max(addr_state, version) AS addr_state
FROM history WHERE version <= 2
GROUP BY loan_id HAVING arg_max(op, version) <> 'DELETE' ORDER BY loan_id;
```

```text
┌─────────┬────────────┐
│ loan_id │ addr_state │
│  int32  │  varchar   │
├─────────┼────────────┤
│       1 │ CA         │
│       2 │ WA         │
│       3 │ WA         │
└─────────┴────────────┘
┌─────────┬────────────┐
│ loan_id │ addr_state │
│  int32  │  varchar   │
├─────────┼────────────┤
│       2 │ WA         │
│       3 │ WA         │
└─────────┴────────────┘
```

Для каждого займа берём последнюю запись до нужной версии и отбрасываем удалённые. Так `time travel` читает снимок из журнала.
</details>
