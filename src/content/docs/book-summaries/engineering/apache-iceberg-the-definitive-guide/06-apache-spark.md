**Главная мысль:** Spark работает с Iceberg через подключённую библиотеку и каталог. SQL и DataFrame API позволяют создавать, читать и изменять таблицы, а процедуры расширений — обслуживать их.

## О чём глава

После [выбора каталога](/book-summaries/engineering/apache-iceberg-the-definitive-guide/05-catalogs/) рассмотрим настройку Spark и основные операции. Конкретная поддержка зависит от совместимых версий Spark, Scala, Iceberg и подключённых расширений.

![Spark и таблицы Iceberg](/assets/apache-iceberg-the-definitive-guide/ch06-overview.png)

На схеме Spark обращается к каталогу за метаданными и выполняет операции над файлами в хранилище. SQL, DataFrame API и процедуры используют одну настроенную среду.

## Настройка Spark и Iceberg

Spark нужен runtime Iceberg, соответствующий версиям Spark и Scala. Его можно подключить при запуске через `--packages` либо предоставить JAR. В PySpark параметры задают при создании `SparkSession`; уже созданная сессия может не применить настройки расширений задним числом. Для некоторых SQL-операций дополнительно включают `IcebergSparkSessionExtensions`.

Именованный каталог настраивают через `spark.sql.catalog.<имя>`. `SparkCatalog` подключает отдельный каталог Iceberg, например Hadoop или Hive. `SparkSessionCatalog` расширяет встроенный каталог Spark и позволяет работать рядом с таблицами других форматов. Для пользовательской реализации задают `catalog-impl`, а для особого доступа к файлам — `io-impl`.

Книга показывает Glue с `GlueCatalog` и `S3FileIO`: кроме runtime требуются совместимые зависимости AWS, адрес warehouse и права на каталог и хранилище. Секреты следует передавать через подходящий механизм учётных данных среды, а не фиксировать в SQL или исходном коде. Само подключение пакета не создаёт каталог и не настраивает права.

Каталог с типом `hadoop` получает путь warehouse, а каталог с типом `hive` — адрес Hive Metastore. С помощью полностью квалифицированного имени можно явно выбрать каталог и пространство имён вместо зависимости от текущих настроек сеанса. Для Glue дополнительно указывают реализацию каталога и ввода-вывода для S3. Сначала проверьте, что Spark может обнаружить существующую таблицу и прочитать её метаданные; это позволяет отделить ошибки подключения от ошибок конкретного запроса.

## DDL: создание и изменение таблиц

В Spark SQL `USING iceberg` выбирает формат таблиц. Имя обычно включает каталог, пространство имён и таблицу; пространство имён должно существовать. Этот Spark SQL проверен на Spark 3.5.5 и Iceberg 1.8.1 с локальным каталогом `demo` и пространством имён `shop` в [полном скрипте](https://github.com/argon4ik902/dataengineer_ru/blob/8b3d5b5fc02220ff2b5a44d87991d68ad3b3eccc/scripts/iceberg-tdg-code/register_table.py).

```sql
-- Spark SQL; проверено: Spark 3.5.5 и Iceberg 1.8.1
CREATE TABLE demo.shop.orders (
  id BIGINT,
  ordered_at TIMESTAMP,
  amount DECIMAL(10, 2)
)
USING iceberg
PARTITIONED BY (days(ordered_at));
```

В проверенном скрипте после создания и вставки одной строки таблица зарегистрирована в JDBC-каталоге; чтение вернуло `Новый каталог: 1` и `Сумма: 15.00`.

Преобразование `days` задаёт скрытое разбиение: запрос может фильтровать исходный `ordered_at`. Физическое размещение файлов не следует определять исключительно по структуре каталогов. DataFrameWriterV2 также умеет создать таблицу через `df.writeTo(...).create()` и задать разбиение через `partitionedBy`; поддерживаемые преобразования зависят от версии API.

Через DataFrame API можно сначала описать схему пустого набора, создать DataFrame, а затем вызвать `writeTo` с полным именем таблицы. Метод `partitionedBy` задаёт поля или поддерживаемые преобразования до `create()`. Важно различать создание таблицы и добавление строк: повторное создание существующей таблицы не эквивалентно безопасной вставке. Для таблицы, созданной через каталог, права на пространство имён и место хранения должны быть настроены заранее.

### ALTER TABLE

Spark позволяет добавлять, переименовывать и удалять поля, изменять поддерживаемые типы и свойства. Изменение спецификации разбиения добавлением, удалением или заменой поля меняет правило для последующих записей, но не переписывает старые файлы. Операция обслуживания может позже переписать их с текущей спецификацией.

Команды `WRITE ORDERED BY` и настройки распределения описывают желаемую организацию записи при поддержке движка. Они не гарантируют глобальный порядок всех исторических файлов. Поля идентификатора описывают идентичность строк для поддерживающих операций, но сами по себе не обеспечивают проверку уникальности как ограничение первичного ключа СУБД.

Часть операций, включая изменение разбиения и порядка записи, требует SQL extensions. Список возможностей зависит от версии; проверяйте его перед переносом примеров из книги в другую среду.

### DROP TABLE

Поведение удаления зависит от каталога и версии. В описанной книгой интеграции Iceberg начиная с версии 0.14 обычный `DROP TABLE` удаляет регистрацию, а `DROP TABLE ... PURGE` также предназначен для удаления данных. Это не универсальное обещание для всех каталогов: перед удалением проверьте документацию используемой реализации и наличие других ссылок на файлы.

## Чтение данных

`spark.table("demo.shop.orders")` возвращает DataFrame; `SELECT`, `WHERE`, агрегации и оконные функции доступны и через Spark SQL. Например, фильтр по дате может помочь отсечь разделы, если выражение поддерживается планировщиком. DataFrame остаётся ленивым описанием вычисления до запуска действия, такого как `show()` или `count()`.

Книга сравнивает SQL `RANK()` и DataFrame `row_number()`: это разные функции. При одинаковых значениях сортировки `RANK()` присваивает одинаковый ранг и может оставить пропуски, а `row_number()` нумерует строки последовательно. Если порядок между равными значениями важен, добавьте явный дополнительный ключ сортировки.

Агрегации `count`, `avg`, `sum` и `max` выполняются поверх данных таблицы как обычные операции Spark. Например, группировка сотрудников по подразделению с вычислением максимальной зарплаты возвращает одну строку на подразделение. Оконная функция, напротив, добавляет результат к каждой исходной строке. Движок может использовать метаданные для оптимизации, но наличие агрегации не означает, что чтение файлов всегда удастся избежать.

## Запись данных

### Вставка и MERGE

`INSERT INTO` добавляет строки, а DataFrameWriterV2 предлагает `df.writeTo("demo.shop.orders").append()`. `MERGE INTO` сопоставляет источник и цель, после чего выполняет подходящие условия обновления или вставки. Для его применения нужно проверить расширения и поддержку конкретной версии Spark и Iceberg. Сопоставление нескольких строк источника с одной целевой строкой требует особого внимания к правилам движка и качеству источника.

### Перезапись

`INSERT OVERWRITE` заменяет данные, а не добавляет их. В статическом режиме область замены определяется условием раздела; отсутствие ограничения может затронуть всю таблицу. Скрытые преобразования усложняют управление областью через обычный `PARTITION`.

В динамическом режиме заменяются разделы, для которых запрос выдаёт строки; DataFrameWriterV2 предоставляет `overwritePartitions()`. Пустой результат и изменение спецификации разбиения могут дать поведение, отличное от ожиданий, поэтому перед запуском необходимо проверить область замены. Для заданного предиката API также предоставляет `overwrite(condition)`.

Для динамической перезаписи книга задаёт `spark.sql.sources.partitionOverwriteMode=dynamic` до выполнения SQL. Такая настройка относится к поведению сеанса, поэтому её следует явно фиксировать вместе с заданием. При использовании DataFrameWriterV2 вызов `overwritePartitions()` выражает намерение заменить разделы через API записи. В обоих случаях входной набор определяет затрагиваемые разделы, а результат зависит от текущей спецификации и поддержки движка.

### DELETE и UPDATE

`DELETE FROM` удаляет подходящие строки, `UPDATE` изменяет их. Если условие позволяет удалить целые файлы или разделы, движок может выполнить часть работы на уровне метаданных. Иначе используются поддерживаемые режимы COW или MOR. Нельзя считать, что любое построчное удаление обязательно переписывает файл: это зависит от настроек и реализации.

## Обслуживание таблиц

Процедуры Spark Iceberg включают `rewrite_data_files` для compaction, `rewrite_manifests` для метаданных, `expire_snapshots` для сокращения истории и `remove_orphan_files` для файлов без ссылок. Их требуется запускать с правильным каталогом и расширениями. Каждая операция требует ресурсов и сопровождается ограничениями, рассмотренные в [главе 4](/book-summaries/engineering/apache-iceberg-the-definitive-guide/04-performance/).

Удаление старой истории ограничивает `time travel`, а очистка файлов без ссылок требует учитывать длительные записи. Предварительный просмотр кандидатов помогает проверить область очистки, прежде чем выполнять удаление. Следите за результатом каждой процедуры и не считайте её успешной лишь по факту запуска.

Проверенный [пример Spark](https://github.com/argon4ik902/dataengineer_ru/blob/8b3d5b5fc02220ff2b5a44d87991d68ad3b3eccc/scripts/iceberg-tdg-code/spark_table.py) создаёт временную таблицу, выполняет `INSERT`, `MERGE`, историческое чтение и compaction; его результаты приведены в [главе 3](/book-summaries/engineering/apache-iceberg-the-definitive-guide/03-write-and-read-queries/) и [главе 4](/book-summaries/engineering/apache-iceberg-the-definitive-guide/04-performance/).

## Итоги главы

- Spark требует совместимый runtime Iceberg, настройки каталога и при необходимости SQL extensions.
- SQL и DataFrame API покрывают многие операции, но не обязательно одинаковый набор возможностей.
- Изменение разбиения не переписывает старые файлы автоматически.
- Область перезаписи и поведение удаления зависят от режима и реализации.
- Процедуры обслуживания изменяют таблицу и требуют контроля результатов.

## Ключевые термины

| Термин | Значение |
|---|---|
| `SparkCatalog` | Подключение отдельного каталога Iceberg к Spark. |
| `SparkSessionCatalog` | Интеграция Iceberg со встроенным каталогом Spark. |
| DataFrameWriterV2 | API Spark для записи DataFrame в таблицы. |
| Динамическая перезапись | Замена разделов, соответствующих записанным строкам. |

## Что это значит на практике

- Фиксируйте совместимые версии Spark, Scala и runtime Iceberg в окружении.
- Проверяйте диапазон данных до перезаписи и поддержку свойств каждым движком.
- Тестируйте процедуры обслуживания на изолированной таблице до применения к рабочим данным.
