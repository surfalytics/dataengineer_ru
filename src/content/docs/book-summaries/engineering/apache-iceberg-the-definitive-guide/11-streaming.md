**Главная мысль:** Iceberg может быть источником или приёмником потоковой обработки, но гарантии и доступные изменения зависят от коннектора и всего pipeline. Частые фиксации требуют обслуживания файлов и истории.

## О чём глава

После [эксплуатации таблиц](/book-summaries/engineering/apache-iceberg-the-definitive-guide/10-production/) рассмотрим потоковую запись и чтение через Spark, Flink, Kafka Connect и сервисы AWS. Важны не только задержка, но и восстановление после сбоев, поддержка изменений и стоимость обслуживания.

![Потоковая обработка и таблица Iceberg](/assets/apache-iceberg-the-definitive-guide/ch11-overview.png)

Схема показывает источник событий, потоковую обработку, фиксации в таблице и последующее чтение.

## Spark Structured Streaming

Spark обрабатывает поток через Structured Streaming и предоставляет DataFrame API для чтения и записи Iceberg. В описанной книге интеграции потоковое чтение поддерживает добавления из `append`-состояний; обновления и удаления нельзя автоматически считать потоком CDC. Проверяйте ограничения и параметры обработки других операций для конкретной версии.

При записи `append` добавляет результаты каждого микропакета. Режим `complete`, если он поддерживается выбранным приёмником и запросом, представляет полное состояние результата и может заменять содержимое таблицы; это не режим передачи только изменений. Путь checkpoint должен быть устойчивым и отдельным для каждого логического запроса, чтобы после сбоя движок мог восстановить прогресс.

Книга описывает чтение Kafka, преобразование сообщений и запись в Iceberg с периодическим триггером. Потоковые данные в разделённой таблице могут быть распределены между несколькими разделами внутри одной задачи. `fanout`-запись позволяет держать открытые писатели по разделам без предварительной сортировки, но при большом числе разделов увеличивает потребление ресурсов. Доступность и настройки зависят от интеграции.

В примере книги Kafka содержит JSON с временем, символом, ценой и объёмом. Spark читает сообщения через `readStream.format("kafka")`, преобразует значение в структуру и записывает результат через `writeStream.format("iceberg")`. У записи задаются `outputMode("append")`, интервал триггера и `checkpointLocation`. Для реальной нагрузки необходимо явно определить схему сообщений и обработку повреждённых записей: показанная схема не решает эти вопросы автоматически.

При частой записи в разделённую таблицу данные одного микропакета могут затрагивать много разделов. Вариант с `fanout-enabled` облегчает запись без обязательной предварительной сортировки по разделам, но каждый открытый писатель расходует ресурсы. Если один микропакет содержит тысячи разделов, необходимо оценить память и файловые дескрипторы, а не считать fanout бесплатной оптимизацией.

### Чтение из Iceberg

Поток может начинаться с заданного времени и передавать добавленные данные дальше, например в таблицу партнёра. Перед этим нужно согласовать схемы, правила доступа, фильтрацию и обработку ошибок. Задание должно сохранять собственный checkpoint; новый путь checkpoint может изменить поведение запуска и не равнозначен восстановлению прежнего задания.

Проверяйте, что срок хранения состояний позволяет читателю продолжить работу после ожидаемого простоя. Если история удалена слишком рано, потребителю может не хватить информации для восстановления с прежней позиции. Мониторьте задержку, ошибки и скорость роста файлов вместе с доступностью источника и приёмника.

### Обслуживание потоковой таблицы

Каждый микропакет способен создавать новые файлы и метаданные. Слишком частые фиксации уменьшают задержку видимости, но увеличивают число мелких файлов и нагрузку на каталог. Более редкие фиксации могут снизить накладные расходы ценой задержки. Compaction, переписывание манифестов и удаление устаревших состояний нужны по измеренной необходимости, а не с одинаковой частотой для всех таблиц.

## Apache Flink

Flink предоставляет DataStream API для потоковых вычислений и Table API/SQL для декларативной работы с таблицами. Оба API могут использовать потоковые данные; выбор определяется необходимым уровнем контроля, а не только тем, ограничен ли источник. Flink поддерживает event time, окна, контрольные точки и управление обратным давлением.

### Потоковое чтение

Для SQL задают потоковый режим и параметры источника, например интервал обнаружения новых состояний и стартовый `snapshot`. Возможность задавать параметры через SQL hint зависит от настроек и версии. DataStream API предоставляет источник Iceberg и загрузчик таблицы, а также настройки стратегии начала чтения и интервала опроса.

При выборе стартового состояния важно понимать, включается ли оно в чтение или используется как граница для следующих изменений. Проверяйте эту семантику по версии коннектора и тестируйте восстановление. Файлы и история, необходимые отстающему читателю, должны оставаться доступными достаточно долго.

Этот Flink SQL проверен на Flink 1.20.5 и Iceberg 1.8.1 в изолированном контейнере с таблицей `employee` из [главы 9](/book-summaries/engineering/apache-iceberg-the-definitive-guide/09-apache-flink/) и включёнными динамическими параметрами таблиц.

```sql
-- Flink SQL; проверено: Flink 1.20.5 и Iceberg 1.8.1
SELECT * FROM employee /*+ OPTIONS('streaming'='true', 'monitor-interval'='1s') */;
```

Фактический вывод: `+I, 1, Software Engineer, Engineering, 25000.0, NA`. После вывода запрос ожидал следующее состояние и был остановлен по тайм-ауту. Проверка подтверждает начальное чтение, но не проверяет последующую фиксацию или восстановление. Для этой формы также нужно разрешить динамические параметры таблиц, если этого требует конфигурация Flink. Запрос остаётся потоковым и не обязан завершиться самостоятельно. Типы поддерживаемых изменений следует проверять отдельно: потоковое чтение не всегда воспроизводит удаления и обновления как CDC.

Начальная точка определяет, какие данные получит читатель. Читатель, начинающий с текущего состояния, может пропустить более ранние добавления; читатель, начинающий с истории, должен иметь доступ к необходимым метаданным и файлам. При перезапуске с сохранённым состоянием checkpoint используется прогресс задания, поэтому первоначальный параметр старта нельзя считать заменой проверенного процесса восстановления.

Стратегия опроса также определяет нагрузку на каталог. Короткий интервал может уменьшить задержку обнаружения новой фиксации, но приводит к более частым обращениям даже при отсутствии изменений. Реальная задержка включает подготовку файлов, завершение фиксации, обнаружение и обработку downstream, поэтому один параметр мониторинга не равен общей задержке доставки.

Книга также показывает DataStream API с `IcebergSource`, `TableLoader`, `streaming(true)` и стратегией `INCREMENTAL_FROM_LATEST_SNAPSHOT`. При такой стратегии важно проверить, что означает начальная точка в конкретной версии: она выбирается для инкрементального потребления, а не обязательно для полного начального снимка. Вариант через SQL использует hint `start-snapshot-id`; поведение на границе надо подтвердить тестом с известной историей.

Для ограничения задержки важны не только интервал опроса и размер пакета, но и длительность checkpoint и фиксации. Наблюдайте время последней успешной фиксации, отставание источника и ошибки восстановления. Если поток отстал настолько, что необходимые состояния удалены политикой хранения, продолжение с прежней позиции может оказаться невозможным.

### Потоковая запись

Flink может записывать данные через SQL, Table API или DataStream sink. Запись подготавливает файлы, а фиксация связана с контрольными точками задания. При восстановлении состояние Flink и согласованность с каталогом определяют, какие данные будут обработаны повторно и как результат станет видимым.

Для upsert нужны поддерживаемая версия формата и корректно заданные поля равенства. Изменения могут записываться как файлы данных и файлы удалений, поэтому все читатели должны их поддерживать. Заданный ключ `NOT ENFORCED` не проверяет уникальность источника; ошибки ключа могут изменить логический результат.

## Kafka Connect

Kafka Connect запускает коннекторы, которые перемещают записи между Kafka и внешними системами. Iceberg sink, описанный в книге, координирует записи в таблицы, может распределять события по нескольким целям, обрабатывать коды CDC и использовать upsert. Конкретные функции и имена параметров зависят от реализации и версии коннектора.

Конфигурация включает список таблиц, подключение к каталогу, настройки Kafka и служебного control topic, интервал и таймаут фиксации. Для маршрутизации важно определить поле и правило сопоставления с таблицей. Ошибка маршрута, несовместимая схема или недоступный каталог должны быть видимы оператору через состояние заданий и журналы.

Книга перечисляет поддержку exactly-once у рассматриваемого sink. Это гарантия в пределах определённой реализации и условий работы, а не общее свойство любого Kafka Connect pipeline. Проверяйте настройки контрольного топика, срок хранения, восстановление после сбоя и поведение источника; атомарная фиксация таблицы сама не доказывает отсутствие потерь или повторов на всём пути.

При настройке коннектора различайте параметры worker и параметры отдельного connector: первые задают работу процесса и соединение с Kafka, вторые определяют топики, таблицы и поведение конкретного задания. Набор свойств и способ регистрации зависят от режима Kafka Connect и версии коннектора. Не размещайте реальные учётные данные в опубликованной конфигурации.

В описании коннектора `iceberg.tables` задаёт целевые таблицы, `iceberg.tables.routeField` — поле маршрутизации, а `iceberg.tables.cdcField` — поле кода изменения. Параметры `iceberg.control.commitIntervalMs` и `iceberg.control.commitTimeoutMs` управляют периодичностью и ожиданием фиксации в описанной версии. Это примеры свойств книги, а не гарантия их неизменности в другой версии коннектора.

Уменьшение интервала фиксации может ускорить появление данных в Iceberg, но увеличить число файлов и состояний. Увеличение таймаута не исправляет недоступность каталога или ошибку записи. При сбое сверяйте прогресс коннектора с фактически опубликованным состоянием таблицы и проверяйте повтор обработки на изолированных данных.

## Потоковая обработка в AWS

Архитектура AWS может включать источник событий, сервис приёма и хранения потока, обработчик и конечную таблицу. Книга рассматривает Kinesis Data Streams, Firehose, сервис аналитики на Flink и управляемый Kafka через MSK. Названия, возможности и версии сервисов меняются, поэтому конкретную интеграцию и стоимость нужно проверять для своей среды.

Glue Studio может использовать Kafka или Kinesis как источник и записывать результат в Iceberg. Нужны настройка формата `iceberg`, каталога, warehouse и доступа к S3. Книга отдельно отмечает различия управления фиксацией в Glue 3.0 и 4.0; не переносите эту конфигурацию на другую версию без проверки. Пример `INSERT INTO` в существующую таблицу добавляет данные и сам по себе не создаёт таблицу.

Например, задержка потребителя может расти при успешной записи в таблицу, если обработчик не успевает за поступлением новых данных. Наблюдайте обе стороны потока и своевременно устраняйте причину отставания.

В описанной книге конфигурации Glue 3.0 с Iceberg 0.13.1 использовался DynamoDB lock manager, тогда как Glue 4.0 применял оптимистическую блокировку. Это сведения о конкретных исторических версиях, а не универсальный рецепт. При выборе другой версии проверьте совместимость каталога, библиотек и настройки фиксации.

Для внешнего приёмника полезно зафиксировать контрольные точки и источник истины для прогресса до запуска. Если обработчик публиковал агрегат, но завершился до сохранения позиции чтения, повтор может применить ту же партию ещё раз. Проверка восстановления должна охватывать именно такой порядок сбоев, а не только успешный запуск.

## Итоги главы

- Потоковая запись создаёт последовательность состояний и требует регулярного обслуживания.
- Spark и Flink предлагают разные API и ограничения потокового чтения.
- Инкрементальные добавления не равнозначны CDC всех изменений.
- Checkpoint и согласованность фиксаций необходимо проверять для всего pipeline.
- Kafka Connect и AWS предлагают разные способы доставки данных в таблицу.

## Ключевые термины

| Термин | Значение |
|---|---|
| Микропакет | Конечная порция потока, обработанная за один запуск обработки. |
| `Checkpoint` | Сохранённое состояние обработки для восстановления задания. |
| `Fanout writer` | Запись по нескольким разделам без предварительной сортировки по ним. |
| CDC | Передача сведений о вставках, изменениях и удалениях. |

## Что это значит на практике

- Проверяйте поведение источника при обновлении и удалении, а не только при добавлении.
- Согласуйте срок хранения истории с максимально допустимым отставанием читателя.
- Измеряйте компромисс между частотой фиксации, задержкой и числом файлов.
