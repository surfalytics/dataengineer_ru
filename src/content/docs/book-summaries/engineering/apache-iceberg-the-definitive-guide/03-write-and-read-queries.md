**Главная мысль:** Движок записывает новые файлы и метаданные, затем согласованно фиксирует новую версию через каталог. При чтении он проходит по метаданным выбранного состояния и определяет, какие файлы нужны запросу.

## О чём глава

В [главе 2](/book-summaries/engineering/apache-iceberg-the-definitive-guide/02-architecture/) разобрано дерево метаданных. Теперь проследим создание таблицы, вставку, `MERGE`, обычное и историческое чтение. Примеры книги используют Spark SQL и Dremio; поддержка синтаксиса зависит от версии и настройки движка.

![Запись и чтение через каталог и метаданные Iceberg](/assets/apache-iceberg-the-definitive-guide/ch03-overview.png)

Схема показывает, как запись готовит данные и метаданные до фиксации в каталоге.

## Запросы на запись

Движок разбирает запрос, получает текущее состояние таблицы через каталог, проверяет схему и спецификацию разбиения. Затем он подготавливает файлы данных и метаданные. Последний шаг — фиксация, которая делает новую версию видимой. Конкретные шаги внутри движка могут отличаться, но подготовленные файлы сами по себе ещё не означают успешную фиксацию.

### Создание таблицы

Книга использует таблицу заказов с разбиением по часу исходного времени заказа. Скрытое разбиение позволяет задать преобразование, не добавляя отдельный пользовательский столбец часа. Этот Spark SQL проверен в локальном Hadoop catalog на Spark 3.5.5 и Iceberg 1.8.1; полный [скрипт](https://github.com/argon4ik902/dataengineer_ru/blob/8b3d5b5fc02220ff2b5a44d87991d68ad3b3eccc/scripts/iceberg-tdg-code/spark_table.py) создаёт временную таблицу.

```sql
-- Spark SQL; проверено: Spark 3.5.5 и Iceberg 1.8.1
CREATE TABLE orders (
  order_id BIGINT,
  customer_id BIGINT,
  order_amount DECIMAL(10, 2),
  order_ts TIMESTAMP
)
USING iceberg
PARTITIONED BY (hours(order_ts));
```

Движок создаёт метаданные со схемой, идентификаторами полей, спецификацией разбиения и идентификатором таблицы. Каталог регистрирует таблицу и её текущий файл метаданных. При создании пустой таблицы `snapshot` может ещё отсутствовать: утверждение книги о том, что каждый `CREATE` обязательно создаёт начальный `snapshot`, не следует считать общим правилом для всех реализаций.

### Вставка

При `INSERT` движок получает текущую схему и разбиение, записывает строки в файлы данных, затем подготавливает файлы манифестов, список манифестов и новые метаданные со сведениями о новом `snapshot`. При записи манифест может получить число строк, границы значений и количество `null`. Существующие манифесты, относящиеся к новому состоянию, могут повторно использоваться.

В конце движок пытается атомарно обновить ссылку каталога с исходной версии на подготовленную. Если другая запись успела зафиксироваться, требуется повторная проверка и, при необходимости, повтор или отказ операции. Возможность повтора зависит от вида изменения и правил проверки конфликтов. Пока фиксация не завершена, обычный читатель не должен считать подготовленные файлы частью нового состояния.

Для наглядности представим вставку заказа с номером 123 и временем 7 марта в 08:10. Преобразование часа определяет значение раздела, а движок записывает саму строку в файл данных. Запись о файле содержит его расположение и статистику. Список манифестов связывает описание файла с новым состоянием, а новый файл метаданных указывает на это состояние как на текущее. Названия физических файлов и размещение зависят от реализации и настроек.

При чтении до завершения фиксации другая задача продолжает видеть ранее опубликованное состояние. После успешного переключения новый читатель, получивший актуальные метаданные, может увидеть вставку. Уже запланированный запрос при этом продолжает работать со своим выбранным состоянием: фиксация не должна незаметно менять набор его файлов в середине чтения.

### Изменение через MERGE

`MERGE INTO` сопоставляет данные источника и целевой таблицы по условию. Например, существующему заказу можно обновить сумму, а новый заказ вставить. Следующий Spark SQL проверен в полном примере на Spark 3.5.5 и Iceberg 1.8.1 после создания таблицы и временного представления `orders_staging`.

```sql
-- Spark SQL; проверено: Spark 3.5.5 и Iceberg 1.8.1
MERGE INTO orders AS target
USING orders_staging AS source
ON target.order_id = source.order_id
WHEN MATCHED THEN UPDATE SET target.order_amount = source.order_amount
WHEN NOT MATCHED THEN INSERT *;
```

При `copy-on-write` затронутые файлы переписываются: неизменённые строки этих файлов тоже должны сохраниться в новом результате. При `merge-on-read` движок может записать сведения об удалениях и новые данные отдельно. Выбор определяется настройками операции и поддержкой движка. Новые манифесты и метаданные фиксируют изменившийся состав файлов; другие файлы могут остаться общими для нескольких состояний.

Предположим, что источник содержит обновление суммы заказа 123 и новый заказ 124. Движок сопоставляет строки по номеру заказа, изменяет совпавшую строку и добавляет отсутствующую. При COW файл со старой строкой перестаёт входить в новое состояние, но может оставаться доступным прежнему состоянию. Новый заказ с другим часом может попасть в другой раздел. Реальные распределение и число файлов определяет план записи.

## Запросы на чтение

### Обычный SELECT

Движок получает из каталога файл текущих метаданных, находит нужный `snapshot` и его список манифестов. Далее он использует сведения о разбиении и границы значений, чтобы исключить заведомо неподходящие манифесты и файлы. После этого он читает выбранные данные и применяет оставшиеся условия запроса; файлы удалений также учитываются, если они применимы.

Например, при фильтре по январю движок может исключить файл с данными только за март, если доступная статистика это доказывает. Но пересечение границ ещё не гарантирует наличие подходящих строк: это только основание оставить файл в плане. Неполная статистика или неподдерживаемый предикат могут уменьшить пользу отсечения. Разбиение и метаданные не гарантируют фиксированную скорость запроса.

Отбор проходит несколько уровней. Сводки в списке манифестов помогают исключить целые файлы манифестов; записи в оставшихся файлах позволяют проверить отдельные файлы данных. Затем сам формат файла может предоставить дополнительные сведения, например статистику групп строк Parquet. Отсечение на одном уровне не заменяет проверку на остальных.

### Time travel

`Time travel` читает сохранённое прошлое состояние по идентификатору `snapshot` или времени. Это полезно для воспроизведения отчёта или анализа данных до ошибочного изменения. Текущий файл метаданных помогает найти выбранное состояние, затем движок проходит по его списку манифестов и читает относящиеся к нему файлы.

В проверенном скрипте Spark SQL получает идентификатор после первой записи и подставляет его в запрос до чтения:

```python
first = spark.sql("SELECT snapshot_id FROM catalog.db.orders.snapshots").first().snapshot_id
for label, table in (("До MERGE", f"orders VERSION AS OF {first}"), ("После MERGE", "orders")):
    rows = spark.sql(f"SELECT order_id, order_amount FROM {table} ORDER BY order_id").collect()
```

В полном примере имя таблицы формируется внутри цикла и передаётся в `spark.sql`. Идентификатор создаётся при запуске, поэтому его нельзя заменить заранее заданным числом.

В проверенном Spark-примере чтение до и после `MERGE` вернуло:

```text
До MERGE [(1, '19.00')]
После MERGE [(1, '22.00'), (2, '15.00')]
```

В Dremio книга показывает другую форму: `SELECT * FROM orders AT SNAPSHOT <snapshot_id>`. Для времени Spark использует `TIMESTAMP AS OF`, а Dremio — `AT TIMESTAMP`. Доступность синтаксиса зависит от версии. При выборе по времени берётся подходящее состояние не позднее указанного момента; если его нет, запрос завершается ошибкой. Удаление устаревших состояний или необходимых файлов ограничивает доступную историю.

Историю состояний можно изучать через таблицы метаданных, предоставляемые движком. Книга показывает `orders.history` в Spark и функцию `table_history` в Dremio. По истории находят время фиксации и идентификатор нужного состояния, после чего используют подходящую форму запроса. Результат исторического чтения не равен откату: откат отдельно изменяет текущую ссылку таблицы.

На схеме показан порядок чтения: выбранный `snapshot` указывает на список манифестов, а метаданные помогают выбрать файлы данных.

### Практика с PyIceberg

Проверенный [скрипт table_history.py](https://github.com/argon4ik902/dataengineer_ru/blob/8b3d5b5fc02220ff2b5a44d87991d68ad3b3eccc/scripts/iceberg-tdg-code/table_history.py) создаёт настоящий локальный каталог SQLite и таблицу Iceberg, дважды добавляет данные и читает первое и текущее состояния. Для запуска нужны Python 3.12, `pyiceberg[sql-sqlite,pyarrow]==0.10.0`, `pyarrow==26.0.1` и `sqlalchemy==2.1.9`; затем выполните `python scripts/iceberg-tdg-code/table_history.py` в подготовленном окружении. Временная директория удаляется после завершения.

Фактический вывод проверенного запуска:

```text
Число snapshot: 2
После первой записи: [1, 2]
Сейчас: [1, 2, 3]
Файлов данных в текущем snapshot: 2
```

Первая запись остаётся доступной по её идентификатору, хотя текущее состояние уже включает третью строку. Это проверка PyIceberg с локальным каталогом, а не проверка Spark или Dremio.

## Итоги главы

- Создание таблицы регистрирует её схему и другие метаданные в каталоге.
- Запись сначала подготавливает файлы, а затем фиксирует новую версию через каталог.
- Конкурентные изменения проверяются перед фиксацией и могут потребовать повтора или завершиться конфликтом.
- При чтении статистика и разбиение помогают исключить ненужные файлы.
- Историческое чтение выбирает сохранённый `snapshot`, а не изменяет текущее состояние.

## Ключевые термины

| Термин | Значение |
|---|---|
| Фиксация изменения | Шаг, после которого подготовленная версия становится текущей. |
| `Snapshot` | Зафиксированное состояние данных таблицы. |
| Отсечение | Исключение файлов из чтения по условиям и метаданным. |
| `Time travel` | Чтение сохранённого исторического состояния. |

## Что это значит на практике

- Проверяйте результат фиксации, прежде чем считать записанные файлы видимыми читателям.
- Анализируйте план запроса и фактически прочитанные файлы, чтобы оценить пользу отсечения.
- Настраивайте срок хранения истории под требования к воспроизводимости и откату.
