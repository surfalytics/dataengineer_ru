**Главная мысль.** Агент может менять SQL до первого успешного запуска. Чтобы поручить ему инженерную задачу, нужно заранее определить, где он вправе пробовать варианты, какими данными может пользоваться и какой результат подтвердит правильность решения.

## О чём глава

В предыдущей главе авторы обсуждали основания доверия к ответу аналитического ассистента. Здесь они рассматривают другого участника — инженера, который с помощью Claude Code меняет сам процесс обработки. Модель пишет SQL, запускает его, читает результат, меняет подход и повторяет попытку. Если пробовать изменения в общей базе, ошибка одной сессии станет входом для другой. При отсутствии независимого теста успешное исполнение запроса легко принять за решение задачи. Авторы связывают возможное десятикратное ускорение с тремя слоями инженерной работы.

## Первый слой. Среда ветвится вместе с кодом

Например, ветку Git создать легко, но она изолирует только исходный текст. Два разработчика с разными ветками всё ещё могут перезаписать одну промежуточную таблицу или занять одни и те же вычислительные ресурсы. Снаружи невозможно понять, какая версия кода создала наблюдаемое состояние базы. Журнал человеческих действий полезен при разборе происшествия, но он не предотвращает взаимное влияние сессий.

Авторы проводят аналогию с многоверсионным управлением конкурентным доступом (MVCC). Каждый участник работает с согласованной версией данных и видит собственные изменения. В DataKitchen такую рабочую среду называют Kitchen. Она объединяет ветку кода, указатель на репрезентативные тестовые данные и отдельный вычислительный контекст. Снимок с копированием при записи позволяет читать общие исходные блоки. Новые данные появляются в слое конкретной среды. Доступы задаются через интерфейс управления средой, а ход выполнения хранится в записи Order Run.

![Как ветка среды ограничивает изменения одного эксперимента](/assets/dataops-way-to-data-quality/ch49-env.png)

Единица работы становится обозримой. Агент меняет одно преобразование, запускает его на копии и читает результат. Другой агент или разработчик в это время может проверять альтернативу. Ничьи непроверенные таблицы не становятся общей входной зависимостью. Когда инженер примет решение, он сможет выпустить выбранное изменение и освободить остальные среды. Поэтому за эффект изоляции отвечают фактические границы доступа к коду, данным и вычислениям.

## Второй слой. Четыре свойства FITT

**Functional.** Для конкретной версии кода известны входы, а выход можно воспроизвести. Сырьё хранится неизменяемым. Скрытая зависимость от времени, текущего состояния соседней таблицы или результата вчерашнего запуска нарушает это свойство. Чтобы оценить правку, агенту нужна возможность повторить расчёт на том же входе.

**Idempotent.** Повторный запуск приводит целевую таблицу к тому же состоянию. Одно лишь использование SQL этого не гарантирует. Повторный `INSERT` допишет строки, а обычный `CREATE TABLE AS SELECT` наткнётся на существующую таблицу. Авторы предлагают явно задавать временное окно и контролировать состояние собственного результата. Такой небольшой функциональный, идемпотентный шаг они называют FI chunk. Исправление превращается в повторяемый опыт — прошлые неудачные прогоны не накапливают дубликаты.

**Tested.** Ожидаемый результат определяется тестами. Сам состав данных должен проявлять пограничные случаи: позднюю запись, отмену заказа, изменение схемы. Маленькая синтетическая выборка может быть удобной для поиска опечатки и скрыть ошибку в производственной логике.

**Two-stage.** У процесса два устойчивых состояния. В сыром слое лежит именно то, что пришло, со временем получения. Из него строится конечный аналитический результат. Промежуточные вычисления возможны, но они не должны требоваться как самостоятельная история, которую придётся восстанавливать перед перезапуском. Один и тот же процесс должен уметь пересчитать день или несколько месяцев по заданным границам периода.

![Путь входа через идемпотентное преобразование и тесты](/assets/dataops-way-to-data-quality/ch49-fitt.png)

Для агента это даёт небольшой объект изменения и понятный критерий завершения. В своей среде он записывает результат, прогоняет проверки и только затем предлагает выпуск. Авторы связывают этот порядок с подходом Write–Audit–Publish. Идемпотентность нужна и без агента, но при автоматическом повторе она становится особенно важной: иначе ошибка увеличивается с каждой попыткой.

## Третий слой. Откуда приходит обратная связь

Производственные проверки следят за свежестью, объёмом, схемой и распределением значений. Проверки разработки выясняют, сохранилось ли нужное поведение после правки. При этом часть правил годится для обоих случаев. Авторы используют эвристику 1:10:100 для сравнения стоимости предупреждения, промежуточного исправления и устранения проблемы после передачи потребителю. Относительные масштабы иллюстрируют смысл раннего обнаружения.

По оценке авторов, около 80% нужных проверок покрывают автоматически получаемые правила согласованности. Остальные 20% зависят от предметной области. Профиль может заметить изменившуюся долю пустых значений, но не знает, в какие дни запрещены отгрузки. Показанный авторами TestGen генерирует проверки по схеме и профилю. Решение о том, какие ограничения бизнеса должны остановить выпуск, принадлежит команде.

У агента появляется внешняя обратная связь. Он меняет код, исполняет его на снимке, получает нарушение конкретного правила и повторяет попытку. Иногда проблема остаётся и требует человеческого решения — например, какой допуск приемлем при расхождении между отчётными периодами. Важна и сквозная проверка. Благодаря ей можно поймать несовместимость шагов, каждый из которых проходит собственные модульные тесты.

## Как команда сохраняет контекст работы

Авторы описывают практики своих сессий Claude Code. Соглашения и устойчивые определения хранят в версионируемом `CLAUDE.md`, а ход длинной задачи фиксируют в документе с требованиями. Перед изменениями проверяют план и допущения. Узкая постановка задачи даёт обозримую разницу между версиями. Перед очисткой контекста сохраняют работу на диске. Упомянутый авторами ориентир для очистки — 75% заполненного контекста. Эти приёмы полезны лишь в той мере, в какой позволяют другому человеку воспроизвести решение и проверить результат.

## Пример. Три варианта загрузки продаж

Старое преобразование зависело от скрытого состояния, ломалось при повторном запуске и в неудачный день занимало 40 минут. В иллюстрации главы инженер заводит три изолированные среды с одинаковыми исходными данными и общим набором проверок. В каждой проверяется отдельная стратегия.

| Вариант | Что увидел инженер |
|---|---|
| Параметризованное окно | После четырёх попыток пройдено 86% тестов. Поздние записи дают расхождение между периодами. |
| Явная промежуточная таблица | Пройдено 94%. Остался случай частично исполненного, затем отменённого заказа. |
| Полная пересборка из сырья | Пройдено 100%. Выполнение на снимке занимает восемь минут при рабочем интервале в пятнадцать. |

![Три экспериментальные среды и результаты общих тестов](/assets/dataops-way-to-data-quality/ch49-choices.png)

Инженер изучает изменение для полной пересборки и выбирает его. Код других вариантов, тестовые записи и вычислительные контексты можно убрать независимо. По описанию авторов, работа, на которую последовательно ушёл бы день, в примере заняла менее двух часов. Мерой выигрыша здесь служат время до проверенного изменения и участие инженера. Число сгенерированных строк вообще не показывает, стала ли загрузка правильнее.

## Итоги главы

Начинать авторы предлагают с тестов критичных преобразований. По их опыту, даже 50% покрытия на важных шагах меняет объём задач, доступных агенту. Затем один проблемный шаг делают идемпотентным, создают изолированную среду и лишь после этого подключают агента. Этот порядок позволяет оценить качество результата до масштабирования работы.

## Ключевые термины

| Термин | Значение |
|---|---|
| Kitchen | Название изолированной среды разработки в DataKitchen. |
| FI chunk | Небольшое функциональное и идемпотентное преобразование. |
| Zero-copy clone | Снимок, использующий общие исходные блоки и сохраняющий изменения отдельно. |

## Что это значит на практике

> **Пояснение:** Возьмите одну загрузку, которую опасно перезапускать. Зафиксируйте версию входов, выполните её дважды на копии и сравните результат. Если второе исполнение меняет число заказов, этот дефект надо устранить до экспериментов с автоматическими повторами.
