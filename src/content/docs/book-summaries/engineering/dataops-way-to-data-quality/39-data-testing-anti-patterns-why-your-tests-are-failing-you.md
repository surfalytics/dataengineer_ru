**Главная мысль.** Набор тестов может внушать ложную уверенность, если сообщает об обычных колебаниях и пропускает ошибки, которые доходят до пользователя. Авторы предлагают посмотреть, какое решение команда принимает по результату каждой проверки.

## О чём глава

В [предыдущей главе](/book-summaries/engineering/dataops-way-to-data-quality/38-data-production-tripwires-in-databricks-stop-bad-data-before-it-reaches-production/) блокирующая проверка останавливала перенос дефектных данных между слоями. Однако для этого она должна отличать дефект от нормального поведения таблицы. Семь типичных ошибок показывают, почему большая коллекция зелёных тестов порой даёт слабую защиту.

![Как выбрать ожидание для проверки](/assets/dataops-way-to-data-quality/ch39-expectations.png)

У каждого правила должен быть предмет проверки. Для выручки это диапазон, для справочника — известное множество кодов, для таблицы событий — объём новых записей.

## Две ошибки в ожидаемых значениях

Если за день пришло 1 234 567,89 единицы выручки, из этого ещё не следует, что завтра ожидается та же сумма. Правило с одним разрешённым числом начнёт падать при каждой нормальной операции. Для валют или статусов заказа перечень допустимых значений уместен, поскольку его задаёт бизнес. А дневную выручку авторы предлагают проверять на положительность и сопоставлять с тем же днём прошлой недели, например с допуском 30%.

Вторая ошибка — зафиксировать увиденные во вторник 10 423 строки. Как только добавятся ещё 200, команде придётся менять число или отключать тест. В примере dbt авторы используют `dbt_utils.equality`. Он сравнивает строки с эталонной моделью.

> **Пояснение:** для проверки одного лишь объёма достаточно сравнить `COUNT(*)` обеих таблиц. Для таблицы событий сравнивают дневной прирост с историей приростов. При полной перезагрузке справочника авторы советуют искать падение объёма более чем на 5% относительно прошлого запуска.

## Оповещения и сопровождение

Если в канал приходит больше 20 сообщений за день и инженеры уже отключили уведомления, следующий реальный сбой тоже могут не заметить. Сигналы стоит разделить по приоритетам P1, P2 и P3, учесть выходные и окна загрузки, а пороги подобрать по истории. По правилу авторов больше трёх срабатываний за неделю без соответствующего инцидента требуют пересмотра порога.

![Глубина тестирования по значимости таблиц](/assets/dataops-way-to-data-quality/ch39-tiers.png)

Глубину проверки выбирают по последствиям для потребителя. Например, если 500 тестов выполняются 45 минут, а около 40% красных сигналов относятся к давно заброшенным таблицам, добавление проверок мало поможет. Авторы предлагают поручить владельцу таблицы и её тесты. Раз в квартал команда тратит 30 минут на правила, которые падали более 30 дней без реакции. Содержать 100 актуальных тестов на 20 важнейших таблиц полезнее, чем игнорировать 2 000 бесхозных.

## Зелёный запуск и ошибочный результат

Успешный статус загрузки и совпавшее число строк не выявят соединение по неправильному ключу, сдвиг периода на один день или устаревший валютный курс. Для выручки можно сверить детализацию и итог с допуском 0,1%. Для атрибуции проверяют существование пользователя, для складских остатков — допустимость отрицательного количества у товара с разрешённым отложенным заказом. При закрытии счёта сумма позиций должна совпасть с итогом.

Проверки часто концентрируются у источника: данные там устроены проще. В результате сырая таблица может получить 50 тестов, а отчёт о выручке для руководства — всего два. Авторы предлагают взять 20 таблиц, на которые действительно опирается бизнес, и пройти от востребованных дашбордов к исходным зависимостям. Частоту обращений подскажут BI-команда и каталог данных.

## Два расписания и три критерия

![Разные события запускают разные проверки](/assets/dataops-way-to-data-quality/ch39-triggers.png)

CI проверяет последствия изменения программы. Если поставщик начал присылать пропуски во вторник, а новую версию кода никто не выпускал, CI не запустится. Поэтому критичные рабочие таблицы авторы проверяют как минимум ежедневно, быстро обновляемые — после каждой загрузки. Задания свежести dbt или SQL в оркестраторе позволяют сделать это существующими средствами.

Полезный тест замечает реальный сбой, пропускает корректные данные и подсказывает, что исправить. По этим признакам команда решает, какое правило сохранить, перенастроить или удалить.

## Практика в DuckDB

> **Пояснение:** в SQL-примере книги для дневных событий нижний множитель равен 0,5, верхний равен 2,0. Если событий сегодня нет, группировка не создаст строку сегодняшнего дня. В примере ниже текущий день задан явно, а прошлые дни представлены отдельными строками.

При истории в 100 событий за день сравните результат для 0, 50, 200 и 201 события. Повторите проверку для ровных граничных значений.

```sql
WITH history AS (
    SELECT day, 100 AS added FROM range(1, 15) AS days(day)
), observed AS (
    SELECT * FROM (VALUES (0), (50), (200), (201)) AS today(added)
)
SELECT observed.added,
       observed.added BETWEEN AVG(history.added) * 0.5
                          AND AVG(history.added) * 2.0 AS in_range
FROM observed CROSS JOIN history
GROUP BY observed.added ORDER BY observed.added;
```

```text
0   false
50  true
200 true
201 false
```

## Итоги главы

- История таблицы помогает отличить нормальное изменение выручки или объёма от дефекта.
- Доступные бизнесу значения статуса берут из согласованного перечня.
- Для оповещения выбирают получателя, приоритет и условие пересмотра порога.
- Проверка содержимого выявляет ошибки, которые пропускает мониторинг выполнения.
- Покрытие важных таблиц пересматривают с их владельцами и потребителями.
- Рабочие данные проверяют по графику поступления независимо от изменений кода.

## Ключевые термины

| Термин | Значение |
|---|---|
| Ложное срабатывание | Сигнал, который пришёл при допустимых данных. |
| Карта покрытия | Перечень важных таблиц с привязанными к ним проверками. |

## Что это значит на практике

> **Пояснение:** Для отчёта, на который бизнес жалуется при зелёном CI, найдите последнее вычисление показателя. Проверьте его результат на данных рабочей среды и договоритесь, кто будет разбирать отклонение.
