**Главная мысль.** Чтобы перейти от нескольких тысяч таблиц к общей оценке качества, недостаточно найти в каталоге Microsoft функцию со словом *quality*. Нужно связать профиль, правило, конкретный запуск, результат и реакцию людей. По оценке авторов, значительная часть этой работы остаётся за командой.

## О чём глава

В обзоре 2026 года DataKitchen насчитала 19 позиций в четырёх таблицах возможностей пяти продуктов. Это подсчёт строк сравнения, а не независимых движков. Например, Fabric Activator встречается дважды, поскольку служит разным задачам. В качестве сквозного примера авторы рассматривают организацию с 4 000 таблиц. Ей нужно обследовать данные, проверить известные правила, заметить неожиданное изменение и объяснить состояние человеку, который не писал тесты.

## 1. Что именно исследует профиль

В Purview Unified Catalog пользователь выбирает актив, открывает профиль и получает статистику отдельных столбцов: распределения, границы, стандартное отклонение, уникальность и полноту. Рекомендации помогают выбрать поля. При этом профилирование работает на случайной выборке до **1 млн строк**. Для большой Delta-таблицы счётчики поэтому могут отличаться от полного подсчёта. Хранятся до 50 снимков. Запускает операцию человек для каждого актива. Двадцать таблиц так обследовать нетрудно, несколько тысяч — уже другая задача.

Важно отличать эту операцию от сканирования метаданных Data Map. Последнее берёт первые **128 строк** для классификации и извлечения схемы. Оно может подсказать, на что похоже значение, но не отвечает, какая доля столбца пуста. И это ещё не сканирование качества, которое затем читает строки для выполнения правил.

У Power Query автор выделяет три представления: качество столбца с допустимыми, пустыми и ошибочными значениями, распределение и подробный профиль. По умолчанию исследуются первые **1 000 строк**. Можно выбрать весь набор, но тогда редактор повторно сканирует его при изменениях. Data Wrangler в блокноте Fabric даёт похожий интерактивный разбор DataFrame. Когда пользователь закрывает редактор, общей истории для мониторинга не появляется.

Для локального SQL Server остаётся старый SSIS Data Profiling Task. Он может выполняться по расписанию, находить кандидатов в ключи и функциональные зависимости. Однако результат сохраняется в XML для отдельного просмотрщика. Встроенного условного перехода к следующей задаче на основании этого профиля нет. Поэтому наличие профиля и возможность использовать его как автоматическую проверку нужно выяснять по отдельности.

## 2. Где выполняются правила

**Проверка строки** отвечает, допустима ли конкретная запись. **Агрегатная проверка** рассматривает множество записей: например, ниже ли доля пропусков 20%. Построчное условие для обязательного поля не выражает допустимый процент пропусков во всём наборе. В книге сравниваются пять способов исполнения таких правил.

| Средство | Где и как проявляется нарушение |
| --- | --- |
| Purview Unified Catalog | Отдельный скан рассчитывает результаты и оценки, которые можно сворачивать до домена. |
| Ограничения материализованного lake-представления Fabric | При обновлении представления ошибочные строки исключаются или обновление останавливается. |
| Assert в ADF и Synapse | Правила действуют внутри соответствующего mapping data flow. |
| Ограничения T-SQL | В SQL Server и Azure SQL отклоняется запись, нарушившая реально применяемое ограничение. |
| Задание dbt в Fabric | Тесты хранятся в Git с моделями, а `dbt build` может остановить зависимую модель. |

**Purview.** Авторы насчитывают восемь шагов до первого теста. В том числе нужны права ответственного, регистрация и сканирование источника, а для проверки качества — отдельное подключение. Готовые правила оценивают шесть измерений: точность, полноту, соответствие, согласованность, свежесть и уникальность. Пользовательское правило включает условие успешной строки, необязательный фильтр и политику для пропусков. Доступны регулярные выражения, язык выражений ADF и Spark SQL с подзапросами и оконными функциями.

Например, расчёт доли пропусков берёт среднее от признака `NULL`, а оконный счётчик с группировкой по идентификатору обнаруживает повторы. В коррелированном подзапросе важно явно указывать, к какой таблице относится поле: без квалификатора сравнение с внешней строкой может превратиться в сравнение поля с самим собой. Проверка формально исполнится, хотя вместо минимума по группе будет взят глобальный минимум.

Оценка Purview делит число прошедших строк на сумму прошедших, ошибочных, пустых и не приведённых к типу. Исключённые строки покидают знаменатель. Поэтому, убрав из расчёта проблемную категорию, можно улучшить балл без исправления данных. Далее оценки сворачиваются от столбца к активу, продукту и домену. Платёж привязан к управляемым активам и вычислениям сканирования, а значит, растёт и с числом таблиц, и с частотой проверок.

Для одного актива книга указывает предел в **200 активных правил**. На таблице из 300 столбцов этого не хватит даже для одного правила на столбец. Пользовательский SQL работает с одним набором и не поддерживает произвольные соединения между таблицами. Справочная проверка возможна при дополнительных ограничениях. Поэтому сквозную сверку поставки из SAP с итогом хранилища не заменить произвольным SQL в интерфейсе Purview. Кроме того, сканирование после расчёта итоговой таблицы диагностирует уже опубликованное нарушение.

**Fabric и ADF.** Для материализованного представления `ON MISMATCH DROP` исключает ошибочную строку из результата и учитывает количество исключений. При таком режиме сами исключённые строки не сохраняются в карантин. `ON MISMATCH FAIL` останавливает обновление и служит действием по умолчанию. При сочетании ограничений обновление останавливается. Условия задают вручную и применяют при обновлении этого представления. В ADF/Synapse проверка Assert доступна внутри mapping data flow. На другие способы преобразования, например хранимые процедуры, это покрытие автоматически не распространяется. Описанный авторами перенос таких преобразований в Fabric в июне 2026 года ещё имел статус предварительной версии.

**SQL Server и dbt.** В обычном SQL Server ограничения `NOT NULL`, `CHECK`, `UNIQUE` и внешние ключи способны защитить запись непосредственно в момент изменения. Однако они не создают балл качества и пропускают статистические сдвиги, если отдельные значения разрешены. Более того, ограничения в Fabric Warehouse с `NOT ENFORCED` не дают той же гарантии, а часть объявлений ключей для Fabric Lakehouse вообще недоступна. В описанной версии задания dbt в Fabric использовался dbt Core 1.9 и четыре адаптера. Режим предварительной версии и набор поддерживаемых адаптеров относятся к периоду книги. В проекте dbt есть история Git и тесты рядом с моделями, но для 4 000 таблиц всё равно придётся обеспечить реальное покрытие.

![Чем завершится дефект при разных способах контроля](/assets/dataops-way-to-data-quality/ch62-enforce.png)

## 3. Кто следит за изменением во времени

Тест сравнивает данные с известным правилом. Мониторинг нужен и тогда, когда заранее неизвестно, какой порог оказался бы правильным. Авторы выделяют свежесть, объём, схему и числовые метрики.

Правило свежести Purview даёт бинарную оценку 100 или 0 и поддерживается не для всех источников. По нему не видно, какова величина опоздания. Activator может реагировать на отсутствие очередного события или на результат SQL-запроса с заданным порогом. Например, если воскресный объём обычно вдвое меньше, постоянная нижняя граница создаст ложные срабатывания, пока инженер сам её не изменит.

Power BI умеет находить и объяснять аномалии на линейном графике временного ряда, но пользователю приходится открыть отчёт. Эта функция не записывает результат регулярного сканирования и не вызывает дежурного. Более развитое непрерывное обнаружение есть в Fabric Real-Time Intelligence. Для него нужны данные в Eventhouse с KQL-базой, а для описанного расширенного сценария — Python plugin. Например, `series_decompose_anomalies()` может исследовать историю количества строк, когда кто-то уже обеспечил её доставку из нужной таблицы.

![Как различаются механизмы наблюдения](/assets/dataops-way-to-data-quality/ch62-monitor.png)

Изменение схемы также можно пропустить, даже если запись надёжно защищена. ADF допускает дрейф или отклоняет несовместимый вход в зависимости от настройки. Delta отклоняет несовместимую запись или допускает эволюцию схемы в соответствующем режиме. Транзакционный журнал Delta сохраняет историю. Но без дополнительного процесса он сам не сообщит пользователям, когда и почему столбец изменился.

## 4. Как собрать отчёт для руководителя

В Purview Health Management готовая оценка поднимается до домена и показывает историю проверок. Авторы предупреждают, что готовый отчёт не настраивается произвольно. Для обновления нужны отдельные *health controls* и подписка метаданных на self-serve analytics. Эти контроли оценивают в том числе назначение владельцев и наличие описаний. Если забыть о зависимости, на экране может сохраниться устаревший показатель.

Для своей панели Purview выгружает метаданные в OneLake или ADLS Gen2. Команда строит семантическую модель и отчёт Power BI. Отдельный отчёт Fabric показывает количество нарушений по ограничениям материализованных представлений в конкретном lakehouse. Наконец, результаты разных движков можно складывать в свои таблицы аудита и читать через Power BI или SSRS. За схему и поддержку такой интеграции отвечает её разработчик. Очередь действий Purview помогает разбирать проблемы, а Activator посылает уведомления; сами по себе эти механизмы не создают сводную панель.

## Что останется на локальной платформе

Data Quality Services и Master Data Services были удалены из SQL Server 2025, согласно обзору авторов. В более ранних версиях DQS умел очищать и сопоставлять записи. Purview измеряет качество, и эту работу по исправлению он не заменяет. Авторы признают ту же границу у собственного TestGen. Для локального SQL Server работают ограничения T-SQL и профилировщик SSIS. Сканирование качества Purview, по описанию книги, требует локальной среды Kubernetes, а профилирование для такого источника недоступно. Существуют также ограничения правил свежести и поддерживаемых выражений.

Из 19 позиций авторы пометили 12 как включающие ручную работу. Сквозной процесс может потребовать шести или семи средств с отдельными расписаниями. Если в доменную оценку вошли только таблицы, на которые хватило времени написать правила, высокая оценка характеризует эту выборку. Для измерения точности понадобится ещё и достоверный эталон. Сочетание балла с фактическим покрытием помогает руководителю понять, какое решение по нему можно принять.

## Проверка примеров

> **Пояснение:** редакция воспроизвела в DuckDB два выражения из главы на четырёх платежах. Для одного отсутствует сумма, у двух совпадает идентификатор. Проверка доли пропусков строго меньше 0,20 и оконный подсчёт повторов дали следующий результат. [Скрипт проверки](https://github.com/surfalytics/dataengineer_ru/blob/main/scripts/dataops-way-to-data-quality-code/ch62_sql_rules.py)

```python
    null_rate, passes = connection.execute("""
        SELECT avg(CASE WHEN amount IS NULL THEN 1 ELSE 0 END) AS rate,
               avg(CASE WHEN amount IS NULL THEN 1 ELSE 0 END) < 0.20 AS passes
        FROM payments
    """).fetchone()
    violations = connection.execute("""
        SELECT count(*) FROM (
            SELECT count(*) OVER (PARTITION BY vendor_id) AS occurrences FROM payments
        ) AS measured WHERE occurrences > 1
    """).fetchone()[0]
    print(f"Доля пропусков: {null_rate:.2f}; проверка: {passes}")
    print(f"Строк с повторяющимся идентификатором: {violations}")
```

```text
Доля пропусков: 0.25; проверка: False
Строк с повторяющимся идентификатором: 2
```

Определение `CREATE OR REPLACE MATERIALIZED LAKE VIEW silver.valid_orders` с `DROP` и `FAIL` требует Fabric Lakehouse с исходной `bronze.orders`. Вызов `display` и Data Wrangler рассчитаны на блокнот Fabric, KQL — на Eventhouse, а правила и сканирование Purview — на соответствующий ресурс и полномочия. Эти среды для проверки примеров недоступны.

## Итоги главы

- Одно сканирование метаданных, профилирование и запуск правил отвечают на разные вопросы.
- Для оценки таблицы в целом бывают нужны агрегатные и межтабличные правила.
- Исключение строки не равно сохранению её для последующего расследования.
- Обнаружение аномалий требует истории и доступа к конкретному временному ряду.
- Надёжность доменного балла зависит от охвата и способа расчёта.

## Ключевые термины

| Термин | Значение |
| --- | --- |
| Профилирование данных | Описание наблюдаемых свойств набора данных. |
| Полнота | Наличие требуемых записей и значений. |
| Точность | Соответствие значений действительному положению дел. |

## Что это значит на практике

Для одного отчёта покажите, где запускается проверка, что происходит с ошибочной строкой, в каком хранилище остаётся история и когда обновляется оценка у потребителя. Так обнаруживаются промежутки между настроенными компонентами.
