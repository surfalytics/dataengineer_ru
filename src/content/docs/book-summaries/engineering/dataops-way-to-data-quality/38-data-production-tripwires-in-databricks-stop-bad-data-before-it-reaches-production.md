**Главная мысль.** Проверку качества можно сделать обычной задачей в графе Databricks. Если она завершится с ошибкой, планировщик не запустит зависимое преобразование. Следующий слой сохранит данные последнего успешного расчёта.

## О чём глава

Задание может успешно записать таблицу, в которой столбец незаметно потерял 30% значений. Слои бронзы, серебра и золота создают удобные места контроля, однако сам переход между ними ничего не проверяет. В примере DataKitchen отдельные задачи запускают TestGen после каждой трансформации и передают планировщику результат. Благодаря этому оператор видит проблему в том же журнале, где наблюдает за обычными заданиями.

![Четыре задачи Databricks и их порядок](/assets/dataops-way-to-data-quality/ch38-job.png)

## Как встроить проверку

В существующем графе добавляют задачу, которая зависит через `depends_on` от построения серебра. Построение золота теперь зависит от проверки серебра. Затем ставят проверку золота. Если проверка серебра завершается ненулевым кодом, его ошибочное содержимое остаётся доступно для расследования, а золото ещё не перезаписано.

Авторы предлагают передавать `run_tests` как параметр запуска задания. Это позволяет отключить проверки для отдельного пересчёта или отладки без повторного развёртывания. При этом переменная bundle подставляется в момент развёртывания и сама по себе не даёт такой возможности. В книге приведены оба механизма. В параметрах задачи Python значение читается из `{{job.parameters.run_tests}}`.

Для новых проектов DataKitchen описывает задания и ресурсы в YAML с помощью Databricks Asset Bundles. В dev имена и пути привязаны к пользователю, поэтому два инженера могут запускать собственные варианты одновременно. Для prod предусмотрены общий путь и отдельная учётная запись. Обе проверки используют один скрипт, а аргумент `--layer` выбирает набор тестов для серебра или золота.

## Как TestGen возвращает результат

Например, в описанной реализации TestGen работает в Docker на выделенной виртуальной машине. Скрипт задания подключается к ней по SSH и запускает команды в контейнере. Ключ берут из хранилища секретов и на время запуска записывают в файл с ограниченными правами. Такая интеграция требует обслуживания ключей и сетевого доступа между вычислительными средами.

Скрипт находит идентификатор набора по имени и проекту, запускает TestGen CLI, получает результаты тестов и переносит их в таблицу Delta. В Unity Catalog счётчики доступны на таблицах и столбцах. Комментарий содержит ссылку на конкретный запуск. Затем число неудачных проверок определяет код завершения задачи.

![Куда поступают результаты проверки](/assets/dataops-way-to-data-quality/ch38-results.png)

> **Пояснение:**
> Мы локально выполнили условие из книги в отдельных процессах Python для нуля и двух ошибок. Печать признака следующего шага показывает решение по коду завершения. Для полного облачного прогона требуются рабочая область Databricks, вычислительный кластер и настроенный экземпляр TestGen.
> [Проверочный скрипт](https://github.com/surfalytics/dataengineer_ru/blob/main/scripts/dataops-way-to-data-quality-code/ch38_gate.py).

```python
failed = int(summary.get("failed_ct", 0) or 0)
if failed > 0:
    sys.exit(f"FAIL: {failed} test(s) failed in {suite_key}.")
```

```text

failed_ct=2, код=1, следующий шаг=False
FAIL: 2 test(s) failed in silver-suite.
```

## Разбор и повторный запуск

В журнале оператор видит число ошибок и имя набора. При этом в Delta можно найти конкретную таблицу, столбец и вид теста. После исправления исходных данных или логики повторяют выполнение с неудачного шага. Таким способом команда сохраняет историю и возвращает в обработку только проверенный результат. Для проверки золота этот принцип защищает последующие зависимые шаги; уже записанная таблица золота остаётся доступной для расследования.

![Действия после неудачной проверки серебра](/assets/dataops-way-to-data-quality/ch38-recovery.png)

В издании 2026 года переход к HTTP авторы описывают как план. Предполагается запустить тесты запросом, дождаться завершения и получить JSON. При этом само правило допуска останется в графе, а определения тестов будут по-прежнему храниться отдельно. Поэтому изменение конкретного условия качества не потребует переписывать зависимости заданий.

## Итоги главы

- Задачу проверки ставят между зависимыми преобразованиями.
- Параметр запуска и переменную развёртывания подставляют на разных этапах.
- Одна программа выбирает набор тестов по слою.
- Ненулевой код блокирует дальнейшие зависимые задачи.
- Таблица результатов и каталог помогают найти конкретную причину.
- После исправления обработку продолжают с места сбоя.

## Ключевые термины

| Термин | Значение |
|---|---|
| Блокирующая проверка | Задача, которая решает, можно ли продолжить обработку результата. |
| Databricks Asset Bundles | Способ описывать и развёртывать ресурсы Databricks как код. |
| Unity Catalog | Каталог, в котором у объектов можно видеть сведения о проверках. |

## Что это значит на практике

Проверьте зависимости перед публикацией важной витрины. Смоделируйте неудачную проверку серебра и убедитесь, что задача золота не стартует, а оператор находит причину и идентификатор запуска.
