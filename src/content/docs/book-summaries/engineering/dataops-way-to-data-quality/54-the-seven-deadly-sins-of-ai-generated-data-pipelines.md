**Главная мысль.** Ошибка сгенерированного преобразования часто выглядит как успешный запуск. Чтобы принимать такие изменения, команда должна проверять новые значения и поведение процесса при повторе.

## О чём глава

Три из четырёх моделей dbt до обеда написал ИИ. Сколько часов затем ушло на чтение, проверку соединений и выяснение, не выполнилась ли загрузка дважды? По приведённому авторами опросу Stack Overflow за 2025 год, инструменты ИИ использовали 84% разработчиков, половина профессиональных разработчиков применяла их ежедневно, а доля доверяющих точности результата снизилась с 40% до 29%. Авторы также ссылаются на оценку GitClear о росте частоты быстрой переработки кода до девяти раз и повторяющихся блоков до восьми раз. В данных неудачный результат может просто завысить выручку на 4%, оставив график вполне убедительным.

## Две ошибки построения процесса

**Повторная загрузка дублирует строки.** После тайм-аута агент повторяет добавление заказов из выбранного окна. В результате вторая попытка добавляет то же самое. Авторы предлагают сначала очищать окно, затем загружать его из неизменяемого источника. Время окна должно быть определено для обрабатываемой партии. Возможность пережить остановку между операциями зависит и от управления транзакцией.

**Модель угадывает значение схемы.** Имена полей не объясняют, что `status_id = 9` означает отмену, финансовый год начинается в феврале, а естественный ключ клиента потерял уникальность после приобретения другой компании. Поэтому нужны профили, определения и история изменений. Если значение известно только аналитику, модель воспроизведёт собственное предположение о нём.

## Три ошибки проверки

**Код растёт, тесты остаются прежними.** За 4 000 новыми строками SQL остаются 40 старых тестов. Авторы предлагают проверять каждую затронутую модель и выводить ограничения из реальных данных, независимо от описания, которое дал автор преобразования.

**Граф зависимостей принимают за свидетельство корректности.** После добавления `APAC` в `CASE` связи между таблицами остались прежними, а комиссия в примере снизилась на 30%. Авторы предлагают сопоставить набор регионов на входе и выходе и их число. Lineage пригодится, чтобы определить, кому сообщить об обнаруженном расхождении.

> **Пояснение:** при переводе заказов APAC из партнёрского канала в прямой сам регион остаётся в данных. Список регионов и их количество могут совпасть. Для этого случая проверяют канал заказов APAC или сверяют сумму комиссии.

**Ручное написание тестов откладывают.** Удобнее сгенерировать очередное преобразование, чем тратить время на сотни похожих YAML-правил. Авторы предлагают генерировать базовые проверки свежести, объёма, доли пропусков, внешних ключей и схемы. Инженер уточняет исключения и добавляет несколько правил, зависящих от бизнеса.

## Две ошибки при работе агента

**Агент сам объявляет свою работу правильной.** Ответ «всё сработало» не обнаружит, что логика условия и объяснение этой логики повторяют одно ошибочное предположение. Для этого внешний исполнитель должен проверить реальные ограничения и детализацию на реальных строках в отдельной среде. В примере авторов у трёх решений одинаковый граф зависимостей, но они проходят 86%, 94% и 100% тестов.

**Скорость выпуска подменяет проверку.** Когда между запросом пользователя и производством прошло тридцать секунд, легко пропустить CI и ревью. Авторское решение — поместить тесты внутрь цикла. Агент получает фактический результат через инструмент, исправляет ошибку и открывает запрос на слияние уже с результатами проверок. В итоге человеку остаётся оценить изменение и пригодность самих условий.

## Итоги главы

Авторы объединяют семь ошибок четырьмя мерами: повторяемой архитектурой, доступным деловым контекстом, растущим вместе с кодом покрытием и независимой проверкой внутри цикла агента.

## Ключевые термины

**Идемпотентность** — сохранение одинакового состояния результата при повторении операции. **Размножение строк** возникает, когда соединение находит для исходной строки больше соответствий, чем предполагает расчёт.

## Что это значит на практике

> **Пояснение:** Оба варианта SQL из книги выполнены в DuckDB на двух исходных заказах во временных таблицах. После двух добавлений запрос количества вернул `after_append_twice = 4`. После двух циклов «удалить окно и вставить» он вернул `after_replace_twice = 2`. В воспроизводимом примере каждая замена заключена в транзакцию. [SQL для повторной загрузки](https://github.com/surfalytics/dataengineer_ru/blob/main/scripts/dataops-way-to-data-quality-code/ch54_retries.sql)


Два запуска на одном и том же входе:

```sql
-- DuckDB. Все таблицы примера временные.
CREATE TEMP TABLE stg_orders (order_id INTEGER, order_date DATE);
INSERT INTO stg_orders VALUES (1, CURRENT_DATE), (2, CURRENT_DATE - 1);
CREATE TEMP TABLE fact_orders AS SELECT * FROM stg_orders WHERE false;

INSERT INTO fact_orders SELECT * FROM stg_orders WHERE order_date >= CURRENT_DATE - 1;
INSERT INTO fact_orders SELECT * FROM stg_orders WHERE order_date >= CURRENT_DATE - 1;
SELECT count(*) AS after_append_twice FROM fact_orders;
```

```text
4
```

Повторная замена окна:

```sql
BEGIN TRANSACTION;DELETE FROM fact_orders WHERE order_date >= CURRENT_DATE - 1;
INSERT INTO fact_orders SELECT * FROM stg_orders WHERE order_date >= CURRENT_DATE - 1;
COMMIT;
BEGIN TRANSACTION;
DELETE FROM fact_orders WHERE order_date >= CURRENT_DATE - 1;
INSERT INTO fact_orders SELECT * FROM stg_orders WHERE order_date >= CURRENT_DATE - 1;
COMMIT;
SELECT count(*) AS after_replace_twice FROM fact_orders;
```

```text
2
```
