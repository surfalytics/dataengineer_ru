**Главная мысль.** Поставки из аптек, CRM, страховых систем и справочников освещают разные участки работы. Каждый столбец может выглядеть правдоподобно, даже когда сведения об одном враче или пациенте уже невозможно согласовать.

## О чём глава

Команде бренда нужно объяснить, почему сдвинулась доля рынка. Для этого она объединяет данные разных поставщиков. У каждого свои идентификаторы, периодичность и правила обновления. Авторы выделяют шесть характерных причин расхождений.

## Проверять связи и отсутствие записей

Код территории может отсутствовать в иерархии, у продаж может не оказаться соответствующей записи в справочнике клиентов, а один пациент может одновременно числиться в двух взаимоисключающих состояниях. При этом формат отдельного значения не выдаёт ни одну из этих ошибок. Кроме того, есть обратное требование: идентификатор, который удалили по запросу, должен отсутствовать при каждой последующей поставке.

![От действительного кода к проверенной ссылке в иерархии](/assets/dataops-way-to-data-quality/ch44-relations.png)

## Различать новую поставку и переписанную историю

Например, еженедельный файл может не поступить, загрузиться дважды или прийти с половиной обычного объёма. Некоторые поставщики корректируют последние месяцы при каждом пересчёте. Команде нужны разные правила для разрешённого окна пересмотра и закрытых периодов. Сдвиг долей плательщиков, специальностей или регионов может указывать на ошибку сопоставления. Широкие файлы с отдельными столбцами по месяцам авторы предлагают сначала привести к длинному формату, а затем проверять динамику.

![Разные ожидания для нового, недавнего и закрытого периода](/assets/dataops-way-to-data-quality/ch44-periods.png)

## Привязать проверку к месту возникновения ошибки

NPI и DEA предусматривают контрольные цифры. Актуальность продукта или кода диагноза приходится проверять по версионному справочнику. Если неверный ключ тихо исчез при соединении, посчитать строки лишь в готовой витрине уже недостаточно. При получении файла проверяют комплектность, после преобразования — сохранность связей, перед публикацией — сверку итогов и правильность бизнес-логики.

![Три места контроля при подготовке коммерческих отчётов](/assets/dataops-way-to-data-quality/ch44-layers.png)

Для воронки каждая запись должна принадлежать ровно одной стадии. Для пути пациента имеет значение последовательность событий: дата отгрузки не должна предшествовать регистрации. По каждой группе итог должен сходиться с детализацией. Из-за десятков источников и тысяч столбцов вручную обычно защищают лишь несколько знакомых полей. Фиксированный порог в 50 000 строк со временем устаревает, предупреждения начинают игнорировать.

## Итоги главы

- Проверка корректного формата не обнаружит потерянную связь между двумя таблицами.
- После удаления объекта требуется постоянно проверять его отсутствие.
- Плановый пересмотр данных отличается от незаявленного изменения закрытого периода.
- Причину сбоя легче установить на том слое, где впервые нарушается ожидание.

## Ключевые термины

| Термин | Значение |
|---|---|
| Окно пересмотра | Периоды, для которых поставщик вправе обновить ранее переданные значения. |
| Контрольная цифра | Часть идентификатора, позволяющая обнаружить некоторые ошибки записи. |

## Что это значит на практике

> **Пояснение:** Для каждого входного файла запишите ожидаемую периодичность, ключ сопоставления и допустимую глубину пересмотра. Без этих сведений трудно объяснить, почему автоматическая проверка должна поднять тревогу.
