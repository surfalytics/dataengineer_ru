**Главная мысль.** Найти подозрительные значения и написать исправляющий SQL можно автоматически. Решение, какое изменение допустимо, принимает человек по каждому предложению.

## О чём глава

Партнёр регулярно присылает цену текстом, сотни неизвестных адресов и невозможный код штата `XY`. Например, можно каждый месяц применять один и тот же `UPDATE`, однако автоматика не знает, обозначает ли `PREMIUM` новую категорию и следует ли превращать 222 сомнительных значения в `NULL`. Авторы описывают два небольших приложения на Python и заявку Jira между ними.

## Сначала предложение

`testgen_to_jira.py` читает схему источника. Затем Claude через MCP получает из TestGen нарушения, определения проверок и примеры реальных строк. Каждая находка сопровождается объяснением и конкретным SQL. После ответа модели программа исключает из предложений для Jira всё, что содержит персональные данные. Затем она оставляет операции, применимые к доступным таблицам. Заявка получает состояние `Needs reply`. Поэтому на этом этапе изменения данных не происходит.

![Как первая программа готовит заявку](/assets/dataops-way-to-data-quality/ch53-propose.png)

## Затем решение владельца

Человек может разрешить очистить только значения-заглушки, а изменение типов отложить до следующего выпуска. Решение фиксируется флагом `Please fix` и уточняющим комментарием. Отклонённое или оставшееся без ответа предложение не должно переходить к выполнению.

![Почему один флаг читают вместе с комментарием](/assets/dataops-way-to-data-quality/ch53-approval.png)

## Как исполняется решение

`jira_apply_fixes.py` выбирает согласованные заявки, читает предложенный SQL и комментарии. Модель составляет конечную последовательность, исключая отложенное и объединяя пересекающиеся изменения. По умолчанию программа создаёт заново рабочую копию `table_applied`. Операции выполняются в одной транзакции. `DROP` и `TRUNCATE` требуют отдельного разрешения. Пробный запуск исполняет SQL и откатывает его.

В результате после фиксации программа возвращает в Jira журнал операций, ставит метку `fix-applied` и переводит заявку в `Fix complete`. Вместе флаг, исключение персональных данных, работа на копии и транзакция ограничивают последствия неверного предложения.

![Из утверждённой заявки к контролируемому результату](/assets/dataops-way-to-data-quality/ch53-apply.png)

## Итоги главы

Решение человека связывает конкретное предложение с разрешённым объёмом изменений. Журнал в заявке нужен, чтобы впоследствии проверить, что именно выполнилось.

## Ключевые термины

**Disposition** — принятое решение по предложению. **Dry run** в описанной реализации выполняет операцию внутри откатываемой транзакции.

## Что это значит на практике

> **Пояснение:** По заявке должно быть видно, какие SQL-операции предложили, какие пользователь разрешил и какие действительно выполнились. Книга описывает программы и ссылается на техническое задание. Исполняемых исходников этих программ в главе нет.
