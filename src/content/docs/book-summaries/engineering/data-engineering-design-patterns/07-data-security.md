**Главная мысль:** Данные - ценный актив, поэтому их нужно защищать. Глава даёт паттерны для пяти задач: удалять данные по запросу, ограничивать доступ, защищать сами данные, прятать персональные данные и безопасно подключаться к системам.

## О чём глава

В [главе 6](/book-summaries/engineering/data-engineering-design-patterns/06-data-flow/) мы открыли датасеты другим командам. Теперь вопрос: как их защитить. Датасеты стали ценными активами, и ими интересуются злоумышленники. Поэтому инженер данных думает не только о пайплайнах.

Автор называет четыре темы:

- **Compliance.** Законы о приватности (GDPR в Европе, CCPA в США) точно задают границы между вами и клиентом.
- **Access control.** Если датасет открыт всей компании, другая команда может случайно его перезаписать.
- **Data protection.** Даже при доступе к таблице прочитать данные нельзя без ключа расшифровки.
- **Connectivity.** Логины и пароли в Git повышают риск утечки. Их нужно хранить в другом месте.

## Все паттерны главы

| Паттерн | Когда применять |
|---|---|
| `Vertical Partitioner` | Нужно удалять данные пользователя дёшево. Вы строите систему с нуля |
| `In-Place Overwriter` | Данные уже лежат в старой системе. Переделать хранение нельзя |
| `Fine-Grained Accessor for Tables` | Пользователь видит таблицу, но не все её колонки и строки |
| `Fine-Grained Accessor for Resources` | Нужно дать задаче доступ только к своим облачным ресурсам |
| `Encryptor` | Нужно защитить данные на диске и в сети |
| `Anonymizer` | Нужно отдать данные наружу без возможности найти человека |
| `Pseudo-Anonymizer` | Нужно скрыть значения, но оставить пользу для аналитики |
| `Secrets Pointer` | В коде не должно быть логинов и паролей |
| `Secretless Connector` | Можно обойтись совсем без паролей |

## Удаление данных (Data Removal)

Законы о приватности требуют удалять данные пользователя по его запросу. Ниже два способа это сделать.

### `Vertical Partitioner`

**Проблема.** Вы показали коллегам дизайн пайплайна удаления персональных данных. Они заметили лишний расход хранилища: часть колонок неизменна (дата рождения, номер документа), но повторяется в каждой записи. Коллеги просят хранить каждое такое свойство один раз. Тогда при запросе на удаление данных будет меньше.

**Как работает:**

- Датасет делят на изменяемую и неизменяемую части. Горизонтальное деление группирует записи (партиции по дате, [глава 8](/book-summaries/engineering/data-engineering-design-patterns/08-data-storage/)). Вертикальное делит саму строку и пишет части в разные места. Их можно совмещать.
- Сначала выбирают колонки для деления и атрибут, по которому части потом соединят (`user_id`).
- В загрузку добавляют логику деления. Атрибуты, которые меняются с каждым событием, идут в одно хранилище. Неизменные и персональные - в другое.
- Деление делают через `SELECT` по разным наборам колонок. В запрос можно добавить бизнес-правила, например дедупликацию.
- Персональные атрибуты записаны один раз, и удалять их дешевле. К тому же для частей можно задать разные правила доступа и хранения.

**Компромиссы:**

- **Query performance.** Это нормализация: неизменные свойства живут отдельно. Запись быстрее, но чтение медленнее: каждому читателю нужен `join`, а он идёт по сети.
- **Querying complexity.** Потребители должны знать, где лежат свойства. Помогают единая точка входа (view), документация в каталоге данных и lineage ([глава 10](/book-summaries/engineering/data-engineering-design-patterns/10-data-observability/), `Dataset Tracker`).
- **Polyglot persistence.** Один датасет может жить в разных хранилищах (NoSQL, реляционная БД, key-value). Тогда деление нужно в каждом, и пайплайнов удаления несколько. Выход: один job делит строки, а потребители кладут части в своё хранилище.
- **Raw data.** Паттерн действует только после первой трансформации. Сырые данные до деления тоже нужно чистить. Простой путь - короткий retention, если он укладывается в срок ответа на запрос. Но это снижает возможность backfill.

**Примеры.** В `Spark` метод `foreachBatch` создаёт два датасета и пишет каждый в свой топик Kafka: визиты без пользовательских колонок и user context. Топик user context потом превращают в таблицу Delta Lake, а `MERGE` дедуплицирует записи.

В Delta Lake удаляют через `DELETE`. После него нужен `VACUUM`, иначе данные можно прочитать из старой версии таблицы.

В Kafka удаление идёт через `tombstone message`: ключ записи и значение `null`. Если у топика `cleanup.policy` равна compaction, фоновый процесс удалит запись. Это работает для user context, где на ключ одна запись. Для визитов не работает: много событий делят один ключ, и compaction оставит только последнее.

### `In-Place Overwriter`

**Проблема.** Вы получили в наследство старую систему с терабайтами данных в партициях по времени. Стратегии для персональных данных нет. Систему широко используют, и она должна соблюдать новые правила приватности, в том числе удаление по запросу. Ресурсов на переделку нет.

**Как работает:**

- Если хранилище умеет `DELETE`, выполняют его с условием `WHERE`.
- В Delta Lake и Iceberg есть time travel. Если не освободить блоки удалённых строк, персональные данные останутся. Нужна чистка.
- Если нативного удаления нет (JSON, CSV), его имитируют. Тяжёлый job читает весь набор, убирает записи удалённых пользователей и заменяет данные.
- Заменять датасет напрямую нельзя: job может упасть или повториться, и данные пропадут. Поэтому job пишет в `staging area`, где результат остаётся закрытым. Потом отдельный job (promotion) заменяет публичный датасет. Если он упадёт, данные не потеряны: результат лежит в staging.
- Для топика Kafka с compaction и ключами: читают записи и для ключей удалённых сущностей шлют `null`. Compaction удалит старые записи.

> **Deletion Vectors.** В табличных форматах есть два способа удалять. Первый: помечают удалённые строки в небольшом отдельном файле (deletion vector). Тогда читатель сам отбрасывает удалённые строки при чтении, а запись дешевле. Второй: пишут в файлы все строки, кроме удалённых. Он тяжелее для писателя, зато читатель берёт файлы как есть.

> **Retention period.** Если срок хранения короче срока ответа на запрос, retention можно считать способом удаления. Проверьте это с CDO и юристами.

**Компромиссы:**

- **I/O overhead.** Чтение и перезапись файлов дают большую нагрузку. Место может почти удвоиться. Нагрузка ниже, если хранилище пропускает лишние файлы. В Parquet, Delta Lake и Iceberg есть статистика по блокам: если в блоке нет нужных строк, чтение блока пропускается.
- **Cost.** Паттерн читает всё, поэтому дороже `Vertical Partitioner`. У пользователя 2000 записей: здесь затронуты 2000, там хватило бы одной. Объединяйте запросы на удаление в один запуск.

**Примеры.** Для Delta Lake код тот же, что в `Vertical Partitioner`. Интереснее JSON. `Spark` job читает данные текстовым API (так датасет не меняется) и берёт только поле фильтра (`user_id`). Запись идёт в staging: `Spark` распределённый и без транзакций, поэтому прямая перезапись при сбое оставит частично верный результат. После успеха файлы переносят командой типа rename. В облачных object store rename часто означает copy и remove, и при сбое можно получить пустой результат. Если копирование упадёт, новый датасет остаётся в staging.

> **Impossible Rollback.** Подход со staging не идеален. Если в job удаления есть баг и его нужно повторить, исходные данные уже перезаписаны. Помогут паттерн `Proxy` или версионирование на уровне инфраструктуры. Версии поддерживают S3, Azure Storage и GCS.

## Контроль доступа (Access Control)

Даже лучший паттерн удаления не заменит контроль доступа. Нужно и соблюдать правила, и пускать к критичным данным только своих. Сами данные могут быть главным конкурентным активом.

### `Fine-Grained Accessor for Tables`

**Проблема.** Вы перенесли нагрузки HDFS/Hive в облачное хранилище. Первое требование простое: оно поддерживает пользователей и группы с доступом к таблицам. Второе сложнее. У пользователя есть доступ к таблице, но не ко всем её колонкам и строкам. Нужна авторизация на уровне этих ресурсов.

**Как работает.** Есть три способа ограничить колонки:

- `GRANT` с перечнем колонок (PostgreSQL, Redshift).
- Теги в каталоге данных. В BigQuery создают policy tags в Data Catalog, назначают их защищённым колонкам и выдают пользователям роль Fine-Grained Reader на каждый тег.
- Маскирование. Пользователь видит колонку, но без доступа содержимое скрыто. Так делают Databricks Unity Catalog и Snowflake. Функция показывает содержимое, только если пользователь входит в группу инженеров.

Строки закрывает row-level security. Это динамическая функция, которая добавляет `WHERE` к запросу. В Databricks она называется `ROW FILTER`, в Redshift - Row-Level Security, в BigQuery и Snowflake - row access policy. Если БД не умеет row-level, его имитируют view с условием по `current_user`. У каждого пользователя тогда своя версия view.

```sql
ALTER TABLE users ENABLE ROW LEVEL SECURITY;
CREATE POLICY own_rows ON users USING (login = current_user);
```

**Компромиссы.** Функция встроена в БД, поэтому минусов мало.

- **Row-level security limits.** Условия строятся из данных сессии: имя, группа, IP.
- **Data type.** Для вложенных типов доступ по колонкам не сработает. Их разворачивают и отдают из другой таблицы или через `Dataset Materializer`.
- **Query overhead.** Динамические функции добавляют задержку. Её снижают отдельной таблицей или view с разрешёнными данными, но это дублирует данные.

**Примеры.** `PostgreSQL` поддерживает оба вида: колонки через `GRANT`, строки через политику с условием `login = current_user`. В `DynamoDB` (NoSQL с доступом по ключу) строки закрывает IAM policy с атрибутом `dynamodb:LeadingKeys`: пользователь читает только строки, ключ которых начинается с его `user_id`.

### `Fine-Grained Accessor for Resources`

**Проблема.** Аудит безопасности нашёл слишком широкие права в облаке. Например, один job может перезаписать все датасеты в object store. Аудитор советует принцип `least privilege`: каждый компонент получает минимум прав, и job работает только со своим датасетом.

**Как работает.** Все крупные облака (AWS, Azure, GCP) реализуют `least privilege`. Есть два подхода:

- Через ресурс. Область доступа описана у самого ресурса. Пример: IAM policy на бакете GCS.
- Через identity. Права привязаны к пользователю или приложению. В AWS это IAM roles, которые принимают сервисы. Пример: job на `EMR` получает права чтения и записи в Kinesis Data Streams.

Права гибкие. Можно указать ресурс, набор ресурсов с общим префиксом или условие на этапе выполнения, например теги ресурса в AWS S3. Последнее похоже на row-level доступ.

**Компромиссы.** Политики описывают через IaC (Terraform) или скрипт. Это не сложно технически, но есть цена.

- **Security by the book.** Принцип `least privilege` порождает много мелких политик, которые трудно поддерживать. Чтобы их не было много, используют wildcard, например `visits*`. Но нельзя гарантировать, что пользователь должен иметь доступ ко всем будущим ресурсам с таким префиксом. Обсудите упрощение с безопасниками.
- **Complexity.** Смесь двух подходов усложняет систему. Выберите один, лучше тот, что покрывает больше сценариев.
- **Quotas.** У политик есть лимиты. В AWS IAM по умолчанию 1500 custom policies, в GCP IAM - 300 custom roles на проект. Часть лимитов можно поднять.

**Примеры.** Без доступа к бакету S3 вы получите ошибку `AccessDenied`. Её исправляют identity-подходом (роль с правами чтения только на ваш бакет) или resource-подходом (политика бакета разрешает чтение пользователю `visits-s3-reader`).

## Защита данных (Data Protection)

Логический контроль доступа - только часть решения. Нужно защитить и сами данные от неожиданного использования.

### `Encryptor`

**Проблема.** Данные физически где-то лежат. Заказчики боятся, что кто-то перехватит трафик между брокерами и job или украдёт данные с серверов. Нужно защитить данные на диске (at rest) и в сети (in transit).

**Как работает.** Паттерн имеет два уровня.

- `Data at rest`. Шифрование хранимых данных. При клиентском шифровании производитель шифрует данные сам и сам управляет ключом. При серверном всю работу делает сервер, включая ключи. Серверное шифрование широко поддерживают облака: AWS и GCP используют KMS, Azure - Key Vault.
- Чтение идёт в четыре шага. Запрос приходит в хранилище. Оно просит ключ расшифровки у хранилища ключей. Если клиенту нельзя расшифровывать данные, запрос падает. Иначе хранилище расшифровывает данные и отдаёт клиенту. Облако скрывает это от вас: вы настраиваете стратегию шифрования и права на хранилище данных и хранилище ключей.
- `Data in transit`. Данные шифруются при обмене по сети. В облаке нужно включить безопасное соединение в SDK клиента и задать нужную версию протокола на сервисе.

**Компромиссы:**

- **Encryption/decryption overhead.** Данные хранятся в изменённом виде, и каждая запись и чтение нагружают CPU.
- **Data loss risk.** Шифрование может закрыть доступ и своим пользователям, если ключ потерян или недоступен. Облака смягчают это через soft delete для ключей: удаление действует не сразу, и в grace period ключ можно восстановить.
- **Protocol updates.** Шифрование в сети проще включить, но его нужно обновлять. TLS 1.0 и 1.1 признаны устаревшими, сервисы на них нужно обновить. В облаке это обычно сводится к смене версии на сервисе.

**Примеры.** В `Terraform` для S3 два шага. Сначала ключ в AWS KMS и права на шифрование и расшифровку для роли. Параметр `deletion_window_in_days` задаёт окно восстановления ключа. Затем ключ привязывают к бакету. Для Azure Event Hubs можно задать минимальную версию TLS, и клиенты со старыми версиями будут отклонены.

### `Anonymizer`

**Проблема.** Внешняя аналитическая фирма разбирает поведение ваших клиентов. В данных много PII, а часть пользователей не согласилась делиться ими с третьими лицами. Нужен пайплайн, который сделает датасет совместимым с правилами приватности.

> **Not Only PII.** Защиты требует не только PII. Есть также защищённые медицинские данные (PHI) и данные интеллектуальной собственности (IP). Автор для простоты пишет про PII.

**Как работает.** Нужно убрать или изменить чувствительные части, чтобы потребитель не мог опознать пользователя. Три способа:

- **Data removal.** Убрать выбранные колонки. Самый простой.
- **Data perturbation.** Добавить шум, чтобы значение изменило смысл. Например, в IP добавляют лишние символы в случайных местах: «123.456.789.012» превращается в «1823.456.7809.012».
- **Synthetic data replacement.** Заменить значения данными из генератора, обычно ML-модели, которая понимает тип колонки. Страна «Португалия» превращается в «Хорватию».

Первые два легко сделать трансформацией колонки. Для третьего может понадобиться команда data science. Менее удачный вариант: своя функция замены для каждой колонки со случайными значениями.

**Компромисс.** Information loss. Датасет становится чем-то новым. Пользователи, включая аналитиков и data scientists, не смогут опираться на эти колонки. Это ведёт к неверным моделям и выводам.

**Пример.** Удаляем колонку с днём рождения и заменяем email случайным из библиотеки Faker. В `Spark` колонку можно не выбирать в `SELECT` (если колонок мало) или убрать через `drop`. Замену делают `withColumn` или `mapInPandas`.

```python
from faker import Faker
from pyspark.sql import functions as F

fake = Faker()
random_email = F.udf(lambda: fake.email())
anonymized = users.drop("birthday").withColumn("email", random_email())
```

### `Pseudo-Anonymizer`

**Проблема.** После `Anonymizer` у аналитиков нет части колонок, и они не отвечают на большинство вопросов бизнеса. Они просят новый датасет, где PII скрыта, но заменена более полезной формой.

**Как работает.** Есть четыре метода. Каждый заменяет значение другим, которое больше или меньше связано с исходным:

| Метод | Что делает |
|---|---|
| Masking | Заменяет часть символов, например SSN `999-55-1040` становится `XXX-XX-1040` или `9XX-5X-1XXX` |
| Tokenization | Заменяет значение вымышленным. Связь хранится в token vault. Доступ к vault нужно защитить |
| Hashing | Необратимо заменяет значение. Email после SHA-256 и Base64 становится строкой вроде `gD0B+pUp...` |
| Encryption | Шифрует колонки или строки ключом. Владелец ключа может восстановить оригинал |

Метод выбирают по типу данных. Masking - простая трансформация колонки. Tokenization требует таблицы соответствий и больше работы.

> **Anonymization versus pseudo-anonymization.** Часто их путают. Псевдонимизированные данные можно опознать при объединении с другими датасетами. Анонимизированные - нет, даже после объединения.

**Компромиссы:**

- **False sense of security.** Защита слабее, чем у `Anonymizer`. Главная беда - объединение датасетов. Пример автора: есть две псевдонимизированные таблицы, предпочтения в еде и регистрация. После объединения видна маска страны `S*n M****o` и роль «изобретатель». Стран с таким именем мало, и человека можно опознать. При полной анонимизации страна и роль были бы заменены на «Европа» и «Software engineer», и опознать его было бы нельзя.
- **Information loss.** Пример: маска SSN. Два разных номера `999-55-1040` и `999-13-1040` дают одну маску. Есть и потеря типа: при generalization число заменяется диапазоном, то есть строкой.

**Примеры.** В `PySpark` `mapInPandas` меняет страну на область и маскирует SSN. Диапазон зарплаты сюда не входит: зарплата целая, диапазон - строка, и типы несовместимы. Для неё берут обычное отображение колонки.

## Подключения (Connectivity)

Защитить данные мало. Данные текут между системами, и к ним нужен доступ. Два паттерна показывают безопасные способы.

### `Secrets Pointer`

**Проблема.** Пайплайн визитов в реальном времени обогащает событие геолокацией через внешний API. Единственный способ входа - пара логин и пароль. Раньше команда случайно раскрыла пароль от другого API. Тот API тарифицировался по запросам, и утечка вызвала рост счёта. Хочется не хранить логин и пароль в коде.

**Как работает.** Лучший способ защитить credentials - нигде их не хранить, а использовать ссылку (pointer).

- Все чувствительные значения лежат в secrets manager (Google Secret Manager, AWS Secrets Manager). Это центральное место, поэтому проще следить за доступом. Новые credentials можно задать без правки всех потребителей.
- Потребитель знает только имя секрета и запрашивает значение у сервиса во время выполнения. Чтобы экономить запросы, он может кэшировать значение.
- Защита в два уровня. Сначала потребитель должен иметь доступ к secrets manager (помогают fine-grained паттерны). Потом сами credentials: если они неверны, доступа к API или БД нет.

**Компромиссы:**

- **Cache invalidation.** С кэшем вы не знаете, актуальны ли credentials. Зато запросов меньше. Простой путь: дать job упасть, после перезапуска он перечитает секрет. Это плохо, если credentials меняются часто. Не забудьте об идемпотентности: повторы не должны портить данные. Асинхронное обновление тоже возможно, но credentials могут смениться после начала записи.
- **Logs.** Паттерн даёт ложное чувство, что утечки не будет. Но секрет можно случайно записать в лог.
- **A secret remains secret.** Credentials всё равно существуют. Кто-то должен безопасно создать значения: человек-администратор или стек IaC, который задаёт случайные значения при создании БД.

**Пример.** `Spark` job читает таблицу PostgreSQL и пишет JSON. В описании входа вместо значений стоят ссылки. Credentials живут как отдельный актив, не привязанный к коду. Если БД создаёт IaC (Terraform), имена секретов одинаковы во всех средах, а IaC генерирует значения. Конфигурации по средам не нужны.

```python
client = boto3.client("secretsmanager")
password = client.get_secret_value(SecretId="pwd")["SecretString"]
```

### `Secretless Connector`

**Проблема.** Маленькая команда подключает новый сервис обработки. Все примеры используют API keys, а управлять ключами она не хочет. Нужно решение без credentials в коде.

**Как работает.** Два подхода:

- **IAM.** Админ задаёт права чтения и записи для пользователя, группы или роли документом политики. Это относится и к application users, например к job по расписанию. Они не логинятся, но должны получать доступ. Процесс в четыре шага: приложение запрашивает операцию в сервисе (читает объект). Сервис идёт в IAM проверять права. IAM возвращает список прав. Сервис отвечает либо данными, либо ошибкой.
- **Сертификаты** (certificate-based authentication). Схема та же, но вместо IAM работает центр сертификации (CA), который проверяет сертификаты соединения.

**Компромиссы:**

- **Workless impression.** Работа всё равно есть: сущность нужно настроить для доступа без credentials. В AWS нужно право assume role, которое даёт временные credentials через Security Token Service (STS).
- **Rotation.** Относится к сертификатам. Регулярная ротация ключей снижает риск утечки, но добавляет работы. Чтобы не сломать потребителей, сначала создают и раздают новые credentials. Пока поддерживают и старые, и новые. Старые удаляют только после подтверждения, что все перешли.

**Примеры.** `Spark` подключается к PostgreSQL по сертификату: пароля в параметрах нет. Режим SSL `verify-full` проверяет, что имя хоста совпадает с именем в сертификате. В GCP job `Dataflow` читает из GCS через Service Account (так в GCP называют application user). Его связывают с бакетом (роль только на чтение) и с самим job.

## Итоги главы

- `Vertical Partitioner` хранит персональные атрибуты один раз, поэтому удалять дёшево. `In-Place Overwriter` работает с любым хранилищем, но читает и переписывает много данных.
- `Fine-Grained Accessor for Tables` ограничивает колонки (GRANT, теги, маскирование) и строки (row-level security).
- `Fine-Grained Accessor for Resources` реализует `least privilege` в облаке. Wildcard упрощает, но нарушает принцип.
- `Encryptor` защищает данные на диске и в сети. Цена - CPU и риск потерять ключ.
- `Anonymizer` убирает возможность найти человека, но теряет информацию. `Pseudo-Anonymizer` сохраняет пользу, но при объединении таблиц человека можно найти.
- `Secrets Pointer` убирает пароли из кода, но не из логов. `Secretless Connector` убирает пароли совсем, но требует настройки и ротации.

## Ключевые термины

| Термин | Значение |
|---|---|
| `PII` | Персональные данные, по которым можно найти человека |
| `Tombstone message` | Запись с ключом и `null` для удаления в Kafka |
| `Staging area` | Временное место для результата до публикации |
| `Least privilege` | Минимум прав, нужных для работы |
| `Row-level security` | Ограничение строк, которые видит пользователь |
| `Column masking` | Скрытие значения колонки для части пользователей |
| `KMS` | Сервис управления ключами шифрования |
| `Secrets manager` | Центральное хранилище паролей и ключей |
| `IAM` | Управление доступом пользователей и сервисов в облаке |

## Что это значит на практике

- Разделяйте PII и события при загрузке. Тогда запрос на удаление затронет мало данных.
- После `DELETE` в Delta Lake или Iceberg запускайте `VACUUM` или аналог. Иначе time travel вернёт данные.
- Объединяйте запросы на удаление в один запуск. Это экономит I/O.
- Давайте задачам отдельные роли с `least privilege`. Не используйте один общий ключ.
- Для колонок с PII включайте маскирование или `GRANT` по колонкам. В `dbt` и в warehouse храните это как код.
- Включайте шифрование по умолчанию на бакетах и задавайте минимальную версию TLS.
- Не кладите пароли в Git. Используйте secrets manager или доступ через роль.
- Проверьте, что секреты не попадают в логи.
- Перед отдачей данных наружу решите: нужна полная анонимизация или хватит псевдонимизации. Проверьте риск объединения таблиц.
