**Главная мысль:** Поток данных - это порядок шагов в пайплайне и связи между пайплайнами. Паттерны этой главы помогают резать работу на части, соединять и разделять ветки и решать, сколько запусков идёт одновременно.

## О чём глава

В [главе 5](/book-summaries/engineering/data-engineering-design-patterns/05-data-value/) мы получили ценный датасет, но он пока остаётся локальным. Эта глава отвечает на вопрос: как связать шаги, из которых получается датасет, и как открыть его другим командам. Автор разбирает четыре группы: последовательность (sequence), `fan-in`, `fan-out` и запуск пайплайнов (orchestration).

Паттерны работают на двух уровнях:

- **Оркестрация** (`orchestration layer`): задачи в `Airflow`, `AWS Step Functions`, `Azure Data Factory`. Здесь же связи между командами.
- **Обработка данных** (`processing layer`): код в `Spark`, SQL. Здесь паттерны делают бизнес-логику понятнее.

## Паттерны главы

| Паттерн | Когда применять |
|---|---|
| `Local Sequencer` | Большая задача падает и каждый раз стартует с нуля. Нужно разбить её на шаги |
| `Isolated Sequencer` | Два пайплайна принадлежат разным командам, но один даёт данные другому |
| `Aligned Fan-In` | Одна задача ждёт успеха всех родителей (например, 24 часа в сутки) |
| `Unaligned Fan-In` | Задача должна стартовать, даже если часть родителей упала |
| `Parallel Split` | Один результат нужен нескольким независимым задачам |
| `Exclusive Choice` | Из нескольких веток нужно выбрать только одну |
| `Single Runner` | Запуск зависит от результата предыдущего. Одновременно идёт только один |
| `Concurrent Runner` | Запуски независимы. Их можно гнать параллельно |

## Последовательность (Sequence)

Здесь вопрос такой: где провести границы между шагами и между пайплайнами. Пример: job пишет результат в несколько баз. Если это одна задача, то для перезагрузки в одну базу придётся перезапускать всё.

### Local Sequencer

**Проблема.** Старый job вырос с десятков до сотен строк, трансформаций стало втрое больше. Он часто падает и каждый раз стартует с начала. Нужно упростить поддержку, но убирать бизнес-логику нельзя.

**Как работает:**

- Большой компонент делят на малые шаги, которые идут друг за другом. Это обычная практика software engineering, она улучшает `separation of concerns`.
- Порядок следует за зависимостью данных: задача B стартует после A, если ей нужны данные A.
- Пример: загрузка делится на проверку готовности (`Readiness Marker`) и саму загрузку (`Full Loader`). Это две задачи оркестратора или два шага одного job.
- Выбор между оркестратором и кодом обработки делают по трём критериям:

| Критерий | Что смотреть |
|---|---|
| Separation of concerns | Если трудно придумать имя задаче, в ней слишком много |
| Maintainability | При retry и backfill пересчитываются все шаги до упавшего. Если проверка готовности вызывает 10 платных API, а job упал три раза, счёт быстро растёт |
| Implementation effort | Оркестратор уже умеет запускать SQL или API. В одной задаче это придётся писать самому |

**Цена.** Главный риск - неверные границы. Слишком много задач нагружают планировщик. Мало задач дают долгие перезапуски. Как выбрать границу:

- Подумайте о границах перезапуска. `Readiness Marker` и `Full Loader` падают независимо. Но после сбоя загрузки проверку готовности повторять не нужно: загрузка уже значит, что данные есть (если источник не удаляет данные).
- В коде обработки границу ставят между самыми дорогими операциями. Тогда сбой финала не заставляет считать дорогой промежуточный датасет заново.
- Операции одной транзакции оставляют вместе. Пример: job по `Dynamic Late Data Integrator` обрабатывает данные и обновляет последнюю версию в state table.

**Примеры.** В `Airflow` порядок задают знаком `>>`. Облачные оркестраторы тоже умеют цепочки: в `AWS EMR` это Step API. Автор советует завершать кластер при любой ошибке шага. Иначе можно открыть частичные данные и считать job успешным. `Airflow` по умолчанию не стартует задачу, пока родитель не успешен. В `PySpark` и SQL каждая переменная служит входом для следующего шага.

```python
# Airflow: цепочка из трёх задач
wait_for_data >> load_to_table >> expose_table
```

> **More Than CRON.** Оркестратор даёт намного больше, чем `cron`. Но если у задачи нет зависимостей, обычного `cron` может быть достаточно.

### Isolated Sequencer

**Проблема.** Ваша команда чистит и обогащает данные и отдаёт их в BI-инструмент. Построение дашбордов вы оставили команде визуализации: это не ваша зона. Она просит только очищенный датасет. Один пайплайн объединить нельзя из-за организации команд.

**Как работает:**

- Границу проводят по роли: провайдер и потребитель. Если вы и то и другое, смотрите на сложность. Когда логика нечитаема, делите на два пайплайна. Иначе используйте `Local Sequencer`.
- Затем выбирают способ запуска:

| Стратегия | Как работает | Связность |
|---|---|---|
| Data-based | Провайдер пишет данные и marker. Потребитель ждёт marker (`Readiness Marker`) | Слабая. Потребитель свободен в выборе данных |
| Task-based | Провайдер сам запускает пайплайн потребителя | Сильная. Переименование у потребителя ломает провайдера |

- При data-based потребитель может перейти на другой датасет, не предупредив провайдера. При task-based так нельзя: если датасет удалят, пайплайн провайдера может упасть.
- Task-based подходит, когда общего датасета нет. Например, потребитель только шлёт уведомление.

**Цена:**

- **Scheduling.** Лучше одно расписание у обоих. Иначе провайдер пропускает часть триггеров или потребитель подстраивает своё расписание.
- **Communication.** Паттерн связывает команды. Проверку условия на другой стороне сделать дорого, а иногда невозможно: сторона может не принимать входящие соединения. Надёжнее организационное решение: каждая команда знает свои входы и выходы и предупреждает о breaking changes.

**Примеры.** В `Airflow` data-based делают через `FileSensor`. Sensor потребителя - страж зависимости: если он падает, провайдер не доставил данные. Но из кода не видно, что пайплайны связаны. Здесь помогает data lineage ([глава 10](/book-summaries/engineering/data-engineering-design-patterns/10-data-observability/)) и стандарт OpenLineage.

Task-based делают через `ExternalTaskMarker` в пайплайне провайдера и `ExternalTaskSensor` у потребителя. Связь явная. Marker к тому же переносит backfill: при перезапуске провайдера потребитель перезапускается следом.

## Fan-In: много веток в одну

### Aligned Fan-In

**Проблема.** Ежедневная агрегация посещений блога. Данные лежат партициями по часам, а потребителям нужен только полный день. Один суточный job слишком большой, а часовое деление хочется использовать.

**Как работает:**

- Родительские задачи должны все завершиться успехом. Тогда стартует общая задача.
- В оркестраторе строят ветки по часам. Каждая считает частичный агрегат, общая задача считает итог за день.
- В обработке данных ветки соединяют так:
  - `UNION` - добавляет строки, те же колонки (вертикально).
  - `JOIN` - добавляет колонки (горизонтально). Строк при этом меньше.
- Плюс первый: ошибка видна раньше. Суточный job узнал бы об ошибке последнего часа только в конце.
- Плюс второй: перезапускать нужно только упавший час, а не все 24.

**Цена:**

- **Infrastructure spikes.** 24 задачи стартуют одновременно. Без эластичной инфраструктуры ограничьте параллелизм или запускайте каждую ветку сразу после своего часа, а итог собирайте в последнем запуске дня.
- **Scheduling skew.** Все успешные ветки ждут самую медленную.
- **Scheduling overhead.** Слишком мелкие задачи нагружают оркестратор.
- **Complexity.** Чем больше разбиение, тем длиннее пайплайн. Помогают вопросы: «Что составляет одну единицу выполнения?» и «Что нужно перезапускать отдельно?»

**Примеры.** В `Airflow` пайплайн описывают один раз в цикле `for`, и оркестратор создаёт задачу на каждую итерацию. Для статичного списка можно написать `[load_1, load_2] >> process`. Это длиннее, но читается лучше.

```python
for hour in [f"{h:02d}" for h in range(24)]:
    sensor = wait_for_hour(hour)
    loader = load_hour(hour)
    clear >> sensor >> loader >> build_daily
```

В обработке данных это `UNION`. Осторожно: он идёт по позиции. Датасеты `a, b, c` и `c, b, a` смешаются неверно: сложатся `a + c`, `b + b`, `c + a`. В `Spark` для этого есть `unionByName`, но им редко пользуются.

```python
# unionByName склеивает колонки по имени, а не по позиции
combined = hour_00.unionByName(hour_01)
```

### Unaligned Fan-In

**Проблема.** `Aligned Fan-In` работает несколько недель. Но иногда один час не обработан, и потребители не получают агрегаты вообще. Договорились отдавать частичный датасет и дозаполнять пробелы потом.

**Как работает:**

- Условие запуска ослабляют: дочерняя задача стартует даже при сбое части родителей.
- Если сбои допустимы, считаем по частичным данным.
- Если упали все, запускаем fallback или обработчик ошибок.
- В `Airflow` это `trigger_rule`, например `ALL_DONE`. Эта задача ждёт завершения всех родителей, каким бы ни был итог. В менее декларативных средах статусы проверяют явно.

**Цена.** Добавляются новые минусы к минусам `Aligned Fan-In`:

- **Readability.** Условие спрятано в коде. Если есть две дочерние задачи (при успехе и при сбоях), из графа не видно, какая сработает. Помогают встроенные функции: `on_failure_callback` в `Airflow`, поле `Catch` в `Step Functions`.
- **Partial data.** Потребитель должен знать, что данные неполные. Способы:
  - таблица полноты рядом с датасетом (12 из 24 часов = 50%);
  - флаг в самих данных, например `is_approximate`;
  - тег в metadata хранилища;
  - уведомление потребителям.
- Можно не публиковать частичный результат, а писать его во внутреннюю таблицу.

**Примеры.** В `Airflow` меняется один параметр. Подзапрос в выходной таблице считает число обработанных часов и ставит флаг.

```sql
-- Пометить строку как приблизительную, если часов меньше 24
CASE WHEN hours_count = 24 THEN false ELSE true END AS is_approximate
```

В `Step Functions` пример строят на трёх lambda: первая находит новые партиции, вторая работает как `Map` и возвращает флаг успеха для каждой, третья при наличии ошибок ставит таблице атрибут `is_partial`.

## Fan-Out: одна ветка в несколько

Один датасет часто нужен разным командам, например аналитикам и data science.

### Parallel Split

**Проблема.** Вы заменяете старый framework на C#, который никто не знает. Ваш reverse engineering может быть неточным. Поэтому старые пайплайны остаются, пока потребители не перейдут. На время миграции результат пишут в два места.

**Как работает:**

- Две и больше независимые дочерние задачи зависят от общего родителя. Оркестратор описывает это через DSL или функции языка.
- В обработке данных есть три условия:
  - Общий датасет считают один раз: временная таблица в SQL или `persist()` в `Spark`.
  - Ветки не мешают друг другу. Общие переменные только для чтения.
  - Если расчёт чувствителен ко времени, выделите отдельные ресурсы или автомасштабирование.
- Повтор не должен дублировать данные. В `Delta Lake` для этого есть `txnAppId` и `txnVersion`: при повторе записывается только первый раз. Без такой защиты используйте паттерны [главы 4](/book-summaries/engineering/data-engineering-design-patterns/04-idempotency/).

**Цена:**

- **Blocked execution.** Следующий запуск ждёт самую медленную ветку. Если она падает, следующие запуски не стартуют. Медленную ветку выносят в отдельный пайплайн (как в `Isolated Sequencer`).
- **Hardware.** Если один job грузит CPU, а второй память, общая инфраструктура не подходит. Сначала создают промежуточный датасет, потом запускают job на своём железе.

**Примеры.** В `Airflow` ветки получаются из цикла по форматам вывода. Общая точка - первый sensor, общей задачи в конце нет. В `Spark` вход читают один раз и вызывают `persist()`. Если памяти мало, можно хранить на диске.

```python
file_sensor = FileSensor(task_id='input_dataset_waiter')

for output_format in ['delta', 'csv']:
    trigger = SparkKubernetesOperator(
        task_id=f'load_job_trigger_{output_format}',
        params={'output_format': output_format})
    sensor = SparkKubernetesSensor(task_id=f'load_job_sensor_{output_format}')
    file_sensor >> trigger >> sensor
```

```python
(input_dataset.write.mode('append').format('delta')
    .option('txnVersion', 1).option('txnAppId', 'devices-loader-v1')
    .save(devices_table))
```

### Exclusive Choice

**Проблема.** Миграция прошла хорошо. С 1 января 2024 года новая версия job должна работать только для новых дат. При backfill старые даты идут через старую версию. Новый пайплайн создавать не хочется: история запусков потеряется.

**Как работает:**

- Дочерних задач две, но выполняется одна. Перед ветвлением ставят задачу-условие.
- В `Airflow` это `BranchPythonOperator`, в `Azure Data Factory` - `if condition`, в `Step Functions` - `Choice`.
- В обработке данных это обычный `if/else`.
- Условие лучше строить на metadata (дата запуска, параметр, схема файла). Условие по данным требует чтения и дороже.

**Цена.** Главная опасность - гибкость. Много веток быстро портят понимание.

- **Complexity factory.** Много `if-else` дают много веток, которые сливаются и делятся. Проверка: объясните пайплайн новому коллеге. Если объяснение длинное, пайплайн сложен. Автор называет это rubber duck debugging.
- **Hidden logic.** Условия внутри job легко забыть. Лучше вынести выбор в оркестратор и запускать разные точки входа.
- **Heavy conditions.** Условие по данным увеличивает время job. Читайте данные один раз и по возможности инкрементально.
- Для периода действия логики часто проще завести пайплайн с `start_date` и `end_date`.

**Примеры.** В `Airflow` параллельный запуск получали повторным описанием цепочки, но для выбора нужен `BranchPythonOperator`: он по дате запуска направляет выполнение в ветку CSV или Delta. В обработке данных условие приходит из конфигурации. Тогда клиентский код получает нужный `SparkSession`, а запись выбирается по типу вывода. Повтор условий убирают фабрика и отдельные классы для Delta и CSV. Другой вариант: условие по схеме файла. Если полей минимум три, job пишет в новое место. Схему берут из metadata, и это быстро.

## Оркестрация (Orchestration)

До сих пор потоки были статичными. Теперь вопрос: сколько запусков одного пайплайна идёт одновременно.

### Single Runner

**Проблема.** Вы сделали sessionization с `Incremental Sessionizer` из [главы 5](/book-summaries/engineering/data-engineering-design-patterns/05-data-value/) как proof of concept и запускали job вручную. Проект выходит в релиз. Граф есть, нужен способ его запускать.

**Как работает:**

- Sessionization инкрементальна, значит последовательна. Паттерн гарантирует один запуск пайплайна за раз.
- В `Airflow` это `max_active_runs=1`, в `Azure Data Factory` - настройка `Concurrency`.
- Добавьте `depends_on_past=True`. Тогда задача не стартует, если та же задача прошлого запуска упала.
- На уровне кластера есть `StepConcurrencyLevel` в `AWS EMR`.
- Если оркестратор не умеет этого, используйте `Readiness Marker`, который ждёт прошлый запуск. Но будущие запуски он не блокирует: все они будут ждать.

**Цена:**

- **Backfilling.** Пересчёт очень медленный. Ограничение - требование бизнеса, параллельные запуски дадут неверный результат. Можно лишь не пересчитывать лишние шаги. Например, если нужно только заново вставить датасет в другое место, обработку пропускают.
- **Latency.** Пример: почасовой поток вместо 30 минут идёт 1,5 часа, данные задерживаются всё больше. Страдают все потребители. На масштабируемой инфраструктуре помогут больше мощности или лучшая логика.
- В `Data Factory` лишние запуски встают в очередь (до 100). При переполнении будет ошибка 429.

```python
with DAG('visits_trend_generator', max_active_runs=1, default_args={
    'depends_on_past': True,
}) as dag:
    ...
```

### Concurrent Runner

**Проблема.** Команда загрузки приносит данные из внешних источников. Загрузка идёт 30-60 минут, но иногда дольше, и при `Single Runner` все поставки опаздывают. Датасеты не зависят друг от друга.

**Как работает:**

- Задайте параллелизм больше 1: в `Airflow` это `max_active_runs=5`.
- Оркестратор берёт следующий запуск, пока число активных ниже лимита. Найдите баланс с другими пайплайнами.
- `depends_on_past` можно оставить `False`. В `Data Factory` можно задать concurrency, но не зависимость по задаче.

**Цена:**

- **Resource starvation.** В multitenant-среде несколько пайплайнов с большим параллелизмом и backfill могут занять весь планировщик. Помогает `workload management`: группе выделяют квоту. В serverless лимиты высокие: `Step Functions` разрешает до 10 000 параллельных дочерних запусков.
- **Shared state.** Общее состояние при параллельных запусках даёт непредсказуемый результат. Пример - `Dynamic Late Data Integrator`: backfill может запуститься несколько раз или не запуститься вовсе.

## Итоги главы

- Паттерны потока данных работают на уровне оркестратора и на уровне кода обработки.
- `Local Sequencer` делит большую задачу на шаги. Границы ставят по перезапускам: дорогое отделяют, транзакцию держат вместе.
- `Isolated Sequencer` связывает пайплайны разных команд через marker (слабая связь) или прямой триггер (сильная связь).
- `Aligned Fan-In` быстрее показывает ошибки и позволяет перезапускать один час, но создаёт пик нагрузки и ожидание самой медленной ветки.
- `Unaligned Fan-In` разрешает старт при сбое части родителей. Потребителей нужно предупредить о неполных данных.
- `Parallel Split` считает общий датасет один раз и защищает записи от дубликатов. `Exclusive Choice` выбирает одну ветку по условию на metadata.
- `Single Runner` нужен инкрементальным пайплайнам, но замедляет backfill. `Concurrent Runner` ускоряет независимые запуски, но требует квот и осторожности с общим состоянием.

## Ключевые термины

| Термин | Значение |
|---|---|
| `Data orchestration layer` | Уровень оркестратора. Задачи, расписание, зависимости |
| `Data processing layer` | Уровень кода обработки. `Spark`, SQL |
| `Fan-in` | Много веток сходятся в одну задачу |
| `Fan-out` | Одна задача расходится в несколько веток |
| `Trigger rule` | Условие запуска задачи по статусу родителей |
| `Sensor` | Задача, которая ждёт данные или событие |
| `Backfill` | Пересчёт прошлых периодов |
| `Scheduling skew` | Ожидание самой медленной ветки |
| `Partial data` | Результат по неполным входным данным |
| `Concurrency` | Число запусков одного пайплайна одновременно |
| `Resource starvation` | Один пайплайн забирает все ресурсы |

## Что это значит на практике

- Делите большой DAG на задачи по границам перезапуска. Дорогие шаги должны перезапускаться отдельно.
- Между командами договаривайтесь о схеме и расписании. Держите зависимости явными: `Readiness Marker` или `ExternalTaskSensor`.
- Для fan-in задайте лимит параллелизма. Иначе 24 или больше веток нагрузят кластер.
- Если публикуете частичные данные, пишите флаг полноты в таблицу. Потребитель не должен гадать.
- Условия `if/else` выносите в оркестратор. Не прячьте их в код job.
- Для инкрементальных пайплайнов ставьте `max_active_runs=1` и `depends_on_past`. Независимым загрузкам разрешайте параллелизм.
- При backfill следите за ресурсами других команд. Используйте квоты.
