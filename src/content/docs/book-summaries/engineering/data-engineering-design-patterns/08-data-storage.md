**Главная мысль:** Быстрый запрос начинается с правильной раскладки данных. Раскладка уменьшает объём чтения, а значит, время и стоимость. Но у каждой оптимизации есть цена: статичность, место на диске или стоимость записи.

## О чём глава

В [главе 7](/book-summaries/engineering/data-engineering-design-patterns/07-data-security/) мы защищали данные. Теперь вопрос другой: как хранить их так, чтобы запросы шли быстро и стоили дешевле. Время запроса можно сократить двумя способами. Первый - добавить ресурсы. Это быстро, но это реакция на жалобы, под давлением. Второй - заранее продумать раскладку данных. Этому посвящена глава.

Темы главы:

- Партиционирование: горизонтальное и вертикальное. Оно уменьшает объём данных и помогает идемпотентности ([глава 4](/book-summaries/engineering/data-engineering-design-patterns/04-idempotency/)), но работает только для колонок с малой cardinality.
- `Bucket` и `Sorter` для колонок с большой cardinality.
- Ускорение чтения: метаданные, материализация и manifest.
- Представление данных: `Normalizer` и `Denormalizer`.

## Все паттерны главы

| Паттерн | Когда применять |
|---|---|
| `Horizontal Partitioner` | Запросы читают часть строк по времени или по бизнес-ключу с малым числом значений |
| `Vertical Partitioner` | В строке есть изменяемые и неизменяемые атрибуты, или у групп атрибутов разные правила доступа |
| `Bucket` | Колонка с большим числом значений часто стоит в фильтре или в `JOIN` |
| `Sorter` | Запросы часто фильтруют или сортируют по одним и тем же колонкам |
| `Metadata Enhancer` | Нужно пропускать ненужные файлы или блоки, не читая их |
| `Dataset Materializer` | Один тяжёлый запрос выполняется снова и снова |
| `Manifest` | Листинг файлов в object store медленный |
| `Normalizer` | Важнее всего согласованность данных и дешёвые обновления |
| `Denormalizer` | Важнее всего скорость чтения, `JOIN` слишком дорогие |

## Партиционирование

Первый вопрос про хранилище: как разделить набор данных, чтобы читать нужную часть. Есть два паттерна: горизонтальный и вертикальный.

### Horizontal Partitioner

Это самый распространённый способ организации данных. Он прост и популярен с первых дней data engineering.

- **Проблема:** Задача считает скользящие агрегаты за 4 дня. Данных стало больше, и фильтр по возрасту замедлился. Вы добавили мощность кластера, но затраты выросли. Нужно вернуть низкую цену и скорость.
- **Как работает:**
  - Выбираем атрибут партиционирования (`partition key`, он же distribution key). Для каждого его значения данные пишутся в отдельное физическое место.
  - Временной ключ может прийти из контекста запуска (время работы job, одинаковое для всех записей) или из самих данных (`event time`). Во втором случае из-за late data один датасет может попасть в разные partition.
  - Ключ может быть и бизнес-атрибутом: клиент, партнёр, регион. Ключи можно вкладывать: год, месяц, день, страна.
  - Декларативный способ: `PARTITIONED BY` в Databricks и BigQuery. Продюсеру не нужно знать про partition. Другой способ: логику задаёт продюсер, как `partitionBy` в Spark или свой partitioner в Kafka.
  - Многие хранилища показывают метаданные partition (время обновления, число строк): `INFORMATION_SCHEMA.PARTITIONS` в BigQuery, view `partitions` в Iceberg.
  - На партиционировании построен `Fast Metadata Cleaner`.
- **Цена.** Главный минус - статичность.
  - **Granularity.** Слишком много partition вредит базе. Если миллион пользователей в день, а ключ - имя пользователя, будет миллион partition: листинг замедлится, появятся мелкие файлы (проблема из `Compactor`). Берите атрибуты с малой cardinality: час или день. Для ID устройств IoT лучше `Bucket`.
  - **Skew.** Partition бывают разного размера. В микробатче самая большая partition определяет время всего батча. Помогает backpressure: лишние записи перекошенной partition уходят в буфер и идут в следующем батче. Её задержка растёт, но остальные работают почти в реальном времени.
  - **Mutability.** Смена ключа требует переместить все данные. Исключение: Apache Iceberg меняет схему партиционирования на уровне метаданных, и она применяется только к новым записям.
  - `Sharding` - частный случай партиционирования на уровне железа: данные делятся между машинами. Горизонтальное партиционирование не требует перемещения между машинами.
- **Примеры.** В `Spark` метод `partitionBy` создаёт каталоги год/месяц/день/час по колонке `change_date`. В Kafka пишут свой partitioner на Java и указывают класс в `partitioner.class`. Но автор советует простоту: любой код усложняет систему, поэтому чаще берут partitioner по умолчанию. В реляционных базах (PostgreSQL) партиции создают командами таблицы.

```sql
-- PostgreSQL: одна партиция на день
CREATE TABLE visits (
  visit_id TEXT, event_time TIMESTAMP, page TEXT,
  PRIMARY KEY (visit_id, event_time)
) PARTITION BY RANGE (event_time);

CREATE TABLE visits_20250101 PARTITION OF visits
  FOR VALUES FROM ('2025-01-01') TO ('2025-01-02');
```

### Vertical Partitioner

Паттерн с тем же именем есть в [главе 7](/book-summaries/engineering/data-engineering-design-patterns/07-data-security/). Там он применён к безопасности, а здесь - к хранению. Горизонтальный паттерн работает со строкой целиком. Вертикальный делит строку и пишет части в разные таблицы или файлы.

- **Проблема:** В событии визита есть атрибуты, которые меняются с каждым событием (время, страница), и атрибуты, которые постоянны весь визит (IP). Вторые не хочется хранить по сто раз.
- **Как работает:**
  - Классифицируем атрибуты: изменяемая и неизменяемая группы. Выбираем атрибут, который их соединяет (`visit_id`).
  - Job пишет группы каждой строки в отдельные места: таблицы или каталоги.
  - Плюс гибкость: для разных групп можно задать разный срок хранения и доступ.
  - Отличие от горизонтального - в эвристике: там правило применяется к целой строке, здесь строка делится.
- **Цена:**
  - **Domain split.** Связанные атрибуты лежат в двух местах, их трудно найти. Нужна хорошая документация.
  - **Querying.** Полную картину собрать сложнее, нужен `JOIN`. Помогает view над всеми таблицами (например, через `Dataset Materializer`).
  - **Data producer.** Продюсер не может просто взять строку и записать её. Он делит строку и пишет несколько раз, возможно дороже по сети.
- **Примеры.** В `Spark` вызывают `persist()`, чтобы не читать вход дважды, и строят две таблицы через `select()` и `drop()`. В PostgreSQL помогает `INSERT INTO ... SELECT` или `CREATE TABLE AS SELECT` (CTAS).

## Организация записей

Партиционирование грубое: оно переносит строки или их части в разные места и не работает для колонок с большой cardinality. Следующие паттерны добавляют умную раскладку записей.

### Bucket

Если нужно ускорить колонку с большой cardinality, например уникальный `user_id`, можно держать вместе не строки с одним значением, а группы строк.

- **Проблема:** Бизнес-атрибут стоит в 80% предикатов. Как partition его брать нельзя: папок будет слишком много, и вы упрётесь в лимиты метаданных.
- **Как работает:**
  - Анализируем данные и выбираем колонки bucket. Если датасет уже партиционирован, bucket-колонки служат вторичным ключом группировки.
  - Задаём число bucket. Оно зависит от cardinality: больше bucket - они меньше. Номер bucket: `hash(key) % число_buckets`. В отличие от partition, разные значения лежат вместе.
  - `Bucket pruning`: фильтр по bucket-колонке пропускает все bucket без нужных ключей.
  - `Shuffle elimination`: если две таблицы разбиты одинаково, `JOIN` грузит связанные записи в один процесс без обмена по сети (как при `Distributed Aggregator`).
  - Популярным bucketing сделал Hive. Теперь он есть в Spark и AWS Athena.
- **Цена:**
  - **Mutability.** Схема bucket неизменяема. Смена колонки или размера - дорогой backfill.
  - **Bucket size.** Подобрать размер трудно, если данные будут расти. По текущему объёму потом bucket станут большими. Если угадывать заранее, можно создать лишние bucket.
- **Примеры.** Athena применяет bucketing только логически: данные она не пишет. Поэтому `INSERT INTO` в таблицу с bucket даст ошибку. Колонки задают в `CLUSTERED BY`, а также формат bucketing (например, как в Spark). В `Spark` вызывают `bucketBy`, и он считает bucket по модулю.

### Sorter

Другой способ пропускать ненужные блоки данных - хранить записи в определённом порядке.

- **Проблема:** Вы храните данные в недельных таблицах ради `Fast Metadata Cleaner`. Чистка стала проще, но запросы не ускорились. Менять стратегию идемпотентности вы не хотите. Известно, что большинство запросов фильтруют или сортируют по `event_time`.
- **Как работает:**
  - Выбираем колонки сортировки и объявляем их при создании таблицы. База сама упорядочит записи.
  - Запросы по этим колонкам пропускают лишние блоки, часто по метаданным блока (см. `Metadata Enhancer`).
  - Обычная лексикографическая сортировка есть как `CLUSTER BY` в BigQuery и clustered tables в Snowflake.
  - Кривая `Z-order` - вариант сортировки: она размещает рядом строки в многомерном пространстве вместо порядка сверху вниз. Подробности алгоритма вне книги. Z-order реализован в Delta Lake и Iceberg. Он лучше лексикографической сортировки для нескольких колонок: нужно читать меньше блоков. В Redshift похожую вещь делают interleaved sort keys.
  - Z-order иногда называют clustering, но по сути он сортирует данные на диске, поэтому автор относит его к `Sorter`.
- **Цена.** Читателю лучше, писателю хуже.
  - **Unsorted segments.** Сортировка не мгновенна: новые записи лежат в несортированных блоках без выигрыша. Сортировку планируют в job записи или отдельно. Если встроить её в запись, время job вырастет.
  - **Composite sort keys.** При составном ключе запрос должен упоминать ведущие колонки. Если фильтр только по второй колонке (например, page ID при ключе «время, страница»), движок всё равно читает почти все блоки.
  - **Mutability.** Ключи часто можно сменить, но придётся пересортировать всю таблицу. Для большой таблицы это дорого.
- **Примеры.** В BigQuery clustered table задают через `CLUSTER BY`. Если фильтровать только по второй колонке, выигрыш мал. Эту проблему решает кривая: в Delta Lake Z-order compaction вызывают с колонками кривой, и файлы перепаковываются так, чтобы записи лежали лучше.

```sql
-- BigQuery: partition по дню, сортировка по двум колонкам
CREATE TABLE visits_raw (...)
PARTITION BY DATE(event_time)
CLUSTER BY visit_id, page;
```

## Оптимизация чтения

Следующие паттерны дополняют раскладку и ускоряют доступ.

### Metadata Enhancer

Колонночные форматы вроде Parquet стали переломом в data engineering как раз из-за метаданных.

- **Проблема:** Вы партиционировали JSON по `event time`, и батчи ускорились. Но аналитикам нужна малая часть записей одной большой partition. Они жалуются на задержку и счёт в сервисе с оплатой за запрос: запрос сначала грузит весь датасет и только потом фильтрует. Нужно фильтровать до загрузки.
- **Как работает:** Нужно пропустить ненужные файлы до чтения. Для этого собирают и хранят статистику о записях.
  - В колонночном формате вроде Parquet в каждом файле есть footer с диапазоном значений колонки. Его считает продюсер при создании файла. Для запроса `WHERE age > 50` движок смотрит footer и решает, нужен ли файл. Читать все footer приходится, но это несравнимо дешевле чтения всех файлов.
  - Parquet лежит в основе Delta Lake, Iceberg и Hudi, поэтому паттерн есть и там. Кроме того, они хранят в commit log число строк коммита, min и max по колонкам и число `NULL`. Так быстро считают количество и фильтруют по несуществующим значениям.
  - В реляционных базах и хранилищах статистика лежит в отдельной таблице, и по ней планировщик строит планы.
- **Цена.** Минусов мало.
  - **Overhead.** Job при записи считает статистику по каждой колонке, и время слегка растёт. Базе нужно держать статистику свежей, иначе план далёк от лучшего.
  - **Out-of-date statistics.** Автообновление идёт по порогу, например числу изменённых строк. При мелких изменениях статистика устаревает. Обновить можно вручную (`ANALYZE TABLE`), но это временно нагрузит базу.
- **Примеры.** При записи Parquet в Spark статистика появляется сама: для колонки ID видны min, max и число NULL. Delta Lake добавляет свой слой в commit log, тоже без явного кода.

### Dataset Materializer

Тяжёлый запрос с shuffle и CPU-расчётами, который идёт снова и снова, замедляет чтение. Выход неожиданный: дублирование данных.

- **Проблема:** Вы сделали view над несколькими партиционированными таблицами, чтобы получать три недели данных. Потребители жалуются на задержку: view выполняет запрос при каждом чтении.
- **Как работает:** Когда расчёт медленный, проще всего его материализовать.
  - Пишем запрос (`SELECT`, `UNION`, `JOIN`) и сохраняем результат как materialized view или как таблицу.
  - Главное отличие - обновление. View можно обновлять вручную, а современные хранилища (Redshift, BigQuery, Databricks, Snowflake) умеют автообновление. Например, `AUTO REFRESH YES` в Redshift. Но оно идёт не сразу после изменения: зависит от нагрузки и объёма, поэтому менее предсказуемо.
  - Таблицу нужно обновлять самим. Взамен больше свободы: к ней можно применить partition, bucket и sorting.
- **Цена:**
  - **Refresh cost.** Каждое обновление повторяет запрос и занимает ресурсы базы, в том числе у обычных пользователей. Помогает инкрементальное обновление, хорошее для insert-only нагрузок. Databricks и BigQuery поддерживают его, но не для всех операций SQL, и иногда обновляют всё.
  - **Data access.** Датасет собирает несколько таблиц, и согласовать retention и доступ трудно. Если нет доступа к одной таблице, view тоже нужно закрыть. Или используйте `Fine-Grained Accessor`.
  - **Data storage overhead.** Оптимизация платится местом. Можно материализовать только часть, остальное оставить обычными пересчитываемыми частями.
- **Примеры.** В BigQuery автообновление можно задать, например, каждые 15 минут. Оно должно сработать в течение пяти минут после изменения, но при нехватке мощности задержится. Вручную в PostgreSQL: `REFRESH MATERIALIZED VIEW`.

Инкрементальный вариант: по колонке `insertion_time` берём только строки после прошлого запуска и объединяем с датасетом. Это связка `Incremental Loader` и `Merger`.

```sql
MERGE INTO visits_counter t
USING (
  SELECT user_id, COUNT(*) AS visits
  FROM visits
  WHERE insertion_time > '2025-01-01 03:00:00'
  GROUP BY user_id
) i ON t.user_id = i.user_id
WHEN MATCHED THEN UPDATE SET visits_count = t.visits_count + i.visits
WHEN NOT MATCHED THEN INSERT (user_id, visits_count) VALUES (i.user_id, i.visits);
```

### Manifest

Листинг файлов в object store медленный, особенно при многих файлах: это много API-вызовов. Параллелить листинг можно, но есть путь лучше.

- **Проблема:** Вы создали датасет Parquet в object store, батчи работают быстро. Теперь датасет нужно открыть аналитикам через слой хранилища данных. Тесты показали, что самая медленная операция у читателей - листинг файлов.
- **Как работает.** Файлы листят один раз или совсем не листят, если продюсер записывает имена заранее.
  - Табличные форматы Delta Lake, Iceberg и Hudi делают это сами. Они пишут список файлов транзакции в commit log. Читатель берёт список оттуда, без листинга. Commit log в этом смысле служит manifest.
  - Ручные manifest полезны, когда с одним датасетом работают многие читатели, например при fan-out ([глава 6](/book-summaries/engineering/data-engineering-design-patterns/06-data-flow/)).
  - Manifest помогает и при записи. В Redshift `COPY` берёт manifest, и для каждой загрузки можно задать свой список файлов. Повтор загрузит те же файлы, и пайплайн идемпотентен ([глава 4](/book-summaries/engineering/data-engineering-design-patterns/04-idempotency/)). Похоже работает Storage Transfer Service в GCP.
- **Цена:**
  - **Complexity.** Шаг создания manifest усложняет пайплайн. Но создать manifest (список недавно записанных файлов) проще, чем многократно выполнять медленный и непредсказуемый листинг.
  - **Size.** Manifest может вырасти до нескольких гигабайт при мелких файлах или непрерывном streaming. У реализаций бывает лимит размера или retention записей. В ранних версиях Spark Structured Streaming manifest рос так, что job иногда не мог перезапуститься (исправлено, SPARK-27188).
- **Примеры.** Первый: внешняя таблица в BigQuery для Delta Lake. Delta Lake генерирует manifest со списком файлов последней версии таблицы, и внешняя таблица ссылается на него в `uris`. Второй: в Redshift manifest из двух файлов создают до загрузки и привязывают к запуску. При повторе job берёт тот же файл.

## Представление данных

Хранение - это не только раскладка и скорость чтения. Остаётся вопрос представления: какие атрибуты хранить вместе и какие таблицы создавать.

### Normalizer

Первый паттерн представления разделяет данные и поэтому хранит их согласованно: информация не дублируется.

- **Проблема:** В таблице визитов лежат атрибуты события (время, страница) и неизменяемые атрибуты (устройство, ОС и её версия). Они повторяются в каждой строке. Хранилище растёт, а обновления этих атрибутов медленные. Нужна модель без повторов.
- **Как работает.** Идея - хранить каждый факт один раз. Паттерн имеет две реализации: нормальные формы (NF) и `snowflake schema`. Процесс у них общий:
  1. Определяем бизнес-сущности: визиты, устройства, браузеры, переходы.
  2. Описываем атрибуты каждой сущности, например название и версия браузера.
  3. Описываем связи: визит зависит от браузера, браузер - от ОС.
- NF широко используют в транзакционных нагрузках. Они снижают дубли и объём записи. Три основные формы:
  - `1NF`: значения атомарны, без повторов, у каждой строки есть первичный ключ.
  - `2NF`: каждая не ключевая колонка зависит от всего первичного ключа.
  - `3NF`: нет транзитивных зависимостей между не ключевыми колонками, все зависят только от ключа.

> **More Normal Forms.** Форм больше трёх, но этих трёх достаточно, чтобы применить паттерн.

Автор показывает три сломанные формы на примере таблиц об играх:

| Форма | Что сломано | Как чинить |
|---|---|---|
| `1NF` | В колонке comments лежит несколько значений | Вынести каждый comment в таблицу `games_comments` |
| `2NF` | Ключ - название и платформа. Язык платформы зависит только от платформы | Создать таблицу платформы и языка |
| `3NF` | Страна студии зависит от студии, а не от игры (транзитивная зависимость) | Создать таблицу `studios` |

- Для аналитики есть размерная модель: одна fact table (наблюдение: заказ, визит) и несколько dimension tables (контекст: товар, браузер).
- `Snowflake schema` - вариант, где измерения описываются другими измерениями. Например, дата делится на подизмерения: кварталы и месяцы.
- Главная цель: согласованность важнее скорости. Обновление сразу видно во всех связанных таблицах.
- **Цена.** Главный минус - сложность. Это плата за согласованность.
  - **Query cost.** Данные разнесены, и запросы часто требуют `JOIN`. В распределённой среде это дорого из-за обмена по сети. Снижают трафик через `colocation` малых таблиц рядом с большими или через broadcast малых таблиц на все узлы.
  - Большую таблицу проще всего уменьшить фильтром. Иначе поднимите порог broadcast: в `Spark` это `spark.sql.autoBroadcastJoinThreshold`.
  - **Archival.** Измерение может зависеть от времени. Цена товара меняется по годам, и вы хотите знать цену на дату. Это решают техники `SCD` из `Static Joiner` ([глава 5](/book-summaries/engineering/data-engineering-design-patterns/05-data-value/)).
- **Примеры.** Таблицы визита раскладываются на несколько. Браузеры и устройства лежат отдельно, потому что они не зависят от визита и общие для многих визитов. Контексты визита не лежат в `visits`: возникли бы повторяющиеся группы, а это нарушает `1NF`. Полная картина визита требует длинного запроса. Нормализованные датасеты неудобно читать, и на больших данных их число `JOIN` вредит скорости. В snowflake то же самое.

### Denormalizer

Раз соединения дороги, их можно убрать. Побочные эффекты придут ниже.

- **Проблема:** Компания построила реляционную модель поверх хранилища. Данных стало много, и аналитики жалуются на время запросов. Самое дорогое решение соединяет все восемь таблиц, а они нужны в 80% запросов.
- **Как работает.** В отличие от `Normalizer`, паттерн сокращает или убирает `JOIN`. Значения всех соединяемых таблиц кладут в одну строку, и обмен по сети не нужен. Два способа:
  - Как обычные колонки. Колонки копируют как есть, и пользователь берёт их прямо в `SELECT`. Пример: визиты вместе с пользователями и устройствами в одной таблице. Это `One Big Table`.
  - Как вложенные структуры. Строки соединяемых таблиц кладут в одну колонку типа `STRUCT`. Пользователь обращается к атрибутам этой колонки.
  - Промежуточный путь - `star schema`. Это размерная модель, где fact table и dimension tables остаются, но вложенных измерений нет: измерения, описывающие другие измерения, уходят в измерение верхнего уровня.
- Стоимость запроса заметно падает из-за меньшего трафика.
- Паттерны не исключают друг друга. Можно построить нормализованную модель, а поверх неё - денормализованную для запросов. Для синхронизации служат паттерны последовательности ([глава 6](/book-summaries/engineering/data-engineering-design-patterns/06-data-flow/)). Нормализованную схему можно скрыть как приватную опорную модель.
- **Цена.** Денормализация жертвует согласованностью.
  - **Costly updates.** Все атрибуты теперь копии, и обновление меняет много строк. Универсального решения нет. Если считать таблицу снимком на момент времени, обновления не нужны. Иначе придётся принять дорогое обновление ради быстрого ответа.
  - **Storage.** Одно и то же повторяется много раз. Помогает кодирование, например словарь: длинные строки заменяют числами. Это экономит место и иногда ускоряет запросы: наличие значения проверяют по словарю.
  - **One big antipattern.** `One Big Table` без доменной логики превращается в мусорную корзину: данные пользователя, прошлые заказы, колонки текущего визита и любимый цвет. Чтобы понять, где остановиться, дайте таблице имя. Если в названии просятся «и» или «с», несвязанных атрибутов слишком много.
- **Примеры.** `One Big Table` создавать дорого, но платят один раз за обновление, а читатели работают намного быстрее. В `star schema` при записи создаётся больше таблиц, а при чтении нужны `JOIN`: данные не полностью плоские.

```sql
-- Нормализованно: нужно два JOIN
SELECT v.visit_id, u.login, d.type
FROM visits v
LEFT JOIN users u ON v.user_id = u.id
LEFT JOIN devices d ON v.device_id = d.id;

-- Денормализованно: JOIN не нужен
SELECT visit_id, user_login, device_type FROM visits_one_big_table;
```

## Итоги главы

- Партиционирование уменьшает объём чтения. Горизонтальное делит строки по ключу с малой cardinality, вертикальное делит атрибуты одной строки.
- У `Horizontal Partitioner` три риска: слишком много partition, `skew` и трудная смена ключа.
- Для большой cardinality подходят `Bucket` (`hash(key) % N`, bucket pruning, `JOIN` без shuffle) и `Sorter` (порядок записей, `Z-order`). Их трудно менять после создания.
- `Metadata Enhancer` пропускает ненужные файлы по статистике, `Dataset Materializer` меняет место на скорость чтения, `Manifest` заменяет медленный листинг.
- `Normalizer` ставит согласованность выше скорости. `Denormalizer` убирает `JOIN`, но делает обновления дорогими.

## Ключевые термины

| Термин | Значение |
|---|---|
| `Partition` | Физически отдельное место хранения для значения ключа |
| `Cardinality` | Число различных значений в колонке |
| `Skew` | Неравномерный размер partition |
| `Bucket` | Группа строк, выбранная по `hash(key) % N` |
| `Z-order` | Кривая сортировки по нескольким колонкам сразу |
| `Data skipping` | Пропуск файлов или блоков по min/max статистике |
| `Materialized view` | Сохранённый результат запроса с обновлением |
| `Manifest` | Файл со списком файлов набора данных |
| `Normal form` | Правила нормализации таблиц (`1NF`-`3NF`) |
| `One Big Table` | Широкая денормализованная таблица |

## Что это значит на практике

- Партиционируйте по времени или по ключу с малым числом значений. Для `user_id` берите `Bucket`.
- Проверяйте число partition. Тысячи мелких partition замедляют листинг.
- В BigQuery и Snowflake комбинируйте partition по дате и clustering по частым фильтрам.
- В Delta Lake и Iceberg периодически делайте `OPTIMIZE` и `Z-order` по колонкам фильтра.
- Используйте Parquet: его статистика даёт `data skipping` бесплатно. Следите за свежей статистикой в хранилище.
- Для тяжёлых витрин в `dbt` выбирайте `table` или `incremental` вместо `view`.
- В хранилище часто строят нормализованный слой для консистентности и денормализованную витрину для BI.
