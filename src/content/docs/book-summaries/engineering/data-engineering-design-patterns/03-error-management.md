**Главная мысль:** Ошибки в пайплайнах неизбежны: плохие записи, дубли, опоздавшие данные, сбои задач. Паттерны главы не убирают ошибки. Они делают так, чтобы пайплайн жил с ними и данные не портились.

## О чём глава

Глава отвечает на вопрос: что делать, когда данные или сама система ведут себя не так, как вы ждёте. Она идёт после [главы о загрузке](/book-summaries/engineering/data-engineering-design-patterns/02-data-ingestion/). Данные делают другие, и вы наследуете их проблемы: ненадёжная сеть даёт поздние данные, временный сбой даёт повторную доставку и дубли. Данные и ожидания меняются, поэтому надо ждать худшего. Главные темы: необработанные записи, дубли, опоздавшие данные, фильтрация и отказоустойчивость стриминга.

Ошибки бывают двух типов:

- **Transient:** временные. Они проходят сами. Пример: база недоступна несколько секунд. Помогает retry.
- **Nontransient:** сами не проходят. Пример: `poison pill message`, запись, которую нельзя обработать. Нужно вмешательство человека или специальный паттерн.

Автоматические retry создают новую проблему: дубли. Поэтому глава 3 заканчивается выводом: нужна идемпотентность. Это тема главы 4.

## Паттерны главы

| Паттерн | Когда применять |
|---|---|
| `Dead-Letter` | Одна плохая запись не должна останавливать весь job |
| `Windowed Deduplicator` | Источник дублирует записи из-за retry продюсера |
| `Late Data Detector` | Нужно понять, что событие пришло слишком поздно |
| `Static Late Data Integrator` | Опоздавшие данные приходят в известном окне (например, до 15 дней) |
| `Dynamic Late Data Integrator` | Окно опоздания неизвестно. Хотите пересчитать только затронутые партиции |
| `Filter Interceptor` | Нужно знать, какой фильтр отбросил сколько строк |
| `Checkpointer` | Стриминговый job должен продолжить с места остановки после сбоя |

## Необработанные записи

### `Dead-Letter`

Подход fail-fast (упасть сразу) прост, но для долгих streaming job он не всегда возможен. Плохие записи можно пропустить, но тогда они потеряны. Если терять нельзя, их сохраняют отдельно для разбора.

**Проблема.** Streaming job пишет события посещений из Kafka в object store. Продюсеры начали слать записи, которые нельзя обработать, и job падает. Три дня подряд вы перезапускаете его и вручную правите offset в файлах checkpoint. Нужно решение, при котором job работает при единичных плохих записях, а ошибки можно разобрать позже.

**Как работает:**

- Найдите места, где job может упасть: функция `map`, парсинг, преобразование.
- Оберните их в `try-catch` (или `if-else`, если фреймворк возвращает `NULL` вместо ошибки).
- Плохую запись отправьте в отдельное хранилище: dead-letter storage. Добавьте метаданные: текст ошибки, имя job, версию, время (паттерн `Metadata Decorator`).
- Хранилище выбирайте по трём признакам: надёжность, простой мониторинг и скорость записи. Мониторинг главный: важно знать, когда появились плохие записи и сколько их. По этим числам видно, ошибки случайны или система разваливается. Подходят object store и брокеры.
- По желанию добавьте replay pipeline. Он возвращает исправленные записи в основной поток. Нужен, только если важны прошлые данные.

Паттерн работает и в batch. Streaming пишет одну запись за раз, batch пишет в dead-letter сразу пачку плохих строк.

**Компромиссы:**

- **Snowball backfilling.** При fail-fast всё просто: pipeline остановился, потребители не получили данных. Без него они обрабатывают, возможно, неполные данные. Replay кладёт записи в партиции, которые потребители уже обработали. Им нужен `backfill`, а их потребителям тоже. Выход один: не делать replay и потерять записи. Или сделать `backfill`, но тогда набор станет несогласованным, если кто-то не может пересчитать.
- **Как отличить replay-записи.** Добавьте колонку вроде `was_dead_lettered` или метаданные: job, версия, время replay.
- **Порядок и согласованность.** IoT-датчики шлют событие каждую минуту, сессия закрывается после пяти минут неактивности. Если события пять минут лежат в dead-letter, сессия закроется раньше времени. С порядком так же: записи 10:00, 10:01, 10:02, запись 10:01 вернулась через replay, и порядок стал 10:00, 10:02, 10:01.
- **Error-safe функции.** Они возвращают `NULL` вместо исключения. Нужно сравнивать вход и выход: вход не `NULL`, а выход `NULL` значит ошибку. У разных функций разная семантика безопасности.
- **Ошибка или сбой.** Паттерн скрывает проблемы. Добавьте алерт. Если плохих записей слишком много, job должен остановиться.

Идея на SQL (данные придуманы):

```sql
-- TRY_CAST возвращает NULL вместо ошибки.
-- Вход не NULL, а выход NULL: значит, запись битая.
SELECT *, NOT (raw_price IS NOT NULL AND price IS NULL) AS is_valid
FROM (SELECT order_id, raw_price, TRY_CAST(raw_price AS DECIMAL(10, 2)) AS price
      FROM orders_raw);
-- дальше: is_valid = true пишем в основную таблицу, false в dead-letter таблицу
```

**Примеры в книге.**

- **Flink.** Паттерн строится на side output (дополнительный приёмник). Функция `map_rows` оборачивает преобразование в `try-catch`, а в `except` пишет строку в side output. В конце job читает side output и пишет в отдельный топик Kafka.
- **Spark SQL и Delta Lake.** Error-safe `CONCAT` вернёт `NULL`, если одна из колонок пуста. Запрос состоит из подзапроса с преобразованием и внешнего запроса, который проверяет результат. Без явных исключений в SQL код получается длинным и тяжёлым для поддержки. В Spark можно писать два результата из одного кэшированного (`persist`) датафрейма.

## Дубликаты

### `Windowed Deduplicator`

Доставка «ровно один раз» в распределённых системах бывает редко, обычно записи приходят «минимум один раз». Для обработки «один раз» нужна дедупликация. Ключ в том, чтобы считать данные ограниченными: в streaming это окна по времени, в batch это текущий набор.

**Проблема.** Batch job читает события, которые стриминг-слой синхронизировал в object store, и отдаёт их бизнес-пользователям. Нужна обработка «ровно один раз» для каждой уникальной записи. Но из-за retry продюсеров в данных есть дубли.

**Как работает:**

- Выберите атрибуты, которые делают запись уникальной (`visit_id` или пара `visit_id` + `visit_time`).
- В batch область дедупликации это текущий набор. Можно включить и прошлые наборы, но это дороже. Используйте `DISTINCT` или `ROW_NUMBER() ... = 1`. В batch нет явного окна, есть неявное глобальное окно на весь набор. От этого и имя паттерна.
- В streaming данных бесконечно много. Поэтому дедупликация идёт в окне по времени. Job хранит уже виденные ключи в `state store` и при каждой записи проверяет, видел ли он ключ. Логика сложнее, чем в batch.
- Старые ключи удаляются по `watermark`. Так состояние не растёт бесконечно.

Три вида `state store` (компромисс между скоростью и согласованностью):

| Вид | Скорость | Риск |
|---|---|---|
| Local (в памяти) | Самый быстрый | Состояние пропадёт при сбое |
| Local с fault tolerance | Быстрый, но есть запись на диск | Чем чаще запись, тем медленнее job |
| Remote | Надёжный | Выше latency и стоимость |

**Компромиссы:**

- **Память против времени.** Вы не знаете, не придут ли дубли через несколько минут. Короткое окно пропустит часть дублей, но нагружает мало. Длинное окно требует больше ключей в `state store`.
- **Дедупликация не равна exactly-once delivery.** После сбоя и автоматического retry запись может обработаться второй раз. Обычно с этим мирятся как с ценой автоматической обработки временных ошибок. Для настоящего exactly-once нужны паттерны идемпотентности (глава 4).

```python
# Spark Structured Streaming: ключ живёт 10 минут
(events.withWatermark("visit_time", "10 minutes")
       .dropDuplicates(["visit_id", "visit_time"]))
```

**Примеры в книге.**

- **Batch.** `dropDuplicates` в Spark принимает список колонок. Без параметра берутся все колонки схемы. Если такой функции нет, используйте оконную функцию с `PARTITION BY` по ключу и фильтром `position = 1`.
- **Streaming.** В Spark та же `dropDuplicates` работает и для потока. Нужна колонка времени (`visit_time`) и `watermark`. У него две роли: граница опоздавших данных (старые записи в pipeline не попадают) и срок хранения ключа. Старые ключи удаляются сами, и состояние долгого job не растёт без границ.

## Опоздавшие данные

Опоздавшие данные звучат безобидно, но сильно влияют на пайплайны. Важно различать два времени:

- `event time`: когда событие произошло.
- `processing time`: когда пайплайн его увидел. Оно никогда не опаздывает.

### `Late Data Detector`

Обнаружение нужно, чтобы дополнять закрытые партиции и контролировать состояние в stateful job.

**Проблема.** События посещений обычно приходят в течение 15 секунд. Но пользователь иногда теряет сеть, клиент копит события и отправляет их после восстановления. Job должен находить поздние события и применять к ним свою стратегию, например игнорировать.

**Как работает:**

- Нужен атрибут времени события. Без него события нельзя разделить на опоздавшие и вовремя.
- Для каждой партиции отслеживайте прогресс по `event time`. Используйте `MAX`: значение должно только расти. `MIN` здесь приведёт к `stuck in the past`: job может никогда не сдвинуться вперёд.
- Для всех партиций вместе выберите стратегию:
  - `MIN`: ждём самую медленную партицию. Меньше потерь, больше буфер.
  - `MAX`: идём за самой быстрой. Меньше буфер, больше пропусков.
  - Комбинация: например, `MAX` внутри источника и `MIN` между источниками.
- У продюсеров бывают потеря связи и медленная сеть, поэтому добавляют `allowed lateness`. Вычислите `watermark = MAX(event time) - allowed lateness`. Событие раньше `watermark` считается опоздавшим.
- Новый кандидат в `watermark` меньше текущего игнорируйте. Watermark не идёт назад.

Опоздавшее событие можно проигнорировать. Если оно ценно, его добавляют паттерном `Late Data Integrator`.

Пример: допустимое опоздание 30 минут. Пришли события 10:00, 10:05, 10:06. Watermark станет 9:36. Затем пришло 9:20 и 9:31. Они раньше 9:36, значит это опоздавшие.

**Компромиссы:**

- **Захват опоздавших.** Spark Structured Streaming сам обнаруживает и игнорирует опоздавшие события, но почти не даёт API, чтобы их собрать. Flink гибче: функция обработки видит текущий watermark и может отправить запись в side output.
- **`MIN` и stateful job.** Такой job копит состояние и выдаёт его, когда watermark его перешёл. При `MIN` возможен цикл «закрыл, открыл, закрыл»: watermark ушёл на 10:30, вы выдали состояния, а поздние записи сдвинули его на 9:00, и их надо открывать снова. Хуже `stuck in the past`: если поздние данные идут снова и снова, watermark не сдвинется, а состояние растёт.
- **`MAX` и перекос.** Если 4 из 5 источников опоздали на 40 минут, их записи считаются поздними, и потребитель их потеряет. Серебряной пули нет. Помогают мониторинг и повторная загрузка опоздавших.

**Примеры в книге.**

- **Spark Structured Streaming.** `withWatermark` принимает колонку времени и допустимое опоздание (в примере час). Если watermark уже 02:15, событие 01:50 игнорируется. Окна на три часа ждут в `state store` и выдаются после записи 04:31, когда watermark впервые сдвигается.
- **Flink.** Нужны извлекатель времени события и функция обработки. Она сравнивает время события с текущим watermark и пишет запись в разные приёмники. В примере допускается отставание до пяти секунд, а опоздавшие уходят в side output.

### `Static Late Data Integrator`

Поздние данные можно игнорировать, и тогда `backfill` не нужен. Но если их много, терять их нельзя. Интернет-магазин не захочет потерять половину заказов.

**Проблема.** Ежедневный job считает статистику по сайтам, которые ссылаются на ваши посты. Результаты приблизительные 15 дней. Записи старше пропускаются. Job обрабатывает только текущий день и теряет опоздавшие записи. Хочется включить их без 15 отдельных запусков.

**Как работает:**

- Задайте статическое окно `lookback` (например, 14 дней). Каждый запуск пересчитывает текущий день плюс все дни в окне. Окно статическое: поздние данные старше него игнорируются.
- Поместите интеграцию в основной pipeline. Для stateful pipeline, где результат зависит от прошлых запусков, сначала идут поздние данные, потом текущий день: нужна корректная история. Для stateless подходит любой порядок, в том числе параллельно.
- В Airflow удобно использовать Dynamic Task Mapping: задачи по дням создаются через `expand`.

> **Просто для вас, но не для других.** Проще всего партиционировать по `processing time`. Но если где-то в системе важен `event time`, вы лишь переносите проблему. Если в вашей партиции на 9 часов 80% данных за 9 часов, 10% за 8 и 10% за 7, потребитель с партициями по `event time` получит поздние данные.

**Компромиссы:**

- **Snowball backfilling.** Потребители тоже пересчитают те же партиции, и их потребители тоже. Остаётся уведомить прямых потребителей о каждом `backfill`.
- **Перекрытие запусков.** При окне 4 дня запуски 10, 11 и 12 октября пересчитывают одни и те же дни. Перезапускайте только последний запуск.
- **Триггер.** Backfill-задачи должны быть внутри основного pipeline. Отдельный pipeline на каждую партицию даёт те же перекрытия.
- **Лишние ресурсы.** В окне может не быть поздних данных. Добавьте контрольную задачу или возьмите `Dynamic Late Data Integrator`.
- **Время.** Нужны партиции по времени: их границы служат отметками, с которыми сравнивают записи.

**Пример.** Airflow с Dynamic Task Mapping. Время запуска меняется, поэтому задачи интеграции создаются на каждый день окна. Pipeline копирует файлы: сначала файл за текущий день, потом `backfill` двух предыдущих дат (размер окна вычитается из даты запуска).

### `Dynamic Late Data Integrator`

Статическое окно не всегда подходит. Иногда нужно загружать только партиции, затронутые поздними данными.

**Проблема.** Окна в 15 дней мало. Владелец продукта хочет обогащать статистику всеми поздними данными, в том числе старше 15 дней. Нельзя пересчитывать вслепую две последние недели.

**Как работает:**

- Заведите state table: партиция, `last processed time`, `last update time`, флаг `is_processed`.
- Партиция требует backfill, если `last update time > last processed time` и она старше текущей.
- Запрос запускают после успешной обработки. Затем обновляют `last processed time`.
- `last update time` берите у хранилища. В BigQuery это `INFORMATION_SCHEMA.PARTITIONS`, в Iceberg колонка `last_updated_at` в метаданных партиций. Для Delta Lake считайте по версиям таблицы через `DeltaLog`.
- Если можно выделить затронутые сущности, перезаписывайте не всю партицию, а только их часть. Это экономит ресурсы, но реализовать сложнее.

```sql
SELECT partition
FROM state_table
WHERE last_update_time > last_processed_time
  AND partition < current_partition
  AND is_processed = false;
```

**Компромиссы:**

- **Concurrency.** При параллельных запусках одна партиция может попасть на `backfill` дважды. Нужен флаг `is_processed` в запросе. Первая задача pipeline помечает текущую партицию. Задача выбора партиций помечает выбранные обработанными. Задача, которая обновляет `last processed time`, снова ставит `false`, чтобы партицию можно было переиграть. Ключевые задачи получают `depends_on_past=True` в Airflow. Если задача выбора упадёт, будущие запуски не стартуют, и нужно ручное вмешательство.
- **Очень старые данные в stateful pipeline.** Допустим, последний запуск был 2024-10-20 (с `Incremental Sessionizer`), а на следующий день пришли данные за 2024-09-21. Придётся пересчитать все запуски за этот период. Поэтому даже у динамического окна нужен максимальный допустимый возраст.
- **Сложность.** Нужно строить `backfill` pipeline динамически. Время изменения партиции не всегда легко получить.

**Пример.** Airflow с Dynamic Task Mapping. В Delta Lake времени обновления партиции нет, но `DeltaLog.getChanges` возвращает созданные и удалённые файлы с указанной версии. По ним находят последнюю версию каждой партиции. Дальше job пишет список партиций на `backfill` в файл с временной меткой, чтобы избежать гонок при параллельных запусках.

## Фильтрация

### `Filter Interceptor`

Ошибка не всегда техническая. Бывают и человеческие, например неверный фильтр, из-за которого пользователям отдают неполные данные.

**Проблема.** После релиза доля отфильтрованных строк выросла с 15% до 90%. Это изменились данные или регрессия в коде? План выполнения не поможет: движок объединяет условия фильтра в одно.

**Как работает:**

- В коде с API (Scala, PySpark) оберните каждое условие фильтра. При `false` увеличивайте счётчик (в Spark это accumulator).
- В конце job соберите значения счётчиков.
- В SQL вынесите условия в колонки подзапроса. Для `a IS NOT NULL` и `b != "abc"` это `a_is_not_null` и `b_is_not_abc`. Затем используйте их как предикаты в основном запросе.

> **Оставайтесь прагматичными.** Если программный API лучше подходит, используйте его, даже если вы раньше писали только SQL. Верно и обратное.

**Компромиссы:**

- **Накладные расходы.** Небольшие: счётчики простые, и передавать их по сети недорого. В SQL больше, если нужна временная таблица.
- **Декларативные языки.** Здесь SQL слабее программного API. Код на API проще понять и поддерживать.
- **Streaming.** Stateless job может стать stateful, так как нужно считать фильтры. Нужны границы по времени (окна), иначе статистику нельзя связать с текущим моментом. С окнами видны тренды.

**Примеры в книге.**

- **Spark, API.** Класс `FilterWithAccumulator` объединяет условие и accumulator. Через `mapInPandas` функция проходит по всем фильтрам и увеличивает accumulator при ложной проверке. В конце значения читают из списка.
- **Spark SQL.** Создают таблицу со всеми колонками и псевдонимом на основе `if-elseif-...-else`. По ней считают строки на каждое условие и строят пользовательскую таблицу с валидными записями.

## Отказоустойчивость

### `Checkpointer`

Критичная ошибка особенно опасна в streaming: события идут непрерывно, часто в append-only журнале. В данных нет партиций, по которым можно понять, с чего продолжить, поэтому job нельзя перезапустить как batch.

**Проблема.** Streaming job считает уникальные визиты в 10-минутных окнах. Вы боитесь, что сбой заставит читать данные с начала. Нужно сохранять результат по мере работы.

**Как работает:**

- Job сохраняет последнюю прочитанную позицию (offset) и состояние в хранилище надёжнее, чем среда job: она может смениться при перезапуске.
- Два варианта:
  - Через фреймворк: Spark Structured Streaming и Flink пишут метаданные в object store.
  - Через SDK хранилища: Kafka (`__consumer_offsets`), Kinesis KCL (таблица DynamoDB).
- Два способа записи: по конфигурации (частота checkpoint, как в Spark и Flink) или явным вызовом `commit` в вашем коде (как в consumer для Kafka).

```python
# Spark: путь для checkpoint
(stream.writeStream
       .option("checkpointLocation", "/data/checkpoint")
       .start())
```

**Компромиссы:**

- **Гарантия против latency.** Запись позиции дёшева. Но паттерн применяют и к состоянию (например, `Stateful Sessionizer`), а оно намного больше. Частые checkpoint замедляют job. Редкие означают больше повторной работы после сбоя.
- **Ощущение exactly-once.** Это только ощущение. Задачи идут параллельно и асинхронно. Если одна упадёт до checkpoint, после перезапуска успешные записи обработаются снова. Для exactly-once нужны паттерны идемпотентности (глава 4).
- **Режимы доставки.** Checkpoint после обработки даёт `at least once` (возможны дубли). Checkpoint до обработки даёт `at most once` (возможна потеря).

**Примеры в книге.**

- **Spark.** Путь задаёт `checkpointLocation`. Spark пишет обработанные offset в файлы по номеру итерации. Это накладно, зато меньше риск дублей. Асинхронные checkpoint (Spark 3.4.0) на 2024 год экспериментальные и не поддерживают `state store` в open source версии.
- **Flink.** Работает по времени, а не по итерациям. `RETAIN_ON_CANCELLATION` сохраняет файлы после сбоя (по умолчанию Flink удаляет их при перезапуске). Режим `EXACTLY_ONCE` относится к stateful операциям, например оконным счётчикам: каждая запись отражается в состоянии один раз.

## Итоги главы

- Ошибки неизбежны. Паттерны делают так, чтобы pipeline жил с ними.
- `Dead-Letter` сохраняет необработанные записи отдельно. Он требует алерта, иначе скрывает серьёзные сбои.
- Replay из dead-letter запускает цепочку `backfill` у потребителей и может сломать порядок.
- `Windowed Deduplicator` убирает дубли в окне. Он не гарантирует exactly-once.
- `Late Data Detector` считает `watermark` как `MAX(event time)` минус `allowed lateness`. Watermark не идёт назад.
- `Static Late Data Integrator` пересчитывает фиксированное окно, `Dynamic` только затронутые партиции.
- `Filter Interceptor` считает строки, отброшенные каждым условием.
- `Checkpointer` хранит позицию и состояние. Exactly-once даёт только идемпотентность (глава 4).

## Ключевые термины

| Термин | Значение |
|---|---|
| Transient error | Временная ошибка. Проходит сама, помогает retry |
| Nontransient error | Постоянная ошибка. Нужна ручная работа |
| Poison pill message | Запись, которую нельзя обработать. Останавливает job |
| Dead-letter storage | Отдельное хранилище для плохих записей |
| Replay pipeline | Пайплайн, который возвращает записи из dead-letter в поток |
| Snowball backfilling | Backfill одного пайплайна вызывает backfill всех потребителей |
| State store | Хранилище состояния streaming job |
| Event time / processing time | Время события / время обработки |
| Watermark | Граница `event time`. Раньше неё записи считаются опоздавшими |
| Allowed lateness | Допустимое опоздание при расчёте watermark |
| Lookback window | Окно в прошлое, которое пересчитывается при каждом запуске |
| Side output | Дополнительный выход job для особых записей |
| Checkpoint | Сохранённая позиция и состояние job |
| At least once / at most once | Возможны дубли / возможна потеря |

## Что это значит на практике

- Не давайте job падать из-за одной плохой записи. Пишите её в dead-letter и ставьте алерт на объём.
- Если плохих записей много, остановите job. Иначе вы молча потеряете данные.
- Продумайте replay до запуска. Спросите: кто ещё читает эти партиции и сможет ли он пересчитать?
- Дедуплицируйте по ключу и по окну. Но не считайте это exactly-once. Делайте запись идемпотентной.
- Всегда выбирайте `allowed lateness` осознанно. Мониторьте число опоздавших записей.
- В Airflow используйте `expand` для окна lookback. Перезапускайте только последний запуск, а не все.
- Считайте отфильтрованные строки по каждому условию. Это быстро показывает, баг в коде или в данных.
- Всегда включайте checkpoint в streaming. Подберите частоту под допустимую задержку.
