**Главная мысль:** Проверки качества смотрят на сами данные. Этого мало. Нужно ещё видеть, что пайплайн работает вовремя, и знать, откуда пришли данные. Для этого есть два столпа: детекторы (detection) и трекеры (tracking).

## О чём глава

[Глава 9](/book-summaries/engineering/data-engineering-design-patterns/09-data-quality/) защищала сами данные. Но одних проверок качества мало для контроля всего стека. Пример: `AWAP` хорошо ловит плохие данные, но если сам AWAP-job не запустился из-за сбоя выше по потоку, вы об этом не узнаете. Паттерны наблюдаемости закрывают такие дыры мониторингом и alerting. Они опираются на два столпа:

- **Detection.** Детекторы замечают проблемы с данными (`Flow Interruption Detector`, `Skew Detector`) и со временем (`Lag Detector`, `SLA Misses Detector`).
- **Tracking.** Трекеры показывают связи между датасетами, колонками и слоем обработки (`Dataset Tracker`, `Fine-Grained Tracker`).

Автор подчёркивает: наблюдаемость - не только задача операционной команды, она важна и инженерам данных.

## Паттерны главы

| Паттерн | Когда применять |
|---|---|
| `Flow Interruption Detector` | Данные перестали поступать, но job не упал |
| `Skew Detector` | Нужно убедиться, что объём данных не сильно изменился |
| `Lag Detector` | Нужно знать, как сильно consumer отстаёт от producer |
| `SLA Misses Detector` | Job должен завершаться за заданное время |
| `Dataset Tracker` | Нужно знать, какие датасеты и команды связаны между собой |
| `Fine-Grained Tracker` | Нужно знать происхождение отдельных колонок и строк |

## Детекторы данных (Data Detectors)

Первая категория смотрит на состояние данных: есть ли они и сколько их. Самая серьёзная проблема здесь - недоступность датасета. Без данных не запустится job, и вся цепочка потребителей останется без данных.

### Flow Interruption Detector

**Проблема.** Streaming job синхронизирует данные в object store. Этот датасет - источник для многих batch job разных команд. Семь месяцев всё работало. Потом job начал читать записи, но не писать их. Он не упал, поэтому никто не заметил. Заметили потребители, когда пожаловались на отсутствие данных. Узнавать об этом от потребителей плохо для репутации, поэтому нужен собственный механизм наблюдения.

**Как работает:**

- Для непрерывного потока (continuous delivery) ждём хотя бы одну запись за единицу времени. Если за минуту записей нет, шлём alert.
- Для нерегулярного потока (irregular delivery) смотрим на окно. Alert идёт, если пауза длиннее допустимого окна. Так меньше ложных срабатываний и меньше alarm fatigue.
- Для batch и таблиц смотрим на свежесть. Есть три слоя:
  - metadata: время последнего изменения. Для часовой загрузки alert идёт, если изменений нет больше часа. Это дешевле всего.
  - data: если metadata нет, добавляем колонку с временем изменения. Если нельзя, сравниваем число строк по периодам (не изменилось два часа подряд - сигнал). Нужно хранить статистику прошлых запусков.
  - storage: время записи последнего файла. Подходит для любого формата.

**Примеры.** Kafka, Prometheus и Grafana: считаем сообщения в минуту и шлём alert, когда последние значения (в примере пять) равны нулю. Alert настраивают в интерфейсе Grafana, а не в коде.

```text
sum without(instance)(rate(
  kafka_server_brokertopicmetrics_messagesin_total{topic="visits"}[1m]))
```

Для batch в PostgreSQL можно включить `track_commit_timestamp` и читать время последнего commit через `pg_xact_commit_timestamp`. Alert срабатывает, если разница с текущим временем больше порога. Producer тоже может сам отправить метрику «время последней записи»: так делает job, который синхронизирует Kafka с Delta Lake и шлёт метрику в Prometheus.

**Минусы:**

- Трудно выбрать порог. Одна запись в минуту может быть слишком мало или слишком много. Порог по истории даёт ложные срабатывания при пиках, например при маркетинговой акции.
- Metadata может быть недоступна. Также время изменения меняется при смене схемы, хотя новых данных нет.
- На уровне storage `compaction` создаёт новые файлы, но данные не новые. Это ложный сигнал активности.

### Skew Detector

**Проблема.** После `Flow Interruption Detector` потребители снова недовольны: batch job обработал неполный датасет. Job сработал правильно, но у поставщика был сбой при генерации, и данных пришло вдвое меньше. Нужно всегда обрабатывать полный датасет.

**Как работает:**

- Skew здесь значит, что в двух запусках подряд объём данных разный.
- Выберите окно сравнения. Например, сегодня против вчера.
- Задайте допуск (tolerance). Например, плюс-минус 50% объёма. Допуск берут из истории или спрашивают у бизнеса.
- Посчитайте перекос. Первый способ: разница в процентах между окнами. Второй способ: отношение стандартного отклонения к среднему, `STDDEV(x) / AVG(x)`. Он подходит для партиций, например в Kafka или PostgreSQL.

Пример для партиций таблицы PostgreSQL. Имена таблиц выдуманы.

```sql
SELECT STDDEV(n_live_tup) / AVG(n_live_tup) * 100 AS skew_pct
FROM pg_catalog.pg_stat_user_tables
WHERE relname LIKE 'visits_part_%';
```

Паттерн удобно ставить в первый audit-шаг `AWAP`. Он остановит обработку неполного датасета.

**Минусы:**

- **Seasonality.** Рекламная кампания или лето и зима меняют объём. Одно правило для всех периодов не работает. Правило строят на знании бизнеса и добавляют исключения для самых изменчивых периодов.
- **Communication.** Ложные срабатывания остаются, например при успешной кампании. Здесь нужны коммуникационные навыки: синхронизироваться с отделами и менять alert на нужные периоды.
- Fatality loop. Если вчерашний датасет был неполным и в три раза меньше, сегодняшний полный датасет выглядит как перекос. Решение: чинить данные у поставщика. Или сравнивать с последним успешным запуском, а не со вчерашним.

**Примеры.** Для партиционированных таблиц PostgreSQL запрос берёт число строк из `pg_stat_user_tables`. Когда отношение достигает порога, это перекос хранилища. `STDDEV` и `AVG` есть и в Prometheus: так считают перекос в Kafka. Для window-to-window в Airflow sensor ждёт новую партицию, `compare_volumes` проверяет, что она не меньше и не больше предыдущей чем на 50%, и только потом идёт загрузка в PostgreSQL.

## Детекторы времени (Time Detectors)

Вторая категория смотрит на время и помогает найти проблемы задержки в слое обработки.

### Lag Detector

Lag показывает, насколько consumer отстаёт от producer. Часто это сигнал будущих проблем со свежестью и доступностью данных.

**Проблема.** Неделю назад streaming job получил на 30% больше данных, чем раньше. Вы пропустили письмо об этом, и теперь потребитель жалуется на медленную доставку. Вы пообещали, что это в последний раз. Чтобы решить проблему с масштабированием, сначала нужно измерять, как быстро consumer читает.

**Как работает:**

- Выберите единицу lag. Для Kafka это offset или время записи. Для Delta Lake это номер версии (commit). Для таблицы с партициями по времени это timestamp партиции.
- Посчитайте разницу: `lag = last_available_unit - last_processed_unit`.
- Для партиционированных источников агрегируйте lag по партициям. `MAX` покажет худший случай. Перцентили (`P90`, `P95`) покажут, как живёт большинство партиций. Лучше использовать оба.

**Ловушка среднего.** Допустим, lag по семи партициям равен 10, 5, 30, 2, 3, 5 и 3 секунды. Среднее равно 8 секундам. Но `P90` равен 18 секундам. По среднему кажется, что всё хорошо, хотя это не так.

**Минус:** data skew. Если одна партиция получает больше нагрузки, `MAX` будет плохим. Но это не значит, что consumer плохой. Лучше исправить распределение данных.

Как собрать метрику:

- Spark Structured Streaming: listener срабатывает после каждого окна записей. `StreamingQueryListener` в `onQueryProgress` читает offsets, сравнивает их с последними в каждой partition, считает lag и отправляет в Prometheus через Pushgateway.
- Delta Lake: job идёт по расписанию с триггером `availableNow`: обрабатывает всё доступное и останавливается. Так можно использовать checkpoint Spark и не вести прогресс вручную. Последнюю прочитанную версию берут из прогресса запроса и шлют в мониторинг.
- Последнюю записанную версию должен сообщить producer: после записи данных он выполняет `DESCRIBE HISTORY`.
- Alert настройте на разницу между записанной и прочитанной версиями.

### SLA Misses Detector

`Lag Detector` измеряет скорость consumer, но это не единственная мера времени. Его дополняет SLA, который прямо проверяет время выполнения.

**Проблема.** Batch job стартует в 6:00 и должен закончиться за 40 минут. Потребители - критичные пайплайны, которые должны построить бизнес-статистику до 8:00. Вы оптимизировали job под SLA, но знаете, что бывает непредвиденное. Нужно уведомлять себя и потребителей сразу, когда job идёт дольше 40 минут.

**Как работает:**

- Batch: время окончания минус время старта. Если разница больше порога, это SLA miss и нужен alert.
- Streaming с microbatch или окнами: тот же расчёт на каждую итерацию.
- Streaming без окон: для каждой записи считаем разницу между временем чтения и временем записи в выход. Потом агрегируем через `MAX` или перцентиль. Метрики можно собирать через `Online Observer` или `Offline Observer` из главы 9.

**Lag и SLA не взаимозаменяемы.** Пример: consumer ограничен по throughput и всегда обрабатывает одинаковый объём. SLA соблюдается, но lag растёт. Обратный пример: у batch job нет lag на старте, но он может долго работать и нарушить SLA.

**Минусы:**

- В batch всё просто. В streaming труднее из-за семантики прихода данных.
- Late data и event time. SLA по processing time показывает скорость вашего job. SLA по event time включает задержку поставщика, например при потере сети. Эти два SLA лучше разделять и мерить оба.
- Processing time проще, но не единственный. Event time показывает сквозное время от создания данных. Если producer потерял сеть и доставил буфер позже, SLA по event time нарушен не по вашей вине, а SLA по processing time может соблюдаться. Поэтому processing time считают как разницу между чтением и записью записи, а event time - между временем создания и записи.

**Примеры.** В Airflow у задачи есть параметр `sla`, например 10 секунд. В версии 2.10.2 SLA считается от старта запуска пайплайна, а не от старта задачи. Если запуск назначен на 08:00 и задача стартует позже 08:00:10, она уже опоздала. Автор отмечает в сноске, что рефакторинг SLA запланирован в Airflow 3.1.

> **Пояснение:** это наше дополнение, его нет в книге. В Airflow 3 параметр `sla` убрали, а в Airflow 3.1 появились Deadline Alerts. Проверьте это по документации своей версии Airflow.

В streaming книга показывает два job на Flink. Первый пишет в Kafka запись с атрибутом `start_processing_time_unix_ms`. Второй читает его вместе со временем записи в выходной топик, считает разницу и выдаёт перцентили по окнам в одну минуту. Их отправляют в мониторинг для alert по SLA.

## Data Lineage

До сих пор мы наблюдали за данными, которые вы обрабатываете. Что делать, если проблема не у вас? Например, поздние события сломали SLA по event time. Тогда нужно знать, к кому идти за помощью. Для этого строят «семейное дерево» датасетов: кто из чего сделан. Lineage работает на уровне датасетов и на уровне записей.

### Dataset Tracker

Паттерн работает с контейнерами данных: таблицами, папками, топиками, очередями. Он строит дерево зависимостей между ними и показывает поставщиков и потребителей.

**Проблема.** Вы потребляете датасет плохого качества: batch job регулярно падает из-за несогласованной схемы. Оказалось, что тип одного поля менялся со временем. Ваш поставщик об этом не знает: он сам обрабатывает данные другой команды. Нужно понять цепочку зависимостей и найти, какая команда внесла ошибку.

**Как работает:**

- Строим граф зависимостей, где у каждого узла есть команда-владелец. Пример: датасет заказов собран из двух таблиц, которые в свою очередь построены на топике Kafka.
- Вариант 1, управляемый сервис. Он анализирует зависимости между job, таблицами и дашбордами. Примеры: Unity Catalog в Databricks и Dataplex в GCP (для BigQuery и Dataproc).
- Вариант 2, свой lineage. Сначала определяют входы и выходы каждого запроса, задачи или пайплайна на двух уровнях:
  - оркестратор: каждый пайплайн сообщает входы и выходы во внешний lineage-сервис. Часть инструментов, как Airflow с OpenLineage, находит зависимости сам.
  - база: lineage-job разбирает выполненные запросы. Например, `SELECT ... FROM orders o JOIN users u ...` превращается в дерево, из которого берут все таблицы.
- Затем нужен слой, который интерпретирует зависимости и рисует их. Это гибко, но требует больше усилий.

**Минусы:**

- **Vendor lock.** Управляемые решения часто работают только в границах своего сервиса. Например, Dataplex не видит загрузку через BigQuery Data Transfer Service. Данные в чужом облаке видны частично.
- **Custom work.** Оркестратор выводит входы и выходы из конфигурации только для встроенных операторов. Для своих типов задач логику нужно писать самим.

**Примеры.** Автор берёт OpenLineage API и Marquez UI: оба открытые. Для Airflow задайте `OPENLINEAGE_URL` и установите пакет `apache-airflow-providers-openlineage`. Для многих операторов (например, `PostgresOperator`) extractors OpenLineage делают всё сами. Для Spark подключите зависимости OpenLineage при создании `SparkSession`.

### Fine-Grained Tracker

**Проблема.** Вы применили `Denormalizer`, и таблица за три года выросла до 30+ колонок. Команда часто меняется, и новые коллеги спрашивают о зависимостях таблицы. `Dataset Tracker` отвечает на большинство вопросов, но не на один: из каких колонок исходных таблиц собрана каждая колонка вашей таблицы.

**Как работает:**

- Column-level lineage. Некоторые платформы дают его из коробки: `system.access.column_lineage` в Databricks, Purview в Azure. Свой вариант: разбор плана выполнения запроса и поиск всех входных колонок для каждой выходной.
- Row-level lineage. Нужно знать, какой job создал строку. Добавляем эту информацию дополнительным атрибутом или колонкой, например паттернами декорирования данных. Это делают через колонку или заголовки (headers) сообщения Kafka.

Пример для `CONCAT(u.first_name, d.delivery_address)`. Выходная колонка зависит от `users.first_name` и `addresses.delivery_address`. Для Spark у популярных инструментов (OpenLineage) есть встроенная поддержка.

**Минусы:**

- Custom code. Если трансформация идёт через свою функцию, lineage-инструмент видит чёрный ящик и не поймёт логику.
- Row-level lineage не интегрируется с обычными инструментами визуализации. Нужен свой слой запросов.
- Evolution. Логика колонок меняется. Инструмент должен хранить историю, иначе вы получите неверное происхождение колонки.

**Примеры.** Column-level lineage для Spark и OpenLineage использует тот же код `SparkSession`, что и `Dataset Tracker`. Row-level интереснее. Два job (`visits_decorator_job` и `visits_reducer_job`) пишут в заголовок записи Kafka атрибуты `job_version`, `job_name` и `batch_version`. У второго job есть ещё `parent_lineage` с данными первого. По ним проще понять цепочку и обсудить отладку с производителями данных.

## Итоги главы

- Паттерны наблюдаемости закрывают дыры проверок качества: сбой выше по потоку, неполные данные, задержки.
- `Flow Interruption Detector` ловит остановку потока: для непрерывной доставки ждёт запись за единицу времени, для нерегулярной смотрит на окно, для batch проверяет свежесть.
- `Skew Detector` сравнивает объём окон или partition с допуском. Риски: сезонность, ложные срабатывания и `fatality loop`.
- `Lag Detector` измеряет отставание consumer. Для partition берут `MAX` и перцентили, а не среднее.
- `SLA Misses Detector` сравнивает время выполнения с лимитом. Processing time и event time нужно мерить отдельно.
- `Dataset Tracker` строит граф происхождения датасетов и команд, `Fine-Grained Tracker` показывает происхождение колонок и строк.

## Ключевые термины

| Термин | Значение |
|---|---|
| `Observability` | Видимость состояния данных и пайплайнов: мониторинг и alerting |
| `Alarm fatigue` | Усталость от слишком частых и ложных alert |
| `Data skew` | Неравномерный объём данных между партициями или запусками |
| `Lag` | Отставание consumer от последней доступной записи |
| `SLA` | Максимальное допустимое время выполнения job |
| `Data lineage` | Происхождение данных и связи между датасетами |
| `OpenLineage` | Открытый стандарт и API для сбора lineage |
| `Fatality loop` | Один плохой запуск ломает сравнение для следующих |

## Что это значит на практике

- Добавьте alert на отсутствие новых данных. Job без ошибок не значит, что данные доходят.
- Используйте `P90`, `P95` и `MAX`, а не среднее. Среднее прячет проблемные партиции.
- Сравнивайте объём данных с допуском и учитывайте сезонность. Договоритесь с бизнесом о ложных срабатываниях.
- Ставьте `Skew Detector` в первый audit-шаг `AWAP` и в проверки `dbt`-пайплайна перед публикацией.
- Измеряйте SLA отдельно по processing time и по event time. Так вы поймёте, чья это проблема.
- Подключите OpenLineage к Airflow и Spark. Lineage быстрее покажет, к какой команде идти при инциденте.
- Для критичных датасетов храните в записях версию job и имя job. Это помогает при отладке.

## Вопросы для самопроверки
