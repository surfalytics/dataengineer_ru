**Главная мысль:** Пайплайн идемпотентен, если сколько раз его ни запускай, результат один и тот же. Retry и backfill тогда не создают дубликаты. Для этого есть четыре семейства паттернов: перезапись, обновление, опора на базу данных и неизменяемый набор данных.

## О чём глава

Глава отвечает на вопрос: как сделать так, чтобы повторный запуск не портил данные. [Предыдущая глава](/book-summaries/engineering/data-engineering-design-patterns/03-error-management/) закрывает большинство проблем, но не все. Автоматический retry удобен для инженера, но опасен для данных. Повторная задача может заново выполнить успешную запись. В лучшем случае получатся дубликаты, и потребитель их уберёт. В худшем их нельзя убрать, потому что непонятно, что это одни и те же данные.

Идемпотентность решает это. Пример: `abs(-1) == abs(abs(abs(-1)))`. Сколько раз ни вызывай функцию, ответ тот же. Для job это значит: результат одинаков при любом числе запусков, без дубликатов или с дубликатами, которые легко опознать. Брокер без транзакций при retry всё равно может записать сообщение дважды, но идемпотентная обработка поможет потребителям опознать такие записи.

Главные темы: перезапись, обновление, опора на базу данных и неизменяемый набор. Автор отмечает Максима Бошемена: он сделал идемпотентность популярной в 2018 году статьёй о functional data engineering.

## Все паттерны главы

| Семейство | Паттерн | Когда применять |
|---|---|---|
| Overwriting | `Fast Metadata Cleaner` | Нужно быстро очистить большую таблицу, и БД умеет `TRUNCATE` или `DROP` |
| Overwriting | `Data Overwrite` | Метаданных нет (например, object store), но можно заменить данные |
| Updates | `Merger` | Приходит только часть данных (изменения), записи имеют стабильный ключ |
| Updates | `Stateful Merger` | Нужен безопасный backfill для `Merger` |
| Database | `Keyed Idempotency` | Стриминг или key-value база, ключ можно построить из неизменяемых полей |
| Database | `Transactional Writer` | Потребители не должны видеть частичную запись |
| Immutable dataset | `Proxy` | Данные нельзя менять или удалять, а читать нужно одну актуальную версию |

## Overwriting: перезапись данных

Самый простой путь к идемпотентности: удалить старые данные и записать новые. Проблема в стоимости. На больших таблицах `DELETE` медленный. Поэтому есть два паттерна: через метаданные и через данные.

### Fast Metadata Cleaner

Операции с метаданными работают на логическом уровне, а не на физическом: они не трогают файлы с данными. Поэтому они самые быстрые.

**Проблема.** Ежедневный job обрабатывает от 500 ГБ до 1,5 ТБ событий. Для идемпотентности он сначала делает `DELETE` строк прошлого запуска, потом `INSERT`. Три недели всё работало, потом таблица сильно выросла, и `DELETE` стал тормозить.

**Как работает:**

- `DELETE` сначала находит строки, потом переписывает все затронутые файлы. `TRUNCATE` и `DROP TABLE` работают только с метаданными. Поэтому они быстрые. `TRUNCATE TABLE` по смыслу равен `DELETE FROM` без условия, но не сканирует таблицу.
- Нужно изменить взгляд на набор: он состоит из нескольких физических таблиц, которые вместе дают одно целое. Например, 52 недельные таблицы дают годовой набор, и сверху `view` их объединяет.
- Размер таблицы это `idempotency granularity` (в примере неделя): единица, которую можно очистить и перезапустить.
- Оркестратор делает три шага. Первый: проверить дату и выбрать ветку (например, паттерном `Exclusive Choice`). В понедельник идёт инициализация, в другие дни сразу загрузка. Второй: создать среду идемпотентности через `TRUNCATE` или `DROP` (после `DROP` таблицу создают заново). Третий: обновить `view`.
- Для `DROP` порядок такой: убрать таблицу из `view`, удалить, создать заново, вернуть в `view`. Иначе читатель увидит ошибку.
- Для полных наборов поток проще: таблицу пересоздают при каждой загрузке.

**Компромиссы:**

- **Гранулярность идемпотентности.** Она же граница `backfill`. Повторять нужно с задачи, которая создаёт таблицу. Иначе набор станет несогласованным. Если таблица недельная, `backfill` одного дня требует перезапуска всей недели. Для остальных дней можно перезапустить только шаг загрузки.
- **Точечный backfill** (один клиент, один поставщик) не работает. Метаданные относятся к таблице целиком.
- **Лимиты хранилища.** У BigQuery и Redshift есть лимит на число партиций и таблиц. Помогает шаг `freezing`: недельные таблицы позже склеивают в месячные или годовые.
- **Нужна поддержка в БД.** Паттерн работает в хранилищах, lakehouse и реляционных БД. В object store его трудно сделать, там берут `Data Overwrite`.
- **Нужен единый вход** (`view`), чтобы пользователи не знали о внутренних таблицах и читали данные из одной точки.
- **Schema evolution.** Новое необязательное поле надо добавлять в старые таблицы отдельным пайплайном. Через сам паттерн это означало бы пересчёт данных, а это хуже. Если поле обязательное, его можно включить в паттерн: повтор прошлых запусков добавит поле.

**Пример.** Airflow и PostgreSQL. `BranchPythonOperator` проверяет дату и ведёт либо к загрузке, либо к созданию недельной таблицы с номером недели из контекста Airflow. Затем свой оператор обновляет `view` новой таблицей. Загрузка в недельную таблицу общая для обеих веток.

### Data Overwrite

Если метаданных нет (например, в object store нет `TRUNCATE` и `DROP`), остаётся операция над данными.

**Проблема.** Ежедневный job работает с посещениями в object store, партиции по event time. Стратегии идемпотентности нет: каждый backfill создаёт дубликаты. `Fast Metadata Cleaner` не подходит, потому что нет слоя метаданных.

**Как работает.** Паттерн заменяет сами данные. Способы зависят от стека:

- **Framework:** режим записи в Spark (`save mode`) или Flink (`write mode`) настраивают один раз, и фреймворк сам чистит существующие файлы перед записью. Если хранилище позволяет условия, перезапись можно сделать выборочной. Так в Delta Lake через `replaceWhere` заменяют только часть данных.
- **SQL, вариант 1:** `DELETE` и затем `INSERT`. Он позволяет выбрать строки.
- **SQL, вариант 2:** `INSERT OVERWRITE`. Он короче, но заменяет всю таблицу или партицию без выбора строк. Его поддерживают, например, Databricks и Snowflake.
- **Команды загрузки:** `LOAD DATA OVERWRITE` в BigQuery или флаг `--replace=true` (это сокращение для `WRITE_TRUNCATE`). В других системах перед загрузкой делают `TRUNCATE`.

> **Не только список колонок.** `INSERT` не требует явных значений. Можно вставить строки из другого запроса: `INSERT INTO visits (id, v_time) SELECT visit_id, visit_time FROM visits_raw`.

```sql
-- Заменяем содержимое таблицы новой версией (пример с выдуманными таблицами)
INSERT OVERWRITE INTO orders
SELECT * FROM orders_staging WHERE status = 'valid';
```

**Компромиссы:**

- **Объём данных.** Без партиционирования перезапись замедляется с ростом таблицы. Помогают партиции и другие приёмы хранения (глава 8).
- **Нужен `vacuum`.** `DELETE` может не стереть данные физически. В table formats, BigQuery и Snowflake старые блоки остаются из-за time travel. Они удаляются после retention или после `vacuum`.
- **Режим `overwrite` в Spark не транзакционный.** Всё зависит от формата. В Delta Lake удаление это новый commit, файлы остаются на месте.

**Примеры.** `INSERT OVERWRITE` очищает таблицу или партиции перед вставкой, и запрос можно усложнить джойнами или агрегациями. В BigQuery за это отвечает `writeDisposition` в задаче загрузки, флаг `--replace=true` стирает данные перед записью CSV. Spark в режиме `overwrite` ведёт себя так же: сначала сносит данные.

## Updates: обновление данных

Полная замена не подходит, если поставщик присылает только изменённые строки. Тогда новые строки нужно объединить со старыми.

### Merger

Паттерн подходит, когда идентичность строк неизменна и набор принимает только вставки и обновления. Но на практике есть нюансы.

**Проблема.** Поток изменений из Kafka (через `Change Data Capture`) нужно перенести в таблицу Delta Lake batch-пайплайном. Таблица должна отражать данные источника на любой момент, без дубликатов.

**Как работает:**

- Сначала определяют ключ слияния. Это одно поле (`user_id`) или несколько (`visit_id` и `visit_time`).
- Используют команду `MERGE` (она же `UPSERT`). Её поддерживают движки, table formats и хранилища.
- Три случая: нет в таблице, значит `INSERT`. Есть в таблице, значит `UPDATE` (вероятно, пришла свежая версия). Удаление.
- `MERGE` не умеет удалять то, чего нет во входе. Поэтому удаления передают как `soft delete`: поле `is_deleted = true`.
- В ветке `INSERT` тоже проверяют `is_deleted = false`. Иначе при первом запуске удалённая запись попадёт в таблицу и там останется.

> **Проще перезаписать.** Если провайдер присылает полный набор, перезапись проще: паттерн `Merger` нужен для инкрементов, которые нельзя заменить целиком.

```sql
MERGE INTO customers AS t
USING customers_input AS i ON t.customer_id = i.customer_id
WHEN MATCHED AND i.is_deleted THEN DELETE
WHEN MATCHED THEN UPDATE SET name = i.name
WHEN NOT MATCHED AND NOT i.is_deleted THEN
  INSERT (customer_id, name) VALUES (i.customer_id, i.name);
```

**Компромиссы:**

- **Уникальность.** Нужен неизменяемый ключ. Без него `MERGE` вставит новую строку вместо обновления.
- **I/O.** `MERGE` работает с данными, а не с метаданными, поэтому он дороже. Современные движки сначала ищут нужные файлы по метаданным и пропускают лишние.
- **Backfill ломает консистентность.** Допустим, нужно переиграть пайплайн с 08:00. Набор инкрементальный, поэтому `backfill` стартует с самой свежей версии таблицы. Часть строк в ней отсутствует в кусках, записанных после 08:00. Пока `backfill` идёт, потребители видят не те данные, что при обычном запуске. Смягчить можно восстановлением таблицы к первому переигрываемому запуску вне пайплайна (time travel). Но тогда `Merger` из stateless становится stateful.
- Если поставщик допустил ошибки, replay не нужен. Попросите набор с исправлениями и примените его как новый инкремент. `MERGE` проставит верные значения, если идентичность строк не изменилась.

**Пример.** Airflow и один SQL-запрос, который грузит новые устройства. Сначала файл попадает во временную таблицу, она исчезает в конце транзакции. Таблицу создают через `LIKE`, чтобы не повторять атрибуты целевой таблицы и не получить рассинхронизацию схем. Затем идёт `MERGE`: `WHEN NOT MATCHED THEN INSERT` для новых строк и `WHEN MATCHED THEN` для обновлений. Удалений в примере нет, файл инкрементальный.

### Stateful Merger

**Проблема.** Вы синхронизируете две таблицы Delta Lake паттерном `Merger`. Через неделю нашли ошибку в объединённых данных, и бизнес просит `backfill`. Согласованность важна, поэтому нужно сначала восстановить таблицу к последней корректной версии. `Merger` на это не рассчитан.

**Как работает.** К пайплайну добавляют таблицу состояния (`state table`) и два шага:

- В начале: восстановить таблицу, если нужно.
- В конце: записать в `state table` пару "время запуска и версия таблицы после `MERGE`".
- Как понять режим. Берут версию, созданную прошлым запуском, и сравнивают с текущей версией таблицы. Равны: обычный запуск. Отличаются: backfill, нужен откат к версии прошлого запуска.
- Если версии для прошлого запуска нет, это первый запуск (или `backfill` первого запуска). Таблицу очищают `TRUNCATE` и идут к `MERGE`.
- Оркестратор часто сам знает, что идёт backfill. Тогда сравнение версий не нужно.
- Пример: запуск в 09:00 создал версию 5, запуск в 10:00 версию 6. Запуск в 11:00 видит версию 6 и у себя, и у предыдущего запуска. Это обычный запуск. Повтор запуска 09:00 видит разницу (4 против 6) и сначала восстанавливает таблицу.
- Пример с датами: повтор 2024-10-05 не находит версии для 2024-10-04 и очищает таблицу. Повтор 2024-10-07 видит, что версия запуска 2024-10-06 отличается от текущей, и откатывает таблицу. Потом оркестратор повторяет 2024-10-08, и там версии уже совпадают, поэтому он идёт как обычный запуск.

**Компромиссы:**

- **Нужна версионность.** Каждая запись создаёт новую версию таблицы. Table formats (Delta Lake, Iceberg) её дают. Без них хранят все сырые данные в отдельной таблице с колонкой времени запуска. Проверка на `backfill` ищет в ней записи с будущим временем запуска. Если есть, удаляют строки с `execution_time >= время запуска`, и в сырой таблице остаётся последняя корректная версия. Затем таблицу пересобирают из неё (например, паттерном `Windowed Deduplicator`), грузят вход текущего запуска и делают `MERGE`.
- **`vacuum` и retention.** Через заданный срок файлы удаляются, и старые версии пропадают. Можно увеличить retention, но вырастет цена хранения. Либо принять, что `backfill` за пределами retention невозможен.
- **Операции без изменения данных.** `Compaction` не меняет данные, но создаёт новую версию. Если брать просто «прошлую версию», можно потерять операции между двумя `MERGE`. Тогда берут версию текущего запуска и вычитают 1 (версии растут на единицу). Пример: для запуска 2024-10-07 версия 9, откатываем к 8. Это уплотнённая таблица между запусками 07 и 08.

**Пример.** Delta Lake и Airflow. State table из двух полей: время запуска и версия таблицы. Задача восстановления читает последнюю версию и версию прошлого запуска, сравнивает их и делает `TRUNCATE` или откат. Затем идёт `MERGE`, а после него версия пишется в state table.

## Database: идемпотентность силами БД

Если оркестрации мало или её нет (например, стриминг), часть работы делает база данных.

### Keyed Idempotency

Паттерн использует key-based хранилища и идемпотентную генерацию ключа: сколько ни пытайся записать, запись появится один раз.

**Проблема.** Streaming job собирает сессии пользователей. Он буферизует сообщения в окне времени на пользователя и пишет обновлённую сессию в key-value хранилище. При retry не должно быть дубликатов.

**Как работает:**

- Ключ строят из неизменяемых полей. Тогда повторная запись просто перезаписывает ту же запись.
- Если есть готовый уникальный атрибут (`user_id`), берут его.
- Если нет, нужна комбинация. Нельзя взять один `user_id` как ключ сессии: каждая новая сессия затрёт предыдущую. Пара `user_id` и время первого события выглядит разумно, но есть ловушка. Job упал, а после перезапуска пришли поздние данные. «Первое» время изменилось, и ключ тоже. Время события изменяемо.
- Безопаснее брать `append time`: время физической записи в брокер. В Kafka это timestamp сообщения, в Kinesis это `approximate arrival timestamp`. В таблицах это `ingestion time`.
- Для batch ключом может быть дата запуска. Файл `2024_11_20` при повторе будет перезаписан. То же работает для партиций и даже таблиц, если можно создавать таблицу каждый день. Атрибуты должны быть неизменяемыми.

```sql
-- Первая запись по пользователю по неизменяемому времени загрузки
SELECT user_id,
       FIRST_VALUE(visit_time) OVER (
         PARTITION BY user_id ORDER BY ingestion_time ASC, visit_time ASC
       ) AS first_visit
FROM visits;
```

**Компромиссы:**

- **Зависит от БД.** В Cassandra, ScyllaDB, HBase это работает сразу. В реляционной БД `INSERT` с тем же ключом даёт ошибку, нужен `MERGE`, и выражение усложняется. Kafka поддерживает ключи, но это append-only журнал: он не убирает дубли при записи. Это делает асинхронная compaction позже. Пока она не отработала, потребители видят дубликаты. Но у них один ключ, поэтому их проще отличить.
- **Изменяемый источник.** Compaction может удалить слишком старые события. Если она удалила первое событие, из которого строился ключ, после рестарта job возьмёт следующую запись, и ключ изменится. Но и данные изменились, поэтому новый ключ допустим.
- В Kafka `append time` лучше брать из настройки брокера (`log.message.timestamp.type`). Время, заданное продюсером, менее надёжно.

**Пример.** Spark Structured Streaming читает визиты из Kafka и пишет сессии в ScyllaDB. Уникальный ключ таблицы состоит из `session_id` и `user_id`. Job берёт из записи Kafka значение и `timestamp` (это `append time`) и строит ключ из него. Для Kinesis достаточно переименовать колонку `approximate arrival timestamp` в `append_time`.

### Transactional Writer

Транзакции дают семантику «всё или ничего»: изменения видны потребителям, только когда писатель их подтвердит (`commit`).

**Проблема.** Batch job использует свободные вычислительные мощности облака и экономит 60% стоимости. Но потребители жалуются на качество данных. Когда провайдер забирает узел, задачи падают и перезапускаются на другом. Они пишут данные заново, и потребители видят дубликаты и неполные записи. Job не должен отдавать частичные данные.

**Как работает:**

- Три шага: открыть транзакцию (явно через `BEGIN` или неявно), записать данные, сделать `commit`.
- Пока нет `commit`, потребитель изменений не видит. При ошибке делают `rollback` или просто не делают `commit`.
- Для хранилищ (BigQuery, Redshift, Snowflake) транзакцию ведёт сама БД.
- Для автономных job и ELT в хранилище (BigQuery, Redshift, Snowflake) транзакция декларативная, и её полностью ведёт хранилище.
- Для распределённых job (обычно ETL) есть два варианта. Локальная транзакция у каждой задачи: хорошо работает, пока нет повторов job. Или одна транзакция на весь job: она стартует до задач и коммитится после завершения всех. Гарантия сильнее, но сделать сложнее. В Spark с Delta Lake commit происходит при записи в commit log. Если этот шаг упал, файлы данных остаются и их надо убрать.
- Идемпотентность идёт от семантики «всё или ничего»: при ошибке коммита нет, и записи остаются невидимыми.
- Поддержка: Delta Lake, Iceberg, Hudi, Kafka, хранилища, PostgreSQL, MySQL и другие СУБД.

**Компромиссы:**

- **Шаг commit.** Открытие и подтверждение транзакции добавляют работы и разрешение конфликтов. Файлы JSON или CSV видны сразу. Файлы Delta Lake видны, только когда появился файл commit. Потребители ждут самую медленную задачу. Зато они получают только полные данные.
- **Поддержка в движках неполная.** Kafka-транзакции есть в Flink, но их нет в Spark. Это сужает применение паттерна.
- **Идемпотентность только в рамках транзакции.** При локальных транзакциях без координации рестарт job перепишет данные уже закоммиченных задач. Backfill тоже добавит те же записи новой транзакцией.
- Читатели с уровнем `read uncommitted` могут увидеть незафиксированные записи (dirty reads). Их потом могут откатить.

**Примеры.**

- **Batch.** Два файла грузятся в таблицу двумя `MERGE`. В одном файле слишком длинные значения: первая операция пройдёт, вторая упадёт, но commit не случится. База не примет частичный успех. Для table formats файлы без файла commit не читаются.
- **Kafka.** Продюсер открывает транзакцию специальным сообщением, а при commit пишет метасобытие. Это работает нативно или через Flink. Важен таймаут транзакции: exactly-once опирается на checkpoint Flink, и если он дольше таймаута, commit не пройдёт.

## Immutable dataset: неизменяемые данные

### Proxy

Идея из известной поговорки: любую проблему можно решить ещё одним уровнем косвенности.

**Проблема.** Job каждый раз пишет полный набор и затирает старый. Юристы просят хранить копии всех прошлых версий, но отдавать только последнюю таблицу из одного места. Набор должен быть неизменяемым, то есть записываться один раз.

**Как работает:**

- Каждую загрузку пишут в новое место: таблица с суффиксом версии или времени.
- После создания таблицы убирают права на запись. В object store для этого есть `WORM`: `Object Lock` в S3, immutability policies в Azure Blob, bucket locks в GCP.
- Читатели ходят через единую точку: `view` вида `SELECT * FROM <последняя таблица>`.
- `View` подходит для большинства хранилищ и реляционных БД, а также для OpenSearch (через алиасы), Cassandra, ScyllaDB и MongoDB.
- Без `view` можно вести `manifest file` со списком файлов или местом данных. Его создание лучше отделить от обработки: если оно упадёт, данные пересчитывать не придётся, а это обычно медленнее.
- В Delta Lake, Iceberg и BigQuery есть time travel. Каждая запись создаёт версию, старые данные остаются. Отдельные таблицы не нужны, но retention ограничен и часто не настраивается (в BigQuery это 7 дней на момент написания книги). Права записи там снять нельзя, но управление правами и не нужно.

**Компромиссы:**

- **Нет `view` в БД.** Тогда нужен `manifest`, и чтение усложняется.
- **Неизменяемость нужно закрепить и в хранилище.** Настройки оркестратора недостаточно. Нужны блокировки и запрет записи, значит нужна помощь инфраструктурной команды.
- Имя таблицы должно быть уникальным при каждом запуске, например из времени старта DAG. Иначе повторный запуск попробует перезаписать старую таблицу.
- Права пользователя job должны разрешать только создание таблиц, не удаление. Иначе даже случайное удаление сломает неизменяемость.

**Пример.** Airflow и PostgreSQL, два шага. Первый грузит данные в скрытую внутреннюю таблицу командой `COPY`. Второй обновляет `view`. Тонкость: имя внутренней таблицы. Повторный запуск не может переписать прошлый набор, поэтому пишет в новую таблицу. Функция `get_devices_table_name` берёт время старта pipeline из контекста Airflow и строит уникальный суффикс.

## Как выбрать паттерн

> **Пояснение:** эту таблицу мы добавили сами, в книге её нет.

| Ситуация | Паттерн |
|---|---|
| Данные поставляются целиком, БД умеет `TRUNCATE` | `Fast Metadata Cleaner` |
| Данные поставляются целиком, метаданных нет | `Data Overwrite` |
| Приходят только изменения | `Merger` |
| Изменения приходят, и нужен консистентный backfill | `Stateful Merger` |
| Стриминг, key-value хранилище | `Keyed Idempotency` |
| Нельзя показывать частичные данные | `Transactional Writer` |
| Нужна неизменяемость и история | `Proxy` |

## Итоги главы

- Идемпотентность делает так, что сколько раз ни запускай job, результат не меняется. Retry и backfill тогда безопасны.
- Перезапись самый простой путь, если весь набор доступен. `Fast Metadata Cleaner` использует `TRUNCATE` и `DROP`, `Data Overwrite` заменяет сами данные.
- `Fast Metadata Cleaner` задаёт границу `backfill` по размеру таблицы, например неделя.
- Если приходят только изменения, используют `Merger` с командой `MERGE`. Удаления передают как `soft delete`.
- Обычный `Merger` при `backfill` даёт несогласованные данные. `Stateful Merger` решает это таблицей состояния и откатом версии.
- `Keyed Idempotency` строит ключ из неизменяемых полей, лучше из `append time`.
- `Transactional Writer` прячет частичную запись до `commit`, но идемпотентность работает только в рамках транзакции.
- `Proxy` хранит все версии неизменяемыми и отдаёт последнюю через `view`.

## Ключевые термины

| Термин | Значение |
|---|---|
| `Idempotency` | Повторный запуск даёт тот же результат |
| `Idempotency granularity` | Единица, которую можно очистить и перезапустить (например, неделя) |
| `Metadata operation` | Операция над описанием данных (`TRUNCATE`, `DROP`), а не над файлами |
| `MERGE` / `UPSERT` | Вставка новых и обновление существующих строк одной командой |
| `Soft delete` | Удаление через флаг, например `is_deleted` |
| `State table` | Таблица с версиями данных по запускам пайплайна |
| `Append time` | Время записи сообщения в брокер. Не меняется при позднем событии |
| `Commit` / `rollback` | Фиксация или откат транзакции |
| `WORM` | Write once read many: запись один раз, чтение много раз |
| `Vacuum` | Физическое удаление устаревших файлов и версий |

## Что это значит на практике

- Проектируйте каждый job так, чтобы его можно было запустить дважды. Retry и backfill в Airflow это норма.
- Для полных наборов выбирайте перезапись, для инкрементов выбирайте `MERGE`. Это самый простой путь.
- В `dbt` инкрементальные модели с `unique_key` это по сути `Merger`. Проверьте, что ключ неизменяемый.
- Не делайте ключ из значений, которые могут измениться. Пример: время первого события сессии. Позднее событие его поменяет. Лучше брать время загрузки.
- Если нужен откат при backfill, используйте time travel (Delta Lake, Iceberg) и таблицу состояния.
- Помните: `Checkpointer` из главы 3 не даёт exactly-once. Повторную запись делают безопасной паттерны этой главы.
- Для аудита и юридических требований храните версии и отдавайте последнюю через `view`.
