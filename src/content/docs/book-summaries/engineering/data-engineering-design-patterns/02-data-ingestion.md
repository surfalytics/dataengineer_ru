**Главная мысль:** Загрузка - первый шаг любой системы. Выбор паттерна зависит от размера данных, частоты изменений, нужной задержки и от того, как провайдер сообщает о готовности данных.

## О чём глава

Глава отвечает на вопрос: как принести данные в систему и не сломать ничего ниже по потоку. Предыдущая глава, [Введение в паттерны](/book-summaries/engineering/data-engineering-design-patterns/01-introduction/), дала общий язык. Здесь он применяется к загрузке. Главные темы: полная и инкрементальная загрузка, репликация, уплотнение файлов, готовность данных, запуск по событию.

Инженер редко создаёт данные сам. Провайдером может быть другой пайплайн вашей команды, другая команда или чужая компания. У каждого свои ограничения, и вам приходится подстраиваться. Иначе данных не будет. Если загрузка сделана плохо, потребители пожалуются на неполный или сломанный набор. Тогда нужны ручное восстановление и `backfill`.

## Все паттерны главы

| Паттерн | Когда применять |
|---|---|
| Full Loader | Набор небольшой или нет признака изменений. Нужна полная копия каждый раз |
| Incremental Loader | Набор растёт. Есть колонка-дельта или партиции по времени |
| Change Data Capture (CDC) | Нужна задержка в секундах и учёт физических удалений |
| Passthrough Replicator | Нужна точная копия данных между средами |
| Transformation Replicator | Копия нужна, но часть полей (PII) нельзя переносить |
| Compactor | Слишком много маленьких файлов, листинг файлов тормозит чтение |
| Readiness Marker | Нужно знать, что набор данных полностью готов |
| External Trigger | Данные приходят нерегулярно. Нужен запуск по событию |

## Full Load: полная загрузка

Полная загрузка работает со всем набором при каждом запуске. Она подходит для начальной загрузки базы и для справочников.

### Full Loader

**Проблема.** Для Silver-слоя нужен справочник устройств от внешнего провайдера. Он меняется несколько раз в неделю, в нём до миллиона строк. В данных нет колонки, по которой видно изменённые строки.

**Как работает:**

- Простейший вариант - два шага: extract и load (`EL`). Это `passthrough job`: данные идут из источника в приёмник без изменений. Для однотипных хранилищ хватает встроенных команд экспорта и импорта.
- Для разных хранилищ нужна тонкая трансформация между шагами. Тогда это `ETL`, и обычно берут фреймворк обработки (Spark).

**Последствия:**

- **Объём данных.** Если набор растёт медленно, ресурсы почти не меняются. Если он вдвое вырос за день, статичные ресурсы не справятся. Помогает автомасштабирование.
- **Согласованность.** Соблазн: заменить данные через `drop-and-insert`. Но потребитель, который читает набор в этот момент, получит частичные данные или вообще ничего. Транзакции решают это проще всего. Без них используйте единый слой доступа (view) и меняйте только скрытые таблицы под ним (подробнее в паттерне `Proxy`, глава 4).
- **Откат.** После полной перезаписи нельзя вернуть старую версию, если нет `time travel`. Он есть в Delta Lake, Iceberg и BigQuery. Его можно сделать самому через тот же слой доступа.

```sql
-- Загрузка в версионную таблицу
COPY devices_20240101 FROM '/data/devices.csv' CSV HEADER;

-- Переключение: потребители видят либо старую, либо новую версию
CREATE OR REPLACE VIEW devices AS SELECT * FROM devices_20240101;
```

**Примеры в книге:**

- **Скрипт.** `aws s3 sync` с ключом `--delete` синхронизирует два бакета и удаляет в приёмнике объекты, которых нет в источнике.
- **Spark и Delta Lake.** Spark масштабируется при скачках объёма. Delta Lake даёт транзакции и версии, а код короткий: читаем JSON, пишем таблицу Delta.
- **Airflow и PostgreSQL.** Нужны две задачи. Первая пишет набор в таблицу с версией в имени (`COPY`, версия приходит параметром оператора). Вторая меняет view, как в коде выше.

> **Не только загрузка.** Все паттерны главы влияют на аналитику и data science, потому что кладут данные в систему.

## Incremental Load: инкрементальная загрузка

Для растущего набора полная загрузка дорога. Инкрементальные паттерны берут только часть набора и работают чаще.

### Incremental Loader

**Проблема.** Часть событий посещений всё ещё пишется в транзакционную базу устаревшими продюсерами. Их нужно переносить в Bronze, но брать всё каждый раз нельзя. События неизменяемые.

**Как работает.** Есть два варианта:

- **Колонка-дельта.** Загрузчик помнит последнее значение (для неизменяемых событий это обычно `ingestion_time`) и берёт только новые строки.
- **Партиции по времени.** Загрузчик берёт целую партицию, например за прошлый час. Данные уже отфильтрованы, состояние хранить не нужно: партицию выводят из времени запуска. Перед чтением нужен `Readiness Marker`.

```python
# Колонка-дельта с границами окна: повторный запуск даёт тот же результат
batch = df.filter(
    f"ingestion_time BETWEEN '{date_from}' AND '{date_to}'"
)
batch.write.mode("append").save(output_path)
```

**Последствия:**

- **Риск event time.** Если колонка-дельта - время события, поздние данные за уже обработанное время будут пропущены.
- **Physical deletes.** Колонка-дельта находит изменённые строки, но удалённая строка просто исчезает из источника, а в вашей копии остаётся. Решения: `soft delete` (продюсер делает `UPDATE` с флагом вместо `DELETE`) или `insert-only` таблицы (`append-only`). Во втором случае потребитель сам определяет удаления и изменения.
- **Backfill.** Если запустить загрузку по колонке-дельте за два месяца, она станет полной и потребует больше ресурсов. Ограничьте окно, например одним часом: `delta_column BETWEEN ingestion_time AND ingestion_time + INTERVAL '1 HOUR'`. Тогда объём предсказуем, а несколько `backfill` идут параллельно. В партиционной версии проблемы нет.

**Примеры в книге:**

- **Скрипт.** Команда копирует из бакета объекты с префиксом `date=2024-01-01`. Ловушка: без префикса справа структура в приёмнике станет плоской.
- **Airflow и Spark, партиции.** DAG начинается с `FileSensor`, который ждёт следующую партицию. Без него можно загрузить частичные данные. Для Glue, BigQuery и Databricks есть свои сенсоры. Аргументы путей берут из неизменяемого времени запуска (`{{ ds }}`), поэтому `backfill` проще.
- **Колонка-дельта.** Сенсор не нужен. Задача сразу фильтрует нужное окно времени, и повторный запуск не возьмёт лишних строк.

### Change Data Capture

**Проблема.** Загрузчик по расписанию слишком медленный, потребители жалуются на ожидание. Нужно передавать каждое изменение таблицы в брокер за 30 секунд.

**Как работает.** `Incremental Loader` не уложится: у него накладные расходы на запуск задачи и запрос. CDC читает низкоуровневый `commit log` базы. Это append-only журнал всех операций.

- Изменения идут в стриминг-брокер или другой приёмник.
- Потребитель решает, хранить ли всю историю или только последнюю версию строки.
- Перехватываются все операции, включая физические удаления. Просить `soft delete` не нужно.

**Последствия:**

| Риск | Что значит |
|---|---|
| Сложность | `Full Loader` и `Incremental Loader` инженер делает сам. Для CDC часто нужна помощь ops: включить журнал, создать пользователя |
| Область данных | Клиент часто видит изменения только после своего запуска. Для истории комбинируйте с другими паттернами |
| Payload | Вместе со строкой приходят метаданные: тип операции, время, типы колонок. Лишнее нужно игнорировать |
| Семантика | Статичные строки становятся данными в движении. `JOIN` двух таблиц без результата значит «пары нет». `JOIN` двух потоков без результата может значить «пара ещё не пришла» |

**Примеры в книге:**

- **`Debezium` с `Kafka Connect`.** Настройка идёт через конфиг: подключение, схемы, префикс топика. Таблица `dedp_schema.events` попадает в топик `dedp.dedp_schema.events`. Для PostgreSQL нужен logical replication с плагином `pgoutput` и пользователь с правами.
- **Delta Lake.** Встроенный `change data feed` включается свойством `enableChangeDataFeed`. Читают через `readChangeFeed`, можно задать лимиты (`maxFilesPerTrigger`) и начать с нужной версии. В выдаче есть колонки `_change_type`, `_commit_version`, `_commit_timestamp`. Обновления дают пары `update_preimage` и `update_postimage`.

## Replication: репликация

Репликация копирует данные как есть. В реальности вход часто приходится менять, например из-за требований регуляторов. Она отличается от загрузки: репликация идёт между однотипными хранилищами и сохраняет метаданные (первичные ключи, позиции событий). Загрузка гибче.

### Passthrough Replicator

**Проблема.** Есть среды dev, staging и prod. Справочник загружается в prod из внешнего API. API не идемпотентен: в течение дня на один вызов он даёт разные ответы. Поэтому в dev и staging нельзя просто повторить загрузку. Нужны те же данные, что в prod.

**Как работает.** Два способа:

- **Уровень вычислений:** задача `EL`, которая копирует файлы или строки без изменений. Любое преобразование рискует качеством: строка в дату, округление.
- **Уровень инфраструктуры:** политика репликации у облачного провайдера. Он копирует записи сам (replication rule для S3, MirrorMaker для Kafka).

**Последствия:**

- **Простота.** Используйте самую простую команду копирования. Для JSON читайте сырой текст, а не парсите. Если важны имена или число файлов, не берите распределённый фреймворк без нужных настроек.
- **Безопасность.** Используйте `push`: среда-владелец сама отправляет данные в другие. Тогда баг не дестабилизирует целевую среду. Но и так бывают сбои: задача может занять последний свободный IP-адрес подсети.
- **PII.** Если в данных есть персональные поля, нужен `Transformation Replicator`.
- **Задержка.** У инфраструктурной репликации она часто есть. Проверьте SLA провайдера.
- **Метаданные.** Одних Parquet-файлов Delta Lake недостаточно, нужен и журнал. В Kafka важны ключи, заголовки и порядок внутри партиции.

**Примеры в книге:**

- **Spark и JSON.** Самый простой API копирует строки без разбора. Число файлов в приёмнике может отличаться, но данные те же.
- **Kafka с порядком.** Функция `write_sorted_events` сохраняет заголовки (`includeHeaders`) и порядок записей (`sortWithinPartitions('offset')`).
- **Инфраструктура.** MirrorMaker для Kafka. Для бакета S3 есть репликация, настроенная через Terraform.

### Transformation Replicator

**Проблема.** Перед релизом задачи нужно тестировать на реальных данных. Синтетика не воспроизводит проблемы качества провайдера. Но в данных есть PII, и вне prod его нельзя использовать.

**Как работает.** Главная проблема тестирования - сами данные. В dev и staging доступ шире, поэтому между чтением и записью добавляется трансформация. Она убирает или заменяет чувствительные поля. Варианты:

- Функция в Spark или Flink.
- SQL `SELECT`.
- Замена значений (например, паттерном `Anonymizer`).

```sql
-- Уменьшение набора: убрать поля с PII
SELECT * EXCEPT (ip, latitude, longitude) FROM visits;

-- Или выдать только разрешённые колонки
GRANT SELECT (visit_id, event_time, user_id) ON TABLE visits TO user_a;
```

`EXCEPT` есть в Databricks и BigQuery. В PySpark то же делает `drop`. `GRANT` в Redshift длиннее, но добавляет защиту (см. `Fine-Grained Accessor`). Если колонки нужны задаче, пишут колоночную трансформацию, которая меняет значения. Для сложных правил или логики на уровне строки нужна функция отображения (в книге на Scala для Spark).

**Последствия:**

- **Риск сломать данные выше, чем в Passthrough.** Пример: схема задаёт формат времени не такой, как в данных JSON или CSV. Колонки времени теряются, и задача на staging падает. Совет: читайте спорные колонки как строки.
- **Десинхронизация.** Сегодняшний список PII может устареть: появятся новые поля, или старые станут PII. Используйте каталог данных или data contract с тегами чувствительных полей. Тогда правила применяются автоматически.

## Data Compaction: уплотнение данных

### Compactor

**Проблема.** Стриминговый пайплайн пишет события в object store, данные должны быть готовы для batch не позже чем через 10 минут. Через три месяца batch-задачи тратят 70% времени на листинг файлов и 30% на обработку. Маленьких файлов слишком много.

**Как работает.** Проблема известна со времён Hadoop. Много файлов значит долгий листинг и тяжёлый ввод-вывод. Compactor объединяет маленькие файлы в большие:

- В Delta Lake это команда `OPTIMIZE`. В Iceberg это действие `rewrite data files`. Обычно это транзакционная задача, которая пишет слитые файлы новым коммитом.
- В Hudi таблица `merge-on-read` пишет данные колонками, а изменения строками (запись быстрее). Compaction сливает строки с колоночным хранилищем.
- В Kafka это `log compaction`. Остаётся последняя запись по каждому ключу. Данные перезаписываются, уникальность ключей не гарантируется.

**Последствия:**

- **Цена и производительность.** Compaction - обычная задача, на больших таблицах дорогая. Запускайте её редко, лучше вне рабочих часов. Но тогда потребители какое-то время читают неуплотнённые данные. Идеала нет. Иногда раз в день достаточно. Иногда compaction лучше включить прямо в загрузку: штраф для потребителей дороже, чем медленная загрузка.
- **Согласованность.** Compaction переписывает данные, которые уже читают. Для форматов с ACID (Delta Lake, Iceberg) это безопасно. Для сырых JSON и CSV сложнее.
- **Очистка.** Старые файлы остаются и продолжают тормозить метаданные. Нужна отдельная очистка (`VACUUM`). После неё нельзя откатиться к версии на удалённых файлах.

```python
table = DeltaTable.forPath(spark, table_dir)
table.optimize().executeCompaction()   # уплотнить
table.vacuum()                         # удалить старые файлы
```

**Примеры в книге:**

- **Delta Lake.** `optimize` перепаковывает только файлы, которые были на старте задачи. Она не конфликтует с читателями и писателями. `vacuum` трогает только файлы старше порога хранения. Иначе можно удалить файлы, которые ещё пишутся.
- **PostgreSQL.** `VACUUM` освобождает место от мёртвых строк (`dead tuples`).
- **Kafka.** Настройки топика: `log.cleanup.policy`, `log.cleaner.min.compaction.lag.ms` и `log.cleaner.max.compaction.lag.ms`. В отличие от Delta, Kafka не гарантирует расписание. Уникальную запись по ключу вы видите не всегда.

## Data Readiness: готовность данных

Следующий вопрос: «Когда начинать загрузку?»

### Readiness Marker

**Проблема.** Каждый час готовится Silver-набор: исправлены проблемы качества, добавлен контекст из API. На него опираются ML и BI. Команды жалуются на неполные данные и просят сигнал готовности. Запустить их пайплайны напрямую вы не можете: они в других командах.

**Как работает.** Набор помечается как готовый. Есть два варианта:

- **Flag file.** После успешной записи создаётся файл, например `_SUCCESS`. Spark создаёт его сам для сырых форматов. В Delta Lake роль маркера играет commit log. Иначе файл создаёт оркестратор отдельной последней задачей.
- **Партиции по соглашению.** Если данные пишутся по часам, партиция 10 готова, когда началась партиция 11.

```python
# Airflow: ждём маркер, не занимая слот воркера
FileSensor(filepath=f"{path}/_SUCCESS", mode="reschedule")
```

**Последствия:**

- **Нет принуждения.** Это модель `pull`. Потребитель может начать читать раньше. Договоритесь об условиях запуска и объясните риски.
- **Поздние данные.** Вы закрыли партиции 8, 9 и 10, и потребители их забрали. Потом нашлись поздние данные за 9 часов. Вы кладёте их в партицию 9, а потребитель считает её закрытой и не заметит. Делайте закрытые партиции неизменяемыми или заранее сообщайте условия изменения. Подробнее в главе 3 (раздел про поздние данные).

**Примеры в книге:**

- **Spark.** Сначала пишет файлы данных, и только потом `_SUCCESS`.
- **Airflow, потребитель.** `FileSensor` с `mode="reschedule"` не занимает слот воркера всё время. Он просыпается и проверяет файл.
- **Airflow, продюсер.** Если маркера нет из коробки, последняя задача DAG создаёт файл (в примере `COMPLETED`). Маркер всегда последний шаг, после финальной трансформации.

## Event Driven: загрузка по событию

Если частота данных непредсказуема, нужно перейти от статичной загрузки к событийной.

### External Trigger

`Readiness Marker` построен на `pull`: потребитель сам проверяет данные. Для событийных наборов лучше `push`: продюсер сам сообщает о готовности.

**Проблема.** Бэкенд выпускает новые функции не чаще раза в неделю. Справочник функций обновляется ежедневно, даже когда изменений нет. Это тратит ресурсы. Бэкенд при релизе шлёт событие в шину. Нужно запускать пайплайн только при новом релизе.

**Как работает.** Задача по расписанию, которая копирует всё или часто проверяет источник, тратит ресурсы. Паттерн состоит из трёх действий:

1. Подписаться на канал уведомлений.
2. Обработать событие: решить, запускать ли пайплайн или задачу. Если шина не умеет фильтровать события, фильтр пишет сам обработчик.
3. Запустить загрузку в оркестраторе или прямо в слое вычислений. Обычно одно событие запускает один пайплайн.

> **Не только триггер.** Если запускать нечего, загрузку можно выполнить прямо в обработчике. Это `event-driven ingestion`.

**Последствия:**

- **Push или pull.** Pull-обработчик работает постоянно и чаще всего получает ноль сообщений. Push-обработчик спит, пока источник не уведомит его. Каждое сообщение запускает новый экземпляр. Push экономнее.
- **Контекст запуска.** Триггер легко превращается в ping оркестратора. Но запущенный пайплайн тоже надо поддерживать, а без контекста не понять, почему он стартовал. Передайте метаданные: версию триггера, конверт уведомления, время обработки, время события.
- **Ошибки.** Событие нельзя потерять. Проектируйте обработчик под сбои. Используйте паттерны главы 3, например `Dead-Letter`.

**Пример.** Serverless-функция (AWS Lambda) запускается при появлении объекта в бакете и вызывает API Airflow. У DAG стоит `schedule_interval=None`, и он стартует только от явного вызова. Устойчивость обеспечивает инфраструктура: у Lambda есть места назначения для неудачных вызовов (`failed-event destinations`). Можно настроить размер пакета и параллельность. В коде книги ключи записаны прямо в тексте ради читаемости. Так делать нельзя, защита описана в главе 7.

## Итоги главы

- Даже простой перенос данных имеет ловушки. Загрузку нельзя недооценивать.
- `Full Loader` прост, но нужны транзакции или слой доступа (view), чтобы потребитель не увидел частичные данные.
- `Incremental Loader` берёт новую часть по колонке-дельте или по партициям. Физические удаления он не видит.
- Ограничивайте окно загрузки, иначе `backfill` станет полной загрузкой.
- CDC читает `commit log`, даёт задержку в секундах и видит удаления. Но нужна настройка базы, а данные становятся данными в движении.
- Репликация копирует данные между средами. `Transformation Replicator` убирает PII, но рискованнее для качества данных.
- `Compactor` объединяет маленькие файлы, но требует расписания и очистки (`VACUUM`).
- `Readiness Marker` сообщает, что набор готов, но принудить потребителей к соглашению нельзя.
- `External Trigger` запускает загрузку по событию. Push экономнее, чем pull.

## Ключевые термины

| Термин | Значение |
|---|---|
| Passthrough job | Задача `EL`: данные проходят без изменений |
| Delta column | Колонка для поиска новых или изменённых строк |
| Soft delete | Удаление через флаг, а не физически |
| Insert-only table | Таблица, куда только добавляют строки |
| Commit log | Журнал всех изменений базы |
| CDC | Захват изменений из журнала базы |
| Change data feed | Встроенный CDC в Delta Lake |
| PII | Персональные данные, которые нельзя свободно копировать |
| Small files problem | Много маленьких файлов замедляют листинг и чтение |
| Compaction | Объединение маленьких файлов в большие |
| `VACUUM` | Очистка файлов, которые больше не нужны |
| Flag file | Файл-маркер готовности, например `_SUCCESS` |
| Push / pull | Продюсер уведомляет сам / потребитель сам проверяет |

## Что это значит на практике

- Начинайте с `Full Loader` для небольших справочников. Это самое простое решение.
- Для больших и растущих наборов используйте партиции по времени. Состояние хранить не нужно, `backfill` проще.
- Ограничивайте окно загрузки верхней границей. Тогда повторный запуск даёт тот же результат.
- Не делайте `drop-and-insert` в таблице, которую читают. Используйте транзакции или переключение view.
- CDC включайте, когда нужны секунды и удаления. Заранее договоритесь с командой базы о журнале.
- Копируйте prod-данные в dev только через `Transformation Replicator` с учётом PII.
- Запланируйте compaction и очистку для таблиц от стриминга.
- Не запускайте зависимые пайплайны по времени. Используйте маркер готовности или событие.
