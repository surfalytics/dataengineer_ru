**Главная мысль:** Сырые данные сами по себе почти бесполезны. Ценность появляется, когда их дополняют, сжимают в понятный вид или доставляют в нужном порядке.

## О чём глава

Глава отвечает на вопрос: как сделать данные полезнее для пользователей. [Главы 3 и 4](/book-summaries/engineering/data-engineering-design-patterns/04-idempotency/) были про надёжность, но надёжный pipeline ещё не создаёт полезный набор. Данные в хранилище сами по себе не ценность: после загрузки они бедные и с проблемами качества. Браузер отдаёт версию, язык и ОС пользователя. Но чем похожи посетители одного браузера, из отдельных событий не видно.

Есть два пути. Первый: добавить информацию через `enrichment` (объединить два набора) и `decoration` (вычислить поля записи). Второй: убрать лишнее и получить обзор через `aggregation` и `sessionization`. Отдельная тема: порядок записей (`ordering`).

## Все паттерны главы

| Паттерн | Когда применять |
|---|---|
| `Static Joiner` | Нужно добавить к событиям медленно меняющийся справочник |
| `Dynamic Joiner` | Обе стороны join постоянно меняются (два потока) |
| `Wrapper` | Нужно сохранить исходную запись и рядом положить вычисленные поля |
| `Metadata Decorator` | Нужно добавить технический контекст, но скрыть его от бизнес-пользователей |
| `Distributed Aggregator` | Связанные записи лежат на разных машинах или в разных хранилищах |
| `Local Aggregator` | Данные уже разложены по ключу, и shuffle не нужен |
| `Incremental Sessionizer` | Сессии строятся пакетно, по партициям |
| `Stateful Sessionizer` | Сессии нужны почти в реальном времени |
| `Bin Pack Orderer` | Нужен порядок записей и bulk-запись при частичных коммитах |
| `FIFO Orderer` | Нужен порядок, и каждое событие нужно отправить сразу, без буфера |

## Data Enrichment: добавить контекст из другого датасета

Событие знает, кто и когда сделал действие. Но оно не знает профиль пользователя или его историю. Эти данные берут из другого источника.

### Static Joiner

Если набор для обогащения статичен, это самый простой случай.

**Проблема.** Бизнес просит набор, который показывает связь между датой регистрации пользователя и его ежедневной активностью. В сырых событиях нет контекста пользователя. Он есть только в статичном справочнике.

**Как работает.** Паттерн подходит для данных в покое и для streaming.

- Выберите ключ для join, например `user_id`.
- Соедините события со справочником обычным `JOIN`. Его поддерживают и фреймворки, и классические хранилища.
- Если справочник меняется со временем, добавьте условие по времени. Справочник тогда ведётся как `SCD` (slowly changing dimensions). Тип 2 хранит строки с датами действия, у текущего значения дата конца пуста. Тип 4 использует две таблицы: текущие значения и вся история.
- Данные можно брать и из API через HTTP-библиотеку. Берите их пачками (bulk): сеть самая дорогая часть. Или материализуйте данные API в таблицу заранее и используйте её в `JOIN`.
- Для идемпотентности материализуйте API и ведите `SCD`. Тогда повторный запуск всегда использует тот же набор.

```sql
SELECT v.visit_id, v.page, u.email
FROM visits v
JOIN users u
  ON u.id = v.user_id
 AND v.event_time BETWEEN u.start_date AND u.end_date;
```

**Компромиссы:**

- **Поздние данные и согласованность.** В идеале посещение сразу после смены профиля получает свежий профиль. На деле так бывает не всегда (см. главу 3). В streaming помогает `Dynamic Joiner`. В batch оркестратор может подождать справочник через `Readiness Marker` (глава 2).
- **Идемпотентность.** При `backfill` решите, должен ли результат быть идемпотентным относительно справочника. Если источник (или API) не умеет запросы по времени, загрузите копию к себе и ведите как `SCD`.

**Примеры в книге.**

- **`SCD` type 2.** Таблица `users` хранит `start_date` и `end_date`. Они входят в условие `JOIN`.
- **Справочник устройств.** Это insert-only таблица, поэтому условия по времени нет, и берут `left join`. Ловушка: у справочника и streaming job разные жизненные циклы. Job не ждёт обновления справочника, возможны промахи, а при полной перезаписи даже join с пустой таблицей (для JSON и CSV это реальный риск). В table format с атомарностью пустую таблицу не прочитать.
- **API.** Spark-writer копит записи в буфер. Когда буфер заполнен, он делает один вызов с уникальным списком IP.

### Dynamic Joiner

`Static Joiner` плохо подходит для двух streaming наборов. Streaming это непрерывно движущиеся данные, а batch работает с медленно меняющимися.

**Проблема.** Тысячи новых пользователей в неделю, профили меняются чаще, и статичный справочник устарел. Каждое изменение попадает в брокер через `Change Data Capture`. Нужен способ объединять события с обеих сторон.

**Как работает.** Как и в `Static Joiner`, нужны ключи и способ join. Но добавляются временные границы. Без них много join останутся пустыми: у наборов разная задержка, и одна сторона может отставать.

- Для обеих сторон нужен буфер с ограничением по времени. Быстрый поток выравнивается с медленным. Если пользователи отстают от посещений на час, буфер хранит посещения лишний час и ждёт пару.
- Хранить события вечно нельзя: не хватит ресурсов. Поэтому есть `GC watermark`. Он удаляет из буфера записи, которые уже слишком стары. Если запись пришла очень поздно, join потерян. Это цена ограниченного буфера.
- Пусть поток A быстрее потока B. A копит неразрешённые ключи. Когда B догоняет, A ищет пару во входе и в буфере. Если пары нет, `GC watermark` убирает записи старше самого старого события B.
- Логику буфера реализуют фреймворки. Вам нужно задать условие по времени и `watermark`.

```python
visits.withWatermark("event_time", "10 minutes").join(
    ads.withWatermark("display_time", "10 minutes"),
    F.expr("""page = visit_page AND
              display_time BETWEEN event_time AND event_time + INTERVAL 2 minutes"""),
    "left_outer")
```

**Компромиссы:**

- **Память против точности.** Больше буфер, больше совпадений, но выше цена. Меньше буфер, но выше риск промахов при большой разнице задержек. Универсальной формулы нет.
- **Поздние данные.** Streaming хуже их переносит. Если у потока пользователей временно пропала связь, `GC watermark` уйдёт вперёд, и поздние события будут проигнорированы. Полноты join нет ни у одного из двух паттернов без доп. усилий: нужно отслеживать и интегрировать поздние данные (глава 3).

**Примеры в книге.**

- **Spark.** Условие join содержит бизнес-правило: реклама показывается не позже чем через две минуты после посещения. `withWatermark` допускает опоздание до 10 минут с обеих сторон.
- **Flink.** Тот же join поддерживается. Есть и более управляемый `temporal table join` (пример на Java, в Python API его нет). `TemporalTableFunction` берёт для события самую свежую рекламу: `update_time <= event_time`.

## Data Decoration: подготовить запись к использованию

### Wrapper

В software engineering обёртка добавляет объекту поведение или атрибуты. В данных то же самое: она отделяет исходные части записи от преобразованных.

**Проблема.** Посещения приходят от разных провайдеров, схемы разные. Нужен job, который достанет поля и положит их в одно место. Вычисленные значения должны быть явно отделены от исходных, а исходная структура сохранена для отладки.

**Как работает.** Запись нельзя просто разобрать в новую структуру: исходные значения потеряются. Поэтому на уровне записи добавляют конверт с исходными и вычисленными значениями. Вычисленные поля идут из самих данных или из контекста выполнения (время обработки, версия job).

- Паттерн работает в форматах streaming (Avro, Protobuf, JSON) и в таблицах: отдельной таблицей, которую можно присоединить, или колонками в той же таблице.
- Для таблиц есть 4 варианта: исходная строка как struct плюс вычисленные колонки; исходные колонки плюс вычисленный struct; все колонки на одном уровне; две таблицы, связанные ключом.
- Первые два варианта денормализованы. Они быстрее читаются. Вариант с отдельными таблицами нормализован. Он читается медленнее, но лучше, когда данные нужно логически изолировать или нельзя менять исходную структуру. Везде нужен контроль схемы (глава 9).

> **Wrapper в таблице.** Конверт в таблице не виден, но он есть: это строка таблицы. Не нужно ломать колоночный формат и класть несколько колонок в одну с вложенными атрибутами.

```sql
SELECT
  CASE WHEN context.user.connected_since IS NULL THEN false ELSE true END AS is_connected,
  CONCAT_WS('-', page, context.referral) AS page_referral_key,
  STRUCT(visit_id, event_time, user_id, page, context) AS raw
FROM input_visits;
```

**Компромиссы:**

- **Разделение домена.** Поля пользователя оказываются в двух структурах: raw и computed. Видно, что преобразовано, а что нет. Но искать данные сложнее: потребитель должен знать оба места. Выход: считать обёрнутые данные данными первых слоёв (Silver), а не конечным видом для пользователей.
- **Размер.** Вычисленные значения входят в запись и увеличивают размер и трафик. С `Metadata Decorator` иначе. Помогает проекция колонок: читать только нужные. Это обычное дело для колоночных хранилищ (Redshift, BigQuery).

**Примеры в книге.** В PySpark контекст добавляется колонкой, затем строится struct из исходного значения (`raw_data`) и контекста (`processing_context`), и всё пишется как JSON. В Spark SQL конверт `decorated` строят через `NAMED_STRUCT`. Можно сделать наоборот: вычисленные значения станут колонками, а сырые уйдут в struct. Если все колонки на одном уровне, нужны ясные имена, иначе пользователь не отличит сырые значения от вычисленных.

### Metadata Decorator

Wrapper универсален, но если добавленные значения не должны быть видны пользователям, они только запутают. Пользователю всё равно, какая версия job создала запись. Такие значения прячут в слое метаданных хранилища.

**Проблема.** Streaming job выходят почти каждую неделю. Развёртывание гладкое, но не видно, как релиз влияет на данные. Нужно добавлять к каждой записи технический контекст (версию job), но не отдавать его пользователям.

**Как работает.** Wrapper здесь не подходит. Реализация зависит от поддержки метаданных в хранилище.

- В `Kafka` у записи есть необязательные headers (пары ключ-значение). Это нативная возможность.
- В объектных хранилищах метаданные можно задать tags файла, если они одинаковы для всех строк файла.
- В реляционных и NoSQL базах метаданных нет. Тогда контекст кладут в данные, но не показывают пользователям. Вариант 1: отдельная колонка (`processing_context`), которую скрывают через view или права доступа (`Fine-Grained Accessor for Tables`, глава 7). Вариант 2: отдельная таблица контекста в схеме только для технической команды, связь по `processing_context_id`. Так контекст не дублируется в каждой строке. Пользователям нельзя давать ни техническую таблицу, ни это поле.

> **Wrapper и метаданные.** Технически похоже. Разница в семантике. Метаданные описывают данные и не предназначены для бизнес-пользователей. Wrapper добавляет и бизнес-атрибуты тоже.

**Компромиссы:**

- **Реализация.** Не все брокеры поддерживают метаданные: у `Kinesis Data Streams` нет headers. В таблицах нужна доп. колонка или таблица, это больше работы.
- **Данные.** Технических ограничений нет, но бизнес-поля (адрес доставки, сумма счёта) в метаданные класть не стоит. Потребители скорее всего не станут искать их там. Метаданные это данные о данных, а пользователям интересна вторая часть.

**Примеры в книге.** Spark пишет в Kafka: метаданные это массив пар ключ-значение, опция `includeHeaders` включает колонку `headers`. Второй вариант: таблица контекста. Загрузка вставляет контекст выполнения и добавляет его первичный ключ в недельную таблицу посещений.

## Data Aggregation: уменьшить, чтобы увидеть картину

### Distributed Aggregator

Первые паттерны главы добавляли информацию. Но и удаление информации создаёт ценность. Этот паттерн использует распределённые фреймворки: они умеют объединять физически разные, но логически похожие данные.

**Проблема.** Job очищает события из Bronze и пишет в Silver. Одному из потребителей нужен OLAP-куб для дашбордов: статистика (число, средняя длительность) по осям (география, устройства). Данные лежат в дневных партициях. Куб нужен за день и за неделю.

**Как работает.** Если набор помещается на одну машину, хватит `group by` языка и функции reduce. В big data связанные записи лежат в разных местах, и работу делят машины кластера. Код остаётся таким же: группировка и reduce.

- Внутри фреймворк делает `shuffle`: записи, лежавшие на разных машинах, пересылаются по сети, чтобы все строки одного ключа оказались вместе.
- Если агрегат допускает частичный расчёт (например `count`), каждый узел сначала считает локально. Потом пересылаются только числа.
- Это модель `MapReduce` (2004). Она эволюционировала от дисковой Hadoop к Spark в памяти.
- Паттерн работает и для данных в разных хранилищах: файлы плюс таблица в `PostgreSQL`, или `external table` в `BigQuery`.

**Компромиссы:**

- **Сетевой обмен.** Обменов два: первый подвозит вход на узлы (хранение и вычисления обычно разделены), второй это `shuffle`. Он часто главный источник задержки. Его можно избежать при определённых условиях (`Local Aggregator`).
- **`Data skew`.** Один ключ встречается намного чаще других. Его пересылка и обработка на одном узле самые дорогие. Помогает `salting`: к ключу добавляют соль (случайное число), агрегируют по ключу с солью, затем по исходному ключу ещё раз. В Spark есть и `Adaptive Query Execution`.
- **Масштабирование.** Узел закончил reduce, но фреймворк держит его для отказоустойчивости, и пока job идёт, он не освобождается. Решение: `shuffle service`. Он хранит и отдаёт только shuffle-данные, и узел можно освободить (External Shuffle Service в Spark, Shuffle в GCP Dataflow).

```python
(df.withColumn("salt", (F.rand() * 3).cast("int"))
   .groupBy("group_key", "salt").agg(...)
   .groupBy("group_key").agg(...))
```

**Примеры в книге.** Для демо взяты `PostgreSQL` и локальные JSON-файлы: Spark объединяет их, хотя они физически разделены. Наличие shuffle проверяют через `explain()`: ищите узел `Exchange hashpartitioning`. Фильтрация идёт локально, до обмена по сети. В `BigQuery` файлы из GCS объявляют внешней таблицей и читают как обычные. Внешние таблицы есть в Redshift, Synapse и Snowflake.

### Local Aggregator

Обмен по сети не нужен, если данные уже правильно разложены на входе или набор помещается на одну машину.

**Проблема.** Streaming job строит окна по посещениям из брокера с партициями. Объём стабилен, партиции не меняются. Нужно убрать `shuffle` группировки, который фреймворк добавляет сам.

**Как работает.** За паттерн три фактора: дорогой `shuffle`, статичные партиции источника и связанные атрибуты в одном месте. Сеть нужна один раз, для чтения входа. Все записи одного ключа уже в одной входной партиции.

- Задачи изолированы и не ждут других. Это особенно полезно для streaming, где медленная единица задерживает всё.
- Работа производителя: писать запись с ключом группировки в одну физическую партицию (статичный ключ и неизменное число партиций).
- Работа потребителя: в `Kafka Streams` есть `groupByKey`. В `Spark` подсказок нет, но помогают `mapPartitions` и `foreachPartition`. Spark избегает shuffle и для наборов в buckets с тем же ключом и числом buckets. Bucketing это партиционирование партиций (паттерн `Bucket`, глава 8).
- В `AWS Redshift` похожий эффект даёт `DISTSTYLE KEY` и `DISTSTYLE ALL` (маленькую таблицу копируют на все узлы).

**Компромиссы:**

- **Масштабирование.** Нужны статичный источник и согласованные партиции. Если число партиций изменить, для ключа появятся несколько групп. Придётся перераспределить все записи, это дорого. В streaming ещё сложнее: нужна остановка (`stop-the-world`), чтобы дообработать остаток на старых партициях.
- **Ключи группировки.** Нужна одна логика ключа для всех потребителей. Иначе запись пришлось бы писать в несколько мест с разными ключами. Если одному потребителю нужна группировка по типу изменения, а другому по `user_id`, для одного из них нужен `Distributed Aggregator`.

**Примеры в книге.**

- **Kafka Streams.** `groupByKey` на `KStream` использует ключ записи и группирует локально, без сети.
- **Spark.** Job сортирует посещения в каждой партиции по `visit_id` и `event_time`, и writer строит агрегат страниц сессии. Когда `visit_id` меняется, результат уходит в топик Kafka.
- **Redshift.** Таблица `users` с `ALL` копируется на все узлы, её join идёт локально. Таблица `visits` с `KEY` держит строки с одним `DISTKEY` на одном узле.

## Sessionization: события в сессии

Сессия объединяет события одной активности: начало, действия, конец. Конец обычно определяется периодом неактивности.

### Incremental Sessionizer

Сессия кажется компонентом реального времени, и данные для неё обычно оттуда. Но строить её можно и в batch. Этот паттерн для batch.

**Проблема.** Посещения лежат в почасовых партициях. Сессия начинается с первого посещения и заканчивается, если за два часа нет новых. Сессия длится от нескольких минут до трёх часов, поэтому занимает максимум три партиции. Аналитикам тяжело каждый раз обрабатывать много подряд идущих партиций. Вы хотите применить `Incremental Loader` к сессиям.

**Как работает.** Записи одной сессии лежат в нескольких партициях подряд. Это семейство инкрементальной обработки. Нужны три хранилища:

- **Входные данные:** сырые события (почасовые партиции).
- **Завершённые сессии.** Сюда можно писать и текущие сессии, но лучше отличать их атрибутом вроде `is_final = false`.
- **Pending (незавершённые) сессии.** Сессии, которые закроются в одном из следующих запусков. Хранилище закрытое, формат может отличаться от публичного. Можно добавить технические детали, например ID запуска для идемпотентности.

Логика начинается с объединения входа с pending-сессиями прошлого запуска для каждой сущности (пользователь, товар, визит). Получится новая сессия (нет pending), восстановленная сессия с новыми данными или восстановленная без новых данных (она скоро истечёт).

Затем применяют логику сессии из трёх состояний: **инициализация** (сессия началась, например заход на главную), **накопление** (сессия идёт: хранить страницы по порядку), **завершение** (по событию или по неактивности, например три часа). Завершённые сессии идут в публичный вывод, остальные остаются в pending. Логику пишут через `WINDOW` или `GROUP BY` с функцией на языке программирования.

- `Idempotency`: перед запуском удалите готовые и pending-сессии этого запуска и всех следующих (`DELETE ... WHERE execution_time_id >= '{{ ds }}'`). Потом сессии строятся заново.

**Компромиссы:**

- **Период неактивности.** Чем он длиннее, тем больше поздних данных попадёт в сессию, но тем больше нужно ресурсов. Он же держит сессии в скрытой зоне дольше. Частичные сессии можно выдавать раньше (это смягчает и задержку batch). Но они меняются: в антифроде после первой партиции сессия «не рискованная», а после второй «рискованная». Помечайте такие сессии (`is_completed = false`).
- **Поздние данные, партиции и backfill.** Сессии зависят от прошлого: сессия 09:00 влияет на 10:00, та на 11:00. Поздние данные одной сущности могут повлиять на следующие сессии. Backfill одной партиции заставляет пересчитать все следующие, это быстро дорожает. Простой выход: переиграть все следующие партиции (код прост, цена высока). Умный выход: найти затронутые сущности и пересчитать их отдельным pipeline (дешевле, но сложнее).

**Примеры в книге.** Airflow. Две параллельные задачи чистят завершённые и pending-сессии этого и следующих запусков через `DELETE FROM` по неизменяемому `ds`. Затем запрос из четырёх блоков. Первый грузит вход во временную таблицу, чтобы при сбое не повторять загрузку. Второй объединяет вход с pending-сессиями по времени выполнения Airflow (оно идемпотентно), применяет `WINDOW` и функции `COALESCE`, `LEAST`, `GREATEST`, `ARRAY_CAT`. Время истечения считается только для сессий с новыми данными. Дальше идёт запись: pending-сессии (`expiration_batch_id` не равен текущему запуску), потом завершённые.

### Stateful Sessionizer

Если важна свежесть, `Incremental Sessionizer` не поможет: при почасовых партициях лучшая задержка один час.

**Проблема.** Потребители довольны доступностью сессий, но многим нужна меньшая задержка. Посещения в брокере доступны за секунды. Нужно переписать batch pipeline и строить сессии почти в реальном времени.

**Как работает.** Обычные streaming pipeline stateless и не подходят. Нужна stateful версия с `state store`, как в `Windowed Deduplicator`. Здесь он играет роль pending-хранилища из `Incremental Sessionizer`: хранит все текущие сессии. Рабочий процесс тот же:

- Паттерн создаёт сессию или возобновляет её из `state store`.
- Затем объединяет её с новыми записями по бизнес-логике (например, хранит страницы по порядку).
- Если сессия завершена (или нужна частичная), паттерн пишет её в выход. Иначе новое состояние идёт в `state store`.
- В фреймворке `state store` есть из коробки. Обычная схема (Spark Structured Streaming, Flink): хранилище в памяти для скорости и регулярная синхронизация в отказоустойчивое хранилище.

Логику строят на одной из двух абстракций:

- **Session window.** Окно для каждого ключа сессии. Длина задаётся `gap duration`: максимальная неактивность между двумя событиями с одним ключом. Если пауза больше, создаётся новое окно, иначе событие попадает в открытое.
- **Arbitrary stateful processing.** Больше работы, но гибче: вы сами задаёте логику паузы, статичную или динамическую, у каждого ключа свою. Есть в Spark Structured Streaming, Flink и GCP Dataflow.

**Компромиссы:**

- **At-least-once.** Состояние сохраняется нерегулярно (`checkpointing`). Остановленный job стартует с последнего успешного checkpoint, и часть событий обрабатывается повторно. Не используйте в ключе сессии значения, которые меняются между запусками, например реальное время.
- **Масштабирование.** Смена мощностей требует перераспределения состояния. Пока ключи не назначены новым рабочим, job не обрабатывает данные. Это дороже, чем в stateless.
- **Период неактивности.** Баланс цены и полноты. Длинный период увеличивает нагрузку и задержку вывода.
- **Время истечения.** Очистку состояния завершённых сессий считают по event time (надёжнее, лучше по умолчанию) или по processing time. Второе опасно: любая неожиданная задержка (например, повторы записи) закроет сессии слишком рано.

**Примеры в книге.**

- **Spark, arbitrary stateful processing.** Декларативная часть задаёт колонку истечения (`event_time`), ключ (`visit_id`), функцию, структуры сессий и таймаут по event time. Логика в `map_visits_to_session`: если состояние истекло, она собирает итоговую сессию, иначе накапливает данные. Накопление идёт в две части. Первая определяет базовое время истечения: в первой итерации `watermark` ещё нет, поэтому берут время события или `watermark`. Лучше опираться на `watermark`: он связан с прогрессом job. Пример: ключ A активен 8 минут. По `watermark` его можно выдать сразу после первого элемента ключа B (10:10 < 10:14), а по event time нельзя (10:18 > 10:14). Вторая часть читает прошлое состояние и обновляет время истечения.
- **Flink.** Проще: session window с `gap duration` 10 минут и допустимым опозданием 15 минут (так поздно могут прийти события, которые вольются в уже выданное окно).

## Data Ordering: доставка в правильном порядке

Порядок важен, когда потребитель читает события хронологически. Угроза: частичный коммит (`partial commit`). Bulk API записывает только часть пачки. При повторе порядок ломается.

### Bin Pack Orderer

Кошмар упорядоченной доставки в большом масштабе это частичные коммиты (`partial commit`). Некоторые базы дают bulk API: оно пишет много записей за раз и экономит сеть. Но запрос может пройти полностью, частично или совсем не пройти. Частичный успех может сломать порядок.

> **Частичные коммиты.** В классическом коммите два состояния: успех и сбой. Здесь есть третье: база приняла только часть записей. Пример: записи 10:00, 10:10, 10:20. База может записать все, две, одну или ни одной. Опасны средние случаи: неизвестно, какие записи не доставлены. Если записана только 10:20, придётся повторять 10:00 и 10:10, и порядок нарушится. Такая семантика у `PutRecords` в Kinesis, `BatchWriteItem` в DynamoDB и bulk в Elasticsearch.

**Проблема.** Внешние сайты встраивают ваши страницы, и события посещений нужно отдавать партнёрам через внешний API. Нужен общий job с окном по processing time 10 минут и агрегатами по минутам. События уходят по минутам и провайдерам, в порядке event time. Хранилище API это брокер с частичными коммитами, поэтому порядок при retry нужно беречь.

**Как работает.** Можно доставлять каждую запись отдельно, но это много запросов. Bulk вместе с этим паттерном гарантирует порядок при частичных коммитах.

1. Отсортируйте записи по ключу группировки и времени.
2. Разложите строки по delivery bins: события разных сущностей с одной позицией кладут в один bin. В каждом bin у ключа только одна запись. Bins это массивы или списки.
3. Отправляйте bins по очереди. Retry внутри bin остаётся локальным: у ключа в нём одна запись, порядок не нарушается. Следующий bin не уходит, пока текущий не записан полностью.

**Компромиссы:**

- **Retry.** Порядок гарантирован в рамках одного запуска. Если упадёт весь pipeline, повтор затронет уже отправленное, и общий порядок сломается.
- **Сложность.** Нужна своя логика сортировки и bins, это сложнее обычной сортировки.

**Примеры в книге.** Spark и Kinesis. Сначала локальная сортировка: каждая задача сортирует свои партиции без сети. Затем код проходит по строкам и кладёт каждую в bin, пока `visit_id` не меняется. Когда он меняется, позиция bin сбрасывается в 0. Потом bins по очереди уходят в Kinesis.

### FIFO Orderer

`Bin Pack Orderer` сохраняет порядок при частичных коммитах и даёт пропускную способность за счёт bulk. Но есть более простая альтернатива для случаев без жёстких требований к задержке и объёму.

**Проблема.** Streaming job находит особые события и пересылает их в порядке обработки в другой поток. Каждую запись нужно доставить как можно быстрее, поэтому буфер недопустим.

**Как работает.** Алгоритм сортировки не нужен: нужно отправлять первым пришедшее первым (FIFO). Паттерн только находит записи и шлёт запрос. Важно получить подтверждение доставки каждой записи перед следующей, иначе возможны потеря или нарушение порядка.

- Вариант с API на одну запись: `PutRecord` в Kinesis или `send(...)` Kafka с синхронным `flush(...)`.
- Вариант с bulk API при конкурентности 1. Он годится только для хранилищ с полной семантикой коммитов. Много bulk-запросов одновременно слать нельзя: если один не записался, порядок сломается.
- В `Kafka`: `max.in.flight.requests.per.connection = 1` или `idempotent producer`, который допускает до 5 параллельных запросов и сохраняет порядок.
- В `Kinesis` с частичными коммитами используют `PutRecord` и `SequenceNumberForOrdering`. Без него записи идут примерно по порядку. В `Pub/Sub` есть `ordering_key`, но гарантия только для одного продюсера в одном регионе.

> **In-flight запросы.** Продюсер отправляет следующий bulk, не ожидая ответа. Это поднимает пропускную способность, но порядок может сломаться: если прошёл только второй из двух запросов, а первый повторили.

**Компромиссы:**

- **I/O и задержка.** Один запрос на каждую запись, поэтому нагрузка и задержка растут. Можно смягчить многопоточностью, но порядок сохраняется только в рамках сущности: все записи одного пользователя или товара отдают одному процессу.
- **FIFO не значит exactly-once.** Он лишь доставляет старые записи первыми. Пример: `send(...)` прошёл, а следующий `ack(...)` упал. После рестарта продюсер снова отправит уже доставленные записи. Нужны паттерны идемпотентности (глава 4).

**Примеры в книге.** Kafka. Простейший вариант: продюсер отправляет запись, сразу делает `flush` и ждёт записи на брокере. Дорого по сети. Вариант с bulk: без `flush`, буфер до секунды, конкурентность 1. Эффективнее, но единица тормозит. Лучше `idempotent producer` с большим временем буферизации. Для хранилищ с частичными коммитами (Kinesis) bulk недоступен: нужен `PutRecord` с `SequenceNumberForOrdering`.

## Итоги главы

- Данные становятся ценными, когда их дополняют или сжимают.
- `Static Joiner` объединяет события со статичным справочником. Для идемпотентного `backfill` справочник ведут как `SCD`.
- `Dynamic Joiner` объединяет два потока через буфер и `GC watermark`. Ни один join не гарантирует полноты без работы с поздними данными.
- `Wrapper` отделяет исходные значения от вычисленных. `Metadata Decorator` прячет технический контекст в метаданные.
- `Distributed Aggregator` группирует данные через `shuffle`. Риски: перекос ключа и цена сети.
- `Local Aggregator` убирает `shuffle`, но требует статичных партиций и одного ключа группировки.
- `Incremental Sessionizer` строит сессии в batch, `Stateful Sessionizer` в streaming через `state store`. Из-за зависимости от соседних партиций `backfill` дорог.
- `Bin Pack Orderer` держит порядок при частичных коммитах. `FIFO Orderer` проще, но не даёт exactly-once.

## Ключевые термины

| Термин | Значение |
|---|---|
| Enrichment | Добавление данных из другого датасета |
| Decoration | Добавление вычисленных или технических полей к записи |
| `SCD` type 2 / type 4 | Хранение истории справочника: строки с датами или отдельная таблица |
| `GC watermark` | Граница, после которой запись удаляется из буфера join |
| `Shuffle` | Пересылка записей между узлами по ключу |
| `Data skew` | Перекос: один ключ намного больше остальных |
| `Salting` | Добавление случайного значения в ключ, чтобы разбить перекос |
| Session window | Окно по ключу, которое закрывается после паузы `gap duration` |
| `State store` | Хранилище состояния stateful-задания |
| Partial commit | Bulk-запись, где часть пачки записана, а часть нет |
| Delivery bin | Пачка записей с уникальными ключами для безопасной bulk-доставки |

## Что это значит на практике

- **Справочник для join нужно версионировать.** Тогда backfill даёт тот же результат. Подойдёт `SCD2` или `snapshot` в `dbt`.
- **Не вызывайте внешний API на каждую строку.** Берите пачками или материализуйте API в таблицу.
- **Смотрите план запроса.** Найдите `Exchange` и перекос. Часто один ключ тормозит всё задание.
- **Храните технический контекст отдельно.** Версия job и время обработки полезны при расследованиях, но не нужны в витрине.
- **Сессии зависят от соседних партиций.** Планируйте backfill заранее. Он может быть дорогим.
- **В streaming считайте всё по event time.** Задайте `watermark` и проверьте, как он влияет на потерю поздних записей.
- **Если нужен порядок, проверьте API приёмника.** Узнайте, есть ли у него частичные коммиты.
