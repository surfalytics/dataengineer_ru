**Главная мысль:** big data не отменяет dimensional modeling. Меняются типы данных и платформы, но основа та же: бизнес-цель, `dimension` и `fact`, `conformed dimension`, `durable key`. Сырые данные любого формата нужно превратить в факты и привязать к общим dimensions.

## О чём глава

Главы [19](/book-summaries/engineering/data-warehouse-toolkit/19-etl-subsystems/) и [20](/book-summaries/engineering/data-warehouse-toolkit/20-etl-development-process/) учили строить `ETL` для привычных реляционных данных. Глава 21 отвечает на вопрос: что меняется, когда данные бывают любого формата и не подходят для обычного SQL? Авторы не дают модель для каждого случая. Они сравнивают две архитектуры и собирают практики.

- Что такое big data и какие требования она предъявляет.
- Две архитектуры: расширенная RDBMS и MapReduce/Hadoop.
- Практики управления, архитектуры, моделирования и governance.

![Data highway: кеши с растущей задержкой и качеством, и backflow из хранилища](/assets/data-warehouse-toolkit/ch21-data-highway.png)

Схему читайте сверху вниз: данные идут от сырого источника к хранилищу через кеши с растущей задержкой и качеством. Пунктир — `backflow`: из хранилища в ранние кеши возвращаются `durable key` и итоги.

## Что такое big data

Размер здесь не главное. Big data — это структурированные, полуструктурированные, неструктурированные и сырые данные во многих форматах. Часть из них совсем не похожа на чистые числа и текст, которые хранилища держали 30 лет. Многие нельзя анализировать SQL-подобными средствами. Главное, по мнению авторов, это смена подхода: как думать о данных как об активе, где их собирать, как анализировать и как зарабатывать на выводах. Примеры задач: ранжирование поиска, учёт рекламы, геномика, умные счётчики, антифрод, отток клиентов. Модели для каждой задачи в главе нет.

Обычные RDBMS и SQL с этим не справляются. Книга перечисляет 19 требований к подходящей системе. Вот главные.

- Петабайты данных, тысячи процессоров, нет единой точки отказа.
- Хранение в исходном формате: изображения, сигналы, иерархии, пары «имя и значение».
- Загрузка не медленнее гигабайт в секунду, до объявления структуры данных.
- `UDF` (user-defined function) — функции пользователя внутри запроса, на разных языках, с библиотеками.
- Streaming-запросы на входящих данных.
- Join dimension на миллиард строк с fact на триллион без предварительной кластеризации.

В ответ появились две архитектуры.

## Extended RDBMS: реляционная база с новыми типами

Производители реляционных баз добавляют новые типы данных: векторы, матрицы, текст, изображения, видео и наборы пар «имя и значение». Хранить их как blob недостаточно. База должна обрабатывать их внутри ядра с помощью специальных UDF, которые пишут аналитики. Полезен и приём в два прохода. Сначала RDBMS работает как `fact extractor` над исходными данными. Потом результаты возвращаются на вход как обычные строки и колонки.

## MapReduce/Hadoop: фреймворк для функций над данными

`MapReduce` создал Google в начале 2000-х для поиска по веб-страницам на тысячах машин. Авторы называют его средой выполнения UDF, где функция может быть очень сложной. Главная реализация — открытый проект Apache `Hadoop`. Он работает на своей файловой системе `HDFS` и умеет читать и писать в Amazon S3. Подробно эту архитектуру книга не разбирает.

## Сравнение двух архитектур

Авторы считают, что у архитектур разные долгосрочные плюсы и они ещё долго будут жить рядом. Таблица показывает картину на момент написания книги.

| Критерий | Extended RDBMS | MapReduce/Hadoop |
|---|---|---|
| Лицензия и цена | В основном проприетарная, дорогая | Open source, дешевле |
| Структура данных | Должна быть задана | Не нужна |
| Сильная сторона | Быстрый поиск по индексам | Полное сканирование больших объёмов |
| SQL и транзакции | Полная поддержка | SQL косвенно (например, Hive), транзакций почти нет |
| Сложные структуры и логика | Косвенная поддержка | Глубокая поддержка |

> **Пояснение:** Hive — слой над Hadoop, который позволяет писать SQL-подобные запросы к данным в HDFS.

## Рекомендуемые практики для big data

Рынок big data незрелый, но опыт уже накопился. Практики реляционных хранилищ за 30 лет остаются в силе: источники по бизнес-задачам, простой и быстрый интерфейс, dimensions и facts, `conformed dimension`, `SCD`, `durable surrogate key`. Новые практики книга делит на четыре группы.

## Практики управления

### Стройте среду вокруг аналитики

Среду нужно строить вокруг сложной аналитики, а не вокруг ad hoc запросов и стандартных отчётов. Каждый шаг от источника до экрана аналитика должен поддерживать аналитические функции. Их реализуют как UDF или в metadata-driven среде.

### Не стройте legacy-среду сейчас

Среда big data меняется слишком быстро для долгоживущего фундамента. Держите баланс между подходами: Hadoop, grid computing, pushdown в RDBMS, свои серверы, облако. Окончательного победителя не будет. Hadoop авторы считают гибкой средой для ETL: он добавляет данным структуру, чтобы их можно было загрузить в RDBMS. Книга советует исходить из того, что вы перепишете и перенесёте все приложения за два года.

### Стройте из результатов sandbox

Data scientists экспериментируют на любых языках. После proof of concept IT переписывает удачное на поддерживаемый стек. Авторы пишут, что IT здесь должен быть «необычно терпимым» к разнообразию технологий.

### Начните с простых приложений

Простой старт — Hadoop как дешёвое гибкое хранилище для backup и archive. Так команда набирается навыков при малом риске. Есть и второй плюс: исходное приложение может исчезнуть, например из-за лицензии, и данные из него лучше заранее сбросить в документированный формат.

## Практики архитектуры

### Data highway

`Data highway` — логическая цепочка кешей с растущей задержкой. Книга советует строить физически только те кеши, которые нужны. Всего их может быть пять.

| Кеш | Задержка | Пример |
|---|---|---|
| Raw source | Сразу | Антифрод по картам |
| Real time | Секунды | Подбор рекламы на странице |
| Business activity | Минуты | KPI dashboards |
| Top line | 24 часа | Сводка за сутки для руководителей |
| DW и long time series | День, период, год | Отчёты, ad hoc, история |

Каждый кеш — отдельное физическое хранилище. Путей может быть несколько. Например, данные идут в real time cache и одновременно в суточный top line cache, который похож на классический `ODS` (operational data store). Из него данные уходят в DW. Многие данные на highway остаются нереляционными.

### Fact extractor

`Fact extractor` превращает сырые данные в числа и передаёт их в следующий кеш. Пример из книги: анализ неструктурированных твитов даёт трендовые показатели вроде share of voice, resolution time и sentiment ratio.

### Стройте комплексные экосистемы

Big data позволяет объединить в одной среде таблицы RDBMS, документы, e-mail и внутреннюю бизнес-соцсеть. Книга приводит воображаемый пример: у крупного финансового института есть защищённая соцсеть для сотрудников и партнёров. Переписку в ней нужно хранить так, чтобы по ней можно было делать запросы. Её собирают в Hadoop, делают `dimensionalization` (см. ниже) и потом архивируют.

### Планируйте качество данных

Качество растёт вдоль highway. Это классический компромисс между задержкой и качеством. Данные с очень малой задержкой неизбежно грязные: на проверки нет времени. Проверка одного поля идёт быстро. Проверка связей между полями и источниками медленнее. Суточные кеши строят на более полных данных: из них убраны неполные и отклонённые транзакции. В мгновенном потоке таких данных просто нет.

### Добавляйте ценность как можно раньше

Фильтрацию, чистку, conforming, matching, join и диагностику делайте на самых ранних шагах. Фильтрация уменьшает объём, который идёт дальше. Conforming добавляет общие enterprise-атрибуты в customer, product и date, поэтому возможны join между областями. Авторы отмечают и другую школу: чистить только при анализе, чтобы не удалить интересные выбросы.

### Backflow: данные идут назад по highway

Dimensions из хранилища (customer, product, date) нужно возвращать в ранние кеши. Для этого во всех кешах нужны одинаковые `durable key`. Поэтому «задача номер один» каждого ETL-шага между кешами — заменить собственные ключи источника на durable keys. Тогда анализ в любом кеше подключает данные хранилища простым join. Назад идут и производные данные из fact tables, например исторические итоги.

### Streaming-аналитика

Streaming-аналитику стоит включить в выбранных потоках. Анализ начинается, пока данные ещё поступают. Иногда запрос можно остановить, когда результат превысил порог. Академическая работа `CQL` (continuous query language) описала семантику движущихся окон по времени. Книга советует искать такие расширения в загрузчиках RDBMS и HDFS.

### Избегайте boundary crash

`Boundary crash` — упор в предел диска или памяти. Раньше из-за него разработчики писали обходной код, который не помогал главной задаче приложения. В обычных базах проблему почти убрали, но big data возвращает её. Hadoop упрощает рост: можно добавлять обычные серверы. Но их всё равно нужно закупить и подключить. Поэтому планируйте масштаб далеко вперёд.

### Прототип в публичном облаке, потом private cloud

Публичное облако разворачивается мгновенно. Для быстрых прототипов это удобно, если чувствительность данных позволяет. Авторы предупреждают: не оставляйте огромный набор данных у провайдера на выходные. Для rack-aware MapReduce с data locality публичное облако может не дать нужного контроля над хранилищем.

### Ищите ускорение в 10–100 раз

Книга советует искать и ждать ускорений в 10–100 раз. Открытый рынок породил сотни узких решений, и некоторые из них в 100 раз быстрее стандартных. Пример — прогресс в задаче «big join». Минус: такие решения могут не вписаться в единую архитектуру. Ещё две темы с огромными требованиями к скорости: визуализация петабайтов и semantic zooming без предагрегатов (спуск от агрегата к деталям, как при приближении карты).

### Следите за вычислительными ресурсами

Отделяйте аналитику big data от обычного хранилища, чтобы сохранить SLA. Hadoop, скорее всего, не конкурирует с RDBMS за ресурсы. Но если аналитика идёт на машине хранилища, будьте осторожны: требования big data быстро растут.

### Используйте in-database analytics

Когда данные уже в таблицах, SQL вместе с аналитическими расширениями работает очень мощно. Авторы отдельно называют PostgreSQL: у него расширяемый синтаксис для UDF внутри ядра.

## Практики моделирования

### Мыслите dimensions и facts

В любом формате данных есть базовые сущности: клиент, продукт, место, время. Нужно найти dimensions в каждом источнике и прикрепить их к каждому атомарному наблюдению. Это `dimensionalization`. Для неё подходит сама аналитика big data. Пример из книги: в твите «Wow! That is awesome!» анализ часто находит клиента, место, продукт и сессию. Dimensionalization нужно автоматизировать и делать на самом раннем шаге.

### Объединяйте источники через conformed dimensions

Авторы считают это, возможно, самой сильной практикой из классического DW/BI. Customer dimensions разных источников могут иметь разные ключи, поля и даже `grain`. Но в них можно встроить общий enterprise-атрибут, например демографическую категорию клиента. Тогда запросы к источникам выполняют отдельно, а результаты по этому атрибуту сливают простым sort-merge. Атрибут вводят постепенно, и старые приложения не ломаются. Подробнее в главах [8](/book-summaries/engineering/data-warehouse-toolkit/08-crm/) и [19](/book-summaries/engineering/data-warehouse-toolkit/19-etl-subsystems/).

### Закрепляйте dimensions durable surrogate keys

Не опирайтесь на `natural key` приложения для главных сущностей. Natural keys несовместимы между приложениями, и ими управляет кто-то другой. Поэтому к natural key каждого источника добавляют сквозной `durable surrogate key`. Durable значит, что никакое бизнес-правило его не меняет: ключ принадлежит DW/BI, а не источнику. Surrogate значит, что это простое целое число, выданное по порядку или созданное надёжным хешем.

### Объединяйте структурированные и неструктурированные данные

Многие данные никогда не попадут в реляционную базу и останутся в Hadoop. Но с conformed dimensions и durable surrogate keys все виды данных можно объединить в одном анализе. Пример из книги: медицинское исследование выбирает группу пациентов и добавляет к данным DW/BI снимки, заметки врачей и мнения о лечении в соцсетях.

### Отслеживайте изменения через SCD

`SCD` — старая и надёжная практика хранилищ. В big data она так же важна. Приёмы SCD разобраны в [главе 5](/book-summaries/engineering/data-warehouse-toolkit/05-procurement/).

### Объявляйте структуру при анализе

Книга советует не объявлять структуру до момента анализа. При загрузке структура может быть непонятна, содержимое может сильно меняться, а разные аналитики вправе видеть данные по-разному. Минус: такие данные трудно индексировать. Но большинство алгоритмов big data читают весь набор целиком. Для данных, которые идут в RDBMS, перенос в именованные колонки — ценный шаг ETL.

> **Пояснение:** сегодня этот подход называют `schema-on-read`, а обратный — `schema-on-write`. В книге таких слов нет.

### Загружайте данные как пары «имя и значение»

Источники big data полны сюрпризов: приходят неожиданные данные, которые нужно загрузить на высокой скорости. Выход — грузить их как простые пары «имя и значение». Пример из главы [8](/book-summaries/engineering/data-warehouse-toolkit/08-crm/): заявитель на кредит пишет среди активов «редкая почтовая марка = $10 000». Такая пара загрузится без ошибки, даже если вы не знаете, что с ней делать.

### Прототипируйте через data virtualization

`Data virtualization` объявляет логические структуры поверх физических данных. Пример — SQL view. Цена: вычисления при каждом запросе вместо ETL, который строит таблицы заранее. Книга советует материализовать виртуальную схему, когда она проверена и нужна скорость физических таблиц.

## Практики governance

### Отдельного big data governance нет

Governance должен охватывать всю экосистему данных, а не быть отдельным решением для big data. Минимум: privacy, security, compliance, качество данных, метаданные, `MDM` (master data management) и бизнес-глоссарий.

### Dimensionalize данные до governance

Governance нужен, даже когда вы не знаете, что внутри данных. Лучший шанс классифицировать их — как можно полнее выполнить dimensionalization на самом раннем этапе: разобрать, сопоставить и сделать identity resolution на лету. Авторы советуют даже не использовать данные до этого шага.

### Privacy важнее всего

Если в данных есть сведения о людях или организациях, privacy — самый важный взгляд на governance: тут больше всего ответственности и риска. Для большинства анализов персональные данные маскируют, а данные агрегируют так, чтобы нельзя было узнать человека. Hadoop плохо управляет обновлениями после записи. Поэтому данные маскируют или шифруют при записи (`persistent data masking`) или маскируют при чтении (`dynamic data masking`).

### Не выбирайте big data вместо governance

Не откладывайте governance в спешке. Даже для прототипов ведите чек-лист вопросов на будущее. Авторы не хотят неэффективной бюрократии и шутят, что можно стремиться к «agile bureaucracy».

## Итоги главы

- Big data — это не размер, а разнообразие форматов и новый взгляд на данные как на актив.
- RDBMS и SQL не покрывают требования к big data, поэтому появились extended RDBMS и MapReduce/Hadoop. Книга ждёт, что они будут жить рядом.
- Практики хранилищ за 30 лет остаются в силе: dimensions и facts, conformed dimensions, SCD, durable surrogate keys.
- Не стройте legacy-среду: считайте, что приложения вы перепишете за два года, и начинайте с простого.
- Data highway — цепочка кешей с растущей задержкой и качеством, а backflow возвращает в ранние кеши dimensions из хранилища.
- Fact extractor превращает неструктурированные данные в числа, а dimensionalization привязывает любые данные к клиенту, продукту, месту и времени.
- Структуру можно объявлять при анализе, а неожиданные поля загружать как пары «имя и значение».
- Governance общий для всех данных, а самое важное в нём — privacy.

## Ключевые термины

| Термин | Значение |
|---|---|
| `UDF` | Функция пользователя внутри обработки данных |
| `MapReduce` / `Hadoop` | Фреймворк для распределённых функций над данными и его главная реализация |
| `Data highway` | Цепочка кешей с растущей задержкой и качеством |
| `Fact extractor` | Превращает сырые данные в числовые факты |
| `Backflow` | Возврат dimensions и итогов из DW в ранние кеши |
| `Boundary crash` | Упор в предел диска или памяти |
| `Dimensionalization` | Поиск dimensions в данных и привязка к наблюдениям |
| `Data virtualization` | Логическая структура (view) поверх физических данных |
| `Schema-on-read` | Структуру определяют при чтении (термин не из книги) |

## Что это значит на практике

Это заметки автора конспекта, а не текст книги.

- Сегодня вместо Hadoop чаще используют lakehouse и облачные платформы (Parquet, Iceberg, Spark). Идеи главы остаются верными.
- Сырой слой держите в исходном виде (JSON, Parquet). Это ваш архив.
- Для отчётов делайте типизированную модель: dimensions и facts. Не просите BI читать JSON каждый раз.
- Часто используемые поля выносите из JSON в колонки. Строки, которые не прошли приведение типов, пишите в таблицу отклонений.
- Добавляйте `durable key` для клиента и продукта при первой загрузке. Тогда любой слой подключается к dimension простым join.
- Новую схему сначала пробуйте через view над сырыми данными. Материализуйте её, когда она проверена.
- Исключите или замаскируйте персональные поля до публикации.

## Практика в DuckDB

Запустите `duckdb` в терминале или откройте [shell.duckdb.org](https://shell.duckdb.org). Расширение `json` встроено в DuckDB. Блоки идут по порядку. Решения тоже запускайте по порядку.

### Шаг 1. Создаём сырые JSON-данные

### Задания

**1.** Schema-on-read. Не создавая схему, найдите, какие поля встречаются в событиях и как часто. Потом достаньте `user.id`, `user.country` и `coupon` из JSON.

<details>
<summary>Решение</summary>

```sql
-- профиль структуры: какие поля есть и в скольких событиях
SELECT k AS field, count(*) AS events
FROM (SELECT unnest(json_keys(payload)) AS k FROM raw_events)
GROUP BY k
ORDER BY events DESC, field;

-- достаём значения. Если поля нет, получаем NULL
SELECT event_id,
       payload->>'$.user.id'      AS user_id,
       payload->>'$.user.country' AS country,
       payload->>'$.coupon'       AS coupon
FROM raw_events
ORDER BY event_id;
```

Поля `items`, `ts`, `type`, `user` есть во всех шести событиях. `attrs` есть в трёх, `coupon` в одном. Отсутствие поля не ломает запрос: вернётся `NULL`.
</details>

**2.** Flatten. Разверните массив `items` из покупок в строки: одна строка на товар. Потом разверните `attrs` в пары «имя и значение».

<details>
<summary>Решение</summary>

```sql
-- одна строка на товар в покупке
SELECT e.event_id,
       i->>'$.sku'                                  AS sku,
       i->>'$.qty'                                  AS qty_raw,
       try_cast(i->>'$.price' AS DECIMAL(10,2))     AS price
FROM raw_events e, unnest(from_json(e.payload->'$.items', '["JSON"]')) AS t(i)
WHERE e.payload->>'$.type' = 'purchase'
ORDER BY e.event_id, sku;

-- пары имя и значение
SELECT e.event_id, j.key AS attr_name, trim(j.value::VARCHAR, '"') AS attr_value
FROM raw_events e, json_each(e.payload->'$.attrs') AS j
ORDER BY e.event_id, attr_name;
```

Первый запрос вернёт 5 строк (товары из событий 1, 3, 4 и 5). Второй вернёт 4 пары. События 3, 4 и 6 не имеют `attrs`, и в результат не попадут.
</details>

**3.** Schema-on-write. Создайте типизированную таблицу `stg_event_item` с `try_cast` для времени и количества. Строки, где приведение не удалось, сохраните в `rejected_event_item`. Оставшиеся поместите в `clean_event_item`.

<details>
<summary>Решение</summary>

```sql
CREATE TABLE stg_event_item AS
SELECT e.event_id,
       try_cast(e.payload->>'$.ts' AS TIMESTAMP)  AS event_ts,
       e.payload->>'$.user.id'                    AS user_id,
       e.payload->>'$.user.country'               AS country,
       i->>'$.sku'                                AS sku,
       try_cast(i->>'$.qty' AS INT)               AS qty,
       try_cast(i->>'$.price' AS DECIMAL(10,2))   AS price,
       e.payload::VARCHAR                         AS raw_json
FROM raw_events e, unnest(from_json(e.payload->'$.items', '["JSON"]')) AS t(i)
WHERE e.payload->>'$.type' = 'purchase';

CREATE TABLE rejected_event_item AS
SELECT * FROM stg_event_item
WHERE event_ts IS NULL OR qty IS NULL OR price IS NULL;

CREATE TABLE clean_event_item AS
SELECT * FROM stg_event_item
WHERE event_ts IS NOT NULL AND qty IS NOT NULL AND price IS NOT NULL;

SELECT 'clean' AS bucket, count(*) AS rows_cnt FROM clean_event_item
UNION ALL
SELECT 'rejected', count(*) FROM rejected_event_item;
```

Чистых строк 4, отклонена 1 (событие 4: плохая дата и `qty = "two"`). В `raw_json` лежит исходный документ. Так можно разобрать причину и перезагрузить.
</details>

**4.** Fact extractor. Из текстов отзывов получите числовые факты. Определите тональность по ключевым словам и посчитайте по дням число положительных, отрицательных и нейтральных отзывов, а также долю положительных.

<details>
<summary>Решение</summary>

```sql
CREATE TABLE fact_feedback AS
SELECT feedback_id,
       payload->>'$.user'                       AS user_id,
       CAST(payload->>'$.ts' AS DATE)           AS feedback_date,
       CASE
           WHEN lower(payload->>'$.text') LIKE '%отлично%' OR lower(payload->>'$.text') LIKE '%супер%'  THEN 'positive'
           WHEN lower(payload->>'$.text') LIKE '%плох%'    OR lower(payload->>'$.text') LIKE '%долго%'  THEN 'negative'
           ELSE 'neutral'
       END AS sentiment
FROM raw_feedback;

SELECT feedback_date,
       count(*) FILTER (WHERE sentiment = 'positive') AS positive,
       count(*) FILTER (WHERE sentiment = 'negative') AS negative,
       count(*) FILTER (WHERE sentiment = 'neutral')  AS neutral,
       round(count(*) FILTER (WHERE sentiment = 'positive') / count(*), 2) AS positive_share
FROM fact_feedback
GROUP BY feedback_date
ORDER BY feedback_date;
```

2 марта: 1 положительный, 1 отрицательный. 3 марта: 1 положительный, 1 нейтральный. Тексты превратились в числа, которые можно суммировать. Это и есть fact extractor. Правила на ключевых словах — простой пример. В реальной системе тут стоит модель.
</details>

**5.** Загрузка в dimensional model. Постройте `dim_user` с unknown member и surrogate key. Создайте `dim_product` из sku. Загрузите `fact_purchase_item` с grain «один товар в одном событии покупки». Затем посчитайте выручку по странам.

<details>
<summary>Решение</summary>

```sql
-- dim_user: user_key = surrogate key хранилища, user_id = natural key источника.
-- страна берётся из самого свежего события
CREATE TABLE dim_user AS
SELECT 0 AS user_key, 'unknown' AS user_id, 'Unknown' AS country
UNION ALL
SELECT row_number() OVER (ORDER BY user_id), user_id, coalesce(country, 'Unknown')
FROM (
    SELECT payload->>'$.user.id' AS user_id,
           arg_max(payload->>'$.user.country', try_cast(payload->>'$.ts' AS TIMESTAMP)) AS country
    FROM raw_events
    GROUP BY 1
);

CREATE TABLE dim_product AS
SELECT row_number() OVER (ORDER BY sku) AS product_key, sku
FROM (SELECT DISTINCT sku FROM clean_event_item);

-- grain: один товар в одном событии покупки
CREATE TABLE fact_purchase_item AS
SELECT c.event_id,
       row_number() OVER (PARTITION BY c.event_id ORDER BY c.sku) AS line_no,
       strftime(c.event_ts, '%Y%m%d')::INT      AS date_key,
       coalesce(u.user_key, 0)                  AS user_key,
       p.product_key,
       c.qty,
       c.qty * c.price                          AS amount
FROM clean_event_item c
LEFT JOIN dim_user u    ON u.user_id = c.user_id
JOIN dim_product p      ON p.sku = c.sku;

SELECT u.country, sum(f.amount) AS revenue, count(*) AS items
FROM fact_purchase_item f
JOIN dim_user u USING (user_key)
GROUP BY u.country
ORDER BY revenue DESC;
```

Выручка RU: `2 * 10.5 + 99 + 10.5 = 130.50`, три позиции. DE: 15.00, одна позиция. KZ в результате нет, потому что событие 4 отклонено. Его нужно разобрать в `rejected_event_item`.
</details>
