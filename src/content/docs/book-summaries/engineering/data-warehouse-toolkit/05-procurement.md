**Главная мысль:** закупки состоят из нескольких процессов, и для каждого шага лучше сделать свою fact table. Но главное в главе другое: описания в dimension меняются, и для каждого атрибута нужно заранее решить, как хранить историю. Авторы описывают восемь способов: `SCD` type 0–7.

![Star schema закупок: fact table строки заказа поставщику и dimensions даты, товара, поставщика, склада и договора](/assets/data-warehouse-toolkit/ch05-procurement-star.png)

Это упрощённая схема для практики ниже. В центре fact table строки заказа, вокруг неё dimensions. В `dim_vendor` атрибут `tier` хранится как Type 2, а `region` как Type 1. Что это значит, объясняет вторая часть главы.

## О чём глава

[Глава 4](/book-summaries/engineering/data-warehouse-toolkit/04-inventory/) показала склад и `bus matrix`. Глава 5 идёт дальше по цепочке создания стоимости (value chain): от склада к закупкам. Закупки отвечают на два вопроса. Как разложить поток закупочных документов по fact tables? И что делать, когда описание поставщика, товара или клиента меняется со временем?

- Закупки: вопросы бизнеса и строки `bus matrix`.
- Одна fact table на все операции или отдельные таблицы на каждый шаг.
- `Accumulating snapshot` для всего пути закупки.
- Базовые типы `SCD`: type 0, 1, 2, 3 и 4.
- Гибриды: type 5, 6 и 7.

## Закупки как бизнес-процесс

Закупки нужны любой организации, которая покупает товары или услуги для себя или для перепродажи. Для ритейлера важна хорошая цена товара, для производства — цена сырья. Авторы отмечают: заметную экономию дают меньшее число поставщиков и договоры с предпочтительными поставщиками.

В закупках есть переговоры по договорам, заявки на закупку (`purchase requisition`), заказы поставщику (`purchase order`, PO), приёмка и платежи. Бизнес задаёт такие вопросы:

| Тема | Что хочет знать бизнес |
|---|---|
| Спрос и цены | Что мы покупаем чаще всего, у скольких поставщиков и по каким ценам. Можно ли сэкономить, объединив поставщиков |
| Дисциплина | Покупают ли сотрудники у предпочтительных поставщиков или обходят договоры (`maverick spending`) |
| Цена по договору | Получаем ли мы согласованную цену или есть отклонение (`purchase price variance`) |
| Поставщики | `Fill rate` (доля заказанного, которую поставили), доставка вовремя, просрочки, доля back order (не поставлено сразу), доля брака при приёмке |

## Транзакции закупок и bus matrix

Процесс выбран: закупки. В нём много операций: заявки, заказы, уведомления об отгрузке, приёмки на складе и платежи. Как в главе 4, первая идея проста: одна fact table, grain — одна операция закупки. Dimensions: дата, товар, поставщик, условия договора и тип операции. Факты: количество и сумма. Номер договора — `degenerate dimension`: номер документа лежит прямо в fact table, и своей таблицы у него нет. По нему видно объём закупок по каждому договору.

В этой схеме дата и товар знакомы по [главе 3](/book-summaries/engineering/data-warehouse-toolkit/03-retail-sales/): это общие `conformed dimension`. У производства сырьё лежит в отдельной dimension сырья. Новые dimensions такие:

- `Vendor` — одна строка на поставщика.
- `Contract terms` — одна строка на типовой набор согласованных условий. Это похоже на dimension акций из главы 3.
- `Transaction type` — по нему группируют и фильтруют операции, например оставляют только заказы.

### Одна fact table или несколько

Теперь выбор: одна fact table с типом операции или отдельные таблицы. Авторы пишут, что простой формулы нет. Помогают четыре вопроса.

| Вопрос | Ответ в закупках |
|---|---|
| Как бизнес анализирует данные? | Заказ, отгрузку, приёмку и платёж он считает разными процессами |
| Это разные процессы? | Да. Подсказка: у каждого шага свои номера документов (номер заказа, номер чека платежа). Они становятся `degenerate dimension` |
| Источники пишут метрики с разным grain? | Да, источников три: закупки, склад и кредиторская задолженность |
| У операций разные dimensions? | Да. Скидка есть только у платежа, а сотрудник, принявший товар, только у приёмки |

В главе 4 всё было иначе: разные движения запасов были одним процессом, и хватило одной fact table.

Быстрый способ взвесить варианты — набросать `bus matrix`. Авторы советуют добавить в неё два столбца: самый детальный grain (`atomic grain`) и метрики. Так матрица становится ближе к подробной матрице реализации из [главы 16](/book-summaries/engineering/data-warehouse-toolkit/16-insurance/).

| Процесс | Grain | Метрики |
|---|---|---|
| Заявки на закупку | Строка заявки | Количество и сумма |
| Заказы поставщику | Строка заказа | Количество и сумма |
| Уведомления об отгрузке | Строка уведомления | Отгруженное количество |
| Приёмка на складе | Строка приёмки | Принятое количество |
| Счета поставщика | Строка счёта | Количество и сумма счёта |
| Платежи поставщику | Один платёж | Сумма счёта, скидка, сумма к оплате |

Итог для закупок: отдельные fact tables. Их dimensions богаче. В общей таблице пришлось бы обобщать: дата заказа и дата приёмки стали бы «датой операции», закупщик и приёмщик склада — «сотрудником». Модель хуже читается. Цена выбора — больше таблиц для загрузки и агрегатов. Но ETL не обязательно сложнее: загрузить каждый источник в свою таблицу обычно проще, чем собрать несколько источников в одну.

### Дополнительный snapshot закупок

Если бизнес следит, как товар идёт по цепочке закупок и сколько длится каждый этап, нужен `accumulating snapshot`. Это одна строка на весь путь закупки, которую обновляют на каждой вехе (подробнее в [главе 4](/book-summaries/engineering/data-warehouse-toolkit/04-inventory/)). В ней лежат даты заказа, приёмки, счёта и платежа, суммы и lags между вехами: от заказа до приёмки, от приёмки до платежа, от счёта до платежа.

Авторы предупреждают: такая таблица подходит только процессу с чёткими вехами. Если процесс — непрерывный поток без конца, она не нужна.

## Slowly changing dimensions: основы

До сих пор мы считали, что dimensions не зависят от времени. В жизни атрибуты меняются, хотя и медленно: компания пересматривает товарные линии, клиент переезжает.

![Как выбрать тип SCD: нужна ли история атрибута, и какой тип подходит](/assets/data-warehouse-toolkit/ch05-scd-types.png)

Схема — шпаргалка по выбору типа. Спросите, нужна ли история атрибута, и идите по стрелке к типу. В нижнем ряду гибриды.

Авторы дают три правила:

- Решает бизнес, а не IT. Проектировщик обсуждает изменения с представителями бизнеса по data governance (`data stewards`). Нельзя думать, что история не нужна только потому, что о ней не говорили при сборе требований.
- Нельзя класть меняющиеся атрибуты в fact table, считая dimension статичной. Авторы называют это недопустимым.
- Для каждого атрибута выбирают свой способ. В одной dimension их можно смешивать.

Ralph Kimball ввёл понятие slowly changing dimensions в 1995 году, и сокращение `SCD` прижилось. Типы 1, 2 и 3 известны давно. Авторы добавили номера 0, 4, 5, 6 и 7 для приёмов, которые раньше описывали менее точно.

Все примеры ниже — из магазина электроники. Товар — программа IntelliKidz. 1 февраля 2013 года её переводят из отдела Education в отдел Strategy, чтобы поднять продажи.

### Type 0: оставить исходное значение

Значение никогда не меняется, и факты всегда группируются по исходному значению. Type 0 подходит атрибутам с пометкой «исходный», например исходному кредитному рейтингу клиента. Так же ведёт себя большинство атрибутов в dimension даты.

`Durable key` всегда хранят как Type 0. Это ключ, который хранилище присваивает сущности само. Он не меняется, даже если меняется `natural key` из источника: например, номер сотрудника сменился после увольнения и возвращения (см. [главу 3](/book-summaries/engineering/data-warehouse-toolkit/03-retail-sales/)). В этой главе durable key считается неизменным.

### Type 1: перезаписать

`Type 1` — перезапись. Старое значение в строке dimension заменяют текущим: у IntelliKidz отдел `Education` меняют на `Strategy`. Ключи не меняются, fact table не трогают. Все старые факты по-прежнему ссылаются на `product_key` 12345.

Поэтому истории нет. Если продажи вырастут, объяснить рост будет нечем: старые и новые факты выглядят так, будто товар всегда был в Strategy. Type 1 подходит для небольших исправлений и для атрибутов, где старое значение не нужно. Авторы предупреждают, что команды часто берут Type 1 по умолчанию, а потом бизнесу нужна история. Перейти на другой тип после этого трудно.

Скрытые последствия Type 1:

- Тот же отчёт даёт разные итоги до и после перезаписи.
- Готовые агрегаты по этому атрибуту нужно пересчитать, чтобы они сходились с детальными данными.
- Если модель развёрнута как `OLAP cube` (многомерный куб с предрассчитанными агрегатами), а атрибут входит в иерархию, куб нужно обработать заново.

Книга предупреждает: Type 1 выглядит самым простым, но делает недействительными агрегаты и кубы по этому атрибуту.

### Type 2: новая строка

`Type 2` — главный способ хранить историю. Когда атрибут меняется, в dimension вставляют новую строку с новым `surrogate key`. Каждая строка — версия профиля, которая была верна в свой период. У одного natural key теперь несколько surrogate keys.

| `product_key` | SKU (`natural key`) | Отдел | Действует с | Действует по | Текущая |
|---|---|---|---|---|---|
| 12345 | ABC922-Z | Education | 2012-01-01 | 2013-01-31 | нет |
| 25984 | ABC922-Z | Strategy | 2013-02-01 | 9999-12-31 | да |

Fact table снова не трогают. Факты до 1 февраля 2013 года ссылаются на ключ 12345, новые факты получают ключ 25984. Так новая строка точно делит историю. Допустим, в январе IntelliKidz продали на 500 долларов, в феврале на 100. При Type 1 отчёт покажет 600 долларов в Strategy. При Type 2 он покажет 500 долларов в Education и 100 в Strategy.

Для Type 2 не нужно пересчитывать агрегаты и обрабатывать кубы. Чтобы посчитать товары, считайте `DISTINCT` по natural key (SKU), а не по surrogate key: natural key связывает версии одного товара.

Type 2 — самый безопасный выбор, если бизнес не уверен в правилах для атрибута. Из Type 2 можно сделать вид Type 1 (так работают типы 6 и 7 ниже). Обратно не получится: перевод из Type 1 в Type 2 задним числом требует новых строк и перекодирования ключей в fact table.

> **Пояснение:** в SQL Type 1 — это `UPDATE` существующей строки. Type 2 — это `UPDATE` даты конца у старой строки и `INSERT` новой. Практика ниже делает это через `MERGE`.

#### Даты действия и признак текущей строки

В dimension с Type 2 добавляют служебные колонки: дату начала действия (`row_effective_date`), дату конца (`row_expiration_date`) и признак текущей строки. Они нужны ETL: при загрузке факта он ищет версию, которая действовала на дату события (так делает задание 1 в практике ниже). В запросах к fact table по этим датам фильтровать не нужно: join идёт по одному ключу.

Для новой строки дату конца ставят `9999-12-31`, а не `NULL`. Тогда строку, действовавшую на дату, можно надёжно искать через `BETWEEN`. Когда появляется новая версия, период старой строки закрывают сразу перед началом новой, без разрывов. Если изменения отслеживают точнее одного дня, берут дату и время. Тогда дату конца можно сделать равной началу следующей строки, а вместо `BETWEEN` писать `>= начало AND < конец`. Одной даты начала мало: поиск версии усложняется. Признак текущей строки быстро выбирает только текущие профили.

Type 2 требует surrogate keys. Natural key не подходит: у одного товара несколько версий. Natural key с номером версии или с датой начала тоже не подходит: вернутся проблемы операционных ключей из главы 3, а в запросах появится join по датам. Как вести surrogate keys, показывают [глава 19](/book-summaries/engineering/data-warehouse-toolkit/19-etl-subsystems/) и [глава 20](/book-summaries/engineering/data-warehouse-toolkit/20-etl-development-process/).

#### Type 1 атрибуты в Type 2 dimension

В одной dimension часто смешивают Type 1 и Type 2. Тогда исправление Type 1 может потребовать обновить несколько строк. Пример: исправили дату вывода товара на рынок после Type 2 изменения отдела. Правильную дату, скорее всего, нужно записать в обе версии IntelliKidz. Правила для ETL определяют data stewards, а команда DW/BI помогает обсуждению.

### Type 3: новая колонка

Type 2 не связывает новое значение со старыми фактами: фильтр по Strategy покажет только факты после 1 февраля 2013 года. Обычно это нужно. Но иногда надо увидеть факты так, будто изменения не было. Чаще всего это реорганизация отдела продаж: районы перерисовали, но несколько месяцев пользователи хотят смотреть недавние продажи по старым районам.

`Type 3` решает эту задачу так: новую строку не добавляют, а добавляют колонку. В dimension появляется `prior_department` со значением `Education`. Основную колонку `department` перезаписывают как Type 1: там теперь `Strategy`. Старые отчёты сразу показывают новый отдел, а прежний доступен через `prior_department`. Текущее и прежнее значения верны одновременно. Авторы называют это «альтернативными реальностями».

Больший номер не значит лучший способ. Type 3 используют редко, когда нужно видеть два взгляда сразу.

- Type 3 плохо подходит для непредсказуемых изменений, например смены штата клиента. Прежний штат, который сменился 10 дней назад у одних клиентов и 10 лет назад у других, ничего не даёт. Для таких атрибутов лучше Type 2.
- Type 3 лучше всего для крупной смены, которая затрагивает много строк сразу: пересмотр товарной линии или отдела продаж.
- Колонке с прежним значением дают точное имя, например «отдел 2012» или «отдел до слияния». Но такие имена могут вызвать побочные изменения в BI-слое. Если атрибут входит в иерархию, куб, как и при Type 1, нужно обработать заново.

#### Несколько Type 3 атрибутов

Если атрибут меняется регулярно, например товарные линии пересматривают каждый год, бизнес хочет смотреть метрики по любому прошлому значению. Тогда Type 3 обобщают: колонка «текущий отдел» (её перезаписывают) и колонки по годам, например «отдел 2012» и «отдел 2011». Если товара тогда не было, в колонке стоит «неприменимо». Колонку с текущим значением используют чаще всего, поэтому старые запросы не придётся менять при следующей перестройке. В январе 2014 года добавляют колонку «отдел 2013», копируют в неё текущее значение и перезаписывают текущую колонку новым отделом.

### Type 4: mini-dimension

Что делать, когда атрибуты меняются быстро, а dimension огромная, на миллионы строк? Размер замедляет просмотр значений и фильтры. А Type 2 не годится: не хочется добавлять строки в таблицу, где их уже миллионы.

`Type 4` решает обе проблемы: часто анализируемые или часто меняющиеся атрибуты выносят в отдельную маленькую dimension — `mini-dimension`. Для клиента это, например, возраст, оценка частоты покупок и уровень дохода. В mini-dimension одна строка на каждую встретившуюся комбинацию значений, а не на клиента. Постоянные атрибуты остаются в большой таблице клиентов.

Непрерывные значения, например доход, превращают в диапазоны (`band`). Иначе комбинаций будет почти столько же, сколько клиентов. Диапазоны — главный компромисс: сделать их мельче позже трудно. Если пользователям нужно точное значение, например кредитный балл, его хранят в fact table в дополнение к диапазону.

Fact table хранит два ключа клиента: основной и ключ mini-dimension, действовавший на момент события. Это даёт два выигрыша:

- Маленькая dimension — быстрый вход в факты. Запрос не трогает огромную таблицу клиентов, пока в нём нет её атрибутов.
- Fact table сама хранит историю профиля. Клиенту исполнилось 26 лет: следующая загрузка запишет другой ключ профиля, а старые строки не изменятся.

Размер mini-dimension нужно ограничивать. Пять атрибутов по 10 значений дают 100 000 строк. Авторы считают это разумным пределом, если строить все комбинации заранее. Можно строить только те, что встретились в данных. Если и этого мало, используют несколько mini-dimensions (см. [главу 10](/book-summaries/engineering/data-warehouse-toolkit/10-financial-services/)).

Профиль иногда меняется без события: клиента обновили, а продажи не было. Если бизнесу нужен точный профиль на любую дату, добавляют `factless fact table` (таблицу без числовых фактов) с датами начала и конца. Она фиксирует каждое изменение связи между клиентом и профилем. А если клиентов анализируют без фактов, например «сколько клиентов в округе по возрастным группам», текущий ключ профиля кладут и в таблицу клиентов. Это следующий тип.

## Гибридные техники SCD

Гибриды комбинируют базовые способы. Они нужны, когда надо сохранить исторически точное значение для факта и при этом показать исторические факты по текущим значениям. Но за гибкость платят сложностью: инженерам она нравится, а бизнес-пользователей отпугивает. Книга советует не брать гибриды, пока бизнес не подтвердит, что они нужны.

Номера объясняются так: Type 5 — это 4 + 1, Type 6 объединяет типы 1, 2 и 3 (и сумма, и произведение равны 6), а Type 7 — просто следующий номер.

### Type 5: mini-dimension и Type 1 outrigger

Type 5 дополняет Type 4. В основную dimension клиента добавляют ключ текущей mini-dimension. Это Type 1 атрибут: его перезаписывают при каждой смене профиля. Такую ссылку из dimension на другую dimension называют `outrigger`. Делать этот ключ Type 2 нельзя: частые изменения вернутся в большую таблицу.

Type 5 нужен, если надо посчитать текущие профили без метрик из fact table или свернуть исторические факты по текущему профилю клиента. В BI-слое основную dimension и текущую mini-dimension показывают как одну таблицу, а колонки называют `current_age_band` и так далее. Но два пути к демографии, через fact и через outrigger, для некоторых пользователей слишком сложны.

### Type 6: Type 1 атрибуты в Type 2 dimension

В Type 6 у строки две колонки отдела: исторический (Type 2) и текущий. Когда отдел меняется, добавляют новую строку, и у неё оба отдела равны. А у всех прежних строк этого товара текущий отдел перезаписывают.

| `product_key` | Исторический отдел | Текущий отдел | Действует с | Действует по |
|---|---|---|---|---|
| 12345 | Education | Critical Thinking | 2012-01-01 | 2013-01-31 |
| 25984 | Strategy | Critical Thinking | 2013-02-01 | 2013-06-30 |
| 31726 | Critical Thinking | Critical Thinking | 2013-07-01 | 9999-12-31 |

В таблице товар дважды сменил отдел. Исторический отдел группирует факты по значению на момент события. Текущий отдел собирает факты всех трёх ключей под текущее значение.

Итого: новая строка фиксирует изменение (Type 2), колонка хранит текущее значение (Type 3), а следующие изменения перезаписывают её (Type 1). Часть колонок лучше скрыть от пользователей, чтобы не пугать выбором.

### Type 7: две dimensions, Type 1 и Type 2

Type 7 появился как ответ на вопрос, подойдёт ли Type 6 для 150 атрибутов в большой dimension. В fact table лежат два ключа: surrogate key версии (Type 2) и `durable key`. Первая dimension хранит исторически точные атрибуты версий. По durable key fact связан со второй dimension, где только текущие значения (Type 1). Её колонки называют с префиксом `current`.

Функционально это то же, что Type 6. Но Type 6 растит число колонок в одной таблице, а Type 7 использует два ключа в fact. Для ETL Type 7 всегда проще: таблицу текущих значений можно отдавать как view над Type 2 dimension, где остались только текущие строки. Цена — лишняя колонка в fact table. Зато запросы по текущим значениям фильтруют меньшую таблицу. Без durable key в fact им пришлось бы идти к фактам через большую Type 2 таблицу, и отчёты замедлились бы.

#### Type 7 для отчёта «на любую дату»

Иногда, хотя это редкость, просят свернуть исторические факты по профилю на произвольную дату. Например, показать три года по иерархии, которая действовала 1 декабря прошлого года. Два ключа в fact это позволяют. Сначала отфильтруйте Type 2 dimension по датам начала и конца: на каждый durable key останется одна строка. Потом соедините результат с fact по durable key. Без фильтра по датам на один durable key придётся несколько строк. Авторы называют эту возможность непростой и советуют давать её только узкой группе опытных аналитиков.

## Сводка по типам SCD

Таблица показывает, как каждый тип влияет на анализ фактов.

| Тип | Что делаем в dimension | К какому значению привязаны факты |
|---|---|---|
| 0 | Не меняем значение | К исходному |
| 1 | Перезаписываем значение | К текущему |
| 2 | Добавляем строку с новым профилем | К значению на момент события |
| 3 | Добавляем колонку с прежним значением | К текущему и к прежнему, на выбор |
| 4 | Выносим быстро меняющиеся атрибуты в mini-dimension | К профилю на момент события |
| 5 | Type 4 плюс ключ текущего профиля (Type 1) в основной dimension | К профилю на момент события и к текущему |
| 6 | В Type 2 dimension добавляем колонки Type 1 и перезаписываем их во всех версиях | К значению на момент события и к текущему |
| 7 | Type 2 dimension плюс view с текущими значениями, в fact два ключа | К значению на момент события и к текущему |

Авторы пишут, что этот раздел придётся перечитать, когда вы будете выбирать стратегию для своего DW/BI.

## Итоги главы

- Выбор между одной fact table и несколькими зависит от четырёх признаков: как бизнес видит процессы, сколько процессов на самом деле, сколько источников и какие у операций dimensions.
- Для закупок авторы выбирают отдельные fact tables на каждый шаг, потому что dimensions получаются точнее, а ETL часто проще.
- `Accumulating snapshot` по всему пути закупки показывает длительность этапов, но подходит только процессу с чёткими вехами.
- Для каждого меняющегося атрибута выбирают свой тип SCD, и решает бизнес вместе с data stewards, а не IT.
- Type 1 перезаписывает значение: это просто, но история теряется, а агрегаты и кубы нужно пересчитывать.
- Type 2 добавляет строку с новым surrogate key и точно делит историю, поэтому это основной способ и самый безопасный, если бизнес не уверен.
- Type 3 и Type 4 решают особые случаи: Type 3 хранит прежнее значение в колонке для крупных реорганизаций, Type 4 выносит быстро меняющиеся атрибуты в mini-dimension.
- Гибриды Type 5, 6 и 7 дают и исторический, и текущий взгляд, но усложняют модель.

## Ключевые термины

| Термин | Значение |
|---|---|
| `SCD` | Slowly changing dimension: способ хранить изменения атрибута dimension |
| `Purchase order line` | Строка заказа поставщику. Grain fact table заказов |
| `Fill rate` | Доля заказанного, которую поставщик реально поставил |
| Type 1 | Перезапись значения. Истории нет |
| Type 2 | Новая строка и новый surrogate key для новой версии |
| Type 3 | Новая колонка для прежнего значения |
| `Mini-dimension` | Маленькая dimension для быстро меняющихся атрибутов, значения в диапазонах |
| `Outrigger` | Ключ другой dimension внутри dimension |
| `Durable key` | Ключ сущности, который не меняется между версиями |
| `Row effective date`, `row expiration date` | Период, в который версия строки действует |

## Что это значит на практике

- По каждому атрибуту спросите бизнес: «История нужна?». Решают data stewards, а не IT.
- Если бизнес не уверен, берите Type 2. Из Type 2 можно сделать вид Type 1, обратно переходить трудно.
- Join fact с Type 2 dimension идёт по surrogate key. Даты нужны при загрузке: для позднего факта (late arriving) ищите версию dimension на дату события, а не берите последнюю.
- В `dbt` Type 2 делает `snapshot` со стратегиями `timestamp` или `check`. У текущей версии `dbt_valid_to` по умолчанию пустой. Книга советует вместо `NULL` ставить `9999-12-31`, поэтому заменяйте его в dimension-модели поверх snapshot.
- Считайте сущности по natural key или durable key, а не по surrogate key.
- Type 1 атрибут в Type 2 dimension обновляйте во всех строках сущности. Правило согласуйте с data stewards.
- После Type 1 перезаписи пересчитайте агрегаты и обработайте куб.
- Не сливайте заказы, приёмки и платежи в одну fact table, если у них разные источники, grain и dimensions.
- Для Type 7 таблицу текущих значений можно сделать как view над Type 2 dimension.

## Практика в DuckDB

Запустите `duckdb` в терминале или откройте [shell.duckdb.org](https://shell.duckdb.org). Блоки идут по порядку в одной сессии. Не пропускайте задания: каждое меняет таблицы для следующего.

### Шаг 1. Создаём схему и данные

```sql
CREATE MACRO key_to_date(k) AS strptime(k::VARCHAR, '%Y%m%d')::DATE;

CREATE TABLE dim_product AS
SELECT * FROM (VALUES (1, 'Болты М8'), (2, 'Гайки М8')) t(product_key, product_name);

-- tier = Type 2, region = Type 1
CREATE TABLE dim_vendor AS
SELECT * FROM (VALUES
    (1, 'V1', 'Acme', 'Silver', 'Запад',  DATE '2024-01-01', DATE '9999-12-31', true),
    (2, 'V2', 'Bolt', 'Gold',   'Восток', DATE '2024-01-01', DATE '9999-12-31', true)
) t(vendor_key, vendor_id, vendor_name, tier, region,
    row_effective_date, row_expiration_date, is_current);

-- срез из источника на 2024-03-01
CREATE TABLE stg_vendor AS
SELECT * FROM (VALUES
    ('V1', 'Acme', 'Gold', 'Центр'),   -- tier и region изменились
    ('V2', 'Bolt', 'Gold', 'Восток')
) t(vendor_id, vendor_name, tier, region);

-- grain: одна строка заказа. po_number и po_line_number - degenerate dimensions
CREATE TABLE fact_po_line AS
SELECT po_number, po_line_number,
       strftime(po_date, '%Y%m%d')::INT AS po_date_key,
       product_key, vendor_key, ordered_qty, ordered_amount
FROM (VALUES
    ('PO1', 1, DATE '2024-01-10', 1, 1, 100, 1000),
    ('PO1', 2, DATE '2024-01-10', 2, 1,  50,  400),
    ('PO2', 1, DATE '2024-02-05', 1, 2, 200, 3000)
) t(po_number, po_line_number, po_date, product_key, vendor_key, ordered_qty, ordered_amount);
```

### Задания

**1.** Type 2 через `MERGE`. Закройте текущую версию V1, у которой изменился `tier`. Потом вставьте новую версию. После этого загрузите три заказа за март и апрель (PO3–PO5, данные в решении) с поиском версии по дате.

<details>
<summary>Решение</summary>

```sql
-- 1) закрываем версию
MERGE INTO dim_vendor d
USING stg_vendor s
   ON d.vendor_id = s.vendor_id AND d.is_current
WHEN MATCHED AND d.tier <> s.tier THEN
    UPDATE SET row_expiration_date = DATE '2024-03-01', is_current = false;

-- 2) вставляем новую версию тем, у кого нет текущей строки
INSERT INTO dim_vendor
SELECT (SELECT max(vendor_key) FROM dim_vendor) + row_number() OVER (ORDER BY s.vendor_id),
       s.vendor_id, s.vendor_name, s.tier, s.region,
       DATE '2024-03-01', DATE '9999-12-31', true
FROM stg_vendor s
WHERE NOT EXISTS (
    SELECT 1 FROM dim_vendor d WHERE d.vendor_id = s.vendor_id AND d.is_current
);

-- 3) новые факты: версия на дату заказа
INSERT INTO fact_po_line
SELECT o.po_number, o.po_line_number,
       strftime(o.po_date, '%Y%m%d')::INT,
       o.product_key, v.vendor_key, o.ordered_qty, o.ordered_amount
FROM (VALUES
    ('PO3', 1, DATE '2024-03-12', 1, 'V1',  80,  800),
    ('PO4', 1, DATE '2024-04-03', 2, 'V2',  60,  900),
    ('PO5', 1, DATE '2024-04-20', 1, 'V1',  40,  420)
) o(po_number, po_line_number, po_date, product_key, vendor_id, ordered_qty, ordered_amount)
JOIN dim_vendor v
  ON v.vendor_id = o.vendor_id
 AND o.po_date >= v.row_effective_date
 AND o.po_date <  v.row_expiration_date;

SELECT vendor_key, vendor_id, tier, region, row_effective_date, is_current
FROM dim_vendor ORDER BY vendor_id, vendor_key;
```

У V1 теперь две версии. Заметьте: в старой строке region `Запад`, в новой `Центр`. Это несогласованность. Её исправит задание 4.
</details>

**2.** Две fact tables. Создайте `fact_po_receipt` (приёмки) на grain «одна приёмка строки заказа». Сравните заказанное и полученное по поставщику. Агрегируйте каждый fact отдельно.

<details>
<summary>Решение</summary>

```sql
CREATE TABLE fact_po_receipt AS
SELECT * FROM (VALUES
    ('PO1', 1, 20240120,  90),
    ('PO1', 1, 20240125,  10),   -- вторая поставка по той же строке
    ('PO1', 2, 20240122,  50),
    ('PO2', 1, 20240215, 150),
    ('PO3', 1, 20240320,  80),
    ('PO4', 1, 20240410,  30)
) t(po_number, po_line_number, receipt_date_key, received_qty);

WITH ordered AS (
    SELECT po_number, po_line_number, vendor_key,
           sum(ordered_qty) AS ordered_qty
    FROM fact_po_line GROUP BY ALL
), received AS (
    SELECT po_number, po_line_number, sum(received_qty) AS received_qty
    FROM fact_po_receipt GROUP BY ALL
)
SELECT v.vendor_id,
       sum(o.ordered_qty)                       AS ordered,
       sum(coalesce(r.received_qty, 0))         AS received,
       round(sum(coalesce(r.received_qty, 0)) * 100.0 / sum(o.ordered_qty), 1) AS fill_rate_pct
FROM ordered o
LEFT JOIN received r USING (po_number, po_line_number)
JOIN dim_vendor v USING (vendor_key)
GROUP BY v.vendor_id
ORDER BY v.vendor_id;
```

Fill rate — это отношение двух сумм. Мы не храним его в fact. Строка PO5 ещё не получена, поэтому нужен `LEFT JOIN`.
</details>

**3.** Type 6. Добавьте в `dim_vendor` колонку `current_tier` со значением из текущей версии. Покажите расходы по историческому `tier` и по `current_tier`.

<details>
<summary>Решение</summary>

```sql
ALTER TABLE dim_vendor ADD COLUMN current_tier VARCHAR;

UPDATE dim_vendor d
SET current_tier = c.tier
FROM dim_vendor c
WHERE c.vendor_id = d.vendor_id AND c.is_current;

SELECT v.tier AS tier_at_order, v.current_tier, sum(f.ordered_amount) AS spend
FROM fact_po_line f
JOIN dim_vendor v USING (vendor_key)
GROUP BY ALL
ORDER BY 1, 2;
```

Расходы на V1 до марта попадают в `Silver` по истории. По `current_tier` они все в `Gold`. Одна таблица отвечает на оба вопроса.
</details>

**4.** Type 1 внутри Type 2. Исправьте `region` у V1 во всех версиях, а не только в текущей. Проверьте, что у каждого vendor один region.

<details>
<summary>Решение</summary>

```sql
UPDATE dim_vendor d
SET region = s.region
FROM stg_vendor s
WHERE d.vendor_id = s.vendor_id
  AND d.region <> s.region;     -- без is_current: меняем все версии

SELECT vendor_id, count(DISTINCT region) AS regions
FROM dim_vendor
GROUP BY vendor_id
ORDER BY vendor_id;
```

Каждый vendor теперь имеет ровно один region. Type 1 атрибут нельзя обновлять только в текущей строке.
</details>

**5.** Type 4. У поставщика быстро меняется оценка надёжности. Вынесите её в mini-dimension с диапазонами. Привяжите каждый заказ к диапазону оценки на дату заказа. Используйте `ASOF JOIN`.

<details>
<summary>Решение</summary>

```sql
CREATE TABLE dim_score_band AS
SELECT * FROM (VALUES
    (1, 'Low',    0,  49),
    (2, 'Medium', 50, 79),
    (3, 'High',   80, 100)
) t(score_band_key, band_name, min_score, max_score);

CREATE TABLE stg_vendor_score AS
SELECT * FROM (VALUES
    ('V1', DATE '2024-01-01', 55),
    ('V1', DATE '2024-03-15', 80),
    ('V2', DATE '2024-01-01', 90),
    ('V2', DATE '2024-04-01', 40)
) t(vendor_id, score_date, score);

CREATE TABLE fact_po_line_scored AS
WITH po AS (
    SELECT f.*, v.vendor_id, key_to_date(f.po_date_key) AS po_date
    FROM fact_po_line f
    JOIN dim_vendor v USING (vendor_key)
)
SELECT po.po_number, po.po_line_number, po.vendor_key, b.score_band_key, po.ordered_amount
FROM po
ASOF JOIN stg_vendor_score s
  ON po.vendor_id = s.vendor_id AND po.po_date >= s.score_date
JOIN dim_score_band b ON s.score BETWEEN b.min_score AND b.max_score;

SELECT b.band_name, count(*) AS po_lines, sum(f.ordered_amount) AS spend
FROM fact_po_line_scored f
JOIN dim_score_band b USING (score_band_key)
GROUP BY b.band_name
ORDER BY min(b.min_score);
```

В fact лежит ключ диапазона на момент заказа. В `dim_vendor` не нужны новые строки при каждой смене оценки. Мы создали новую таблицу для наглядности. В реальной загрузке `score_band_key` — просто ещё одна колонка в `fact_po_line`.
</details>
