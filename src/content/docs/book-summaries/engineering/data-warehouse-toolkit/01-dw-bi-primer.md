**Главная мысль:** хранилище данных строят для бизнеса, а не для разработчиков. Оно должно быть простым и быстрым. Для этого авторы выбирают dimensional modeling: данные лежат в понятных `fact` и `dimension` таблицах на самом детальном `grain`, а все витрины делят общие `conformed dimensions`.

Первая глава задаёт словарь книги. Она отвечает на вопросы: зачем бизнесу DW/BI, что такое dimensional model и из каких частей состоит хранилище по Kimball. Предыдущей главы нет, общий план книги смотрите в [обзоре](/book-summaries/engineering/data-warehouse-toolkit/).

- Цели DW/BI и метафора издателя.
- `fact table`, `dimension table`, `star schema`, `OLAP cube`.
- Архитектура Kimball и её альтернативы: Inmon и hybrid.
- Пять мифов о dimensional modeling.
- Dimensional thinking за пределами схем и agile.

![Архитектура Kimball: источники, ETL system, presentation area и BI-приложения](/assets/data-warehouse-toolkit/ch01-kimball-architecture.png)

Читайте схему слева направо: данные идут из источников через `ETL system` (подготовка данных) в `presentation area` (витрины для бизнеса), а оттуда в отчёты и ad hoc SQL. Блоки `Clean` и `Conform` — это шаг transform. В книге front room — это presentation area вместе с BI-приложениями.

## Два мира: ввод данных и анализ

Книга говорит просто: в операционные системы данные кладут, из DW/BI системы их берут.

- Операционная система работает с одной записью за раз, повторяет одни и те же задачи и обычно не хранит историю: данные обновляются до текущего состояния.
- DW/BI система сжимает сотни или сотни тысяч транзакций в один ответ и хранит историю, иначе нельзя оценить динамику.

Авторы предупреждают о «псевдохранилищах»: это копия операционной системы на отдельном сервере. Она снимает нагрузку с источника, но не решает остальные различия, и бизнес остаётся недоволен удобством и скоростью.

## Цели DW/BI

Авторы выводят цели из жалоб руководителей: данных много, а добраться до них нельзя; на совещаниях спорят, чьи цифры верны. Получается семь требований:

1. **Данные доступны.** Структура и названия повторяют слова бизнеса, запросы быстрые. Авторы сводят это к двум словам: simple and fast.
2. **Данные согласованы.** Одинаковое название метрики значит одно и то же, разный смысл — разные названия.
3. **Система переживает изменения.** Новые вопросы и новые данные не ломают старые приложения.
4. **Данные приходят вовремя.** Для оперативных решений нужны часы или минуты, и бизнес с командой должны договориться, что значит «вовремя», когда нет времени на очистку.
5. **Данные защищены.** В хранилище лежит, что и кому компания продаёт и по какой цене.
6. **Хранилище — основа для решений.** Главный результат — решения. Старое название «decision support system» авторы считают самым точным.
7. **Бизнес принимает систему.** Хранилищем можно не пользоваться, поэтому без пользователей проект провален, даже при отличной технике.

Два последних требования самые важные и самые частые упущения. Поэтому от команды нужны и навыки администратора БД (DBA), и понимание бизнеса (MBA).

## Метафора издателя

Менеджер DW/BI похож на главного редактора журнала. Редактор изучает читателей, делает журнал привлекательным и держит их доверие. Менеджер DW/BI делает то же: понимает решения пользователей, выбирает надёжные данные, делает простые интерфейсы и одинаково называет данные по всей компании. Главная мысль: смотрите наружу, на пользователей, а не внутрь, на продукты и процессы. Технология только средство, поэтому её нет среди главных обязанностей менеджера.

## Введение в dimensional modeling

`Dimensional modeling` — предпочтительный способ показать аналитические данные: он даёт понятные бизнесу данные и быстрые запросы. Главный приём — простота. Руководитель говорит: «Мы продаём продукты на разных рынках и измеряем результат по времени». Проектировщик слышит продукт, рынок и время. Такой бизнес выглядит как куб с тремя рёбрами, а в его точках лежат замеры, например объём продаж.

`3NF` (нормализованная модель) убирает дубли и режет данные на сотни таблиц. Для операций это хорошо: insert или update затрагивает одно место. Для BI это слишком сложно: пользователь такую схему не запомнит, а оптимизатор БД не справляется с непредсказуемыми запросами. Обе модели можно нарисовать как ER-диаграмму, поэтому авторы называют 3NF «нормализованной моделью», а не «ER-моделью».

> Dimensional model хранит ту же информацию, что и нормализованная, но делает данные понятными, запросы быстрыми, а схему устойчивой к изменениям.

### Star schema и OLAP cube

В реляционной БД dimensional model называется `star schema`, в многомерной — `OLAP cube`. Логика общая, физика разная. Куб сам индексирует данные и считает агрегаты, поэтому запросы быстрее, но загрузка медленнее. Книга советует загружать atomic данные в star schema, а кубы наполнять из неё. Поэтому дальше техники описаны для star schema.

### Что учесть при OLAP cubes

- Главная причина брать OLAP — гибкая защита (закрыть детали, открыть итоги) и аналитика богаче SQL. Скорость сегодня менее важна: помогли in-memory и колоночные СУБД.
- Куб хорошо работает с `SCD` type 2, `transaction` и `periodic snapshot` fact tables. Другие типы SCD требуют пересчёта, а `accumulating snapshot` не поддерживается (главы [4](/book-summaries/engineering/data-warehouse-toolkit/04-inventory/) и [5](/book-summaries/engineering/data-warehouse-toolkit/05-procurement/)).

### Fact tables: замеры бизнес-процесса

`Fact table` хранит замеры (measurements) событий бизнес-процесса. Книга советует хранить данные одного процесса в одной dimensional model: замеры занимают больше всего места, и копировать их для каждого отдела нельзя.

Каждая строка — одно событие замера, например один товар в одной продаже. Уровень детализации строки называется `grain`. Все строки fact table должны иметь один grain, иначе суммы посчитаются дважды. Авторы называют соответствие «одно событие = одна строка» фундаментом dimensional modeling.

> **Пояснение:** `grain` — это ответ на вопрос «что значит одна строка?». Если в одной таблице лежат позиции заказа и итог заказа, сумма по таблице удвоится.

Самые полезные facts числовые и аддитивные, потому что BI-запрос берёт тысячи строк и складывает их:

- `additive`: суммируется по любой dimension. Пример: сумма продаж.
- `semi-additive`: нельзя суммировать по времени. Пример: остаток на счёте.
- `non-additive`: нельзя суммировать совсем. Пример: цена за единицу. Остаются счётчики и средние.

Текстовый fact встречается редко: обычно текст — это описание, и его место в dimension. Если по товару не было продаж, строку не добавляют: нули раздули бы таблицу. Fact tables разреженные, глубокие (много строк) и узкие (мало колонок), и занимают 90 % и более места dimensional model. По grain они бывают трёх видов: transaction (самый частый), periodic snapshot и accumulating snapshot (главы [3](/book-summaries/engineering/data-warehouse-toolkit/03-retail-sales/) и [4](/book-summaries/engineering/data-warehouse-toolkit/04-inventory/)).

У fact table два или больше foreign keys на primary keys dimensions. Если каждый ключ имеет пару в dimension, выполняется `referential integrity`: например, каждый `product_key` из `fact_sales` есть в `dim_product`. Собственный primary key обычно составной (`composite key`) из части foreign keys. Таблица с составным ключом — fact table, остальные — dimensions.

### Dimension tables: описательный контекст

`Dimension table` хранит текстовый контекст события: кто, что, где, когда, как и почему. Она широкая (50–100 атрибутов — обычное дело) и короче fact table. У каждой dimension один primary key. Пример: `dim_product` с ключом `product_key`, артикулом `SKU` (это `natural key`, то есть ключ из источника), названием, брендом, категорией и размером упаковки.

Атрибуты — главный источник фильтров, группировок и подписей отчёта. Поэтому, пишут авторы, хранилище «настолько хорошо, насколько хороши атрибуты». Книга советует:

- писать настоящие слова, а не аббревиатуры;
- заменять коды расшифровками и хранить их в dimension, а не в BI-приложениях;
- оставлять код рядом с описанием, если он нужен бизнесу;
- выносить смысл, зашитый в код, в отдельные атрибуты.

**Fact или атрибут?** Замер со многими значениями, который участвует в расчётах, — fact. Дискретное описание, которое почти не меняется и работает в фильтрах, — атрибут. Стандартная себестоимость выглядит как атрибут, но если она часто меняется, её можно сделать fact. Книга называет это решение редко трудным.

Иерархии (товар → бренд → категория) хранятся плоско, названия повторяются в каждой строке:

| product_key | product_name | brand | category |
|---|---|---|---|
| 1 | Порошок A | PowerClean | Бытовая химия |
| 2 | Порошок B | Zippy | Бытовая химия |
| 3 | Мыло | Zippy | Гигиена |

Авторы советуют не нормализовать такие иерархии. Вынос бренда и категории в справочники называется `snowflaking`. Dimensions намного меньше fact tables, поэтому экономия места почти не влияет на размер базы, и книга советует менять место на простоту.

### Fact и dimension вместе: star schema

Каждый бизнес-процесс представляет одна dimensional model: в центре fact table, вокруг dimension tables с контекстом, который был верен в момент события. Это называется star join. Преимущества:

- **Понятность.** Простая симметричная схема, в которой пользователи узнают свой бизнес.
- **Скорость.** Оптимизатор ограничивает проиндексированные dimensions, а потом проходит fact table за один проход.
- **Расширяемость.** Все dimensions равноправны, модель не привязана к типовым запросам.

Atomic данные дают больше всего разрезов, поэтому на них строят каждую fact table. Тогда можно без перезагрузки данных и без изменения старых результатов добавить новую dimension (с одним значением на строку fact), новый fact на том же grain или новый атрибут dimension. Подробнее в [главе 3](/book-summaries/engineering/data-warehouse-toolkit/03-retail-sales/).

В отчёте атрибуты dimensions дают фильтры и подписи, а fact table даёт числа.

```text
-- типичный запрос к star schema
SELECT s.district, p.brand, sum(f.sales_amount) AS sales_dollars
FROM fact_sales f
JOIN dim_store s   USING (store_key)
JOIN dim_product p USING (product_key)
JOIN dim_date d    USING (date_key)
WHERE d.month_name = 'June'
GROUP BY s.district, p.brand;
```

Атрибуты и агрегат идут в `SELECT`, таблицы связаны в `FROM`, фильтр стоит в `WHERE`, агрегация задана в `GROUP BY`.

## Архитектура Kimball

В книге четыре отдельных компонента, и их роли нельзя путать. Back room — это `ETL system`, front room — это presentation area и BI-приложения.

| Компонент | Что в нём | Кто ходит |
|---|---|---|
| Source | Операционные системы | Операционные пользователи |
| ETL system | Extract, transform, load | Только команда ETL |
| Presentation area | Dimensional models | Бизнес и BI-инструменты |
| BI-приложения | Отчёты, дашборды, ad hoc SQL | Бизнес |

### Operational source systems

Это системы, где фиксируются транзакции. Для хранилища они внешние: содержимым и форматом управлять почти нельзя. Главные цели — скорость и доступность, запросы узкие, по одной записи. Истории мало, и хранилище снимает с них эту задачу.

### ETL system

`ETL system` — рабочая область, структуры данных и процессы между источниками и presentation area ([глава 19](/book-summaries/engineering/data-warehouse-toolkit/19-etl-subsystems/)).

- **Extract.** Прочитать источник и скопировать нужные данные. С этого момента они принадлежат хранилищу.
- **Transform.** Очистить (опечатки, пропуски, форматы), объединить источники, убрать дубли.
- **Load (deliver).** Собрать и загрузить dimension и fact tables. Больше работы с dimensions: `surrogate key` (искусственный ключ вместо ключа источника), расшифровки кодов, сплющивание 3NF. Fact tables большие, но готовятся просто.

Нужна ли в ETL нормализованная БД? Если источник уже в 3NF, это допустимо, но данные загружаются дважды, и растут время и бюджет. Некоторые проекты провалились: все силы ушли на нормализацию, а presentation area не построили.

> Нормализованная БД для ETL допустима, но это не цель. Бизнесу она должна быть закрыта.

### Presentation area

`Presentation area` — место, где данные доступны для прямых запросов. ETL закрыт, поэтому для бизнеса presentation area и есть хранилище. Авторы формулируют четыре правила:

1. **Dimensional.** Данные в star schema или OLAP cube.
2. **Atomic.** Детальные данные нужны для непредсказуемых запросов. Агрегаты рядом ради скорости допустимы, но одни агрегаты нет. Нельзя держать atomic данные в 3NF, а в dimensional только итоги.
3. **По бизнес-процессам.** Модель строят по событию замера, а не по «отчёту дня» и не по отделам. Для продаж нужна одна fact table, а не отдельные базы для продаж, маркетинга и финансов.
4. **Conformed dimensions.** Все модели используют общие dimensions. Это основа `enterprise data warehouse bus architecture` ([глава 4](/book-summaries/engineering/data-warehouse-toolkit/04-inventory/)). Без неё получаются изолированные «stovepipe» наборы данных, которые не стыкуются. Шина позволяет строить хранилище по частям, итерациями.

### BI-приложения

Это любой способ, которым бизнес использует presentation area. Все BI-приложения читают именно её. Это может быть ad hoc инструмент или data mining. Ad hoc инструментами эффективно пользуется малая часть людей, остальным нужны готовые шаблоны.

### Метафора ресторана

Авторы сравнивают DW/BI с рестораном: `ETL system` — кухня, presentation area и BI — обеденный зал, посетители — бизнес. Кухню проектируют заранее ради пропускной способности, стабильного качества и надёжности. Соусы готовят один раз на кухне, а не на столе. Так и в ETL: бизнес-правила применяют один раз профессионалы, а не каждый пользователь по-своему. Кухня закрыта для гостей, поэтому ETL закрыт для бизнеса.

> Правильная DW/BI среда переносит работу из front room в back room. Работа front room повторяется бизнесом снова и снова, а работа back room делается один раз.

Зал оценивают по еде, интерьеру, обслуживанию и цене. В DW/BI это качественные данные, удобство для пользователей, своевременная выдача и стоимость системы. Менеджер должен сам следить за удовлетворённостью: гости часто уходят молча.

## Альтернативные архитектуры DW/BI

Различия между подходами с годами смягчились, а dimensional modeling полезна в каждом. Для авторов архитектура — только средство, а главное — результат, который принимает бизнес.

### Independent data marts

Каждый отдел строит свою `data mart` (витрину) со своими правилами и названиями, и цифры отделов не сходятся. Подход распространён: он не требует координации и сначала быстрый и дешёвый. Потом растут дубли, споры и сверки. Авторы категорически не советуют его. Такие витрины часто используют dimensional modeling, но игнорируют atomic данные, процессы и conformed dimensions.

### Hub-and-spoke Corporate Information Factory (Inmon)

В `CIF` данные проходят ETL и попадают в нормализованное atomic хранилище в 3NF — `EDW` (Enterprise Data Warehouse). В CIF оно обязательно, из него наполняют витрины. Обе школы хотят интеграции: CIF ждёт её от нормализованного EDW, Kimball — от conformed dimensions.

> Нормализация не равна интеграции. Она создаёт таблицы для связей «многие к одному», а интеграция устраняет противоречия между источниками. Kimball решает противоречия без требования нормализации.

Витрины в CIF обычно dimensional, но строятся по отделам и содержат агрегаты, поэтому их трудно сверить с EDW. По мнению авторов, чистый CIF не работает как хранилище: atomic данные заперты в сложных таблицах, а отделы получают несовместимые витрины.

### Hybrid: hub-and-spoke плюс Kimball

В гибриде EDW в 3NF полностью закрыт для бизнеса и служит только источником для presentation area по Kimball. Книга считает hybrid уместным, если 3NF EDW уже есть, но не даёт быстрой и гибкой аналитики. С чистого листа он дороже: данные перемещаются несколько раз, atomic детали хранятся дважды.

## Мифы о dimensional modeling

Ложные представления мешают команде договориться о практиках.

### Миф 1: только для агрегатов

Вопросы бизнеса предсказать нельзя, поэтому нужны самые детальные данные: из них можно свернуть любой ответ. Агрегаты только дополняют детали ради скорости. Неверно и то, что в такой модели можно хранить мало истории: её объём задают требования бизнеса.

### Миф 2: только для отделов

Границы задают бизнес-процессы (заказы, счета, обращения), а не отделы: разным функциям нужны одни и те же метрики одного процесса. Несколько выгрузок из одного источника дают разные аналитические базы.

### Миф 3: не масштабируется

Fact tables с миллиардами строк — обычное дело, известны таблицы на 2 триллиона строк. Нормализованная и dimensional модели содержат одну и ту же информацию и отвечают на одни и те же вопросы, но с разной сложностью.

### Миф 4: только для предсказуемого использования

Модель строят вокруг процессов замера, а не вокруг списка «топ-10 отчётов»: список меняется, события замера стабильны. Ещё один миф: модель не гибка. На деле гибкость дают симметрия и самый детальный grain. Модель только с итогами упирается в «кирпичные стены». Авторы предупреждают: если вы заранее предположили вопрос, вы заранее агрегировали данные, и это может быть фатально.

### Миф 5: нельзя интегрировать

Можно, если модели следуют bus architecture. Conformed dimensions строят как централизованные мастер-данные в ETL и используют повторно. Нужно согласовать названия, значения и определения. Это тяжёлая работа, но её не обойти ни в нормализованной, ни в dimensional модели. Если витрины не следуют шине, виноват не dimensional modeling.

## Ещё причины думать dimensionally

Dimensional thinking нужен не только для схем:

- **Требования.** Слушайте про бизнес-процессы, а не про списки отчётов.
- **Объём проекта.** Один бизнес-процесс на проект, а не дашборд сразу по нескольким.
- **Приоритеты.** Единица работы в плане — бизнес-процесс. Оцените процессы по ценности и выполнимости и начните с лучших.
- **Архитектура.** Главный результат — `enterprise data warehouse bus matrix`: матрица процессов и общих dimensions ([глава 4](/book-summaries/engineering/data-warehouse-toolkit/04-inventory/)).
- **Data governance.** Начинайте с главных dimensions: дата, клиент, товар, сотрудник, счёт. Отвечают за них эксперты бизнеса.

Подробнее в главах [17](/book-summaries/engineering/data-warehouse-toolkit/17-lifecycle-overview/) и [18](/book-summaries/engineering/data-warehouse-toolkit/18-dimensional-modeling-process/).

## Agile и dimensional modeling

Agile режет работу на небольшие части, которые готовятся за недели. Он совпадает с Kimball по ценности для бизнеса, сотрудничеству и итерациям, но ему не хватает планирования и governance. Их даёт `bus matrix`.

Говорят, что в agile нет времени согласовывать conformed dimensions. Авторы возражают: именно они делают agile возможным, потому что новый процесс почти целиком сводится к новым fact tables. Без рамки команды строят аналитику «в вакууме» и получают изолированный stovepipe.

## Итоги главы

- Операционные системы и DW/BI решают разные задачи, поэтому копия источника не становится хранилищем.
- Хранилище должно быть простым и быстрым, согласованным, устойчивым к изменениям, защищённым и принятым бизнесом.
- Одна строка `fact table` описывает одно событие замера на единственном `grain`, а `dimension tables` дают текстовый контекст.
- Dimensions хранят иерархии плоско, без `snowflaking`, а качество атрибутов определяет качество аналитики.
- Star schema понятна бизнесу и легко расширяется, а atomic данные дают ей больше всего гибкости.
- Presentation area должна быть dimensional, atomic, организована по процессам и построена на conformed dimensions, а `ETL system` закрыта для бизнеса.
- Нормализация не равна интеграции: чистый CIF авторы считают неработоспособным, independent data marts дают несходящиеся цифры, а hybrid оправдан только при готовом 3NF EDW.
- Пять мифов опровергает одно правило: модель по процессу замера, на самом детальном grain и с общими dimensions.

## Ключевые термины

| Термин | Значение |
|---|---|
| Fact table | Числовые замеры событий бизнес-процесса |
| Grain | Что значит одна строка fact table |
| Dimension table | Описательный контекст события |
| Star schema / OLAP cube | Dimensional model в реляционной или многомерной БД |
| 3NF | Нормализованная модель: хороша для операций, плоха для BI |
| Atomic data | Самые детальные данные без агрегации |
| Additive / semi-additive / non-additive | Суммируется везде, не по времени, нигде |
| Snowflaking | Вынос иерархий dimension в справочники |
| ETL system | Back room: всё между источниками и presentation area |
| Presentation area | Dimensional модели, доступные бизнесу |
| Conformed dimension | Общая dimension, согласованная между моделями |
| Bus architecture / bus matrix | Модели на общих dimensions / матрица процессов и dimensions |
| EDW / CIF | Нормализованное atomic хранилище в подходе Inmon |

## Что это значит на практике

- Строим витрины по бизнес-процессам: заказы, платежи, звонки. Не по отделам.
- Всегда храним atomic данные. Агрегаты — отдельные таблицы сверху.
- Перед проектированием записываем grain одной фразой: «одна строка — это...». Разные grain в одной таблице не смешиваем.
- Названия колонок и значения в dimension должны быть понятны бизнесу. `Region`, а не `REG_CD`. Расшифровки кодов лежат в dimension.
- Текст не храним в fact table. Нули за периоды без активности не добавляем.
- Слой `marts` в `dbt` — это presentation area. Слой `staging` — часть back room, его закрываем от пользователей BI.
- Если две команды строят одну метрику по-разному, нужна общая conformed dimension и общее определение.

## Практика в DuckDB

Запустите `duckdb` в терминале или откройте [shell.duckdb.org](https://shell.duckdb.org). Блоки идут по порядку в одной сессии.

### Шаг 1. Создаём маленькую star schema

```sql
CREATE TABLE dim_date AS
SELECT
    strftime(d, '%Y%m%d')::INT AS date_key,
    d::DATE AS full_date,
    monthname(d) AS month_name,
    dayname(d) AS day_name
FROM generate_series(DATE '2024-06-01', DATE '2024-06-30', INTERVAL 1 DAY) t(d);

CREATE TABLE dim_product AS
SELECT * FROM (VALUES
    (1, 'SKU-1', 'Порошок A',  'PowerClean', 'Бытовая химия'),
    (2, 'SKU-2', 'Порошок B',  'Zippy',      'Бытовая химия'),
    (3, 'SKU-3', 'Мыло',       'Zippy',      'Гигиена'),
    (4, 'SKU-4', 'Шампунь',    'Clean Fast', 'Гигиена')
) t(product_key, sku, product_name, brand, category);

CREATE TABLE dim_store AS
SELECT * FROM (VALUES
    (1, 'Магазин 1', 'Atherton', 'Запад'),
    (2, 'Магазин 2', 'Belmont',  'Запад'),
    (3, 'Магазин 3', 'Camden',   'Восток')
) t(store_key, store_name, district, region);

-- grain: одна позиция в чеке
CREATE TABLE fact_sales AS
SELECT
    strftime(DATE '2024-06-01' + (i % 30)::INT, '%Y%m%d')::INT AS date_key,
    1 + i % 4 AS product_key,
    1 + i % 3 AS store_key,
    'T' || lpad((i // 3)::VARCHAR, 4, '0') AS ticket_number,
    1 + i % 3 AS sales_units,
    (1 + i % 3) * (10 + 5 * (1 + i % 4)) AS sales_amount
FROM range(0, 240) t(i);

SELECT count(*) AS fact_rows FROM fact_sales;
```

### Задания

**1.** Отчёт «Продажи за июнь» по району и бренду. Фильтры берите из dimension, числа из fact.

<details>
<summary>Решение</summary>

```sql
SELECT s.district, p.brand, sum(f.sales_amount) AS sales_dollars
FROM fact_sales f
JOIN dim_store s   USING (store_key)
JOIN dim_product p USING (product_key)
JOIN dim_date d    USING (date_key)
WHERE d.month_name = 'June'
GROUP BY ALL
ORDER BY s.district, sales_dollars DESC;
```
</details>

**2.** Atomic или агрегат. Создайте агрегат по бренду и месяцу. Проверьте, что сумма совпала с fact. Потом ответьте: можно ли из агрегата узнать продажи конкретного товара?

<details>
<summary>Решение</summary>

```sql
CREATE TABLE agg_sales_brand_month AS
SELECT d.month_name, p.brand, sum(f.sales_amount) AS sales_amount
FROM fact_sales f
JOIN dim_product p USING (product_key)
JOIN dim_date d USING (date_key)
GROUP BY ALL;

-- обе суммы равны
SELECT (SELECT sum(sales_amount) FROM fact_sales)         AS atomic_total,
       (SELECT sum(sales_amount) FROM agg_sales_brand_month) AS agg_total;
```

Нет, товар из агрегата не достать. В агрегате остались только бренд и месяц. Atomic fact отвечает на любой вопрос, агрегат — только на заранее заданные.
</details>

**3.** Graceful extension. Добавьте в `dim_product` новый атрибут `is_premium`. Потом сгруппируйте продажи по нему. Fact не меняйте.

<details>
<summary>Решение</summary>

```sql
ALTER TABLE dim_product ADD COLUMN is_premium BOOLEAN;
UPDATE dim_product SET is_premium = (brand = 'PowerClean');

SELECT p.is_premium, sum(f.sales_amount) AS sales_amount
FROM fact_sales f
JOIN dim_product p USING (product_key)
GROUP BY p.is_premium;
```

Старые запросы работают как раньше. Данные не перезагружали.
</details>

**4.** Conformed dimensions и drill across. Создайте таблицу `fact_forecast` с grain «магазин × товар × неделя» (4 недели июня). Сравните план и факт по магазину. Агрегируйте каждый fact отдельно, потом соедините по общим ключам.

<details>
<summary>Решение</summary>

```sql
CREATE TABLE fact_forecast AS
SELECT s.store_key, p.product_key, w.week_no,
       75 * p.product_key AS forecast_amount
FROM dim_store s CROSS JOIN dim_product p CROSS JOIN range(1, 5) w(week_no);

WITH actual AS (
    SELECT store_key, product_key, sum(sales_amount) AS actual_amount
    FROM fact_sales GROUP BY ALL
), plan AS (
    SELECT store_key, product_key, sum(forecast_amount) AS forecast_amount
    FROM fact_forecast GROUP BY ALL
)
SELECT s.store_name,
       sum(a.actual_amount)   AS actual,
       sum(pl.forecast_amount) AS forecast,
       round(sum(a.actual_amount) / sum(pl.forecast_amount), 2) AS actual_to_forecast
FROM actual a
JOIN plan pl USING (store_key, product_key)
JOIN dim_store s USING (store_key)
GROUP BY s.store_name
ORDER BY s.store_name;
```
</details>

**5.** Ловушка. Соедините два fact напрямую и покажите, что суммы раздуваются. Затем объясните, почему drill across из задания 4 правильный.

<details>
<summary>Решение</summary>

```sql
-- неверно: каждая строка sales повторяется 4 раза, по числу недель плана
SELECT sum(f.sales_amount) AS wrong_sales
FROM fact_sales f
JOIN fact_forecast fc USING (store_key, product_key);

SELECT sum(sales_amount) AS right_sales FROM fact_sales;
```

Прямая join двух fact даёт fan-out. Строка продаж размножается на каждую недельную строку плана. Поэтому сначала приводим fact к общему grain, потом соединяем.
</details>
