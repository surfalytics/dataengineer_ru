## Чистые DAG

### Стиль кода

Первый шаг: общий стиль на всю команду, например PEP 8 или Google Python Style Guide.

Проверять стиль помогают инструменты:

- **Static checkers** (`Pylint`, `Flake8`) читают код и сообщают о нарушениях.
- **Formatters** (`Black`, `YAPF`) сами переписывают код в единый вид. У `Black` есть режим `--check`: он только сообщает, что изменил бы.
- `Ruff` объединяет linter и formatter. Он написан на Rust, поэтому быстрее заменённых инструментов. Настройки похожи на `Flake8` и `Black`, так что перейти легко. Он также умеет правила для Airflow, например проверку, что имя переменной совпадает с `task_id`.


### Единый стиль Airflow

Один результат в Airflow получают разными способами. Авторы советуют выбрать один способ и не менять его.

| Что | Варианты |
|---|---|
| Определение DAG | `with DAG(...)`, `DAG(...)` с `dag=`, декоратор `@dag` (Taskflow) |
| Зависимости | `>>`, `<<`, `[a] >> b`, `set_upstream`, `set_downstream` |

С Taskflow способ зависимостей уже задан самим API. Смешивать записи зависимостей в одном DAG не стоит: `a >> b`, потом `c << b`, потом `set_upstream` читать тяжело.

### Секреты в одном месте

Airflow хранит credentials в metastore, в `connections`. Авторы видели много DAG с ключами прямо в коде или в файлах рядом.

Для своего Python-кода берите connection тем же путём, что и встроенные operators: `BaseHook.get_connection(conn_id)`. Тогда все секреты лежат и защищаются в одном месте.

Если секреты лежат в Kubernetes secrets или в cloud vault, подключите `secrets backend`: секреты остаются в менеджере, а DAG получают их через Airflow.

### Конфигурация

Для параметров (пути, имена таблиц) есть много мест: переменные в DAG, YAML, INI, JSON, переменные окружения, Python-модули, `Airflow Variables` в metastore. Авторы не выбирают лучшее: нужен один подход везде.

- Параметры, общие для DAG, держите в одном месте. Это принцип DRY: поменяли в одном файле, нигде не забыли.
- Секреты в конфигурационных файлах не храните. Эти файлы лежат открытым текстом.
- Помните, где грузится конфиг. Файл, прочитанный на уровне DAG, читает scheduler или DAG processor. Файл, прочитанный внутри task, читает worker. Файловые системы у них могут быть разные, и результат будет неверным. Лучше общее хранилище, доступное всем компонентам.

### Не считайте в определении DAG

Airflow должен выполнить Python-файл, чтобы получить DAG. Он перечитывает файл примерно каждые 30 секунд (зависит от настроек), чтобы подхватить правки. Всё, что стоит вне tasks, выполняется при каждом чтении.

Тяжёлое вычисление там блокирует весь парсинг. Авторы называют это `computation creep`: ошибка подкрадывается незаметно. Читать маленький файл с диска не страшно. Грузить данные из облака или БД каждые 30 секунд плохо. Частый случай: `Variable.get()` или `BaseHook.get_connection()` в теле файла. Они бьют по БД при каждом парсинге.

Решение одно: перенесите вызов внутрь функции task. Тогда он идёт один раз, при запуске ([ch12_light_task.py](https://github.com/surfalytics/dataengineer.ru/tree/main/scripts/airflow-code/ch12_light_task.py)).

```python
from airflow.sdk import BaseHook, task


@task
def call_api():
    conn = BaseHook.get_connection("my_api")  # БД читаем при запуске task, а не при парсинге
    return conn.host
```

### Фабрики

Часто вы пишете много похожих DAG: те же шаги, разные пути и преобразования. Тогда пишут `factory function`. Она принимает конфиг и создаёт задачи или целый DAG, как фабрика.

Бывают фабрики задач и фабрики DAG. Фабрика задач возвращает первую и последнюю task цепочки, чтобы подключить её к графу. Если делать несколько DAG из одного файла, у каждого должно быть своё имя в `globals()`. Иначе Airflow увидит только последний DAG из цикла.

Авторы советуют осторожность: обычно один файл на один DAG. Зато фабрика вместе с YAML позволяет людям без знания Airflow настраивать ETL простыми файлами.

### Task groups

В DAG из фабрики быстро становится слишком много tasks. `TaskGroup` складывает связанные tasks в один узел интерфейса. Его раскрывают кликом. Группы можно вкладывать друг в друга.

В примере DAG из главы 6 задачи погоды и продаж сворачиваются в две группы. Сложность скрыта, но видна, когда нужна.

### Явное расписание

Расписание можно задать строкой (`@daily`, cron) или классом timetable. Строка опасна по двум причинам:

- Её смысл зависит от настроек экземпляра: `create_cron_data_intervals` и `create_delta_data_intervals`. На двух установках `@daily` может дать разное.
- По умолчанию в Airflow 2 работали intervals, в Airflow 3 работают точки во времени.

Авторы настоятельно советуют всегда задавать класс timetable явно: `CronTriggerTimetable` или `CronDataIntervalTimetable`.

### Dynamic Task Mapping

Фабрика подходит, если структура DAG известна заранее. А если нет? Пример автора: каждый день приходят новые файлы, но число файлов разное. Например, API отзывов о фильмах отдаёт за сутки разное число записей.

Одна task на все записи не атомарна, её нельзя повторить для одной записи. И параллельно её не выполнить. `Dynamic Task Mapping` решает проблему: структура DAG меняется под данные каждого запуска. В одном run будет 3 экземпляра task, в другом 300.

У каждого operator два метода:

- `expand()` получает значения, по которым надо размножить. Для каждого элемента создаётся своя task.
- `partial()` получает параметры, одинаковые для всех экземпляров, например `task_id`.

С Taskflow запись чище, потому что XCom скрыт: `print_rating.expand(rating=fetch_ratings())`. В классическом синтаксисе каждый элемент пришлось бы заворачивать в список из-за XCom. Можно размножать и `task_group`.

![Dynamic Task Mapping: expand создаёт по задаче на каждый элемент списка](/assets/data-pipelines-with-apache-airflow/ch12-dynamic-mapping.png)

В grid view такая task помечена `[]`. Под ней видны экземпляры с `map index`, в них можно заглянуть.

## Воспроизводимые задачи

Задачу надо уметь запустить снова в другое время и получить тот же результат. Для этого нужны три свойства.

### Идемпотентность

Задача `idempotent`, если повтор даёт тот же итог. Повторы обычны. Вы меняете код и перезапускаете runs. Или Airflow сам делает retry после сбоя, хотя задача уже что-то записала.

Обычно идемпотентность дают так: результат перезаписывают, а не дописывают. Побочные эффекты (например, уведомления) тоже обдумайте. Их лучше сократить.

### Детерминизм

Задача `deterministic`, если для одного входа выдаёт один выход. Источники недетерминизма:

- неявный порядок: в dict, или строки из БД без `ORDER BY`;
- внешнее состояние: случайные значения, глобальные переменные, файлы на диске, которых нет во входе;
- параллельная обработка без явной сортировки результата;
- race conditions в многопоточном коде;
- неверная обработка исключений.

Лекарство простое: думать об источниках недетерминизма, явно сортировать, фиксировать seed.

> **Пояснение:** порядок элементов в set зависит от hash seed процесса. Скрипт запускает один и тот же код с двумя seed.

```text
PYTHONHASHSEED=1
без sort: ['clicks', 'orders', 'events', 'refunds', 'users']
с sorted: ['clicks', 'events', 'orders', 'refunds', 'users']
PYTHONHASHSEED=2
без sort: ['refunds', 'events', 'clicks', 'orders', 'users']
с sorted: ['clicks', 'events', 'orders', 'refunds', 'users']
random с фиксированным seed даёт одни и те же числа:
  seed=42: [82, 15, 4]
  seed=42: [82, 15, 4]
```

Без `sorted` порядок плавает. Скрипт: [ch12_deterministic.py](https://github.com/surfalytics/dataengineer.ru/tree/main/scripts/airflow-code/ch12_deterministic.py).

### Функциональный подход

Можно писать задачи как чистые функции из функционального программирования: результат зависит только от входа, побочных эффектов нет. Такие функции обычно и идемпотентны, и детерминированы. Идею переносят на данные и называют `functional data engineering`. Введение в неё написал Maxime Beauchemin, один из авторов Airflow.

## Эффективная работа с данными

### Меньше данных

Лучший способ работать быстро: брать только нужные данные. Проверьте, нужны ли все источники. Выбросьте лишние строки и колонки. Ранние агрегаты сильно уменьшают промежуточные наборы.

Пример: нужны месячные продажи по группе клиентов. Можно соединить обе большие таблицы и потом фильтровать и агрегировать. Лучше сначала агрегировать продажи и отфильтровать клиентов, а потом соединять малые наборы.

![Сначала join и фильтр или сначала фильтр и агрегат: второй вариант соединяет маленькие наборы](/assets/data-pipelines-with-apache-airflow/ch12-early-filter.png)

Многие инструменты делают это сами. Но проверьте, не обрабатывает ли DAG лишнее.

### Инкрементальная обработка

Если данные не сократить, но они привязаны ко времени, обрабатывайте их частями. Разбейте на партиции по времени и обрабатывайте партицию в каждом run. Тогда в run идёт только её объём, а результаты каждого запуска дописываются, и полный набор копится со временем.

Ошибка не требует пересчёта всего: перезапускают только упавший run. Если нужен анализ по всему набору, фильтры и агрегаты делают инкрементально, а большой анализ ведут по уменьшенному результату.

### Кэш промежуточных данных

DAG из атомарных шагов легко повторять. Но чтобы повторить один шаг, его входные данные должны быть под рукой. Иначе придётся перезапускать все предыдущие шаги, и смысл разбиения на tasks теряется. Поэтому сохраняйте результат каждого шага, например в cloud storage.

Минус: много версий больших наборов занимают много места. Компромисс: храните промежуточные данные ограниченное время.

Авторы советуют всегда хранить самую сырую версию, например то, что вы только что получили из API. Источники часто не хранят историю. С сырой копией можно пересчитать всё после правки кода или сбоя.

### Не храните данные на локальном диске

Для `BashOperator` и `PythonOperator` локальный диск worker под рукой, и это соблазн. Но Airflow запускает tasks на разных worker. Две зависимые tasks могут оказаться на машинах, которые не видят файлы друг друга.

Берите общее хранилище, одинаковое для всех workers: bucket в облаке или общую БД.

### Offload во внешние системы

Airflow задуман как оркестратор, а не как движок обработки. С маленькими данными можно загрузить их прямо на worker. С большими это заставит держать огромные машины. Маленький кластер Airflow даёт больше, если тяжёлую работу отдать системам, созданным для неё.

- Фильтры и агрегаты выполняйте в БД, а не в Python на worker.
- Большие вычисления отдавайте внешнему кластеру Spark.

Каждый инструмент должен делать то, что умеет лучше всего.

## Pools

На больших объёмах легко перегрузить кластер Airflow или внешние системы: общую БД, GPU, кластер Spark. Много tasks одновременно просят один ресурс, а он рассчитан на меньшую нагрузку.

`Pool` ограничивает такой доступ. В pool фиксированное число слотов (`slots`). Слот это право на доступ к ресурсу. Слоты задают степень параллелизма: pool на 10 слотов пускает не более 10 задач одновременно.

Pool создают в UI: Admin, Pools, Add Pool. Нужны имя, описание и число слотов. У флажка внизу формы особый смысл: считать ли `deferrable` tasks в слотах. Task привязывают к pool параметром `pool="имя"`. Перед запуском scheduler берёт свободный слот, и число свободных слотов падает на один. Если слотов нет, scheduler откладывает task, пока слот не освободится.

![Pool на 2 слота: две задачи идут, остальные ждут свободный слот](/assets/data-pipelines-with-apache-airflow/ch12-pool-slots.png)

## Итоги главы

- Единый стиль кода и единый способ записи DAG и зависимостей делают DAG понятными.
- Секреты хранят в connections или в secrets backend, а не в коде. Конфигурацию держат одним способом и в одном месте.
- Тяжёлые вычисления и обращения к БД выносят из тела файла DAG внутрь tasks, чтобы парсинг оставался быстрым.
- Фабрики убирают повторяющийся код. Task groups убирают визуальный шум. Расписание задают классом timetable явно.
- Dynamic Task Mapping создаёт tasks по данным запуска, когда число элементов неизвестно заранее.
- Задачи должны быть идемпотентными и детерминированными. Для этого помогают перезапись результата, явная сортировка, seed и функциональный стиль.
- Данных берут минимум, обрабатывают инкрементально, хранят промежуточные результаты в общем хранилище и оставляют сырую копию.
- Тяжёлую обработку отдают внешним системам.
- Pools с числом слотов защищают общие ресурсы от перегрузки.

## Ключевые термины

| Термин | Значение |
|---|---|
| `Idempotent` | Повтор даёт тот же итог |
| `Deterministic` | Тот же вход даёт тот же выход |
| `Factory function` | Функция, которая создаёт задачи или DAG по конфигу |
| `TaskGroup` | Группа задач в одном узле UI |
| `Dynamic Task Mapping` | Создание задач по данным во время запуска |
| `expand()` / `partial()` | Что размножить / что оставить постоянным |
| `Secrets backend` | Подключение внешнего хранилища секретов |
| `Pool` | Набор слотов, ограничивающий параллелизм |
| `Offloading` | Перенос тяжёлой работы во внешнюю систему |

## Что это значит на практике

- Подключите `ruff` и `black` в CI. Договоритесь о стиле DAG и зависимостей.
- Проверьте DAG на тяжёлый код вне задач. Особенно на запросы к БД и API.
- Секреты только в connections или secrets backend.
- Пишите задачи так, чтобы запись была `overwrite` по партиции. Тогда retry и backfill безопасны.
- Не пишите промежуточные файлы на диск worker. Берите общее хранилище.
- Ограничивайте нагрузку на хрупкие системы через pools.
- Задавайте timetable явно. Не полагайтесь на строку `@daily`.
- Для переменного числа файлов берите Dynamic Task Mapping, а не цикл внутри одной task.

## Практика

Проверено на Airflow 3.4.0: `DagBag` и `airflow dags test`. Подробности в [README.md](https://github.com/surfalytics/dataengineer.ru/tree/main/scripts/airflow-code/README.md).

Mapping в Taskflow и pool. Отзывы заменены функцией, сеть не нужна.

```python
@dag(
    dag_id="reviews_mapping",
    start_date=pendulum.datetime(2025, 1, 1, tz="UTC"),
    schedule=CronTriggerTimetable("0 16 * * *", timezone="UTC"),  # явный timetable, не "@daily"
    catchup=False,
)
def reviews_mapping():
    @task
    def fetch_ratings():
        # число отзывов в день разное: здесь возвращаем три
        return [
            {"movie": "Alpha", "rating": 4.5},
            {"movie": "Beta", "rating": 3.0},
            {"movie": "Gamma", "rating": 5.0},
        ]

    @task(pool="default_pool")  # pool ограничивает число одновременных задач
    def print_rating(rating):
        print(f"MAPPED movie={rating['movie']} rating={rating['rating']}")

    print_rating.expand(rating=fetch_ratings())


reviews_mapping()
```

Запуск `airflow dags test reviews_mapping 2025-01-02` завершился успешно. В логе три экземпляра `print_rating`, по одному на отзыв:

```text
MAPPED movie=Alpha rating=4.5
MAPPED movie=Beta rating=3.0
MAPPED movie=Gamma rating=5.0
```

Полный файл: [ch12_mapping_dag.py](https://github.com/surfalytics/dataengineer.ru/tree/main/scripts/airflow-code/ch12_mapping_dag.py). Фабрики и task groups в [ch12_factory_dag.py](https://github.com/surfalytics/dataengineer.ru/tree/main/scripts/airflow-code/ch12_factory_dag.py). Проверка структуры:

```text
ошибки импорта: нет
factory_customers -> ['fetch_customers', 'preprocess_customers']
factory_sales -> ['fetch_sales', 'preprocess_sales']
grouped -> ['customers.fetch_customers', 'customers.preprocess_customers', 'sales.fetch_sales', 'sales.preprocess_sales']
reviews_mapping -> ['fetch_ratings', 'print_rating']
print_rating mapped: True
pool: default_pool
timetable: CronTriggerTimetable
call_api это task: _TaskDecorator
```

Два DAG из одного файла получили разные имена. В `grouped` у tasks есть префикс группы. Скрипт: [ch12_check.py](https://github.com/surfalytics/dataengineer.ru/tree/main/scripts/airflow-code/ch12_check.py).

### Задания

**1. Уберите тяжёлый код.** В теле файла стоит `api_key = BaseHook.get_connection("my_api").password`. Что в этом плохо и как исправить?

<details>
<summary>Решение</summary>

Строка идёт при каждом парсинге файла, то есть примерно раз в 30 секунд, и каждый раз читает БД. Перенесите вызов внутрь функции task, как в первом примере главы. Тогда БД читается только при запуске task.

</details>

**2. Фабрика или mapping?** Нужно загружать 5 фиксированных таблиц. Нужно также обрабатывать файлы, число которых меняется каждый день. Что берёте для каждого случая?

<details>
<summary>Решение</summary>

Для 5 таблиц подходит фабрика: структура DAG известна заранее. Для файлов переменного числа нужен Dynamic Task Mapping: число task instances зависит от данных запуска.

</details>

**3. Pool на 3 слота.** В pool 3 слота. В нём 10 задач по 1 минуте. Сколько минимум минут займёт выполнение?

<details>
<summary>Решение</summary>

Четыре минуты: три волны по три задачи и одна волна из одной (10 = 3 + 3 + 3 + 1). Больше трёх задач одновременно не идут.

</details>
