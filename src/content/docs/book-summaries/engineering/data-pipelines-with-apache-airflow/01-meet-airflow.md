**Главная мысль:** pipeline лучше описывать как граф из небольших задач. Airflow запускает этот граф по расписанию, следит за порядком задач и помогает чинить сбои. Он создан для batch-pipelines, а не для потоков.

## О чём глава

Глава отвечает на три вопроса. Как представить data pipeline в виде графа задач? Где Airflow стоит среди других workflow managers? Когда Airflow подходит, а когда нет? Общую картину книги смотрите в [обзоре](/book-summaries/engineering/data-pipelines-with-apache-airflow/).

## Зачем нужны data pipelines

Объёмы данных выросли от мегабайтов в день до гигабайтов в минуту. Автор сравнивает Airflow с дирижёром оркестра: он не играет сам, а соединяет системы и координирует их работу: загрузку, преобразование, обучение модели.

## Data pipeline как граф

Пример из книги: дашборд погоды на неделю вперёд. У него три шага:

1. Взять прогноз из weather API.
2. Очистить данные, например перевести градусы Фаренгейта в Цельсий.
3. Отправить данные в дашборд.

Шаги нельзя поменять местами, поэтому порядок надо соблюдать явно.

### Рисуем pipeline как граф

Порядок становится виден, если нарисовать pipeline как граф. Каждая задача (`task`) это узел. Зависимость между tasks это стрелка. Стрелка от task 1 к task 2 значит: task 1 должна закончиться до старта task 2.

Такой граф называют `DAG` (directed acyclic graph). Слово `directed` значит, что у стрелок есть направление. Слово `acyclic` значит, что в графе нет циклов. Это важное свойство. Без него возникли бы циклические зависимости: task 2 ждёт task 3, а task 3 ждёт task 2. Такой граф невозможно выполнить, обе задачи стоят (`deadlock`).

![DAG без циклов и граф с циклом: во втором task 2 и task 3 ждут друг друга](/assets/data-pipelines-with-apache-airflow/ch01-dag-vs-cycle.png)

Циклические графы бывают, например в итеративных алгоритмах ML. Но Airflow использует отсутствие циклов, чтобы эффективно выполнять граф.

### Как выполняется граф

У DAG есть простой алгоритм выполнения:

1. Для каждой незавершённой задачи проверь upstream-задачи, то есть те, от которых она зависит.
2. Если все upstream готовы, поставь задачу в очередь.
3. Выполни очередь и отметь задачи готовыми.
4. Повтори с шага 1, пока не завершатся все задачи.

На погодном дашборде это три прохода. В первом в очередь идёт только `fetch`: у неё нет входящих стрелок. Во втором готова `fetch`, поэтому идёт `clean`. В третьем идёт `push`. Задач больше нет, pipeline завершён.

![Три прохода алгоритма для fetch, clean, push: какая задача готова, какая в очереди, какая ждёт](/assets/data-pipelines-with-apache-airflow/ch01-execution-loops.png)

### Граф или один скрипт

Зачем граф, если три шага можно записать в один скрипт? Автор берёт пример побольше. Владелец компании по продаже зонтов хочет модель машинного обучения, которая связывает продажи с погодой. Модель должна предсказывать спрос на зонты по прогнозу погоды на ближайшие недели. Нужны шаги:

1. Подготовить данные о продажах: загрузить из системы-источника и очистить.
2. Подготовить данные о погоде: загрузить прогноз из API и очистить.
3. Объединить два набора данных.
4. Обучить модель.
5. Развернуть модель, чтобы бизнес мог ей пользоваться.

![Граф pipeline для прогноза спроса на зонты: две независимые ветки и общий join](/assets/data-pipelines-with-apache-airflow/ch01-umbrella-dag.png)

Загрузка и очистка погоды и продаж не зависят друг от друга. На графе это две ветки без общих стрелок. Алгоритм ведёт их параллельно, ресурсы используются лучше, время работы короче.

Граф также разбивает pipeline на небольшие шаги. Один большой скрипт при сбое приходится перезапускать целиком. В графе перезапускают только упавшие tasks и те, что идут после них (`downstream`).

Запустим этот алгоритм на графе зонтов. Это чистый Python, без Airflow.

```python
"""Глава 1: алгоритм выполнения графа задач (без Airflow, чистый Python).
Граф из книги про зонты: две независимые ветки, join, train, deploy."""

# task -> список upstream-задач, от которых она зависит
graph = {
    "fetch_weather": [],
    "clean_weather": ["fetch_weather"],
    "fetch_sales": [],
    "clean_sales": ["fetch_sales"],
    "join_datasets": ["clean_weather", "clean_sales"],
    "train_model": ["join_datasets"],
    "deploy_model": ["train_model"],
}

done = set()
loop = 0
while len(done) < len(graph):
    loop += 1
    # шаг 1: открытые задачи, у которых все upstream готовы
    ready = sorted(t for t, up in graph.items() if t not in done and all(u in done for u in up))
    print(f"loop {loop}: в очередь идут {ready}")
    # шаг 2: выполняем очередь и отмечаем задачи готовыми
    done.update(ready)
print("все tasks выполнены")
```

```text
loop 1: в очередь идут ['fetch_sales', 'fetch_weather']
loop 2: в очередь идут ['clean_sales', 'clean_weather']
loop 3: в очередь идут ['join_datasets']
loop 4: в очередь идут ['train_model']
loop 5: в очередь идут ['deploy_model']
все tasks выполнены
```

Обе ветки идут парой в одном проходе. Скрипт [ch01_execute_graph.py](https://github.com/surfalytics/dataengineer.ru/tree/main/scripts/airflow-code/ch01_execute_graph.py) лежит в репозитории.

### Workflow managers

Выполнять граф зависимых задач нужно давно, поэтому инструментов много. Книга сравнивает их в таблице: Airflow, Argo, Azkaban, Dagster, Luigi, Make, NiFi, Oozie, Prefect, Temporal и другие. У всех одна основа: запустить pipeline из tasks с зависимостями. Главных различий два.

- **Как описан workflow.** Oozie берёт статичные XML-файлы. Workflow читается легко, но гибкости мало. Luigi и Airflow описывают workflow кодом. Это гибко, но код сложнее читать и тестировать, всё зависит от навыков автора.
- **Что встроено.** В Make и самописных скриптах нет расписания, нужен ещё `cron`. Другие инструменты дают расписание, мониторинг и веб-интерфейс сразу, склеивать несколько утилит не надо.

Автор советует сравнить возможности инструментов с вашими требованиями.

## Знакомство с Airflow

Airflow это open source платформа для разработки и мониторинга workflows.

### Pipeline как Python-код

Pipeline в Airflow это DAG из tasks. Его пишут в `DAG file`: это Python-скрипт с задачами, зависимостями и метаданными о том, как и когда запускать. Airflow 3 допускает и другие языки (для Go есть экспериментальный SDK), но основной остаётся Python, и вся книга идёт на нём.

Код даёт гибкость: можно создавать tasks по условию и даже целые DAG по конфигам. Об этом глава 12.

### Интеграции

Task может выполнить всё, что можно написать на Python. Поэтому есть много `providers`: пакетов для баз данных, big data и облачных сервисов. Они позволяют собрать pipeline из процессов в разных системах.

### Расписание и выполнение

Для DAG задают расписание: каждый час, день, неделю или в стиле `cron`. Вот минимальный DAG для погодного дашборда с ежедневным расписанием и двумя повторами при сбое.

```python
"""Глава 1: DAG погодного дашборда. Три tasks, расписание раз в день, 2 повтора при сбое."""
from datetime import timedelta

import pendulum
from airflow.providers.standard.operators.bash import BashOperator
from airflow.sdk import DAG

with DAG(
    dag_id="weather_board",
    start_date=pendulum.datetime(2025, 1, 1, tz="UTC"),
    schedule="@daily",  # расписание: один run на каждый день
    default_args={"retries": 2, "retry_delay": timedelta(minutes=5)},
):
    fetch = BashOperator(task_id="fetch", bash_command="echo fetch forecast")
    clean = BashOperator(task_id="clean", bash_command="echo clean forecast")
    push = BashOperator(task_id="push", bash_command="echo push to dashboard")

    fetch >> clean >> push
```

В Airflow пять основных компонентов.

| Компонент | Что делает |
|---|---|
| DAG processor | Читает DAG-файлы, парсит их и через API server сохраняет в metastore |
| Scheduler | Проверяет расписание. Если время пришло, ставит tasks в очередь на workers |
| Workers | Берут tasks из очереди и выполняют их: делают реальную работу |
| Triggerer | Следит за tasks, которые ждут внешнее условие, в фоне |
| API server | Веб-интерфейс для DAG и runs. Шлюз между компонентами и metastore |

`Metastore` это база метаданных: в ней хранятся DAG, runs и состояния tasks. Автор подчёркивает: любое обращение к базе идёт через API server.

Сердце Airflow, по словам автора, это scheduler. Он работает непрерывно и в цикле делает пять шагов:

1. DAG processor читает файлы и сохраняет в metastore tasks, зависимости и интервал расписания каждого DAG.
2. Scheduler проверяет, прошёл ли `schedule interval` с прошлой проверки. Если да, tasks DAG планируются к выполнению.
3. Для каждой запланированной task он смотрит, готовы ли upstream. Если да, task идёт в очередь.
4. Если task ждёт внешний ресурс, её можно отдать triggerer. Тогда worker свободен для готовых tasks.
5. Цикл идёт заново с шага 2.

Это тот же алгоритм из начала главы, плюс логика расписания. Из очереди tasks берёт пул workers. Они работают параллельно и передают результаты в metastore через API server, так что прогресс и логи видны в интерфейсе. О расписании подробнее в главах 3 и 4.

> **Пояснение:** `deferred task` ждёт внешнее событие, например файл. Она не держит worker: ожидание берёт triggerer.

### Мониторинг и сбои

Веб-интерфейс показывает обзор DAG, их результатов и здоровье компонентов. Вкладка Dags даёт список DAG с расписанием, статусом последнего run и временем следующего. Внутри DAG есть два главных вида.

- `Graph view` показывает tasks и зависимости, как схемы этой главы. Он удобен для структуры DAG и результатов отдельного run.
- `Grid view` показывает все текущие и прошлые runs. Столбец это один run, строка это история одной task. По словам автора, это самый мощный вид: видно, как DAG вёл себя со временем, и можно залезть в упавшую task.

При сбое Airflow по умолчанию повторяет task настраиваемое число раз, можно с паузой. Это помогает пережить случайные сбои. Если повторы не помогли, task получает статус failed, и Airflow может прислать уведомление. В grid view видна упавшая task и её логи. Там же есть `clear`: task и все её downstream tasks запустятся заново. Это удобно после правки кода.

### Incremental load и backfilling

Расписание Airflow не только запускает DAG в нужный момент, как `cron`. Оно ещё знает прошлый и следующий интервалы. Время делится на интервалы (день, неделя), и DAG запускается на каждый из них.

Это позволяет делать `incremental pipelines`. Каждый run обрабатывает данные только своего интервала, то есть `delta`, а не весь набор заново. На больших объёмах это экономит время и деньги.

С интервалами работает `backfilling`: запуск DAG за интервалы из прошлого. Так можно заполнить новый набор данных историей. А если очистить (`clear`) старые runs после правки кода, данные пересчитаются.

## Когда брать Airflow

### Причины выбрать

Airflow хорошо подходит для batch-oriented pipelines. Автор перечисляет случаи:

- сложные workflow по регулярному расписанию, например ежедневная загрузка;
- сложные workflow по событиям, а не по точному времени;
- работа с данными по интервалам времени;
- интеграции с разными системами, например PostgreSQL и BigQuery, которые можно расширять на Python;
- практики разработки: workflow это код, к нему применимы git и review;
- `backfilling`: пересчёт данных после правки кода.

Платформа открыта, поэтому нет vendor lock-in. Она давно в production, хорошо масштабируется, и у неё есть managed-версии.

### Причины не выбирать

Некоторые решения в основе Airflow подходят не для всех задач:

- **Streaming.** Airflow создан для регулярных и batch-задач. Поток кликов с сайта он хорошо обработает пачкой, но не по одному событию в реальном времени.
- **Команда без опыта в коде.** DAG на коде бывает сложно писать. Таким командам лучше инструмент с графическим интерфейсом, например Azure Data Factory, или со статичным описанием.
- **Большие сценарии.** Код DAG быстро усложняется. Нужна инженерная дисциплина: переиспользуемые DAG и модульные tasks, то есть `DRY` и `SRP`. Ещё в Airflow нет развитых data lineage и data versioning. Если они нужны, Airflow сочетают со специальными инструментами. Современные версии поддерживают OpenLineage.

Ещё один случай из итогов главы: Airflow не годится для pipelines, где структура DAG меняется изо дня в день.

## Итоги главы

- DAG это граф: узел это task, стрелка это зависимость. Так pipeline понятнее, его проще отлаживать и перезапускать, а независимые ветки идут параллельно.
- Граф не должен иметь циклов, иначе tasks ждут друг друга и pipeline не выполнить.
- Airflow пишут на Python: DAG file описывает tasks и зависимости, Airflow разбирает файл и строит DAG.
- Среди workflow managers Airflow выделяется для batch: код вместо статичных файлов, встроенные расписание, интерфейс и мониторинг.
- Пять компонентов: DAG processor, scheduler, workers, triggerer и API server. Все обращения к metastore идут через API server.
- Scheduler повторяет алгоритм выполнения графа и добавляет расписание. Сбои Airflow обрабатывает сам: retries, статус failed, `clear`.
- Интервалы расписания дают incremental load и backfilling.
- Airflow плохо подходит для streaming, для команд без кода и для DAG, у которых структура меняется каждый день.

## Ключевые термины

| Термин | Значение |
|---|---|
| `DAG` | Directed acyclic graph: граф tasks без циклов |
| `Task` | Один шаг pipeline, узел графа |
| `DAG file` | Python-файл, который описывает DAG |
| `DAG processor` | Компонент, который парсит DAG-файлы |
| `Scheduler` | Компонент, который решает, когда и что запускать |
| `Worker` | Процесс, который выполняет task |
| `Triggerer` | Компонент для deferred tasks, ждущих события |
| `API server` | Веб-интерфейс и шлюз к metastore |
| `Metastore` | База метаданных Airflow |
| `Provider` | Пакет интеграции с внешней системой |
| `Upstream` / `downstream` | Задачи до данной и после неё в графе |
| `Backfilling` | Запуск DAG за прошлые интервалы |
| `Incremental load` | Обработка только новых данных за интервал |

## Что это значит на практике

- Режьте pipeline на небольшие tasks. Тогда сбой стоит дешёвого перезапуска, а не полной перегрузки.
- Принимайте Airflow как orchestrator. Он запускает работу в warehouse, `dbt`, Spark. Тяжёлую обработку данных не делайте внутри worker.
- Для потоковых данных (Kafka и подобные) берите другие инструменты. Airflow можно использовать для batch-слоя вокруг них.
- Пусть каждый run берёт данные своего интервала. Тогда backfilling работает сам.
- Помните: DAG это код. Храните его в git и проверяйте через review.
- Независимые источники ставьте в отдельные ветки графа. Тогда они идут параллельно.
- При сбое сначала смотрите `grid view` и логи упавшей task. Потом делайте `clear`.
