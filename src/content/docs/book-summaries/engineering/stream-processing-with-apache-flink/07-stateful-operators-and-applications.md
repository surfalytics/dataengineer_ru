**Главная мысль:** состояние живёт дольше одного вызова функции и часто дольше одной версии приложения. Поэтому вместе с формулой вычисления разработчику приходится выбирать владельца данных, срок хранения, формат записи и способ восстановления после обновления.

## О чём глава

В главе «[Операторы на основе времени и оконные операторы](/book-summaries/engineering/stream-processing-with-apache-flink/06-time-and-window-operators/)» оконный оператор сам создавал и удалял данные для завершённых интервалов. В пользовательской функции правила хранения определяет разработчик. Авторы разбирают задачу обнаружения скачка температуры и показывают, почему одного поля в объекте функции для этого недостаточно. Затем они переходят от отдельного значения к жизненному циклу всего задания.

## Как реализовать функцию с состоянием

### Состояние по ключу

Для обнаружения резкого изменения нужны два последовательных показания одного прибора. Поток разделяют по идентификатору. В функции объявляют дескриптор с именем и типом хранимого значения. Через контекст выполнения Flink возвращает интерфейс `ValueState`. Один объект этого интерфейса обслуживает разные ключи: конкретное значение выбирается при обработке текущей записи. Поле самой функции содержит ссылку для доступа, а сохранением и восстановлением содержимого управляет Flink.

Чтение пустого значения надо отличать от чтения числа ноль. Нулевая температура допустима, а при первом появлении прибора сравнивать ещё не с чем. После проверки функция записывает текущую температуру, даже если предупреждения не было. Если обновлять состояние только при скачке, следующее показание будет сравниваться с устаревшим образцом.

> **Пояснение:** в проверенном Java-примере датчик A передаёт 20 и 32, а между его показаниями датчик B выдаёт 50. Порог равен десяти. Ниже приведён фрагмент метода обработки после разбиения потока по идентификатору.

```java
Integer previous = last.value();
if (previous != null && Math.abs(previous - reading.f1) > 10) {
    out.collect(reading.f0 + ": " + previous + " -> " + reading.f1);
}
last.update(reading.f1);
```

Вывод Flink 1.7.1:

```text
A: 20 -> 32
```

Значение B не вызвало ложного предупреждения, поскольку у этого ключа ещё не было истории. В книге для такой функции также показан сокращённый интерфейс Scala. Оба подхода опираются на одно свойство: среда предоставляет именно состояние текущего ключа.

### Состояние экземпляра в виде списка

Когда данные относятся к самому оператору, `keyBy` не требуется. В интерфейсе `ListCheckpointed` версии 1.7 функция хранит рабочие данные у себя и отдаёт их для снимка списком. При восстановлении ей передают набор прежних частей. Так можно представить позиции входных партиций или локальный накопленный счётчик. Если прежние экземпляры передали несколько частичных счётчиков, новый экземпляр должен правильно их объединить. Простой выбор первого элемента потеряет вклад остальных.

Формат списка определяет возможную детализацию перераспределения. Один большой элемент можно передать одному исполнителю. Несколько независимых элементов можно раздать нескольким. Если приложение предполагает, что прежний и новый экземпляры всегда совпадают один к одному, оно может успешно восстановиться с прежним числом исполнителей и дать неверный результат после изменения параллелизма.

### Общие правила для нескольких экземпляров

Для изменяемых правил обнаружения скачков есть два потока. Первый содержит измерения, второй — управляющие записи с новыми порогами. Управляющий поток рассылают всем экземплярам, которые проверяют датчики. Широковещательное состояние версии книги задаётся как отображение ключей в значения. При обработке управляющей записи функция может обновить таблицу, а при обычном измерении — прочитать применимое правило.

Поскольку копий несколько, независимый случайный выбор на каждом исполнителе приведёт к расхождению. Обновление должно давать совместимый результат на всех экземплярах, в том числе когда порядок получения независимых команд различается. Иначе после восстановления поведение будет зависеть от того, чья именно копия оказалась у конкретной задачи. Широковещательная таблица удобна для относительно небольшого набора правил: каждый экземпляр несёт стоимость её полного содержания.

### Снимки и уведомления

Интерфейс `CheckpointedFunction` даёт отдельные методы для инициализации состояния и подготовки снимка. В первом функция получает доступ к хранилищу состояния оператора, регистрирует дескрипторы и при восстановлении считывает прежние значения. Во втором переносит нужное содержимое в управляемую структуру к очередному снимку. В отличие от обычного поля объекта, зарегистрированную структуру Flink знает по имени и может включить в восстановление.

Локальное выполнение метода снимка ещё не сообщает, что весь граф прошёл эту границу. О завершении знает координатор. Оператор, которому важен такой сигнал, может реализовать `CheckpointListener`. Авторы отдельно предупреждают, что обратный вызов о завершении может быть пропущен. Строить корректность внешней записи на предположении, что каждому номеру снимка обязательно соответствует ровно один вызов, нельзя. Например, обработка более позднего подтверждения должна учитывать незавершённую работу, которая относилась к более ранней границе.

## Включение восстановления

Наличие `ValueState` обеспечивает хранение между вызовами функции, но для восстановления после отказа нужно включить периодическое создание снимков. Минимальный интервал задают при настройке среды исполнения. Интервал описывает частоту попыток, а фактическое время успешного снимка зависит от выравнивания, объёма данных и доступности хранилища. Если задания перезапускаются без единого завершённого снимка, восстановить ранее накопленное состояние из него невозможно.

Для локальной проверки можно начать с малого набора измерений. Рабочее задание требует долговечного места для снимков и входа, который допускает повторное чтение. Кроме того, внешние результаты должны выдерживать повторы. Значение во внутреннем счётчике и уведомление, уже отправленное пользователю, находятся по разные стороны этой границы.

## Как подготовить задание к будущим изменениям

### Стабильные идентификаторы

В снимке Flink связывает состояние с идентификатором оператора. Автоматический идентификатор зависит от структуры графа и может измениться при правке предыдущих шагов. Тогда новый граф перестанет узнавать старое состояние, хотя тип счётчика и смысл вычисления остались прежними. Задавайте долговечным операторам явный `uid` и сохраняйте его в последующих версиях. Имя состояния в дескрипторе тоже участвует в соответствии. Переименование `last-temperature` в другое имя выглядит как создание другой структуры.

### Максимальная степень параллелизма

Максимум определяет число групп ключей. При сохранении состояния ключи уже распределены по этим группам. Изменение обычного числа исполнителей переносит группы между подзадачами, а изменение их исходного числа меняет сам способ адресации. Планировать этот предел нужно до накопления большого объёма данных.

![Четыре группы ключей меняют распределение при переходе с двух до трёх подзадач](/assets/stream-processing-with-apache-flink/ch07-key-groups.png)

В книге приведены правила выбора максимума в этой версии. Для небольших заданий встречается значение 128, верхняя граница — 32 768 групп. Авторы показывают, как задать для среды максимум 512, а для конкретного оператора — 1024. Если в ближайшие годы одному оператору может понадобиться больше экземпляров, проверьте его собственное ограничение. Свободные ресурсы в кластере не позволят превысить уже зафиксированное число групп.

## Стоимость и надёжность хранения

### Выбор механизма хранения

В Flink 1.7 `MemoryStateBackend` хранит рабочие данные в куче JVM и отправляет снимки в память координатора. Он подходит для небольших проверок. У `FsStateBackend` рабочие значения также размещены в памяти исполнителя, но снимки пишутся в файловую систему. Поэтому большой объём долговечного хранилища не снимает ограничения на объём рабочей кучи. При отказе компьютера с единственной локальной копией снимок исчезнет одновременно с процессом.

`RocksDBStateBackend` хранит рабочие значения в локальной RocksDB и может оставлять часть данных на диске. Такой вариант подходит для состояния, которое не помещается в Java-кучу, и допускает инкрементные снимки. Цена — сериализация при доступе и нагрузка на локальный диск. Ускорение файлового хранилища снимков не обязательно ускорит частые обращения к рабочему значению. Эти затраты полезно измерять отдельно.

### Какая структура соответствует доступу

Если программе нужны значения по отдельным внутренним ключам, имеет значение выбор между `MapState` и обычной картой внутри `ValueState`. Во втором случае для изменения одного элемента может понадобиться извлечь и заново записать всю карту. То, что было приемлемо для маленького объекта в памяти, становится дорогим после переноса в RocksDB. Специализированные структуры позволяют системе работать с небольшими частями значения.

Так же следует различать список, который требуется перечислить целиком, и набор независимых записей, из которого обычно извлекают одну. Таким способом одну и ту же модель предметной области можно реализовать через несколько представлений, и различие видно в стоимости чтения, записи и создания снимков. Выбор делают по операциям, которые действительно выполняются при обработке каждой записи.

### Как удалить устаревшие данные

Задание может проработать месяцы, и ключ, который перестал появляться, не исчезнет только из-за отсутствия новых записей. Авторы предлагают связывать удаление с предметным правилом. Например, после длительного молчания датчика можно считать следующее показание первым. Можно сохранить момент ожидаемого удаления и зарегистрировать таймер. Когда приходит новая запись, срок продлевается. Обработчик прежнего таймера не должен стереть состояние, если после регистрации прибор успел прислать более свежее измерение.

Удаление меняет бизнес-результат. Если предыдущая температура забыта, первый скачок после долгого перерыва не будет обнаружен. Поэтому срок хранения нельзя выбирать исключительно по желаемому размеру снимка. Проверяйте одновременно стоимость диска и смысл отсутствующего значения для следующего события.

## Обновление приложения с сохранением состояния

Изменение чистого вычисления без изменения сохранённого формата обычно проще, чем смена типа уже записанного значения. Добавленное состояние начинает жизнь пустым. При удалении оператора старый снимок может содержать данные, которым новая программа не найдёт владельца. Для осознанного отказа от таких данных предусмотрен параметр, разрешающий оставить часть состояния невосстановленной. Его применение требует понимания того, что именно будет отброшено.

Сохранение прежнего имени само по себе не делает разные сериализаторы совместимыми. Если раньше значение сохранялось как строка, новый сериализатор числа не сможет прочитать старое двоичное представление. В версии 1.7 авторы отдельно выделяют поддерживаемую эволюцию схем Avro по правилам совместимости Avro. План обновления стоит проверять восстановлением на копии реального снимка. Тест, стартующий с пустого состояния, до проблемы старых байтов просто не дойдёт.

## Чтение состояния из внешнего приложения

Механизм `queryable state` позволяет опубликовать определённое состояние по имени и дать внешнему клиенту доступ к отдельному ключу. Клиент обращается к прокси, который выясняет у координатора расположение нужной группы ключей и направляет запрос рабочему процессу. При этом кэш расположения уменьшает число обращений к координатору. После перераспределения прежний адрес может устареть, поэтому запросу может понадобиться повтор.

Чтение удобно, когда внешней программе нужно узнать текущий показатель одного объекта. Оно не заменяет согласованный снимок всего графа. Пока клиент посылает второй запрос, поток продолжает изменять значения. Публикация должна быть настроена явно, а запрашивающий клиент использует совместимые типы ключа и значения. Это относится к интерфейсу описанной версии Flink.

![Внешний клиент обращается к прокси, который находит исполнителя нужной группы ключей](/assets/stream-processing-with-apache-flink/ch07-query.png)

## Итоги главы

- Имя и тип дескриптора задают доступ к зарегистрированному состоянию.
- Для каждого ключа доступно своё значение, даже когда ключи обслуживает один экземпляр.
- Рабочие данные и долговечный снимок могут находиться в разных хранилищах.
- Выбор максимальной степени параллелизма ограничивает дальнейшее масштабирование.
- Очистка требует правила для следующего события после истечения срока.
- Проверять совместимость обновления следует на ранее сохранённых данных.

## Ключевые термины

| Термин | Значение |
| --- | --- |
| `ValueState` | Одно управляемое значение для текущего ключа. |
| `uid` | Заданный приложением идентификатор оператора. |
| `state backend` | Компонент, который хранит рабочее состояние и записывает снимки. |

## Что это значит на практике

Перед первым производственным запуском запишите идентификаторы операторов, оцените число ключей и проверьте сценарий восстановления после изменения параллелизма. Для каждой структуры определите, какое событие позволяет её очистить и что произойдёт, если ключ появится снова.
