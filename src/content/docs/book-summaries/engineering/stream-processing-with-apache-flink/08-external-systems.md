**Главная мысль:** согласованный снимок Flink сам по себе не отменит запись в другой системе. Сквозная гарантия зависит от трёх звеньев: источник должен повторить вход, Flink — восстановить состояние, а получатель — безопасно пережить повтор или завершить согласованную транзакцию.

## О чём глава

В главе «[Операторы и приложения с учетом состояния](/book-summaries/engineering/stream-processing-with-apache-flink/07-stateful-operators-and-applications/)» сбой можно было исправить восстановлением сохранённого значения. Теперь представим, что оператор уже обновил таблицу банка, послал сообщение в Kafka или опубликовал файл. Авторы рассматривают, что увидит внешний читатель после перезапуска и какие обязанности для этого берут на себя готовые и пользовательские соединители.

## Гарантии согласованности приложения

### Идемпотентная запись

Предположим, результат для датчика A должен равняться 23. Повторное присваивание значения 23 по тому же первичному ключу даёт тот же конечный результат. Если вместо этого каждый раз прибавлять 23 к текущему значению, повтор изменит ответ. Идемпотентность относится к смыслу конкретной операции. Наличие первичного ключа ещё не превращает любое обновление в безопасное при повторе.

При повторном чтении нескольких событий читатель может временно увидеть более старое состояние. Если программа восстановилась и последовательно записала в таблицу вчерашнее значение, а вслед за ним сегодняшнее, конечный результат совпадёт. Однако между этими записями внешний запрос способен вернуть уже устаревшее показание. Для некоторых витрин это допустимо. Для уведомления, которое нельзя отозвать, нужна другая договорённость.

### Транзакционная запись

Другой подход накапливает изменения и публикует их после завершения снимка всего задания. В варианте с журналом упреждающей записи `sink` сохраняет результаты в состоянии Flink. После подтверждения снимка он отправляет накопившиеся записи во внешнюю систему. Такой подход требует места для буфера. Кроме того, если отказ случится между внешней записью и подтверждением того, что она уже выполнена, часть результатов может отправиться снова.

При двухфазной фиксации записи направляют во внешнюю транзакцию ещё до завершения снимка. На барьере приёмник подготавливает транзакцию и сохраняет идентификатор, необходимый для её дальнейшего завершения. Во время следующего интервала он уже пишет в другую транзакцию. После глобального подтверждения прежнюю транзакцию можно фиксировать. После перезапуска приёмник должен суметь завершить подготовленную транзакцию или безопасно обработать повторный запрос фиксации.

## Готовые соединители

### Kafka как источник

Топик состоит из партиций, а позиция внутри каждой партиции задаётся смещением. Flink распределяет партиции между экземплярами источника. Один экземпляр может читать несколько партиций. Если экземпляров больше, чем партиций, лишние читатели не создают дополнительного параллелизма чтения. При перераспределении важно передать новому владельцу и партицию, и соответствующую позицию.

Для первоначального запуска потребитель может начать с ранних, последних, сохранённых или явно заданных смещений. При восстановлении из согласованного снимка нужны позиции именно этого снимка. Иначе внутреннее состояние оператора будет описывать одну часть входа, а потребитель начнёт с другой. Смещения, опубликованные в Kafka для наблюдения за группой, и смещения, которые Flink использует для восстановления, поэтому решают разные задачи. Десериализатор превращает байты сообщений в записи DataStream. Если важны ключ или служебные сведения записи, нужен интерфейс, который их предоставляет.

![Источник сохраняет отдельную позицию чтения каждой из двух назначенных партиций](/assets/stream-processing-with-apache-flink/ch08-kafka-offsets.png)

### Kafka как получатель

Для `at-least-once` перед подтверждением снимка соединитель должен дождаться отправки ранее принятых записей и обнаружить ошибки производителя. Тогда потерю можно предотвратить, но после повторного чтения некоторые сообщения окажутся в топике ещё раз. Начиная с Kafka 0.11 транзакции позволили соединителю версии книги реализовать `exactly-once`. Получатель при этом должен читать только подтверждённые транзакции, задав `isolation.level=read_committed`.

Тайм-аут транзакции должен покрывать работу до фиксации и возможное восстановление. В книге у приёмника указан один час, а у брокера по умолчанию разрешены пятнадцать минут. Параметры производителя и брокера нужно согласовать. Если брокер уже отменил транзакцию, один только снимок Flink не заставит его подтвердить исчезнувшие записи. И наоборот, пока транзакция открыта, читатель с соответствующей изоляцией может ждать её завершения. Поэтому интервал снимков влияет и на задержку появления внешнего результата.

При выборе партиции учитывают соглашение с читателями. Один и тот же ключ часто требуется направлять в одну партицию для сохранения порядка по этому ключу. Фиксированное соответствие между экземпляром производителя и партицией удобно только при подходящей конфигурации параллелизма. Изменение числа отправителей может изменить раскладку. В книге показан отдельный интерфейс для пользовательского выбора партиции.

### Файлы и Cassandra

Файловый источник способен однократно прочитать известный набор файлов или периодически искать новые. Внутри системы обнаружение файлов и чтение назначенных частей — разные операции. Повторный просмотр каталога сам по себе ещё не делает изменяемый на месте файл безопасным журналом. Если старые байты перезаписаны, восстановление с прежней позиции может дать другой вход.

`StreamingFileSink` группирует выходные записи по каталогам и пишет части файла. Открытая часть принимает новые строки. После закрытия она ждёт фиксации, и лишь успешный снимок переводит её в готовый для чтения результат. Политика закрытия определяет размер и срок жизни частей. Слишком частая смена создаст множество маленьких файлов, а слишком редкая задержит появление готовой части. В главе отдельно разобраны построчное кодирование и форматы, записываемые блоками. Возможности конечной файловой системы тоже входят в условия корректности.

Соединитель Cassandra связывает поля записи с параметрами запроса CQL. Запись по тому же первичному ключу может обновить уже существующую строку. Однако прибавление к счётчику и присваивание полного значения обладают разной семантикой при повторе. Предлагаемый в книге журнал упреждающей записи помогает согласовать отправку с границами снимков. Выбор гарантии всё равно требует понимать, что именно выполнит Cassandra при повторном запросе.

## Собственный источник

Для простого источника Flink 1.7 предоставляет `SourceFunction` с методами запуска и отмены. Параллельный источник дополнительно должен решить, какую независимую часть входа читает каждый экземпляр. Кнопка отмены в панели бесполезна, если цикл функции никогда не проверит сигнал и не выйдет из блокирующего чтения. При доступе к внешней системе нужно предусмотреть способ освободить ресурс и остановиться.

Для воспроизводимого источника важно согласовать выдачу записи и продвижение сохранённой позиции. В примере последовательного генератора нельзя допустить снимок между этими действиями. Если значение уже отправилось, а позиция в снимке осталась прежней, после восстановления оно вернётся. Если в снимке успела продвинуться позиция, но запись ещё не ушла, она может потеряться. Версия API в книге предоставляет блокировку снимка через контекст источника. Под ней должны вместе происходить передача очередной записи и изменение соответствующего состояния. Долгое ожидание появления новых данных внутри этой критической секции задерживало бы снимки всего задания.

Источник может передавать записи с метками и сам выпускать `watermark`. Это особенно удобно, когда он знает состояние отдельных входных партиций. Если часть источников временно бездействует, оператору с несколькими входами нужна информация о простое. Иначе минимум входных времён может не продвигаться при продолжающемся потоке с остальных партиций.

## Собственный приёмник

### Запись через JDBC

Книжный приёмник открывает соединение с базой при инициализации, повторно использует подготовленные выражения и освобождает ресурсы при закрытии. Правильность определяется самим SQL. Обновить температуру по идентификатору и вставить строку при отсутствии такого идентификатора — способ реализовать присваивание полного значения. В многопоточном приложении нужно отдельно решить, как конкурентные писатели делят ключи либо пользуются атомарной операцией базы.

> **Пояснение:** воспроизводимый пример использует один экземпляр приёмника и Derby 10.14.2.0. Он передаёт последовательность A=20, A=23, A=23 и читает таблицу уже после завершения задания. Так можно проверить эффект повторной команды отдельно от отказа кластера.

```java
update.setInt(1, reading.f1);
update.setString(2, reading.f0);
if (update.executeUpdate() == 0) {
    insert.setInt(1, reading.f1);
    insert.setString(2, reading.f0);
    insert.executeUpdate();
}
```

Проверенный результат:

```text
A 23
```

### Когда нужна транзакция

`GenericWriteAheadSink` сохраняет ожидающие записи до подтверждения снимка. Если процесс успел отправить строки и упал до надёжной отметки об успешной отправке, восстановление может повторить эту работу. Поэтому такой приёмник особенно удобен, когда внешняя операция допускает повтор. Отметка о завершении и внешний эффект должны рассматриваться вместе.

`TwoPhaseCommitSinkFunction` разделяет открытие транзакции, запись, подготовку, фиксацию и отмену. Пример с файлами сначала пишет во временное место. При подготовке поток закрывают, а после подтверждения снимка готовое содержимое становится доступно по конечному пути. Для такой реализации нужно хранилище с атомарной публикацией готового файла. Простая замена переименования на последовательность «скопировать, затем удалить» меняет возможные результаты при сбое.

## Асинхронный доступ к внешним данным

Если для каждого датчика нужно узнать комнату установки, последовательное ожидание ответа базы оставляет поток исполнения без работы. Асинхронная функция передаёт запрос клиенту, возвращает управление Flink и позже завершает результат через обратный вызов. Можно ограничить число одновременно ожидающих запросов и задать тайм-аут. Иначе временное замедление базы превратится в неограниченный рост очереди внутри приложения.

Режим сохранения порядка выдаёт результаты в порядке входа. Тогда один медленный запрос задерживает уже готовые ответы за ним. Режим без сохранения порядка может выдавать быстрые ответы раньше. При работе со временем события проходящие `watermark` всё же накладывают границы на такое переупорядочение. Обещание асинхронности также нельзя выполнить простым вызовом блокирующего JDBC-метода в потоке оператора. В примере книги блокирующую работу выносят отдельно. Следует учитывать ёмкость пула и способность внешней системы обслуживать параллельные обращения.

## Практика в DuckDB

> **Пояснение:** сравните журнал событий с таблицей последних значений. Первая операция сохраняет каждую доставку, вторая повторно присваивает значение по первичному ключу. Этот опыт проверяет смысл SQL-записи. Сам протокол снимков выполнял бы Flink.

```sql
CREATE TABLE deliveries(sensor VARCHAR, temp INTEGER);
INSERT INTO deliveries VALUES ('A', 20), ('A', 23), ('A', 23);
SELECT count(*) AS deliveries, count(DISTINCT temp) AS different_values FROM deliveries;
```

```text
3 | 2
```

```sql
CREATE TABLE latest(sensor VARCHAR PRIMARY KEY, temp INTEGER);
INSERT INTO latest VALUES ('A', 20);
INSERT INTO latest VALUES ('A', 23) ON CONFLICT(sensor) DO UPDATE SET temp = excluded.temp;
INSERT INTO latest VALUES ('A', 23) ON CONFLICT(sensor) DO UPDATE SET temp = excluded.temp;
SELECT sensor, temp FROM latest;
```

```text
A | 23
```

## Итоги главы

- Позиция источника должна восстанавливать тот же вход, которому соответствует состояние.
- Идемпотентность зависит от конкретной операции над внешними данными.
- Подготовленная транзакция должна пережить восстановление задания.
- Читатель Kafka выбирает, допускает ли он ещё не подтверждённые сообщения.
- Готовый файл можно публиковать только при выполнении требований к хранилищу.
- Асинхронный доступ ограничивают числом запросов и временем ожидания.

## Ключевые термины

| Термин | Значение |
| --- | --- |
| Сквозная гарантия | Свойство наблюдаемого результата, включая внешнего получателя. |
| Идемпотентная запись | Повтор той же операции оставляет тот же конечный результат. |
| Двухфазная фиксация | Подготовка записи и её окончательная публикация разделены подтверждением. |
