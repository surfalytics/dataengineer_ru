**Главная мысль:** работающий процесс Flink ещё не означает готовый кластер. Исполнители должны находить координатор, получать ресурсы и читать одни и те же долговечные файлы. Для длительной работы нужно также заранее определить, кто вернёт потерянный процесс и откуда он восстановит задание.

## О чём глава

В главе «[Чтение и запись при работе с внешними системами](/book-summaries/engineering/stream-processing-with-apache-flink/08-external-systems/)» приложение подключалось к внешним системам. Теперь эти соединения, библиотеки и пути к файлам должны работать со всех узлов. Авторы рассматривают варианты размещения Flink 1.7 и показывают, как отделить выбор инфраструктуры от настройки самого процесса. Названия ключей и значения по умолчанию далее относятся к версии книги.

## Режимы развёртывания

### Автономный кластер

В простейшем варианте на узлах устанавливают совместимые Java и дистрибутив Flink, размещают конфигурацию и указывают адрес координатора. Запуск рабочего процесса успешен только тогда, когда тот зарегистрировался и предложил слоты ResourceManager. Поэтому одного списка процессов ОС недостаточно для проверки готовности. Веб-панель или REST показывают зарегистрированных исполнителей и доступную ёмкость кластера.

Сценарии из дистрибутива помогают запускать и останавливать компоненты на настроенных машинах. Для запуска удалённых процессов нужно настроить доступ к этим машинам. Пакеты, содержимое каталога библиотек и конфигурация должны совпадать там, где узлы исполняют одинаковые роли. Кластер не доставит отсутствующую системную библиотеку на соседний сервер только потому, что она есть на клиенте разработчика.

> **Пояснение:** для проверки ниже один TaskManager Flink 1.7.1 запущен с двумя слотами в изолированном контейнере. Запрос сделан до отправки задания.

```bash
curl -fsS http://localhost:8081/overview
```

```text
{"taskmanagers":1,"slots-total":2,"slots-available":2,"jobs-running":0,"jobs-finished":0,"jobs-cancelled":0,"jobs-failed":0,"flink-version":"1.7.1","flink-commit":"89eafb4"}
```

Здесь различие между процессом и слотом видно непосредственно. Кластер зарегистрировал один рабочий процесс и при этом предлагает планировщику две единицы размещения. После запуска приложения часть слотов будет занята, хотя число процессов останется тем же.

### Docker

Образ фиксирует дистрибутив, библиотеки и среду Java. Разные контейнеры одного образа могут выполнять разные роли, если команда запуска определяет, стартует координатор или TaskManager. При раздельном запуске контейнеров `localhost` указывает на сеть самого контейнера. Рабочий процесс должен обращаться к имени, которое разрешается в координатор из его сети. Снаружи при необходимости публикуют порт REST или веб-панели.

Docker Compose позволяет описать общий набор компонентов и количество исполнителей. Но образ не решает вопрос о долговечности записей. Приложение пишет журнал для диагностики, хранит рабочие данные в локальной базе, а при восстановлении читает подтверждённый снимок. Удаление контейнера не должно удалять единственную копию данных, необходимых для восстановления. По той же причине локальный путь внутри двух контейнеров может иметь одинаковое написание и обозначать два разных хранилища.

### Apache Hadoop YARN

В кластере YARN ресурсы выдаёт внешний планировщик. Клиент передаёт необходимые материалы для запуска приложения, а ApplicationMaster договаривается с YARN о контейнерах. Внутри выделенных контейнеров запускаются компоненты Flink. Поэтому приходится согласовать две картины ресурсов: число слотов и память самой системы Flink с размером контейнеров и очередью YARN.

Сеанс YARN создаёт работающий Flink-кластер, в который можно отправлять несколько заданий. Это сокращает ожидание при повторных запусках, но задания делят выделенную ёмкость. Другой режим выделяет ресурсы конкретному заданию. Когда оно завершится, кластер задания можно освободить целиком. Авторы рассматривают оба варианта. Для переноса своей команды запуска нужно знать адрес и конфигурацию настоящего YARN-кластера. **Запуск на YARN для конспекта не проверялся.**

### Kubernetes

В варианте книги координатор и исполнители работают в отдельных pod. Образ содержит Flink и, при выбранной схеме упаковки, пользовательские зависимости. Deployment описывает желаемое число экземпляров, а Service даёт стабильное имя и сетевую точку доступа. Pod может исчезнуть и получить новый адрес. Поэтому адрес рабочего соединения нельзя жёстко связывать с адресом случайно выбранного первого pod.

Конфигурацию можно передать через смонтированные файлы. При запуске важно правильно выбрать команду для каждой роли, объявить нужные порты и настроить запросы ресурсов. Kubernetes способен создать процесс на месте исчезнувшего. Для возвращения конкретного потокового задания всё ещё нужны метаданные графа и доступный снимок. Здесь рассматривается схема развёртывания из книги. **Запуск её манифестов в Kubernetes не проверялся.**

## Высокая доступность

![Ведущий и резервный координаторы обращаются к ZooKeeper для выбора лидера и к общему хранилищу за данными восстановления](/assets/stream-processing-with-apache-flink/ch09-ha.png)

В описанной версии ZooKeeper хранит сведения для координации и выбора лидера. Большие двоичные данные, включая содержимое снимков, помещают в долговечное файловое хранилище. Такое разделение важно при планировании отказа. Работающий кворум не сможет вернуть файлы с потерянного диска, а сохранённые файлы не выбирают из двух живых процессов того, который должен руководить вычислением.

В автономном режиме запускают несколько кандидатов на роль координатора. Каждый подключается к одному ансамблю ZooKeeper и использует настройки конкретного Flink-кластера. Ведущий обслуживает приложение, остальные готовы принять ответственность после потери лидера. При размещении нескольких независимых кластеров в одном ансамбле их пути и идентификаторы должны различаться. Иначе изолированные задания окажутся в одном пространстве координации.

Для YARN важна также политика повторного запуска ApplicationMaster. Даже если Flink подготовлен к избранию нового координатора, внешний диспетчер может исчерпать разрешённое число попыток и завершить приложение. В книге показан пример с четырьмя попытками на уровне Flink. Этот запрос должен укладываться в разрешённый YARN предел. В Kubernetes соответствующую роль при потере процесса выполняет контроллер pod. Для обоих вариантов остаются общими адрес кворума и долговечное хранилище, доступное замене. **Переключение лидера с ZooKeeper описано по книге и отдельно не испытывалось.**

## Интеграция с Hadoop и файловыми системами

Flink не требует развёрнутого Hadoop для каждой работы с DataStream, но интеграция может понадобиться для YARN, HDFS либо конкретной реализации файловой системы. Процесс должен получить совместимые клиентские библиотеки и конфигурацию. В ней могут быть адреса служб и параметры безопасности. Если доступ к HDFS настроен только в командной оболочке инженера, задание на TaskManager может получить ошибку при первом обращении к тому же пути.

Flink выбирает реализацию файловой системы по схеме URI. Для локального файла путь интерпретируется на машине, которая его открывает, тогда как URI распределённого хранилища указывает на общий ресурс. В книге отдельно обсуждаются реализации для S3 и дополнительные JAR из дистрибутива. При выборе нужно проверить поддерживаемую схему и требуемую операцию. Возможность прочитать объект по ключу не означает, что хранилище поддерживает публикацию файла точно так, как ожидает конкретный приёмник.

Доступ к каталогу снимков проверяют из двух процессов. Сначала исполнитель пишет туда данные, затем новый процесс читает их по тому же URI. Запись и чтение из одной интерактивной оболочки проверяют гораздо меньше: у нового исполнителя могут отличаться права, схема адреса или набор библиотек.

## Конфигурация системы

### Java, загрузка классов и процессор

В одном процессе встречаются системные библиотеки Flink и классы пользовательского приложения. Версии зависимостей могут расходиться. Результат зависит от того, какой загрузчик первым находит класс, а не только от наличия подходящего JAR в одном из каталогов. Авторы обсуждают способы разрешения таких конфликтов и настройку порядка загрузки. Ошибку отсутствующего метода полезно разбирать с фактической версией загруженного класса, а не по дереву зависимостей на ноутбуке.

Число слотов определяет планирование, но слот сам по себе не резервирует эксклюзивное физическое ядро. Несколько вычислительно дорогих задач внутри одного процесса делят доступное процессорное время. Если задания в основном ждут ввода-вывода, одно и то же соотношение слотов и ядер даст другое поведение. Поэтому количество рабочих экземпляров выбирают вместе с измерением загрузки и задержки под представительной нагрузкой.

### Память и сетевые буферы

Помимо объектов Java, процесс расходует память на сетевые буферы, внутренние структуры JVM и, при использовании RocksDB, нативные структуры этой библиотеки. Уменьшение Java-кучи может помочь уложиться в лимит контейнера или, напротив, усилить сборку мусора. Увеличение кучи до всего доступного лимита оставит мало места остальным потребителям. При диагностике сравнивают размер кучи и общее потребление процесса.

В версии книги сетевой бюджет по умолчанию рассчитывается с долей 10% и ограничивается снизу и сверху значениями 64 МиБ и 1 ГиБ. Буферы выделяются вне кучи. Для графа с большим числом каналов пул может исчерпаться ещё при развёртывании. В таком случае добавление слотов на тот же процесс иногда ухудшает ситуацию: задач и соединений становится больше, а сетевой бюджет остаётся прежним. Сначала следует определить, на какой компонент памяти указывает ошибка.

### Диск, снимки и безопасность

Рабочий диск используется для временных файлов, журналов и локальной RocksDB. Эти данные могут конкурировать за ёмкость и операции ввода-вывода. Снимки для переживания потери узла должны находиться в доступном после отказа хранилище. Кластерная конфигурация задаёт выбор `state backend` и каталоги по умолчанию. Само задание может переопределять часть настроек. Локальное восстановление ускоряет повторное использование сохранившихся данных, но не отменяет потребность в долговечной копии.

Авторы также разбирают защиту сетевых соединений и доступ к службам с Kerberos. Для длительного задания важно, каким способом процесс подтверждает права после истечения первоначального билета. Доступ клиента при отправке и доступ рабочего узла после нескольких часов работы могут различаться. Следовательно, проверка запуска должна включать работу с защищённым источником или хранилищем от имени тех процессов, которые реально его используют.

## Итоги главы

- Режим развёртывания определяет, кто выдаёт ресурсы и возвращает потерянные процессы.
- Зарегистрированные слоты лучше отражают доступное место исполнения, чем число запущенных JVM.
- Высокая доступность требует координации и долговечных файлов восстановления.
- Совпадающие локальные пути на разных машинах могут вести к разным данным.
- Лимит памяти процесса должен учитывать потребителей вне Java-кучи.
- Права на хранилище проверяют со стороны всех участников восстановления.

## Ключевые термины

| Термин | Значение |
| --- | --- |
| ZooKeeper | Служба координации, используемая для выбора лидера в описанном режиме. |
| Сеанс YARN | Выделенный набор ресурсов Flink для последовательных или совместных запусков заданий. |
| Сетевой буфер | Часть памяти для передачи сериализованных записей между задачами. |

## Что это значит на практике

Составьте карту зависимостей запуска. Для каждого процесса запишите имя, по которому его находят соседи, требуемые права и файлы, которые должны сохраниться при его замене. При проверке отдельно имитируйте потерю рабочего процесса и потерю машины с локальным диском.
