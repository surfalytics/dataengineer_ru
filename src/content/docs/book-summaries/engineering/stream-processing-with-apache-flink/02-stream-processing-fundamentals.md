**Главная мысль:** чтобы описать результат непрерывного вычисления, недостаточно назвать функцию. Нужно указать, к какому экземпляру оператора попадёт событие, по каким часам программа определит его окно и как восстановит накопленные данные после сбоя.

## О чём глава

В главе «[Введение в потоковую обработку с учетом состояния](/book-summaries/engineering/stream-processing-with-apache-flink/01-stateful-stream-processing/)» одно задание читало показания датчиков. Теперь авторы разбирают, что изменится, если распределить такое вычисление между несколькими машинами. Один и тот же граф может быстро принимать записи и при этом выдавать результат с опозданием. Более того, две обработки одинакового входа могут по-разному распределить события по минутам. Чтобы разобраться в причинах, сначала рассмотрим сам граф.

## Введение в потоковое программирование

### Логический и физический графы

На логической схеме подсчёта популярных хештегов достаточно нескольких вершин. Первая читает сообщения, следующая извлекает из каждого сообщения все хештеги. Ещё одна вершина суммирует появления каждого тега, а последняя передаёт результат наружу. Рёбра показывают, чьи результаты служат входом следующей операции. Из одного сообщения могут получиться несколько тегов или ни одного. Поэтому число записей после вершины вовсе не обязано совпадать с числом записей на входе.

Логический граф задаёт смысл программы. Чтобы запустить её, система строит физический граф с конкретными экземплярами вычислений. Если теги извлекают три экземпляра функции, каждый получает свою часть сообщений. Граф всё ещё описывает один подсчёт, но теперь надо решить, где хранить счётчик отдельного тега. Если произвольно распределять одинаковые теги между тремя счётчиками, каждый из них сообщит только часть итогового числа.

### Два вида параллелизма

При параллелизме данных несколько экземпляров одной функции выполняют одинаковую работу над разными записями. При параллелизме задач одновременно действуют разные операции графа. Пока одна вершина извлекает теги из нового сообщения, другая уже прибавляет единицу к счётчику предыдущего тега. Обе формы могут использоваться в одном приложении. Увеличение числа экземпляров полезно лишь до тех пор, пока между ними можно распределять работу и следующий шаг успевает принимать результаты.

### Как передать запись следующей вершине

При прямой передаче экземпляр отправляет данные своему соседу. Если они работают на одном узле, передача может обойтись без сети. При широковещательной передаче каждый получатель видит копию каждой записи. Так удобно разослать небольшой набор правил, который нужен всем исполнителям, хотя число передаваемых копий возрастает.

При разбиении по ключу система вычисляет адрес получателя из ключа. Все сообщения с одним хештегом оказываются у одного счётчика. Равномерность нагрузки зависит от самих данных. Один исключительно популярный тег остаётся работой одного экземпляра. Наконец, случайное распределение помогает делить независимые записи между получателями примерно поровну. Оно подходит для функций, которым не требуется совместная история определённого ключа.

## Параллельная обработка потоков

### Как измерить скорость

Задержка отвечает на вопрос, сколько времени одна запись провела между входом и наблюдаемым результатом. В это время входит и ожидание в очередях. `Throughput` показывает, сколько записей или байтов система обработала за интервал. Высокое значение одного показателя не определяет другого. Если оператор накопит большую порцию записей перед отправкой, общие издержки передачи уменьшатся, но первая запись будет ждать остальные.

Авторы предлагают представить кофейню. Когда у стойки пусто, посетитель ждёт примерно столько, сколько бариста готовит заказ. Затем поток посетителей растёт, а число чашек, которое бариста может приготовить за минуту, ограничено. После достижения этой границы новые посетители удлиняют очередь. В приложении такую роль выполняют буферы. Они сглаживают короткий всплеск, но не устраняют постоянное отставание получателя. При `backpressure` медленный получатель ограничивает скорость отправителя. Так перегрузка становится заметной и на более ранних шагах графа.

Поэтому для сравнения двух систем нужно знать нагрузку, при которой измеряли задержку. Кроме того, среднее время скрывает редкие долгие ожидания. Если решение должно успевать к определённому сроку, стоит смотреть на распределение задержек. Простое увеличение очереди способно улучшить картину у отправителя, но ухудшить время, которое видит конечный потребитель.

### Операции над записями и окна

Источник создаёт входной поток, а `sink` передаёт результаты во внешнюю систему. Между ними стоят преобразования. Поэлементная операция рассматривает очередную запись отдельно. Фильтр может отбросить её, отображение — заменить другой записью, а извлечение тегов из текста — выдать несколько результатов. Для таких функций легко добавить параллельные экземпляры, если важен только результат для каждой записи.

Непрерывная агрегация сохраняет промежуточное значение. Например, максимум по датчику можно обновить, сравнив новый замер с единственным сохранённым числом. Чтобы вычислить среднее, удобно поддерживать сумму и количество. Однако ответ на вопрос «какой максимум за последние десять минут?» уже нельзя свести к сравнению нового значения с прежним максимумом. Когда старый рекорд покинет интервал, понадобятся сведения об остальных измерениях.

Окна ограничивают группу, к которой применяется функция. Время и число записей задают разные границы. Окно из двух событий заполнится только с приходом второй записи, тогда как минутное окно описывает отрезок на временной оси. В `tumbling window` соседние окна не пересекаются. В `sliding window` размер и шаг выбирают независимо. При шаге меньше размера один замер участвует в нескольких вычислениях. Наконец, `session window` объединяет активность, пока пауза между событиями остаётся достаточно короткой. Начало следующей сессии определяют сами данные.

Если сначала разделить поток по ключам, окна будут формироваться отдельно для каждого ключа. Два события красного цвета образуют первую пару красного потока, даже если между ними пришло несколько синих. Окно из двух событий общего потока даст совсем другое разбиение. Поэтому порядок операций «разбить по ключу» и «сгруппировать события в окна» определяет смысл результата.

## Семантика времени

![Телефон сохраняет событие до восстановления связи, а сервер получает его уже после игровой минуты](/assets/stream-processing-with-apache-flink/ch02-two-clocks.png)

### Сколько длится игровая минута

В мобильной игре команда получает награду, когда участники вместе лопнут 500 пузырьков за минуту. Алиса играет по дороге на работу. Когда поезд уходит под землю, сервер перестаёт видеть её действия. Телефон продолжает их записывать и отправляет накопленное после восстановления связи. Для сервера одинаково своевременными выглядят записи, которые пришли вместе. Для игроков важнее, когда каждый из них действительно совершил действие.

### Часы машины и метка события

При `processing time` оператор смотрит на локальные часы в момент обработки записи. Такой таймер легко настроить, а результат можно выдавать регулярно, даже когда источник временно молчит. Но после повторного чтения скорость обработки будет другой. События, раньше оказавшиеся в разных минутах, могут попасть в одну. Выбор подходит, например, для оперативного наблюдения за тем, что видит сама система прямо сейчас.

При `event time` принадлежность к минуте задаёт временная метка записи. Событие Алисы остаётся в своей игровой минуте при задержке сети и при повторном чтении архива. Для этого метке нужно доверять, а программа должна уметь принимать события вне порядка. Дополнительный вопрос возникает в момент публикации результата. Если связь ещё не восстановилась, сервер не знает, все ли команда уже прислала.

### Когда можно выдать результат

`Watermark` сообщает оператору, до какого времени источник считает поток достаточно полным для вычисления результата. Это предположение может нарушиться. Если быстро продвигать эту отметку, пользователь раньше увидит награду, но выше вероятность получить запоздалую запись уже после расчёта. Если ждать дольше, в первоначальный результат попадёт больше событий. Цена ожидания — задержка ответа и более долгое хранение незавершённых вычислений.

Поэтому выбор часов и решение о поздних данных стоит обсуждать вместе. Для игровых очков важно сохранить принадлежность события к минуте. Для сигнала о недоступности работающего сервиса может быть важнее сработать через секунду по настенным часам. Ускоренное чтение вчерашнего журнала ещё сильнее подчёркивает разницу между этими задачами.

## Модели состояния и согласованности

Состояние должно переживать обработку одной записи и оставаться доступным при приходе следующей. Для независимых датчиков его удобно разделить по идентификаторам. Тогда оператор работает с локальными значениями и избегает согласования каждой записи со всеми остальными машинами. Сбой меняет задачу. Если процесс исчез, его преемнику нужно вернуть как накопленные значения, так и место во входном потоке. В противном случае корректная функция продолжит вычисление с неверного исходного числа.

| Гарантия | Возможное поведение после отказа |
| --- | --- |
| `at-most-once` | Программа продолжает с новых записей. Событие, обработку которого прервал сбой, может пропасть из результата. |
| `at-least-once` | Источник воспроизводит записи. Потерю можно предотвратить, но повторное прибавление единицы завысит счётчик. |
| `exactly-once` | При восстановлении состояние и вход согласуются так, что каждая запись влияет на результат один раз. Код при этом может прочитать её повторно. |

Гарантию нужно связывать с конкретной границей. Система способна восстановить внутренний счётчик и всё же повторно отправить внешнее уведомление. Уже полученное письмо нельзя отозвать загрузкой прежнего состояния. Для сквозной гарантии необходим подходящий способ взаимодействия с получателем. Подробнее механизмы снимков разбирает [Архитектура Apache Flink](/book-summaries/engineering/stream-processing-with-apache-flink/03-flink-architecture/).

## Итоги главы

- Логический граф описывает операции, физический граф показывает их исполняемые экземпляры.
- Разбиение по ключу определяет владельца состояния.
- Окна ограничивают набор записей для вычисления.
- Время события позволяет повторно отнести запись к исходному интервалу.
- `Watermark` делает явным предположение о полноте поступивших данных.
- Гарантия результата указывает, какие последствия отказа допускает программа.

## Ключевые термины

| Термин | Значение |
| --- | --- |
| Задержка | Время от поступления отдельной записи до ответа. |
| `backpressure` | Ограничение скорости, которое передаётся от получателя к отправителю. |
| `event time` | Временная шкала, заданная метками самих событий. |

## Что это значит на практике

Для каждого показателя запишите ключ, границы окна, источник времени и способ обработки опоздавших записей. При испытании на отказ проверьте и накопленный итог, и результат у внешнего получателя.
