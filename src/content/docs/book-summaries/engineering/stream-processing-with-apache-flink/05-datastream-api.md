**Главная мысль:** приложение DataStream описывает путь записи от источника до получателя. От типа потока зависит, какие операции разрешены дальше. Например, после разбиения по идентификатору датчика можно обновлять отдельный накопленный результат для каждого прибора.

## О чём глава

В главе «[Настройка рабочей среды для Apache Flink](/book-summaries/engineering/stream-processing-with-apache-flink/04-flink-development-environment/)» приложение запускали из IDE. Теперь авторы разбирают, что именно оно передаёт на исполнение. Сначала соберём вычисление средней температуры, затем заменим его отдельные шаги и посмотрим, какие требования это предъявляет к передаче записей, выбору ключа и типам данных.

## Первое приложение DataStream

### От среды выполнения до результата

Программа запрашивает `StreamExecutionEnvironment`. В зависимости от способа запуска эта среда связывает программу с локальным или удалённым исполнением. Здесь задают общие настройки, в том числе временную шкалу и исходную степень параллелизма. Операция `addSource` создаёт типизированный поток показаний. Каждое показание содержит идентификатор прибора, время измерения и температуру. Сам объект `DataStream` описывает данные, которые будут передаваться между операторами. В нём не хранится коллекция всех будущих измерений.

Из входной записи извлекают время и назначают правила продвижения `watermark`. Затем `map` переводит температуру из градусов Фаренгейта в градусы Цельсия: из исходного значения вычитают 32 и умножают разность на 5/9. Идентификатор и время измерения сохраняются. Дальше `keyBy` выбирает идентификатор датчика, а окно на пять секунд собирает измерения этого датчика за один интервал. Оконная функция возвращает одно среднее значение для группы. Если бы разделение по ключу отсутствовало, усреднялись бы показания разных приборов.

Результат можно передать файловому приёмнику или внешнему сервису, а при разработке удобно вызвать `print()`. Печатает экземпляр оператора, поэтому в кластере вывод нужно искать на рабочих узлах. Наконец, `execute()` запускает подготовленный граф. До этого вызовы описывали вычисление, и отсутствие новых строк в консоли само по себе ничего не говорило о наличии данных у источника.

## Преобразования потоков

### Одна запись на входе

`map` выдаёт ровно одну запись для каждой входной. Тип результата может отличаться: из целого объекта датчика можно извлечь строку с его идентификатором. `filter` проверяет условие и сохраняет прошедшие проверку записи исходного типа. Например, фильтр пропустит температуры выше порога. `flatMap` вызывает функцию с коллектором, в который та может записать произвольное число результатов, включая ноль. Так из строки извлекают отдельные слова или отбрасывают пустой ввод без отдельного фильтра.

Число вызовов функции и число выходных записей поэтому следует различать. Вызов `flatMap` для пустой строки всё равно состоится, но следующие операторы не получат ничего. Если результат преобразования жёстко соответствует одной входной записи, `map` яснее выражает это условие.

### Разбиение и накопление по ключу

`keyBy` возвращает `KeyedStream`. Он гарантирует, что записи с одинаковым ключом поступят одному экземпляру следующего оператора. Записи разных ключей вполне могут разделить один экземпляр. Разбиение ничего не обещает о сортировке ключей или числовом порядке временных меток. Оно даёт функции доступ к нужной части состояния и может потребовать передачи по сети.

Над таким потоком доступны нарастающие суммы, минимумы и максимумы. После каждого входа оператор обновляет сохранённый результат соответствующего ключа и может сразу его выдать. У `min` и `minBy` разный смысл. Первый выбирает минимум указанного поля, второй возвращает целую запись, которой принадлежал минимум. Для вопроса «когда датчик показал наименьшую температуру?» нужна связь значения с исходной записью. Функция `reduce` даёт больше свободы: она получает старый агрегат и новую запись и возвращает обновлённый агрегат того же типа. При первом появлении ключа накопление начинается с самой записи.

![Для датчика A сумма меняется с двух на пять, а значение B хранится отдельно](/assets/stream-processing-with-apache-flink/ch05-keyed-sum.png)

> **Пояснение:** в коротком Java-примере ниже вход конечный, а степень параллелизма равна единице, чтобы порядок вывода был воспроизводим. Это тот же принцип нарастающего агрегирования, который авторы показывают для потока датчиков.

```java
env.fromElements(Tuple2.of("A", 2), Tuple2.of("B", 5), Tuple2.of("A", 3))
    .keyBy(0)
    .sum(1)
    .print();
```

Вывод на Flink 1.7.1 с Java 8:

```text
(A,2)
(B,5)
(A,5)
```

Третья запись показывает новое накопленное значение для A. При неограниченном числе разных ключей размер такой таблицы может расти всё время работы задания. Это ограничение относится и к встроенному агрегату, и к пользовательской функции `reduce`. Сам факт появления более свежего ключа не делает состояние старого ключа ненужным.

### Несколько входов и выходов

`union` объединяет два или больше потоков одного типа в поток того же типа. Записи перемежаются по мере поступления. Глобального порядка между исходными потоками такое объединение не создаёт. `connect` связывает ровно два входа, зато они могут не совпадать по типу. Пользовательская функция получает разные методы для первого и второго входа. Общий выход остаётся одного типа.

Например, один вход доставляет измерения, а второй присылает управляющие записи. Функция может запомнить новое правило при обработке управляющей записи и применить его к следующему измерению. Для этого нужно решить, какой экземпляр видит какие правила. Если все экземпляры должны видеть одно изменение, управляющий поток рассылают всем. Если правило относится к одному датчику, оба входа следует согласованно разделить по его ключу. Порядок вызовов методов разных входов заранее не задан.

В API версии 1.7 `split` присваивает записи одно или несколько имён выходов, а `select` извлекает записи для выбранных имён. Одна запись может попасть в несколько ветвей. Следовательно, сложение результатов двух таких ветвей может повторно учесть событие. Кроме того, именованные выходы сохраняют тип исходного потока. Другой механизм для дополнительных выходов разбирается в следующей главе.

### Как распределить нагрузку

При `shuffle` получатель выбирается случайно. `rebalance` циклически перебирает все параллельные экземпляры следующего оператора. `rescale` тоже распределяет записи по кругу, но каждый отправитель взаимодействует лишь с подмножеством получателей, если это допускает соотношение степеней параллелизма. Уменьшение числа каналов полезно, когда не требуется обмен «каждый с каждым». `broadcast` копирует каждую запись всем получателям. Прямая передача сохраняет соответствие между подзадачами. Можно также реализовать собственную функцию распределения.

Эти операции меняют маршруты передачи. Они не дают интерфейса состояния по ключу. Даже если пользовательская функция распределения случайно разместила все записи одного датчика рядом, для нарастающего агрегата с доступом к состоянию API ожидает `KeyedStream`.

## Настройка параллелизма

Степень параллелизма задают для всей среды или для отдельного оператора. Локальная среда может исходить из числа доступных вычислительных ядер. При запуске через клиент учитываются параметры задания и конфигурация кластера. Настройка на конкретном операторе позволяет выделить больше экземпляров дорогому преобразованию, сохранив привычное число у остальной части графа. Источник с одной последовательностью данных при этом может вообще не поддерживать распараллеливание.

Менять число экземпляров стоит вместе с проверкой распределения ключей. Дополнительные исполнители бесполезны, если почти все записи относятся к одному ключу. Если же дорогое преобразование не зависит от истории отдельных записей, равномерная передача после непараллельного источника может дать остальным экземплярам работу.

## Типы и сериализация

Flink нужна информация о типе, чтобы выбрать представление записи, построить сериализатор и получить доступ к выбранным полям. Издание рассматривает базовые типы, массивы, кортежи, классы Scala, Java POJO и типы, для которых система использует универсальную сериализацию. В Java доступны специальные классы кортежей от `Tuple1` до `Tuple25`. Поля кортежа адресуются по позиции. Для составной записи с осмысленными полями часто удобнее класс, в котором идентификатор и температура названы явно.

Чтобы Flink распознал Java-класс как POJO, он должен быть общедоступным, иметь доступный конструктор без аргументов и предоставлять доступ к полям непосредственно или стандартными методами чтения и записи. Произвольный пользовательский класс тоже может передаваться между задачами, но для него Flink может выбрать универсальный сериализатор. Универсальный сериализатор может работать медленнее, а Flink знает меньше о структуре записи.

В Scala сведения о типе часто создаются при компиляции. В Java Flink пытается извлечь их из объявления функции, хотя стирание параметров типов ограничивает такой анализ. После лямбда-выражения с обобщённым результатом система иногда видит только общий класс. В этом случае тип результата указывают через `returns` или передают соответствующую информацию о типе. Ошибка обнаруживается при построении графа, ещё до обработки первой записи.

## Как задать ключ и обратиться к полю

Для кортежа можно указать позиции полей. В Java отсчёт начинается с нуля. В строковом выражении используются соглашения конкретного типа и языка: у Scala-кортежа первое поле называется `_1`. Именованные поля составной записи доступны по пути, включая вложенные элементы, например почтовый индекс в адресе человека. Несколько полей вместе образуют составной ключ.

Селектор ключа принимает целую запись и возвращает вычисленное значение. Это удобно, если нужный ключ нельзя выразить одним полем или если важна проверка типов компилятором. При выборе способа записи полезно мысленно проверить два события, которые должны встретиться у одного оператора. Даже безупречно скомпилированный селектор по времени вместо идентификатора разобьёт историю измерений одного датчика на независимые группы.

## Пользовательские функции и зависимости

Именованный класс функции подходит для нетривиальной логики и явного описания типов. Лямбда сокращает простое преобразование, но её окружение должно передаваться вместе с функцией на рабочий узел. Уже открытое соединение с внешней системой для этого плохо подходит. Расширенные функции Flink дают методы жизненного цикла `open` и `close`, а также контекст времени выполнения. Через него экземпляр может узнать свой индекс и обратиться к управляемому состоянию. Ресурс разумно открыть на рабочем узле в момент инициализации и закрыть при штатном завершении.

Библиотеки, которые уже предоставляет кластер, объявляют в Maven с областью `provided`. Пользовательские библиотеки и необходимые соединители обычно нужно доставить вместе с приложением, например собрать в один JAR с помощью Maven Shade. Иначе проект запустится в IDE за счёт её полного пути классов и упадёт в кластере при первом обращении к отсутствующему классу.

## Итоги главы

- Тип потока ограничивает набор допустимых следующих операций.
- Нарастающий агрегат выдаёт промежуточный ответ после очередного события.
- Один ключ может ограничить масштабирование всего вычисления.
- Объединение потоков не восстанавливает глобальный порядок событий.
- Явное описание типа помогает построить сериализатор для сложного результата.
- Состав JAR должен соответствовать библиотекам на рабочих узлах.

## Ключевые термины

| Термин | Значение |

| `KeyedStream` | Поток с разбиением по выбранному ключу. |
