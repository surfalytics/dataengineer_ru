**Главная мысль:** при эксплуатации важны скорость при обычной нагрузке и скорость восстановления. Задание должно успевать за обычным входом и после отказа иметь запас, чтобы догнать накопившиеся события. Наблюдать поэтому нужно одновременно за нагрузкой, прогрессом обработки и возрастом последнего успешного снимка.

## О чём глава

В главе «[Настройка Flink для потоковых приложений](/book-summaries/engineering/stream-processing-with-apache-flink/09-flink-cluster-setup/)» подготавливался кластер. Здесь на нём уже месяцами работает приложение с состоянием. Его нужно обновить, увеличить число исполнителей, понять причину задержки или перенести на другой кластер. Авторы начинают с управления отдельным заданием, затем переходят к планированию задач, конфигурации восстановления и наблюдению за работающей программой.

## Запуск и управление приложениями

### Что хранится в плановом снимке

`Savepoint` описывает состояние операторов и данные, необходимые для его загрузки. Снимок хранится в выбранном каталоге. Служебный файл с метаданными связывает идентификаторы операторов с сохранёнными частями. Поэтому при переносе нельзя ограничиться копированием одного файла, который выглядит как описание снимка. Новая программа должна иметь доступ ко всему, на что ссылаются метаданные.

Плановый снимок инициирует пользователь. Его жизненный цикл отличается от периодических снимков для автоматического восстановления. Например, можно сохранить состояние перед выпуском новой версии, остановить приложение и оставить снимок, пока результат обновления не проверен. Удалять его следует средствами, предусмотренными для освобождения состояния, и только когда больше не потребуется восстановление из этой точки. Совпадение пути к каталогу ещё не гарантирует совместимость кода. Существенны идентификаторы операторов, имена состояний и их сериализаторы.

### Командная строка

Клиент `flink run` отправляет JAR и класс с точкой входа. Степень параллелизма задаётся для запуска, если конкретные операторы не переопределили её. В присоединённом режиме пользователь остаётся связан с выполняющимся заданием. Параметр `-d` возвращает управление после отправки. Идентификатор задания позволяет дальше запросить состояние именно этого запуска. При двух заданиях с одинаковым названием имя не служит надёжным идентификатором.

Список работающих заданий показывает, принял ли кластер отправку. Но для проверки результата этого мало. Следует посмотреть, стартовали ли вершины графа и пошли ли записи через нужный оператор. При обычной отмене задание прекращается. Если после отмены требуется продолжить с текущего состояния, в версии книги используют отмену с сохранением. Последовательность «сначала сохранить, затем через некоторое время отменить» допускает обработку новых событий между двумя действиями. После восстановления их придётся прочитать снова.

![Работающее задание останавливается с сохранением состояния и запускается из него с двумя параллельными экземплярами](/assets/stream-processing-with-apache-flink/ch10-resume.png)

> **Пояснение:** в проверке на Flink 1.7.1 приложение датчиков сначала работало с параллелизмом 1. После появления результата клиент остановил его с сохранением состояния. Переменная `JOB` в командах ниже — идентификатор работающего задания, а `SAVEPOINT` — URI, который вернула отмена.

```bash
./bin/flink cancel -s file:///tmp/book-savepoints "$JOB"
./bin/flink run -d -p 2 -s "$SAVEPOINT" \
  -c io.github.streamingwithflink.chapter1.AverageSensorReadings examples-scala.jar
```

В каталоге снимка проверен файл `_metadata`. Новый запуск получил другой идентификатор. Проверяющий сценарий дождался статуса работающей вершины и нашёл в ответе REST степень параллелизма 2:

```text
После восстановления: RUNNING, параллелизм 2
```

При масштабировании Flink перераспределяет состояние по правилам, разобранным в седьмой главе. Сам факт появления второго исполнителя не означает, что источник стал читать вдвое быстрее. Ограничением могут оставаться партиции, один особенно частый ключ или скорость внешнего приёмника. После запуска сравнивают не только параллелизм в графе, но и скорость отставания от входа.

### REST и упаковка задания в образ

REST-интерфейс позволяет автоматизировать действия, которые иначе выполняет CLI или веб-панель. Одни запросы описывают весь кластер, перечень TaskManager и доступные метрики. Другие относятся к одному заданию, его вершинам, снимкам и исключениям. При отправке задания через REST сначала загружают JAR, затем запускают его с параметрами. Идентификатор загруженного файла и идентификатор работающего задания нужны на разных этапах.

Некоторые запросы инициируют долгую операцию и сразу возвращают идентификатор запроса. Получение этого идентификатора ещё не доказывает, что снимок записан. Клиент должен дождаться конечного статуса и проверить результат или ошибку. Это особенно существенно в сценарии обновления: если перейти к остановке или удалению старых ресурсов сразу после принятия запроса, можно потерять ожидаемую точку возврата.

Другой способ доставки — образ для конкретного задания. В образ помещают версии Flink, код приложения и нужные библиотеки. Команда контейнера запускает предусмотренную роль, а пользовательские параметры передаются при развёртывании. Такой образ легче повторно запустить с тем же составом классов. При обновлении кода понадобится новый образ, зато изменения однозначно отделены от случайной замены JAR в работающем контейнере. Состояние всё равно размещают там, откуда его сможет прочитать следующий контейнер.

## Управление планированием задач

### Где разорвать цепочку

По умолчанию совместимые соседние операторы объединяются в общую исполняемую задачу. Это сокращает передачу данных и число переключений потоков. В веб-интерфейсе несколько логических шагов тогда видны как одна исполняемая вершина. При попытке понять, какой из шагов тормозит, общая метрика такой цепочки даёт меньше подробностей, чем измерение отдельных операций.

DataStream API позволяет начать новую цепочку, запретить объединение конкретного оператора или выключить его для всего задания. Изолировать стоит тот участок, для которого нужны отдельные ресурсы, отдельное измерение или независимое планирование. Разрыв добавляет передачу записей и буферы. Поэтому небольшая функция, которую выделили лишь для удобного имени в панели, может оказаться дороже своей вычислительной работы.

### Какие задачи могут разделить слот

Группа совместного использования определяет, какие операторы допускается размещать в одном слоте. Так можно отделить тяжёлую функцию от других стадий или сгруппировать совместимые части приложения. Разделение на группы способно увеличить необходимое число слотов. Если для одной группы нужно четыре экземпляра, а для независимой второй — два, общий доступ к четырём слотам может оказаться недостаточным, даже когда вычислительных ядер кажется достаточно.

Правило размещения задаёт возможность, но не обещает отдельное физическое ядро для каждой функции. Чтобы оценить результат, полезно смотреть, как изменились занятость исполнителей, скорость обработки и длина очередей после изменения. При одинаковой скорости входа отложенная работа может просто переместиться из одного места графа в другое.

## Снимки и восстановление

### Частота, длительность и число одновременных снимков

Частые снимки уменьшают объём входа, который придётся перечитать после сбоя, зато увеличивают нагрузку на сеть, хранилище и координацию. Редкие снимки дешевле в обычном режиме. Но при отказе прямо перед очередной успешной попыткой восстановление начнётся с гораздо более старой позиции. Для внешнего транзакционного приёмника частота подтверждений влияет ещё и на момент, когда читатель увидит результат.

В настройках версии книги разделены интервал инициирования, тайм-аут попытки, допустимое число одновременных снимков и минимальная пауза между ними. Если длительный снимок почти исчерпывает интервал, приложение может постоянно сохранять данные. Минимальная пауза оставляет вычислению время без следующей попытки. Увеличение числа параллельных снимков, напротив, разрешает нескольким попыткам одновременно расходовать ресурсы. Оно не заставляет медленное хранилище писать быстрее.

Сжатие уменьшает объём передаваемых данных ценой дополнительной работы процессора. Его эффект зависит от содержимого состояния и ограничивающего ресурса. Авторы также обсуждают сохранение периодических снимков вне обычного жизненного цикла задания. Если включить такое хранение, нужно заранее определить, оставлять ли файлы при ручной отмене и кто затем их удалит. Старые каталоги могут продолжать занимать место после завершения вычисления.

### Механизм хранения

У `MemoryStateBackend`, `FsStateBackend` и `RocksDBStateBackend` разные места для рабочих данных и долговечных снимков. Выбор для кластера можно переопределить в приложении. Для большой RocksDB доступны инкрементные снимки. Вместо повторной передачи всех файлов система может сослаться на уже сохранённые неизменившиеся части и записать новые. Поэтому размер последней передачи и полный объём данных, необходимый для восстановления, — разные величины.

Асинхронная запись снимка освобождает поток обработки раньше окончания передачи всех байтов. При этом оператору всё равно нужно согласовать границу и подготовить локальное состояние. Если задержку создаёт выравнивание барьеров между быстрым и медленным входом, ускорение записи файлов мало повлияет на ожидание перед началом снимка. В панели полезно отделять время выравнивания от времени собственно записи.

### Перезапуск и возврат к текущему входу

Стратегия перезапуска определяет, когда попробовать ещё раз и после скольких ошибок прекратить попытки. В книге рассматриваются отсутствие рестартов, фиксированная задержка между попытками и ограничение частоты отказов в заданном интервале. Последнее позволяет пережить редкие временные проблемы, но остановить программу, которая падает снова и снова. Бесконечный повтор при несовместимом формате состояния не восстановит задание и может надолго скрыть устойчивую ошибку.

При локальном восстановлении Flink пытается переиспользовать сохранившиеся данные рядом с исполнителем. Это сокращает чтение по сети, если прежний узел и его диск доступны. Если машина потеряна полностью, нужно восстановиться из долговечной копии. Поэтому локальное ускорение полезно сравнивать и при перезапуске процесса, и при фактической потере узла.

Время возврата к норме складывается из обнаружения отказа, ожидания ресурсов, загрузки состояния и повторной обработки входа. За это время внешний источник продолжает принимать новые события. Если до сбоя приложение работало на пределе и сейчас обрабатывает ровно столько, сколько прибывает, накопленное отставание не сократится. Для длительной работы авторы рекомендуют оставлять запас производительности. Быстрый статус `RUNNING` после перезапуска ещё не означает, что пользователи снова видят свежие данные.

## Мониторинг

### Что показывает панель

Сначала проверьте доступность процессов и слотов, затем статус нужного задания. В графе видны отдельные вершины и их параллельные экземпляры. Если медленным оказался только один экземпляр, сравните распределение ключей и объём входа между экземплярами. Если медленны все, проверьте общий внешний ресурс, например приёмник или хранилище снимков. Числа входных и выходных записей помогут отличить отсутствие входа от затора после конкретного оператора.

На вкладке снимков важен не только цвет последней попытки. Посмотрите, сколько времени прошло с последнего успешного завершения, увеличился ли объём состояния, отличаются ли подзадачи по времени выравнивания. Вкладка `backpressure` версии книги использует выборочные наблюдения за потоками задач. Высокий показатель отправителя часто означает, что следующий оператор не успевает освободить буферы. Чтобы найти причину, двигайтесь по графу в сторону получателя, а не только увеличивайте ресурсы у первой замедлившейся вершины.

### Метрики и их адреса

Счётчик накапливает число событий. Измеритель текущего значения, или `gauge`, возвращает значение при опросе, например размер очереди. Гистограмма описывает распределение измерений, а `meter` помогает наблюдать скорость событий во времени. Если есть только общий счётчик обработанных записей, рост числа показывает наличие работы, но время ожидания отдельной записи по нему не восстановить.

Пользовательская функция регистрирует метрику через контекст выполнения. Группы и область метрики связывают её с заданием, задачей или экземпляром. Имя можно сделать удобным для внешней системы мониторинга, но оно должно сохранять информацию, по которой различаются параллельные исполнители. При непрерывном создании групп по произвольному идентификатору клиента число временных рядов может расти вместе с числом клиентов. Поэтому бизнес-ключ и измерение, по которому группируются метрики, не обязательно должны совпадать.

Метрики доступны через REST и через настроенные средства передачи показателей. Авторы отдельно рассматривают оценку задержки служебными метками, которые источник периодически отправляет сквозь граф. В примере интервал отправки равен 500 мс. Это выборочный показатель пути внутри приложения. Он не охватывает время, проведённое реальным событием в телефоне или очереди внешней системы до входа во Flink, и не заменяет измерение бизнес-задержки по фактическим данным.

## Журналирование

Задание пишет сообщения там, где исполняется конкретный фрагмент. Сообщение из клиентского кода и предупреждение из функции на TaskManager могут оказаться в разных файлах. Книга показывает использование SLF4J и настройку поддерживаемой реализации журналирования. Вместо конструирования длинной строки для каждой записи лучше пользоваться уровнем сообщения и параметрами, которые реализация обработает при необходимости.

Подробная запись каждого события способна сама стать источником нагрузки и быстро заполнить диск. Для обычной работы полезнее связать короткое диагностическое сообщение с идентификатором задания и подзадачи, а количественные симптомы наблюдать через метрики. При восстановлении такая привязка помогает сопоставить исключение конкретной задачи со временем неудачного снимка и повторного запуска.

## Итоги главы

- Плановый снимок нужен до остановки той версии задания, состояние которой требуется сохранить.
- Успешное принятие REST-запроса и успешное завершение операции — разные события.
- Цепочка операторов и группа совместного использования слота управляют разными аспектами исполнения.
- Интервал снимков влияет на обычную нагрузку, восстановление и видимость транзакционной записи.
- Локальная копия ускоряет восстановление только пока доступен её носитель.
- Запас вычислительной мощности определяет, сможет ли приложение догнать источник после сбоя.

## Ключевые термины

| Термин | Значение |
| --- | --- |
| `savepoint` | Согласованное состояние, сроком хранения которого управляет пользователь. |
| `gauge` | Значение, измеряемое в момент опроса. |
| Локальное восстановление | Повторное использование доступной локальной копии для сокращения времени загрузки. |

## Что это значит на практике

Перед обновлением проверьте путь к снимку, наличие свободных слотов и совместимость новой версии. После запуска измерьте скорость сокращения отставания и проверьте результат у получателя. При устойчивой ошибке сохраните журнал первого исключения до того, как его скроет серия перезапусков.
