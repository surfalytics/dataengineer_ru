**Главная мысль.** В lakehouse отчёт и модель машинного обучения могут использовать одни и те же данные. Табличный формат определяет согласованное состояние таблицы, а каждый совместимый движок читает нужные ему файлы из общего хранилища.

## О чём глава

Зачем копировать данные из `data lake` в отдельное хранилище для BI, если можно дать SQL-движку доступ к тем же файлам? Гаурав Ашок Талпати разбирает, чего не хватает обычному набору файлов для такой работы. Он прослеживает путь данных от источника до отчёта, объясняет роль транзакций и показывает, как движок находит прежнюю версию таблицы. Автор описывает продукты по состоянию на 16 мая 2024 года, дату пятого предварительного выпуска.

## Архитектура данных и платформа

Архитектура данных описывает компоненты системы, связи между ними, потоки данных и принципы построения. Платформа данных — результат реализации этого плана на выбранных технологиях. Её задача — помочь людям находить ответы с помощью данных, от обычных отчётов до прогнозов и машинного обучения.

Автор сравнивает архитектуру с проектом здания. Требования к надёжности и доступу нужны и жилому комплексу, и торговому центру, хотя конкретная планировка различается. Так и принципы платформы применимы в разных отраслях, а выбор компонентов зависит от задач организации.

Архитектура помогает определить, как данные перемещаются между производителями и потребителями, где возникают ограничения интеграции и какие общие правила применять командам. Например, при разных тарифах уровней хранения нужно решить, какие данные оставлять доступными для частого чтения, а какие переносить в холодное хранение. Выбирая технологии, команда заранее определяет, что проверит на прототипе (PoC) и какой результат сочтёт достаточным.

План должен соответствовать стратегии организации. В частности, `data governance` — это правила, ответственность и контроль качества, доступа и использования данных. Каталог, контроль доступа и принципы предоставления данных помогают применять эти правила на практике и поддерживать доверие потребителей.

## Основные компоненты платформы данных

### Источники и ingestion

Источники бывают внутренними, например CRM и транзакционные базы, и внешними, например курсы валют или сведения о погоде. Они передают структурированные, полуструктурированные и неструктурированные данные с разной частотой. Поэтому платформа должна учитывать не только формат, но и способ поступления каждого потока.

`Ingestion` — извлечение данных из источника и загрузка на платформу. При пакетной загрузке данные могут поступать раз в день, например для регуляторной отчётности. Микропакеты и загрузка почти в реальном времени сокращают интервал до минут или секунд. Для потоковой аналитики автор рассматривает данные, которые нужно получать в течение миллисекунд: ценность события может быстро снижаться с задержкой.

Допустимую задержку определяет потребитель. Если отчёт нужен к открытию магазина, в соглашении об уровне сервиса (SLA) указывают время готовности данных. Затем его сопоставляют с расписанием источника. Автор предлагает настраивать частоту и формат поставки для каждого источника в общем механизме загрузки. Тогда для следующего ежедневного файла достаточно добавить конфигурацию.

### Хранение, обработка и подготовка

Компоненты хранения должны обеспечивать доступность данных и их долговечность после сбоев. Объектное хранилище (`object storage`), например Amazon S3, Azure Data Lake Storage или Google Cloud Storage, подходит для разных типов данных и длительного хранения. Специализированные системы могут понадобиться там, где важны быстрый поиск по ключу, множество параллельных запросов или особая модель доступа. Примеры — аналитическое хранилище данных (`data warehouse`), реляционная база, база в памяти и графовая база.

Данные из источника обычно сначала проверяют и очищают. Технические проверки выявляют нарушения типов и форматов. Правила предметной области помогают заметить невозможное значение или пропущенные сведения. Отдельно проверяют, соответствует ли входная запись согласованной схеме. Условия поставки можно закрепить в соглашении между производителем данных и потребителями (`data contract`). В нём указывают владельца, состав полей, типы, формат и периодичность поставки. По этим условиям команда определяет, какие нарушения обнаружит при загрузке. Например, проверка может выявить отсутствующее обязательное поле или значение с неподходящим типом.

Затем данные объединяют, обогащают и агрегируют. Например, сведения о клиентах из нескольких систем можно соединить, продажи дополнить курсами валют и свести по товару, дате и месту. Автор отдельно выделяет подготовленный слой: данные в нём организуют по бизнес-процессам и отраслевой модели, например с применением моделирования измерений. Такое представление помогает пользователям быстрее строить отчёты и находить ответы. Подготовленные по подходящей модели данные служат основой отчётов и `data product` — набора данных или другого результата, созданного для потребителей как продукт. Им может быть таблица, представление, отчёт или модель машинного обучения.

Порядок преобразований зависит от подхода. При `ETL` данные извлекают, преобразуют и затем загружают в целевую систему. При `ELT` их сначала загружают, а преобразования выполняют уже вычислительными средствами целевой платформы. В обоих случаях нужны проверки качества и понимание того, когда результат будет доступен потребителю.

### Потребление и общие службы

Потребители используют данные через BI-отчёты и дашборды, разовые SQL-запросы, API и модели ML. Последним нужны средства обучения, развёртывания и получения предсказаний. Удобство этих интерфейсов влияет на то, будут ли люди пользоваться платформой. Аналитику может потребоваться разовый ответ во время встречи, тогда как приложению нужен воспроизводимый способ получить данные через API. Поэтому одна система хранения должна сопровождаться разными средствами доступа, соответствующими потребителям.

Общие службы поддерживают несколько этапов сразу. Каталог данных (`data catalog`) помогает найти нужный набор и посмотреть, какие у него поля, типы и ключи. Если доступ ограничен, одних описаний недостаточно: нужны правила, определяющие, кто может читать и передавать данные. Меры защиты зависят от того, где находятся данные. Файлы и диски можно шифровать при хранении, а соединения между системами защищать с помощью TLS. Оркестрация задаёт расписания и зависимости `pipeline` — цепочек перемещения и преобразования данных.

Мониторинг позволяет обнаруживать сбои выполнения, а `data observability` помогает наблюдать за состоянием самих данных: их свежестью, полнотой, точностью и качеством. По мере роста платформы без этих механизмов сбои могут оставаться незамеченными, а доверие потребителей — снижаться.

## Зачем понадобилась новая архитектура

Организации долго строили платформы вокруг хранилищ данных или `data lake` — хранилищ разнородных данных в исходном или обработанном виде. У каждой архитектуры при самостоятельном использовании есть ограничения. Одним из ответов стала двухуровневая система: данные хранят в `data lake`, а для BI дополнительно загружают в хранилище данных. Другие подходы объединяют транзакционные и аналитические нагрузки (`HTAP`) или улучшают движки запросов к файлам. Автор также упоминает облачные хранилища, способные обрабатывать неструктурированные данные, и специализированные форматы поверх объектного хранилища. Общий мотив этих попыток — совместить разнообразие данных и удобство аналитических запросов.

Автор формулирует цель нового подхода: объединить работу с разными типами данных и нагрузками, получить масштабируемость и экономичность `data lake` вместе с транзакционными возможностями и производительностью хранилища данных. Одновременно платформа должна оставаться достаточно простой для потребителей. Это целевые свойства архитектуры: конкретные результаты зависят от выбранных технологий и реализации.

## Lakehouse: хранение и вычисления

`Lakehouse` добавляет к `data lake` табличный транзакционный слой. В представлении автора облачное хранилище и открытые форматы файлов обеспечивают базу, а табличный формат ведёт метаданные и позволяет совместимым движкам работать с таблицами. Вычислительные мощности отделены от хранения и могут масштабироваться независимо.

![Уровень хранения lakehouse: объектное хранилище, открытые файлы и табличные форматы; независимые вычислительные движки обслуживают ETL, BI, потоковую обработку и ML](/assets/practical-lakehouse-architecture/ch01-lakehouse.png)

На схеме общий уровень хранения доступен разным движкам; каждый движок обслуживает поддерживаемые им нагрузки и форматы.

### Что lakehouse берёт у data lake и хранилища

Облачное объектное хранилище позволяет размещать структурированные, полуструктурированные и неструктурированные данные на одной основе. Оно масштабируется отдельно от вычислений и предлагает разные тарифы хранения. Открытые форматы файлов, например Parquet, ORC и Avro, описывают представление данных внутри файлов.

Табличный формат (`table format`) описывает, какие файлы относятся к таблице и как управлять её состоянием. Автор выделяет Apache Iceberg, Apache Hudi и Delta Lake. Они дают транзакционному слою возможности, которых недостаточно у набора обычных файлов: свойства ACID, управление изменениями и доступ к прошлым состояниям. Набор функций и поддержка операций различаются между форматами и движками. Iceberg, например, позволяет читать прежние версии таблицы и менять её схему. Для Hudi автор отмечает гарантии транзакций и откат к прежнему состоянию. Delta Lake хранит историю зафиксированных изменений, по которой можно проследить операции с таблицей. Эти возможности частично пересекаются. При выборе важны операции, которые конкретный движок умеет выполнять с выбранной версией формата.

В истории подхода автор упоминает Hadoop: HDFS уже использовали вместе с Hive и его `metastore` для доступа к данным в файлах. Однако поддержка ACID в Hive развивалась постепенно. В 2021 году исследователи представили на CIDR аргументы в пользу единой открытой платформы для хранилищ данных и сложной аналитики. [Статья на CIDR](https://www.cidrdb.org/cidr2021/papers/cidr2021_paper17.pdf).

### Движки и выбор технологий

Открытый формат не привязывает данные к единственному вычислительному движку. Автор приводит Apache Spark, Presto, Trino и Hive как примеры открытых движков, а Databricks, Dremio и Starburst — как поставщиков коммерческих решений. Одни и те же данные могут обслуживать ETL, BI и ML, если выбранные движки совместимы с файловым и табличным форматами.

При выборе стека полезно взять рабочую таблицу и проверить её на каждом движке. Один движок может прочитать таблицу, но поддерживает ли он обновление строк и новые типы полей? Сохранятся ли ограничения доступа при переходе на другой движок? Для BI автор отдельно советует проверить время ответа на характерных запросах с выбранным сочетанием формата и вычислительных ресурсов.

Автор рекомендует облачное объектное хранилище за масштабирование и разделение ресурсов, но допускает и локальный HDFS. Компромисс касается цены, доступности, эксплуатации и требований к размещению данных. Для Delta Lake автор советует сверять возможности нужной функции в открытой и коммерческой поставках.

## Характеристики и преимущества lakehouse

### Один уровень хранения и разные нагрузки

В описанной архитектуре отдельное хранилище для BI не обязательно: потребители обращаются к общему уровню хранения. Это сокращает необходимость переносить и синхронизировать данные между `data lake` и хранилищем данных. Меньше копирований — меньше мест, где могут возникнуть задержки, несовпадение схем или ошибки при перемещении.

На общем хранилище можно организовать пакетные преобразования, SQL-аналитику, ML и обработку событий. Для ML особенно важен доступ к изображениям, аудио и другим неструктурированным данным наряду с таблицами. В примере автора модели могут читать файлы напрямую, не требуя дополнительной копии агрегированных данных из хранилища обратно в `data lake`. При этом один уровень хранения не отменяет выбора инструментов и настройки производительности для каждой нагрузки. Для задач реального времени автор противопоставляет этому подходу Lambda Architecture: там пакетный и потоковый пути обработки разделены, в том числе из-за разных требований к задержке и SLA. Поддержка отдельных кодовых баз и их результатов усложняет такую систему. В предлагаемой модели пакетные задания и задания реального времени могут использовать общую кодовую базу, если выбранные инструменты это поддерживают.

Отделение вычислений позволяет увеличивать ёмкость хранения без обязательного увеличения вычислительных ресурсов и наоборот. Экономия зависит от тарифов, объёма запросов и эксплуатации; политики жизненного цикла и архивные уровни могут уменьшить стоимость длительного хранения. Детальный контроль доступа и согласованные правила остаются необходимыми, даже если данные физически находятся в одном месте. В двухуровневой системе эти правила приходится поддерживать для обоих хранилищ и следить за их согласованностью; общий слой уменьшает количество таких мест, но не решает задачу автоматически.

### Открытые данные и обмен

Использование открытых форматов уменьшает зависимость от единственного поставщика (`vendor lock-in`): совместимые движки могут работать с общими данными. Однако совместимость нужно проверять отдельно, иначе смена движка всё равно потребует доработок и коннекторов.

`Data sharing` — предоставление данных другим потребителям. Автор описывает Delta Sharing как открытый протокол обмена: производитель предоставляет доступ, а потребитель использует подходящий клиент и движок вместо получения отдельной файловой выгрузки.

![Производитель хранит файлы, потребитель обращается к серверу Delta Sharing за доступом и затем читает разрешённые файлы своим движком](/assets/practical-lakehouse-architecture/ch01-sharing.png)

Схема отделяет запрос доступа через сервер от последующего чтения файлов. Реализация должна управлять разрешениями и предоставлять только необходимые данные; использование открытого протокола не заменяет настройку безопасности.

### Каталог и качество данных

`Data lake` может превратиться в «болото данных», если в нём много файлов, но нет понятных описаний, правил и контроля доступа. Потребителям сложно найти данные и понять, можно ли им доверять. Каталог помогает найти набор, а сведения о владельце, происхождении и правилах доступа — решить, подходит ли он для работы.

`Schema enforcement` — проверка записи на соответствие схеме таблицы. Например, строковое значение в целочисленном поле может быть отклонено. `Schema evolution` позволяет учитывать допустимые изменения схемы, например появление нового атрибута. Если источник добавил поле, владелец таблицы может разрешить совместимое расширение схемы, сохранив прежние проверки для остальных полей. Какие изменения допустимы и что произойдёт при несовпадении типов, зависит от формата, движка и настроек записи.

### Time travel

`Time travel` позволяет запросить предыдущее состояние таблицы, если соответствующая история ещё сохранена и движок поддерживает такой запрос. Например, после исправления категории товара аналитик может сравнить текущее значение с тем, что было до изменения. Чтение по версии выбирает конкретное зафиксированное состояние; чтение по времени ищет состояние, доступное на указанную временную отметку. Синтаксис и правила выбора версии зависят от реализации, а удалённая история недоступна для такого чтения.

Если отчёт сохранил номер версии источника, аналитик может повторить расчёт на тех же данных. Если известно только время формирования отчёта, движок по истории фиксаций выбирает состояние таблицы на тот момент.

## Итоги главы

- Архитектура определяет компоненты платформы, связи и общие принципы до выбора конкретных инструментов.
- Источники, `ingestion`, хранение, обработка и потребление образуют поток данных от производителя к пользователю.
- Метаданные, безопасность, оркестрация и наблюдение за данными поддерживают весь поток.
- `Lakehouse` сочетает открытые файлы, табличный слой и вычислительные движки для разных нагрузок.
- Разделение хранения и вычислений позволяет масштабировать их независимо.
- Единый уровень хранения может сократить копирование, но не устраняет необходимость настройки доступа и качества.
- Совместимость форматов и функций движков нужно проверять до выбора стека.
- `Schema enforcement`, `schema evolution` и `time travel` зависят от возможностей конкретной реализации.

## Ключевые термины

| Термин | Значение |
|---|---|
| `data lake` | Хранилище разнородных данных в исходном или обработанном виде. |
| `lakehouse` | Архитектура с общим хранением, табличным слоем и поддержкой аналитики и ML. |
| Табличный формат | Правила и метаданные, связывающие файлы с состоянием таблицы. |
| `data governance` | Правила и ответственность за качество, доступ и использование данных. |
| `data sharing` | Предоставление данных потребителям с учётом разрешений. |
| `time travel` | Чтение сохранённого прежнего состояния таблицы. |

## Что это значит на практике

- Определите источники, допустимую задержку и потребителей до выбора движка и формата.
- Проверьте, какие операции чтения, записи и изменения схемы поддерживает каждая выбранная комбинация технологий.
- Задайте владельцев данных, права доступа, проверки качества и правила хранения истории.
- Оцените стоимость хранения и вычислений на ожидаемой нагрузке, включая обслуживание таблиц и обмен данными.

## Практика в DuckDB

В примере книги у товара меняется категория. В этой задаче у товара меняется остаток: попробуйте узнать, сколько единиц было доступно покупателю перед обновлением. Для опыта используем DuckDB CLI 1.5.1 и расширение DuckLake. Это отдельный пример к главе. Запустите `duckdb` из пустого рабочего каталога и выполните блоки по порядку в одном сеансе. При первом запуске нужен доступ к репозиторию расширений DuckDB. [Скачать SQL целиком](/assets/practical-lakehouse-architecture/ch01-time-travel.sql).

### Подготовьте две версии остатков

Каталог эксперимента живёт в памяти, а для файлов DuckLake выделена папка `lab_data`. После первой поставки сохраним номер и время фиксации. Затем склад пересчитает остаток чая с восьми упаковок до пяти.

```sql
INSTALL ducklake;
LOAD ducklake;
ATTACH 'ducklake::memory:' AS lab (DATA_PATH 'lab_data');

CREATE TABLE lab.stock (item VARCHAR, qty INTEGER);
INSERT INTO lab.stock VALUES ('чай', 8), ('кофе', 12);

SET VARIABLE stock_version = (SELECT max(snapshot_id) FROM lab.snapshots());
SET VARIABLE stock_time = (SELECT max(snapshot_time) FROM lab.snapshots());

UPDATE lab.stock SET qty = 5 WHERE item = 'чай';
SELECT item, qty FROM lab.stock ORDER BY item;
```

```text
кофе  12
чай    5
```

### Задания

1. Известен номер версии сразу после первой поставки. Сколько чая было в тот момент?
2. Теперь известна только временная отметка той же фиксации. Восстановите весь ассортимент на этот момент и проверьте, какой товар изменился.

<details>
<summary>Решение по номеру версии</summary>

```sql
SELECT qty
FROM lab.stock AT (VERSION => getvariable('stock_version'))
WHERE item = 'чай';
```

```text
8
```

</details>

<details>
<summary>Решение по времени</summary>

```sql
SELECT item, qty
FROM lab.stock AT (TIMESTAMP => getvariable('stock_time'))
ORDER BY item;
```

```text
кофе  12
чай    8
```

</details>

Оба запроса читают состояние после первой поставки. Обычный запрос после них по-прежнему покажет пять упаковок чая.
