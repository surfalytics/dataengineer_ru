**Главная мысль:** демо показывает, что приложение сработало один раз, а тесты проверяют его каждый раз. Просьба добавить тесты заодно заставляет агента навести порядок в коде. Чтобы решения пережили конец сессии, их записывают в файлы вроде `CLAUDE.md` и следят за бюджетом `context window`.

## О чём глава

В [главе 3](/book-summaries/ai/claude-code-up-and-running/03-talking-to-claude-code/) lyrics-trainer научился помнить строку, и автор проверил это руками в браузере. Глава 4 объясняет, как превратить такое демо в `cabin` — скромный, но надёжный проект. Темы: тесты и рефакторинг, тонкий слой для DOM (`DOM glue`), память проекта, контекст как бюджет, `AGENTS.md` и `/add-dir`.

## Демо — это не тест

Ручная проверка сохранения в главе 3 полезна, но это демо. Автор считает демо самым дорогим и ненадёжным способом проверки: оно не трогает граничные случаи и сбои, а разработчик, который хочет увидеть успех, редко пытается систему сломать. Демо доказывает, что приложение сработало один раз, пока вы смотрели. Тесты же запускаются автоматически и сравнивают результат с известным ответом.

При этом автор не требует теста на каждую строку. Его правило: тестируйте то, что нужно тестировать, то есть обязательные условия, сбои и граничные случаи. Трудно здесь одно: решить, что именно стоит проверять. Например, CSS тренажёра не нужен `unit test` (тест одной функции без остальной системы), а номеру строки, переходу с последней строки на первую и запасному варианту для испорченного сохранения тесты нужны.

## Вопрос, который меняет код

Глядя на приложение, сделанное через `vibe coding`, автор первым делом ищет тесты. Обычно их нет, и тогда агента просят их добавить. Часто это запускает рефакторинг, то есть изменение устройства кода без изменения поведения. Запрос в нашем пересказе:

```text
Добавь автоматические тесты для lyrics-trainer. Нужны как минимум тесты на
переход к следующей строке, переход с последней строки на первую,
продолжение с позиции из localStorage и возврат к строке 0, если
сохранённый индекс испорчен.

Поведение в браузере не меняй. Обойдись без фреймворков.
Сначала покажи, какие тесты хочешь добавить. Если текущая структура мешает
их написать, объясни почему и предложи самое маленькое изменение.
```

Запрос не говорит, как менять код: автор рассчитывает, что агент сам предложит вынести JavaScript из файла, где смешаны разметка, стили, клики и `localStorage`.

## Спросите агента, почему код трудно тестировать

На вопрос «почему это неудобно тестировать?» Claude Code отвечает так. Вся логика сидит в блоке `<script>` внутри `index.html`, и импортировать её нельзя. Даже чистое правило «после строки 13 из 14 идёт строка 0» склеено с кликом, записью в `localStorage` и обновлением DOM. Проверить его можно только end-to-end тестом с имитацией браузера и клика, а такой тест медленный и хрупкий. Решение — вынести логику в модуль, который получает зависимости параметрами, и оставить сверху тонкий слой для DOM.

Отсюда вывод автора: первый клиент кода — это тест. Если код трудно тестировать, им, скорее всего, трудно и пользоваться. В режиме `doghouse` (маленький проект для себя) этот сигнал можно игнорировать, а в `cabin` уже нельзя: от кода могут зависеть другие.

## Рефакторинг ради тестов

Приложение умеет шесть вещей: показать строку, перейти к следующей, вернуться к первой после последней, сохранить индекс, продолжить с него и проигнорировать испорченный индекс. Это список для тестов и скрытый план архитектуры: функции делятся на навигацию, сохранение и вывод на страницу.

`DOM glue` — это тонкий код, который находит элементы страницы, вешает обработчики и вызывает настоящую логику. На схеме слева исходный файл, справа модули: зелёные проверяются тестами без браузера.

![Схема рефакторинга: один index.html, где смешаны разметка, состояние, клики и localStorage, превращается в main.js, lineTrainer.js и storage.js; тесты Vitest проверяют lineTrainer.js и storage.js без браузера, в тестах вместо localStorage используется заглушка](/assets/claude-code-up-and-running/ch04-testable-core.png)

В прогоне автора Claude Code сначала предложил ещё меньшую структуру: встроенный тест-раннер Node и один файл двойного назначения. Для просьбы «самое маленькое» это разумно, но автору нужна была другая раскладка, и он поправил агента:

```text
Сделай по схеме тестируемости: lineTrainer.js для навигации по строкам,
storage.js для сохранения, main.js для связки с DOM, Vitest для unit-тестов.
Оставь код маленьким, но держи эти обязанности раздельно.
```

```text
lyrics-trainer/
  CLAUDE.md
  index.html
  package.json
  src/
    lineTrainer.js
    storage.js
    texts.js
    main.js
  test/
    lineTrainer.test.js
    storage.test.js
```

Урок в том, что «самое маленькое» — не волшебное слово. Если структура меньше, чем нужно вашей цели или соглашениям репозитория, скажите об этом и сузьте задачу.

## Маленькое тестируемое ядро

Ядро выглядит скучно, и автор считает это плюсом. Каждая функция делает одно дело и ничего не знает о кнопках, CSS и `localStorage`. Это принцип единственной ответственности (Single Responsibility Principle) из SOLID. Наша версия:

```js
// Ядро: правила навигации по строкам. Не знает ни про DOM, ни про localStorage.

// Любое плохое значение (не число, меньше 0, за концом текста) превращаем в 0.
export function normalizeIndex(value, length) {
  const index = Number(value);
  if (!Number.isInteger(index) || index < 0 || index >= length) {
    return 0;
  }
  return index;
}

export function createLineTrainer(lines, startIndex = 0) {
  let index = normalizeIndex(startIndex, lines.length);
  return {
    currentLine: () => lines[index],
    currentIndex: () => index,
    // После последней строки возвращаемся к первой.
    next() {
      index = (index + 1) % lines.length;
      return lines[index];
    },
  };
}
```

В модуле сохранения главное решение — хранилище приходит параметром. Приложение передаёт браузерный `localStorage`, а тест передаёт заглушку с теми же методами `getItem` и `setItem`. Так вопрос «что значит сохранить» отделён от вопроса «где браузер хранит данные», и к этому агента подтолкнула именно просьба о тестах.

```js
// Сохранение позиции. Хранилище передаём параметром:
// в браузере это localStorage, в тестах — простой объект-заглушка.
import { normalizeIndex } from "./lineTrainer.js";

export const DEFAULT_KEY = "lyricsTrainer.lineIndex";

export function loadSavedIndex(storage, lineCount, key = DEFAULT_KEY) {
  return normalizeIndex(storage.getItem(key), lineCount);
}

export function saveIndex(storage, index, key = DEFAULT_KEY) {
  storage.setItem(key, String(index));
}
```

Тесты такие же простые:

```js
it("после последней строки возвращается к первой", () => {
  const trainer = createLineTrainer(lines, lines.length - 1);
  expect(trainer.next()).toBe(lines[0]);
  expect(trainer.currentIndex()).toBe(0);
});
```

Полный проект с `index.html`, `main.js` и тестами лежит в [scripts/claude-code-code/ch04_lyrics_trainer](https://github.com/surfalytics/dataengineer_ru/tree/main/scripts/claude-code-code/ch04_lyrics_trainer).

## Тонкий слой для DOM должен быть скучным

После рефакторинга `main.js` только создаёт тренажёр с сохранённым индексом, а по клику вызывает `next()`, сохраняет индекс и перерисовывает строку. Он всё ещё трогает DOM и `localStorage`, но правил в нём нет. Поэтому, если упадёт браузерный тест, сразу понятно, где искать: в связке со страницей или в логике.

## Запустите тесты, потом посмотрите на всё приложение

Автор удивился, что Claude Code не запустил новые тесты сам, пока его не попросили. Если у вас так же, попросите запустить `npm test`. У автора вышло 2 файла и 15 тестов за 129 мс. Наша версия из 9 тестов выводит:

```text
 Test Files  2 passed (2)
      Tests  9 passed (9)
```

Модули нужно отдавать по HTTP, поэтому страницу теперь открывают через локальный сервер: `npm start`.

Если тесты падают, попросите агента их починить:

```text
Набор тестов Vitest падает. Прочитай вывод, объясни вероятную причину,
потом исправь код и тесты, пока всё не пройдёт. Поведение в браузере
не меняй. В конце перечисли, что изменил и что проверил.
```

Слова «объясни причину» важны: иначе агент может убрать симптом и не назвать допущение, которое к нему привело. Для таких циклов есть команда `/loop`, но новые модели обычно и сами повторяют попытки, пока все тесты не пройдут.

После зелёных тестов автор просит агента снова посмотреть на всё приложение: состояние, пробелы в тестах, имена, доступность и места, где одностраничной структуре тесно. Менять ничего нельзя, нужен только отчёт с важностью и рекомендацией. Первый запрос сужает внимание агента, а второй снова расширяет его до дизайна.

Сколько тестов достаточно, помогает оценить покрытие кода тестами (code coverage). Автор не гонится за 100%, а тесты, жёстко привязанные к реализации, считает вредными: они мешают будущему рефакторингу. Позже автор подключит SonarCloud с порогом покрытия около 80% и его `MCP server`, чтобы Claude Code сам получал результаты.

## Память проекта: CLAUDE.md

Рефакторинг дал модули, тесты и решения, но с концом сессии ничего из этого не сохранится само. Для этого нужна память проекта (`project memory`). Claude Code хранит её в текстовом файле `CLAUDE.md`. Таких файлов может быть несколько: в корне проекта, в `.claude` проекта, в `~/.claude` пользователя и в подпапках. При старте сессии Claude Code объединяет всю иерархию.

Файл можно создать командой `/init` и потом поправить. Длинным он быть не должен, потому что целиком загружается в контекст каждой сессии. Хороший `CLAUDE.md` — минимальный набор инструкций, с которым агент ведёт себя последовательно. Наша версия для тренажёра:

```markdown
# Lyrics Trainer

Браузерное приложение: учим текст из общественного достояния по одной строке.
Без фреймворков, логика вынесена в тестируемые модули.

## Архитектура
- `index.html` — оболочка страницы.
- `src/` — модули с логикой, их покрывают тесты.
- `src/main.js` — только связка с DOM.
- Тесты лежат в `test/` и запускаются через Vitest.

## Команды
- `npm test` — unit-тесты.
- `npm start` — локальный сервер на http://localhost:8000.

## Соглашения
- Сначала простые модули JavaScript, фреймворк — только по явной просьбе.
- API браузера прячем за маленькими функциями, чтобы ядро тестировалось.
- Без шага сборки.

## Порядок работы
- Перед заметным изменением предложи план.
- После новой функции запусти тесты и посмотри на всё приложение целиком.
```

Автор предупреждает: не складывайте в `CLAUDE.md` всё, что знаете. Пишите факты о проекте и постоянные инструкции, а остальное выносите в файлы и подключайте `@`-импортом (строка `@docs/testing.md`). `README.md` пишут для людей, поэтому не дублируйте в нём инструкции для агента.

## Два вида памяти

`CLAUDE.md` пишете вы, а `auto memory` — это заметки, которые Claude пишет себе сам по вашим поправкам и повторяющимся приёмам. Автор советует видеть не один файл памяти, а слои, которые попадают в сессию.

![Слои, которые попадают в контекст запроса Claude Code: поведение продукта, инструкции пользователя и организации, проекта, путей, auto memory, текущая сессия и prompt](/assets/claude-code-up-and-running/ch04-memory-layers.png)

Слева слои от общего к конкретному, справа их вклад в контекст. Что важно помнить:

| Слой | На что обратить внимание |
|---|---|
| Пользователь и организация | Опасно, если локальную привычку записали как общее правило |
| Пути | Правила загружаются вместе с подходящими файлами и после сжатия контекста могут пропасть |
| `auto memory` | Лежит в `~/.claude/projects/<project>/memory/` на вашей машине, в git не попадает, общая для всех worktree репозитория |
| Ваш `prompt` | Обычно самый сильный сигнал, он перебивает размытый унаследованный контекст |

Память — это контекст, а не жёсткое ограничение (`enforcement`). Она повышает шанс правильного поведения, но не заменяет права, `hooks` и `sandbox` из главы 5. Правила для части путей, например `tests/**/*.js`, кладут в `.claude/rules/`.

Проверяют память командой `/memory`: она показывает загруженные `CLAUDE.md` и правила, включает `auto memory` и открывает её папку. Автор описывает типичный сбой. В Python-части репозитория Claude узнал, что «мы предпочитаем pytest», а потом предложил pytest для JavaScript-кода на Vitest. Это не случайность: унаследованный контекст применили слишком широко. Запустите `/memory`, исправьте или удалите заметку в `auto memory`, сузьте правило в `~/.claude/CLAUDE.md` или запишите про Vitest в правило рядом с тестами.

## Контекст — это бюджет

Каждый запрос несёт всё, что было в сессии: разговор, файлы, вывод команд, сводки и `CLAUDE.md`. По опыту сообщества, качество ответов падает по мере заполнения `context window`, даже если всё помещается. У предела Claude Code сам сжимает контекст, но это может случиться посреди задачи, и важные для вас детали пропадут. Ручная команда `/compact` тоже теряет детали, зато момент выбираете вы.

Перед сжатием полезно запустить `/context`. Она показывает в токенах и процентах, сколько занимают system prompt, инструменты, память, `skill`, разговор и сколько места свободно.

![Что заполняет context window: system prompt, инструменты, CLAUDE.md, skills и сообщения; при полном окне автосжатие теряет детали, а /compact с целью и проверочная сводка дают контроль; важное заранее лежит в CLAUDE.md](/assets/claude-code-up-and-running/ch04-context-budget.png)

С окном 200K сжатие случается часто. С окном 1M оно реже, но если ответы стали хуже, а в контексте уже 300–400K токенов, сжать стоит и при свободном месте. Важное заранее сохраните в файл, а `/compact` дайте цель:

```text
/compact Сохрани текущую архитектуру lyrics-trainer, план тестов, решение
обойтись без фреймворков, граничные случаи localStorage и открытые задачи.
```

После сжатия попросите контрольную сводку и поправьте её, пока не сработало автоматическое сжатие:

```text
Перечисли, что ты считаешь верным о проекте сейчас: архитектура, команда
для тестов, незаконченная работа и решения, к которым не возвращаемся
без моей просьбы.
```

## Альтернатива: AGENTS.md

С именами файлов есть историческая ловушка. Anthropic первой назвала файл `CLAUDE.md`, Google для Gemini CLI (теперь Antigravity CLI) выбрала `GEMINI.md`, а OpenAI с Codex предложила общий стандарт `AGENTS.md`. Google согласилась, а Anthropic, по крайней мере на момент написания книги, нет. Поэтому Claude Code читает `AGENTS.md`, только если его подключить `@`-импортом:

```markdown
# CLAUDE.md

@AGENTS.md

## Заметки для Claude Code

- Если context window почти полон, перед большим рефакторингом делай /compact.
- Перед широкими изменениями используй plan mode.
- Команды бери из AGENTS.md, если этот файл не говорит иначе.
```

Команда `/init`, скорее всего, сама перенесёт нужное из `AGENTS.md` в новый `CLAUDE.md`, но это стоит проверить. Главный урок автора: память — не магия, а просто файлы. Если они устарели, размыты или не загружаются, пользы от них нет. «Память» здесь — не RAM, а файлы на диске, которые переживают конец сессии.

## Другие папки в проекте: /add-dir

Иногда расширять нужно саму границу проекта: фронтенд лежит рядом с API, библиотека — рядом с приложением, а новый проект делают по образцу старого. По умолчанию агент работает только в текущей папке, но команда `/add-dir ../my-other-project` добавляет в сессию ещё одну. Добавленная папка тоже занимает контекст.

Так автор переносит между репозиториями слайдов GitHub workflow, который собирает PDF и публикует релиз: подключает первый проект через `/add-dir` и просит повторить. Описывать это в пользовательском `CLAUDE.md` незачем, ведь процесс нужен не везде.

## Итоги главы

- Демо доказывает, что приложение сработало один раз, а тесты проверяют его каждый раз.
- Тестируют обязательные условия, сбои и граничные случаи, а не всё подряд.
- Просьба добавить тесты часто ведёт к рефакторингу: логика уходит в модули, которые проверяются без браузера.
- Зависимости вроде `localStorage` лучше передавать параметром, чтобы в тесте их заменила заглушка.
- `CLAUDE.md` должен быть коротким, а `auto memory` нужно проверять через `/memory`.
- Память — это контекст, а не `enforcement`.
- Контекст — это бюджет: смотрите `/context` и сжимайте сами через `/compact` с целью.

## Ключевые термины

| Термин | Значение |
|---|---|
| тестируемое ядро | Логика отдельно от интерфейса, её проверяют без браузера |
| тонкий слой для DOM (`DOM glue`) | Связывает страницу с ядром, своих правил не содержит |
| `CLAUDE.md` | Инструкции, которые вы пишете сами |
| `auto memory` | Заметки, которые Claude пишет себе сам |
| сжатие контекста (`compact`) | История заменяется сводкой, часть деталей теряется |

## Что это значит на практике

- Выносите преобразования `pipeline` в чистые функции, а подключение к базе передавайте параметром, тогда pytest проверит логику без хранилища.
- В `CLAUDE.md` репозитория с dbt запишите команды и соглашения по именам, но запрет трогать prod делайте правами.
