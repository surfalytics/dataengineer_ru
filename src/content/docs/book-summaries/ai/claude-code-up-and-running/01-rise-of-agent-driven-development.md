**Главная мысль:** с агентом вроде Claude Code узким местом становится не набор кода, а управление работой. Агент делает production-работу, а человек задаёт направление, проверяет результат и решает, хорош ли он. Сколько дисциплины нужно, зависит от ставок проекта, а не от числа строк кода.

## О чём глава

Это первая глава книги. Она отвечает на вопрос: что меняется в разработке, когда в проекте работает агент. Общий план книги — на [странице конспекта](/book-summaries/ai/claude-code-up-and-running/).

- `Agent-Driven Development` и цена сопровождения кода.
- Три масштаба проекта: `doghouse`, `cabin`, `skyscraper`.
- Claude Code как `harness` вокруг модели, цикл запроса и `agent teams`.

## Agent-Driven Development: агент делает, человек направляет

Когда агент сам работает в проекте, трудная часть — уже не набор кода, а управление работой: назвать результат, задать условия успеха, проверить итог и решить, когда первого ответа мало.

Эту практику автор называет `Agent-Driven Development`, или `AgDD`. Агент ведёт production-работу, то есть пишет и меняет код, а человек отвечает за направление, проверку и оценку. Термин уже используют в отрасли, и автор не считает его своим. Вклад книги — три масштаба проекта и такое разделение ролей между агентом и человеком.

Проблемы, о которых пишет книга, не новые: требования меняются, тесты устаревают, CI падает. Claude Code их не убирает, но меняет, кто делает работу и где прячутся ошибки.

Автор предупреждает: цель — не просто больше кода быстрее. Сопровождение (maintenance) всегда было главной статьёй расходов: по руководству NIST 1985 года — 60–70% стоимости ПО, по Роберту Глассу — 40–80%. Вдвое больше кода — вдвое больше того, что надо понимать, тестировать и защищать. Поэтому `AgDD` окупается, только когда агент снижает цену полезного изменения, а не цену набора текста.

## Когда шуточный проект становится серьёзным

Однажды читатель в шутку дал автору Kindle и фломастер, чтобы тот подписал электронную книгу. Автор решил, что это можно сделать всерьёз: выдавать PDF-сертификат владения со сканом подписи, подписанный цифровым сертификатом X.509, и с QR-кодом на страницу проверки. Но библиотеки (BouncyCastle, PDFBox) оказались низкоуровневыми и скучными, и автор отложил идею на неопределённый срок.

С Claude Code эта работа стала посильной. Через несколько часов работал сервис на Spring Boot, и агент даже помог его развернуть. Первая версия была типичным `vibe coding`: агент пишет код по описанию, а человек проверяет только, что всё работает. Для шутки это было уместно.

Но проект касался подписей и развёртывания в production, и автор не мог оставить его таким. Сейчас у сервиса есть слои, Java 25 и property-based тесты на важных для безопасности частях. Проект по-прежнему скромный, но на него уже полагаются люди, и это меняет методологию.

## Три масштаба сложности ПО

Сервис не просто вырос, он сменил масштаб. Автор делит проекты на три вида:

- `doghouse` — маленький проект на выходные, который никто не проверяет. Здесь уместен `vibe coding`.
- `cabin` — скромный, но надёжный проект. Нужны явные договорённости (`trust contract`), границы и тестируемое ядро.
- `skyscraper` — корпоративная система: координация, проверяемый CI/CD, общие процессы, ревью безопасности.

![Три масштаба проекта: doghouse для vibe coding, cabin с границами и тестируемым ядром, skyscraper с координацией и CI/CD; первая версия certificate-service — doghouse, нынешняя — cabin](/assets/claude-code-up-and-running/ch01-three-scales.png)

Проект переходит в `cabin`, когда на него начинают полагаться люди, а в `skyscraper` — когда в нём начинают работать другие люди. Первая версия сервиса была `doghouse`, нынешняя — `cabin`, и автор осознанно перевёл сервис из одного режима в другой тем же инструментом, Claude Code.

У сервиса есть пользователи, криптография и CI, и автор думал добавить «офисное здание» между `cabin` и `skyscraper`. Он отказался: граница между ними — координация, а не размер. Формальные ревью, общий pipeline и документация, без которой другие не сделают свою работу, делают проект `skyscraper`, даже маленький.

Беда начинается, когда режимы смешивают. `Doghouse` с шестью неделями проектирования так и не появится. `Skyscraper` без тестов и с выпуском в production к пятнице сломается дорого.

## Агент в терминале

Claude Code — это `harness` вокруг модели Anthropic. Модель (Fable, Opus или Sonnet) — движок: она читает, планирует и решает. Всё остальное на схеме и есть Claude Code.

![Claude Code как harness: в центре модель-движок, вокруг цикл агента, терминал, контекст проекта, инструменты, запросы разрешения, MCP, hooks, skills и понимание рабочей папки](/assets/claude-code-up-and-running/ch01-harness.png)

Почти все приёмы книги относятся к `harness`, а не к модели. Автор пишет: «Модель — это ручка настройки», то есть лишь один из параметров.

Claude Code — не чат: разговор ведёт к действиям над файлами проекта, и вы их проверяете. Он не похож и на GitHub Copilot, который дописывает код строка за строкой. Агент планирует многошаговую работу: решает, писать ли сначала тест, и видит, что нужно изменить три файла в определённом порядке.

### Где работает Claude Code

Кроме терминала, Claude Code работает в приложении Claude, веб-версия, расширения для IDE и мобильная версия. Автор советует не запоминать список: он изменится, а работа всё равно держится на контексте, инструментах и правах. В книге основной интерфейс — терминал.

### Цикл запроса

После запроса Claude Code загружает контекст, планирует шаги и использует инструменты. Перед рискованным действием он спрашивает разрешения (`permission gate`), затем выдаёт результат и ждёт вашей реакции.

Схема цикла с развилкой «чтение или запись» — в [главе 2](/book-summaries/ai/claude-code-up-and-running/02-getting-started/#первый-вопрос-и-цикл-запроса).

Цикл — это механика, а `AgDD` — дисциплина вокруг неё: что просить, что одобрять, что отклонять и когда работа переросла начальный режим.

## Темы Agent-Driven Development

Книга возвращается к трём темам: инструмент, работа и роль разработчика.

### Механика: инструмент

Нельзя управлять тем, чего не понимаешь. Поэтому нужно знать, какие инструменты вызывает агент, какие действуют разрешения и что делает `CLAUDE.md`, но учить это нужно на реальных задачах, а не списком.

### Сама работа выглядит иначе

В `doghouse` хватает `vibe coding`. В `cabin` нужны обсуждение дизайна до кода, тесты, память проекта и явные границы доверия. `Skyscraper` добавляет `skills`, `hooks`, `subagent`, `agent teams`, CI/CD и ревью безопасности. Дисциплину задают ставки: цель, круг пользователей, срок жизни и ответственность, а не число строк кода (LOC).

Агент снимает страх перед изменениями: жалеть код, на который ушло три минуты, а не три недели, незачем. Поэтому легче переименовать переменную во всём коде или переписать модуль. Автор советует после крупной правки просить агента снова проверить всю систему, потому что второй проход ловит проблемы, которые первый создал или выявил.

### Роль разработчика меняется

Claude Code работает как встроенный наставник: спросите, зачем этот импорт или почему выбран этот паттерн. Знание приходит, когда оно нужно, и со временем перестаёшь замечать, на каком языке код.

Принципы дизайна важны как никогда. Production-работу берёт AI, а человеку остаётся сказать, что значит «хорошо», выбрать паттерны и отличить настоящую сложность от случайной. Новичок без этого чутья получит правдоподобный код, который тонко ломается, и не поймёт почему. Зато агент помогает учиться: спросите, чист ли код, и он подскажет исправление.

## Агенты на реальном коде

Если у работы есть независимые части, Claude Code может собрать команду. Это уже продвинутый уровень: сначала хорошие запросы, потом память проекта и права. Автор включил экспериментальную функцию `agent teams` и дал задачу на своём репозитории. Вот похожий запрос для проекта на dbt:

```bash
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
claude
```

```text
Собери agent team для этого dbt-проекта. Нужны три участника:
- один ищет модели без тестов и пробелы в покрытии;
- один ищет проблемы безопасности: секреты в profiles.yml, лишние права;
- один обновляет README и описания моделей, если они устарели.
Пусть работают параллельно, где можно, а потом сведи итоги.
Отчитайся: что изменено, что нашёл каждый участник
и какие решения оставить человеку.
```

На репозитории автора Claude Code сам распределил работу: два участника только читали код, а агента для документации он ограничил файлами `README.md` и `CLAUDE.md`, чтобы тот не мешал остальным. Ревью тестов нашло интеграционный тест, который молча пропускался. Ревью безопасности нашло проблемы с аутентификацией и путями к файлам. Третий участник исправил устаревшие номера версий и описал недостающие endpoints.

Автора удивило не то, что агент умеет ревьюить, а то, что самому не пришлось делить работу вручную. Он назвал результат, три точки зрения и нужный отчёт, то есть спроектировал саму систему работы.

У `agent teams` есть цена: команда из трёх тратит токены примерно втрое быстрее. Функция выключена по умолчанию и не подходит для последовательной работы или правок одних и тех же файлов. Книга вернётся к ней в главе 7.

## Итоги главы

- Claude Code — не быстрое автодополнение, а `harness` вокруг модели: контекст, инструменты, права и цикл запроса.
- В `Agent-Driven Development` агент делает работу, а человек отвечает за направление, проверку и оценку.
- Цель не в объёме кода, потому что каждая строка увеличивает цену сопровождения.
- Дисциплину выбирают по ставкам проекта: `doghouse`, `cabin` или `skyscraper`.
- Граница между `cabin` и `skyscraper` — координация людей, а не размер кода.
- Смешивать режимы опасно: проект либо не выйдет, либо дорого сломается.
- Оценка дизайна становится ценнее, а агент помогает её развивать.

## Ключевые термины

| Термин | Значение |
|---|---|
| `Agent-Driven Development` (`AgDD`) | Агент делает работу, человек направляет и проверяет |
| `harness` | Всё вокруг модели: цикл, контекст, инструменты, права |
| Цикл запроса (`request loop`) | Контекст, план, инструменты, разрешение, результат, реакция |
| `vibe coding` | Агент пишет код, человек проверяет только, что работает |
| `doghouse` / `cabin` / `skyscraper` | Проект на выходные, надёжный, корпоративный |
| `agent teams` | Несколько сессий работают параллельно и сводят итоги |

## Что это значит на практике

- Перед запросом запишите результат и условия успеха: какие модели и тесты должны пройти.
- Разовый скрипт выгрузки — это `doghouse`, а pipeline, от которого зависят дашборды, — уже `cabin`.
- Код агента тоже придётся сопровождать, поэтому удаляйте лишние модели и макросы.
- После крупной правки просите агента заново проверить весь проект.
