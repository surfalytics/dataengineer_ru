**Главная мысль:** Skill — это папка с инструкциями, которую Claude подключает сам, когда задача ей подходит. Вы один раз записываете, как делать работу правильно, и Claude делает её так каждый раз. Главное в skill — поле `description`: по нему Claude решает, нужен ли skill сейчас.

## О чём глава

В [главе 13](/book-summaries/ai/claude-ai-bible/13-claude-code/) Claude Code брал постоянные правила проекта из `CLAUDE.md`. Эта глава о пакете знаний под одну задачу, который грузится только по необходимости. Темы: устройство skill, роль `description`, первый skill по шагам, скрипты и образцы, проверка, библиотека skill и обмен ими.

Автор начинает с примера. Одна сотрудница знает всё про коммерческие предложения: порядок разделов, обязательный абзац юристов, нужный тон. Остальные забывают абзац и берут старый шаблон цен. Skill упаковывает её знания так, чтобы любой человек или Claude делали предложение её способом.

![Как Claude подключает skill: читает description всех skill, при совпадении грузит тело SKILL.md, а скрипты и образцы только по шагу инструкции; внизу три слоя загрузки](/assets/claude-ai-bible/ch14-skill-loading.png)

Запрос сравнивается с описаниями, и только при совпадении в контекст попадает тело skill. Нижний ряд показывает, когда каждый слой занимает контекст.

## Какую проблему решает skill

Раньше приходилось объяснять всё заново в каждом разговоре: три абзаца про формат, тон и частые ошибки. Каждый раз текст выходил немного другим, и результат «плыл», а коллега писал свои абзацы и получал свой результат. Опыт, который живёт в голове или в старых переписках, не масштабируется.

Skill выносит этот опыт в файл, который идёт вместе с задачей. Его пишут один раз, а применяется он сам, поэтому новичок делает работу правильно с первого дня. Вторая польза — чистый контекст: подробные инструкции не грузятся в каждый разговор, а ждут своей задачи.

## Из чего состоит skill

Skill — это папка с одним обязательным файлом `SKILL.md` из двух частей:

- **Метаданные** — блок «ключ: значение» в начале файла с полями `name` и `description`. Описание автор называет самым важным предложением: оно говорит Claude, когда skill нужен.
- **Тело** — инструкции в Markdown: шаги, правила, форматы, примеры. Это как хорошая страница внутренней wiki, только для Claude.

Ещё в папку можно положить скрипты для точных, детерминированных операций (расчёт, преобразование файла) и ресурсы: шаблоны, образцы, чек-листы.

Части skill грузятся слоями. Описание в одном-двух предложениях видно всегда. Тело грузится при срабатывании, а скрипты и ресурсы — только когда до них дошёл шаг инструкции. Поэтому даже справочник на тысячу строк ничего не стоит, пока он не нужен.

## Когда срабатывает skill: всё решает description

Skill не вызывают по имени, как команду. Claude сам читает описания доступных skill и сравнивает их с запросом: совпало — skill грузится, нет — skill не используется. Значит, `description` — это не документация, а логика сопоставления. В нём называют задачу, ситуации и слова, которыми люди на самом деле просят эту работу.

Тело отвечает на вопрос «как делать» и может быть длинным. Описание проверяется постоянно, поэтому оно короткое и точное. Правило автора: условия — в описании, метод — в теле.

Самая частая ошибка — skill, который не срабатывает. Skill на 600 слов про возврат денег с описанием «Handles refunds» молчит на просьбу «верни клиенту деньги»: этих слов в описании нет. Поэтому в описание добавляют разные формулировки той же просьбы.

## Первый skill по шагам

Пример автора выдуманный: книжная сеть Marlowe & Finch с филиалами в разных округах. Руководители округов пишут недельные сводки продаж каждый по-своему, и головной офис не может их сравнить. Шаги такие:

1. **Назвать умение точно:** не «reports», а `weekly-store-summary`.
2. **Взвесить каждое слово описания:** недельная сводка, отчёт по филиалам, итоги продаж, «цифры за понедельник».
3. **Написать тело:** разделы, их порядок, правила, тон и то, что нельзя пропускать.

Наша версия файла на русском короче книжной, но устроена так же:

```markdown
---
name: weekly-store-summary
description: >
  Готовит стандартную недельную сводку по филиалам книжной сети из сырых цифр продаж.
  Используй, когда просят недельную сводку, отчёт по филиалам, итоги продаж
  за неделю, «цифры за понедельник» или сравнение филиалов с прошлым годом.
---

# Недельная сводка по филиалам

Цель: управляющий за минуту видит, каким филиалам нужно внимание.
Одинаковый формат важнее красивых слов.

## Что нужно на входе

По каждому филиалу: выручка за неделю, выручка за ту же неделю год назад,
число покупок, число посетителей. Если чего-то нет, спроси. Не угадывай.

## Формат (всегда в этом порядке)

1. Заголовок: общая выручка и изменение к прошлому году в процентах.
2. Таблица: филиал, выручка, изменение к прошлому году, покупки, посетители, конверсия.
3. Лучший и худший филиал по изменению к прошлому году.
4. Список наблюдения: филиалы с падением выручки или с конверсией ниже 8%.
   Если таких нет, напиши: «В списке наблюдения никого нет».
5. Одно конкретное действие на следующую неделю.

## Правила

- Конверсию считай только скриптом: `python3 scripts/conversion.py <покупки> <посетители>`.
- Деньги: символ валюты, разделитель тысяч, без копеек.
- Тон сухой и короткий. Без слов «отлично» и «ужасно».
- Не делай выводов, которых нет в цифрах.

## Образец

Структура и длина — как в `resources/example-summary.md`.
```

В описании собраны слова, которыми управляющий просит отчёт, а тело задаёт точный порядок разделов, правила и ссылки на скрипт и образец. Автор советует написать такой файл для своей повторяющейся задачи: по его оценке, это займёт минут двадцать.

## Хорошие и плохие описания

Автор сравнивает три описания для skill, который оформляет отчёт об инциденте после сбоя:

| Описание | Оценка |
|---|---|
| «Отчёты об инцидентах» | Плохо: сработает ли он на «опиши, что случилось во время сбоя», — как повезёт |
| «Skill для разных отчётов, полезен во многих ситуациях, где нужна документация» | Плохо: длинно и размыто, сработает на всё или ни на что |
| «Оформляет отчёт после сбоя в production. Используй, когда нужно описать инцидент, написать postmortem или записать, что случилось и как это исправили» | Хорошо: названы результат, ситуация и фразы для запроса |

Рецепт автора: назовите результат и ситуацию, перечислите слова живых людей. Помогает не длина, а точность.

## Скрипты и ресурсы в папке

Тело хорошо для суждений и формата. Но то, что должно выполняться одинаково каждый раз, лучше отдать скрипту. Конверсию (покупки, делённые на посетителей) Claude обычно посчитает верно, но «обычно» не годится для числа, по которому принимают решения. Поэтому инструкция велит запустить скрипт. Наша версия:

```python
"""Конверсия филиала: покупки / посетители, в процентах.
Запуск: python3 scripts/conversion.py <покупки> <посетители>"""
import sys


def conversion(units: float, footfall: float) -> str:
    if footfall == 0:  # посетителей не было: делить нельзя
        return "0.0%"
    return f"{units / footfall * 100:.1f}%"


if __name__ == "__main__":
    print(conversion(float(sys.argv[1]), float(sys.argv[2])))
```

Запуск для трёх филиалов, у последнего не было посетителей:

```bash
python3 scripts/conversion.py 412 3870
python3 scripts/conversion.py 95 1420
python3 scripts/conversion.py 10 0
```

```text
10.6%
6.7%
0.0%
```

Модель отвечает за текст и выводы, скрипт — за точность. Такое разделение автор считает признаком хорошего skill. Ресурсы работают так же: по образцу `resources/example-summary.md` Claude повторяет структуру и длину сводки. Папка целиком:

```text
weekly-store-summary/
├── SKILL.md
├── scripts/
│   └── conversion.py
└── resources/
    └── example-summary.md
```

## Проверка и доработка

Skill — это программа, и с первого раза он редко работает идеально. Автор предлагает две проверки:

- **Срабатывание.** В новом разговоре просите так, как попросил бы живой человек: «дай цифры за понедельник». Не сработало — описание узкое, добавьте в него эту фразу. Сработало на чужой запрос — описание широкое, сузьте его.
- **Результат.** Соблюдён ли формат, запущен ли скрипт, спросил ли Claude про пропуски или выдумал их? Такие ошибки исправляют в теле.

![Две проверки skill: проверка срабатывания ведёт к правке description, проверка результата ведёт к правке тела](/assets/claude-ai-bible/ch14-testing-loop.png)

Меняйте по одной вещи: обычно виновато одно неясное предложение, а не весь skill. Ещё автор советует намеренно ломать срабатывание: спрашивать торопливо, синонимами и соседними вопросами, на которые skill должен молчать.

## Как писать тело, чтобы Claude ему следовал

Claude буквально выполняет конкретные указания и импровизирует там, где их нет. Поэтому будьте конкретны там, где вам важно. Четыре приёма автора:

- **Сначала цель, потом шаги.** Фраза «Сводка нужна, чтобы управляющий сразу видел проблемные филиалы» поможет Claude решить спорный шаг. Шаги без цели соблюдают букву, но не смысл.
- **Жёсткие правила — отдельно.** Абзац юристов слово в слово, то, что недопустимо никогда, выносят в раздел «Правила» или «Никогда». Если всё сказано одинаково мягко, модель не отличит гибкое правило от обязательного.
- **Покажите пример.** Образец результата закрывает место для толкований, а плохой пример с пометкой, что в нём не так, работает ещё лучше.
- **Продумайте нехватку данных.** Фраза «Если чего-то не хватает, спроси. Не угадывай» убирает целый класс уверенных, но неверных ответов.

Тонкая ошибка — подробно описать шрифт и заголовки, а трудное решение, ради которого задача существует, упомянуть мимоходом. Такой skill идеально форматирует и проваливает суть.

## Личная библиотека skill

Когда skill становится много, автор советует три вещи:

- **Один skill — одна работа.** У skill на восемь задач не может быть точного описания. Разделите его.
- **Следите за пересечением описаний.** Если описания двух skill похожи, Claude может взять не тот. Проведите границу или объедините их.
- **Называйте единообразно** и время от времени чистите библиотеку от лишнего.

Пример из книги: консультантка из Найроби, которая помогает НКО с заявками на гранты, собрала 11 skill под форматы разных фондов. Общий шаг «объяснить бюджет простыми словами» она вынесла в отдельный skill, и остальные стали опираться на него. Время на заявку сократилось примерно на треть, потому что библиотека без пересечений начала давать накопительный эффект.

## Когда skill подходит, а когда нет

Skill окупается, если задача повторяется и у неё есть свой правильный способ. Разовую задачу проще объяснить в разговоре, а если годится любой подход, записывать нечего. Skill не нужен, если требуется связь с внешней системой (это `MCP server`, [глава 16](/book-summaries/ai/claude-ai-bible/16-mcp/)) или если весь метод сводится к «сделай хорошо». Проверка автора: можно ли записать три конкретных правила? Если нет, упаковывать нечего.

`CLAUDE.md` в Claude Code всегда в контексте проекта и хранит правила для всей работы в нём. Skill грузится под задачу и подходит многим проектам, поэтому метод одной задачи лучше вынести из `CLAUDE.md` в skill.

![Дерево решений: внешняя система ведёт к MCP server, разовая задача к вопросу в разговоре, задача без конкретных правил обходится без skill, правила проекта идут в CLAUDE.md, остальное становится skill](/assets/claude-ai-bible/ch14-when-skill.png)

Дерево читают сверху вниз: каждый ответ ведёт к другому инструменту или к следующему вопросу.

## Как делиться skill

Skill — это просто папка: упакуйте её в zip и отправьте. У коллеги Claude включит skill так же, потому что логика срабатывания записана в файле. Так личный приём становится активом команды: формат меняют в одном skill, и результат меняется у всех.

Общие skill держат в одном репозитории, чтобы не было семи расходящихся копий. Чтобы раздать skill вместе с `MCP server`, `slash`-командами и агентами одним пакетом, есть `plugin` и `marketplace` ([глава 15](/book-summaries/ai/claude-ai-bible/15-plugins/)).

## Итоги главы

- Skill — это папка с `SKILL.md`, и Claude подключает её сам, когда задача совпадает с описанием.
- Поле `description` решает, сработает ли skill, поэтому в нём перечисляют реальные фразы запроса.
- Описание видно всегда, тело грузится при срабатывании, а скрипты и ресурсы — по шагу инструкции.
- Точные расчёты отдают скрипту, а не модели.
- Skill проверяют дважды: срабатывает ли он и верен ли результат.
- В теле сначала идёт цель, жёсткие правила вынесены отдельно, а про пропуски Claude должен спрашивать.
- Один skill делает одну работу, а описания разных skill не пересекаются.
- Папку skill легко передать команде, и тогда опыт становится общим.

## Ключевые термины

| Термин | Значение |
|---|---|
| `skill` | Папка с инструкциями, скриптами и ресурсами, которую Claude подключает по `description` |
| `SKILL.md` | Обязательный файл: метаданные сверху, инструкции ниже |
| `description` | Поле метаданных: когда skill нужен |
| пересечение описаний | Похожие описания двух skill, из-за которых Claude берёт не тот |
| `CLAUDE.md` | Постоянные правила проекта, всегда в контексте |

## Что это значит на практике

- Ревью dbt-модели, разбор упавшего DAG и ночной отчёт о качестве данных хорошо ложатся в skill.
- Сверку числа строк и суммы считайте скриптом или SQL-файлом из папки skill.
- Правила репозитория держите в `CLAUDE.md`, а доступ к хранилищу даёт `MCP server`, а не skill.
- Храните общие skill в репозитории команды и меняйте их через pull request.
