## О чём глава

Как построить датасет, на котором получится обучить лучшую модель и уложиться в бюджет? В [главе 7](/book-summaries/ai/ai-engineering/07-finetuning/) данные были исходным материалом для `finetuning`. Следующая [глава 9](/book-summaries/ai/ai-engineering/09-inference-optimization/) расскажет, как быстро и дёшево запускать готовую модель.

## Данные как отдельная функция

Лучшая команда и самый большой кластер не помогут, если данных нет. Обучать модель с нуля могут всё меньше компаний. Поэтому всё больше компаний делает ставку на данные: именно они отличают продукт от продукта конкурентов.

Рост важности виден по отчётам OpenAI. Над данными для GPT-3 работали два человека. Над данными для GPT-4 уже около восьмидесяти. Работа с данными стала отдельной функцией. Появились разметчики (`data labelers`), создатели датасетов и инженеры качества данных.

Автор предупреждает: сбор, генерация и обработка идут не по прямой. Вы будете возвращаться к прошлым шагам. Разным этапам обучения нужны разные данные. Для `pre-training` объём меряют в токенах, для `SFT` в примерах. Глава в основном про данные для `post-training`, потому что они важнее разработчикам приложений.

## Взгляд на AI через данные

`Model-centric AI` улучшает качество через модель: новая архитектура, больший размер, новые способы обучения. `Data-centric AI` улучшает качество через данные: лучшая обработка и датасеты, на которых модель учится с меньшими ресурсами. Раньше benchmarks были в основном model-centric: данные фиксированы, участники строят модель. Теперь есть и data-centric соревнования. Модель фиксирована, участники строят лучший датасет. Примеры: конкурс Andrew Ng 2021 года и DataComp 2023 года для модели CLIP.

Автор оговаривается: на практике прогресс требует вложений и в модель, и в данные.

## Data curation: подготовка данных

Данные не решают все проблемы модели, но часто дают важную часть решения. Хорошие данные делают модель сильнее и безопаснее. Плохие усиливают смещения и галлюцинации. Автор называет `data curation` дисциплиной, которая требует понимать две вещи: как учится модель и какие ресурсы есть. В маленькой команде тот, кто отвечает за обучение, отвечает и за данные.

### Какие данные нужны

Формат примера зависит от этапа обучения.

| Этап | Один пример |
|---|---|
| Самообучение (`self-supervised finetuning`) | Последовательность текста |
| Instruction finetuning (`SFT`) | (инструкция, ответ) |
| Preference finetuning | (инструкция, выигравший ответ, проигравший ответ) |
| `Reward model` | Тот же формат или ((инструкция, ответ), оценка) |

Данные должны показывать то поведение, которому вы учите модель. Сложное поведение размечать труднее всего.

- **Chain of thought.** Чтобы модель отвечала по шагам, в данных нужны ответы по шагам. Chung et al. показали: такие примеры заметно поднимают качество на CoT-задачах, иногда почти вдвое. Но писать шаги долго, поэтому таких датасетов мало.
- **Tool use.** Примеры обычно пишут эксперты. Есть две ловушки. Эксперт может пропустить шаги, поэтому за ним лучше наблюдать. И то, что удобно человеку, неудобно модели: человек ищет через браузер, модели проще вызвать API. Поэтому для tool use часто используют симуляции. Формат тоже особый: за один ход AI может послать несколько сообщений разным адресатам. Llama 3 для этого получила чат-формат с заголовками источника и адресата.
- **Один ход или много.** `Single-turn` данные проще собрать. `Multi-turn` данные учат решать задачи: модель уточняет намерение, принимает поправки. Для них нужны специальные сценарии.
- **Удаление плохого.** Curation это и удаление. Если бот раздражает непрошеными советами, найдите такие примеры, уберите их и добавьте примеры без советов.

### Три критерия: quality, coverage, quantity

Автор сравнивает обучение с готовкой. Качество это свежесть продуктов. Охват это правильный набор ингредиентов. Количество это сколько продуктов у вас есть.

## Data quality: качество данных

Малый набор качественных данных может обойти большой шумный. Команда Yi нашла, что 10 тысяч тщательных инструкций лучше сотен тысяч шумных. В работе LIMA Llama на 65B параметров дообучили на 1000 примерах. Люди сочли её ответы равными GPT-4 или лучше в 43% случаев. Но цена есть: LIMA оказалась менее надёжной, чем продуктовые модели. Команда Llama 3 заметила, что данные людей часто содержат ошибки и противоречия, и сделала AI-инструменты разметки.

Что такое качественные данные? Данные качественны, если помогают выполнять работу эффективно и надёжно. Автор выделяет шесть свойств.

![Шесть свойств качественных данных и пример нарушения каждого](/assets/ai-engineering/ch08-quality-traits.png)

- **Relevant.** Примеры подходят задаче. Юридический датасет XIX века не подходит для сегодняшних вопросов.
- **Aligned.** Разметка совпадает с требованием задачи: точность, креативность или краткость. Автор не пишет «accurate», потому что верный ответ не всегда то, что хочет пользователь.
- **Consistent.** Разметка согласована между примерами и между разметчиками. Противоречия сбивают модель. Помогают ясные `annotation guidelines`.
- **Correctly formatted.** Все примеры в формате модели. Лишние токены форматирования вредят: уберите HTML, лишние пробелы и переводы строк.
- **Sufficiently unique.** Дубликаты создают смещения и загрязнение данных (`contamination`).
- **Compliant.** Данные соблюдают внутренние правила и законы. Если нельзя использовать персональные данные, их не должно быть в датасете.

> **Пояснение.** Для data engineer это готовый чеклист data quality tests. Формат проверяют схемой и regexp, уникальность через `GROUP BY` и `hash`, соответствие правилам сканом PII.

Автор помнит свою «болезненную» ошибку: столбец с дробными числами сохранили как целые. Значения округлились, и модель повела себя непонятно. Ещё одна мысль автора: данные, которых нет ни у кого другого, могут быть очень ценными. Это уже про уникальность источника, а не примеров.

## Data coverage: охват данных

Данные должны покрывать все способы, которыми пользователи будут работать с приложением. Одни пишут длинные инструкции, другие короткие. У кого-то в запросах опечатки. Приложение может работать с несколькими языками программирования. У каждого приложения свои оси разнообразия. Переводчику с французского не нужно языковое разнообразие, но нужно разнообразие тем и стилей. Для универсальных чат-ботов данные должны быть разнообразными по темам и речевым шаблонам. Ding et al. считают, что самый простой путь улучшить чат-модель это поднять качество и разнообразие данных. Исследователи NVIDIA для Nemotron собирали инструкции с разными форматами вывода, разной длиной ответа, открытые и «да или нет». Есть и предостережение: работа «The Data Addition Dilemma» показала, что иногда более разнородные данные ухудшают качество.

Meta сообщила, что рост качества Llama 3 в первую очередь связан с лучшими данными. Её `data mix` (смесь доменов) отличается на каждом из трёх этапов. В pre-training и SFT математика, reasoning и код занимают 42% и 36%, на preference finetuning только 12,82%. Вероятно, потому что этот этап должен отражать реальные предпочтения пользователей. Небольшая доля качественных данных по коду и математике в конце обучения поднимала результаты на ключевых benchmarks.

Как выбрать смесь? Простой путь: смесь, которая отражает реальное использование. Или подобрать экспериментами. Meta обучала несколько малых моделей на каждой смеси-кандидате и предсказывала поведение большой.

Zhou et al. сравнили три датасета по 2000 примеров для модели на 7B: качественный, но однообразный; разнообразный, но шумный; и разнообразный и качественный. Третий датасет дал лучший результат. Оба свойства нужны.

## Data quantity: объём данных

Вопрос «сколько данных нужно» похож на вопрос «сколько нужно денег». Крайности такие: в одном шуточном эксперименте LLM научилась по одному примеру, а некоторые команды дообучают модель на миллионах. Но миллионы примеров это мало рядом с pre-training: Llama 3 учили на 16 триллионах токенов. Автор отмечает ещё риск `ossification`: при очень большом finetuning веса после pre-training «костенеют» и хуже адаптируются. Малые модели костенеют сильнее. Если у вас миллионы примеров, взвесьте, не лучше ли обучить модель с нуля, но обычно finetuning эффективнее.

Кроме качества и разнообразия, на нужный объём влияют три фактора.

- **Метод finetuning.** Полный finetuning даёт лучшее качество, но требует на порядки больше данных, чем PEFT вроде `LoRA`. Десятки тысяч пар: пробуйте полный. Сотни или тысячи: лучше PEFT.
- **Сложность задачи.** Классификация тональности требует меньше данных, чем вопросы по финансовым отчётам.
- **Качество базовой модели.** Чем она сильнее, тем меньше примеров нужно. В руководстве OpenAI на 100 примерах сильные модели были заметно лучше. На 550 000 примерах все пять моделей выровнялись.

**Начните с малого.** Соберите 50 хорошо подготовленных примеров и проверьте, растёт ли качество. Если рост есть, больше данных поможет ещё. Если роста нет, большой датасет редко спасёт. Но не спешите с выводом «не помогает»: виноваты могут быть `learning rate`, плохие prompts и качество данных. Автор подчёркивает, что в подавляющем большинстве случаев улучшение видно уже на 50-100 примерах.

### Как уменьшить объём качественных данных

Сначала дообучите модель на менее качественных или менее релевантных данных. Три варианта.

1. Самообучение на документах, потом supervised на парах.
2. Данные о тональности твитов, потом отзывов.
3. Синтетические данные, потом реальные. Это самый сложный путь: нужны два finetuning и согласованный переход между ними.

### Кривая «качество от объёма»

Дообучите модель на 25%, 50% и 100% данных и постройте график. Крутой подъём значит, что удвоение данных поможет. Плато значит, что нет. Обычно работают `diminishing returns`: первые 1000 примеров дают +10 процентных пунктов, следующие 1000 только +5. У разнообразия свой эффект. В работе Chung et al. рост числа задач finetuning с 9 до 282 заметно поднял качество, дальше рост почти остановился. Разнообразие может быть в типах задач, темах и форматах вывода. Наконец, объём ограничен бюджетом: $10 000 при $2 за пример дают не больше 5000 примеров. Бюджет делят между данными и вычислениями.

## Сбор и разметка данных

Цель: датасет нужного размера, качества и разнообразия, с соблюдением приватности и правил. Лучший источник это ваше приложение. Его данные полностью релевантны и согласованы с задачей. Данные приложения это контент пользователей, данные, которые система создаёт при работе, и обратная связь. Если они постоянно улучшают продукт, это `data flywheel`. Про обратную связь см. [главу 10](/book-summaries/ai/ai-engineering/10-architecture-and-user-feedback/). Перед созданием своих данных проверьте, что уже есть. Чаще всего работает подход `mix-and-match`: датасет собирают из нескольких источников.

Автор показывает упрощённый пример. Нашли датасет на 10 000 примеров. Убрали плохие инструкции: 9 000. Отложили 3 000 плохих ответов и написали их вручную. Добавили шаблоны для редкой темы, AI сгенерировал 2 000 инструкций, люди написали ответы. Итог: 11 000 хороших примеров. На практике шагов больше. Бывает, что приходится обновить правила и разметить заново.

Открытые датасеты ищут на Hugging Face, Kaggle, в Google Dataset Search, на государственных порталах, в репозиториях вроде UC Irvine и в evaluation harness. Готовым данным не доверяйте полностью. Проверьте качество, лицензию и происхождение: даже при разрешённой лицензии часть данных могла прийти из источника, где коммерческое использование запрещено.

Свои данные часто нужно размечать. Самая трудная часть это `annotation guidelines`: что такое хороший ответ и чем он отличается от плохого. LinkedIn назвал их одной из главных трудностей. Автора тревожит, что аккуратную разметку часто заменяют надеждой, что модель «сама разберётся». Для многих приложений это слишком рискованно. Те же правила нужны для данных оценки из [главы 4](/book-summaries/ai/ai-engineering/04-evaluate-ai-systems/).

## Аугментация и синтез данных

Вместе с вычислениями и талантами данные это главная проблема AI. Цель отрасли: генерировать данные программно. Есть две техники. `Data augmentation` делает новые данные из реальных: зеркальное отражение фото кошки. `Data synthesis` создаёт данные, имитирующие реальные: симуляция движения мыши по странице. Автор часто использует слово «синтез» для обоих. Искусственные данные давно есть в разработке ПО: `Faker` генерирует имена и адреса для тестов. AI умеет создавать намного более сложные данные: договоры, балансы, описания товаров. Но synthetic data не заменяют человеческие полностью: чаще лучше смесь.

### Зачем синтезировать данные

Автор называет пять причин.

1. **Quantity.** Данных можно сделать много, особенно для редких событий: аварии беспилотных машин, редкая погода.
2. **Coverage.** Можно целенаправленно создавать нужные свойства: очень длинные тексты, токсичные диалоги для детектора, состязательные примеры, данные для редкого класса. Anthropic сделал датасеты для 154 поведений AI. Датасеты, написанные моделью, приближались к человеческим, а иногда превосходили их.
3. **Quality.** Синтетика иногда лучше. Люди работают с инструментами иначе, чем AI. AI может придумать задачи сложнее, чем средний эксперт. Оценки предпочтений от AI бывают последовательнее, чем у разных людей.
4. **Приватность.** В здравоохранении и страховании часто нельзя использовать реальные данные. Можно синтезировать их без чувствительной информации.
5. **Distillation.** Учим малую модель на данных большой.

### Традиционные способы синтеза

Синтез пришёл из тестирования ПО, игр и робототехники. Генерацию алгоритмами называют `procedural generation`. Есть два традиционных подхода.

**Rule-based.** Шаблон плюс случайный генератор. Транзакцию по карте строят из полей ID, дата, сумма, магазин, статус. Так делают модели для поиска мошенничества, пока реальных данных нет. Шаблоны подходят для счетов, резюме, договоров, регулярных выражений. DeepMind обучила AlphaGeometry на 100 миллионах синтетических примеров. Простые преобразования делают новые данные из старых: для картинок поворот, обрезка, стирание части. Для текста замена слов синонимами. Контрфактическая аугментация (`counterfactual augmentation`) меняет гендерные слова парными и ослабляет смещение. В русском языке такая замена ломает согласование, нужна морфология или LLM.

Интересное преобразование: `perturbation`, добавление шума. Исследование «One Pixel Attack» показало, что изменение одного пикселя обманывает классификатор для 67,97% картинок CIFAR-10. Обучение на возмущённых данных делает модель устойчивее. Для BERT заменяли 1,5% токенов случайными словами.

**Simulation.** Эксперименты в виртуальной среде дешевле и безопаснее. Лошадь на шоссе для беспилотной машины проще симулировать. Робота учат наливать кофе, оставляя удачные попытки. Но симуляция упрощает мир, и разрыв называют `Sim2Real`. Для tool use симулируют разные последовательности действий и берут самую эффективную. Симуляции ценны для редких событий: банкротств, дефектов материалов, экстремальной погоды.

## AI-синтез данных

Мощные модели расширяют эти возможности.

- **Симуляция API и людей.** AI может имитировать ответы API без вызова (StableToolBench). Боты учатся в `self-play`, то есть играют сами с собой. OpenAI гоняла бота для Dota 2 через игры на примерно 180 лет в день. DeepMind учила AlphaGo на миллионах партий. Тот же приём работает для агентов: две версии модели ведут переговоры или играют клиента и оператора поддержки.
- **Перефразирование.** Из 15 000 примеров MATH и GSM-8K получился MetaMath на почти 400 000 примеров. Модели на нём обошли более крупные.
- **Перевод.** Данные переводят с языков с большим числом ресурсов на языки с малым. Качество проверяют обратным переводом (`back-translation`): если X' сильно отличается от X, перевод плохой. Так же переводят код между языками программирования.
- **Pre-training и post-training.** Для post-training synthetic data используют намного чаще: AI может пересобрать знания в новых форматах, но новые знания синтезировать труднее. Но интернет уже заполняется AI-контентом, а Cosmopedia это 25 миллиардов синтетических токенов.
- **Preference data.** Выбрать лучший ответ для AI проще, чем написать. Главная трудность: `position bias`. Исследователи NVIDIA спрашивали судью дважды с обменом порядка и брали пару в датасет, только если победитель совпал.

### Синтез instruction data

AI может создавать инструкции, ответы или то и другое. Начните со списка тем, ключевых слов или шаблонов, чтобы охватить свой случай. UltraChat: ChatGPT придумал 30 тем, для каждой 30-50 подтем, потом инструкции и ответы. Alpaca: из 175 seed-пар Self-Instruct модель GPT-3 сделала 52 000 пар.

Длинный ответ AI писать трудно, и он чаще содержит галлюцинации. Поэтому есть обратный путь, **reverse instruction**. Берут готовый качественный текст, например статью Wikipedia, и просят AI придумать prompt, который вызвал бы такой текст. Ответы без галлюцинаций. Цикл можно повторять: слабая модель создаёт инструкции, на них учится и становится лучше. Другой приём: **длинный контекст**. Длинный документ режут на куски, делают пары вопрос-ответ, а как контекст дают весь документ.

Llama 3 синтезировала instruction data для кода так.

![Пайплайн Llama 3 для синтетических данных по коду: генерация, проверка, исправление, перевод и back-translation](/assets/ai-engineering/ch08-llama3-code-pipeline.png)

- AI пишет описания задач и решения на разных языках.
- Parsers и linters ловят синтаксические ошибки, unit tests (тоже от AI) ловят ошибки выполнения.
- Упавшее решение отправляют на исправление вместе с отзывами проверок. По наблюдению авторов, около 20% решений сначала были неверны, но исправились.
- Код переводят на другие языки. Не прошедший тесты отбрасывают.
- Объяснения проверяют обратным переводом: по ним AI снова пишет код, и объяснение берут, только если код верен.

Итог: больше 2,7 миллиона synthetic-примеров для SFT Llama 3.1.

### Проверка данных (data verification)

Качество synthetic data меряют так же, как другие выходы AI: `functional correctness` и `AI judge` ([глава 3](/book-summaries/ai/ai-engineering/03-evaluation-methodology/)). Люди чаще синтезируют то, что умеют проверять, поэтому код синтезируют чаще всего. Для остального используют `AI verifier`: оценка от 1 до 5 или «хорошо/плохо». Для фактов ищут несоответствия (глава 4). Можно обучить детектор AI-контента: если синтетику легко отличить, она плоха. Можно искать выбросы через `anomaly detection`. Если синтетика должна походить на сильную научную статью, можно обучить классификатор, который предсказывает, примут ли её на конференцию. Работают и простые эвристики. Self-Instruct отсеивал повторы, слишком длинные и короткие инструкции, одну инструкцию с разными ответами и примеры, где выход повторяет вход. Итоговый тест один: улучшают ли данные модель.

### Ограничения AI-синтетики

Synthetic data никогда не заменят человеческие полностью. Автор называет четыре ограничения.

- **Контроль качества.** «Garbage in, garbage out». Без надёжной оценки данным не доверяют.
- **Поверхностная имитация.** Модели-имитаторы повторяют стиль учителя, но хуже держат факты и плохо обобщаются. Ученик может научиться галлюцинировать: выдавать ответы, похожие на решения, не умея решать. То же возможно и с разметкой людей, если разметчик использует знания, которых у модели нет.
- **Model collapse.** При рекурсивном обучении на AI-данных качество падает (Shumailov et al.). Модели чаще создают вероятные события и реже редкие, поэтому редкое со временем пропадает. Gerstgrasser et al. показали: коллапс неизбежен, если данные только синтетические, и его можно избежать смесью с реальными. Рекомендации по доле нет. Есть и обратные примеры. Li et al. дообучали Llama 2-7B на математике: synthetic data работали почти как реальные и не насыщались до миллиона примеров. Nemotron-4 340B использовала 98% synthetic data. Но эти опыты сделаны на одной итерации модели.
- **Смещения и происхождение.** Модель на выходах модели может усилить смещения. Генерация скрывает `data lineage`. Если модель X обучалась на нарушающих авторские права данных или на benchmark B, ваша модель и ваша оценка на B могут быть испорчены.

## Model distillation: модельная дистилляция

`Distillation` учит малую модель (`student`) подражать большой (`teacher`). Цель обычно в том, чтобы получить более дешёвую и быструю модель. DistilBERT на 40% меньше BERT, сохраняет 97% понимания языка и работает на 60% быстрее. Alpaca это Llama-7B, дообученная на примерах `text-davinci-003`: 4% размера учителя. Многие лицензии запрещают обучать другие модели на выходах модели, особенно конкурирующие. BuzzFeed снизил стоимость inference на 80% с Flan-T5 и LoRA.

Не всякое обучение на synthetic data это distillation. Ученик может стать сильнее учителя: Команда NVIDIA предобучила базу на 340B параметров и дообучила её на данных от Mixtral-8x7B-Instruct, модели на 56 миллиардов параметров. Ученик Nemotron-4-340B-Instruct на многих задачах обошёл учителя. Llama 3 показала: обучение на данных более сильной модели сильно помогает, обучение на своих данных не помогает или вредит. Но если оставлять только проверенные данные, модель удаётся улучшать на её же данных.

## Обработка данных (data processing)

Автор советует читать статьи о моделях: в них часто описано, как отбирали и обрабатывали данные.

![Три слоя данных raw, cleaned, final и три совета по порядку шагов](/assets/ai-engineering/ch08-processing-order.png)

Три совета по эффективности.

1. Ставьте шаги в порядке стоимости. Если очистка дороже дедупликации, сначала дедуплицируйте.
2. Сначала запускайте скрипты на малой выборке.
3. Не меняйте данные на месте. Храните копию исходных.

> **Пояснение.** Это слои `raw`, `cleaned`, `final`, как в `dbt`: источники остаются нетронутыми, а преобразования лежат в отдельных моделях.

### Inspect: смотрим на данные

Узнайте, откуда данные, как их обрабатывали и для чего использовали. Постройте распределения токенов, длины входов и ответов, тем и языков. Делайте срезы по источнику, времени и разметчику. Одни разметчики дают более короткие ответы или более высокие оценки. Если у примера несколько разметок, посчитайте расхождение между разметчиками и разберите конфликты. Microsoft сравнила GPT-3 и GPT-4 по парам глагол-существительное и длине ответов: GPT-4 разнообразнее и пишет длиннее.

Инструменты не заменяют ручной осмотр. В проектах автора 15 минут просмотра данных давали инсайт, который спасал от часов головной боли. Greg Brockman, сооснователь OpenAI, писал, что это, вероятно, самая выгодная по отдаче деятельность в ML. Разметьте несколько примеров сами и сравните. Проверьте факты. Ищите один запрос с разными ответами и один ответ с разными запросами.

### Deduplicate: убираем повторы

Дубликаты искажают распределение: если «красный карандаш, 20 долларов» повторить три раза, модель решит, что красные товары дорогие. Они же загрязняют тест (`test contamination`): пример в train, копия в test. Anthropic показала: если повторить 0,1% данных 100 раз, модель на 800 миллионов параметров может упасть до уровня модели на 400 миллионов. Дубликаты бывают целые документы, абзацы внутри документа и цитаты между документами. Что считать дубликатом (документ, абзац, 80% совпадения), решаете вы. Три способа поиска:

- **Pairwise comparison.** Сравниваем каждый пример с каждым. Точно, но дорого на больших данных.
- **Hashing.** Раскладываем по корзинам и сравниваем только внутри корзины: `MinHash`, `Bloom filter`.
- **Dimensionality reduction.** Сначала уменьшаем размерность, потом сравниваем попарно (техники векторного поиска из [главы 6](/book-summaries/ai/ai-engineering/06-rag-and-agents/)).

### Clean and filter: очищаем и отбираем

Уберите лишние токены форматирования. Databricks нашла, что удаление Markdown и HTML подняло точность на 20% и сократило длину входа на 60%. Уберите всё, что нарушает правила: PII, защищённый авторским правом и токсичный контент, поля вроде имени и пола. Плохие данные уберите техниками проверки. Здесь особенно важен ручной просмотр: он находит шаблоны для эвристик. Например, Kern et al. заметили, что разметка во второй половине сессии хуже: разметчики устают. Если данных больше, чем вы можете использовать, отфильтруйте их: `active learning`, `importance sampling`, `data pruning`.

### Format: приводим данные к формату модели

У каждой модели свой токенизатор и `chat template` ([глава 5](/book-summaries/ai/ai-engineering/05-prompt-engineering/)). В неверном шаблоне появляются странные ошибки. После finetuning prompt обычно проще: описание задачи и few-shot примеры не нужны, модель выучит их из данных. Это может снизить стоимость входных токенов. Форматы данных влияют на качество, поэтому поэкспериментируйте. И следите, чтобы prompt на inference совпадал с форматом обучения до мелочей. Если вход в формате «бургер -->», проблемы дадут «бургер» без стрелки, лишний префикс и лишний пробел в конце.

## Итоги главы

- Качество модели определяют данные, поэтому у AI-команд появились отдельные роли работы с данными.
- `Data-centric AI` улучшает модель через данные. Обычно нужны оба подхода.
- Подготовка данных идёт по трём критериям: quality (шесть свойств), coverage и quantity.
- Малый чистый датасет может обойти большой шумный (Yi, LIMA). Но лучше всего датасет, который и качественный, и разнообразный.
- Нужный объём зависит от метода finetuning, сложности задачи и базовой модели. Начните с 50-100 примеров и постройте кривую: отдача убывает.
- Главный источник данных это ваше приложение (`data flywheel`). Открытые датасеты проверяйте. Правила разметки это узкое место.
- Synthetic data улучшают quantity, coverage, quality и приватность. Способы: правила, симуляция, AI и distillation.
- Synthetic data нужно проверять функционально или через AI judge. Поэтому чаще всего синтезируют код.
- У synthetic data есть пределы: поверхностная имитация, model collapse, смещения и потеря происхождения. Смесь с реальными безопаснее.
- Обработка идёт по шагам: inspect, deduplicate, clean and filter, format. Prompt на inference должен совпадать с форматом обучения.

## Что изменилось к 2026 году

Книга написана в 2024 году. Вот что важно знать сейчас. Это наше дополнение, его нет в книге.

- **Synthetic data стал основным источником для post-training.** Большие лаборатории генерируют задачи и ответы моделями, а затем фильтруют проверками.
- **Проверяемые данные ценнее всего.** Для RLVR нужны задачи с автоматической проверкой: тесты для кода, точный ответ для математики, SQL с ожидаемым результатом. Дата-инженер может строить такие наборы из своих данных.
- **Данные для оценки агентов.** Нужны не пары «вопрос-ответ», а сценарии: стартовое состояние, задача, проверка итога.
- **Пайплайн из главы (inspect, dedup, clean, format) не изменился.**

## Что это значит на практике

- **Относитесь к датасету как к продукту.** Версии, схема, владелец, документация. Это обычная data engineering работа.
- **Храните сырые данные неизменными.** Делайте слои raw, cleaned, final, как в `dbt`.
- **Дедуплицируйте и следите за утечками.** Проверяйте пересечение train и eval по ключу или hash. Для почти-копий используйте `MinHash` и `LSH`, а не попарное сравнение.
- **Добавьте data quality tests:** пустые значения, длина, формат, язык, дубликаты, PII. Запросы «должно вернуться 0 строк» можно положить в CI.
- **Следите за lineage.** Для каждого примера храните источник, дату, версию guideline, разметчика, модель-генератор и лицензию.
- **Собирайте данные приложения заранее.** Логи, ответы, feedback. Сразу продумайте схему, согласие и удаление PII.
- **Считайте цену одного хорошего примера:** разметка, генерация, обработка, хранение.
- **Стройте срезы по источнику, времени и разметчику.** Грязный источник или уставший разметчик видны в SQL за минуту. В модели они проявятся через недели.
- **Синтезируйте то, что можно проверить.** Для кода это тесты, для SQL сравнение результата с ожидаемым.
- **Не обучайте только на синтетике.** Держите долю реальных данных отдельно.
- **Фиксируйте формат.** Один `chat template` и один формат prompt для обучения и для inference.

### Дедупликация, конфликты и утечка в eval на DuckDB

Ключ это нормализованная инструкция: нижний регистр, без лишних пробелов. Правила идут по порядку. Первая причина отбраковки и есть вердикт.

```sql
CREATE TABLE raw AS SELECT * FROM (VALUES
  (1, 'Как сделать JOIN?',   'Используйте JOIN ... ON.',   'docs'),
  (2, '  как сделать  join?', 'используйте join ... on.',   'forum'),
  (3, 'Что такое CTE?',      'Запрос с именем WITH.',      'docs'),
  (4, 'Что такое dbt?',      'Инструмент для SQL-моделей.', 'synthetic'),
  (5, 'Что такое CTE?',      'Это временная таблица.',     'forum'),
  (6, 'Что такое Kafka?',    'Брокер сообщений.',          'docs')
) t(id, instr, answer, source);
CREATE TABLE eval AS SELECT 'что такое dbt?' AS instr;

WITH n AS (
  SELECT *, lower(trim(regexp_replace(instr, '\s+', ' ', 'g'))) AS k FROM raw),
r AS (
  SELECT *,
    row_number() OVER (PARTITION BY k, lower(answer) ORDER BY id) AS rn,
    count(DISTINCT lower(answer)) OVER (PARTITION BY k) AS n_answers
  FROM n)
SELECT id,
  CASE WHEN rn > 1 THEN 'duplicate'
       WHEN n_answers > 1 THEN 'conflict'
       WHEN k IN (SELECT instr FROM eval) THEN 'eval_leak'
       ELSE 'keep' END AS verdict
FROM r ORDER BY id;
```

```text
id  verdict
1   keep
2   duplicate
3   conflict
4   eval_leak
5   conflict
6   keep
```

Строка 2 это копия строки 1 с другим регистром. Строки 3 и 5 дают разные ответы на один вопрос: обе уходят, пока вы не решите, какая верна. Строка 4 совпала с eval-набором. Из шести строк остались две.

### Model collapse на игрушечной модели

«Модель» это распределение по 50 событиям. Каждое поколение учится на выборке из предыдущего. Во втором прогоне половина выборки приходит из реальных данных.

```python
import random
random.seed(1)
N, SIZE = 50, 200
real = [1 / (i + 1) for i in range(N)]            # частые и редкие события
real = [p / sum(real) for p in real]

def next_gen(model, real_share):
    n_real = int(SIZE * real_share)
    data = random.choices(range(N), real, k=n_real)
    data += random.choices(range(N), model, k=SIZE - n_real)
    counts = [data.count(i) for i in range(N)]
    return [c / SIZE for c in counts]             # новая модель = частоты выборки

for share in (0.0, 0.5):
    model, alive = real, []
    for g in range(20):
        model = next_gen(model, share)
        alive.append(sum(p > 0 for p in model))
    print(f"real={share}: events alive at gen 1/10/20 =", alive[0], alive[9], alive[19])
```

```text
real=0.0: events alive at gen 1/10/20 = 38 19 15
real=0.5: events alive at gen 1/10/20 = 43 39 36
```

Без реальных данных живых событий остаётся 15 из 50, и редкие исчезают первыми. Событие с нулевой частотой не вернётся. Со свежими реальными данными число событий держится около 36-43.

### Судья с position bias и обмен позиций

У каждой пары есть скрытое «настоящее» качество, поэтому мы знаем победителя. Судья шумит и любит первую позицию. Метод NVIDIA: спросить дважды с обменом порядка и взять пару, только если судья согласен сам с собой.

```python
import random
random.seed(7)

def judge(a, b):                      # шумный судья, любит первую позицию
    return 'first' if a + random.gauss(0, .2) + .15 > b + random.gauss(0, .2) else 'second'

pairs = [(random.random(), random.random()) for _ in range(5000)]
once = sum((judge(a, b) == 'first') == (a > b) for a, b in pairs)
kept = right = 0
for a, b in pairs:
    w1 = judge(a, b)                  # порядок (a, b)
    w2 = judge(b, a)                  # порядок обменян
    if (w1 == 'first') == (w2 == 'second'):   # судья согласен с собой
        kept += 1
        right += (w1 == 'first') == (a > b)
print(f"one call:  accuracy {once / len(pairs):.1%}, kept 100%")
print(f"two calls: accuracy {right / kept:.1%}, kept {kept / len(pairs):.1%}")
```

```text
one call:  accuracy 79.6%, kept 100%
two calls: accuracy 93.3%, kept 68.7%
```

Два вызова поднимают точность меток с 80% до 93%. Цена: около трети пар выпадает, в основном спорные.
