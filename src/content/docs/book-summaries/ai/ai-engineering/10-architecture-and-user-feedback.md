**Главная мысль:** AI-приложение растёт по шагам. Каждый новый блок решает одну проблему, но добавляет сложность и новые места, где всё может сломаться. Поэтому системе нужны `observability` (понимание того, что с ней происходит) и обратная связь от пользователей: они показывают, что ломается и как улучшать продукт.

## О чём глава

Предыдущие главы разбирали отдельные приёмы: оценку, prompt, `RAG`, агентов, `finetuning`, данные. [Глава 9](/book-summaries/ai/ai-engineering/09-inference-optimization/) ускоряла один вызов модели. Эта глава собирает всё в продукт. Она отвечает на два вопроса. Из каких блоков состоит рабочее AI-приложение? Как узнать, что оно решает задачу пользователя?

Часть 1 идёт от схемы «запрос, модель, ответ» к полной архитектуре: контекст, `guardrails`, `router` и `gateway`, кэш, агентные циклы, затем `monitoring`, `observability` и `orchestration`. Часть 2 про обратную связь (`user feedback`): как достать сигналы из диалога, когда и как их просить и какие у них смещения. Дата-инженеру это знакомо: логи, метрики, trace и дрейф, только для LLM.

![Итоговая архитектура AI-приложения: сбор контекста, input guardrails, model gateway с router и scorers, output guardrails, кэши, write actions, а под схемой monitoring и orchestrator](/assets/ai-engineering/ch10-architecture.png)

Как читать схему. Запрос идёт слева направо: кэш, сбор контекста, input guardrails, блок модели (router, генерация, scorers), output guardrails, ответ. Две полосы внизу, `monitoring` и orchestrator, относятся ко всей схеме.

## Архитектура AI-приложения по шагам

Сложную схему сразу не рисуют. Берут самый простой вариант и добавляют блоки, когда появляется проблема. Так делает и команда в продакшене. Схему проверили в нескольких компаниях, но ваш продукт может от неё отличаться.

Простейшая форма: приложение отправляет запрос в `Model API` и отдаёт ответ пользователю. Это может быть чужой провайдер (OpenAI, Google, Anthropic) или ваша модель на своём сервере. Ни контекста, ни защиты, ни оптимизации здесь нет.

Дальше автор чаще всего видит такой порядок:

1. Улучшить контекст: внешние данные и tools.
2. Поставить `guardrails`.
3. Добавить `router` и `gateway`.
4. Добавить кэш, чтобы ответы стали быстрее и дешевле.
5. Добавить сложную логику и write actions.

Порядок не закон: выбирайте тот, который подходит вашему приложению. `Monitoring` и `orchestration` автор разбирает после этих пяти шагов.

## Шаг 1. Улучшаем контекст

Первое расширение строит контекст для каждого запроса: то, что модель должна знать, чтобы ответить. Способы поиска (текст, картинки, таблицы) мы разбирали в [главе 6](/book-summaries/ai/ai-engineering/06-rag-and-agents/). Контекст можно пополнять и через `tools`: поиск в вебе, новости, погода. Автор сравнивает это с `feature engineering` в классическом ML: мы готовим для модели входную информацию так же, как признаки.

Провайдеры API поддерживают контекст по-разному:

- **Файлы:** разные типы документов и разный лимит на их число. Свой RAG вместит столько, сколько влезет в векторную базу.
- **Retrieval и tools:** у фреймворков разные алгоритмы, размер `chunk`, набор tools, параллельные вызовы.

> **Пояснение.** Слово `read-only` здесь важно. Эти действия только читают данные. Действия, которые меняют мир, появятся на шаге 5.

## Шаг 2. Ставим guardrails

`Guardrails` (ограждения) снижают риски для вас и пользователей. Их ставят везде, где есть риск, на входе и на выходе. Полностью убрать риски нельзя: модели вероятностные, а люди ошибаются.

### Input guardrails: защита входа

Вход защищают от двух рисков: утечки приватных данных во внешний API и вредных prompt (атаки разобраны в [главе 5](/book-summaries/ai/ai-engineering/05-prompt-engineering/)).

Утечка возникает, когда данные уходят за пределы компании. Сотрудник вставляет секрет в prompt (так случилось в Samsung с ChatGPT). Разработчик кладёт в системный prompt внутренние правила. Или `tool` достаёт приватные данные из внутренней базы. Что считать чувствительным, решаете вы. Обычно это `PII` (документы, телефоны, счета), лица на картинках и слова, связанные с интеллектуальной собственностью. Такие данные часто ищут инструменты на основе AI.

Если запрос содержит чувствительное, есть два пути:

1. Заблокировать запрос целиком. Просто, но строго.
2. Заменить значения плейсхолдерами вроде `[PHONE NUMBER]`. Пары «плейсхолдер и значение» лежат в `PII reverse map`. Когда модель вернёт ответ с плейсхолдером, его меняют обратно. Наружу уходит только маскированный текст, а пользователь видит настоящие данные.

### Output guardrails: защита выхода

У output guardrails две задачи: поймать сбой и решить, что делать дальше. Чтобы поймать сбой, нужно знать, как он выглядит в вашем приложении. Пустой ответ обычно плох, но иногда пользователь сам просил молчать, поэтому guardrail должен знать контекст запроса.

Автор делит сбои на две группы:

- **Качество:** неверный формат (например, невалидный JSON), галлюцинации, просто плохой ответ.
- **Безопасность:** токсичность, приватные данные в ответе, ответы, которые запускают удалённые tools или код, риски для бренда.

Из главы 5: считайте и `false refusal rate`, долю ложных отказов. Слишком строгая система блокирует законные запросы и злит пользователей.

Политики при сбое такие:

- **`retry`.** Модель вероятностная, поэтому повтор часто даёт другой, хороший ответ. Цена: ещё один вызов и больше задержка.
- **Параллельные вызовы.** Отправьте запрос сразу дважды и выберите лучший ответ. Задержка остаётся, но вызовов API больше.
- **Передача человеку.** Часть запросов уходит операторам. Одни команды ставят отдельную модель, которая решает, когда передать диалог (например, увидев гнев в тональности). Другие передают диалог после заданного числа ходов, чтобы пользователь не застрял в петле.

### Как реализовать guardrails

Первый компромисс: надёжность против `latency`. Некоторые команды отказываются от guardrails ради скорости. Другие нюансы:

- **`Stream completion`.** Токены сразу идут пользователю, поэтому частичный ответ трудно проверить. Небезопасный текст может дойти раньше, чем guardrail его заблокирует.
- **Свои модели или API.** Сторонние API уже включают многие guardrails. Своя модель ничего не отправляет наружу, поэтому input guardrails нужны реже.
- **Уровни.** Провайдеры встраивают guardrails в модель, но им приходится искать баланс между безопасностью и гибкостью. Свои guardrails ставят на стороне приложения. Готовые решения есть: Purple Llama, NeMo Guardrails, PyRIT, Perspective API, Content Moderation API от OpenAI.

Риски входа и выхода пересекаются, поэтому одно решение часто защищает обе стороны. Блок `scoring` (scorers оценивают выход) стоит внутри блока модели: scorers часто сами работают на AI.

## Шаг 3. Добавляем router и gateway

Когда моделей в приложении становится много, нужны `router` и `gateway`. Они снижают сложность и цену работы с несколькими моделями.

### Router: выбираем решение под запрос

Вместо одной модели на все запросы выбираем решение под каждый. Это даёт специализацию (одна модель разбирает технические сбои, другая отвечает про оплату) и экономию (простые запросы идут в дешёвую модель).

Router обычно строят на `intent classifier`: он предсказывает, чего хочет пользователь. В примере автора чат-бот поддержки отправляет сброс пароля на страницу FAQ, ошибку в счёте к живому оператору, техническую проблему к специальному боту. Классификатор даёт ещё два эффекта. Он отсекает неуместные запросы: на вопрос «за кого вы проголосуете?» бот отвечает заготовкой и не тратит вызов API. И он замечает неясные запросы: на одно слово «заморозить» бот переспрашивает, счёт или погода.

Router может и предсказывать следующее действие агента: вызвать интерпретатор или поиск. Он должен быть быстрым и дешёвым, потому что его вызывают всегда. Часто это небольшая дообученная модель (GPT-2, BERT, Llama 7B) или маленький классификатор с нуля.

Модели имеют разные лимиты контекста. Если запрос в 1000 токенов идёт в модель на 4K, а поиск приносит ещё 8000 токенов, контекст режут или запрос отправляют в модель с большим окном. Router обычно работает до retrieval: он решает, входит ли запрос в область приложения и нужен ли поиск.

### Gateway: единая дверь к моделям

`Model gateway` даёт организации единый и безопасный интерфейс ко всем моделям, своим и коммерческим. Если API провайдера изменилось, правят только gateway, а не каждое приложение. Простейший gateway это обёртка: по параметру `model_type` она вызывает нужный адаптер.

Gateway решает ещё задачи:

- **Доступ и расходы.** Приложения получают доступ к gateway, а не ключи провайдера, которые легко украсть. Gateway задаёт, кто и какую модель может вызывать, и ограничивает число вызовов.
- **Fallback.** При `rate limit` или сбое API gateway переключает запрос на другую модель или повторяет его позже. Сбои API бывают часто.
- **Логирование и аналитика.** Все запросы и так идут через gateway. Некоторые gateway включают кэш и guardrails.

Готовых gateway много: Portkey, MLflow AI Gateway, Kong, Cloudflare. Похожий `tool gateway` для инструментов в 2024 году почти не использовали.

## Шаг 4. Кэш: меньше задержка и расходы

Здесь речь о системном кэше. `KV cache` и `prompt caching` мы разобрали в [главе 9](/book-summaries/ai/ai-engineering/09-inference-optimization/). Есть два механизма.

### Exact cache

`Exact cache` отдаёт сохранённый ответ, только если запрос совпал точно. Так же кэшируют результаты векторного поиска. Кэш особенно полезен для многошаговых запросов и долгих действий: поиск документов, SQL, веб.

Память ограничена, поэтому кэш часто строят на PostgreSQL, Redis или многоуровневом хранилище. Размер держит `eviction policy`: `LRU` (вытесняем давно не использованное), `LFU` (самое редкое) или `FIFO` (самое старое). Кэшировать нужно не всё. Запросы про конкретного пользователя («статус моего заказа») и зависящие от времени («какая погода?») кэшировать бессмысленно. Многие команды учат классификатор, который решает, стоит ли кэшировать запрос.

> **Предупреждение.** Кэш может утечь данные. Клиент X спрашивает про условия возврата электроники. Они зависят от уровня членства, поэтому система берёт данные X. Вопрос выглядит общим, и ответ попадает в общий кэш. Клиент Y задаёт тот же вопрос и видит данные X.

> **Пояснение.** Для дата-инженера это знакомая ошибка: в ключ кэша не вошло измерение, от которого зависит результат. Так выглядит `GROUP BY` без нужной колонки.

### Semantic cache

`Semantic cache` отдаёт сохранённый ответ и для похожих запросов, например «столица Вьетнама» и «как называется столица Вьетнама». Для этого строят `embedding` запроса, ищут ближайший embedding в кэше и сравнивают похожесть с порогом (`similarity threshold`). Нужна векторная база.

Автор скептична: ценность semantic cache сомнительна, потому что все его части ненадёжны. Нужны хорошие embeddings, работающий поиск и надёжная метрика. Порог подбирают пробами, а ложное «похоже» даёт неверный ответ. Поиск сам стоит времени и денег и дорожает с ростом кэша. Semantic cache окупается только при высоком hit rate. Взвесьте риски до того, как его вводить. На схеме появляются два кэша: кэш запросов в начале и кэш поиска между данными и контекстом.

## Шаг 5. Шаблоны агентов и write actions

Собранное до сих пор идёт по линейной цепочке. Шаблоны агентов (`agent patterns`, см. [главу 6](/book-summaries/ai/ai-engineering/06-rag-and-agents/)) добавляют циклы, ветки и параллельность. Например, система видит, что задача не решена, и делает новый запрос данных. Первый ответ и новый контекст снова идут в модель.

Ответ модели может запускать `write actions`: отправить письмо, оформить заказ, начать банковский перевод. Они меняют окружающий мир. Система становится мощнее, но и намного рискованнее. Доступ на запись давайте с максимальной осторожностью.

Теперь архитектура сложна: точек отказа больше, отлаживать труднее. Поэтому дальше речь о наблюдаемости.

## Monitoring и observability

Автор считает, что наблюдаемость нужно закладывать с начала продукта, а не «потом». Чем сложнее система, тем она важнее. Это общая практика программной инженерии. Автор разбирает только то, что специфично для foundation models.

Цель мониторинга та же, что у оценки: снижать риски и находить возможности. Он защищает от сбоев, атак и `drift`, помогает находить улучшения и экономию. Из DevOps пришли три метрики качества наблюдаемости:

- `MTTD`: сколько времени проходит, пока вы заметите проблему;
- `MTTR`: сколько проходит от обнаружения до исправления;
- `CFR`: доля изменений, которые привели к ошибкам и потребовали исправления или отката.

Если вы не знаете свой CFR, платформу надо перестроить. Высокий CFR не всегда значит плохой мониторинг, но тогда пересмотрите оценку: плохие изменения надо ловить до выката. Оценка и мониторинг работают в связке: проблемы из мониторинга возвращаются в пайплайн оценки.

Разница терминов такая. **Мониторинг** следит за внешними результатами и говорит, что что-то сломалось, но не обязательно что именно. **Наблюдаемость** предполагает, что внутреннее состояние можно вывести из внешних выходов. Тогда причину сбоя находят по логам и метрикам без нового кода. Для этого систему оснащают (`instrument`) заранее. Автор называет «мониторингом» сбор данных, а «наблюдаемостью» весь процесс.

### Метрики

Метрика нужна, чтобы сказать, что что-то не так, и подсказать, что улучшать. Сначала решите, какие сбои вы хотите ловить, потом подбирайте метрики. Если боитесь галлюцинаций, смотрите, выводится ли ответ из контекста. Если боитесь больших счетов, считайте токены, цену и hit rate кэша. Метрики качества разобраны в главах 3-6. Как их группировать:

- **Формат и открытые ответы:** доля невалидного JSON; фактическая согласованность, краткость и креативность (часто через AI-судью).
- **Безопасность:** токсичность, приватные данные на входе и выходе, частота срабатывания guardrails и отказов, аномальные запросы (редкие случаи или prompt-атаки).
- **Сигналы диалога:** как часто останавливают генерацию, сколько ходов в диалоге, средняя длина входа и выхода.
- **По компонентам:** у RAG это релевантность и точность контекста, у векторной базы объём индекса и время запроса.
- **Задержка и цена:** `TTFT`, `TPOT`, общая задержка по пользователям; запросы и токены в секунду, чтобы не упереться в `rate limit`.

Метрик будет много. Проверьте, как они связаны с главной метрикой продукта, `north star` (DAU, длина сессии, подписки). Сильная корреляция подсказывает, что улучшать. Отсутствие корреляции подсказывает, на что не стоит оптимизироваться. Проверять можно выборкой или полностью, обычно сочетают оба способа. Считайте метрики со срезами: по пользователям, релизам, версиям prompt, времени.

### Логи и traces

Метрики агрегированы, поэтому они не отвечают на вопрос «что случилось?». Это делают `logs`: журнал событий, куда записи только добавляются. Типичный разбор: метрики говорят, что 5 минут назад что-то сломалось; вы смотрите логи этого времени; сверяете ошибки в логах с метриками.

Правило автора: логируйте всё. Заранее неизвестно, что понадобится. Пишите конфигурацию (endpoint, модель, параметры sampling), запрос пользователя, итоговый prompt, выход, вызовы и выходы tools, старт, конец и сбои компонентов, с тегами и ID. Объём вырастет, и многие инструменты анализа логов сами используют AI. Но автор советует каждый день смотреть данные продакшена и вручную: по Shankar et al. (2024), так меняется взгляд разработчиков на хорошие и плохие ответы, и они обновляют prompt и оценку.

`Trace` связывает родственные события в одну линию запроса от начала до конца. В AI-приложении он показывает шаги системы, найденные документы, итоговый prompt, время и стоимость каждого шага. Если запрос упал, trace показывает шаг: запрос обработан неверно, найденный контекст не тот или модель ответила неверно. В книге пример взят из LangSmith.

### Drift detection: когда что-то меняется незаметно

В AI-приложении незаметно меняться могут три вещи.

- **Системный prompt.** Шаблон обновили или коллега исправил опечатку. Простая логика ловит такую смену.
- **Поведение пользователей.** Люди подстраиваются под технологию: учатся писать запросы так, чтобы ответы были короче. Тогда длина ответа падает, и причина видна только после исследования.
- **Модель за API.** API не меняется, а модель под ним обновляется, и провайдеры не всегда объявляют это ([глава 4](/book-summaries/ai/ai-engineering/04-evaluate-ai-systems/)). Chen et al. (2023) нашли разницу в benchmark между версиями GPT-4 и GPT-3.5 за март и июнь 2023 года. Voiceflow сообщил о падении качества на 10% при переходе с `GPT-3.5-turbo-0301` на `GPT-3.5-turbo-1106`.

## Orchestration AI-пайплайна

`Orchestrator` определяет, как компоненты работают вместе в сквозной пайплайн, и следит, чтобы данные передавались между ними без сбоев. У него два шага. Первый: **определить компоненты**: модели (проще через gateway), источники данных, tools, инструменты оценки и мониторинга. Второй: **chaining**, цепочка шагов, как композиция функций. Например: обработать запрос, найти данные, собрать prompt, получить ответ, оценить его, вернуть пользователю или передать оператору. Orchestrator проверяет формат выхода каждого шага и сообщает, когда поток прерывается.

> **Пояснение.** Orchestrator AI-пайплайна не равен Airflow или Metaflow. Airflow запускает по расписанию пакетные задачи над данными. Orchestrator AI-пайплайна обрабатывает один запрос пользователя за секунды.

Если важна задержка, делайте всё возможное параллельно. Например, router и удаление `PII` можно запустить одновременно.

Инструментов много: LangChain, LlamaIndex, Flowise, Langflow, Haystack. Автор советует сначала построить приложение без них. Каждый инструмент добавляет сложность и может спрятать детали, которые нужны для отладки. Если решите взять, смотрите на три вещи:

1. **Интеграции и расширяемость.** Поддерживает ли он ваши модели и базы. Если нет, насколько трудно добавить.
2. **Сложные пайплайны.** Ветвление, параллельность, обработка ошибок.
3. **Удобство и масштаб.** Понятный API, документация, сообщество. Избегайте тех, кто тайно делает лишние вызовы.

## Обратная связь пользователей (`user feedback`)

Обратная связь всегда помогала оценивать продукт и развивать его. В AI-приложениях ещё важнее: она служит данными для следующих моделей. **Обратная связь ваша собственность, а данные конкурентное преимущество.** Продукт, который рано вышел на рынок, успевает собрать данные и запустить `data flywheel` из [главы 8](/book-summaries/ai/ai-engineering/08-dataset-engineering/). У приложений с открытым кодом здесь слабое место: вы не знаете, как пользователи запускают их у себя. И помните: обратная связь это данные пользователей. Уважайте приватность и объясняйте, как вы их используете.

### Как извлекать обратную связь из диалога

Обратная связь бывает явной и неявной. **Явная** (`explicit`): пользователь отвечает на прямой вопрос приложения, например ставит палец вверх, звёзды или «да/нет». Её лучше понимают. **Неявная** (`implicit`): её выводят из действий. Что в неё входит, зависит от приложения. Foundation models добавили много новых видов.

Диалог упрощает пользователю дачу обратной связи: он просто поправляет модель словами. Но разработчику труднее вытащить сигнал. Реплики говорят и о работе приложения, и о вкусах пользователя. Например, помощник предложил три отеля в Сиднее. Фраза «забронируйте тот, что рядом с галереями» выдаёт интерес к искусству, а вопрос «есть дешевле $200?» выдаёт чувствительность к цене. Обратную связь используют для оценки (метрики), разработки (обучение будущих моделей) и персонализации. Интуиция даёт первые сигналы, но их смысл нужно проверять анализом данных и исследованиями пользователей.

![Карта сигналов диалога: слева сигналы в словах пользователя, справа сигналы в других его действиях, у каждого указано, что он может значить](/assets/ai-engineering/ch10-feedback-signals.png)

**Сигналы в словах (`natural language feedback`).**

- **Ранний выход.** Пользователь остановил генерацию, ушёл или бросил агента: диалог, скорее всего, идёт плохо.
- **Исправление.** Фразы «Нет, ...» и «Я имел в виду...» говорят, что ответ неверен. Часто пользователь перефразирует запрос, и это можно ловить эвристиками или ML. У агентов пользователь направляет действия: «посмотри ещё страницу компании на GitHub». Просьбы «ты уверен?» и «покажи источники» не всегда значат ошибку: возможно, пользователь не доверяет модели.
- **Правки.** Если пользователь исправил сгенерированный код, исправленная часть, вероятно, была неверной. Каждая правка это пара предпочтения: исходный ответ проиграл, исправленный выиграл. Из них делают данные для preference finetuning.
- **Жалобы.** Датасет FITS (около 14 000 примеров, разбор Yuan et al. 2023) показывает разброс. В ~27% пользователь повторяет или уточняет просьбу, в ~16% жалуется, что бот не ответил или дал нерелевантное, в ~11% говорит, что ответ фактически неверен, в ~9% что он неполный. Зная причину, вы знаете, что менять: скажем, сократить ответы через prompt.
- **Эмоции и отказы модели.** Досада без объяснения тоже сигнал (колл-центры слушают, не повышает ли клиент голос). Рост `refusal rate` («Простите, я этого не знаю») обычно значит недовольство.

**Сигналы в действиях.**

- **`Regeneration`.** Перегенерация может значить «не понравилось», а может «хочу посмотреть варианты» (особенно в творческих задачах). При оплате за использование пользователь перегенерирует реже. Если приложение спрашивает «лучше, хуже или так же», получается пара для preference finetuning.
- **Организация диалогов.** Удаление чаще всего значит, что диалог плохой (но не всегда: люди стирают и неловкие диалоги). Переименование значит, что диалог хороший, а заголовок плохой.
- **Длина и разнообразие.** Длинный диалог хорош для AI-компаньона и плох для службы поддержки. Длина с низким разнообразием (бот повторяет одно и то же) говорит, что пользователь застрял.

Явную обратную связь проще читать, но её мало, и ей свойствен `response bias` (недовольные пишут чаще). Неявная богаче и шумнее: «поделился диалогом» бывает и хвалой, и жалобой. Поэтому изучайте своих пользователей и читайте сигналы вместе.

### Как проектировать обратную связь

Просите её на всём пути пользователя, но не мешайте работе.

**Когда собирать.**

- **В начале:** калибровка, как Face ID или вопросы для оценки уровня в языковом приложении. Если калибровка не обязательна, возьмите нейтральные настройки и калибруйте приложение со временем.
- **Когда что-то пошло не так:** дайте отклонить ответ, перезапустить или сменить модель. Пусть пользователь доведёт задачу до конца: сначала с AI, затем с людьми (оператор). Пример: `inpainting`: пользователь выделяет область картинки и описывает правку. Он получает результат, а вы точный сигнал.
- **Когда модель не уверена:** покажите два ответа и пусть пользователь выберет. Полные ответы дают больше информации, но их не хотят читать, и выбор становится случайным. Частичные ответы (как в Gemini) вынуждают кликнуть. Какой способ надёжнее, неясно.
- **Когда всё хорошо:** руководство Apple не советует просить отзыв ни по хорошему, ни по плохому. Но продакты говорят автору, что положительный отзыв показывает, какие функции любят. Чтобы не раздражать пользователей, просите его у небольшой доли, например у 1%.

**Как собирать.** Обратная связь должна встраиваться в работу и легко игнорироваться. Пример хорошего дизайна: Midjourney. Он создаёт четыре картинки, и каждое действие даёт свой сигнал. Upscale сильный плюс выбранной картинке, вариации более слабый плюс, перегенерация означает «не то» (хотя может быть любопытством). В GitHub Copilot Tab принимает подсказку, продолжение набора её отклоняет. Отдельным продуктам вроде ChatGPT это труднее: они вне рабочего процесса. Gmail видит, использовали ли черновик, а ChatGPT не видит, отправили ли вы письмо.

Ещё правила:

- **Контекст обратной связи.** Для глубокого анализа нужны последние 5-10 реплик. Без согласия брать их нельзя, особенно если там личные данные. Помогают пользовательское соглашение и `data donation`: пользователь делится данными вместе с отзывом.
- **Объясняйте, как используете обратную связь:** персонализация, статистика или обучение. Обещайте, что данные не покидают устройство, только если это правда.
- **Не требуйте невозможного:** дайте вариант «Не знаю», если просите выбрать между непонятными ответами.
- **Не путайте.** Автор собирала отзывы о воркшопе через Luma и увидела оценку 1 из 5 при хвалебном тексте. Причина: сердитый смайлик стоял на месте пятой звезды, шкала была в обратном порядке.
- **Приватная или публичная.** В приватном режиме люди откровеннее. Но приватные сигналы хуже для находимости и объяснимости: когда X скрыл лайки в 2024 году, пользователям стало труднее понять, почему лента рекомендует эти твиты.

### Ограничения обратной связи

Обратная связь не бесплатна. У неё те же смещения, что у любых данных.

- **`Leniency bias`.** Люди оценивают лучше, чем думают, чтобы избежать конфликта или потому что спешат. Средняя оценка водителя Uber в 2015 году была 4,8, а ниже 4,6 грозило отключением. Смещение не всегда мешает, если цель в том, чтобы отличить хороших от плохих. Смотрите на распределение оценок, а не на среднее. Помогают варианты вместо цифр: «Отличная машина», «Могло быть лучше».
- **Случайность.** Люди кликают наугад, когда не хотят думать.
- **`Position bias`.** Первый вариант выбирают чаще. Лечится случайным порядком или моделью, которая учитывает позицию.
- **Смещение предпочтений.** Люди чаще выбирают более длинный ответ (длину заметить легче, чем неточность) и тот, что увидели последним (`recency bias`).

**Вырожденная петля (`degenerate feedback loop`).** Вы получаете обратную связь только о том, что показали. Если она меняет модель, предсказания влияют на сигналы, а сигналы на следующую версию. Смещение усиливается. В рекомендациях видео A стоит чуть выше B, получает больше кликов и поднимается ещё выше. Так популярное остаётся популярным (`exposure bias`, `popularity bias`, `filter bubbles`). Если система слышит «люблю кошек» от маленькой группы, она делает больше кошек и приводит больше любителей кошек. Так приложение превращается в «кошачий рай». Тот же механизм усиливает расизм, сексизм и пристрастие к откровенному содержимому. Sharma et al. (2023) показали, что такие модели склонны к `sycophancy`: они чаще согласны с пользователем. Прежде чем встроить обратную связь, узнайте её ограничения.

![Вырожденная петля: видео A чуть выше в выдаче, его чаще показывают, он получает больше кликов, система решает, что он лучше, и ставит его ещё выше](/assets/ai-engineering/ch10-feedback-loop.png)


## Итоги главы

- AI-приложение растёт по шагам. Начинайте со схемы «запрос, модель, ответ» и добавляйте блок, когда появилась конкретная проблема.
- Шаг 1 даёт модели контекст (retrieval и tools): это аналог `feature engineering`. Шаг 2 ставит `guardrails` на вход (PII, вредные prompt) и на выход (формат, безопасность, политика при сбое). Слишком строгие guardrails вредят, поэтому считайте `false refusal rate`.
- Шаг 3 добавляет `router` (решение под запрос, экономия) и `gateway` (единый интерфейс, доступ, лимиты, fallback). Шаг 4 добавляет кэш: ключ `exact cache` должен учитывать пользователя, а `semantic cache` ненадёжен. Шаг 5 вводит циклы и write actions: доступ на запись давайте осторожно.
- Чем сложнее система, тем нужнее `observability`: метрики, логи с ID и traces. Ловите `drift` от смены prompt, поведения пользователей и модели за API. Следите за `MTTD`, `MTTR` и `CFR`.
- Обратная связь это данные и конкурентное преимущество. Она бывает явной и неявной, а диалог даёт много сигналов: правки, перефразирование, перегенерация, длина диалога.
- Встраивайте обратную связь в работу, просите её в нужные моменты и знайте смещения (leniency, position bias) и вырожденные петли.
- Границы блоков размыты: guardrails могут жить в inference-сервисе, gateway или отдельно. Многие трудности AI engineering системные, поэтому смотрите на систему целиком. Дизайн обратной связи теперь тоже задача инженера.

## Что изменилось к 2026 году

Книга написана в 2024 году. Вот что важно знать сейчас. Это наше дополнение, его нет в книге.

- **AI gateway стал отдельным продуктом.** LiteLLM, облачные шлюзы и шлюзы в Databricks или Snowflake дают роутинг, лимиты, логи и учёт стоимости.
- **Observability по стандарту.** OpenTelemetry описывает semantic conventions для GenAI: модель, токены, стоимость, вызовы tools. Langfuse, Arize, Braintrust и другие собирают traces агентов.
- **Архитектура агентов.** К схеме главы добавились MCP-серверы, sandbox для кода и подтверждение рискованных действий человеком.
- **Evals в продакшене.** Часть трафика оценивает LLM-судья онлайн. Feedback и оценки идут в warehouse как обычные данные.
- **Архитектура «по шагам» из главы работает.** Начинайте с простого и добавляйте блоки по мере проблем.
- **Tool gateway уже есть.** Автор пишет, что слой доступа к инструментам в 2024 году почти не используют. Сейчас для MCP-серверов появились шлюзы и реестры, которые дают тот же единый доступ, контроль и учёт для tools, что model gateway для моделей.

## Ключевые термины

| Термин | Значение |
|---|---|
| `guardrail` | Ограждение: проверка входа или выхода модели |
| `PII reverse map` | Таблица «плейсхолдер и исходное значение» для демаскирования ответа |
| `false refusal rate` | Доля нормальных запросов, которые система заблокировала |
| `router`, `intent classifier` | Выбирает модель или действие под запрос по предсказанному намерению |
| `gateway` | Единая точка доступа к моделям: доступ, лимиты, fallback, логи |
| `exact cache`, `semantic cache` | Кэш по точному совпадению; кэш по похожести embeddings |
| `observability` | Возможность понять сбой по логам, метрикам и traces без нового кода |
| `trace`, `span` | Путь одного запроса по шагам; один шаг этого пути |
| `drift` | Незаметное изменение prompt, поведения пользователей или модели |
| `MTTD`, `MTTR`, `CFR` | Время обнаружения, время исправления, доля неудачных изменений |
| `explicit`, `implicit feedback` | Явная обратная связь (лайки, звёзды); неявная (из слов и действий) |
| `degenerate feedback loop` | Модель усиливает свои смещения через обратную связь |
| `sycophancy` | Подхалимство: модель говорит то, что хочет услышать пользователь |

## Что это значит на практике

- **Логи LLM это данные.** Пишите запрос, итоговый prompt, ответ, версии prompt и модели, параметры sampling, токены, `latency` и стоимость в warehouse. ID запроса связывает шаги trace, как `correlation id`.
- **Метрики AI считайте в dbt.** Цена по дням, hit rate кэша, доля отказов и невалидного формата, срезы по версии prompt и релизу. Срез по версиям сразу показывает, что виновата модель, а не prompt.
- **Feedback идёт в eval-датасет.** Плохие диалоги, правки и дизлайки превращайте в тестовые случаи. Правки дают пары для finetuning, если пользователь согласен.
- **Кэш и drift.** Включайте в ключ кэша пользователя или права доступа. Ставьте алерт на смену prompt и версии модели. Высокий hit rate без проверки неверных ответов ничего не значит.
- **PII не должна уйти во внешний API.** Если контекст строится из warehouse, фильтруйте колонки до запроса. Рядом с долей пойманных опасных запросов считайте `false refusal rate`.
- **Начинайте с простого.** Router, кэш, gateway и orchestrator добавляйте, когда есть проблема, которую они решают. Каждый блок добавляет точки отказа.
- **Gateway как слой доступа.** Один вход, учёт расходов по командам, лимиты. Orchestrator LLM не Airflow: Airflow может обновлять индексы и считать метрики по логам.
- **Храните обратную связь как fact table.** Диалог, пользователь, тип сигнала, значение, позиция показа, время. Позиция нужна, чтобы убрать position bias. Контекст отзыва храните только с согласием пользователя (`data donation`).
- **Не обучайтесь на кликах вслепую.** Делайте часть показов случайной и смотрите на распределение оценок, а не на среднее.
- **Меряйте `MTTD`, `MTTR` и `CFR` и для платформы данных.**

## Практика

Три коротких опыта. Данные придуманы, случайные числа зафиксированы. Python: `python3 -I файл.py`, SQL: `duckdb`.

**1. Guardrail: маскирование PII.** Наружу уходят плейсхолдеры, ответ модели демаскируется.

```python
import re

PATTERNS = {"PHONE": r"\+7[\d\s-]{10,}\d", "EMAIL": r"[\w.]+@[\w.]+\w"}

def mask(text):
    rmap = {}
    for kind, rx in PATTERNS.items():
        for i, value in enumerate(re.findall(rx, text), 1):
            tag = f"[{kind}_{i}]"
            rmap[tag] = value
            text = text.replace(value, tag)
    return text, rmap

def unmask(text, rmap):
    for tag, value in rmap.items():
        text = text.replace(tag, value)
    return text

masked, rmap = mask("Клиент +7 916 123-45-67 (anna@example.com) не может войти.")
print("Наружу:", masked)
reply = "Проверьте права для [PHONE_1] и [EMAIL_1]."  # ответ внешней модели
print("Клиенту:", unmask(reply, rmap))
```

**2. Утечка через кэш.** Ключ без пользователя отдаёт ответ клиента `gold` клиенту `basic`.

```python
cache = {}

def answer(question, tier, key_has_user):
    key = (question, tier) if key_has_user else question
    if key not in cache:  # ответ строится из данных клиента
        cache[key] = f"возврат электроники: {14 if tier == 'gold' else 7} дней"
    return cache[key]

q = "Каковы условия возврата электроники?"
for key_has_user in (False, True):
    cache.clear()
    answer(q, "gold", key_has_user)           # первым спросил клиент gold
    second = answer(q, "basic", key_has_user)  # потом спросил клиент basic
    print("ключ с пользователем:" if key_has_user else "ключ без пользователя:", second)
```

```text
ключ без пользователя: возврат электроники: 14 дней
ключ с пользователем: возврат электроники: 7 дней
```

**3. DuckDB: срез по версиям.** В 2000 запросов мы сами вшили две смены: prompt `v1` на `v2` и тихое обновление модели. Срез показывает, кто виноват в росте ошибок формата.

```sql
SELECT setseed(0.42);
CREATE TABLE requests AS
SELECT g AS request_id,
       CASE WHEN g <= 1200 THEN 'v1' ELSE 'v2' END AS prompt,
       CASE WHEN g <= 1400 THEN 'model-0301' ELSE 'model-1106' END AS model,
       (CASE WHEN g <= 1200 THEN 150 + random() * 200
             ELSE 80 + random() * 120 END)::INT AS out_tokens,
       random() >= (CASE WHEN g <= 1400 THEN 0.04 ELSE 0.10 END) AS format_ok
FROM generate_series(1, 2000) AS t(g);

SELECT prompt, model, count(*) AS requests,
       round(avg(out_tokens)) AS avg_out_tokens,
       round(100.0 * avg((NOT format_ok)::INT), 1) AS format_err_pct
FROM requests
GROUP BY prompt, model
ORDER BY min(request_id);
```

```text
┌─────────┬────────────┬──────────┬────────────────┬────────────────┐
│ prompt  │   model    │ requests │ avg_out_tokens │ format_err_pct │
│ varchar │  varchar   │  int64   │     double     │     double     │
├─────────┼────────────┼──────────┼────────────────┼────────────────┤
│ v1      │ model-0301 │     1200 │          250.0 │            4.6 │
│ v2      │ model-0301 │      200 │          133.0 │            6.0 │
│ v2      │ model-1106 │      600 │          139.0 │           12.5 │
└─────────┴────────────┴──────────┴────────────────┴────────────────┘
```

Смена prompt сократила ответы с 250 до 133 токенов, ошибки формата почти не изменились. Смена модели при том же prompt подняла их с 6,0% до 12,5%. Без версий в логах этот вывод невозможен.
