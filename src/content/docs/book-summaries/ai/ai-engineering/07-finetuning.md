**Главная мысль:** Finetuning меняет веса модели. Он нужен, чтобы поправить форму ответа: стиль, формат, поведение. Для фактов лучше `RAG`. Главная техническая проблема finetuning — память GPU. Почти все современные приёмы (`PEFT`, `LoRA`, `QLoRA`, `quantization`) придуманы, чтобы её сэкономить. Решать, делать ли finetuning, нужно только после системных экспериментов с prompt и RAG.

## О чём глава

Глава отвечает на вопрос: как дообучить модель под свою задачу и стоит ли это делать. В [главе 5](/book-summaries/ai/ai-engineering/05-prompt-engineering/) и [главе 6](/book-summaries/ai/ai-engineering/06-rag-and-agents/) модель настраивали снаружи: давали ей инструкции, контекст и инструменты. Здесь мы меняем сами веса. Это даёт больше возможностей, но стоит больше денег, данных и знаний.

Порядок такой: обзор видов finetuning, решение «делать или нет», память как узкое место, техники (`PEFT`, `LoRA`, `QLoRA`, `model merging`) и тактика (модель, framework, гиперпараметры). Автор честно предупреждает: глава самая трудная в книге, и части с лишними для вас деталями можно пропускать. Откуда брать данные для finetuning, расскажет [глава 8](/book-summaries/ai/ai-engineering/08-dataset-engineering/). Практики часто говорят автору, что сам finetuning несложен, трудно достать данные.

## Обзор finetuning

`Finetuning` — это продолжение обучения модели на ваших данных: меняются все веса или часть. Вы начинаете с базовой модели, которая умеет много, но не всё нужное. Чаще всего finetuning учит модель следовать инструкциям, прежде всего держать нужный стиль и формат. Реже он усиливает знания в узкой области или делает модель безопаснее. Цена высокая: данные, железо, люди с опытом ML и поддержка.

### Transfer learning

Finetuning — частный случай `transfer learning`: знание с одной задачи переносят на другую. Идея старая (1976 год). Люди делают так постоянно: кто умеет играть на пианино, тот быстрее учит другой инструмент. Яркий ранний пример в ML: многоязычный переводчик Google (2016). Он научился переводить с португальского на испанский, хотя таких пар в обучении не было. Знание «перетекло» через общее представление языков.

Для LLM схема такая. Pre-training на предсказании следующего токена даёт знания на огромных текстах. Потом это знание переносят на узкие задачи, например юридические вопросы или `text-to-SQL`, где данных обычно мало. Именно эта способность делает foundation models такими ценными. Есть и другой вид переноса, `feature-based transfer`: одна модель извлекает признаки (`embeddings`), другая ими пользуется.

Главный выигрыш — `sample efficiency`: модель учится нужному поведению на меньшем числе примеров. С нуля для юридических вопросов нужны миллионы примеров. Хорошую базовую модель иногда хватает дообучить на нескольких сотнях. По статье про InstructGPT, finetuning «открывает» способности, которые у модели уже есть, но которые трудно вызвать одним prompt.

### Виды finetuning

Любое обучение после pre-training считается finetuning. Автор выделяет пять видов.

| Вид | Что делает |
|---|---|
| `continued pre-training` (self-supervised finetuning) | Продолжает самообучение на сырых текстах вашей области. Дешёвый шаг перед дорогой разметкой |
| `infilling finetuning` | Учит заполнять пропуск. Полезно для правки текста и отладки кода |
| `SFT` | Учит на парах (инструкция, ответ). Подгоняет модель под человеческие ожидания |
| preference finetuning | Учит на тройках (инструкция, лучший ответ, худший ответ) через `reinforcement learning` |
| long-context finetuning | Расширяет длину контекста, часто через `positional embeddings`. Труднее остальных, на коротких текстах модель может ухудшиться |

Пример из книги: из Llama 2 получили всё семейство Code Llama. Сначала обучение на коде с заполнением пропусков (500B токенов), потом ветки: Python (100B токенов) и длинный контекст (20B токенов, с 4096 до 16 384). В конце короткий `SFT` (5B токенов) для версии Instruct. Так получили три семейства: обычное, Instruct и Python.

Разработчики моделей дообучают их до выпуска и часто дают несколько версий. Вы почти всегда будете дообучать модель, которая уже прошла post-training. Чем она лучше и ближе к вашей задаче, тем меньше работы.

## Когда делать finetuning

Finetuning требует намного больше ресурсов, чем prompt, поэтому его пробуют после серьёзных опытов с prompt. Подходы не исключают друг друга: реальные задачи часто требуют обоих.

### Причины делать finetuning

- **Качество на вашей задаче.** Универсальная модель может хорошо пройти benchmarks и всё же ошибаться на редком диалекте SQL или на запросах одного клиента. Тогда finetuning на ваших данных помогает. Так же его применяют, чтобы выдавать строгую структуру, например JSON.
- **Смещения (`bias`).** Модель, которая даёт CEO только мужские имена, можно поправить finetuning на подобранных данных.
- **Маленькие модели.** Их проще дообучать, и они дешевле в production. Частый приём: `distillation`, когда маленькую модель учат на ответах большой. Grammarly дообучила Flan-T5, которая в 60 раз меньше GPT-3, и обошла её на задачах редактирования. Хватило 82 000 пар (инструкция, ответ).

Раньше сильных моделей для finetuning почти не было. Теперь открытых моделей много, и finetuning стал реалистичнее.

### Причины не делать finetuning

Многое из этого достижимо хорошим prompt и контекстом. Минусы такие.

- **Другие задачи могут стать хуже.** Дообучили модель на изменении заказов, а рекомендации и отзывы упали. Лекарство: дообучать на всех нужных задачах, держать отдельные модели или слить их (раздел про `model merging`).
- **Нужны данные.** Размечать вручную долго и дорого. Открытые и AI-данные дешевле, но качество у них разное.
- **Нужны навыки обучения.** Выбор модели, optimizer, `learning rate`, объём данных, `overfitting`, оценка в ходе обучения. Frameworks автоматизируют часть работы, но чинить придётся вам.
- **Нужен деплой.** Хостить самому или брать API? Inference больших моделей нетривиален ([глава 9](/book-summaries/ai/ai-engineering/09-inference-optimization/)).
- **Нужна поддержка.** Новые базовые модели выходят быстро и могут обогнать вашу. Нужна политика: насколько большим должен быть выигрыш, чтобы перейти на новую модель.

**Начинайте с prompt.** Автор часто видит такую историю. Человек говорит, что prompt не работает, и просит finetuning. Разбор показывает, что prompt был минимальным: расплывчатые инструкции, примеры не из реальных данных, нет метрик. После наведения порядка качества хватило. Работа с prompt к тому же даёт основу для finetuning: конвейер оценки, правила разметки и учёт экспериментов.

### Узкие области и призыв к осторожности

Не верьте аргументу «универсальные модели плохи для узкой области, значит, нужна своя». Чем сильнее универсальные модели, тем лучше они решают и узкие задачи.

Пример: BloombergGPT (март 2023), 50 млрд параметров. Обучение заняло около 1,3 млн GPU-часов на A100, то есть 1,3–2,6 млн долларов только на вычисления. В том же месяце вышла GPT-4-0314, и на финансовых benchmarks она оказалась заметно сильнее. На ConvFinQA точность была 76,48 против 43,41, на FiQA (тональность) F1 87,15 против 75,07. С тех пор вышли модели среднего размера, сравнимые с GPT-4: Llama 3-70B-Instruct и Qwen2-72B-Instruct (обе открытые, их можно хостить самому). Автор оговаривается: benchmarks не отражают реальную работу, и для самой Bloomberg модель могла быть полезной. Опыт команды тоже ценен. Общий вывод: и опыты с prompt, и finetuning требуют системного процесса.

У finetuning раньше было ещё одно преимущество: примеры из prompt уходят в веса, и prompt короче. Сегодня выгода меньше из-за `prompt caching` (глава 9). Но число примеров в prompt ограничено длиной контекста, а в finetuning такого лимита нет.

### Finetuning или RAG

Если prompt исчерпан, выбор зависит от типа ошибок.

- **Информационные ошибки: нужен RAG.** Модель не знает ваших данных или знает устаревшее. Пример: вопрос о числе студийных альбомов Тейлор Свифт, модель говорит 10, а правильно 11. Работа Ovadia et al. (2024) показала: на вопросах о свежих событиях RAG побеждает finetuning. Для Mistral-7B точность была 0,48 у базовой модели, 0,88 у базовой с RAG и только 0,50 и 0,59 у дообученных без RAG. Более того, RAG с базовой моделью оказался лучше RAG с дообученными. На MMLU RAG тоже обошёл finetuning почти по всем категориям для трёх моделей (Mistral 7B, Llama 2-7B, Orca 2-7B).
- **Поведенческие ошибки: нужен finetuning.** Факты верны, но форма не подходит. Например, в техническом задании нет деталей, нужных командам, или HTML не компилируется. Сюда же `semantic parsing` (превращение текста в структуру вроде JSON). Сильные готовые модели хороши для частых синтаксисов: JSON, YAML, регулярные выражения. Для редкого синтаксиса, например языка одного инструмента, они слабее, и finetuning оправдан.

Короткое правило: **finetuning для формы, RAG для фактов.** Не все согласны: авторы Llama 3.1 хотят, чтобы модель после обучения «знала, что знает», а не получала новые знания.

Если есть ошибки обоих типов, начинайте с RAG. Он проще: не нужны данные для обучения и хостинг своей модели. Начинайте с простого поиска по словам, например `BM25`. RAG и finetuning можно сочетать, но выигрыш не гарантирован: в том же опыте RAG поверх дообученной модели улучшил MMLU лишь в 43% случаев.

Единого маршрута нет, но типичный порядок такой. Перед каждым шагом задайте критерии и постройте конвейер оценки ([глава 4](/book-summaries/ai/ai-engineering/04-evaluate-ai-systems/)).

1. Один prompt, с версиями.
2. Примеры в prompt (от 1 до 50).
3. Подключите источники данных, начните с простого поиска.
4. Остались информационные ошибки: более сложный RAG, например поиск по `embeddings`. Остались поведенческие: finetuning. RAG усложняет конвейер inference, а finetuning усложняет разработку, но не inference.
5. Объедините RAG и finetuning.

![Дерево решений: eval и prompt, затем тип ошибок: информационные ведут к RAG, поведенческие к finetuning, оба типа начинаются с RAG](/assets/ai-engineering/ch07-finetune-or-not.png)

Как читать схему. Это наша сводка. Сначала eval и системный prompt, потом тип ошибок. Для фактов берите RAG, для формы finetuning. Если ошибки обоих типов, начинайте с RAG.

## Память: главный bottleneck

Finetuning очень прожорлив по памяти. Поэтому большинство техник нацелены на её экономию. Автор даёт формулы для быстрой прикидки: какое железо нужно, чтобы запустить или дообучить модель.

Главное из раздела:

- память становится узким местом и для inference, и для finetuning, причём для finetuning она заметно больше;
- три фактора: число параметров, число `trainable parameters` и числовой формат (сколько байт на значение);
- меньше обучаемых параметров значит меньше памяти: на этом стоит `PEFT`;
- `quantization` переводит значения в формат с меньшим числом бит. Модель 13B в FP32 занимает 52 ГБ на веса, в 2-байтном формате 26 ГБ;
- для inference берут 16, 8, а иногда 4 бита. Обучение чувствительнее к точности, поэтому там используют `mixed precision`.

### Backpropagation и trainable parameters

Параметры при finetuning бывают `trainable` (обновляются) и `frozen` (остаются прежними). Обучают сеть через `backpropagation`: шаг состоит из двух проходов.

- **Forward pass:** считаем выход из входа.
- **Backward pass:** сравниваем выход с ожидаемым, получаем `loss`, считаем `gradient` каждого обучаемого параметра (его вклад в ошибку), и `optimizer` меняет параметр. Чаще всего берут `Adam`, реже `SGD`.

Inference использует только forward pass. Для каждого обучаемого параметра на обратном проходе появляются лишние значения: gradient и состояния optimizer. Чем больше обучаемых параметров, тем больше памяти. Остальные параметры замораживают, и для них gradient считать не нужно.

### Арифметика памяти

Арифметика нужна, чтобы выбрать железо или проверить, потянете ли вы модель. Если для inference нужно 30 ГБ, чип на 24 ГБ не подойдёт. Пусть `N` — число параметров, `M` — байт на значение.

**Inference.** Веса занимают `N × M`. Ещё нужна память под `activations` и `KV cache`. Для многих приложений её принимают за 20% от весов:

```text
память inference ≈ N × M × 1,2
```

Модель 13B по 2 байта: 26 ГБ на веса и 31,2 ГБ всего. Модель 70B по 2 байта требует 140 ГБ только на веса.

**Обучение.** Нужны веса, activations, gradients и состояния optimizer:

```text
память обучения = веса + activations + gradients + optimizer states
```

Каждому обучаемому параметру нужен один gradient и от 0 до 2 значений состояния: у чистого `SGD` ноль, у `momentum` одно, у `Adam` два. Если обновлять все 13B параметров с Adam по 2 байта, то 13 млрд × 3 × 2 байта = 78 ГБ. Если обучаемых параметров 1 млрд, то 6 ГБ.

Оговорка автора: формулы считают activations малыми, но на деле они бывают больше весов. Их можно не хранить, а пересчитывать (`gradient checkpointing`). Память падает, время обучения растёт.

![Память для модели 7B при finetuning: полный finetuning с Adam занимает 56 ГБ, с SGD 28 ГБ, LoRA около 14 ГБ, QLoRA около 3,6 ГБ](/assets/ai-engineering/ch07-memory-breakdown.png)

Как читать схему. Это наша схема, в книге её нет. Каждая строка — способ дообучить модель 7B без учёта activations. Полный finetuning с Adam не помещается в 24 ГБ, а LoRA и QLoRA помещаются с запасом.

### Числовые форматы

Числа в нейросетях хранят как `floating point` по стандарту IEEE 754 или как целые.

| Формат | Бит | Особенность |
|---|---|---|
| `FP32` | 32 | Одинарная точность, стандарт прошлых лет |
| `FP16` | 16 | Половинная точность: 5 бит диапазона, 10 бит точности |
| `BF16` | 16 | Придумал Google. 8 бит диапазона, как у FP32, но всего 7 бит точности |
| `TF32` | 19 | Придумала NVIDIA. Диапазон как у FP32, точность как у FP16 |
| `INT8`, `INT4` | 8, 4 | Целые числа, растут в inference |

Каждый формат с плавающей запятой делит биты на знак (1 бит), диапазон (`exponent`) и точность (`mantissa`). Больше бит диапазона значит шире допустимые значения. Больше бит точности значит меньше ошибка округления. Название TF32 вводит в заблуждение: формат занимает 19 бит, а не 32.

BF16 держит большие числа, но округляет грубее FP16. Это не мелочь. Веса Llama 2 вышли в BF16, многие команды загрузили их в FP16, и качество оказалось намного хуже заявленного. Модель нужно загружать в том формате, для которого она выпущена.

### Quantization

Меньше бит значит меньше памяти: модель 10B занимает 40 ГБ в 32 битах и 20 ГБ в 16. Это простой приём, он подходит для любых задач и архитектур. Строго говоря, quantization — перевод в целочисленный формат, но книга называет так любое снижение точности.

**Что квантовать.** Всё, что занимает много памяти. Чаще квантуют веса: это влияет на качество стабильнее, чем quantization activations.

**Когда квантовать.** После обучения (`PTQ`) или во время обучения. PTQ используют намного чаще, и он важнее для разработчиков приложений. Главные frameworks дают его в несколько строк.

**Inference.** Сначала модели обслуживали в FP32, с конца 2010-х всё чаще в 16 битах и ниже. Метод `LLM.int8()` довёл LLM до 8 бит, `QLoRA` до 4. Можно смешивать точность: Apple в 2024 для запуска на устройстве смешала 2-битный и 4-битный форматы (в среднем 3,5 бита на вес). Предел один: меньше 1 бита на значение не бывает. `BitNet b1.58` Microsoft использует 1,58 бита на параметр (у веса три значения: −1, 0, +1, а log₂(3) ≈ 1,58) и до 3,9B параметров сравнима по качеству с Llama 2 в 16 битах. Низкая точность ещё и ускоряет: можно взять больший batch, вычисления идут быстрее (но преобразование форматов само требует вычислений). Минус: каждое преобразование слегка меняет значение, и много малых изменений способны сильно ухудшить качество. Значения вне диапазона превращаются в `inf` или в произвольное число. Модель обучают в высокой точности ради качества, а для inference снижают её.

**Обучение.** Quantization при обучении нужна для двух целей: получить модель, которая хорошо работает в низкой точности, и снизить стоимость обучения.

- `QAT` имитирует низкую точность при обучении, чтобы модель научилась в ней работать. Время обучения не снижается.
- Прямое обучение в низкой точности помогает обеим целям, но backpropagation к ней чувствительна. Character.AI (2024) сообщила об обучении полностью в INT8. Это убирает разрыв между обучением и inference. Но ошибки округления накапливаются за много шагов, а loss нужно считать точно.
- `Mixed precision`: копию весов держат в высокой точности, остальное в низкой. Нужные части выбирает `automatic mixed precision` (`AMP`).

Часто и этапы идут в разной точности: команда с большими вычислениями обучает модель в высокой, а разработчики с меньшими ресурсами дообучают её в низкой.

FP16 точнее на обычных числах, но за пределом 65 504 даёт `inf`. BF16 грубее, зато диапазон широкий. Проверку мы собрали в разделе «Практика» в конце главы.

## Техники finetuning

Чем меньше памяти нужно, тем больше людей могут дообучать модели. Этот раздел про экономные техники, прежде всего `PEFT`, и про `model merging`. Слияние обычно не считают finetuning, но оно дополняет его: finetuning подгоняет одну модель, а слияние объединяет несколько.

### PEFT: parameter-efficient finetuning

Когда модели были малы, их дообучали целиком (`full finetuning`). Для 7B в 16 битах это 14 ГБ весов и ещё 7B × 3 × 2 байта = 42 ГБ на gradients и состояния Adam. Итого 56 ГБ без activations. Это больше памяти большинства потребительских GPU (12–24 ГБ). К тому же полному finetuning нужны много качественных размеченных данных.

Первое решение — `partial finetuning`: обучать часть слоёв, обычно ближайшие к выходу. Память падает, но метод `parameter-inefficient`. Houlsby et al. (2019) показали: для BERT large нужно обновлять около 25% параметров, чтобы на GLUE сравняться с полным finetuning. При 1 млн обучаемых параметров дообучение верхних слоёв теряло около 9,5% точности, а адаптеры меньше 1% (значения мы прочитали с графика книги).

Тот же Houlsby предложил идею `PEFT`: вставить в каждый блок Transformer два малых модуля-адаптера (`adapter`) и обучать только их. Они получили качество всего на 0,4% ниже полного при 3% обучаемых параметров. Минус: адаптеры добавляют слои, и inference замедляется. Метод считают параметрически эффективным, если он даёт качество, близкое к полному finetuning, и обучает на несколько порядков меньше параметров. Методы PEFT обычно и `sample-efficient`: хватает нескольких тысяч примеров, а полному finetuning нужны десятки тысяч и больше.

### Техники PEFT

Их делят на две группы.

- **Adapter-based (аддитивные)**: добавляют модули к весам. Это `LoRA` (самая популярная), `BitFit`, `IA3` (удобна для нескольких задач за счёт `mixed-task batching`), `LongLoRA` (расширяет контекст).
- **Soft prompt-based**: добавляют к входу обучаемые векторы, `soft prompts`. В отличие от обычных (`hard`) prompt, человек их не читает, и их можно обучить через `backpropagation`. Варианты `prefix tuning`, `P-tuning` и `prompt tuning` различаются тем, куда вставлены векторы. Автор признаётся, что не встречал человека, который объяснил бы их различия «на месте».

Что используют на самом деле? Автор в октябре 2024 разобрал более 1000 issues репозитория `huggingface/peft`. LoRA упомянута примерно в 720, QLoRA в 65, остальные методы меньше чем в 30. LoRA доминирует.

### LoRA

`LoRA` (Low-Rank Adaptation; Hu et al., 2021) добавляет параметры так, что они **не увеличивают latency**: вместо новых слоёв она использует модули, которые потом сливают с исходными весами.

**Как работает.** Для матрицы весов `W` размера `n × m` выберите ранг `r` и постройте две матрицы: `A` размера `n × r` и `B` размера `r × m`. Их произведение имеет тот же размер, что `W`. Его прибавляют к `W` с коэффициентом `α / r`:

```text
W' = W + (α / r) · A × B
```

При finetuning обновляют только `A` и `B`, а `W` заморожена.

![LoRA: матрица W заморожена, матрицы A и B обучаются, их произведение с коэффициентом α/r прибавляется к W и даёт W'](/assets/ai-engineering/ch07-lora.png)

Как читать схему. Две малые матрицы `A` и `B` перемножают, получают добавку размера `W` и складывают с замороженной `W`. Новая матрица `W'` заменяет `W` в слое.

В основе лежит `low-rank factorization`: матрицу 9 × 9 (81 параметр) можно записать как произведение 9 × 1 и 1 × 9 (всего 18 параметров). Это приближение с потерей, и чем выше ранг, тем больше информации сохраняется. LoRA на GPT-3 сравнялась с полным finetuning или обошла его на нескольких задачах при 4,7 млн обучаемых параметров, то есть 0,0027%.

**Почему LoRA работает.** Работы Li, Aghajanyan и Hu показали: у LLM много параметров, но очень малая `intrinsic dimension`, то есть мало параметров реально нужно подправить для новой задачи. Pre-training неявно снижает её: чем лучше модель обучена, тем проще её дообучить на малом числе параметров и данных. Тогда правка весов узкая, то есть низкого ранга. Почему тогда не использовать LoRA и для pre-training? Попытки есть (`ReLoRA`, `GaLore`), но пока до 1,3B и 7B параметров. Если довод про внутреннюю размерность верен, полноранговое pre-training всё равно понадобится.

**Конфигурация.** Нужно решить три вещи.

- **К каким матрицам.** Чаще всего берут четыре матрицы attention: запрос (`Wq`), ключ (`Wk`), значение (`Wv`) и выход (`Wo`). Hu et al. зафиксировали для GPT-3 175B бюджет 18 млн параметров (0,01%). Его можно потратить так: одна матрица с рангом 8, две с рангом 4 или четыре с рангом 2. Лучше всего вышли четыре матрицы с рангом 2 (на WikiSQL 73,7 и MultiNLI 91,7). Если можно взять только две, берите `Wq` и `Wv`: в целом они дают лучшие результаты. Для одной `Wq` с рангом 8 результат на WikiSQL был хуже, 70,4. Позже практики нашли: LoRA на большем числе матриц, включая слои feedforward, даёт лучшее качество. Databricks получила самый большой прирост, применив LoRA ко всем слоям feedforward. Но при ограниченной памяти LoRA на attention обычно эффективнее. Чтобы настроить LoRA, нужно знать архитектуру модели: состав её весов ищите в статье модели.
- **Какой ранг.** Часто хватает `r` от 4 до 64. Рост `r` выше нужного не улучшает качество, а иногда вредит из-за overfitting. Но у Raschka на его задачах лучшим оказался `r = 256`.
- **Какой `α`.** Автор чаще всего видел отношение `α : r` от 1:8 до 8:1. Оптимум разный: при малом `r` иногда нужен большой `α`, при большом `r` малый. Ищите его опытом по парам `(r, α)` на вашей задаче.

**Как обслуживать.** Есть два способа.

1. **Слить** `A` и `B` с `W`: получите `W'`, лишних вычислений и latency нет. Хорош для одной LoRA-модели.
2. **Держать отдельно** `W`, `A` и `B`: слияние идёт в момент inference, latency чуть выше. Хорош для `multi-LoRA serving`.

Второй способ экономит хранилище, если у вас много клиентов. Пример книги: `W` размером 4096 × 4096 (16,8 млн параметров), ранг 8, то есть `A` и `B` вместе 65 536 параметров. Для 100 клиентов 100 слитых `W'` дают 1,68 млрд параметров. Одна `W` и 100 адаптеров дают 23,3 млн, это в 72 раза меньше. Переключение между клиентами тоже быстрее: нужно загрузить только адаптер. Apple использовала несколько адаптеров LoRA на одной базовой модели 3B для разных функций iPhone. Готовые адаптеры можно искать на Hugging Face и в AdapterHub.

Подвох LoRA: она не так мощна, как полный finetuning, и требует менять реализацию модели. Но для популярных моделей `PEFT`, Axolotl, unsloth и LitGPT уже поддерживают её.

### Quantized LoRA: QLoRA

Память адаптера LoRA ничтожна: для Llama 2 13B (26 ГБ весов) адаптер ранга 2 занимает около 6,55 МБ, для GPT-3 (350 ГБ) около 37,7 МБ. Поэтому ещё сильнее урезать параметры LoRA почти бесполезно. Лучше квантовать веса.

`QLoRA` (Dettmers et al., 2023) хранит веса базовой модели в 4 битах в формате `NF4` (он учитывает, что веса обычно распределены нормально вокруг нуля). Для прямого и обратного прохода веса возвращают в BF16. Ещё QLoRA использует `paged optimizers`: они переносят данные между CPU и GPU, когда на GPU кончается память. Так модель 65B дообучают на одной GPU с 48 ГБ. Семейство Guanaco (модели Llama от 7B до 65B, дообученные в 4 битах) в рейтинге Elo с GPT-4 в роли судьи (май 2023) показало конкурентные результаты. Guanaco 65B (41 ГБ) набрал около 1022 против 966 у ChatGPT, а GPT-4 был впереди с 1348. Есть и другие варианты quantized LoRA: QA-LoRA, ModuLoRA, IR-QLoRA. Минус QLoRA: quantization и dequantization дороги, поэтому время обучения может вырасти.

### Model merging и multi-task finetuning

При `model merging` вы объединяете несколько моделей в одну. Слитую модель не обязательно дообучать, но finetuning часто улучшает её. Без finetuning слияние можно сделать без GPU, поэтому оно удобно независимым разработчикам. Ценность двух видов: качество (две модели по-разному хороши на одной задаче, слитая лучше обеих) и экономия памяти (одна модель вместо двух). Для моделей на адаптерах два адаптера можно слить в один.

**Multi-task finetuning.** Одновременное обучение на всех задачах требует больше данных. Последовательное ведёт к `catastrophic forgetting`: модель забывает старую задачу. Слияние даёт третий путь: дообучить отдельные модели параллельно и слить их. Забывания меньше, а каждая задача выучена хорошо.

Слияние нужно и там, где модель надо уместить на телефон, автомобиль или робот. Вместо нескольких моделей кладут одну. Это же способ `federated learning`: копии модели на устройствах учатся на своих данных, потом их сливают.

**Ensembling и merging.** Ансамбль объединяет **ответы** моделей, и на каждый запрос нужно несколько вызовов. Слияние объединяет **параметры**, и вызов один. Многие модели в верхней части Open LLM Leaderboard Hugging Face — слитые.

Методы слияния экспериментальны. Автор группирует их по трём подходам: суммирование, стек слоёв и конкатенация.

**Суммирование.** Если параметры двух моделей в разных масштабах, перед суммой их стоит перемасштабировать.

- **Линейная комбинация.** Взвешенное среднее весов: `(w_A · A + w_B · B) / (w_A + w_B)`. Работает удивительно хорошо, особенно для моделей на одной базовой модели. Идея старая (Perrone, 1993), её часто применяют в federated learning. Работа `model soups` показала: усреднение весов нескольких дообученных моделей повышает точность без роста inference. Чаще усредняют отдельные компоненты, например адаптеры. Если слои разного размера, их можно спроецировать в одну размерность.
- **Task vector.** Дообученная модель минус базовая. Вектор хранит суть задачи. Его можно складывать (получаем обе способности) или вычитать (убираем нежелательное поведение, например смещение): `task arithmetic`. Task vector можно построить и из весов LoRA.

![Task vectors: разность дообученной и базовой модели; сумма даёт обе способности, среднее ослабляет обе, вычитание убирает способность](/assets/ai-engineering/ch07-task-vectors.png)

Как читать схему. Это наша схема. Из `W_A` и `W_B` вычитаем базовую `W₀` и получаем `Δ_A` и `Δ_B`. Сумма собирает обе способности, среднее ослабляет обе вдвое, вычитание убирает одну.

- **SLERP.** Сферическая интерполяция. Векторы представляют как точки на сфере, слитый вектор лежит на кратчайшем пути между ними. Обычное среднее уходит внутрь сферы и укорачивает вектор, SLERP сохраняет длину. Он сливает только два вектора за раз.
- **Удаление лишних изменений.** При finetuning большинство изменений параметров мелкие и не влияют на качество. Для одной модели они безвредны, но в слитой мешают друг другу. `TIES` и `DARE` сначала возвращают такие параметры к значению базовой модели (обнуляют элементы task vector), и качество слитой модели растёт. Чем больше моделей сливаете, тем важнее такая очистка. Здесь pruning нужен не для экономии памяти, а ради качества. В книге оставить 20% самых больших изменений почти так же хорошо, как 100%.

**Стек слоёв** (`layer stacking`, `frankenmerging`). Слои из разных моделей ставят друг на друга. Итог обычно нужно дообучать. Пример: Goliath-120B из двух Llama 2-70B (по 72 слоя из 80). Две важные идеи:

- `sparse upcycling`: из обычной модели делают `MoE`, копируя MLP несколько раз и добавляя `router`. Это даёт модели лучше, чем MoE с нуля. По схожему принципу Together AI смешала шесть открытых моделей в `Mixture-of-Agents`, сопоставимую с GPT-4o на некоторых benchmarks.
- `depthwise scaling` (model upscaling): так получают модель больше имеющейся, не обучая с нуля. Например, команда обучила модель под GPU на 40 ГБ, а теперь есть машина на 80 ГБ. Две копии на 32 слоя, у одной убрали 8 верхних, у другой 8 нижних, и поставили друг на друга. Получилось 24 + 24 = 48 слоёв, так сделали SOLAR 10.7B. Потом модель дообучают.

**Конкатенация.** Параметры склеивают, ранг двух адаптеров становится `r₁ + r₂`. Память не экономится, поэтому метод **не рекомендуют**.

Ловушка: усреднять матрицы `A` и `B` адаптеров по отдельности не то же самое, что усреднять сами правки `A × B`.

## Тактика finetuning

Решение принято, и сам процесс довольно прост. Нужно выбрать базовую модель, метод и framework.

**Базовая модель.** Критерии те же, что в [главе 4](/book-summaries/ai/ai-engineering/04-evaluate-ai-systems/). OpenAI описывает два пути.

- **Progression.** Проверьте код на самой дешёвой модели. Проверьте данные на средней: если training loss не падает при росте данных, что-то не так. Потолок качества узнайте на лучшей. Потом обучите все модели и постройте кривую «цена и качество».
- **Distillation.** Дообучите самую сильную модель на малом датасете, с её помощью создайте больше данных и обучите на них дешёвую модель.

Автор советует до длинного запуска проверить путь для checkpoints: однажды у него обучение упало через восемь часов, потому что папки не существовало.

**Метод.** В начале проекта разумно взять самую сильную модель, какую можете себе позволить: если она не справляется, слабые справятся хуже. Для метода начните с `LoRA`, полный finetuning пробуйте позже. Для полного нужны минимум тысячи примеров. На нескольких сотнях он может быть не лучше LoRA. Подумайте, сколько дообученных моделей вы будете обслуживать: с адаптерами нужна одна полная модель.

**Framework.** Простейший вариант — finetuning API: загрузили данные, выбрали модель. Но вы привязаны к моделям провайдера и его настройкам. Гибче frameworks: LLaMA-Factory, unsloth, PEFT, Axolotl, LitGPT. Если вы дообучаете сами, вам нужны вычисления. Для техник на адаптерах большинству моделей хватает GPU среднего класса. Для нескольких машин нужны DeepSpeed, PyTorch Distributed или ColossalAI. Полный finetuning у многих открытых моделей можно запустить из кода на GitHub.

### Гиперпараметры

- **Learning rate** — размер шага. Обычно между `1e-7` и `1e-3`. Сильные колебания loss значат слишком большой шаг, а очень медленное падение слишком малый. Увеличивайте, пока кривая остаётся стабильной. Частая практика: взять learning rate конца pre-training и умножить на число от 0,1 до 1. По ходу обучения его можно менять расписанием (`scheduler`): в начале больше, к концу меньше.
- **Batch size.** Слишком малый batch (меньше 8) делает обучение нестабильным. Большой batch усредняет сигналы разных примеров, обновления стабильнее, но он требует памяти и дорогого железа. Вычисления остаются узким местом finetuning. Если память не позволяет, используйте `gradient accumulation`: накапливайте gradients за несколько batch и обновляйте веса после.
- **Epochs.** Для миллионов примеров хватает 1–2 epoch, для тысяч нужно 4–10. Если оба loss стабильно падают, помогут ещё epoch и данные. Если train loss падает, а validation loss растёт, это `overfitting`: уменьшайте число epoch.
- **Prompt loss weight.** Сколько токены prompt вносят в loss по сравнению с токенами ответа. При 100% prompt и ответ вносят равный вклад, при 0% модель учится только на ответах. Обычно ставят 10%: модель в основном учится на ответах, потому что при inference prompt задаёт пользователь.

## Итоги главы

- Finetuning — это продолжение обучения модели и вид `transfer learning`. Он повышает `sample efficiency`: вместо миллионов примеров хватает сотен или тысяч.
- Бывают `continued pre-training`, `SFT`, preference finetuning, long-context finetuning и `infilling`. Разработчики приложений чаще всего дообучают модель, которая уже прошла post-training.
- Finetuning нужен для формы, а RAG для фактов. Если ошибки обоих типов, начинайте с RAG. Перед этим нужны eval и системный prompt.
- Цена высокая: данные, навыки ML, деплой, поддержка. Finetuning может ухудшить соседние задачи, а универсальные модели часто обгоняют узкие (пример BloombergGPT).
- При обучении память складывается из весов, `activations`, `gradients` и `optimizer states`. Adam добавляет три значения на обучаемый параметр. Полный finetuning 7B в 16 бит требует 56 ГБ без activations.
- BF16 шире по диапазону, FP16 точнее. Модель нужно загружать в формате, для которого она выпущена.
- `Quantization` снижает число бит на значение. Для inference стандарт `PTQ`, для обучения нужны `QAT` и `mixed precision`. Ниже 1 бита опуститься нельзя.
- `LoRA` обучает две малые матрицы `A` и `B` вместо правки `W`. После слияния она не добавляет latency. Обычно хватает `r` от 4 до 64. `QLoRA` хранит веса в 4 битах и позволяет дообучать 65B на одной GPU с 48 ГБ.
- `Model merging` объединяет модели суммированием, стеком слоёв или конкатенацией. Оно помогает с multi-task finetuning и моделями на устройствах.
- Начинайте с LoRA и сильной базовой модели. Learning rate, batch size и epochs подбирайте по кривым loss.

## Что изменилось к 2026 году

Книга написана в 2024 году. Вот что важно знать сейчас. Это наше дополнение, его нет в книге.

- **Finetuning нужен ещё реже.** Модели стали сильнее, контекст длиннее. Порядок «prompt → RAG → finetuning» остаётся верным.
- **Reinforcement fine-tuning (RFT).** Провайдеры дают дообучать модель через RL с grader: вы задаёте функцию проверки, а не готовые ответы. Это развитие RLVR из главы 2.
- **Distillation из reasoning моделей.** Малые модели учат на цепочках рассуждений больших (так сделаны малые версии DeepSeek-R1).
- **LoRA и QLoRA остаются главными техниками.** Советы главы про память и PEFT актуальны.
- **Примеры моделей в главе устарели.** BloombergGPT, GPT-4-0314, Llama 2, Claude 3.5 Sonnet и Llama 3 уже не передовые. Вывод остаётся верным: сильная универсальная модель часто обгоняет узкую, а новые базовые модели выходят быстрее, чем вы дообучаете свою.

## Ключевые термины

| Термин | Значение |
|---|---|
| `finetuning` | Дообучение модели на своих данных: меняются веса |
| `transfer learning` | Перенос знания с одной задачи на другую |
| `SFT` | Supervised finetuning на парах (инструкция, ответ) |
| `distillation` | Малая модель учится на ответах большой |
| `catastrophic forgetting` | Модель забывает старую задачу, когда учится новой |
| `trainable` / `frozen` | Параметр, который обновляется / остаётся прежним |
| `gradient`, `optimizer states` | Вклад параметра в loss / значения, которые optimizer хранит на параметр (0 у SGD, 2 у Adam) |
| `activations` | Промежуточные значения прямого прохода. Могут занять больше памяти, чем веса |
| `FP16`, `BF16` | 16 бит. У BF16 шире диапазон, у FP16 выше точность |
| `quantization`, `PTQ`, `QAT` | Хранение в меньшем числе бит: после обучения / с имитацией при обучении |
| `PEFT` | Parameter-efficient finetuning: мало trainable параметров, качество близко к полному |
| `LoRA`, `rank` (`r`) | Правка `W` как `A × B`: `W' = W + (α/r) · A × B`. Чаще всего `r` от 4 до 64 |
| `multi-LoRA serving` | Одна базовая модель и много адаптеров |
| `QLoRA` | LoRA с весами в 4 битах (`NF4`) и paged optimizers |
| `task vector` | Дообученная модель минус базовая. Векторы можно складывать и вычитать |
| `SLERP`, `TIES`, `DARE` | Слияние по сфере / методы, которые убирают лишние изменения перед слиянием |
| `learning rate`, `batch size`, `epoch` | Размер шага, число примеров на шаг, один проход по данным |
| `overfitting` | Train loss падает, validation loss растёт |

## Что это значит на практике

- **Начните с оценки, не с обучения.** Нужен eval-набор до finetuning. Без него не видно, стало ли лучше.
- **Данные для finetuning — ваша работа.** Пары (запрос, ответ) берут из логов, тикетов, SQL-запросов. Их нужно чистить, дедуплицировать и версионировать, как обычный data pipeline ([глава 8](/book-summaries/ai/ai-engineering/08-dataset-engineering/)).
- **Не отправляйте приватные данные наружу без проверки.** Finetuning API провайдера получает ваши данные. Проверьте политику, маскируйте PII.
- **Для знаний делайте RAG, для формата finetuning.** Документация, каталог данных и описания dbt-моделей — это факты, их место в индексе. SQL в диалекте вашего хранилища или JSON по строгой схеме — это форма. Сначала проверьте structured output и хороший prompt.
- **Считайте стоимость целиком.** GPU-часы, разметка, хостинг, мониторинг и повторное обучение, когда выйдет новая базовая модель. Память прикидывайте по формулам до заказа железа.
- **Версионируйте артефакты и ищите регрессии.** Датасет, базовая модель, адаптер, гиперпараметры, метрики. После finetuning прогоните общий eval: соседние задачи могли ухудшиться.
- **Начните с LoRA и сильной базовой модели.** Сравните с полным finetuning, если данных тысячи. Подбирайте `r` и отношение `α : r`.
- **Проверяйте формат весов, как типы колонок.** Загружайте модель в формате, для которого её выпустили (BF16 или FP16), и проверяйте `dtype` в пайплайне. Иначе качество упадёт без явной ошибки.
- **Следите за train и validation loss и сохраняйте checkpoints.** Проверьте путь для checkpoints до длинного запуска, как промежуточные снимки в долгом ETL.
- **Храните базу и адаптеры отдельно.** Версионируйте пару (база, адаптер) и датасет. Для многих клиентов берите multi-LoRA serving. Не усредняйте `A` и `B` по отдельности.
- **Для удешевления используйте distillation.** Большая модель генерирует или размечает данные, на них дообучают маленькую. Так падают latency и стоимость inference.
- **Проверяйте лицензии.** Лицензия базовой модели и чужого адаптера с Hugging Face должна подходить для вашего использования.

**1. Память для 7B.** Формулы главы в десяти строках.

```python
N = 7e9                          # параметров в модели
gb = lambda x: x / 1e9

weights = N * 2                  # 16 бит = 2 байта на значение
print(f"inference, 16 бит: {gb(weights * 1.2):.1f} ГБ  (N x M x 1,2)")

grad = N * 2                     # одно значение gradient на параметр
adam = N * 2 * 2                 # Adam: два состояния на параметр
print(f"полный finetuning, Adam: {gb(weights + grad + adam):.0f} ГБ")

r, layers, d = 8, 32, 4096       # LoRA, ранг 8, четыре матрицы attention
lora = layers * 4 * (d * r * 2)  # параметры A и B
lora_gb = gb(lora * 2 * 4)       # веса, gradient и два состояния Adam
print(f"LoRA: {lora / 1e6:.1f} млн trainable, всего {gb(weights) + lora_gb:.1f} ГБ")
print(f"QLoRA: веса в 4 битах, всего {gb(N * 0.5) + lora_gb:.1f} ГБ")
```

```text
inference, 16 бит: 16.8 ГБ  (N x M x 1,2)
полный finetuning, Adam: 56 ГБ
LoRA: 8.4 млн trainable, всего 14.1 ГБ
QLoRA: веса в 4 битах, всего 3.6 ГБ
```

Полный finetuning с Adam не помещается в GPU на 24 ГБ. LoRA и QLoRA помещаются. Это без activations.

**2. Округление: FP16 и BF16.** Ловушка из истории с Llama 2.

```python
import struct

def fp16(x):
    try:
        return struct.unpack("e", struct.pack("e", x))[0]
    except OverflowError:
        return float("inf")

def bf16(x):  # FP32 без 16 младших бит, с округлением до ближайшего
    b = struct.unpack("I", struct.pack("f", x))[0]
    b = (b + 0x7FFF + ((b >> 16) & 1)) & 0xFFFF0000
    return struct.unpack("f", struct.pack("I", b))[0]

for x in [3141.59, 314159.0]:
    print(f"{x:>9}: FP16 {fp16(x)}, BF16 {bf16(x)}")
```

```text
  3141.59: FP16 3142.0, BF16 3136.0
 314159.0: FP16 inf, BF16 313344.0
```

FP16 точнее на обычных числах, но выше 65 504 даёт `inf`. BF16 грубее, зато диапазон широкий.

**3. Размер LoRA и multi-LoRA.**

```python
n = m = 4096                     # одна матрица весов W
r = 8                            # ранг LoRA
full = n * m
lora = n * r + r * m             # A (n x r) и B (r x m)
print(f"W: {full:,}  A+B: {lora:,}  в {full // lora} раз меньше")

clients = 100
merged = full * clients          # 100 слитых матриц W'
multi = full + lora * clients    # одна W и 100 адаптеров
print(f"100 слитых W': {merged:,}")
print(f"W + 100 адаптеров: {multi:,}  ({round(merged / multi)}x меньше)")
```

```text
W: 16,777,216  A+B: 65,536  в 256 раз меньше
100 слитых W': 1,677,721,600
W + 100 адаптеров: 23,330,816  (72x меньше)
```
