Consumer group — это несколько consumers, которые совместно читают один или несколько topics как одно логическое приложение.

Kafka распределяет partitions между участниками группы. Одна partition в конкретный момент назначается только одному consumer внутри этой группы. Например, если topic имеет четыре partitions, а в группе два consumers, каждый обычно получит по две partitions.

Если добавить consumers, обработку можно распараллелить только до количества partitions. При четырёх partitions пятый consumer останется без назначения. Если один consumer упадёт, его partitions перейдут другим участникам.

Разные consumer groups читают один topic независимо и имеют собственные offsets. Поэтому один поток событий могут полностью получить, например, сервис аналитики и сервис уведомлений, но внутри каждого сервиса нагрузка будет поделена между его экземплярами.

![Четыре партиции orders читают три группы. В de-loader у каждого из двух consumers по две партиции, в backend один читает все четыре, в notify пятый простаивает.](/assets/interview/kafka-consumer-groups.png)

Параллелизм даёт не «приложение» само по себе, а **количество экземпляров consumer с одним и тем же `group.id`**: несколько процессов, подов в Kubernetes или потоков, у каждого свой `KafkaConsumer`. Один consumer тоже может держать все 4 партиции (как группа `backend` на схеме), но тогда он обрабатывает их в одном poll-цикле последовательно, и ускорения нет. Чтобы ускориться, запускаешь 2–4 экземпляра с одинаковым `group.id`, и Kafka сама раздаст им партиции.

Потолок параллелизма равен числу партиций. При 4 партициях пятый consumer в классической группе простаивает (группа `notify` на схеме). Поэтому число партиций закладывают с запасом под будущий рост consumers.
