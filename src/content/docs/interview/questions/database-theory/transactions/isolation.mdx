**I в ACID — изоляция.** Пожалуй, это самое сложное свойство для первого знакомства: две транзакции могут одновременно работать с одной таблицей и в один момент видеть разные версии одной строки. Чтобы предсказать результат, понадобятся три вещи: уровень изоляции, момент получения снимка и порядок конфликтующих записей.

## Что гарантирует каждый уровень

| Уровень SQL | Как работает в PostgreSQL |
| --- | --- |
| **Read Uncommitted** | PostgreSQL выполняет его как Read Committed. Другой сеанс не увидит незафиксированную запись. |
| **Read Committed** | Уровень по умолчанию. Обычный `SELECT` получает снимок на начало команды. Между двумя чтениями одна и та же строка может измениться, а в выборке могут появиться новые строки. |
| **Repeatable Read** | Первый запрос или команда изменения фиксирует снимок для всей транзакции. Повторное чтение видит прежние значения и тот же набор строк при неизменном условии и отсутствии собственных изменений. В PostgreSQL на этом уровне также исключены фантомные чтения. Возможны аномалии сериализации. |
| **Serializable** | Для успешно завершившихся транзакций должен существовать последовательный порядок с таким же результатом. PostgreSQL отслеживает опасные зависимости и может прервать транзакцию с `SQLSTATE 40001`. Приложению нужно повторить всю транзакцию, включая чтения и вычисления. |

Собственные изменения транзакция видит и до `COMMIT`. Фантомное чтение — это изменение состава строк при повторе запроса с тем же условием из-за фиксации другой транзакции.

## Кто первым обновит строку

На складе 5 единиц. Сеанс B первым выполнил `BEGIN` и пока считает заказ. Затем A открыл транзакцию и первым дошёл до строки товара A. Оба сеанса используют `Read Committed`.

| Момент | Сеанс A | Сеанс B |
| --- | --- | --- |
| 1 | | `BEGIN` |
| 2 | `BEGIN`, списывает 4 и удерживает строку | |
| 3 | | Пытается списать 3 с условием `qty >= 3`. Ждёт A. |
| 4 | `COMMIT`. Остаток теперь 1. | Продолжает работу и перепроверяет условие на новой версии. |
| 5 | | `UPDATE 0`: условие ложно, списания нет. |

**Стандарт SQL не обещает обслуживание по очереди поступления.** Слово «последовательный» у `Serializable` относится к допустимому итогу. Операции в реальном времени могут перемежаться. В примере порядок объясняется тем, кто первым дошёл до конфликтующей строки и удерживает её. Называть выбор транзакции случайным было бы неточно. При работе с разными строками обе записи часто могут идти параллельно. [Как пройти этот сценарий по схеме](/interview/questions/database-theory/transactions/locks/)

<details>
<summary>Как при Repeatable Read может нарушиться правило, если снимок стабилен?</summary>

Допустим, на смене двое дежурных и хотя бы один обязан остаться. Два сеанса видят обоих по своим снимкам и каждый снимает с дежурства себя. Они изменяют разные строки, поэтому при Repeatable Read оба могут зафиксироваться. Это перекос записи (*write skew*). Если все участники проверяют это правило в Serializable, PostgreSQL не позволит обеим таким транзакциям успешно завершиться с нулём дежурных.

</details>
