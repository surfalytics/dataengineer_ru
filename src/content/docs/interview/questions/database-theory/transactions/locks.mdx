**Снимок отвечает за видимость, блокировка — за конфликт действий.** Пока один сеанс удерживает изменяемую строку, второй может читать её ранее зафиксированную версию обычным `SELECT`. Попытка изменить ту же строку может ждать. На схеме оба сеанса работают в `Read Committed`.

## Когда достаточно блокировки строки

Для списания четырёх единиц проверку и изменение удобно объединить в одну команду. PostgreSQL сам возьмёт необходимую блокировку строки:

```sql
UPDATE stock
SET qty = qty - 4
WHERE sku = 'A' AND qty >= 4
RETURNING qty;
```

Если товаров достаточно, команда вернёт новый остаток. Пустой результат означает, что строка с таким ключом и достаточным остатком не найдена. В примере второй сеанс запрашивает **три** единицы: в его команде обе четвёрки меняются на тройки. Если первый сеанс уже обновляет эту строку, второй ждёт. После `COMMIT` первого PostgreSQL перепроверяет `qty >= 3` на актуальной версии. После его `ROLLBACK` второй сеанс сможет продолжить с прежним остатком.

Когда между чтением конкретной записи и записью нужна дополнительная логика, можно выполнить `SELECT … FOR UPDATE`, принять решение и обновить её **в той же транзакции**. Блокировка удерживается до её завершения. Если строк несколько, одинаковый порядок захвата в разных сеансах снижает риск взаимной блокировки (*deadlock*).

## Когда оправдана блокировка всей таблицы

Допустим, надо пересчитать долю каждого товара в общем остатке склада. На время чтения общего остатка и записи долей требуется остановить **все изменения** в `stock`, включая вставку новых товаров. В одной короткой транзакции можно явно взять табличную блокировку **до чтения**:

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;
LOCK TABLE stock IN SHARE ROW EXCLUSIVE MODE;

UPDATE stock
SET share = qty::numeric / NULLIF((SELECT SUM(qty) FROM stock), 0);

COMMIT;
```

Если другая транзакция уже пишет в `stock`, команда `LOCK TABLE` подождёт её завершения. После получения блокировки конкурирующие `INSERT`, `UPDATE` и `DELETE` будут ждать, даже если работают с другим товаром. Обычный `SELECT` остаётся доступным. `COMMIT` освобождает таблицу. Цена такой гарантии — остановка всех остальных записей в таблицу на время пересчёта. Для списания одного товара достаточно предыдущего примера.

<details>
<summary>Во всех ли уровнях второй UPDATE просто продолжится после ожидания?</summary>

Повторная проверка условия из первого примера характерна для Read Committed. В Repeatable Read и Serializable попытка изменить строку, которую конкурент успел изменить и зафиксировать после получения снимка, может завершиться ошибкой `40001`. Обработчик должен повторить транзакцию целиком. При взаимной блокировке PostgreSQL прерывает одного из участников с кодом `40P01`.

</details>
