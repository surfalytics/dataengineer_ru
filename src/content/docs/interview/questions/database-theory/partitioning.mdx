**Партиционирование** делит одну логическую таблицу на несколько физических таблиц — партиций. Приложение читает и записывает данные через общее имя. При вставке PostgreSQL по **ключу партиционирования** выбирает, куда положить строку. При чтении условие по ключу позволяет исключить целые партиции из плана.

## Зачем делить таблицу?

В таблице заказов лежат данные за несколько лет, а ежемесячный отчёт читает только последний месяц. Если границы партиций совпадают с месяцами, PostgreSQL может сразу пропустить всю историю. Второе применение — хранение данных за заданный срок. Старый месяц можно целиком отсоединить от таблицы или удалить отдельной партицией. Это избавляет от построчного удаления миллионов заказов.

## Как строка попадает в партицию?

```text
orders_by_date · ключ created_at
├─ orders_jan   [1 января, 1 февраля)
├─ orders_feb   [1 февраля, 1 марта)
└─ orders_mar   [1 марта, 1 апреля)
```

Нижняя граница диапазона включена, верхняя исключена. Поэтому заказ от 1 февраля попадёт в `orders_feb`. Для дат за пределами этих диапазонов можно создать партицию `DEFAULT`. Без неё вставка такой строки завершится ошибкой.

<details>
<summary>Создать таблицу с тремя месячными партициями</summary>

```sql
CREATE TABLE orders_by_date (
    shop_id integer NOT NULL,
    created_at date NOT NULL,
    amount integer NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_jan PARTITION OF orders_by_date
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE orders_feb PARTITION OF orders_by_date
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
CREATE TABLE orders_mar PARTITION OF orders_by_date
    FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');
```

</details>

## Как проверить, что лишние партиции пропущены?

```sql
EXPLAIN
SELECT sum(amount) FROM orders_by_date
WHERE shop_id = 42
  AND created_at >= DATE '2026-02-01'
  AND created_at <  DATE '2026-03-01';
```

В плане этого запроса достаточно найти имя `orders_feb`. Январь и март не нужны для ответа, поэтому планировщик исключает их по границам дат. Это **partition pruning**. Для запроса с параметрами исключение возможно и при выполнении. Индекс для отсечения партиций не требуется. После выбора февраля индекс уже может ускорить поиск заказов конкретного магазина **внутри** партиции.

## Как выбрать ключ и способ разбиения?

| Способ | Когда подходит |
| --- | --- |
| `RANGE` — по диапазонам | Отчёты за периоды и удаление старых данных. Пример — месяц заказа. |
| `LIST` — по перечням значений | Данные естественно делятся на известные группы, например по региону обслуживания. |
| `HASH` — по хешу ключа | Нужно распределить множество значений, например идентификаторы клиентов, по заданному числу партиций. |

Начните с условий в частых запросах и правил хранения. Если отчёты фильтруют **только по магазину**, месячное разбиение само по себе оставит в плане все месяцы. У каждой партиции собственные индексы, а избыток мелких партиций увеличивает затраты на планирование. Для `PRIMARY KEY` или `UNIQUE` на родительской таблице PostgreSQL требует включить все столбцы ключа партиционирования.
