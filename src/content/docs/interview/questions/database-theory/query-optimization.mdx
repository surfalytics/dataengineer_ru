## 1. Прочитайте сам запрос

Что означает одна строка результата и сколько строк должно получиться? Проверьте каждый подзапрос и каждый `JOIN`. Например, если к заказу присоединить **все** его платежи, заказ с тремя платежами появится трижды. Если по задаче достаточно проверить наличие успешной оплаты, это условие можно выразить через `EXISTS`. Заодно проверьте пропущенные условия соединения, повторные вычисления и `DISTINCT`, который приходится накладывать на уже размноженные строки. Само количество подзапросов ещё ничего не говорит об их стоимости.

## 2. Найдите лишнюю работу в плане

Для медленного `SELECT` с обычными для приложения параметрами снимите `EXPLAIN (ANALYZE, BUFFERS)`. Зафиксируйте результат, время и обращения к буферам. [Как читать план запроса](/interview/questions/database-theory/query-plan/)

| Что видно в плане | Что проверить |
| --- | --- |
| Оценка `rows` сильно расходится с фактом при полном чтении узла | Найдите первый узел, где возникла ошибка оценки. После массовой загрузки или изменения распределения данных проверьте свежесть статистики. |
| `Nested Loop`, `Hash Join` или `Merge Join` | У вложенного цикла посмотрите число проходов `loops` на внутренней стороне. У хеш-соединения — число партий и временные записи. У слияния — потребовалась ли дорогая сортировка. Сравните объёмы входов с тем, что ожидал планировщик. |
| `Seq Scan` и много `Rows Removed by Filter` | Если таблица большая, а проходят единицы строк, проверьте условие и доступные индексы. Когда нужна большая часть таблицы, последовательное чтение часто дешевле. |
| В плане есть партиции за ненужные месяцы | Сопоставьте условие с ключом и границами партиций. Преобразование даты внутри фильтра может мешать отсечению. |

## 3. Разберитесь, что нужно обновить

PostgreSQL **сам поддерживает индексы при записи**. Новая строка получает индексные записи. При обновлении старая версия строки может ещё понадобиться читателям, а новая должна находиться по актуальному ключу. Когда изменение допускает HOT-обновление, PostgreSQL может обойтись без новых записей в обычных индексах. Ставшие ненужными версии и индексные записи впоследствии обрабатывает `VACUUM`. [Индексы](https://www.postgresql.org/docs/18/indexes-intro.html) · [HOT-обновления](https://www.postgresql.org/docs/18/storage-hot.html)

**Статистика планировщика** описывает распределение значений, например долю частых статусов. Её обновляет `ANALYZE`, обычно через autovacuum. После крупной загрузки можно выполнить `ANALYZE orders_by_date;` и снова сравнить оценки с фактом. Для партиционированной таблицы проверяйте и родителя. Изменения в дочерних партициях сами по себе не запускают его автоанализ. `REINDEX` физически перестраивает индекс и применяется по отдельной причине, например при повреждении или подтверждённом сильном разрастании. [ANALYZE](https://www.postgresql.org/docs/18/sql-analyze.html) · [REINDEX](https://www.postgresql.org/docs/18/sql-reindex.html)

## 4. Вернитесь к WHERE и проверьте изменение

Нужно посчитать сумму февральских заказов магазина 42. На стенде 90 000 строк за три месяца. Исходный фильтр вычисляет месяц для каждой даты.

```sql
SELECT sum(amount) FROM orders_by_date
WHERE shop_id = 42
  AND date_trunc('month', created_at::timestamp) = TIMESTAMP '2026-02-01';
```

Выразим тот же период через границы. PostgreSQL сможет сравнить их непосредственно с ключом партиционирования.

```sql
SELECT sum(amount) FROM orders_by_date
WHERE shop_id = 42
  AND created_at >= DATE '2026-02-01'
  AND created_at <  DATE '2026-03-01';
```

В феврале остаётся 28 000 заказов, из которых магазину 42 принадлежат 28. Прежде чем создавать индекс, посмотрим, какие индексы уже есть у февральской партиции и в каком порядке в них стоят столбцы.

```sql
SELECT indexname, indexdef FROM pg_indexes
WHERE schemaname = current_schema() AND tablename = 'orders_feb';
```

В нашем примере индексов пока нет. Проверим составной B-tree на родительской таблице. PostgreSQL создаст соответствующий индекс на каждой партиции. Первым поставим магазин (равенство), вторым — дату (диапазон).

```sql
CREATE INDEX orders_shop_date_idx
    ON orders_by_date (shop_id, created_at);
```

| Изменение | Что показал план на PostgreSQL 18.7 | Обращения к буферам на корне плана |
| --- | --- | ---: |
| Исходный запрос | Три `Seq Scan` проверили 90 000 строк | 488 hit |
| Только диапазон дат | Один `Seq Scan` проверил 28 000 строк февраля | 152 hit |
| Диапазон и индекс | `Bitmap Index Scan` нашёл 28 записей, `Bitmap Heap Scan` прочитал строки | 28 hit + 2 read |

**Во всех трёх случаях сумма равна 2800.** Сравнивайте результат и объём работы после каждого изменения. Здесь отсечение убрало два месяца, а индекс сократил чтение внутри оставшегося. Счётчики буферов приведены для одного запуска и зависят от состояния кеша.

<details>
<summary>Как повторить измерение?</summary>

Создайте три таблицы-партиции из [примера с заказами](/interview/questions/database-theory/partitioning/), затем загрузите по одному заказу в день для каждого магазина.

```sql
INSERT INTO orders_by_date (shop_id, created_at, amount)
SELECT shop_id, DATE '2026-01-01' + day_no, 100
FROM generate_series(1, 1000) AS shops(shop_id)
CROSS JOIN generate_series(0, 89) AS days(day_no);

ANALYZE orders_by_date;
```

Выполните оба варианта `SELECT` с префиксом `EXPLAIN (ANALYZE, BUFFERS)`. Затем создайте индекс и повторите второй запрос.

</details>

**Если таблица ещё не партиционирована**, сначала проверьте, достаточно ли подходящего индекса. Разбиение имеет смысл, когда крупные запросы регулярно ограничены одним диапазоном или приходится удалять целые периоды. Для поиска нескольких строк в небольшой таблице затраты на миграцию и обслуживание партиций могут превысить выигрыш.
