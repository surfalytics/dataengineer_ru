**VACUUM** очищает место, занятое версиями строк, которые уже никому не видны. Это нужно из-за MVCC. При `UPDATE` PostgreSQL создаёт новую версию строки, при `DELETE` отмечает существующую как удалённую. Освободить их место можно, когда эти версии перестанут быть нужны читателям. [Как работает снимок MVCC](/interview/questions/database-theory/transactions/mvcc/)

## Почему нельзя убрать старую строку сразу?

1. Отчёт начал читать склад и получил снимок, в котором остаток равен **5**.
2. Другая транзакция изменила остаток на **1** и выполнила `COMMIT`. Новые читатели видят **1**, но для отчёта всё ещё нужна версия **5**.
3. Отчёт отпустил снимок. Когда старую версию больше не удерживает ни один снимок или другой механизм PostgreSQL, `VACUUM` сможет освободить её место для повторного использования.

Поэтому долго удерживаемый снимок может мешать очистке даже при регулярно работающем autovacuum. В таблицах с частыми изменениями лишние версии со временем увеличивают число страниц, которые приходится читать.

## Что делает обычный VACUUM?

- **Освобождает место** в таблице для новых версий и по мере необходимости очищает устаревшие записи в индексах. Размер файла на диске обычно сохраняется. Полностью свободные страницы в конце файла иногда удаётся вернуть операционной системе.
- **Ведёт карту видимости.** Если все строки страницы видны всем транзакциям, PostgreSQL может отметить страницу как `all-visible`. При `Index Only Scan` такая отметка позволяет пропустить проверку видимости в самой таблице.
- **Замораживает старые версии.** PostgreSQL помечает достаточно старые идентификаторы создавших их транзакций как «замороженные». Это сохраняет корректную видимость строк при циклическом использовании пространства идентификаторов транзакций.

[Регулярная очистка в PostgreSQL](https://www.postgresql.org/docs/18/routine-vacuuming.html)

## Какую команду выбрать?

| Команда | Что изменится |
| --- | --- |
| `VACUUM orders_feb;` | Освободит место для повторного использования. Обычно допускает параллельные чтения и изменения. |
| `ANALYZE orders_feb;` | Соберёт статистику значений и числа строк для планировщика. |
| `VACUUM (ANALYZE) orders_feb;` | Выполнит очистку, затем обновит статистику. |
| `VACUUM FULL orders_feb;` | Перепишет таблицу плотнее и перестроит её индексы. Потребует дополнительного дискового места и исключительной блокировки, которая остановит чтение и запись этой таблицы на время операции. |

## Как понять, успевает ли autovacuum?

Фоновые процессы автоматически запускают очистку и сбор статистики по мере накопления изменений. Это отдельные операции со своими условиями запуска. Для таблицы с партициями полезно смотреть показатели конкретной партиции, где идут записи.

```sql
SELECT relname, n_live_tup, n_dead_tup,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
WHERE relid = 'orders_feb'::regclass;
```

`n_live_tup` и `n_dead_tup` — **оценки** числа живых и устаревших версий. Если число устаревших версий стабильно растёт, проверьте время последних запусков и наличие долгих транзакций со старым снимком. Одно большое значение сразу после массового удаления ещё не говорит, что очистка сломана.
