**Lazy evaluation** означает, что Spark откладывает обработку данных, пока приложению не понадобится результат. В API для работы с RDD и DataFrame есть два основных вида операций:

- **Transformation** описывает новый набор данных. Например, `filter()` оставляет подходящие строки, а `select()` выбирает колонки. Spark запоминает эти операции и их зависимости.
- **Action** запускает вычисление. Ты вызываешь метод, которому уже нужны данные, и Spark выполняет ту часть плана, которая нужна для ответа. Например, `orders.count()` запускает подсчёт заказов и возвращает одно число.

```python
paid = orders.filter("status = 'paid'").select("shop_id", "amount")
totals = paid.groupBy("shop_id").sum("amount")
totals.write.parquet(output_path)
```

Первые две строки описывают расчёт выручки по магазинам. **Вычисление запускает вызов `parquet(output_path)` в третьей строке.** Чтобы записать результат, Spark отбирает оплаченные заказы, суммирует выручку по магазинам и записывает итоги в файлы.

### Какие вызовы запускают вычисление?

Вместо записи в Parquet к тому же DataFrame `totals` можно применить любое из этих действий.

| Вызов | Что произойдёт |
| --- | --- |
| `totals.show(5)` | Spark получит строки для просмотра и напечатает в консоли до пяти строк с выручкой магазинов. |
| `totals.count()` | Посчитает строки и вернёт на driver одно число. В этом примере оно равно количеству магазинов, у которых были оплаченные заказы. |
| `totals.collect()` | ⚠ **Риск для драйвера.** Соберёт все строки результата в памяти драйвера в виде Python-списка объектов `Row`. |
| `totals.toPandas()` | ⚠ **Риск для драйвера.** Загрузит все строки результата в память драйвера и преобразует их в pandas DataFrame. Само преобразование тоже может потребовать дополнительной памяти. |
| `totals.write.saveAsTable("sales_by_shop")` | Запишет выручку в таблицу `sales_by_shop`. Затем к ней можно обратиться по имени из SQL. |
| `totals.foreachPartition(send_rows)` | Вызовет твою функцию `send_rows` на executors для каждой партиции. Например, функция может отправить строки в базу данных пачками. |

**Почему драйвер может упасть?** Пока данные распределены по executors, каждый хранит лишь свою часть. При `collect()` и `toPandas()` весь результат должен поместиться в памяти одного драйвера. Если памяти не хватит, драйвер может завершиться с ошибкой *out of memory* (OOM), а вместе с ним остановится Spark-приложение.

**Почему один `count()` запускает вычисление, а другой ждёт?** Вызов `paid.count()` сразу возвращает число оплаченных заказов. Вызов `paid.groupBy("shop_id").count()` создаёт DataFrame с планом подсчёта заказов по магазинам. Если вызвать у этого DataFrame `show()`, Spark выполнит подсчёт и покажет результат. [GroupedData.count в документации PySpark](https://spark.apache.org/docs/4.1.1/api/python/reference/pyspark.sql/api/pyspark.sql.GroupedData.count.html)

### Узкие и широкие зависимости

**Узкая зависимость (narrow)** означает, что каждая входная партиция нужна максимум одной выходной. Несколько таких преобразований Spark может выполнить в одной стадии. Например, задача отбирает оплаченные заказы и сразу оставляет у них нужные колонки.

| Пример без shuffle | Что происходит с данными |
| --- | --- |
| `orders.filter("status = 'paid'")` | Каждая задача отбрасывает неоплаченные заказы в своей партиции. |
| `orders.select("shop_id", "amount")` | У каждой строки остаются две колонки. Строка остаётся в своей партиции. |
| `rdd.map(lambda x: x * 2)` | Каждое число удваивается прямо в той партиции, где оно лежит. |
| `lines.flatMap(lambda line: line.split())` | Из одной строки RDD может получиться несколько слов. Все они остаются в партиции исходной строки. |
| `orders.sortWithinPartitions("amount")` | Каждая партиция сортирует свои заказы по сумме. В соседней партиции могут лежать как меньшие, так и большие суммы. |
| `orders.coalesce(4)` при 12 входных партициях | Spark объединяет входные партиции целиком в четыре выходные. Строки одной входной партиции остаются вместе. |

**Широкая зависимость (wide)** возникает, когда записи из одной входной партиции нужно распределить по разным выходным. Для этого Spark выполняет **shuffle**. Ниже примеры для заказов, которые изначально разложены по партициям без учёта ключа операции.

| Пример с shuffle | Зачем перераспределять данные |
| --- | --- |
| `orders.groupBy("shop_id").sum("amount")` | Покупки одного магазина есть в разных партициях. Для итоговой суммы задача собирает частичные суммы этого магазина. |
| `orders.dropDuplicates(["order_id"])` | Копии одного заказа могут лежать в разных партициях. Spark собирает данные по `order_id`, чтобы оставить одну запись на заказ. |
| `orders.join(payments, "order_id")` | При соединении двух больших таблиц по схеме sort-merge join строки заказов и оплат перераспределяются по `order_id`, чтобы совпадающие ключи попали к одной задаче. |
| `orders.orderBy("amount")` | Для общей сортировки Spark распределяет суммы по диапазонам между партициями и сортирует записи внутри каждого диапазона. |
| `orders.repartition(8, "shop_id")` | Spark распределяет строки по хешу `shop_id` между восемью партициями. Все заказы одного магазина попадут в одну из них. |

**Как проверить конкретный запрос?** Вызови `df.explain()` и найди `Exchange` с `hashpartitioning` или `rangepartitioning`. Если нужное разбиение уже есть и Spark о нём знает, дополнительный shuffle может не понадобиться. При broadcast join Spark рассылает маленькую таблицу на executors, и большая таблица сохраняет своё разбиение. [Физический план в Spark UI](https://spark.apache.org/docs/4.1.1/web-ui.html#sql-tab)
