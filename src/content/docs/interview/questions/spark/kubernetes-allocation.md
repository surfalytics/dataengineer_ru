Представь один запуск Spark на год данных. После каждого месяца запись заканчивается, число executors остаётся прежним, а потребление памяти одного и того же контейнера постепенно растёт. В какой-то момент Kubernetes показывает `OOMKilled`, хотя занятая Java heap после сборки мусора возвращалась примерно к прежнему уровню. Одна из возможных причин — то, как нативный аллокатор **glibc malloc** переиспользует память между итерациями. В лимит памяти контейнера входят и страницы вне Java heap. Когда суммарный расход достигает лимита и ядру не удаётся освободить достаточно памяти, оно может завершить процесс.

## Что такое арена malloc?

Когда нескольким потокам одновременно нужна память, glibc может обслуживать их через разные **арены**. Это уменьшает конкуренцию за одну блокировку. Когда библиотека освобождает временный буфер, место снова доступно аллокатору. Однако на той же странице памяти могут оставаться занятые блоки. В результате часть страниц остаётся у процесса, и его резидентная память (RSS) после месяца может снизиться лишь частично. При следующем пике новые выделения могут увеличить её ещё сильнее.

По умолчанию предел числа арен glibc зависит от числа процессоров, которое обнаружила библиотека. На 64-битных системах он обычно составляет до восьми арен на обнаруженное ядро. Это **верхний предел**: арены создаются по мере необходимости. [Настройки аллокатора glibc](https://sourceware.org/glibc/manual/latest/html_node/Memory-Allocation-Tunables.html)

## Как здесь связаны CPU и Kubernetes?

Namespace Kubernetes сам по себе не определяет, сколько CPU видит процесс. У контейнера есть CPU request для размещения, а CPU limit обычно задаёт квоту процессорного времени через cgroup. Отдельно может быть ограничен набор доступных CPU (cpuset). Поэтому процесс может видеть много логических CPU узла даже при небольшом бюджете процессорного времени. У glibc и JVM свои механизмы определения этого числа. [Ресурсы контейнеров Kubernetes](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/)

Для приложения с небольшим бюджетом CPU можно задать следующие параметры в `spark-defaults.conf` до запуска в режиме `cluster`.

```properties
spark.executorEnv.MALLOC_ARENA_MAX                 4
spark.kubernetes.driverEnv.MALLOC_ARENA_MAX        4
spark.executorEnv.JAVA_TOOL_OPTIONS                -XX:ActiveProcessorCount=2
spark.kubernetes.driverEnv.JAVA_TOOL_OPTIONS       -XX:ActiveProcessorCount=2
```

- **`MALLOC_ARENA_MAX=4`** ограничивает число арен glibc четырьмя **на процесс**. В образе с glibc значения 2 и 4 можно сравнить на одинаковой загрузке. Меньшее число арен иногда снижает RSS ценой большей конкуренции потоков. У процесса с другим аллокатором эта настройка может не дать эффекта.
- **`-XX:ActiveProcessorCount=2`** задаёт JVM два активных процессора для расчёта размеров внутренних пулов, например потоков GC. Проверить видимое JVM число CPU можно через `Runtime.getRuntime().availableProcessors()`. Если JVM уже видит два процессора, этот флаг не уменьшит её пулы дополнительно. Квоту контейнера, число слотов Spark и лимит арен glibc задают отдельно. Если `JAVA_TOOL_OPTIONS` уже содержит другие нужные флаги, добавь опцию к ним. [Параметры JVM](https://docs.oracle.com/en/java/javase/17/docs/specs/man/java.html)

## Как проверить гипотезу?

1. Для одного и того же executor сопоставь после каждого месяца **занятую heap после GC**, RSS процессов Java и Python и расход памяти контейнера. В cgroup v2 `memory.current` показывает общий расход, а `memory.stat` помогает отделить анонимную память (`anon`) от файлового кеша (`file`). [Метрики cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
2. Если heap возвращается к исходному уровню, а RSS процесса и `anon` растут, проверь нативные буферы, Python workers и удержание страниц аллокатором. По одному графику RSS отличить фрагментацию от утечки нельзя.
3. Повтори загрузку на тех же данных и с теми же ресурсами, меняя по одному параметру. Сравни пик памяти, уровень после каждого месяца и время обработки. Так видно, помогло ли ограничение арен и сколько это стоило по времени.
