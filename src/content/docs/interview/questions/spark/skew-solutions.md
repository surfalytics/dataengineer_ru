Сначала подтверди, что перекос появился после shuffle, и посчитай частоты ключей. Одно значение вроде `customer_id = 0` может объяснить почти весь хвост стадии.

| Ситуация | Что попробовать |
| --- | --- |
| Одна сторона JOIN маленькая | Broadcast JOIN позволяет большой таблице обрабатывать исходные партиции без shuffle по горячему ключу. |
| Перекошен поддерживаемый shuffle JOIN | AQE может разделить чтение большой партиции между задачами, при необходимости повторив соответствующие блоки второй стороны. Посмотри конечный план и максимальное время задачи. |
| Обе стороны большие, доминируют несколько ключей | Обработай горячие ключи отдельно или примени salting. Редкие ключи можно соединять обычным способом. |
| Перекос при `GROUP BY` | Для суммы или количества посчитай частичные агрегаты по `(ключ, соль)`, затем сложи их по исходному ключу. Для среднего объедини суммы и количества. |

**Как работает salting для внутреннего JOIN.** Для строк горячего ключа большой стороны вычисли одно из, например, восьми значений соли по хешу ID события. Каждую строку **этого ключа** на второй стороне скопируй для всех восьми значений. Соедини по ключу и соли. Так каждая исходная пара встретится ровно один раз. Если независимо раздать случайную соль с обеих сторон, часть совпадений потеряется.

Простой `repartition(800, "customer_id")` оставит один и тот же ключ в одной партиции. После исправления сравни Max и Median по объёму чтения и длительности, а также число выходных строк на горячих ключах. [AQE и перекошенные соединения](https://spark.apache.org/docs/4.1.1/sql-performance-tuning.html#optimizing-skew-join)
