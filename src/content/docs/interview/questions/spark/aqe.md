**Adaptive Query Execution (AQE)** позволяет Spark SQL менять оставшуюся часть физического плана прямо во время выполнения. Первоначальный план строится по оценкам. После shuffle или подготовки данных для broadcast у драйвера появляются реальные размеры промежуточных результатов. По ним Spark решает, как выполнить следующую часть запроса.

| С чем борется AQE | Что меняется в плане |
| --- | --- |
| **Много мелких shuffle-партиций.** После фильтра данных осталось мало, а на чтение каждой партиции запланирована отдельная задача. | Spark может поручить одной задаче чтение нескольких соседних партиций. В плане появляется `AQEShuffleRead coalesced`. |
| **Лишняя сортировка при JOIN.** В начале обе стороны казались большими. После фильтра один из наборов оказался достаточно маленьким для broadcast. | Вместо запланированного `SortMergeJoin` Spark может выбрать `BroadcastHashJoin` и разослать маленький набор на executors. |
| **Перекос данных (skew).** При соединении одна shuffle-партиция оказалась намного больше остальных. Остальные задачи быстро заканчивают работу, а одна ещё долго читает данные. | Для поддерживаемого соединения Spark может разбить чтение тяжёлой партиции между несколькими задачами. При необходимости каждой задаче передаётся соответствующая часть второй стороны. |

Например, для выручки по двум магазинам Spark изначально запланировал восемь shuffle-партиций. Когда задачи записали частичные суммы, оказалось, что объём маленький. AQE объединил чтение, и следующей стадии понадобилась всего одна задача. Уже посчитанные суммы она взяла из готового shuffle.

В Apache Spark начиная с версии 3.2 AQE включён по умолчанию. Настройку текущей сессии можно проверить через `spark.conf.get("spark.sql.adaptive.enabled")`. [Adaptive Query Execution в документации Spark](https://spark.apache.org/docs/4.1.1/sql-performance-tuning.html#adaptive-query-execution)
