**Data skew, или перекос данных,** возникает, когда несколько партиций получают заметно больше работы, чем остальные. Типичный пример — JOIN по `customer_id`, где у половины заказов указан один технический клиент. При распределении по хешу все строки этого клиента попадают в одну shuffle-партицию.

Девяносто девять задач стадии могут уже завершиться, а сотая всё ещё читает данные, сортирует или пишет временные файлы на диск. Освободившиеся CPU простаивают. Добавление executors само по себе не делит эту конкретную задачу на части.

Сначала выясни, **где возник перекос**. Если задачи уже на чтении получили входные файлы разного размера, причина может быть в раскладке файлов. Если разброс появился после `Exchange` по ключу, проверь частые значения этого ключа в соответствующем входе. Долгая задача при одинаковом объёме данных бывает и из-за GC, медленного диска или сложной пользовательской функции.
