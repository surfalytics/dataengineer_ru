Допустим, к каждому заказу нужно добавить город магазина. В SQL пишем один `JOIN` по `shop_id`. В физическом плане одного и того же запроса Spark может выбрать разные способы найти совпадения.

| Стратегия | Когда Spark может её выбрать | Что происходит с данными |
| --- | --- | --- |
| [BroadcastHashJoin](#broadcasthashjoin) | Одну сторону целиком можно разослать на каждый executor. | Spark рассылает маленькую таблицу. Партиции большой стороны остаются на месте. |
| [SortMergeJoin](#sortmergejoin) | Обе стороны велики для broadcast, а ключи можно сортировать. Это обычный выбор Spark для такого соединения. | Spark собирает одинаковые ключи в соответствующих партициях, сортирует обе стороны внутри партиций и сопоставляет строки. |
| [ShuffledHashJoin](#shuffledhashjoin) | Рассылать всю таблицу дорого, но внутри каждой пары партиций одна сторона помещается в память задачи. | После shuffle каждая задача строит свою хеш-таблицу и по ней находит совпадения. |

Во всех трёх схемах один и тот же внутренний JOIN по равенству ключей. Буква обозначает заказ, число — `shop_id`. Заказы **B** и **D** сделаны в магазине **2**, поэтому в результате у обоих будет **Пермь**.

## BroadcastHashJoin

Представь миллиард заказов и справочник магазинов на 2 МиБ. Драйвер собирает справочник, строит хеш-таблицу с ключом `shop_id` и рассылает её на executors. Каждая задача читает свою партицию заказов. Встретила заказ **B** с ключом **2** — нашла в локальной копии **Пермь**. Перераспределять миллиард заказов для этого соединения не понадобилось.

<SparkJoinFlow strategy="broadcast" />

**Когда выберет Spark.** При автоматическом выборе планировщик смотрит на оценку размера стороны после фильтров и отбора колонок. По умолчанию порог `spark.sql.autoBroadcastJoinThreshold` равен **10 МиБ**. Для `INNER JOIN` можно рассылать любую подходящую сторону, для `LEFT JOIN` — правую. Для `FULL OUTER JOIN` эта стратегия недоступна. Подсказка `BROADCAST` позволяет предложить рассылку даже выше порога, но хеш-таблица всё равно должна поместиться в память драйвера и каждого участвующего executor. [Настройки и подсказки Spark SQL](https://spark.apache.org/docs/4.1.1/sql-performance-tuning.html#optimizing-the-join-strategy)

## SortMergeJoin

Теперь и заказов, и магазинов слишком много для рассылки. Spark распределяет обе стороны по `shop_id`, чтобы заказы магазина и запись самого магазина пришли в одну задачу. Каждая задача сортирует **свою** часть заказов и **свою** часть справочника по ключу. Затем проходит по двум отсортированным последовательностям. Если ключи разные, продвигается по стороне с меньшим ключом. Если совпали, выдаёт все пары строк с этим ключом.

<SparkJoinFlow strategy="merge" />

**Когда выберет Spark.** Для соединения по равенству с сортируемыми ключами Spark по умолчанию предпочитает SortMergeJoin, если подходящей стороны для broadcast нет. Цена — shuffle и локальная сортировка. Если предыдущие операции уже обеспечили нужное распределение или порядок, Spark может пропустить соответствующий `Exchange` или `Sort`. [Правила выбора физического JOIN](https://github.com/apache/spark/blob/v4.1.1/sql/core/src/main/scala/org/apache/spark/sql/execution/SparkStrategies.scala)

## ShuffledHashJoin

Начало такое же, как у SortMergeJoin. Обе стороны распределяются по ключу. Дальше каждая задача строит хеш-таблицу **только из своей партиции справочника**. Одна задача хранит магазины **1** и **3**, другая — только магазин **2**. Вторая задача один раз запоминает, что магазин **2** находится в Перми, и находит город по этому ключу для обоих заказов, **B** и **D**. Сортировать заказы или магазины ей не требуется.

<SparkJoinFlow strategy="shuffle-hash" />

**Когда выберет Spark.** В исходном плане без подсказок Spark рассматривает эту стратегию, когда предпочтение SortMergeJoin отключено (`spark.sql.join.preferSortMergeJoin=false`), одна сторона заметно меньше другой и по оценке из её партиций можно построить локальные хеш-таблицы. Отдельный путь — подсказка `SHUFFLE_HASH` или решение AQE по фактическим размерам партиций. Если одна партиция справочника оказалась слишком большой, строящей хеш-таблицу задаче может не хватить памяти. [Правила выбора стороны для хеш-таблицы](https://github.com/apache/spark/blob/v4.1.1/sql/catalyst/src/main/scala/org/apache/spark/sql/catalyst/optimizer/joins.scala)

У AQE есть отдельная настройка `spark.sql.adaptive.maxShuffledHashJoinLocalMapThreshold`. Если её значение не меньше целевого размера shuffle-партиции (`spark.sql.adaptive.advisoryPartitionSizeInBytes`) и все партиции стороны для хеш-таблицы укладываются в этот порог, AQE может предпочесть ShuffledHashJoin даже при включённом предпочтении SortMergeJoin. По умолчанию порог равен нулю, и это правило выключено. [Адаптивный выбор ShuffledHashJoin](https://spark.apache.org/docs/4.1.1/sql-performance-tuning.html#converting-sort-merge-join-to-shuffled-hash-join)

## Как проверить, что выбрал Spark

```sql
EXPLAIN FORMATTED
SELECT o.order_id, s.city
FROM orders o
JOIN shops s ON o.shop_id = s.shop_id
```

Чтобы воспроизвести все три варианта на этих маленьких таблицах, сразу после `SELECT` по очереди поставь подсказки `/*+ BROADCAST(s) */`, `/*+ MERGE(s) */` и `/*+ SHUFFLE_HASH(s) */`. Вот строки из трёх планов одного запроса в Spark 3.5.5. Номера узлов опущены.

```text
BroadcastHashJoin Inner BuildRight
SortMergeJoin Inner
ShuffledHashJoin Inner BuildRight
```

В DataFrame API ту же информацию показывает `df.explain("formatted")`. Для **BroadcastHashJoin** ищи `BroadcastExchange` у стороны, которую рассылают. Для **SortMergeJoin** характерны `Exchange` и `Sort` на входах. У **ShuffledHashJoin** в примере есть `Exchange` на обоих входах и пометка `BuildRight` — хеш-таблицу строят по правой стороне.

С включённым AQE начальный и конечный планы могут различаться. Например, после фильтрации справочник оказался достаточно маленьким для broadcast. Spark может заменить SortMergeJoin на BroadcastHashJoin. Если shuffle уже состоялся, его стоимость останется. Для проверки открой завершённый запрос во вкладке **SQL** в Spark UI и посмотри `Final Plan`. [Адаптивный выбор JOIN в Spark](https://spark.apache.org/docs/4.1.1/sql-performance-tuning.html#adaptive-query-execution)
