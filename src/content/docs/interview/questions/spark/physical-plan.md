**Физический план строит планировщик Spark SQL (`SparkPlanner`) на драйвере.** Он берёт оптимизированный логический план и подбирает для него конкретные операторы. При подготовке к выполнению Spark добавляет обмен данными или сортировку там, где оператору нужны определённые партиции или порядок строк.

Посмотрим на запрос о выручке по магазинам. Логическая операция здесь одна для всего подсчёта — `GROUP BY shop_id` с `SUM(amount)`. В физическом плане она превращается в **две агрегации и обмен между ними**. Ниже сокращённый вывод `totals.explain("formatted")` до запуска запроса.

```text
HashAggregate
+- Exchange
   +- HashAggregate
      +- Project
         +- Filter
            +- Scan parquet
```

Читай снизу вверх, от источника к результату.

1. **Чтение и фильтрация.** `Scan parquet` читает нужные колонки, `Filter` оставляет оплаченные заказы, а `Project` передаёт дальше только номер магазина и сумму.
2. **Нижний HashAggregate.** Каждая задача считает выручку по магазинам в своей партиции. Если заказы одного магазина попали в две партиции, получится две частичные суммы.
3. **Exchange.** Spark распределяет частичные суммы по ключу `shop_id`. Обе суммы одного магазина попадают в одну выходную партицию.
4. **Верхний HashAggregate.** Задача складывает частичные суммы. В результате у каждого магазина одна строка с выручкой.

Для `JOIN` выбор выглядит иначе. Например, небольшой справочник можно разослать на executors и выполнить `BroadcastHashJoin`. Для двух больших таблиц планировщик может выбрать `SortMergeJoin`. При выборе он учитывает условие соединения, доступную статистику, настройки и подсказки в запросе. [Стратегии соединения в Spark SQL](https://spark.apache.org/docs/4.1.1/sql-performance-tuning.html#optimizing-the-join-strategy)
