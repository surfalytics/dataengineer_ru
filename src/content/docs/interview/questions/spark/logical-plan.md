**Первый логический план SQL-запроса строит парсер на драйвере.** Анализатор Catalyst уточняет, к каким таблицам и колонкам обращается запрос. Затем оптимизатор Catalyst переписывает план, сохраняя результат. Для цепочки вызовов DataFrame план строится из самих операций API.

Допустим, считаем `SUM(amount)` по магазинам и берём только оплаченные заказы. В выводе `EXPLAIN EXTENDED` видны три версии одного дерева.

| Раздел вывода | Что в нём происходит |
| --- | --- |
| `Parsed Logical Plan` | Парсер проверил синтаксис SQL и разобрал `FROM`, `WHERE` и `GROUP BY`. Имя `orders` пока обозначено как `UnresolvedRelation`. |
| `Analyzed Logical Plan` | Анализатор находит `orders` в текущей сессии или каталоге, связывает `shop_id`, `status` и `amount` с колонками и проверяет типы. Опечатка в имени колонки обнаружится здесь. |
| `Optimized Logical Plan` | Оптимизатор оставляет фильтр рядом с чтением `orders`. После фильтра для группировки передаются только номер магазина и сумма заказа. |

**Куда можно перенести фильтр?** Если после группировки нужен только магазин № 7, условие по ключу `shop_id = 7` можно проверить ещё до подсчёта сумм. А условие `SUM(amount) > 1000` придётся проверить после группировки, когда сумма уже известна.

Spark старается отсеять строки как можно ближе к чтению. Если источник поддерживает условие, Spark может передать его самому источнику. В физическом плане чтения Parquet такие условия видны в `PushedFilters`. [Как посмотреть планы в Spark SQL](https://spark.apache.org/docs/4.1.1/sql-ref-syntax-qry-explain.html)
