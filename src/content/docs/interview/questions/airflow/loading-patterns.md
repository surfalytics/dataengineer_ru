## 1. SQL-курсор → Python-генератор → пакетный INSERT

Для переноса таблицы без тяжёлых преобразований можно открыть потоковый курсор и запрашивать по **10 000 строк**. Генератор отдаёт порцию в приёмник и только затем запрашивает следующую. В Python DB-API метод называется **`fetchmany(size)`**. В JDBC `fetchsize` — настройка количества строк, запрашиваемых за одно обращение к драйверу.

```python
def batches(cursor, size=10_000):
    while rows := cursor.fetchmany(size):
        yield rows

for rows in batches(source_cursor):
    target_cursor.executemany(insert_sql, rows)
```

Здесь `source_cursor` уже выполняет `SELECT` для своего диапазона, а `insert_sql` — параметризованный `INSERT`. Драйвер должен поддерживать потоковое чтение. Например, в Psycopg можно открыть **именованный серверный курсор**. Обычный клиентский курсор может заранее забуферизовать результат целиком, даже если потом вызывать `fetchmany`.

**Параллелизм и память настраиваются отдельно.** Разбейте месяц на дни через [генератор задач](/interview/questions/airflow/task-mapping/). Каждая задача читает свой полуоткрытый диапазон `[start, end)` и пишет в свою staging-партицию. При четырёх параллельных задачах нагрузку стоит оценивать примерно по четырём активным батчам плюс буферы драйверов. Больше задач может ускорить загрузку, но увеличит число соединений и суммарную память. После проверки загрузки опубликуйте партицию. Если фиксируете каждый батч отдельно, повтор диапазона должен безопасно заменить срез или устранить дубли. [Python DB-API](https://peps.python.org/pep-0249/#fetchmany) · [Курсоры Psycopg](https://www.psycopg.org/psycopg3/docs/advanced/cursors.html)

## 2. dlt — готовый загрузчик для API и БД

Подходит, когда основная работа — постранично забирать записи, нормализовать JSON и записывать данные в поддерживаемый приёмник. Например, ресурс заказов читает API с курсором `updated_at`, а назначение с поддержкой `merge` обновляет строки по `order_id`. Airflow запускает pipeline по расписанию. Для исторических диапазонов dlt поддерживает ограниченный интервал через `initial_value` и `end_value`. Так разные mapped tasks могут обработать независимые периоды, не двигая общий инкрементальный курсор друг другу. [Инкрементальная загрузка dlt](https://dlthub.com/docs/general-usage/incremental/cursor) · [Merge в dlt](https://dlthub.com/docs/general-usage/merge-loading)

## 3. Spark — распределённая обработка

Подходит, когда при переносе нужны большие соединения, агрегации или переразбиение данных. Airflow отправляет Spark-приложение, а работу между исполнителями распределяет Spark. При JDBC-чтении `numPartitions` ограничивает число параллельных подключений, `fetchsize` задаёт размер выборки за одно обращение. Границы `lowerBound` и `upperBound` рассчитывают шаг разбиения. Для выгрузки только за нужные даты добавьте явное условие `WHERE` в запрос к источнику. [JDBC в Spark](https://spark.apache.org/docs/latest/sql-data-sources-jdbc.html)

## 4. Отдельный pod — произвольный язык и окружение

Если загрузчик уже написан на Go или Rust либо требует нестандартных библиотек, упакуйте его в образ. `KubernetesPodOperator` передаст диапазон на вход, запустит контейнер с заданными CPU и памятью и отследит завершение. Например, Rust-парсер может потоково читать архив JSON и писать Parquet. Повторная попытка должна безопасно перезаписать результат своего диапазона. Pod задаёт окружение исполнения. Внутри него можно запустить и Python-генератор, и dlt. [KubernetesPodOperator](https://airflow.apache.org/docs/apache-airflow-providers-cncf-kubernetes/stable/operators.html)
