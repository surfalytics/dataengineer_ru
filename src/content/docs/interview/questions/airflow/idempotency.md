**Идемпотентная загрузка** при повторе одного и того же набора входных данных приводит приёмник к тому же состоянию. Это важно, когда данные уже записались, а задача упала до того, как Airflow отметил её успешной.

## Вариант 1. Перезагрузить известный период

| Шаблон Airflow | Что означает |
| --- | --- |
| `{{ ds }}` | Логическая дата запуска в формате `YYYY-MM-DD`. Удобна для имени файла или раздела, если совпадает с его календарём. |
| `{{ data_interval_start }}` | Начало интервала данных текущего запуска. |
| `{{ data_interval_end }}` | Конец интервала данных текущего запуска. |

Для суток с 4 на 5 марта используйте полуоткрытый диапазон `event_ts >= start AND event_ts < end` в согласованном часовом поясе. Полночь 5 марта попадёт в следующий интервал. В шаблонизируемом SQL Airflow подставляет Jinja-поля. В Python значения можно взять из контекста задачи и передать драйверу как SQL-параметры. Если `day` уже получен из контекста как Python-дата, выражение `f"event_date = '{day.isoformat()}'"` даёт фильтр на этот день. Для временных границ передача параметров драйверу сохраняет типы и избавляет от ручного форматирования.

**Повторная загрузка дня.** Подготовьте полный срез дня во временной таблице, проверьте его и замените целевую партицию. Если СУБД поддерживает транзакционную замену, очистку дня и вставку выполняют одной транзакцией. Иначе лучше опубликовать подготовленную партицию атомарной операцией движка. Если удалить вчерашний раздел, отдельно зафиксировать удаление и затем упасть, пользователь увидит пустой день.

Границы зависят от **timetable**. Для полного дня нужен timetable, который действительно задаёт суточный интервал. В Airflow 3 cron по умолчанию использует `CronTriggerTimetable`, у которого без заданной длительности границы совпадают. У запусков по событиям assets в 3.x может отсутствовать `ds`. [Шаблоны](https://airflow.apache.org/docs/apache-airflow/stable/templates-ref.html) · [Timetables](https://airflow.apache.org/docs/apache-airflow/stable/authoring-and-scheduling/timetable.html)

## Вариант 2. Хранить последнюю обработанную позицию

1. Прочитайте последнюю успешно загруженную границу (`watermark`), например из Airflow Variable. Для текущего пакета возьмите из источника максимум, например `SELECT MAX(change_id) FROM changes`, и зафиксируйте его как `high`. Для ключа, монотонного в порядке появления зафиксированных данных, выбирайте `old < key AND key <= high`.
2. Запишите пакет в приёмник, устраните повторы по устойчивому ключу события или версии и выполните **COMMIT**. Подойдут уникальный ключ с upsert или `MERGE` с корректно подготовленным источником.
3. **Только после COMMIT** сохраните обработанную верхнюю границу. Если задача упадёт между этими действиями, пакет придёт повторно. Дедупликация сделает повтор безопасным. Если продвинуть границу раньше, часть данных можно потерять.

**Когда одного MAX мало?** Несколько событий могут иметь один `updated_at`. Для стабильной постраничной выборки используйте составную позицию `(updated_at, id)`. Даже такая пара не спасёт от строки, которая зафиксировалась позже с более старым значением. Для запаздывающих событий выбирают перекрывающееся окно с дедупликацией либо CDC по позиции журнала. У обычного автоинкрементного ID порядок выдачи тоже может отличаться от порядка фиксации.

Если позицию обновляет только один DAG, простой вариант — одна Variable и `max_active_runs=1`. Если писателей несколько, нужна общая координация. Надёжный вариант — контрольная таблица в приёмнике, где позицию блокируют и фиксируют в той же транзакции, что данные.
